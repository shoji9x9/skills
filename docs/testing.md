# テストの書き方

テスト（`*.test.ts`）を書くときと直すときの規約。
テストする対象は、`scripts/`・`skills/`・private skill（`.agents/skills/<name>/` のうち `.private-skill` を持つもの）の下の実行するコードである。
テストのファイルは、どの対象のものも `scripts/` の下に置く。
`skills/` は利用者のリポジトリへ配布するので、そのテストは配布しない `scripts/skills/<name>/` に置く（置き場所は `AGENTS.md`「ディレクトリ構造」）。private skill のテストも `scripts/skills/<name>/` に置く。
テストは、利用者やほかのスクリプトから見える振る舞いを守るために書く。
内部の作りに依存したテストは、振る舞いを変えない書き換えのたびに直す必要がある。守るもののないテストは、保守の手間だけを増やす。

入力の状態の挙げ方と、チェックの処理で通す入力と落とす入力の決め方は、`.agents/rules/state-space-and-mutation-proof.md` にある。

## テストを書く対象

`scripts/`・`skills/`・private skill の下の実行するコード（`.ts`・`.mjs`・`.sh`）には、すべてテストを書く。
`.agents/skills/` のうち private skill でないものは `skills/` のインストール済みのコピーなので、原本の `skills/` で測る。
テストの無いファイルも、カバレッジの測定では 0% として数えるので、閾値を下回って失敗する（「カバレッジ」の節）。
テストで確かめられないファイルだけを、理由を付けて除外する。

次のものは、実行するロジックを持たないので、テストとカバレッジの対象にしない。

- ツールが読む設定（リポジトリの直下の `vitest.config.ts`・`oxlint.config.ts` などの `*.config.ts`）。そのツールの実行が確かめる
- 型の検査だけで使う宣言（`types/`）。`tsc` が確かめる
- eval の入力（`evals/*/fixtures/`）。eval とその fixture のチェック（`scripts/eval/`）が確かめる
- 種別の定義（`commit-types.ts`）。使う側との一致を `scripts/gates/code/commit-types-consistency.test.ts` が確かめる

この外に実行するロジックを置くときは、`scripts/`・`skills/`・private skill に移すか、この一覧と測定の対象（`scripts/coverage/run-coverage.ts`）を同じ変更で広げる。

次のときは、コードと同じ変更でテストを書く。

- 新しい CLI・関数・分岐を作ったとき。入力の状態（正常・境界・エラー・読めない入力）を挙げてから書く
- 不具合を直したとき。直す前のコードで失敗するテストを先に書き、直した後に通ることを確かめる
- 受け付ける入力を広げたとき・狭めたとき。新しく通る入力と、新しく落ちる入力を 1 件ずつ置く
- 検出・照合・集計・チェックの処理を書いたとき。加えてミューテーションテストの定義を書く（「ミューテーションテスト」の節）

設定や文書を読むチェックは、合成した入力（一時ディレクトリに作った最小のリポジトリ）でテストする。
リポジトリの実物の文書を読むテストは、内容が書き換わるたびに結果が変わる。そうしたテストは名前に「実リポジトリ」を含め、検出できることは合成した入力のテストで示す。

## テストの粒度

テストは、次の 2 つの粒度を組み合わせて書く。

| 粒度 | 確かめるもの | 書き方 |
| --- | --- | --- |
| CLI | 引数の読み方、終了コード、stdout・stderr、書き出すファイル | 子プロセスとして起動する。CLI ごとに、正常・判定の失敗・判定できない（終了コード 2 など）を最低 1 件ずつ置く |
| 関数 | 分岐ごとの入力と結果 | `main` か、公開された関数（ほかのモジュールが使う関数・入出力が仕様で決まる純粋な関数）を同じプロセスで呼ぶ |

分岐の細かい組み合わせは、関数の粒度で書く。子プロセスの起動は 1 回ごとに時間がかかり、ミューテーションテストは変異ごとにテストファイルを丸ごと実行するからである。
CLI の粒度は、引数から関数までのつなぎと、終了コードの取り決めを確かめる数件に絞る。

## 振る舞いを確かめる

テストが確かめるのは、公開された振る舞いである。このリポジトリでは、次のものを公開された振る舞いとして扱う。

- CLI の出力（stdout・stderr）と終了コード、書き出すファイル
- スクリプトやほかのスキルが読む取り決め（JSON のキー、決まった語彙、ファイルの置き場所）
- ほかのモジュールが import して使う関数の戻り値（`scripts/lib/` の関数など）
- 純粋な関数（引数だけで戻り値が決まり、ファイル・環境変数・時刻を読まない関数）の戻り値のうち、出力の一部と同じ意味を持つもの。
  例えば、CLI が出す領域の一覧・判定の結果・正規化した値である。
  その関数がテストのためだけに export されていても、`SKILL.md` がその関数を名前で挙げていなくても、これに当たる

次のものを確かめるテストは、内部の作りに依存している。公開された振る舞いを確かめる形に直す。

- 途中の状態。内部のデータ構造、途中で作る一時ファイル、ソースの文字列（`readFileSync` した実装への `toContain`）
- テストのためだけに export した関数の戻り値のうち、出力に現れない途中の形（内部の表、整形する前の中間の結果）
- 呼び出しの回数と順序（`toHaveBeenCalledTimes` など）。外部コマンドの起動のように外から見えるものは除く
- 仕様が決めていない出力の細部（エラーメッセージの全文、HTML の要素の並び）。取り決めになっている語や値だけを確かめる

純粋な関数を直接呼ぶテストは残してよい。CLI を通すと子プロセスの起動が増えてテストが遅くなり、分岐ごとの入力も作りにくいからである。
戻り値が出力のどの部分と同じ意味かを、テストの名前かコメントで分かるようにする。

関数の粒度のテストを CLI の粒度に書き換えるのは、戻り値が途中の形に当たるときだけにする。
テストの見直しを分担して任せるときは、この節を判断の基準として渡し、直すものにも残すものにも、この基準に照らした理由を記録させる。
受け取った側は、直したものと残したものの件数の比を確かめる。どちらかに偏っていれば、その側から数件を読んで、基準どおりかを確かめる。

## 期待値は仕様から決める

期待値は、仕様（`SKILL.md`・`references/`・Issue の受け入れ条件・出力の取り決め）から決めて、テストに直接書く。
実装が出した値を、そのまま期待値として貼り付けない。実装と同じ式で期待値を計算しない。
どちらも、実装が誤っていればテストも同じ誤りを期待値にするので、何も守らない。

仕様が決めていない値を期待値にしたくなったら、その値を仕様に書くか、確かめる範囲を仕様が決めている部分に絞る。

## 守るもののないテストを書かない

次のテストは、実装が誤っていても通るか、ほかのテストと同じことしか確かめない。書かず、見つけたら消す。

- assertion が無い、`expect(true)` のように常に成り立つ、空の配列への `for` や成り立たない `if` の中にだけ assertion がある
- 定数の配列の長さや中身だけを確かめていて、それを使う処理の振る舞いを確かめない
- 同じ入力の状態と同じ assertion を、ほかのテストが既に確かめている
- テストの中に書いた実装のコピーだけを呼んでいる

消すテストの名前が `*.mutations.json` の `expect_failing` から参照されているときは、同じ変異を検出するテストの名前に書き換えてから消す。
検出するテストがほかに無いなら、そのテストは守るものを持っているので消さない。

## 偽物（スタブ・モック・fixture）を使う場面

偽物は、テストの外にあるものとの境界にだけ使う。

- 使う: ネットワーク（`gh`・`curl`）、実ブラウザ、時刻、利用者の環境にあるとは限らないコマンド、外部のコマンドが失敗する・無い状態
- 使わない: このリポジトリのモジュール。モジュールを差し替えると、本物のつなぎ方を確かめなくなる。`vi.mock` は使わない
- mise と pnpm で版を固定したツール（`git`・`bash`・`shfmt`・`jq` など）は、偽物にせず本物を使う

偽物の作り方は、外から見える置き換え方を選ぶ。

- 外部コマンドは、一時ディレクトリにスタブのスクリプトを置き、`PATH` の前に足して起動する
- 起動するコマンドを環境変数で差し替えられる CLI は、その環境変数で渡す（`MUTATION_PROOF_TEST_COMMAND` など）
- 入っていないパッケージを読み込む CLI は、偽物のモジュールを `node --import` で子プロセスに読み込ませる

呼び出しの回数や引数を確かめてよいのは、それが外から見える振る舞い（外部のコマンドに渡す引数・API に送る内容）のときだけである。
偽物の出力は、実物を実行した記録から作る（`.agents/rules/state-space-and-mutation-proof.md`「外部ツールの出力をまねた偽物は、実測した記録から作り直す」）。
fixture も、原本（テンプレート・スキーマの文書・同梱の雛形）の形から作る（同じ rule の「4. fixture に持たせるもの」）。

## 実行環境を固定する

テストの結果は、実行する人の環境や順序で変わらないようにする。

- 書き込みは、`scripts/lib/testing/test-tmpdir.ts` の `makeTempDir`・`makeTempDirFactory` で作った一時ディレクトリの中だけで行う。リポジトリの tracked のファイルを書き換えない
- テストする処理が読む環境変数（`HOME`・`PATH`・`LC_ALL`・`CLAUDE_PROJECT_DIR` など）は、テストの中で一時ディレクトリかリポジトリの中を指す値に固定する。手元の `~/` の中身に結果を左右させない
- git の hook から実行すると、git がテストに `GIT_DIR` などを渡す。worktree からの push では、テストが一時ディレクトリで起動した git がそれを受け継ぎ、起動したリポジトリに commit や branch を書き込む。
  `scripts/lib/testing/vitest-git-env-setup.ts` が各テストファイルの前に `process.env` から外すので、子プロセスの環境は `process.env` から組み立てる。vitest の外で git を起動するランナーは、同じ変数を自分で外す
- ネットワークに接続しない。時刻に依存する処理は、時刻を引数や環境変数で渡せるようにして、固定した値でテストする
- 子プロセスの環境を明示した値だけで組み立てるときは、`coverageEnv()` を足す（「カバレッジ」の節）
- 子プロセスにはタイムアウトを付ける。付けないと、止まった子プロセスを待つテストは `vitest.config.ts` の `testTimeout` まで待ってから失敗し、原因が出力に残らない

## 並列実行

テストファイルは並列に実行する。分け方は `vitest.config.ts` が持つ。

- リポジトリの tracked のファイルを書き換えて戻すテスト（ミューテーションテストのランナーを実行するもの）は、`ISOLATED` に入れて単独で実行する
- テストの順序に頼らない。ファイルの中でも、前のテストが作った状態を後のテストで使わない
- 子プロセスの終了を待つテストが多いファイルは、`test.concurrent` で並べてよい。そのときは `scripts/lib/spawn-async.ts` の `spawnAsync` で起動し、一時ディレクトリは `makeTempDirFactory` で作る。
  並べたテストの間で、一時ディレクトリ・ロック・環境変数を共有しない。詳しい理由は `docs/tooling.md`「ミューテーションテスト（CI だけで実行）」にある

## カバレッジ

`pnpm run test:coverage`（`scripts/coverage/run-coverage.ts`）が、テスト全体をカバレッジ付きで実行し、ファイルごとの値を閾値と比べる。
lefthook の pre-push と CI の `Unit tests` で実行し、閾値を下回るファイルがあると失敗する。

- JavaScript・TypeScript は c8 で、行・分岐・関数を測る。テストが子プロセスとして起動した CLI の分も数える。
- シェルスクリプトは、テストが起動した bash の xtrace の記録から、実行した文の行を測る（`scripts/coverage/shell-coverage.ts`）。分岐と関数は測らない。
- 閾値は `scripts/coverage/coverage-thresholds.json` で、ディレクトリごとに決める。守る重さで分け、共有ライブラリの `scripts/lib/` を最も高くする。
  閾値はファイルごとに当てる。ディレクトリでまとめた値で比べると、よく測られたファイルが測られていないファイルを隠す。
- テストで測れないファイル（実ブラウザやネットワークが要るもの、利用者のリポジトリにコピーして使う雛形）は、`exclude` に理由を付けて書く。
  外部コマンドを偽物に差し替えて測れるものは、除外せずにテストを書く。

閾値を下回ったら、未実行の行や分岐に意味のある入力の状態（エラー・境界・読めない入力）を作り、仕様から期待値を決めてテストを足す。
数字を上げるためだけに、assertion の無い呼び出しを足さない。
カバレッジが示すのは、その行が実行されたことだけである。実行された行の結果をテストが確かめているかは、ミューテーションテストで確かめる。

テストを足しながら一部だけを測るときは、`--focus` と `--` を使う。

```bash
node scripts/coverage/run-coverage.ts --focus skills/kaizen/ -- scripts/skills/kaizen/
```

`--focus` で始まるファイルの値と、閾値を下回るものだけを出す。
シェルの未実行の行は、出力の最後に示すディレクトリの `shell-summary.json` に、JavaScript の未実行の行は同じディレクトリの `report/index.html` にある（GitHub Actions のジョブでは作らない）。

子プロセスの環境を明示した値だけで組み立てると、計測の環境変数（`NODE_V8_COVERAGE`・`BASH_ENV`・`SHELL_COVERAGE_DIR`）が子プロセスに渡らない。
渡らないと、その子プロセスの実行がカバレッジに数えられない。組み立てた環境に `scripts/lib/testing/coverage-env.ts` の `coverageEnv()` を足す。
スクリプトを一時ディレクトリにコピーして実行するテストは、内容が原本と同じなら原本の実行として数える。書き換えたコピーは数えない。

## ミューテーションテスト

### 目的

テストが通っても、そのテストが誤りを検出できる証拠にはならない。
入力が判定の分岐まで届いていないテストや、assertion がゆるいテストも通るので、通った結果だけでは区別できない。
ミューテーションテストは、実装をわざと誤らせ、狙ったテストが失敗することで、そのテストが機能していることを示す。

### 方法

対象のコードの 1 か所を小さく書き換え（変異）、宣言したテスト（`expect_failing`）が失敗することを確かめる。
`scripts/mutation/check-mutation-proof.ts` が、変異ごとに対象のテストファイルを 1 回実行し、元の内容に戻す。
次のどれかに当たる変異は失敗にする。

- テストが全部通る（その変異を検出できない）
- 置換が当たらない（`find` の出現数が宣言と違う、置換しても内容が変わらない）
- 宣言した以外のテストまで失敗する（前段の規則や起動の失敗で落ちていて、狙った判定を確かめていない）

### 定義を作る対象

ミューテーションテストの定義は、すべてのテストには作らない。テストが誤りを見逃したときの影響が大きい判定に作る。

- 作る: 検出・照合・集計・チェックの処理で、合否・分類・終了コードを決める分岐。pre-commit・CI のチェック（`scripts/gates/`）、Hook（`scripts/hooks/`）、配布スキルのチェック（`skills/*/scripts/*-check.*`）が当たる
- 判定の行ごとに、その判定だけを無効にする変異を 1 つ以上宣言する。通す側の判定（免除・緩和）を無効にする変異も宣言する
- 作らない: 判定を持たない変換・表示・入出力だけのコード。カバレッジの閾値と、仕様から決めた期待値のテストで守る

### 定義の書き方

定義は、テストと同じディレクトリの `<テスト名>.mutations.json` に置く。
`test_file` に対象のテストファイルを書き、`mutations` に変異を並べる。変異の各項目の意味は次のとおりである。

| キー | 意味 |
| --- | --- |
| `id` | 変異の名前。定義ファイルの中で一意にする。`--only` で選ぶときに使う |
| `why` | その変異が無効にする判定。何を壊すと何が見逃されるかを 1 文で書く |
| `file` | 書き換えるファイル（リポジトリからのパス） |
| `find` | 書き換える前の文字列。整形した後のファイルから、そのままコピーする |
| `replace` | 書き換えた後の文字列。判定だけを無効にする最小の書き換え（式を `false` にする、比較を常に真にする）にする |
| `occurrences` | `find` の出現数。省くと 1 になる。出現数がこの値と違えば、置換が当たらないとして失敗にする |
| `expect_failing` | 失敗するはずのテストの名前の一覧。この一覧の外のテストが失敗しても、その変異は失敗にする |

### 限界

すべての変異で狙ったテストが失敗しても、示せるのは、書いたテストが変異させた判定まで届いていることだけである。
書かなかった入力の状態と、変異を宣言しなかった判定は、どの変異でも検出されないので見えない。
入力の状態を挙げるのは、テストを書く前に行う（`.agents/rules/state-space-and-mutation-proof.md`）。
宣言していない判定のうちテストが届いていない行は、カバレッジで見つける。

### 変異を自動で作るツール（Stryker）との分担

変異を宣言する仕組みは、人が挙げた判定しか確かめない。Stryker はすべての行に変異を自動で作るので、宣言し忘れた判定やテストの弱い箇所も見つけられる。
ただし、合否の決め方が違うので、宣言した変異の代わりにはしない。
Stryker は、どれかのテストが落ちれば検出として数え、狙ったテストが落ちたかを確かめない。対象も JavaScript と TypeScript だけで、シェルの判定を確かめられない。

Stryker を使うなら、合否を決めずに、生き残った変異を報告する用途にする。このリポジトリで実行するには、次の対応が要る。

- 変異を入れないファイルを書き換えない設定（`disableTypeChecks: false`）と、作業用のファイルを `.gitignore` の対象に置く設定（`tempDirName`）。
  無いと、未追跡のファイルを走査するチェックのテストが、Stryker のバックアップを拾って失敗する
- 変異の番号とカバレッジを子プロセスに渡す setup ファイル。vitest のランナーは番号をワーカーの中にしか置かないので、CLI を子プロセスで起動するテストでは変異が有効にならない
- ワーカースレッドで動かないテスト（`process.chdir` を使うもの）と、変異を入れたファイルの中身を読むテストの除外

変異の結果の読み違え方と、テストが機能していることの示し方は、`.agents/rules/state-space-and-mutation-proof.md`「5. テストが機能していることの示し方」にある。
PR と週次の実行の分け方・シャード・実行中に守ることは、`docs/tooling.md`「ミューテーションテスト（CI だけで実行）」にある。
