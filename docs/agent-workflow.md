# 作業の原則

`AGENTS.md`「ワークフロー」の各箇条の理由と実例を置く。
節は `AGENTS.md` の小見出し（確かめ方・シェルの書き方・外向きの操作と破壊的な操作・編集）に合わせて分ける。

## 確かめ方

### ファイル・パス・ツールの挙動は、述べる前に確かめる

ファイル・パス・成果物・ツールの挙動・実行環境について述べる前に、Read・grep・実行で確かめる。記憶や一般論で言い切らない。
自明に見える 1 行ほど、確かめるのを省きやすい。

### 規約を満たすかは、その規約をチェックするツールで確かめる

文字数・バイト数・書式のように数えれば分かる規約ほど、自分で近似のスクリプト（`awk 'length > N'` など）を書きやすい。
しかし、単位（バイト・文字・表示幅）はチェックするツールごとに違い、近似のスクリプトは誤検知も見逃しも出す。
commit message は `pnpm exec commitlint --edit <file>` で、Markdown は `pnpm exec markdownlint-cli2 <path>` で確かめる。

### 検証は目的を果たす最小の範囲で実行する

目的より広い一括実行（例: `lefthook run pre-commit --all-files`）は、自動修正や `stage_fixed` による staging などの副作用を伴う。
絞り込み方が分からなければ、範囲を広げる前に `--help` などで調べる。
広い範囲で実行したら、直後に `git status --short` で意図しない変更がないかを確かめ、あれば戻す。

### 「該当なし」を根拠にするチェックは、検出できることを先に確かめる

遮断・除外・フィルタ・シークレットの走査・差分が 0 件という判定では、「本当に無い」と「チェックが動いていない」が同じ出力になる。
そこで、既知の目印を遮断・除外の対象の外に置き、検出されることを確かめてから使う。対象の中に置いて確かめても、何も示せない。
打ち切り（`timeout`）と 0 以外の終了は、合格として扱わずに失敗にする。時間の上限は、実測した所要時間から決める。

件数が 0 でないことも、検出できる証拠にはならない。
誤検知だけが並び、狙った違反を 1 件も拾わない走査でも、出力が 0 件でないので動いているように見える。
そのため、確かめるのは「何か出るか」ではなく「狙ったパターンが出るか」である。修正済みのものを確かめるなら、修正前の版を入力にする。
横断の範囲を確かめるために書く使い捨ての grep やスクリプトも、同じように確かめる。
除外の処理（フェンス・コメントなど）を持つ走査は、除外の中と外の両方に狙ったパターンを置き、区別できることまで確かめる。

### 集合を答えにするチェックと、0 件で何もしない一括処理は、検出できることと件数を確かめる

既知の要素が検出されることを確かめ、総数と突き合わせる。構造化された形式を列挙するときは、実際のパーサを使う。
対象が 0 件のときは成功として扱わず、対象と処理した件数を絶対パスで出す。

### 回帰だという指摘は、旧版と現行版を同じ条件で確かめる

「常に失敗する」というレビューの指摘は、適用する前に、使い捨ての環境で再現して確かめる。

回帰（「この変更で動かなくなった」「以前は動いていた」）は、2 つの版についての主張である。旧版と現行版を同じ条件で測る。
旧版は `git show <base>:<path>` で取り出し、同じ入力・同じ環境変数で実行する。現行版だけで再現しても、「動かなくなった」と「元から動いていない」が同じ出力になる。
差が出なければ回帰ではないので、修正を当てない。代わりに、なぜ元から成り立っていないかをコードの 1 か所に書いておく。書いておかないと、次のレビューが同じ指摘をまた出す。

両方の版で 0 件なら、測定が動いていない場合と区別できない。成り立つはずの構成（通常の構成など）を同じ手順で測り、観測できることを示す。

指摘を却下・保留するときも、同じように確かめる。確かめるのは、以前通っていた入力が失敗するようになるかである。
他のコンポーネントとの対称性（「B は前からそうだった」）は、A を新たに失敗させてよい根拠にならない。
保留すると決めた場合も、その形を再現するテストは同じ変更に入れる。

修正が安いことを、着手する順番の根拠にしない。8 行の修正でも、事実でない前提を書いたコメントが一緒に入る。

### 新しく作った分岐と、新しく受け付ける入力は、その状態を作って確かめる

既知の違反が検出されることを確かめても、測れるのは報告された欠陥だけである。そこで、入力がとりうる状態を列挙して確かめる。
候補を探す処理なら 0 件・1 件・複数件を、表記の揺れなら引用符・空白・改行・引数の有無を挙げる。
あいまいな入力を、警告なしに先に見つかったもので決めない。

### 等しいかを比べる処理を正規化で直すときは、ずれうる軸をすべて挙げる

片方だけ、あるいは 1 つの軸だけを正規化すると、別の軸や別のオプションが有効になったときに同じ不具合に戻る。
例えば Node の `--preserve-symlinks-main` では `import.meta.url` もシンボリックリンクを解決しないので、`process.argv[1]` の側だけを realpath しても一致しない。
正規化に失敗したときの処理を、直そうとしている不具合（警告なしに成功として扱う）と同じ振る舞いにしない。

### 階層で合わさる設定に依存する検証は、有効な設定の出所を先に一覧にする

mise・git・npm などの設定は、階層で合わさる。`mise config ls` などで、どの階層の設定が有効かを切り分けてから原因を判断する。
ユーザーのグローバル設定はリポジトリの外にあるので、手元での失敗が CI と食い違う。
下位の範囲を対象にする一括操作（`mise lock --global` など）は、上位の設定が無いディレクトリから実行し、その範囲の場所で検証し直す。
上位に同じ名前の項目があると、下位の項目が隠れて取りこぼす。

### ツールが欠けた環境のチェックは、意図した分岐に達した証拠まで確かめる

終了コードだけでなく、区別できる stderr などで理由を確かめる。取り除く依存は、チェックの対象だけにする。

同梱物を相対パスで読むコンポーネントは、元の場所で検証する。
1 ファイルだけを別のディレクトリにコピーして実行すると、共通ライブラリが見つからず、警告なしに機能を減らして動く。そうなると、検証しているものが別のものにすり替わる。
コピーするなら、ディレクトリ一式をコピーする。
機能を減らして動く実装には、その実行と本番の構成での実行を出力で区別できる 1 行を出させる。

## シェルの書き方

### パイプでつないだ検証の成否は、対象のコマンドの終了コードで判定する

パイプで出力を整形する検証の成否は、`${PIPESTATUS[0]}` か `set -o pipefail` で取る。末尾の `$?` は、パイプの最後のコマンドの終了コードである。

表示した終了コードは、必ず主張として読まれる。判定に使わないなら表示しない。
`cmd | tail -5; echo "exit=$?"` の `0` は `tail` のもので、添えたつもりの表示が誤った合格の報告になる。
出力を絞りたいときは、`cmd >out 2>&1 || rc=$?` で分けてから `tail out` する。

### バッククォートや `$` を含む本文は、quoted heredoc で渡す

本文は、二重引用符の `-c` ではなく quoted heredoc（`<<'PY'`）でインタプリタに渡す。
二重引用符の中のバッククォートは、シェルがコマンド置換として解釈して失敗する。Markdown のコードフェンス・正規表現・テンプレート文字列でよく起きる。
検証のコマンドに、書きかけの試しの断片を残さない。原因が重なって読めなくなる。失敗した検証は実行していないのと同じなので、別の方法で確かめ直す。

### 終了コードを決める最後の位置に、条件式を置かない

`done; [ $n -ge 30 ] && echo ...` や `[ $i -lt 3 ] && sleep 20` は、成功したのに 0 以外で終わる。呼び出し側（Monitor・Hook・`set -e`）は、それを失敗として扱う。
`if ... then ... fi` で書くか、最後を `true` か `:` で終える。出力だけを見ると成功に見えるので、気付きにくい。
待つ処理は、前景の Bash のループに置かない。ツールのタイムアウトで止められる。完了したら終わる背景のコマンドか、監視ツールに任せる。

### 結果として期待される 0 以外の終了コードを、呼び出し全体の終了コードにしない

`grep` の該当なしや KEDB の照合の一致なしのように、終了コードが状態を表すコマンドは、直後に値を保存する。
そして `case` か `if` で、正常な分岐を 0 に、仕様外の値やチェックの失敗だけを 0 以外にする。
期待される 0 以外を最後のコマンドのまま残すと、判定そのものは成功していても、ツールのエラーとして記録される。
すると、Kaizen の候補・監視・後の成否判定に誤った記録が残る。

保存した状態の変数は、比べる前に、空でないことと期待した型であることを確かめる。代入した名前と参照する名前は、同じ短いブロックの中で突き合わせる。
別の名前を参照して空の値を数値の比較に渡すと、チェックの対象ではなく、包んでいるスクリプト自身のエラーを繰り返す。
1 回取得すれば足りる状態の確認を shell のループに広げず、取得した結果を呼び出し側で判定する。

実行の構成によって有無が変わる成果物の確認も、この位置に置かない。
`cat` や `ls` を終了コードを決める位置に置く前に、在ることを確かめるか、`[ -f ]` で分岐する。
成果物の一覧が構成で変わらないことを確かめずに両方の構成に同じ確認を当てると、本体が成功していてもツールのエラーになる。

### 背景で起動するコマンドは、失敗が終了コードに残る形で書く

`|| echo "exit $?"` のように失敗を握りつぶすと、起動そのものが途中で終わっても、完了の通知が exit 0 になる。
1 つもコマンドを実行していないのに、「実行した」と報告することになる。
入力に原本があるなら、セッションの間だけ残る一時ファイルにコピーせず、原本から読む。scratchpad は、セッションを再開するとパスごと消える。
起動する前に、入力が空でないこと（`[ -n "$VAR" ]`）を確かめる。

背景で起動する子プロセスの stdin は、`</dev/null` にする。引数で入力を渡していても、stdin も読む CLI は珍しくない。
対話の TTY ではすぐ EOF になるので表に出ず、非対話や背景の実行でだけ待ち続ける。

### 止まって見える子プロセスは、何を待っているかを確かめてから扱う

経過時間で判断しない。プロセスが在るか（`pgrep`）は「動いているか」にしか答えず、待っているのか処理しているのかを区別しない。
最初に stderr の最終行と出力のサイズを見て、何を待っているかを確かめてから、待つ・止める・直すを選ぶ。
出力が 0 バイトのまま応答しないなら、処理中よりも入力待ちを疑う。

### 背景の処理が動いているかは、プロセスの有無で判断する

出力ファイルでは判断しない。再起動する前や出力先を消す前に、前のプロセスを確かめる。
同じ処理を重ねて動かしたり、書き込み中のファイルを消したりするのを避けるためである。

### 外部プロセスを動かすツールは、本番と同じ呼び出しで先に小さく試す

ブラウザ・CLI・サーバのような外部プロセスを動かすツールを書く前に、本体が使う機能を、本体と同じ方法・同じ呼び出しで小さく試して測る。
別の方法で確かめても、本体の方法で動くことは保証されない。`Page.setDocumentContent` で確かめて `Page.navigate` で書いたところ、そこで応答しなくなった例がある。
本体では全体を 1 つのタイムアウトでまとめず、呼び出しごとにタイムアウトを設定する。
どの呼び出しかを示す stderr をファイルに出し、止まった位置が出力に残るようにする。

### ファイルを移動して索引を作り直す `set -e` のスクリプトは、何度実行しても同じ結果にする

すでに目的の状態にある入力（同じディレクトリへの `mv` など）は、明示的に飛ばす。
飛ばさないと、何もしない操作で `set -e` が止まり、最後の後片付けや索引の作り直しまで進まない。
最後まで進むことが重要なら、`trap '...' EXIT` を検討する。

### ID・完全な SHA・長い prompt・名前は、構造化された出力から取得して渡す

opaque な ID・完全な SHA・長い prompt を、表示された結果から手で書き写したり補ったりしない。
JSON・API の応答・`git rev-parse` などの構造化された出力から、それを使う同じ呼び出しの中で取得する。
空でないこと・形式・比べる相手との一致を確かめてから渡す。短い SHA の残りを推測すると別の commit を指し、prompt が 1 字違うと別の eval の入力になる。
stdin も読む CLI を非対話で起動するときは `</dev/null` を付け、引数以外から入力が入らないようにする。

名前で呼ぶ識別子（npm スクリプト名・ツール名・タスク名・スキル名）も、同じように扱う。
意味のある単語でも記憶から組み立てず、原本（`package.json` の `scripts`、使えるツールの一覧）を読んでから呼ぶ。

決まった形の呼び出しを繰り返すときは、変わる部分（ID・番号・SHA）を、毎回その場で取得した出力から埋める。
同じ形を繰り返すほど出所の確認を省きやすく、前の回のコマンドをコピーして、変わる部分だけを書き換える形になる。

SHA で対応づけるポーリング（commit・review・check-run）では、ツールの呼び出しごとに、完全な SHA を構造化された応答から取得する。
形式と、対象の現在の HEAD との一致を確かめてから、同じ呼び出しの API に渡す。
「最初に完全な SHA を確かめた」ことと「毎回のポーリングが原本から取得する」ことは別である。
表示された短い SHA を変数の初期値・フィルタの文字列・URL に手で入れると、存在しない SHA になり、常に 0 件か 422 が返る。
0 件を結論にする前に、その SHA で commit か check-suites を取得できることを確かめる。422 や対象の不一致を、「レビューなし」として扱わない。

### 制限付きの sandbox で子プロセスの起動が `EPERM` になったら、sandbox の外で実行する

待ったり再試行したりせず、承認を得て sandbox の外で実行する方法に切り替える。

## 外向きの操作と破壊的な操作

### 本文を伴う外向きの操作は、本文を先にファイルに書いて渡す

渡すフラグは、コマンドごとに違う。`gh pr` と `gh issue` は `--body-file <path>` を、`gh api` は `-F body=@<path>` か `--input <path>` を使う。
`gh api` に `--body-file` は無く、unknown flag で失敗する。
失敗したら、実行し直す前に、途中まで作られたものがないかを確かめる。在れば、新しく作らずに足りない分を補う。

### 順序のある外向きの操作は、`&&` でつなぐ

前の操作が失敗したら、後の操作が実行されない形にする（`reply && resolve`）。
ループで回すときは特に重要である。1 件失敗しても次の反復に進むので、失敗を見逃すと、返信の無いまま解決済みのスレッドのような食い違った状態だけが残る。

取り消せない操作の引数を、その操作と同じコマンドの中のコマンド置換で作らない。別のコマンドで先に取得し、空でないことを確かめてから渡す。
確認を `||` やフォールバックに置かない。引数の出所が不確かなら、先に確認して値を決めてから、本番の外向きの操作に進む（`id=$(...); [ -n "$id" ] && gh api .../$id/...`）。
フォールバックに置くと、不確かだと分かったまま本番を先に実行することになり、外向きの副作用が先に起きる。

### 破壊的な操作は、許可リストで対象を決め、対象と件数を確かめてから実行する

破壊のフラグを付けずに実行して、対象と件数を確かめてから、フラグを付けて実行する。
絞り込みの条件を削って実行し直すときは、破壊のフラグも外し、この確認の手順が残っていることを確かめる。

### プロセスは、起動時に保存した PID で終了させる

プロセスの終了（`pkill`・`killall`）も、破壊的な操作として扱う。自分で起動したプロセスは、起動時に PID を保存して `kill "$PID"` で終了させる。
起動と後片付けが別のツールの呼び出しに分かれるなら、PID をファイルに残して `kill "$(cat <file>)"` で終了させる。
変数はツールの呼び出しをまたいで残らないので、後片付けの段でパターンによる指定に戻りやすい。
パターンで指定するのは PID を持っていないときだけにし、その前に `pgrep -af <pattern>` で対象と件数を確かめる。

`pkill -f` が照合するのはコマンドライン全体なので、そのコマンドを実行している自分のシェルにも一致する。
症状は 0 以外の終了だけで、対象が終了したのか自分が終了したのかを、出力から読めない。
自分の呼び出しが一致しない形（`[d]ump-dom` など）にするか、PID の指定に切り替える。

## 編集

### 文字列の一致で編集するときは、置換元を直前に読んだ内容からそのまま使う

Edit の `old_string` も、`python`・`perl` などのスクリプトによる置換も同じである。
一致しなかったら、目で見て調整して再試行せず、対象を読み直すか、行番号による置換に切り替える。
フォーマッタ（`oxfmt` など）を通した後は、特に注意する。自分が書いた文字列も整形で折り返し・引用符・空白が変わっていて、記憶から組み立てた置換元は一致しない。
整形を挟んだら、置換の前に読み直す。

### 複数の置換をまとめたスクリプトは、置換ごとにファイルに書き戻す

各置換の直後に `p.write_text(s)` を置く。途中で失敗しても成功した分は残り、再実行は残りだけで済む。
最後に 1 回だけ書き込んでよいのは、途中の状態がファイルとして不正になるなど、全件を 1 つの単位として扱う必要がある場合だけである。そのときは理由を 1 行書く。
各 `assert` には、どの置換かが分かるラベルを付ける（`assert s.count(old) == 1, '<置換名>'`）。
行番号だけの AssertionError では、どの置換が古いのかを、スクリプトを読み返すまで特定できない。
「今回は一致するだろう」と考えて、書き戻す単位を粗くしない。

### 網羅を求める指示を受けたら、どう解釈するかを 1 行で述べてから始める

「すべて」「全件」のような指示を受けたら、例えば「全件を検討し、妥当なものは直し、不要と判断したものは根拠を残して直さない」のように述べる。
機械的に当てはめるのではないことと、判断をどう残すかを明らかにする。
判断が分かれうる指示ほど、述べる手間は小さく、途中で訂正が入る手間は大きい。

## エージェントの自己設定編集

エージェントは、自分の設定ファイルを編集できないことがある。
kaizen の Hook のセットアップなど、設定ファイルを書き換える作業で止められたら、適用する内容を一時ファイルに書き出し、ユーザーに `! cp <tmp> <設定ファイル>` などで適用してもらう。

止められないこともある。止められるかは版と権限モードで変わるので、権限やチェックを緩める設定の変更は、止められるかどうかに関わらず人に確認する。
次の表の可否は前提にせず、その場で測った結果を優先する。

| エージェント | 設定ファイル | 編集できるか |
| --- | --- | --- |
| Claude Code | `.claude/settings.json` と `~/.claude/settings.json` | 版と権限モードで変わるので、前提にせず測る。ある版で `defaultMode: auto` のとき、確認なしで両方を書けた。1 つの環境で 1 回測っただけなので、「できる」の側にも一般化しない |
| Codex | `.codex/config.toml`、hooks | できる。ただし、credentials・auth・profile などの上書きは制限される |
| GitHub Copilot | `.github/agents/`（指示） | できない（必ず止められる） |
| GitHub Copilot | `.github/hooks/`（Hook） | できる。手動で承認する設定を勧める |
