# 文章の書き方

人が読んで分かる文章にするための規約。
AI が書いた文章には、英語を直訳したような言い回し、日本のエンジニアが使わない語、装飾の多さが繰り返し現れる。
エージェントが文章を書くときも、人が書くときも、この規約に従う。

## 対象

- 人が読む Markdown
  - `AGENTS.md`、`README.md`、`docs/`、`.agents/rules/`
  - `skills/` の文書と、private skill（`.agents/skills/<name>/` のうち `.private-skill` を持つもの）の文書
  - `evals/` の README と fixtures、`.kaizen/` の学び
- コードコメント（設定ファイルのコメントを含む）
- スクリプトが利用者に表示するメッセージ
- エージェントが人へ返す応答

次のものは対象にしない。

- `SKILL.md` の `description`。エージェントがスキルを選ぶための文で、言い換えると呼び出しの精度が変わる
- `.kaizen/archive/` の学びと `tests/` の結果。過去の記録として書き換えない
- インストール済みのスキルのコピー（`.agents/skills/<name>/`）とエージェント用のリンク（`.claude/`）。`skills/` と同じ中身なので、`skills/` を直す

スクリプトが解析する見出し・列名や、eval の assertion が依存する節名を変えると、スクリプトや eval が動かなくなる。
これらに当たる変更は、そのつど人に確認してから行う。

## 規則

### 1. 行為者を主語にする

物を主語にして比喩の動詞で受ける書き方をやめ、誰が何をするかを書く。

<!-- textlint-disable -->
- 悪い例: 古い宣言が残ると、範囲を狭めても静かに通る。
<!-- textlint-enable -->
- 良い例: 古い宣言が残っていると、範囲を狭めてもチェックはエラーを出さない。

### 2. 比喩の動詞・名詞を使わない

<!-- textlint-disable -->

「倒す」「化ける」「写す」「配線」のような比喩は、何が起きるかを具体的に書く。

<!-- textlint-enable -->
使わない語と言い換え先は `.textlint/words.json` の各エントリの `message` に書いてある。

<!-- textlint-disable -->
- 悪い例: 判定不能を合格に倒さない。
<!-- textlint-enable -->
- 良い例: 判定できないときは合格として扱わない。

### 3. 名詞を「の」で連ねない

名詞を 3 つ以上「の」でつなげたり、漢字を長く連ねたりせず、動詞と助詞で書き直す。

<!-- textlint-disable -->
- 悪い例: 保守性担保機能の形骸化の防止
<!-- textlint-enable -->
- 良い例: 保守性を守る仕組みが使われなくなるのを防ぐ

### 4. 太字と箇条書きを絞る

太字は、読み飛ばされると困る 1 か所だけに使う。1 段落に 2 か所以上置かない。
箇条書きの各項目を `**見出し**:` で始めない。項目に見出しが要るなら、節を分けるか表にする。
理由や条件のつながりがある内容は、箇条書きにせず文章で書く。

### 5. 否定と対比で演出しない

「A ではなく B」「——」でつないだ強調は、言いたいことが B だけなら B だけを書く。
対比そのものに意味があるときだけ残す。

- 悪い例: 終了コードではなく、狙った assertion が落ちたことで判定する——終了コードは起動失敗でも非 0 になる。
- 良い例: 狙った assertion が落ちたことで判定する。終了コードは起動に失敗したときも 0 以外になるので、判定に使えない。

### 6. 文末のコロンで続けない

「次のとおり:」「実行する:」のように文をコロンで終えてリストやコードを続けない。「次のとおりである。」のように文を閉じる。

### 7. 一文を短くする

一文は 150 字以内にし、1 つの文で 1 つのことを言う。
括弧の中に括弧を入れない。補足が長くなるなら、括弧に入れず次の文にする。

### 8. 馴染みのない語・横文字を使わない

日本のエンジニアが普段使わない語は、普段使う語に言い換える。言い換え先は `.textlint/words.json` にある。
英語のまま書くのは、コマンド名・設定キー・製品名のように、そのまま書かないと伝わらないものに限る。
このリポジトリで決めた用語を使うときは、最初に出てくる箇所で意味を書く。

### 9. 状態を書かない

作成日、「現状は」「当面」「〇〇時点」のように、時間がたつと正しくなくなる記述を書かない。
期限や前提がある記述は、条件の形で書く（例: 「dependabot-core#15904 が解決するまで」）。
途中経過や判断の記録は Issue・PR・`.kaizen/` に追記していく。`.kaizen/` の学びは記録なので、この規則は当てない。

## 書き換えで変えないもの

既にある文書をこの規約に合わせて書き換えるときは、書き方だけを変え、次のものは変えない。
規則 2・7・8 を当てると、これらを一般の言い回しに開いたり、離れた箇所に分けたりしやすい。変わっても警告は出ず、エージェントの振る舞いだけが変わる。

- 定義のある語（帰属不明・偽陰性など）は言い換えない。初めて読む人向けの説明を足すなら、括弧で添える。
- スクリプト・テンプレート・他の文書が読む固定の語彙（台帳の方針の値、判定の値など）は、本文でも同じ字面で書く。
- 条件・例外・承認は、それが掛かる動作と同じ文か同じ箇条に置く。長い段落を箇条に分けるときに、別の箇条へ離さない。
- 読み飛ばされると困る 1 か所の太字は外さない（規則 4）。

配布スキルのうちエージェントが読む文書（`SKILL.md`・`references/`・`assets/`）を書き換えたら、eval の入力が変わっていなくても、そのスキルの eval を `with_skill` で実行する。
前回から下がったものは、書き換え前の版と同じ条件で比べる。コメントの行だけを変えたとき（スクリプトや `assets/` の設定ファイルのコメントなど）は対象にしない。

## 機械的なチェック

規則 2・4・6・7・8 の一部は `scripts/gates/lint-prose.js` が textlint でチェックする（pre-commit と CI）。
設定は `.textlintrc.json`、使わない語の一覧は `.textlint/words.json` に置く。

- 書き換えがまだ済んでいないファイルは `scripts/gates/prose-lint-pending.json` に載っていて、指摘を数えない。
  ファイルを書き換えて指摘が 0 件になったら、一覧から外す。
- 語を一覧に足すときは、言い換え先を `message` に、検出されることを確かめる文を `example` に書く。
  `scripts/gates/lint-prose.test.js` が全エントリの `example` で検出されることを確かめる。
- 図の線のように字義どおりの意味で使う語は、その箇所だけ `<!-- textlint-disable -->` で除外する。

規則 1・3・5・9 は機械では判定しきれない。書いた人とレビューする人が確かめる。

人への応答はファイルではないので、textlint ではチェックできない。
代わりに、使わない語の一覧 `.textlint/word-list.md` を `AGENTS.md` から `@` で取り込み、Claude Code がセッション開始時に読み込むようにしている。
`@` での取り込みは Claude Code だけが処理するので、他のエージェントには `AGENTS.md` の文で一覧を開くよう指示している。
この一覧は `.textlint/words.json` の `term` と `instead` から `scripts/gates/check-word-list.js --fix` で生成し、一致をチェックしている。
