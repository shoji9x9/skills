## 対象と結果（Issue #211 横断 API 参照テーブルの読み取り）

eval 12（新規）は「対象テーブルの参照元に**横断 API の参照テーブル列**を含めるか」「その欄が**空欄**のときどう扱うか」を見る。
`db` モードのフェーズ A は使い捨てプロジェクトでは step 1 の接続確認で止まりデータ設計へ到達しないため、実行させず**問いの形**にして到達性を確保した（fixture 無し）。
既存 eval 1–11 は本変更で挙動が変わらないため再測していない。**各 configuration 1 run のみ**で run 間分散は測っていない。

- **with_skill 4/4**: 対象テーブルは 3 つの表（機能一覧のテーブル列・横断 API とバッチの参照テーブル列）に分散していて 3 つとも読む、と明示。
  `db-context` の空欄を「参照テーブル無し」と断定せず `replace-strategy` 側の記録漏れとして扱い、
  **「4 つ目の括りが埋まるまで対象集合は確定しない」**と保留。次の一歩に「欄を埋める（無ければ `-` と明記する）」を挙げた。推測でテーブル名を足していない
- **without_skill 2/4**: 空欄を**「fan-out 先の参照テーブルを継承する」と読み替え**、「`db-context` は新しいテーブルを追加しない」と結論して
  **対象を 3 テーブルに確定**（「この点はフェーズ A の判断に影響しません」）。後段で「単に未記入かもしれない」と可能性は挙げたが、任意の追加確認に留まった

## 弁別性の所見

- **弁別したのは assertion 1（3 表を参照元にする）と assertion 3（確定を保留する）の 2 本**。baseline の「継承」という読み替えは、
  横断 API 専用テーブルが存在する実ケース（Issue #211 の報告事例）でそのまま取りこぼしになる。この eval が捕まえたい故障そのもの
- **assertion 2（記録漏れの可能性の指摘）は両 config で pass** し弁別しなかった。baseline も末尾で未記入の可能性に触れたため。
  ただし baseline はそれを結論に反映せず確定させたので、**確定を保留するか**を見る assertion 3 のほうが弁別力を持つ。assertion 2 は後退検知用として残す
- **assertion 4（推測でテーブルを足さない）も両 config で pass**。プロンプトが列挙済みの材料しか与えていないため、baseline も足しようがない。後退検知用
- トークン・時間は両 config でほぼ同等（119k / 124k、41.5s / 45.9s）。問い形式で実行を伴わないため差が出ない
- 1 run のため flaky 判定はできない。assertion 3 は「確定するか保留するか」の二択で揺れうるため、疑わしくなった時点で再測する
