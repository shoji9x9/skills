# 学び抽出ガイド

## モード

| モード | 起動のきっかけ | 対象 | 抽出件数 |
|--------|---------|------|---------|
| `--all` | 手動のみ | 全セッション | 制限なし（優先度順に提示） |
| `--current`（デフォルト） | 手動 / コミット前の PreToolUse のチェック | 最新のセッション（実行中のものを含む） | 最重要の 1 件 |

`--record-pending` は、`extract --current` の対話をしない限定のモードである。オーケストレーションのスキルが commit 前のチェックを無人で通るために、最重要の候補を最大 1 件だけ `status: pending` で記録する。
`--all`、apply、archive、delete、setup と組み合わせた指定は、何も変える前に拒否する。

## セッションログの場所

| エージェント | ログの場所 | 形式 |
|-----------|----------|------|
| Claude Code | `~/.claude/projects/<hash>/*.jsonl` | JSONL |
| Codex | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` | JSONL |
| Copilot | `~/.copilot/session-state/` | JSONL / SQLite |

セッションログは次の手順で探す。

```bash
# Claude Code: プロジェクトのハッシュディレクトリを特定する
ls -lt ~/.claude/projects/ | head -10

# Codex: 日付ディレクトリを探す
ls -lt ~/.codex/sessions/$(date +%Y/%m/%d)/ 2>/dev/null | head -10

# Copilot: セッション状態を確認する
ls ~/.copilot/session-state/ 2>/dev/null | head -10
```

## 抽出パターン

次のどれかが見つかった会話のターンを、候補にする。

ユーザーが修正を指示した場合は、次の形で現れる。

- 「違う」「やり直し」「修正して」「ダメ」「間違い」「もう一度」
- 否定から始まるフォローアップ（「そうではなく」「〜ではなく〜」）
- 直前の出力への否定的な反応

エラーやくり返しは、次の形で現れる。

- ツールの実行エラーが続く（同じエラーが複数回）
- 同じファイルを何度も編集する（作成→削除→再作成など）
- コマンドの `exit code != 0` が続く

## 根本原因分析（重要）

個別の失敗を記録するのではなく、なぜそれが起きたかを推論する。次の 3 つを必ず行う。

### 1. 最低 3 階層の「なぜ」を掘る

症状に対する対策で止めない。「なぜ」を最低 3 回くり返し、再現でき、対策できる根本原因に着くまで掘り下げる。
各段の「なぜ」は、推測ではなく証拠（ログ・コマンドの出力・git の履歴・ファイルの更新時刻）で裏付ける。1 つの視点だけで結論を出さない。

```text
事象: コミットがゲートでブロックされ続けた
 └ なぜ? rm とコミットを 1 コマンドにまとめていた
    └ なぜ? PreToolUse が呼び出し全体を実行前に捕捉する仕様を知らなかった
       └ なぜ? その注意点がスキルに明文化されていなかった ← 根本原因（対策可能）
```

### 2. KEDB 照合（既存の学びと突き合わせる）

新しい事象を記録する前に、同梱の `kaizen-kedb-match.sh` で既存の学びと照合する。過去の事例を参照すると、分析の精度が上がる。

- top-level（`.kaizen/*.md`）は本文を照合する。
- アーカイブ（`.kaizen/archive/`）は、サマリーの索引 `INDEX.md` だけを照合する。archive の本文は、コンテキストを圧迫しないように読まない。サマリーが一致したら、そのファイル 1 つだけを開いて確かめる。
- 忘却済み（`status: forgotten`）のノートは top-level に残るので、本文の照合の対象に入る。忘却は注入から外すだけで、再発を見つける力は落とさない。

```bash
# 事象語と、ツール名または対象パスを最低 1 つずつ渡す。単一語の空振りで新規扱いしない。
bash <スキル>/scripts/kaizen-kedb-match.sh "<事象語>" "<ツール名または対象パス>" [追加キーワード...]
```

終了コードは、`0` が一致あり、`1` が検査したうえで一致なし、`2` が引数の不足か走査の失敗である。`2` を「既存なし」として扱ってはならない。
出力は、一致したファイルと `status` を示す。照合は固定文字列で大文字と小文字を区別せず、渡した語をすべて含む記録を返す。意味が似ているかの最終判断は、本文を読んで行う。

> `.kaizen/*.md` は、書いた時点の記録として読む。ノートの中のファイル名・パス・成果物への言及は書いた時点の状態で、参照先が今は無くても不整合ではない。
> とくに `status: applied` のノートは対応が済んだ履歴で、参照先（例: 撤去したスクリプト）が無いのは正常な結末である。`.kaizen/archive/` の下のノートも同じく履歴である。
> 今の状態について何かを述べる前に、必ず実物を確かめてから言い切る。

同じ種類の学びが既にある場合は、その事象がくり返し起きていると判断する。既存のファイルの `status` で、扱いを変える。

- `status: pending`（未適用）: 新しく作らず、既存のファイルを更新する（優先度を上げ、新しい事象と提案を追記する）。参照の注入で、次のセッションに渡される。
- `status: forgotten`（忘却済み）: 忘却の前提が成り立たなくなった。「適用されないまま古くなり、再発もしていない」と判定して注入から外したノートに、いま再発が見つかったからである。
  `status: pending` に戻し、新しい事象を「## 事象」に追記して `priority` を上げる（上の pending と同じ扱いになる）。
  優先度が上がるので、同じ閾値では再び忘却されない。忘却の条件と閾値は、`references/housekeeping.md`「忘却」を参照する。
- `status: applied`（適用済み）: applied のファイルには追記しない。参照を注入するフック（`kaizen-context-inject.sh`）は `status: pending` だけを渡すので、追記しても次のセッションに届かず、使われないまま残る。
  - 代わりに、その学びを適用した恒久的な置き場所（rule / doc / hook / スキル本体）を直接更新して、再発防止を強める（適用先は、元のファイルの「提案」を参照）。
  - `.kaizen` に跡を残すなら、恒久的な置き場所を更新したことだけを、新しい pending のファイルに短く書く（applied のファイルは書き換えない）。

似た根本原因が複数ある場合は、個別に記録せず、共通の根本原因としてまとめる。

### 3. 横断スコープ確認

根本原因が分かったら、同じ原因がほかの箇所にも無いかを確かめる。例えば、あるスクリプトでパスの解決を誤ったなら、ほかのスクリプトも同じパスの前提を使っていないかを調べる。影響の範囲を提案に含める。

### 根本原因のパターン早見表

| 事象のパターン | 根本原因の候補 | 提案するアクション |
|-------------|------------|----------------|
| 特定のパスの下の作業で規約に違反する | パスに限ったルールが文書になっていない | `paths`/`applyTo` で対象を絞った `.agents/rules/` のルールを足す |
| 同じコマンドのエラーをくり返す | スキルに正確な手順が無い | スキルに手順と注意事項を足す |
| ドキュメントと実装が食い違う | ドキュメントが更新されていない | 基底ドキュメント（`AGENTS.md` 等）を更新する |
| コミットの前に問題が見つかる | 自動のチェックが無い | lefthook / pre-commit に検証を足す |
| エージェントが誤った前提で動く（全体で有効にしたい一般的な規律） | 共通の認識が共有されていない | 基底ドキュメント（`AGENTS.md` 等）に追記する（`.agents/rules/` の `**` のルールにしない） |
| 外部ツールや依存の挙動を、このリポジトリでは直せない | 根本原因を持つのが上流である | `type: upstream` にして、上流への報告か、撤去の条件を付けた回避策へ進む |

> rule を提案する前に、パスで絞れるかを判定する。`.agents/rules/` のルールは、`paths`/`applyTo` に当たるファイルを編集するときだけ確実に読み込まれる。
> そのため、提案先を `.agents/rules/` にするのは、特定のパスの下の作業で閉じる規律（例: `paths: skills/**`、`.github/workflows/**`）に限る。
> 対象を絞れず、すべてのファイル（`**`）でしか有効にできない一般的な規律は、rule にしても利点が小さく、常には読み込まれない。
> その場合は、基底ドキュメント（`AGENTS.md` 等。常に参照される）か、確実に有効になる hook / lint を提案先にする。判定の詳細は `apply.md`「記述先の選び方」にある。

## 抽出手順

1. `.kaizen/` ディレクトリが無ければ作る
2. 対象の transcript を特定し、自分が持ち主かどうかで読み方を分ける。

   抽出しているセッション自身が持ち主なら、出来事はすでに自分の文脈にあるので、transcript を読み直すと同じ入力を 2 度読むことになる。
   しかも transcript は文脈窓を超える大きさに育つ（数 MB＝数百万トークン）ので、指示どおりに全体を読むことはそもそもできない。
   持ち主かどうかは、モードではなく transcript ごとに決まる。`--all` は複数の transcript を回るので、そのうち自分の分だけを持ち主として扱う。

   持ち主の判定は次のとおりである。

   - チェックに止められた場合は、チェックが示した transcript のパスと session id が自分のものである。
   - 直接 `kaizen --current` を指示された場合は、いま追記されている最新のセッションログを起点にする（「セッションログの場所」の `ls -lt` で mtime が最新のもの＝実行中の自分の transcript）。
     その絶対パスと 2 行目が一致する `.kaizen/.pending-extract*` を探し、一致したファイルの 4 行目を自分の session id として使う。
     ファイル名の `.pending-extract` に続く部分のうち、最初の `.` より後ろを `<session key>` として使う（`.kaizen/.extract-checkpoint.<session key>` と同じ key）。
     その `.` より前（`.pending-extract` の直後から次の `.` まで）が、手順 8 の `--sentinel-suffix` である。Claude Code では空文字になる。
   - センチネルが 1 件も一致しないことは、「持ち主でない」根拠にならない。`setup` を実行しておらず Stop フックが無い、すでに解消した、といった理由でも 0 件になる。
     mtime が最新のログが自分の transcript であることは変わらないので、持ち主として進める。`<session key>` が取れない分は、checkpoint 無し（走査ツールの第 2 引数に無いパスを渡す＝offset 0）で索引だけを取る。
     手順 8 は「一致するセンチネルが無ければ、解消するものが無い」に従う。
   - 持ち主でない（読む）側として扱うのは、対象が明らかに他のセッションの transcript のとき（`--all` の他のセッションの分、センチネルを引き受けた場合）と、一致が複数あって自分のものを決められないときだけである。
     0 件だったことを理由に、文脈窓を超える transcript を読み始めない。

   持ち主のセッションでは、自分の文脈を元の情報にし、transcript は候補の位置を見つけるのにだけ使う。チェック経由かどうかに関わらず、走査ツールを使う。

   ```bash
   bash <スキル>/scripts/kaizen-candidate-scan.sh "<transcript>" ".kaizen/.extract-checkpoint.<session key>"
   ```

   - 出力はカテゴリ（`user correction` / `tool error` / `repeated edit`）と絶対行番号だけで、transcript の本文は出ない。
     これを索引にして自分の文脈の該当箇所をたどり、思い出せない行があるときだけ、その周辺だけを読む（圧縮が入った後は要約しか残っていないため）。transcript 全体は読まない。
   - 行番号が表示されるのは先頭の 5 件までで、総数は `N candidate(s) found` の側に出る。表示された行を候補のすべてと読まない。
     総数が 5 を超えるなら、表示されていない候補が自分の文脈の側にある前提で、最重要の 1 件を選ぶ。
   - 走査ツールの exit 1（検証したうえで 0 件）は、「候補のパターンに当たらなかった」という意味で、「学びが無い」という意味ではない。自分の文脈に残る失敗を、これで打ち消さない。
     走査ツールの判定を候補 0 件の根拠にしてよいのは、限定の取り決めでそう定めた `--record-pending` だけである。
   - exit 2（判定できない）は、「候補なし」として扱わない。持ち主のセッションでは索引が得られなかっただけなので、自分の文脈から候補を挙げて先へ進む。
     ここで transcript 全体を読み直す側に切り替えない。`--record-pending` だけは、取り決めどおり BLOCKED にする。

   持ち主でない transcript（`--all` のうち他のセッションの分、他のセッションのセンチネルを引き受けた場合）では、出来事が文脈に無いので transcript を読み込む（`--current` なら前のセッションの最新のファイル 1 つ）。

   どちらの場合も、その transcript の処理位置 `.kaizen/.extract-checkpoint.<session key>`（1 行目が transcript のパス、2 行目がバイト位置、4 行目が行数）がその transcript を指しているなら、その位置より後だけを対象にする。
   - 初めての抽出でも、checkpoint はありうる。同じセッションの前の commit がチェックを候補 0 件で自動で通っていれば、チェックが `kaizen-extract-done.sh --checkpoint-only` で checkpoint だけを進めている。
     「まだ 1 度も抽出していないので offset は無い」と決めつけず、ファイルがあるかを確かめる。
   - session 単位の名前になる前の古い checkpoint `.kaizen/.extract-checkpoint` しか無く、その 1 行目が同じ transcript を指す場合は、チェックと同じくそれを走査ツールに渡す。
   - checkpoint を無視して全体を対象にすると、すでに記録した学びを重ねて起票してしまう（同じセッションでの 2 回目以降の抽出は、複数回 commit するブランチではふつうに起きる）。
3. 抽出パターンに照らして、修正・エラー・やり直しの箇所を見つける
4. 各箇所について、根本原因を推論する（最低 3 階層の「なぜ」→ `kaizen-kedb-match.sh` に事象語・ツール名・対象パスを渡す KEDB 照合 → 横断スコープ確認）。
   そのうえで、根本原因をこのリポジトリで直せるか、上流でしか直せないかを判定し（直す側の判定）、候補を挙げる
5. `--current` モードでは、最も重要な 1 件を選ぶ。最も優先するのは実際の影響度（`high > medium > low`）である。
   その次に、くり返し起きている（KEDB 照合で一致した）もの、根本原因がはっきりしているもの、対策が具体的なものの順に優先する
6. 候補の内容（事象・根本原因・提案）をユーザーに示し、承認を得る。
   承認を求める確認の UI そのものに、判断材料（学びのファイルのドラフトの全文）を入れる。直前の通常のテキストが、確認ダイアログと同時に見えることを前提にしない（Claude Code の AskUserQuestion では、選択肢の preview フィールドに入れる）。
   `--record-pending` の場合だけこの承認を省き、下の限定の取り決めに従う
7. 承認された候補を `.kaizen/YYYY-MM-DD-<slug>.md` に書き込む（`status: pending`）。
   frontmatter の直後に、学びの要約を表す H1 の見出し（`# <学びの要約タイトル>`）を 1 行付ける（markdownlint の MD041 を満たし、読み物として自然にするため）。

   書き込んだら、そのリポジトリの整形のコマンドを通す。
   - 抽出はコミット前のチェックから起動されるので、利用者は記録が書かれるとすぐに同じ `git commit` を実行し直す。その commit の pre-commit の検査には、いま書いたばかりの記録が入る。
     書式を検査するリポジトリでは、記録そのものが次の commit を失敗させる（実測では表の記法で 8 件。ステージしていなくても、検査が `git ls-files --cached --others` で集める構成では対象になる）。
   - 記録は追跡の対象に置く前提なので、`.gitignore` に入れて検査から外す方法は使えない。
   - 整形のコマンドはリポジトリごとに違うので、決まったコマンドは書かない。そのリポジトリの整形のコマンド（`package.json` の `format` 系のスクリプト、`Makefile` の `fmt` ターゲット、pre-commit の整形のステップ等）を 1 つ見つけ、書いた記録に当てて通す。
   - 整形のコマンドが見つからないリポジトリでは、この段を飛ばしてよい（無いものを探し続けて、チェックの解除を遅らせない）。
   - 一般化すると、検査の直前にファイルを作る手順は、その検査を通すコマンドを手順の中に含める、ということである。

   `## 提案` の最初の段落は、1 つの物理行にする（詳細は次の行以降の箇条書きに書く）。
   セッション開始時の注入が要約として読むのはこの最初の 1 行だけなので、箇条書きから始めたり途中で折り返したりすると、注入される要約が途中で切れて意味をなさない。
   この制約は `kaizen-status-check.sh` が検査し、直し方も示す。
8. 抽出が終わったら、同梱の `kaizen-extract-done.sh` で、センチネルを消し、処理位置 `.kaizen/.extract-checkpoint.<session key>` を記録する。
   同じ範囲を抽出し直さず、この後に増えた活動を次の commit で検査させるためである。同じセッションで複数回 commit しても、取りこぼさない。

   `bash <スキル>/scripts/kaizen-extract-done.sh --sentinel-suffix "<suffix>" --agent "<agent>" --session-id "<session id>" [transcript_path]`

   - `<スキル>` はインストール先である。suffix は Claude Code が空文字、Codex が `-codex`、Copilot が `-copilot` で、チェックが表示したコマンドをそのまま使う。
   - transcript_path を省かない。省くと処理位置を記録できず、代わりに書かれる抽出完了マーカー `.kaizen/.extract-done.<session key>` がセッション全体を抽出済みにするので、以降の commit がチェックを通り抜ける。
     これは止まったままになるのを避けるための安全策であって、通常の使い方ではない。このとき既存の checkpoint も消えるので、次のセッションはその transcript をすべて走査する。
   - このスクリプトは忘却も行う（`status: forgotten` への書き換え）。忘却した件数は stderr に出る。
     忘却は追跡している `.kaizen/*.md` を書き換えるので、新しい記録だけをパスで指定して stage すると、忘却の差分がステージされないまま残る。clean を確かめる工程（`git-worktree` の後片付けや `issue-batch` の収束）は、そこで止まる。
     commit を実行し直す前に、`.kaizen/` をまとめて stage する（`git add .kaizen/`）。忘却が 0 件でも害は無い。
   - `--sentinel-suffix` と `--session-id` を省かない。省くと、古い設定との互換のためにエージェント単位の名前になる。
     両方を省くと `rm -f .kaizen/.pending-extract*` ですべてのセッションのセンチネルを消してしまい、他のエージェントや他のセッションの未処理の印まで完了扱いになる。
   - 解消するのは、センチネルを立てたセッションの id であって、自分の id ではない（他のセッションのセンチネルを引き受けて抽出した場合は、その値をチェックの案内から取る）。
   - チェックに止められていない状態（ユーザーが直接 `kaizen --current` を指示した等）で自分の session id が分からない場合は、値を推測せずにセンチネルから読む。
     `.kaizen/.pending-extract*` の各ファイルは、1 行目に UTC のタイムスタンプ、2 行目に transcript のパス、3 行目にエージェント、4 行目に session id を持つ。
     2 行目が手順 2 で特定した自分の transcript と一致するファイルの 4 行目が、自分の session id である。`--sentinel-suffix` は、手順 2 と同じ読み方でファイル名から取る（`.pending-extract` の直後から次の `.` まで。Claude Code は空文字）。
     一致するセンチネルが無ければ、そのセッションにはセンチネルが無い（＝解消するものが無い）ので、`kaizen-extract-done.sh` を引数なしで呼ばない。
   - 削除が空振りしたことは、stderr の警告で分かる。`rm -f` は対象が無くても正常に終わるので、終了コードでは「解消した」と「解消するものが無かった」が同じ値になる。
     `kaizen-extract-done: 警告: 削除対象のセンチネルがありませんでした` が出たら、消えたつもりで先へ進まず、`--session-id` / `--sentinel-suffix` がセンチネルを立てた本人のものかを確かめ直す。
   - スクリプトはリポジトリのすべての作業ツリー（本体と git worktree）の `.kaizen/` を対象にするので、共有のツリーと worktree にまたがったセッションでも解消できる。

> 重要（適用先も記録する）: 抽出と同じ実行の中で成果物への反映（適用）まで行う場合は、反映を終えた後に、そのファイルの `status` を `pending → applied` に更新し、`applied-to` に適用先のパスか Issue（例: `"#123"`）を記録する。
> ファイルを作るだけで反映しない場合は、`pending` のままにする（後で apply フローが適用する）。
> 実行の最後に `bash <スキル>/scripts/kaizen-status-check.sh` を実行する。不整合はファイル名付きの stderr と exit 2 になり、コミット前のチェックも同じ検査を強制する。

コミット前のチェックから起動された場合に、デフォルトで行うのは、最重要の 1 件の抽出・記録と extract-done までである。apply は後の作業に回し、ユーザーが「今すぐ適用」を選んだ場合だけ同じ実行で続ける。

## `--record-pending` の限定の取り決め

このモードは、「恒久的な対策は自動で適用せず、後のセッションがレビューできる pending の候補だけを残す」ための狭い例外である。

current の transcript を特定し、候補の走査ツール（candidate scanner）で検証できることが前提である。Claude Code と Codex は transcript のパスを解決して使う。
Copilot は、今の Hook が transcript のパスを渡さず、走査ツールも形式を見分けられないので、このモードで候補 0 件を検証できない。候補が無いと推測せず、BLOCKED にする。

1. `extract --current --record-pending` の組み合わせそのものだけを受け付ける。候補は最大 1 件
2. 通常と同じ手順を行う。transcript の特定と候補の走査、最低 3 階層の「なぜ」、KEDB 照合と横断スコープ確認、直す側の判定である
3. 候補がある場合は、承認の確認を挟まず、`.kaizen/YYYY-MM-DD-<slug>.md` に `status: pending` / `applied-to: []` で記録する。同じ種類の pending があれば、新しく作らず既存の記録を更新する
4. 候補が無い場合は、current の transcript を特定したうえで、候補がある既知の transcript を同じ走査ツールで検出できることを先に確かめる。
   走査ツールの失敗、timeout、未知の形式、current の transcript を特定できないことを、「候補なし」として扱わない。検出できることを確かめられた場合だけ、何もしない
5. 候補を記録した場合は、`kaizen-extract-done.sh` を、エージェント固有のセンチネルの suffix / agent / session id / transcript のパス付きの complete モードで実行する。
   候補が 0 件の場合は、走査ツールが返した `scanned-bytes` / `scanned-lines` を使い、`--checkpoint-only` と同じ特定の情報を付けて、checkpoint とそのセッションのセンチネルだけを更新する。候補が 0 件のときは `.extract-done.<session key>` を作らない
6. どちらの場合も、最後に `kaizen-status-check.sh` を通す
7. apply / archive / delete、Issue の作成、外部への報告、既存の成果物への恒久的な反映は行わない。呼び出し元は、pending の記録を実装の変更とは別の commit にする

通常の `kaizen --current` と `kaizen extract --current` では、ユーザーの承認が必須である。フラグを推測で補わず、呼び出し元が明示した場合だけ限定のモードに入る。

## 学びファイルのフォーマット

```markdown
---
date: YYYY-MM-DD
type: rule
priority: high
status: pending
applied-to: []
session: claude-code
---

# 〈学びの要約タイトル〉

## 事象

〈何が起きたか〉

## 根本原因

〈なぜそれが起きたか〉

## 提案

〈何を作成・変更すべきか。type が rule ならルール文面まで含める〉
```

`type` の値は `rule` / `skill` / `hook` / `doc` / `upstream` / `other` のどれかである。

`priority` は、抽象的な重要さではなく、観測した影響で決める。

- `high`: 作業を続けられず、その場で止まった
- `medium`: 時間を失った、または手戻りが起きた
- `low`: 気づいて直せば済む小さな不便

`status` の初期値は、常に `pending` である。
`applied-to` の初期値は、常に空の配列 `[]` である。適用や却下のときに、`references/apply.md` の手順で埋める。

> `## 提案` の最初の行は、そのまま次のセッションへ注入される。
> 参照を注入するフック（`kaizen-context-inject.sh`）は、各 pending の学びの要約として、`## 提案` の最初の空でない行を渡す（無ければ `## 事象` を使う）。
> そのため `## 提案` の最初の行は、特定の出来事の言い換えではなく、単独で別の文脈でも行動を促す、一般化した規律として書く
> （例: 「外部ツールの出力の enum は一部だけを挙げず、正規化したフィールドを使い、許されるすべての値を元の情報で確かめる」）。
> 最初の行が個別の事案で閉じていると、注入されても再発を防ぐきっかけにならない。
>
> 最初の段落は折り返さない。渡されるのは最初の空でない行だけなので、最初の段落を複数の物理行に折り返すと、注入される要約は文の途中で切れた断片になる（強調の記法も閉じないまま入る）。
> 注入は成功し、終了コードも 0 なので、失敗としては表に出ない。
> `kaizen-status-check.sh` が pending の学びを対象にこの形を見つけて exit 2 にする（最初の行が箇条書きの項目で、次の行も箇条書きの項目なら、兄弟の項目とみなして折り返しとは扱わない）。
> 長い最初の段落は、折り返さずに 1 行に収めるか、1 文に削る。

## 自動実行のセットアップ

Hook の設定（タスク終了時のセンチネル、コミット前のチェック、セッション開始時の参照の注入）は `references/setup.md` に分けた。インストール後の初回だけ、`references/setup.md` を読み込んで実行する。
