# 敵対的レビュー（ローカルの未コミット差分・実装役とレビュー役の分離）

commit 前にローカル差分へ敵対的レビューをかける具体手順と、`review.md` への記録を定める。

## 原則

- **ローカルの未コミット差分に対して実施する。** PR を作ってからではなく、`issue-start` の commit へ渡す前に回す
- **実装役とレビュー役を分離する。** レビュー役には**判断の基準**（差分・現行コード・規約・DB 意味論の点検表・`keep` / `may_change`）を渡し、**実装役の主観**（実装意図・確信度・設計判断の経緯）は知らせない（下記手順 3）
- **レビュー役の仕事は動かない理由を見つけること**であって、理解を示すことではない
- **「型検査が通った」「テストが通った」を理由にレビューを省略しない**

## 手順

1. **検証コマンドを先に通す**: レビュー役へ差分本文を渡す前に検証コマンドを通し、自明な破綻を安価に落とす（通ったことをレビュー省略の理由にしない）。
   **どの列を回すかは変更集合を先に見て決める**——`git status --porcelain` と `git diff --name-status`（`--staged` も）で**変更ファイル名と `D` / `R`** を取る（差分本文の取得は手順 2）。
   回すのは `verification_commands.diff`（無ければ `full`）だが、**変更集合がファイルの削除・改名か定義元の削除・改名を含むなら `full` を回す**（差分限定では変更集合の外の壊れが捕まらない）。
   `diff` を回すときの `{changed_files}` の展開規則（対象集合・0 件時の扱い）は `replace-strategy` の `references/project-config.md`「走る範囲」に従う。**完了判定（`SKILL.md` 手順 8）は列に関わらず別途 `full` を回す**。
   **検証コマンドが作業ツリーを書き換えたら、その差分を取り直してからレビューへ渡す**——設定に auto-fix 付きの起動形が紛れていると、
   レビュー役が見る差分と実装役が書いた差分がずれる（起動形はチェック形であるべきで、書き換えが起きたこと自体を `review.md` に記録し設定の是正を促す）
2. **差分の取得**: `git diff`（未ステージ）と `git diff --staged`（ステージ済み）でローカルの未コミット差分**本文**を取得する。**未追跡ファイル**（`git status --porcelain` の `??`）は `git diff` に出ないため、内容を別途読んでレビュー対象に含める。範囲を `review.md` の「レビュー対象」に記録する
3. **レビュー役へ渡すものを分ける**: 実装役とは別のサブエージェント（Agent ツール）をレビュー役として起動する。**判断の基準は渡し、実装役の主観は渡さない**。

   | | 渡すもの |
   |---|---|
   | 渡す | 未コミット差分のテキスト／現行コード（一次情報源）／**新側リポジトリのコーディング規約**（設定の `references.coding_conventions`。未整備なら新側リポジトリの基底ドキュメント・リント設定のパス）／**機械検査が無い規約項目の一覧**（`review.md` の「観点（機械検査が無いもの）」。出所は `.replace/strategy.md`「未検証領域の扱い」）／**DB 意味論の点検表**（設定の `references.db_semantics`。未整備なら `replace-strategy` の `references/project-config.md`「DB 意味論」の点検項目）／意図的差異レジストリの `keep`・`may_change` |
   | 渡さない | 実装意図・設計判断の経緯・確信度の申告（`porting.md` を丸ごと渡さない）。バイアスを持ち込ませないため |

   **規約や点検表を渡すことは「意図を渡す」ことではない**——どちらもレビュー役が独立に照合できる外部基準であり、実装役の主観ではない。
   **`porting.md` の「DB 方言差の点検結果」は渡さない**（実装役が何を確認したかは主観側。レビュー役は点検表と差分だけで独立に当てる）。
   **新側が別リポジトリの場合は規約の所在をパスで渡す**（レビュー役に載っている基底ドキュメントは現側のものなので、そのままでは新側の規約が効かない）。
   **サブエージェントを起動できない実行環境**（起動手段が無い・実行のたびに承認が要り回せない）では、**同じもの**を人間のレビュアーへ渡す。
   この場合も工程は省略せず、レビュー役が人間であったことと結果・対応を `review.md` に記録する。**レビューを受けられないまま commit へ進まない**（能力の不足は工程の免除ではない）
4. **レビュー役の観点**: 現行コード（一次情報源）に照らして動かない理由を探す——ロジックの取りこぼし、状態遷移・エラー処理・バリデーションの差、`porting.md` の `TODO`（未解決）に対応するコードが本当に未解決のままか、`keep` の項目（テーブル名・API・関数名）を勝手に変えていないか。
   加えて**依存の追加・自前実装**を見る: 差分に新しい依存（`package.json` 等）が入っていれば `.replace/dependencies.md` に判断材料（ライセンス・メンテナンス状況・採用規模・配布元の素性・バンドルサイズ・型定義・実行基盤との両立・代替候補と不採用理由）が記録されているか、
   既存パッケージで済む処理を自前で書いていないか（書いているなら理由が記録されているか）。基準の正本は `replace-strategy` の `references/dependency-selection.md`。
   さらに**リポジトリ規約からの逸脱**を見る: 命名・エラー処理・型の扱い・テストの書き方・ファイル配置が渡された規約から外れていないか、
   規約に合わせた結果として**振る舞いが変わっている**のに `intentional_diffs.pending` へ回っていないか（規約と振る舞い保存が衝突したときは振る舞い保存が優先する）。
   **`keep` は規約より上位**なので、規約を理由にテーブル名・API・関数名を変えていたら指摘する。
   加えて**DB の方言差**を渡された点検表の項目ごとに差分へ当てる: `ORDER BY` に NULL の位置が明示されているか、暗黙の型変換が失敗したときに絞り込みが全件へ化けないか、
   比較・`LIKE` の正規化が**両辺**に当たっているか、連結した文字列が NULL で意図しないパターンにならないか、数値・日付の書式がロケール設定に依存していないか。
   **スイートが green であることを点検の代替にしない**（絞り込みの破綻はデータ件数が少ないと現れない）。
   差分に **IaC の変更**（CDK / Terraform 等）が入っていれば、それが実装に付随する差分の範囲に収まっているか（パイプラインの新規構築へはみ出していないか）を見る
5. **指摘 → 修正 → 再レビュー**: 指摘があれば実装役が修正し、再度レビュー役へ差分を渡す。指摘が尽きるまでラウンドを回す
6. **記録**: 各ラウンドの指摘と対応、最終判定を `review.md` に残す

## `review.md` の位置づけ

- 敵対的レビューは **PR のレビュー機能（PR コメント・レビュースレッド）上では行わず**、ローカルの未コミット差分に対して実施する。その記録が `.replace/parity/<slug>/review.md`
- 記録ファイル自体は他のテキスト成果物と同様 **Git 管理してよい**（レビューを PR 上で行わないことと矛盾しない）
- 正本テンプレートは `assets/review-template.md`
