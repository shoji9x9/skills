# ページ分割とフェーズ構成

機能をページ単位のフェーズに分けて 1 つずつ作り切る手順と、api-resource・batch モードで省く工程を定める。

## ページ単位のフェーズ分割（feature モード）

機能 Issue は一度に作らず、ページ単位でフェーズに分ける。

- 1 ページを作り切って比較してから、次のページへ進む。ページをまたいで並行に進めない。並行に進めると調査・実装・比較が浅くなり、差異を見落とす
- ページの単位は、`.replace/features.md` が機能に紐づけたページの一覧を起点にする。推測で足さない
- `.replace/features.md` の「ページ要素の帰属」表で自分の slug が所有する要素は、そのページのフェーズで配置する。
  `扱い` が `スコープ外（配置のみ）` の要素も置く。その先の挙動は作らないが場所を占めるので、置かないと現行との差分になる。
  所有者が空欄の要素があれば、実装側で決めずに `replace-strategy` へ差し戻す
- 1 つのフェーズは、1 ページ分を次の順に最後まで回す単位とする。実装、新側マッピングの充填、見た目の系統差の縮小、敵対的レビュー、スイート green と検証コマンド（`verification_commands.full`）
- 寸法の決まり方の照合は、ページのフェーズに入れず、機能の全ページのフェーズを終えた後に 1 回だけ行う（`SKILL.md` 手順 8）。
  測定スペックと `dimension_model` は機能の全ページを対象にする。途中のフェーズで実行すると、未実装のページが「表示されない」「測っていない」で必ず失敗し、最初のフェーズが完了できない
- 静的資産の新側の突き合わせ（`asset-delivery-check.mjs`）も、同じ理由で全ページのフェーズの後に 1 回だけ行う（`SKILL.md` 手順 8）。
  記録は機能単位で台帳の行に答える。途中のフェーズでは、未実装のページが使う資産を「参照していない」で失敗にしてしまう
- スクロールバーを表示した窓のはみ出し（`parity-suite` の `overflow/` のスペック）は、ページごとに 1 テストなので、そのページのフェーズのスイート green に含める（`はみ出し: <頁名>`）。
  未実装のページのテストは、そのページのフェーズまで実行しない

## フェーズ内の順序（読み取り → 書き込み）

フェーズの中では、読み取りの処理を先に、書き込みの処理を後に扱う。

- 読み取りの処理は DB の復元が要らないので、先に扱うと安く比較できる
- これはフェーズの中の順序で、機能の並び順の話ではない。機能の並び順は `replace-strategy` の依存順が決める
- ファイル出力の実装は読み取り側に、ファイルアップロードの実装は書き込み側に置く。アップロードはアプリのストレージやファイルシステムに残る。
  そのため、規律（復元、一意のプレフィックスと後始末、後始末できないなら明示）は `parity-suite` の `references/data-discipline.md` に従う

## ファイル入出力を持つページ

- バイト列を取得する方法を現側とそろえる（ダウンロードイベント、`page.request`、batch ではファイルシステムを直接読む）。実現の手段は `replace-strategy` の `references/file-io.md` で定義する
- アップロードの方法（`targets[].storage.upload_route`）を現側から変えるなら、それは仕様外の変更ではなく意図的差異である。保存する path の命名規則も変わる。
  そのため、勝手に決めず、`intentional_diffs.pending` に既存を消さずに追記してユーザーに確認する。`upload_route` が未宣言のまま実装しない。
- `presigned` では、ブラウザがストレージへ直接 PUT するので、アプリサーバを通らず、API パリティの対象が変わる。アプリ側に残るのは署名を発行する API だけである。
  方法ごとの影響は、`replace-strategy` の `references/project-config.md`「ファイルストレージ」で定義する
- ストレージの実体へのゴールデンデータの投入はスコープ外である。そのため、事前に置かれたファイルに依存する画面（既存の添付の一覧・サムネイルなど）は、スイート green の対象にできない。
  アップロードの操作で自分が作った状態を使うか、`gaps.md` に未検証として残す（確認済みにしない）
- xlsx や PDF を生成するなら、現側のシート × セル値・構造（xlsx）と、抽出したテキストと構造（PDF）に一致させる。バイトの一致は目標にしない（揮発する項目が入るため、一致させられない）

## api-resource モード（横断 API リソース）

画面を持たないので、ページ分割・視覚差分・新側ロケータマッピングは行わない。

- 担うのは、バックエンドの実装（現行コードとの diff のレビュー）と、API パリティスイートを新側に対して green にすることだけである
- 成果物のパスの `slug` は、そのリソースのものにする
- 完了の判定は、API スイートの green、検証コマンド（`verification_commands.full`。視覚の 3 点セットは無い）、受け入れ条件の突き合わせ（`SKILL.md` 手順 8。全モード共通）である。
  green にする前に、`golden-dataset --phase b --feature <slug> --target <選択中の new target>` で新側の DB へ投入する

## batch モード（バッチ Issue）

画面の工程は実行しない。

- バッチ本体の新側の実装（現行コードとの diff のレビュー）と、その出力（DB の状態・生成したファイル・対象範囲内の副作用の出力）が現行と一致することを担う
- 出力が一致するかは、`parity-suite` がバッチモードで採取した現行のベースライン（`.replace/parity/<slug>/` の下）に対して確かめる
- 完了の判定は、出力の一致、検証コマンド（`verification_commands.full`）、受け入れ条件の突き合わせ（`SKILL.md` 手順 8。全モード共通）である。
  新側でバッチを実行する前に、`golden-dataset --phase b --feature <slug> --target <選択中の new target>` で新側の DB へ投入する
