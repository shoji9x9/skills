# 見た目の系統差を源流で縮める（トークンを寄せる・component_diffs の宣言・gap の記録）

新側の UI ライブラリを reference で選び、旧 design token を寄せ、テーマで消せない構造差を宣言するか gap に記録する手順を定める。これは比較の正規化で、仕様の変更ではない。

## 源流で縮める理由

コンポーネントライブラリが変わる以上、見た目はライブラリによって正当に違う。これを差分ツールの側だけで説明しようとすると宣言が増えるので、実装の側でも源流の差を縮める。
論理名・振る舞い・構造は変えず、見た目の系統差だけを扱う。

## 新側の UI ライブラリは reference で選ぶ（固定しない）

- 新側のライブラリと、旧 → 新のトークンの対応づけは、設定 `references.ui_library` が指すファイルから読む。特定のライブラリ名・DB 名を、このスキルやコードに固定で書かない
- reference は、`replace-strategy` の測定と `ui_library` の設定を基に生成し、レビュー済みのプロジェクトの知識である

## 旧 design token を新側のテーマへ寄せる

- 選んだライブラリがテーマを変えられるなら、旧アプリの design token（色・余白・角丸・タイポグラフィのスケール）を新側のテーマに寄せる。旧 → 新の対応づけは、`ui_library` の reference から得る
- テーマの機能が無いか限られるライブラリなら、源流で縮める効果は限られ、次の項のクラス単位の系統差の宣言の比重が上がる

## フォントは版とヒンティングまでそろえる

フォントは、移行で供給の方法が変わりやすい（フレームワークのフォント最適化の仕組みの違い、配布パッケージの違い）。
同じフォント名を指定しても、版が違うか、ヒンティング命令を持たないビルドだと、本文の幅が変わる。小さなサイズで送り幅の丸め方が変わるからである。

- 部品として選ぶとき（実行フロー 3）は、フォント名だけでなく、版と配信ビルド（ヒンティング命令を含むか）まで見て決め、`.replace/dependencies.md` に記録する
- フォントスタックに総称ファミリー（`system-ui` / `sans-serif`）を残さない。CJK のフォールバック先は OS で変わるので、採取環境では一致し、利用者の環境でだけ崩れる（差分ツールはゼロを返す）
- 版の差かヒンティングの差かを切り分ける手順は、`parity-diff` の `references/font-diff.md` で定義する

## 移行元の宣言を `反映しない` と決めるなら、その宣言が変える次元をすべて測る

移植では、移行元の CSS の宣言を `反映する`（新側に反映する）か `反映しない` かで仕分ける。`反映しない` と決めるときは、その宣言が変える次元をすべて測ってから決める。

<!-- textlint-disable ai-words-ja/no-ai-words -->

旧称: `反映する`・`反映しない` は `写す`・`写さない` と書いていた。既存の porting.md の旧称（見出し「移行元の宣言を写さないと決めた箇所」、列「写していない軸」を含む）は、同じ意味として読む。

<!-- textlint-enable ai-words-ja/no-ai-words -->

`display` / `position` / `box-sizing` のように箱の作り方を変える宣言は、複数の次元を同時に変える（箱の寸法・中身の配置・匿名ボックスの生成）。
1 つの次元が一致していることは、ほかの次元が一致している根拠にならない。この形の差は、3 つの比較方法のどれにも出ないことがある。
特性照合が測れない要素（論理名が現側で画面外の複製に解決する、など）で、差が 0.0156px なら、画素の比較にもほとんど出ない。人が数値を見るまで見つからない。

宣言ごとに、変える次元を並べてから測る。

| 宣言 | 変える次元 | 測る値 |
|---|---|---|
| `display: table` などの箱の作り方 | 箱の寸法・中身の配置・匿名ボックスの生成 | `getBoundingClientRect()` の寸法と中身の位置 |
| `vertical-align` | 中身の配置だけ | 中身の位置 |
| `padding` | 箱の寸法と中身の位置の両方 | 両方 |

- 測り方は、両側で同じ要素の矩形を並べて出すことである（`getBoundingClientRect()` と `getComputedStyle().height` の両方）。追加のツールは要らない
- 箱の寸法だけでは、中身の配置を測ったことにならない。入れ物の寸法が一致したまま、中身だけが動く形があるからである。
  そのため、中身の矩形を入れ物とは別に取る。`Range.selectNodeContents(<容器>)` の矩形を使うと、包む要素が片側に無くても、両側を同じ測り方で取れる。
  記録するのは、入れ物の上端と下端それぞれからの距離である。上端だけだと、行の高さが中身とちょうど同じときに、`vertical-align` が反映されているかを区別できない
- 匿名ボックスの生成は、寸法にも位置にも出ないことがある。子の構造（包む要素の有無・`display` の解決結果）を別の証拠として並べる
- 1 点だけで測らない。中身より行が高くなる状態（別のセルの折り返し・高さの指定・背の高いインライン要素）でも測る。
  その状態を作らないと、`vertical-align` のように条件がそろったときだけ差が出る宣言は、反映してもしなくても同じ値になる
- `反映しない` 理由を先に決めてから確かめない。その結論と矛盾しない観測ではなく、その結論が誤りなら違う値になる観測を選ぶ。
  実測の例を挙げる。当てる相手の `div` が新側に無いので `反映しない` と決め、根拠に文字の位置（セルの上端から 5px）を測って一致を確かめた。
  ところが、測っていなかった箱の高さが 31.0156px（`display: table` は中身で決まる）と 31px で違い、利用者が画面で見つけた。最初に `反映する` と判断していれば、4 行を足すだけだった

- 結果は、`porting.md` の「移行元の宣言を反映しないと決めた箇所」に記録する（様式は [`../assets/porting-template.md`](../assets/porting-template.md)）。
  該当が無くても「該当なし」と書く。空欄にすると、「反映しなくてよい」と「誰も測っていない」を区別できない

## テーマで消せない構造差の扱い

テーマで消せない構造差（フォーカスリングの形・内部の DOM・余白の配り方）は残る。次の 2 段で扱う。

1. クラスやトークンの単位で表せる系統差は、共有の設定の `component_diffs` レジストリに、ユーザーに確認したうえで宣言する。
   これは `intentional_diffs` とは別のキーで、要素の形は `replace-strategy` の `references/project-config.md` で定義する。`parity-diff` が比較の正規化に使う。
   `component` は照合のキーなので、対象の要素の論理名を書く（複数のインスタンスに当てるなら `filter-popup-*` のような glob）。
   ここを空にしたり実在しない名前を書いたりすると、宣言が 1 件も当たらない（`parity-diff` が stderr に警告を出す。照合の方法は `parity-diff` の `references/normalize.md` で定義する）。
   確認が取れるまでは、`component_diffs` にも `intentional_diffs.pending`（分類のラベルの列で、要素の形が違う）にも書かず、対話で確認してから宣言する
2. クラスやトークンの単位でも表せない構造差（フォーカスリングの形・内部の DOM・余白の配り方など）は、`.replace/parity/<slug>/gaps.md` の「宣言できない構造差」の節に追記する。
   様式は `parity-suite` の `assets/gaps-template.md` で定義する。`parity-diff` の正規化の対象外で、未検証として残る

- `component_diffs` は、特性照合（computed style の値の比較）にしか当たらない。現側と新側で computed style が一致し、画素だけが違う差（フォントのサブセットビルドの差など）は、系統的な原因でも、ここに宣言して吸収させることはできない。
  その置き場所は `parity-diff` のインスタンス例外（`property: pixel`）である。共有の設定ファイルではなく、slug の成果物 `.replace/parity/<slug>/component-diff-exceptions.json` に置き、宣言するのもトリアージで承認を取る `parity-diff` である。
  このスキルはここに書かない。テーマで消せないなら、上の 2 の `gaps.md` に書くか、`parity-diff` との往復で承認を取る。
  スキーマ・置き場所・レジストリごとにどの比較方法に当たるかは、`parity-diff` の `references/normalize.md` で定義する

どれも比較の正規化で、仕様の変更ではない。論理名・振る舞い・構造は変えない。
