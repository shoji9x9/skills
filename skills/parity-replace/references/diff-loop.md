# parity-diff との往復ループ（終了の条件・反復の上限・再開の手順）

新側が green になった後に `parity-diff` が検出する差分について、往復ループの止め方と、差し戻されたときの再開のしかたを定める。

## このスキル単体の完了と、ループ全体の終了は別

- このスキル単体の完了は、選んだ target に対してパリティスイートが新側で green になり、検証コマンド（設定 `verification_commands.full`）が通ることである。
  完了の判定には、常に全体を走査する列を使う。
  `parity-diff` の差分ゼロは含めない。`parity-diff` は前提としてこのスキルの完了を求めるので、含めると循環する
- 往復ループ全体の終了の条件は、`parity-diff` で説明のない差分がゼロで、直していない回帰もゼロになることである（すべての差分が、系統差か宣言した例外に分類されている）。
  「許容」の例外を確定させるには、ユーザーの承認が要る（`parity-diff` の側で扱う）
- 単体の完了を「現行と一致」と報告しない。現行との比較が収束したと報告できるのは、往復ループが終わった（`diff-metadata.json` が `converged: true` になった）後だけである。
  そのときも、承認済みの例外・意図的差異・未検証の領域を並べて報告する（収束は、生の差分がゼロであることではない）。
  報告の書き方は、`SKILL.md` の手順 8「完了の報告」に従う

## 1 反復の定義と、数え始める時点

- `parity-diff` の差し戻し（`diff.md`）を受け取った時点で、`loop.iterations` に 1 を足し、`loop.last_diff_report` をその `diff.md` にする。
  修正に着手する前に数える。修正が途中で止まっても、回数が消えないようにするためである。
  同じ書き込みで、`loop.changed_scope` を `null` に戻す。前の反復の範囲を、今の反復の範囲として扱わせないためである（確定した値は、下に書くとおり修正を終えたときに書く）
- 1 反復の範囲は、差し戻しを受け取ってから、修正して対象の target でテストし直し、`parity-diff` へ戻すまでである。
  同じ `diff.md` の中で複数の箇所を直しても 1 反復で、差分の件数では数えない

## 反復の上限

- 上限は `--max-iterations`（デフォルト 5）である。余白を直すと別の要素がずれる（連鎖する）状況では、修正が新しい差分を生み続けることがあるので、上限を置く
- 上限を超えたら止まり、ユーザーに判断を求める（頭から作り直さない）
- 反復の回数は、上の時点で `.replace/parity/<slug>/new/<target>/replace-metadata.json` の `loop.iterations` に記録する（`max_iterations` と `last_diff_report` も記録する）。
  上限は target ごとに数える（環境を変えれば、別の証跡と別の回数になる）

## 差し戻されたときの再開の手順

- このスキルは、差分のレポート `.replace/parity/<slug>/new/<target>/diff.md`（`parity-diff` の出力）を入力として受け取る。`<target>` は、`parity-diff` を実行したのと同じ新側の target である
- 該当するページのフェーズから再開し、頭から作り直さない。diff.md が指す差分の分類を確かめ、要対応のものだけを、該当するページの実装・新側マッピング・テーマの各フェーズへ戻す
- コードの変更を伴う修正は、敵対的レビューまで含めてやり直す（[`adversarial-review.md`](adversarial-review.md)）。差し戻しへの対応が小さく見えても、commit の前のレビューを省略しない。
  `on_diff` のドキュメントが commit や push を指示していても、レビューを先に行う（差し戻しを、レビューを省略する抜け道にしない）
- 差分が「テーマで消せない構造差」に当たるなら、`component_diffs` の宣言か `gaps.md` への追記で扱う（[`theming.md`](theming.md)）。仕様を変えて差分を消すことはしない

## 変更の範囲の記録（`loop.changed_scope`）

差し戻しに対応して新側を直したら、その反復で描画に影響する変更を入れた範囲を、`new/<target>/replace-metadata.json` の `loop.changed_scope` に記録する。
反復ごとに上書きし、最後の反復の範囲だけを持つ。反復の回数に 1 を足すときに `null` に戻し、その反復の修正を終えてから確定した値を書く。
修正の途中で止まった反復は `null` のまま残り、安全な側（すべての組を測り直す）として扱われる。
`parity-diff` はこの値を使って、新側の自分のノイズの測定を再利用してよい組を決める（用途と失効の条件の原本は `parity-diff` の `references/capture-new.md`「測定値の再利用」）。

- `pages`: 変更が描画に影響するページ。差し戻された差分のページだけでなく、修正で実際に触れた範囲を書く。
  値は `.replace/features.md` のページの識別子（現側の `metadata.json.noise_baseline[].page` と同じ語）で書く。
  ファイルのパスやコンポーネントの名前で書くと、`parity-diff` の側で突き合わせられず、すべての組を測り直すことになる
- `global`: 共有の資産（テーマ・design token・共通コンポーネント・グローバル CSS・フォントの読み込みなど）に触れたら `true` にする。`true` なら、`pages` は空でよい。
  共通部品に触れても、その改修の変更の宣言（`parity-component` の `references/amend.md`「現行に合わせ直す修正」）があれば、`global` にせず `components` に書く
- `components`: 変更の宣言がある共通部品の改修を、`[{"slug": "<部品 slug>", "change": ".replace/components/<slug>/changes/<change-id>.json"}]` の形で書く。
  `parity-diff` は、宣言から影響する組だけを導く（導けなければ、すべての組を測り直す）。宣言の無い共有の資産の変更を同じ反復に含むなら、`global: true` も書く（その場合は、すべての組を測り直す）。
  部品を使う他の機能の検証のやり直しは、この記録では起きない。`parity-diff --component-change <宣言>` でまとめて実行する（手順の原本は `parity-diff` の `references/component-change.md`）
- `pages: []` と `null` を取り違えない。`pages: []`（`global: false` で `components` なし）は、「この反復では描画に影響する変更を入れなかった」という明示の申告である。
  `parity-diff` は、すべての組を再利用してよいと読む。範囲が確定していない、または記録していないなら、空の配列ではなく、`loop.changed_scope` ごと `null` にする（`parity-diff` の側ですべての組を測り直す）
- 範囲を少なく申告しない。判断がつかないなら、上に書いたとおり `null` にする。
  少なく申告すると、測り直すべき組を警告なしに飛ばす（誤ったノイズの基準で、本当の回帰を吸収することがある）

## `on_diff` の解釈（対象の target ごと）

対象の target の `on_diff` は、差分を見つけた後にどう動くかを書いた Markdown のドキュメントのパスである（任意）。
意味の原本は、`replace-strategy` の `references/project-config.md`「`on_diff`」節である（ここへ転記しない）。

- `on_diff` があれば、そのドキュメントに従う。よく書かれる内容（先に動く環境でのテストのやり直し、修正の反映〈commit・push・デプロイ〉、反映が終わるのを待つこと）と書き方は、上の原本を参照する
- 省略したときのデフォルトの動き: 上の「差し戻されたときの再開の手順」で、該当するページのフェーズから直し、対象の target を起動してスイートを実行し、`parity-diff` へ戻す（反映の工程は無い）
- ガードレール: 一覧の原本は、上の原本の「ガードレール」である（ドキュメントの指示より優先する）。`on_diff` に従う前に、その一覧を読み、このスキルに関係する項目をすべて当てる。
  ここへ転記しないのは、転記すると原本の改訂に追いつけないからである。
  一覧に届かない（`replace-strategy` がインストールされていないなどで、そのファイルを読めない）場合は、ガードレール無しで従わず、止まってユーザーに判断を求める
- 決定論的にしたい手順は、ドキュメントがリンクするスクリプトを実行する（手順を自分で言い換えて代わりにしない）
- 従ったドキュメントのパスを、`new/<target>/replace-metadata.json` の `loop.on_diff_doc` に記録する（無ければ `none`）

ドキュメントが「修正のループを回さず、Issue を起票して止まる」運用（マージの後にデプロイする環境など）を指示する場合は、その分岐を `parity-diff` の側が担う（このスキルは、差分の Issue を起票しない）。
差し戻されたときは、対象の target の `on_diff` のドキュメントを確かめ、その運用なら止まって、`parity-diff` の側の分岐に任せる。

## 強度チェックの再実行との関係

差し戻しに対応してスイートの assertion を変えた場合は、`parity-suite` の強度チェックを実行し直す必要がある（[`new-mapping.md`](new-mapping.md) の該当する節）。assertion を変えていなければ要らない。
