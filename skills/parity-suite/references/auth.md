# 認証・認可

原則として、認証が必要な前提で設計する。UI も API も、認証していない状態では特性化できない。

## 認証情報の扱い

シークレットの規律の原本は、`replace-strategy` の `references/project-config.md`「シークレットの扱い」である。
規律は、環境変数から読む・設定には変数名だけを書く・`secrets.wrapper` を前に付ける・値を出力したりくり返したりしない、の 4 つである。ここでは定義し直さない。
このスキルに固有の点だけを、次に定める。

- 読むキーは、選択した target の `auth.roles` である（認証が要らない環境では、`auth` ごと省かれる）。
  環境ごとに認証の方式や認証するユーザーが違うことがあるので、target ごとに持つ。
  各ロールは `roles.<ロール名>.{user_name_env, password_env}` を持ち、値は環境変数の名前である。
  TOTP のシークレットのような追加の要素は、`<論理名>_env` で足される。構造の原本は、スキーマを定義する文書である。
- 値を、スクリーンショット・スナップショット・ネットワークのログなどの採取した成果物にも含めない（マスクの方法は下の「マスキング」）。

## UI の認証

- テストのたびにログインをくり返さず、Playwright の `storageState` で認証の状態を使い回す。
- `auth.roles` のロール名ごとに、`storageState` を分ける（下の認可のため）。
  ロール名は、設定・スイート・`metadata.json` のすべてで同じ名前を使い、読み替えない。
- 特性化に使ったロール名の一覧を、`metadata.json` の `suite.auth_roles` に記録する。
  `parity-replace` と `parity-diff` が、新側で同じロールを使うためである。認証が要らないなら、空の配列にする。

## API の認証

- トークンの取得と更新を、仕組みとして持つ。有効期限が切れてテストが失敗する状態にしない。

## 認可はそれ自体が仕様

誰が何を参照・作成・更新できるかは、仕様である。

- ロール・所属・関与の条件ごとに、代表のユーザーを用意する。
  設定の側では、`auth.roles.<ロール名>` の 1 つのロールが 1 人の代表のユーザーに対応する。設定に無いロールが必要になったら、自分で増やさず、ユーザーに確認する。
- 権限で表示・操作・応答が変わる箇所は、ロールごとに特性化する。
- 401 と 403 の使い分けも対象にする（認証されていないのか、認証済みだが権限が無いのか、の区別）。
- 認証が必要な範囲を特定できない場合は、「未検証」として `gaps.md` に残す（確認済みにしない）。

## マスキング

- スクリーンショット・スナップショット・ネットワークのログに、認証情報・トークン・個人情報を残さない。
  動的な領域をマスクする方針は、[`baseline.md`](baseline.md) の撮影条件に従う。
