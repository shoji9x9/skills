# 強度の検証（故障注入＝ネガティブコントロール）

**この工程を飛ばすと、下流の工程はどれも意味を失う。**
assertion を弱めたテストも、assertion が無いテストも pass する。そのため、テストがあること自体は品質の証拠にならない。

## 位置づけと実行のタイミング

- authoring の時点で通すチェックである。その後はスケジュールで実行せず、スイートの assertion が変わるたびに実行し直す。
  抜けを埋めた場合や、データセットを更新してベースラインを再取得した場合も、assertion が変わったものとして扱う。
- 強度は機能ごとに `strength.md` に記録する。`replace-strategy status` がこれを読む。

## ブラックボックスを前提にする

一般的な mutation testing は、テスト対象（SUT）のソースを変異させる。このスキルでは、その方法をそのままは使えない。
パリティスイートは、現行アプリの外側から当てるブラックボックスのテストであり、現行を変更しない。
変更しないことは設計の原則である。加えて現行は、ソースを変異させて mutant ごとに再デプロイするのが現実的でない生成物のこともある。

そこで変異させる対象を差し替える。テストが観測する境界に、既知の故障を注入する（ネガティブコントロール）。

## ポジティブコントロール（注入しない状態で、すべての検出方法が緑）

故障を注入する前に、注入しない状態で、現行の検出一式のすべての検出方法が緑になることを確かめる。
これが対照になる。対照が無いと、赤くなったのが注入のせいだと言えない。
注入スクリプトの副作用、環境の差、古くなったベースラインでも赤くなるので、常に赤い状態を「捕捉できている」と読み違える。

- 同じ実行系で確かめる。同じ Playwright config、同じ `actionTimeout`、同じ差分ツールとしきい値、同じベースラインを使い、注入用の設定だけを足した状態で 1 回実行する。
- 確かめる対象は、注入した後の判定に使う検出方法のすべて（手書き assertion・特性照合・画素・aria 比較）である。
  1 つでも赤ければ、その原因を取り除いてから注入に進む。赤いまま注入すると、その検出方法の結果を読めない。
- 結果は `strength.md` に記録する。注入しない状態が緑であることは、故障ごとの判定の前提である。注入結果の表だけからは、この前提を復元できない。

## 判定の単位は「現行の検出一式」

**強度は、手書き assertion だけでは判定しない。「現行の検出一式＝手書き assertion ＋ ベースライン ＋ 差分ツール」で判定する。**
故障を注入して、一式のどれも赤くならなければ、一式はその故障の種別に対して弱い。
たとえば、ボタンの色を変えても手書き assertion も差分ツールも赤くならなければ、一式はスタイルに対して弱い。

## 故障カタログ

故障カタログは、思いつきで作らない。既知の回帰の分類から導く。
導出元は、意図的差異レジストリ、`references.db_semantics` の差、コンポーネントライブラリの差、既知の移行のハザードである。
故障クラスと注入手段は次の表のとおりである。

| 故障クラス | 例 | 注入手段 | 検出する方法 |
|---|---|---|---|
| 値・件数・並び（データ由来） | 応答の値・順序の改変 | **上流摂動**（`page.route` で応答を書き換え、描画まで伝わらせる。「上流」の定義は下の節） | 手書き assertion（＋差分ツール） |
| 構造（aria） | role・構造の欠落 | DOM 摂動（`page.evaluate`） | 手書き assertion ＋ aria 比較（摂動の後に aria を取得し直し、**ベースラインを相手に**構造を比べる） |
| 静的なラベル・placeholder・role | 文言・placeholder の改変 | **DOM 摂動**（`page.evaluate`。上流摂動が届かない静的なマークアップのための 2 つ目の手段） | 手書き assertion |
| 要素のスタイル（色・余白・フォント・罫線） | 色・余白などの改変 | **スタイル注入**（`page.evaluate`・`addStyleTag`・CSS の応答の摂動）をして撮り直す | 差分ツールを**ベースラインを相手に**実行する（新側は要らない） |
| 文字を持つ要素のスタイル（名前を付けた要素の子孫が文字を持つ） | 文字を持つ子孫だけの `font-family`・`font-size` の改変 | **スタイル注入**（`addStyleTag` で、文字を持つ子孫の要素にだけ当てる。名前を付けた要素自身には当てない） | 特性照合の `kind: "text"`（**要素自身の計算値は変わらない**。ここが赤くならなければ、`text_owners` を採れていないか、照合されていない） |
| 操作したときの手応え（静止画に現れないスタイル） | `cursor`・`user-select`・`pointer-events` の改変 | **スタイル注入**（`page.evaluate`・`addStyleTag`）をして採り直す | **特性照合が欠かせない**（ここが赤くならなければ、固定のプロパティの集合から外れている）。画素には原則として現れない。ただし `pointer-events` の改変が hover の対象を変え、`:hover` のスタイルの差として間接的に現れることはある。**画素が緑であることを合格の条件にしない** |
| ドキュメントレベルの要素 | `title`・favicon・`meta`・`html[lang]` の改変 | DOM 摂動（`page.evaluate` で `document.title` や `link[rel~="icon"]` の `href` を書き換える） | 手書き assertion（**画素にも特性照合にも aria にも現れない**ので、検出できるのはこれだけである） |
| 頁の高さの決め方（最小幅を持つ頁） | `html`・`body`・コンテナの `height: 100%` を `min-height: 100vh` に置き換える | **スタイル注入**（`overflow/` のスペックを `PARITY_OVERFLOW_FAULT_CSS` 付きで `current` に対して実行する。例: `html, body { height: auto !important; min-height: 100vh !important; }`） | `overflow/` の手書き assertion（**スクロールバーを隠した画素にも、特性照合にも aria にも現れない**。最小幅を持つ頁が無い機能では、対象外として `strength.md` に書く） |
| コンテナのスクロールバー（内部でスクロールするコンテナ） | コンテナの `overflow-x` を `hidden` にする（横のバーを出さずに右端を切る）・`scrollbar-width: none` を当てる | **スタイル注入**（`addStyleTag` でコンテナにだけ当てて採り直す） | 特性照合の `kind: "scroll"`（`scroll/horizontal_bar_px`・`scroll/scrollbar-width` など）。**`scrollbars: shown` で採ったときだけ赤になる**。`hidden` ではバーの厚みが両側とも 0 にそろうので、`hidden` で撮った成果物では「未検証の故障種別」に残す |
| 機能の在否（畳まれたコンテナ） | 機能のコンテナを高さ 0 にする・`hidden` にする・操作を結び付けない | **スタイル注入**（`addStyleTag` でコンテナに `height: 0 !important; overflow: hidden !important` などを当てる）か DOM 摂動 | 手書き assertion（**在否を「コンテナと文言がある」だけで確かめる観点は、この故障を見逃す**。見逃したら観点を直す。[`coverage.md`](coverage.md)「機能の在否は「コンテナと文言がある」で確かめない」） |
| 操作で変わる頁の組み方 | 操作のたびにコンテナの高さを書き直す処理が機能しない | **スタイル注入**（反応の網羅表で `layout.changes: true` の操作のコンテナに、操作の前の寸法を `!important` で固定する） | `layout.covered_by` の手書き assertion（**寸法の式・画素・特性照合は初期表示しか見ないので、ここには現れない**。`changes: true` の操作が無い機能では、対象外として `strength.md` に書く） |
| 押した後に残るもの | 選択の塗りを全列に付ける・絞り込み中の見出しの色を消す・押した後に塗りや焦点の輪を残す・ロゴを押しても遷移しない・Clear が検索条件だけを戻す | **スタイル注入**と **DOM 摂動**を、`aftermath.look.items` の行ごとに当てる。当てる向きは、`observed`（現行で測った値）から失敗する向きを選ぶ。すべての行に同じ注入はしない。押す前のスタイルで固定しても、「付かない」と測った行（塗りが付かない列）は変わらない。文言・属性の印（複数列の並べ替えの順位・向き）は、スタイルでは変わらない。付く見た目は、押す前の計算後のスタイルを `!important` で固定する。付かないと測った見た目には、塗り・輪郭を足す。文言・属性の印は `page.evaluate` で書き換える。`changes: false` の操作では、`look.targets` の論理名に、押した後にだけ残る塗り・輪郭を足す。戻り先は **DOM 摂動**で壊す（遷移や状態を戻す処理を結び付けない。例: `page.evaluate` でロゴのリンクの `href` を今の URL にする） | `aftermath` の `covered_by` と撮る状態（**途中の撮影状態と、出て消える反応は、終えた後の見た目と戻り先を見ない**。`changes: false` の「無いこと」を確かめる assertion も、注入で赤くなることを確かめる。何も確かめていない assertion は、現側でも新側でも緑になる。操作を持たない機能だけを、対象外として `strength.md` に書く） |
| 操作の行き先・書き出す中身 | 別タブ・別画面で開く先を、押した行と別の行にする・書き出すファイルの中身を変える（形式・拡張子・ファイル名は保つ） | 行き先は**上流摂動**か **DOM 摂動**で壊す。上流摂動では、`page.context().route()` で詳細の要求の行 id を隣の行に書き換え、注入を終えたら `unroute` する。別タブの最初の要求は `page.route` では横取りできない（出典: <https://playwright.dev/docs/api/class-page#page-event-popup>）。DOM 摂動では、`page.evaluate` で押した行のリンク・データ属性の id を入れ替える。書き出しは**上流摂動**で壊す（`page.route` で書き出しの応答の本文を 1 セルだけ変えて返す。`Content-Type`・`Content-Disposition` は変えない） | 反応の `covered_by` の手書き assertion（**画素・特性照合・aria は、開いた先のタブの中身も、保存したファイルも見ない**。「ボタンがある」「拡張子が合う」だけを見る assertion は、ここで緑のまま残る。`covered_by` の監査（[`coverage.md`](coverage.md)「`covered_by` をテストへ解決し、assertion が期待値まで届くかを監査する」）と両方で押さえる。別タブで開く操作も書き出しも持たない機能では、対象外として `strength.md` に書く） |
| 送る前の判定・表への書き込み | 上限の判定を外して何件でも送る・書き出しの前のアクセスログを書かない | 送る前の判定は**スクリプト注入**で壊す（`page.addInitScript`・`page.evaluate` で、`pre_send.traced_to` の関数を、判定を通さない版に差し替える。例: 上限を無限大にする）。表への書き込みは、現行アプリを変えずには外せない。そこで、**`covered_by` の assertion を、書き込みの無い状態に当てる**（テストが書いた行を後始末で消してから同じ assertion を当て、赤くなることを確かめる） | `pre_send.items[].sides` の `outside` の側の assertion と、`side_effect_writes.sites[].covered_by`（**画素にも特性照合にも aria にも現れない**。判定も書き込みも持たない機能では、対象外として `strength.md` に書く。`source-only` の書き込みは注入の対象外で、新側では `parity-replace` の `porting.md` で押さえる） |
| 状態表示・送っている間の押し直し | 0 件の文言やページの表示を消す・取得の失敗で警告のダイアログを出す・読み込み中の覆いを足す・送信中の覆いを外して押すたびに送る | 状態表示は、`state_displays` の `setup` と同じ横取り（`page.route`）で状態を作ってから、**DOM 摂動**・**スタイル注入**で当てる。「ある」と測った候補は、`observed` の文言・覆いを消す。「ない」と測った候補（`no-request`・`not-applicable` を除く）は、表示を足す（「ない」の assertion が見逃さないことを確かめる）。押し直しは**スクリプト注入**で壊す（送信中の覆い・不活性・二重送信を弾くフラグを外す） | `state_displays` の `covered_by` と `resubmit.covered_by` の手書き assertion（0 件・失敗・保留中・往復中は、どの撮った状態にも入らない。検出できるのはこれだけである） |
| 待ちの欠落 | 初期応答には対象を置かず、通常の範囲内の遅延の後に描画する | 応答や初期化を遅らせ、Locator と自動リトライの assertion が解決を待つことを確かめる | 手書き assertion |

- 検出＝手書き assertion が赤、または差分ツール（特性照合・画素・aria 比較）が赤。名前を付けた要素のスタイルは特性照合が、名前の無い要素のスタイルは画素が検出する。
  画素で検出できるのは、静止画に現れるものだけである。静止画に現れないスタイルを特性照合の固定のプロパティの集合から外すと、どちらの方法にも現れない。
  集合の原本と理由は [`../scripts/trait-capture.mjs`](../scripts/trait-capture.mjs) の `FIXED_PROPERTIES` にある。
- aria 比較は、取得済みの aria スナップショット（参考資料）のベースラインとの構造の比較である。`parity-diff` の 3 つ目の比較方法（テーブル・フォームの内容のパリティ）に当たる。
- 両方を素通りした故障が、一式の弱点である。強化するか、`gaps.md` に記録する（確認済みにしない）。
- 待ちの欠落は、単に遅くしたり固定の sleep を入れたりして注入しない。
  初期応答の時点では対象の要素か期待値が無く、通常の expect のタイムアウトの中で後から現れる状態を作る。
  注入しない状態と遅延を注入した状態を同じ assertion で green にし、判定の行を `page.$`・`locator.all()`・すぐに値を読む形に変異させると赤になることを確かめる。
  これで、クライアントの描画を待てるかを確かめられる。「採った状態の値を壊す」故障だけでは、これは測れない。

### 「上流」は API とは限らない

上流は、その画面がデータを受け取る境界のことで、API の応答のことではない。
境界は現行アプリの作りで決まる。**対象の画面でデータが実際にどこから来るかを見てから、注入手段を選ぶ。**

| 現行の作り | データの上流 | 上流摂動の具体的な方法 |
|---|---|---|
| 画面が API を呼ぶ | API の応答 | `page.route` で API の応答を書き換える |
| API を持たない（サーバーで描画する・静的なサイト。データはリポジトリの中の静的なファイル） | **document の応答そのもの** | `page.route` で document の応答を捕まえ、`route.fetch()` で得た元の応答の本文を書き換えて `route.fulfill()` する |
| 外部のリソース（画像・フォント・CSS）に依存する | その配信 | `route.abort()` で止める（代わりの見た目や欠落を一式が検出できるかを確かめる） |

出典: <https://playwright.dev/docs/api/class-route>。`route.fetch()` は、元の応答を取得し、変更してから fulfill するための API である。`route.abort()` は要求を中止する。

- API を持たないから上流摂動を組めない、と考えない。静的なサイトにも上流はあり、データ由来の故障（値・件数・並び）はここから注入する。
- 摂動が実際に描画まで伝わったことを確かめてから判定する（ポジティブコントロールの画面と見比べる）。
  ルートの指定が当たらず現行をそのまま描画している状態は、「すべての検出方法が緑＝素通り」と見分けが付かない。
  - 注入は、判定に使う検出方法が読む木に当てる。
    市販の部品が aria のための木を別に作る画面で、画面の側の木だけを書き換えて「aria が赤にならない」と見たことがある。
    これは一式が弱いのではなく、注入が機能していなかった（実測）。伝わったことは、検出方法ごとに確かめる。
  - 確かめたことを `strength.md` の注入結果に残す。摂動を当てた後の観測を 1 つ書く。
    「行数が 45 → 0 になった」「`title` が `X` に変わった」のように、注入が当たったと言い切れる観測値にする。
    要求を文章で書くだけでは、機能しなかった注入と弱い一式が同じ出力になる。
    記録の無い行は「素通り」ではなく「注入が機能したか未検証」として扱い、判定に進めない（`gaps.md` と `strength.md` の「未検証の故障種別」に送る）。
  - 届かなかった理由として、次の 3 つを実測している。10 件中 9 件が「赤にならない」で失敗し、どれも一式が弱いのではなく、注入が届いていなかった。
    - `load` の後も描画が続く（`load` の直後に 45 行、3 秒後に 50 行）。
    - `page.route` を仕掛けた相手が違う（別タブで開く画面には `context.route` が要る）。
    - すべての URL を `route.fetch()` で取得し直すと、行が 0 件になる。

## 要素が消える故障では待たせない（タイムアウトと、解決できないロケータの扱い）

注入で要素が消えると、特性の採取（`locator.evaluate` などの操作）はロケータの解決を待ち続ける。
デフォルトでは待ちは打ち切られない（`actionTimeout` のデフォルトは `0` で、無制限である。出典: <https://playwright.dev/docs/api/class-testoptions>）。
そのため、テスト全体のタイムアウトまで止まる。1 つの故障ごとにその時間を待つと、カタログ全体を回すのが現実的でなくなる。

- 待ちを決める設定は 2 つあり、別のものである。
  操作（特性の採取・クリックなど）は `actionTimeout` で決まる。
  手書き assertion（`expect(locator).toBeVisible()` などの自動リトライの assertion）は、独立した expect のタイムアウトで決まる。
  expect のタイムアウトのデフォルトは 5000ms で、`actionTimeout` とは関係しない（出典: <https://playwright.dev/docs/test-timeouts>）。
  片方だけを縮めても、もう片方を伸ばしているプロジェクトでは、強度チェックが遅いままになる。
- 強度チェックの実行では `actionTimeout` を短く設定する（`use.actionTimeout`）。
  注入用のプロジェクトか設定の側で指定し、通常の実行の値は変えない。
  長さは「現行が正常なら確実に解決する」下限で決め、採用した値を `strength.md` に記録する。
  プロジェクトが `expect.timeout` をデフォルトより伸ばしているなら、注入用の設定で同じように短く上書きする。
- ロケータが解決しないことは、失敗ではなく差分（要素の欠落）として扱う。
  呼び出す側（現側専用のスペック）で捕捉し、その論理名を採取結果から落として先に進む。
  例外を上げて run を止めない。止めると残りの検出方法の判定が取れず、故障を「捕捉できた」のか「実行できなかった」のかが分からなくなる。
  - 同梱の `trait-capture.mjs` は、失敗を、どの論理名かを付けたエラーとして上げる（通常の採取では、原因を特定することを優先するため）。
    強度チェックでは、その例外を呼び出す側で捕捉して欠落に変換する。
  - 欠落に変換してよいのは、ロケータが解決しなかった失敗だけである。
    メッセージに `computed style did not resolve` を含む失敗は、`FIXED_PROPERTIES` の名前をそのブラウザが解決できないという、ツールや環境の側の欠陥であり、要素の欠落ではない。
    これを欠落に変換すると、`trait-compare.mjs` がベースラインのすべての論理名を `missing`（＝赤）として出す。
    すると、注入と関係なく「すべての検出方法が赤＝捕捉」に見える（下の「解決できずに run が止まったことを検出として扱わない」と同じ誤判定）。捕捉せずに停止して、原因を直す。
  - `element is outside the document` を含む失敗も、欠落に変換しない。
    これは、論理名が描かれていない要素（支援技術のためのコピー）に解決しているという、マッピングの側の欠陥である。
    注入と関係なく赤が出るうえ、変換するとコピーから採り続ける状態がそのまま残る（原本は [`baseline.md`](baseline.md)「3 点セット」の、論理名を画面に描かれている要素に付ける規則）。
    捕捉せずに停止して、マッピングを直す。
  - その際、`captureTraits` は論理名を 1 件ずつ（`entries` を 1 要素にして）呼び、失敗した名前だけを落として結果をつなげる。
    まとめて 1 回呼んで try/catch で包むと、最初の失敗で関数が抜け、採取済みの分ごと失う。
    採取結果が空になり、差分ツールはベースラインのすべての論理名を `missing` として出す。
    これは注入と関係なく「すべての検出方法が赤＝捕捉」に見えるので、下の「解決できずに run が止まったことを検出として扱わない」と同じ誤判定になる。
  - 欠落は差分ツールが検出する。`trait-compare.mjs` は、ベースラインにあって採取に無い論理名を `kind: "missing"` として出す（＝特性照合が赤）。
    そのため、欠落を差分として表に記録できる。
- 解決できずに run が止まったことを、検出として扱わない。検出とは、手書き assertion か差分ツールが赤になったことであり、実行系が止まったことはどちらでもない。

## 差分ツールの健全性の確認

強度チェックでは、差分ツールの健全性も確かめる。対象は、`parity-diff` が再利用する 3 つの比較方法（特性照合・画素・aria 比較）のすべてである。

- 注入した既知の差を、差分ツールが赤にできること（スタイル注入 → 特性照合・画素、構造の DOM 摂動 → aria 比較）。
- 注入の量が、ノイズの基準値に埋もれないこと（ノイズの基準値は [`baseline.md`](baseline.md) にある）。

**ここで確かめた差分ツールを、`parity-diff` が現新の比較にそのまま再利用する。**
ツール・しきい値・ノイズの基準値は、`metadata.json` の `differ`・`noise_baseline` で引き渡す。

## カタログの外は射程外

故障注入でわかるのは強度の下限（「少なくともこれらは捕捉した」）であって、完全であることの証明ではない。緑は「反例が見つからなかった」ことを示すにすぎない。
**捕捉した故障の種別と、未検証の種別を `strength.md` に記録し、「強い」と宣言しない。**

- 採っていない状態には、故障を仕込めない。故障注入は採取した状態の中で行うので、状態の網羅そのものはこのチェックでは測れない。
  部品が持つ操作のうち採取した状態に入っていないものは、素通りとしても未検証としても現れない。
  網羅は [`coverage.md`](coverage.md)「部品網羅表」で確かめる。
- カタログに無い種類の浅さは、assertion と期待値を突き合わせる監査で見つける。
  故障注入は種類ごとに 1 つずつ作る。そのため、カタログの外の期待値（押した行の詳細や、書き出した中身のように、テストが確かめるべき部分）に assertion が届いていなくても緑になる。
  反応の網羅表の `covered_by` は、実装する役とは別の subagent が 1 行ずつ監査する（[`coverage.md`](coverage.md)「`covered_by` をテストへ解決し、assertion が期待値まで届くかを監査する」）。
  監査で見つかった種類のうち注入できるものは、この表に行を足す。
- 新側の TypeScript と自作のコード（マッピング層・データセットを生成するツール）に本物の mutation testing を行うことは、このスキルの範囲外である。
  通常の開発の作法であり、パリティの強度の検証とは別のものである。
