# 被覆プロファイル（UI 部品ごとの確認軸）

[`coverage.md`](coverage.md)「部品被覆表」は **項目 × インスタンス** の被覆を記録する。
本ファイルは、その**項目集合そのものを部品の構成要素から機械的に導出する**契約を定める。

**塞ぐ穴**: 被覆表は登録された項目しか数えない。データグリッドで代表列だけを操作して
「フィルターあり」「ソートあり」の 2 項目を登録すれば、他の列・非表示列・横スクロール先の列・
コンテキストメニューは**期待セルにすら現れず**、未測定 0 で収束する。
候補集合（部品の構成要素から導出できる確認対象の全体）と被覆集合（実際にセルを持つもの）の差分が
機械的に残らない限り、欠落は実行エージェントの注意深さ次第で通る。

**部品固有の軸をこのファイルにも `coverage.md` にも書かない。** 軸・候補の列挙方法・必須組み合わせ・
同値クラスの制約は各プロファイルが宣言し、共通処理はプロファイルを解釈するだけにする。
Chart・Tree・DatePicker 等を足すときに共通処理・中心ドキュメントへ部品固有の条件分岐を追加しない
（追加が要るなら、それは共通処理の抽象が足りていない）。

## 同梱プロファイル

正本は配布スキル内の [`../assets/coverage-profiles/`](../assets/coverage-profiles/)。
インストール先に外部参照を要求しない（実行時はスキルディレクトリ内から読む）。

| プロファイル | ファイル | 対象 |
|---|---|---|
| データグリッド | [`datagrid.json`](../assets/coverage-profiles/datagrid.json) | 1 インスタンスが多数の列を持ち、列ごとに操作可否が設定される表形式部品 |

形式の正本は [`profile-schema.json`](../assets/coverage-profiles/profile-schema.json)、
追加手順は同ディレクトリの [`README.md`](../assets/coverage-profiles/README.md)。

## プロファイルの選択

1. 被覆表に載せる部品ごとに、`applies_to` が一致する同梱プロファイルを選ぶ
2. **一致するプロファイルが無い複雑な部品を、暗黙に汎用扱い（プロファイル無しの 項目 × インスタンス）にしない。**
   `profile: null` ＋ `profile_absent_reason` を書き、同じ理由を `gaps.md` の未検証領域に残す。
   理由が空なら `coverage-expand.mjs` が落とす（免除の根拠が残らないため）
   - 「複雑な部品」は**構成要素ごとに操作可否が設定される部品**（列・系列・ノード・セル等の単位で
     filterable / sortable / 選択可否などが変わるもの）。単一の操作しか持たない部品は対象外でよい
   - 汎用扱いにしてよいのは、構成要素の軸を持たない部品だけ。判断が付かないときは未検証に倒す
3. 該当プロファイルが無く、その部品の被覆が本質的なら、新しいプロファイルの追加を検討する（追加手順は上記 README）

## 候補の列挙（プロファイルが宣言する `enumeration`）

候補は**インスタンスごとに列挙する**。同じ部品でも画面ごとに列構成・権限・行状態が違うため、
1 インスタンスの列挙を他インスタンスへ流用しない（被覆表のインスタンス規則と同じ）。

- **列挙元は現行ソース・設定・実 UI。** ソースと設定は**候補集合の抽出**に使い、
  **UI 操作の期待値は動作中の現行アプリで確定する**——静的解析だけで確認済みにしない
  （「ソースに `sortable: true` と書いてある」は候補であって実測ではない）
- 列挙は `instances[].enumeration` に記録する。`source`（`kind` / `ref` / `version` / `extracted_at` /
  `condition`）が**来歴**で、どの版のどこから何を条件に抜いたかを後から辿れる形にする。
  `condition` には抽出条件（例: 「グリッド定義の `columns` 配列の全要素。`hidden` も含める」）を書く
- **ソースを読めない場合は確認済みにしない。** `complete: false` ＋ `incomplete_reason` に
  「実 UI からの列挙手順」と「不足しているもの」を書く。`complete: false` は
  `coverage-expand.mjs` / `coverage-check.mjs` の双方で未測定に倒れる（fail-closed）
- 非表示要素・横スクロールしないと到達しない要素は**列挙から落ちやすい**。
  プロファイルの `enumeration.pitfalls` がその部品で落ちやすい経路を列挙するので、
  列挙時に一つずつ潰したことを `condition` に残す

## 候補の展開（プロファイルが宣言する `candidate_rules`）

共通処理は各ルールについて、ルールが指定した軸の**直積**を取って候補を作る。

- 軸は 2 種類。`element` 軸はインスタンスの `enumeration.elements[<軸 id>]` から値を取り、
  `enum` 軸はプロファイルの `values` から取る
- `guard` は `element` 軸の要素が持つ `flags` に対する条件。`{"column.sortable": true}` なら
  `sortable: true` の列だけが候補になる（設定で無効な操作を候補に数えない）
- 候補 id は決定論的に組む: `<ルール id>/<軸値を "/" 連結>`。軸値の並びは**そのルールの `axes` の順**（プロファイルの `axes` 宣言順ではない）。
  順序と区切りを固定するので、同じ列挙からは常に同じ id が出る
- **`required_rules` に挙げたルールが候補を 1 件も生まなかったら失敗させる。**
  コンテキストメニューのように「列挙されなければ静かに 0 件になる」軸を、
  「その部品には無い」と区別できない形で通さないため

### 「本当に無い」を主張する（`justified_absences`）

**fail-closed を行き止まりにしない。** 右クリックメニューを持たないグリッドのように、
候補が 0 件になるのが正しい場合がある。逃げ道が無いと、フラグを偽って `true` にし
`absent` を測る——測定結果に嘘を入れる——以外に収束する手段が消える。

根拠を `instances[].enumeration.justified_absences` に残す。共通処理はこれを読んで、
根拠のある不在だけを通す（根拠が空・使われていない免除はいずれも失敗）。

| `scope` | 使うとき | 通す判定 |
|---|---|---|
| `<軸 id>` | その軸の要素が **1 件も無い**（`elements[<軸 id>]` が空） | その軸を使う `required_rules` の候補 0 件 |
| `<軸 id>/<要素 id>` | 要素は在るが、どのルールの `guard` も通らず候補にならない | その要素の「どの候補にも現れない」 |

- `reason` は必須で、**実 UI でどう確かめたかを書く**（「無いと思う」は根拠にしない）
- **要素が在る軸に軸スコープの免除は使えない。** 要素ごとに根拠を出す（軸ごと免除は列挙をまとめて飛ばせてしまう）
- **効いていない免除は失敗させる。** 状況が変わって候補が展開されるようになったのに根拠だけが残ると、
  古い免除が効いているように見える
- `parity-diff` も要素スコープの免除を読む（軸スコープは要素が無い状態なので突き合わせ対象が生じない）

展開した候補は被覆表の `items` へ 1 対 1 で落とし、`items[].candidate` に
ルール id と軸値を残す。**候補と項目の対応が付かないものは欠落として扱う**（下記）。

## 照合（共通処理が機械的に行う）

`scripts/coverage-expand.mjs` が、被覆表とプロファイルから次を判定する。1 件でも残れば非ゼロ終了。

| 判定 | 失敗にするもの |
|---|---|
| 欠落 | 候補に対応する項目・セルが無い |
| 未列挙 | `enumeration` が無い・`complete: false`・`required_rules` が 0 件 |
| 余剰 | 候補集合に無い項目が `candidate` 付きで載っている（列挙とズレている） |
| 未測定 | セルが `unmeasured`、または行が無い |
| 証拠なし | `present` / `absent` なのに `evidence` が空 |
| 対応付けなし | `present` なのに `covered_by` が空 |
| 同値クラス | 下記の制約に反する |

**未測定・証拠なし・対応付けなしの判定規則は [`coverage.md`](coverage.md)「部品被覆表」が正本**で、
ここでは候補由来の期待セルに対して同じ規則を当てるとだけ決める（規則をここへ転記しない）。

## 視覚採取の同値クラス

**全候補の直積をスクリーンショットとして保存しない。** 列が 40 ある × 操作が 6 種なら 240 枚になり、
`parity-diff` の分類コストが実測不能まで膨らむ。

代わりに **E2E で全候補の機能配線を確認したうえで**、視覚採取は同値クラスの代表だけにする。

- **E2E は削減の対象外。** 削減してよいのは視覚ベースラインの採取だけで、
  全候補は `covered_by` に assertion を持つ必要がある（機能配線の確認は候補ごとに要る）
- 同値クラスは `equivalence_classes[]` に書く。`axis`（どの軸で束ねたか）・`rationale`（束ねてよい根拠）・
  `members`（所属する候補 id）・`representative`（採取する候補 id）を持つ
- **束ねてよい軸はプロファイルの `equivalence.reducible_axes` が決める。**
  そこに無い軸で束ねたら失敗させる（例: 描画が軸ごとに変わる軸で束ねると差分が見えなくなる）
- **全候補の所属を検査する。** どのクラスにも属さない候補、複数クラスに属する候補、
  `members` に含まれない `representative` はいずれも失敗にする
- `rationale` が空なら失敗させる。**「同じに見えたから」は根拠にしない**——
  現行アプリで実際に同じ描画になることを確かめた手順を書く

## `parity-diff` の収束との関係

`parity-diff` は被覆表を**プロファイル無しで数え直す**（プロファイルは `parity-suite` 側の同梱物で、
`parity-diff` のインストールには含まれないため）。数え直しの規則は次のとおりで、
正本は `parity-diff` の `references/convergence.md`。

- `profile` を宣言した部品の期待セルは、**その部品の `items` × インスタンス**ではなく
  **インスタンスごとに記録された候補**（`instances[].candidates`）になる
- **`enumeration.elements` に載っている要素が、そのインスタンスの候補に 1 件も現れなければ失敗させる。**
  「列は 40 列と列挙したが候補は代表 1 列だけ」を機械的に落とす。
  **突き合わせは `items[].candidate.axes` を使って軸ごとに行う**——候補 id を `/` で割った値を
  軸をまたいだ和集合で見ると、別軸に同じ値がある要素（列名 `default` と条件 `default` 等）が
  自分の軸の候補に無くても通ってしまう。軸値を引けない候補は和集合へフォールバックせず未測定にする。
  `justified_absences` の要素スコープがあるものは通す
- 同値クラスの所属検査（全候補が過不足なくいずれかのクラスに属する）も `parity-diff` 側で行う
- 展開ルールの解釈（`guard`・`required_rules`）は `parity-suite` 側の `coverage-expand.mjs` が
  authoring 時に検査し、結果を被覆表の `conformance` に記録する。
  **`conformance` が無い・`ok: false` の被覆表は `parity-diff` が収束させない**
