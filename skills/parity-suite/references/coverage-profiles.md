# 網羅プロファイル（UI 部品ごとの確認の軸）

[`coverage.md`](coverage.md)「部品網羅表」は、**項目 × インスタンス** の網羅を記録する。
このファイルは、その項目の集合そのものを、部品の構成要素から機械的に導くための取り決めを定める。

このファイルで塞ぐ抜けは次のとおりである。網羅表は、登録された項目しか数えない。
データグリッドで代表の列だけを操作して「フィルターあり」「ソートあり」の 2 項目を登録すると、ほかの列・非表示の列・横にスクロールした先の列・コンテキストメニューは、期待するセルにすら現れない。
その結果、未測定 0 件で収束する。
候補の集合（部品の構成要素から導ける確認対象の全体）と、網羅した集合（実際にセルを持つもの）の差が機械的に残らない限り、欠落が通るかどうかは、実行するエージェントの注意深さで決まってしまう。

**部品に固有の軸は、このファイルにも `coverage.md` にも書かない。**
軸・候補の列挙の方法・必須の組み合わせ・同値クラスの制約は、各プロファイルが宣言する。共通の処理は、プロファイルを解釈するだけにする。
Chart・Tree・DatePicker などを足すときに、共通の処理や中心のドキュメントに、部品に固有の条件分岐を足さない。
足す必要があるなら、共通の処理の抽象が足りていない。

## 同梱プロファイル

原本は、配布スキルの中の [`../assets/coverage-profiles/`](../assets/coverage-profiles/) にある。
インストール先に、外のファイルの参照を求めない（実行時はスキルのディレクトリの中から読む）。

| プロファイル | ファイル | 対象 |
|---|---|---|
| データグリッド | [`datagrid.json`](../assets/coverage-profiles/datagrid.json) | 1 つのインスタンスが多くの列を持ち、列ごとに操作できるかが設定される表形式の部品 |

形式の原本は [`profile-schema.json`](../assets/coverage-profiles/profile-schema.json)、追加の手順は同じディレクトリの [`README.md`](../assets/coverage-profiles/README.md) にある。

## プロファイルの選択

1. 網羅表に載せる部品ごとに、`applies_to` が一致する同梱のプロファイルを選ぶ。
2. 一致するプロファイルが無い複雑な部品を、暗黙に汎用の扱い（プロファイル無しの 項目 × インスタンス）にしない。
   `profile: null` と `profile_absent_reason` を書き、同じ理由を `gaps.md` の未検証の領域に残す。
   理由が空なら、`coverage-expand.mjs` が失敗にする（免除の根拠が残らないため）。
   - 「複雑な部品」は、構成要素ごとに操作できるかが設定される部品である。
     列・系列・ノード・セルなどの単位で、filterable・sortable・選択できるかなどが変わるものを指す。単一の操作しか持たない部品は、対象外でよい。
   - 汎用の扱いにしてよいのは、構成要素の軸を持たない部品だけである。判断が付かないときは、未検証として扱う。
3. 該当するプロファイルが無く、その部品の網羅が欠かせないなら、新しいプロファイルを足すことを検討する（追加の手順は上の README）。

## 候補の列挙（プロファイルが宣言する `enumeration`）

候補はインスタンスごとに列挙する。
同じ部品でも、画面ごとに列の構成・権限・行の状態が違う。そのため、1 つのインスタンスの列挙をほかのインスタンスに使い回さない（網羅表のインスタンスの規則と同じ）。

- 列挙の元は、現行のソース・設定・実際の UI である。
  ソースと設定は、候補の集合を取り出すのに使う。UI の操作の期待値は、動いている現行アプリで確定する。静的な解析だけで確認済みにしない。
  「ソースに `sortable: true` と書いてある」は候補であって、実測ではない。
- 列挙は `instances[].enumeration` に記録する。
  `source`（`kind`・`ref`・`version`・`extracted_at`・`condition`）は出所で、どの版のどこから、何を条件に取り出したかを後からたどれる形にする。
  `condition` には、取り出した条件を書く（例: 「グリッドの定義の `columns` 配列のすべての要素。`hidden` も含める」）。
- ソースを読めない場合は、確認済みにしない。
  `complete: false` と `incomplete_reason` に、「実際の UI から列挙する手順」と「足りないもの」を書く。
  `complete: false` は、`coverage-expand.mjs` でも `coverage-check.mjs` でも未測定として扱われる（判定できないときは失敗として扱う）。
- `enumeration.sources` は、強い順（`current-source` → `config` → `app-ui`）に宣言する。
  順序の無い集合として扱うと、いちばん弱い情報源だけで `complete: true` が通る。
  `fail_closed` が求めるのは、ソースを読めないときの `complete: false` だけである。そのため、読めたのに読まなかった場合は何も残らない。
  並びが強い順でない、語彙に無い、重複している、のどれかなら、`validateProfile` が失敗にする。
- 一次情報源（`current-source`）以外で列挙したら、`stronger_source_unavailable_reason` に理由を書く（受け取っていない・難読化されている・動的に生成されて追えない、など）。
  これは `fail_closed` と対になる側のチェックで、記録する側と判定する側の両方が求める。
  一次情報源で列挙したのに理由が残っていれば、使われていない免除として失敗にする。
  部品・インスタンスの集合の側の同じ宣言（`component_inventory`・`instance_inventory`）は、[`coverage.md`](coverage.md)「3 つの集合に出所と完全性を要求する」で定義する。
- 非表示の要素や、横にスクロールしないと届かない要素は、列挙から抜けやすい。
  プロファイルの `enumeration.pitfalls` が、その部品で抜けやすい箇所を挙げている。列挙するときに 1 つずつ確かめ、確かめたことを `condition` に残す。

## 候補の展開（プロファイルが宣言する `candidate_rules`）

共通の処理は、各ルールについて、ルールが指定した軸の直積を取って候補を作る。

- 軸は 2 種類ある。`element` 軸は、インスタンスの `enumeration.elements[<軸 id>]` から値を取る。`enum` 軸は、プロファイルの `values` から取る。
- `guard` は、`element` 軸の要素が持つ `flags` に対する条件である。
  `{"column.sortable": true}` なら、`sortable: true` の列だけが候補になる（設定で無効にした操作を候補に数えない）。
- 候補の id は決定論的に組む。形は `<ルール id>/<軸の値を "/" でつないだもの>` である。
  軸の値の並びは、そのルールの `axes` の順にする（プロファイルの `axes` の宣言の順ではない）。
  順序と区切りを固定するので、同じ列挙からは常に同じ id が出る。
- `required_rules` に挙げたルールが候補を 1 件も生まなかったら、失敗にする。
  コンテキストメニューのように、列挙されなければ警告なしに 0 件になる軸を、「その部品には無い」と区別できない形で通さないためである。
- 同じ要求を排他な `guard` で分けたルールは、代わりの組（ルールの id の配列）として 1 つの要素に書く。どれか 1 つが候補を生めば満たす。
  datagrid の `["row-select", "row-select-revealed"]`（初期表示の列と、表示を切り替えて出す列の、選択の塗り）がこれに当たる。
  別々の要素にすると、すべての列が初期表示で非表示のグリッドのように、片方の `guard` に当たる要素しか無い正当な部品が行き止まりになる。
  要素が実在するので、`justified_absences` でも通せないからである。組のすべてのルールが候補 0 件のときは、すべてに根拠が要る。
  - 組にできるのは、次の条件をすべて満たすルールだけである。
    - すべてのルールに、同じ `requirement`（要求の id）を明示している。
    - `axes` が同じ並びである。
    - `guard` が互いに排他である（同じフラグに逆の値を求める）。
  - 軸や `guard` の形からわかるのは、候補が重ならないことだけで、同じ要求かどうかは宣言でしか表せない。
    別の要求を組にすると、片方の候補が、もう片方の列挙の抜けを隠す。`validateProfile` が失敗にする。

### 操作が要求する撮影状態（`visual_states`）

ルールは「何を測るか」だけでなく、「その操作でどの見た目の状態になるか」も宣言する。
撮影状態を部品ごとに手で数えると、測った操作と撮った状態が結び付かず、撮っていない状態の差は「差 0 件」と同じに見える。
原本は `parity-suite` の [`baseline.md`](baseline.md)「撮影状態の決め方（1）網羅表から導く」にある。

- `candidate_rules[].visual_states` には、6 種類の語彙から選んで書く。
  - 操作の途中の状態は、`opens-container`（コンテナを開く）・`hover`（ポインターを乗せる）・`focus`（フォーカスを当てる）・`active`（押している最中）・`disabled`（不活性）である。
  - 操作を終えた後に残る状態は、`after-operation`（選択の塗り・絞り込み中の見出しの印・並べ替えの印）である。

  途中の種別だけを宣言しない。選択・絞り込み・並べ替えのように結果が画面に残る操作は、残る見た目を撮らないと、差が「差 0 件」と同じに見える。
  結果が列ごとに違いうる操作（行の選択の塗り）は、ルールの `axes` に列の軸を入れて、列ごとに候補を立てる。
- 見た目が変わらないルールは、空の配列と `no_visual_state_reason` を書く。
  キーごと省くと、「見た目が変わらない」と「考えていない」が同じに見えるので、`validateProfile` が失敗にする。
- `coverage-expand.mjs --write` が、この宣言を網羅表の `items[].visual_states` に書き戻す。
  そして、`value: present` のセルから、**部品 × インスタンス × 要求元の候補 × 種別** の行を `visual_state_coverage.rows` に作る。
  種別だけで束ねると、同じ種別を求める別の候補が 1 行にまとまり、片方だけ撮れば通ってしまう。
  ルールの単位でもまとめない。ルールは軸の直積に展開されるので、まとめると `reducible_axes` に無い軸まで畳んでしまう。
  撮るか撮れないかは、プロファイルではなくインスタンスごとの実測で決まる。そのため、行の `captured`・`reason` は人かエージェントが埋める。

### 「本当に無い」を主張する（`justified_absences`）

判定できないときに失敗として扱う仕組みを、行き止まりにしない。
右クリックのメニューを持たないグリッドのように、候補が 0 件になるのが正しい場合がある。
逃げ道が無いと、フラグを偽って `true` にし、`absent` を測る以外に収束する手段が無くなる。これは、測定の結果に嘘を入れることになる。

根拠は `instances[].enumeration.justified_absences` に残す。共通の処理はこれを読み、根拠のある不在だけを通す（根拠が空の免除も、使われていない免除も、失敗にする）。

| `scope` | 使うとき | 通す判定 |
|---|---|---|
| `<軸 id>` | その軸の要素が **1 件も無い**（`elements[<軸 id>]` が空） | その軸を使う `required_rules` の候補が 0 件 |
| `<軸 id>/<要素 id>` | 要素はあるが、どのルールの `guard` も通らず候補にならない | その要素が「どの候補にも現れない」 |

- `reason` は必須で、実際の UI でどう確かめたかを書く（推測で「無い」とした結果は根拠にしない）。
- 要素がある軸には、軸のスコープの免除を使えない。要素ごとに根拠を出す。軸ごとの免除を許すと、列挙をまとめて飛ばせてしまう。
- 使われていない免除は失敗にする。状況が変わって候補が展開されるようになったのに根拠だけが残ると、古い免除が今も機能しているように見える。
- `parity-diff` も、要素のスコープの免除を読む。軸のスコープは要素が無い状態なので、突き合わせる対象が生じない。

展開した候補は、網羅表の `items` に 1 対 1 で対応させ、`items[].candidate` にルールの id と軸の値を残す。
候補と項目の対応が付かないものは、欠落として扱う（下の表）。

## 照合（共通の処理が機械的に行う）

`scripts/coverage-expand.mjs` が、網羅表とプロファイルから次のことを判定する。1 件でも残れば、0 以外で終了する。

| 判定 | 失敗にするもの |
|---|---|
| 欠落 | 候補に対応する項目・セルが無い |
| 未列挙 | `enumeration` が無い・`complete: false`・`required_rules` が 0 件 |
| 出所 | 集合の出所（`component_inventory`・`instance_inventory`・`components[].source`・`enumeration.source`）が無い・語彙に無い `kind`・完全性を宣言していない・一次情報源を使わなかった理由が無い |
| 余剰 | 候補の集合に無い項目が、`candidate` 付きで載っている（列挙とずれている） |
| 未測定 | セルが `unmeasured`、または行が無い |
| 証拠なし | `present`・`absent` なのに `evidence` が空 |
| 対応付けなし | `present` なのに `covered_by` が空 |
| 同値クラス | 下の制約に反する |
| 撮影状態 | 導いた行（**要求元の候補 × 種別**。同値クラスの代表にまとまる）の `captured`・`reason` がどちらも空、行が導いたものと過不足がある、`captured` が `capture_conditions.states`（`opens-container` は `popup_inventory` にも）に無い、同じ撮影の単位で `captured` を根拠なく使い回している |

未測定・証拠なし・対応付けなしの判定の規則は、[`coverage.md`](coverage.md)「部品網羅表」で定義する。
このファイルでは、候補から導いた期待するセルにも同じ規則を当てる、とだけ決める（規則はここに転記しない）。

## 視覚採取の同値クラス

すべての候補の直積を、スクリーンショットとして保存しない。
列が 40 あって操作が 6 種類なら 240 枚になり、`parity-diff` の分類の手間が、測れないほど大きくなる。

その代わりに、すべての候補の機能が動くことを E2E で確かめたうえで、視覚の採取は同値クラスの代表だけにする。

- E2E は減らす対象にしない。
  減らしてよいのは、視覚のベースラインの採取だけである。すべての候補は `covered_by` に assertion を持つ必要がある（機能が動くことの確認は、候補ごとに要る）。
- 同値クラスは `equivalence_classes[]` に書く。
  `axis`（どの軸で束ねたか）・`rationale`（束ねてよい根拠）・`members`（属する候補の id）・`representative`（採取する候補の id）を持つ。
- 束ねてよい軸は、プロファイルの `equivalence.reducible_axes` が決める。
  そこに無い軸で束ねたら、失敗にする（例: 描画が軸ごとに変わる軸で束ねると、差分が見えなくなる）。
- すべての候補の所属を確かめる。どのクラスにも属さない候補、複数のクラスに属する候補、`members` に含まれない `representative` は、どれも失敗にする。
- 撮影状態の行も、同値クラスでまとまる。クラスに属する候補は代表の行にまとまり、属さない候補は自分の行を持つ。
  原本は `parity-suite` の [`baseline.md`](baseline.md)「撮影状態の決め方（1）網羅表から導く」にある。
  クラスを宣言しない限り、まとめる処理は起きない。ルールの単位でまとめると、`reducible_axes` に無い軸まで畳むからである。
- `rationale` が空なら失敗にする。「同じに見えたから」は根拠にしない。現行アプリで実際に同じ描画になることを確かめた手順を書く。

## `parity-diff` の収束との関係

`parity-diff` は、網羅表をプロファイル無しで数え直す。プロファイルは `parity-suite` の側の同梱物で、`parity-diff` のインストールには含まれないからである。
数え直しの規則は次のとおりで、原本は `parity-diff` の `references/convergence.md` にある。

- `profile` を宣言した部品の期待するセルは、その部品の `items` × インスタンスではなく、インスタンスごとに記録された候補（`instances[].candidates`）になる。
- `enumeration.elements` に載っている要素が、そのインスタンスの候補に 1 件も現れなければ、失敗にする。
  「列は 40 列と列挙したが、候補は代表の 1 列だけ」を、機械的に失敗にする。
  - 突き合わせは、`items[].candidate.axes` を使って軸ごとに行う。
    候補の id を `/` で分けた値を、軸をまたいだ和集合で見ると、別の軸に同じ値がある要素（列名の `default` と条件の `default` など）が、自分の軸の候補に無くても通ってしまう。
  - 軸の値を取得できない候補は、和集合の判定に切り替えず、未測定にする。
  - `justified_absences` の要素のスコープがあるものは通す。
- 同値クラスの所属の確認（すべての候補が、過不足なくどれかのクラスに属する）も、`parity-diff` の側で行う。
- 展開のルールの解釈（`guard`・`required_rules`）は、`parity-suite` の側の `coverage-expand.mjs` が authoring の時点で確かめ、結果を網羅表の `conformance` に記録する。
  `conformance` が無い網羅表と、`ok: false` の網羅表は、`parity-diff` が収束させない。
