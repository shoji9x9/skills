# Writing Style

人が読む日本語の文章を、規則に沿って書いて読み直す。
規則の本文と読み直しの 3 つの問いは [`references/rules.md`](references/rules.md) で定義する。この SKILL.md には書き写さない。
プロジェクトは、設定で自分たちの規約・使わない語の一覧・文章のリンターを足して、規則を拡張できる（「プロジェクトの規約で拡張する」）。

## 使い方

```text
writing-style [<読み直す文 | ファイル>]
```

- 引数なし: これから書く文章に規則を当てる。他のスキルの手順から参照されたときは、そのスキルが書いた文を対象にする
- 文やファイルを渡したとき: その文章を読み直し、直した結果を返す

例を次に挙げる。

```text
writing-style "feat: 型の検査を外す書き方を、報告する残りではなく直す対象にする"
writing-style docs/setup.md
```

## 前提

- 前提スキル・MCP は要らない。エージェントが規則を読んで当てる
- Node.js は、設定ファイル（`.config/skills/shoji9x9/writing-style.jsonc` など）を読むときだけ要る（同梱の `scripts/skill-config/skill-config.mjs`）。
  設定ファイルがどの層にも無ければ、Node.js なしでスキルの規則だけを当てる。設定ファイルがあって Node.js が無ければ、設定を読めないとして止まる
- 文章のリンター（textlint など）は前提にしない。設定の `lint_command` で指定されたときだけ実行する

## 他のスキルから使う

要約の文や人が読む本文を書くスキルは、規則を書き写さず、書く手順に次の形の 1 行だけを置く。

```text
<書いた文> は、外に出す前に `writing-style` スキルの手順で読み直す（スキルが無ければ省く）。
```

スキルは `description` を見てエージェントが自分で呼ぶので、「タイトルを書いた直後」のような細かい時点では呼ばれないことがある。
そのため、呼ぶ時点は呼び出す側の手順に書く。外に出す時点は、commit・Issue と PR の作成・コメントの投稿と、それぞれのタイトルや本文の編集である。

## プロジェクトの規約で拡張する

スキルの規則は、どのプロジェクトでも使える最小の集合である。
プロジェクトは、リポジトリの層の設定（`.config/skills/shoji9x9/writing-style.jsonc`）に次のキーを書いて、自分たちの好みに合わせて拡張する。
キーの型は [`config-schemas/writing-style.schema.json`](config-schemas/writing-style.schema.json) で、置き場所と書き込みの決まりは [`references/config-files.md`](references/config-files.md) で定義する。

| キー | 書くもの | エージェントがすること |
| --- | --- | --- |
| `style_docs` | 文章の規約を書いた文書のパスの配列 | 規則に加えて従う。規則を当てる対象・対象外、用語、規則の追加や上書きを書ける。スキルの規則と食い違えば、この文書を優先する |
| `word_list` | 使わない語と言い換え先の一覧のパス | 規則 2・8 で、一覧の語を言い換え先に書き換える。形式は決めない（Markdown の表・JSON など、エージェントが読めればよい） |
| `lint_command` | 文章をチェックするコマンド | 読み直したファイルのパスを引数に付けて、リポジトリのルートで実行し、指摘を直す |

```jsonc
{
  "style_docs": ["docs/style.md"],
  "word_list": "docs/word-list.md",
  "lint_command": "npx textlint"
}
```

上の値は例である。導入先に実在するファイルとコマンドを書き、無いものはキーごと書かない。
規約の文書には、スキルの規則を書き写さない。足したいことと変えたいことだけを書く。

## 手順

規則は日本語の文章に当てる。英語などで書いた文は、日本語に書き直さない。

1. [`references/rules.md`](references/rules.md) を読む。読めなければ、読み直しを済んだものとして扱わず、読めなかったことを報告する
2. 設定を読む。作業しているプロジェクトのルートで実行し、スキルのディレクトリへ `cd` しない。
   読み取りは cwd から設定ファイルの置き場所を決めるので、スキルのディレクトリで実行すると、プロジェクトの設定を見つけられずに `{}` を出力する。

   ```bash
   CFG="<このスキルのディレクトリ>/scripts/skill-config/skill-config.mjs"
   node "$CFG" dump writing-style
   ```

   exit 0 なら、出力はキーごとに `{"value": ..., "source": ..., "path": ...}` の形である。
   `style_docs.value`（パスの配列）と `word_list.value`（パス）のファイルを読む。`path` は設定ファイル自身のパスなので、規約として読まない。
   設定が無ければ `{}` が出力され、読むものは無い。
   指定されたファイルが無ければ、そのことを報告し、そのファイル無しで続ける。
   exit 1（設定の誤り）なら、エラーの内容を利用者に示して止まる。設定を無視して続けない。
   Node.js が無ければ、設定ファイル（[`references/config-files.md`](references/config-files.md)「層と置き場所」の 3 つ）が無いことを確かめて、スキルの規則だけで続ける。1 つでもあれば止まる
3. 書く文章に、規則 1〜10 と、手順 2 で読んだ規約と一覧を当てる
4. 要約として読まれる文（rules.md の規則 10 に挙げたもの）は、外に出す前に「要約として読まれる文の読み直し」の 3 つの問いで読み直す。
   答えられない問いがあれば書き直し、書き直した文にもう一度 3 つの問いを当てる
5. ファイルを書いたか直したときに、設定に `lint_command` があれば、そのファイルのパスを引数に付けて実行する。
   指摘を直して、0 件になるまで繰り返す。コマンドが失敗して指摘を読めないときは、合格として扱わず、そのことを報告する。
   リンターは対象外のファイルを飛ばして指摘 0 件で終わることがあるので、出力で、渡したファイルをチェックしたこと（チェックした件数など）を確かめる。
   確かめられなければ、そのファイルはリンターでチェックしていないと報告する
6. 文やファイルを渡されて読み直したときは、直した箇所ごとに、元の文・直した文・当たった規則か問いを報告する。直す箇所が無ければ、そう報告する

既にある文書を規則に合わせて書き換えるときは、rules.md の「書き換えで変えないもの」に従い、書き方だけを変える。
