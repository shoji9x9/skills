# 質問票と追加資産依頼（工程 5）

**質問票は不足の一覧ではなく、回答可能な問いの集合である。** 「データ辞書をください」では回答が返らない。
先方・SME が**その場で判断できる粒度**まで割り、候補を提示し、答えないと何が止まるかを添えて初めて回答が返る。

成果物は `.replace/bootstrap/questionnaire.md`（テンプレート: [`../assets/questionnaire-template.md`](../assets/questionnaire-template.md)）。

## 質問 1 件に必ず含める項目

| 項目 | 内容 |
|---|---|
| 対象項目 | どのテーブル・カラム・画面・機能の話か（1 件 1 対象。複数をまとめない） |
| 必要な判断 | 何を決めてほしいか（「取りうる値の一覧」「初期状態」「この遷移が正常系か」） |
| 候補 | コード・資産から導出できた候補と、それぞれの導出元。**候補が無いなら「候補なし」と書く**（空欄にしない） |
| 根拠 | ここまでに分かっていること（enum の定義位置、既存テストの使用例など） |
| 未回答時の影響 | 回答が無いと何が止まるか（どの機能の `parity-suite` が開始できないか、どの検証が未検証として残るか） |

- **候補を提示するのは回答を誘導するためではなく、回答コストを下げるため**である。候補に無い答えを選べる形にする
- **未回答時の影響を「不明」で埋めない。** 影響が分からないなら、それは質問の粒度が粗いか対象が曖昧なので、先に割る

## 追加資産依頼

意味論の質問とは別に、**資産そのものの依頼**を分けて立てる（回答者が違うことが多いため）。

- 依頼する資産・その用途・代替できる資産（例: DDL が出せないならスキーマダンプでもよい）を書く
- **本番データを依頼しない。** 依頼するのは非本番・匿名化済みのサンプル、または意味論を説明するドキュメント
- 受領できない場合に何を諦めることになるかを書く（そのまま `gaps` の候補になる）

## 優先度

回答を待つ順序は**ブロックの深さ**で決める。件数や難易度で並べない。

| 優先度 | 対象 |
|---|---|
| 最優先 | 起動・ログイン・主要画面到達に必須（工程 6 が進まない） |
| 高 | スキーマ・DB 設定の不足（工程 3 が確定しない） |
| 中 | 特定機能のシナリオに必須（その機能の `parity-suite` が開始できない） |
| 低 | 代表性・網羅性の向上（未確認でも `gaps` に残して進める） |

## 回答が返ったら

- 回答を `semantics.md` の該当行へ反映し、**確認状態を「確定済み」に更新して回答者と回答日を根拠に残す**（回答そのものが根拠であり、後から辿れるようにする）
- 回答で不足が埋まった資産は `assets-inventory.md` の区分を更新する
- **回答が「分からない」だった場合も記録する。** 確認待ちのまま残すのと、確認して確定できないと分かったのは別の状態であり、後者はその機能を恒久的に `gaps` へ回す判断材料になる
- 反映後、`--resume` で停止していた工程から再開する
