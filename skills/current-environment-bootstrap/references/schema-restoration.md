# DB スキーマと設定の復元（工程 3）

**復元の合否は「テーブルが作れたか」ではなく「挙動に影響する設定まで根拠を持って決まったか」で判定する。**
照合順序 1 つで並び順が変わり、その差は後段の `parity-diff` で「説明できない差分」として現れる——そこまで来てから遡ると、現・新のどちらが正しいかを判定する基準が既に無い。

結果は `.replace/bootstrap/schema.md`（テンプレート: [`../assets/schema-template.md`](../assets/schema-template.md)）に記録する。**項目ごとに根拠（どの資産・どのコードの何行目か）を書く。**

`dataset_mode: static`（DB を持たない構成）では本工程を「該当なし」として記録し、代わりに現行の静的データ形式（ファイル配置・フィールド構成・型）を同じ粒度で復元する。

## 必ず決める項目

次はすべて「値」と「根拠」の両方が揃って初めて確定とする。**片方でも欠ければ不足**として扱う。

| 分類 | 項目 |
|---|---|
| エンジン | DB エンジンの種別、メジャー／マイナーバージョン |
| 構造 | テーブル、カラム、型、NULL 可否、既定値 |
| 制約 | PK、FK、UNIQUE、CHECK、インデックス、シーケンス（開始値・増分） |
| プログラム | ビュー、トリガー、関数、プロシージャと、それらをまとめる単位（パッケージ・モジュール等） |
| 文字・照合 | そのエンジンが文字コードと照合／ソート順を持てる**すべての階層**（インスタンス・DB・スキーマ／ユーザー・テーブル・カラム、および**セッション／接続**） |
| 実行時設定 | タイムゾーン、バージョン互換パラメータ、SQL の解釈を変えるモード設定、追加インストールされたオプション・拡張・コンポーネント |
| 初期化 | 初期化・マイグレーションの実行順、適用済みの範囲 |

- **階層ごとに持てる設定は階層ごとに確認する。** DB 既定の照合順序と、個別カラムに付いた照合順序は別物であり、前者だけを揃えても並び順は一致しない
- **階層の名前と数はエンジンで違う。上表の階層名を持たないエンジンで「該当なし」と書いて済ませない**——並び順・比較・大文字小文字や幅の同一視を変える設定が、
  **別の名前で別の階層に置かれている**ことがある（インスタンス単位のパラメータ、ユーザー単位の既定、接続時に適用される初期化処理など）。
  上表は項目の**チェックリストではなく効果の一覧**であり、「そのエンジンで同じ効果を持つ設定は何か」を毎回引き直す
- **セッション／接続レベルの設定を落とさない。** 接続時に既定を上書きする構成（接続文字列・初期化 SQL・ログオン時に走る処理）では、
  **DB 側の既定を揃えても実際の並び順が一致しない**。アプリがどう接続しているかまで遡って確認する
- **バージョンは「メジャーが同じ」で済ませない。** 照合順序の定義や関数の挙動はマイナーバージョンで変わることがある。判明した粒度をそのまま記録する（推測で丸めない）

## DDL が無い場合

DDL が無くても、**決定論的に完全なスキーマを生成できれば進められる**。

- **マイグレーション**: 空の DB へ全マイグレーションを**実際に適用して**最終スキーマを得る。適用が通り、得られたスキーマが上表の項目を埋められることを確認する。
  「マイグレーションがあるから復元できる」と机上で判定しない（途中のマイグレーションが手作業の前提を含んでいることがある）
- **ORM 定義**: ORM のスキーマ生成機能で DDL を出力し、上表の項目が埋まるかを確認する。
  **ORM 定義・マイグレーションが表現しない領域**（照合／ソート順、セッション初期化、トリガー、プロシージャ、一部の CHECK）は埋まらないことが多い——**埋まらなかった項目を不足として個別に立てる**。
  ツールが表現できない設定は受領資産の別の場所（環境構築手順・接続設定・ログオン処理の定義）に散っているため、**マイグレーションだけを見て「全部入っている」と判定しない**
- どちらの経路でも、**復元したスキーマを実際に構築できるところまで通す**（構築できて初めて「復元可」）

## 既定値で補完しない

**判断できない項目を環境の既定値に落とさない**（禁止事項 4）。既定値での補完は「値が決まった」ように見えて根拠が無く、後段の差分をすべて説明不能にする。

- 一部しか復元できない、または照合順序・タイムゾーン等を判断できないときは、**不足として停止**し、質問票（[`questionnaire.md`](questionnaire.md)）へ回す
- **「開発環境では既定値で動いたから」を根拠にしない。** 動くことと、現行本番と同じ挙動になることは別
- 例外は無い。「この設定は差分に影響しないはず」という判断自体が推測であり、影響しないことを実測で示せない限り不足として扱う

## 記録すること

- 項目ごとの値・根拠・確定／不足の区分
- 復元経路（受領 DDL そのまま／マイグレーション適用／ORM 生成）と、実際に構築を通した結果
- ORM・マイグレーションで**埋まらなかった領域**の一覧（不足として質問票へ回した項目との対応）
- 復元したスキーマを構築するツール・手順の所在（`<bootstrap_tool_dir>`）

`references.db_semantics` の整備は本スキルの担当ではない。ここで作った `schema.md` が `replace-strategy setup` の `db_semantics` 下書きの入力になる。
