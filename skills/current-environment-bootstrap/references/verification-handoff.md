# 起動・到達の検証と引き渡し（工程 7・8・9）

結果は `.replace/bootstrap/verification.md`（テンプレート: [`../assets/verification-template.md`](../assets/verification-template.md)）と
`.replace/bootstrap/metadata.json`（テンプレート: [`../assets/metadata-template.json`](../assets/metadata-template.json)）に記録する。

## 工程 7: 起動・疎通・認証・主要画面到達の実測

**すべて実測する。「起動するはず」「ログインできるはず」は未検証である。**

1. **起動**: 選択した target を `check_urls`（省略時は `url`）で稼働判定し、落ちているときだけ `pre_commands` → `start` の順で起動して再確認する
   （意味論と条件付き実行順の正本は `browser-test` の `references/project-config.md`。最初の稼働判定の失敗は起動の合図で、それ以外の失敗はそこで停止する）
2. **疎通**: 解決した URL へ実際にアクセスし、応答が返ることを確認する
3. **認証**: `auth.roles` の**各ロール**で実際にログインする（環境変数の存在確認だけで済ませない。値は出力しない）。
   ロールごとに結果を記録する——1 ロールでも通らなければ、そのロールでしか見えない画面は未検証になる
4. **主要画面への到達**: 受領資産から把握できる主要画面へ実際に到達し、**エラー表示なく描画されること**を確認する。
   到達できた画面・到達できなかった画面とその理由（データ不足・権限・未実装・設定不足）を一覧で残す
5. **ストレージ**（`uses_storage: true` のとき）: 起動に要る入れ物（バケット・ディレクトリ）が存在し、`storage.env_vars` が設定されていることを確認する（値は出さない）

- **画面が白紙・エラーで表示されたものを「到達できた」にしない**（HTTP 200 は到達の証拠ではない）
- 到達できない画面は「暫定データ不足で未到達」なのか「環境の復元が足りず未到達」なのかを切り分けて記録する。前者は `golden-dataset` で解消し、後者は本スキルへ戻る

## 工程 8: 再構築の再実行検証

**空の環境から、工程 3・6 のツールだけで同じ状態を再現できることを実測する**（禁止事項 8）。手作業が 1 手でも要るなら、それはツールか手順書に落としてから再実行する。

- 手順: 空の環境を用意 → スキーマ構築 → 暫定起動データ投入 → 工程 7 の起動・認証・到達を再度通す
- **1 回目と同じ結果になることまで確認する**（起動できたが画面の内容が違う、は再現できていない）
- 再現できなかった場合、**再現できない箇所を特定して記録し、ツール・手順書を直してから再実行する**。「たぶん環境差」で片付けない
- **`verification.md` に「再構築の再実行: 未実施」と書いたまま引き渡さない。** 未実施は `status: handed-off` の条件を満たさない

## 工程 9: current target の引き渡し

引き渡しは「環境が動いている」ことの宣言ではなく、**どこに根拠があり、どこが未確認かを添えて渡す**ことである。

1. **設定の current target を確定させる**: 再構築で決まった `url`（`none` から実 URL へ）を非破壊で埋め、`side: current` の既定として `default: true` を付ける
   （側ごとに `default: true` は 1 つまで。既に別の current target に付いているなら、どちらを既定にするかをユーザーに確認する）。
   **本スキルが設定へ書くのはこの 1 箇所だけ**で、値はユーザーに確認してから書く
2. **`metadata.json` を書く**: `status` を `handed-off` にし、次を記録する
   - 復元経路（受領 DDL／マイグレーション適用／ORM 生成）と、埋まらなかった領域
   - `semantics` の確定済み・確認待ちの件数と、確認待ちが影響する機能
   - `handoff.boot_requirements`: **`golden-dataset` フェーズ A のデータ設計に含める必要がある起動要件**（認証ユーザー・マスタ・コード表等）。
     フェーズ A の投入は暫定起動データを置き換えるため、ここに列挙しないと再投入後に環境が起動しなくなる
   - `handoff.unconfirmed`: 未確認のまま引き渡す項目の一覧（禁止事項 7。**空にしない**——無ければ「なし」を明示する）
3. **`replace-strategy` の測定へ戻す**: 引き渡し完了を報告し、`replace-strategy setup` の測定（再構築した target が対象）を促す

### `status` の値

| 値 | 意味 | 次にすること |
|---|---|---|
| `blocked` | 不足で停止中（`blocked_on` に理由） | 質問票の回答・追加資産を待ち `--resume` |
| `handed-off` | 工程 7・8 を通し引き渡し済み | `replace-strategy setup` の測定へ |

**「工程の途中」を表す第 3 の値は持たない。** 本スキルの実行は、工程 9 まで進んで `handed-off` になるか、
不足に当たって `blocked` で止まるかのどちらかで終わる。**途中で正常に終わる経路が無い**ため、
書き手のいない値をテンプレートに残すと、下流が来ない状態を前提にした分岐を持つことになる。
将来 `--resume` の途中経過を記録する設計にするなら、**値を足すのと同時に「誰がいつ書くか」を実行フローに定める**。

**`handed-off` を名乗る条件は、工程 7 の起動・認証・主要画面到達がすべて実測済みで、工程 8 の再実行が再現できていること。**
確認待ちの意味論が残っていること自体は `handed-off` を妨げない（残っている一覧を `handoff.unconfirmed` に載せて渡す）。
