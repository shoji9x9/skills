# 受領資産の棚卸しと分類（工程 1・2）

受領資産から現行環境を再構築できるかは、**何が届いているか**ではなく**何が足りないか**で決まる。棚卸しの目的は資産の一覧を作ることではなく、**不足を個別に検出して見えるようにすること**にある。

結果は `.replace/bootstrap/assets-inventory.md`（テンプレート: [`../assets/assets-inventory-template.md`](../assets/assets-inventory-template.md)）に記録する。

## 工程 1: 棚卸し

`current.received_assets` の各パスと `current.repo` を走査し、**実在するものだけ**を一覧化する。

- **「あるはず」を一覧に載せない。** ファイルを開いて中身の種別まで確認したものだけを「受領済み」にする（アーカイブは展開して中身を見る）
- 各資産に**来歴**（誰から・いつ・どの受領物に含まれていたか）と**利用許可の有無**を付ける。判定できないものは「来歴不明」と明記する（禁止事項 4 の判断材料）
- **受領資産に本番の接続情報・認証情報が含まれていたら、値を復唱せず所在だけを報告する**（禁止事項 7・10）
- 現行コードがある場合は、そこから導出しうるもの（マイグレーション・ORM 定義・enum・バリデーション・定数・SQL・既存テスト）の**所在**を控える。導出の実施は工程 3・4

## 工程 2: 必要資産の分類

再構築に要る資産を、次の 3 区分に**個別に**分類する。まとめて「だいたい揃っている」と扱わない。

| 区分 | 意味 | 扱い |
|---|---|---|
| **受領済み** | そのまま使える資産が届いている | 根拠として使う（来歴・利用許可の確認は別途） |
| **導出可能** | 受領コード等から**決定論的に完全復元できる** | 復元して使う。復元根拠を記録する |
| **不足** | 届いておらず、決定論的にも復元できない | 質問票・追加資産依頼へ回す |

- **「導出可能」は完全復元できる場合だけ**の区分である。部分的にしか復元できないもの、複数の解釈が成り立つものは**不足**に置く。
  「マイグレーションがあるから DDL は導出可能」と一括で判定せず、**実際に流して最終スキーマが得られること**を確認してから導出可能にする
- **不足は粒度を落とさない。** 「データ辞書が無い」ではなく「`orders.status` の取りうる値と遷移が不明」まで割る（質問票がそのまま作れる粒度）

## 最低限確認する資産カテゴリ

次のカテゴリは**必ず 3 区分のいずれかに分類する**（該当なしなら「該当なし」と書き、空欄で残さない）。

| カテゴリ | 具体例 | 主な導出元 |
|---|---|---|
| DB スキーマ | DDL、スキーマダンプ、テーブル定義書 | マイグレーション、ORM 定義 |
| DB エンジン・設定 | エンジン種別とバージョン、文字コードと照合／ソート順（**階層ごと。セッション／接続を含む**）、タイムゾーン、バージョン互換パラメータ、追加オプション | スキーマダンプのヘッダ、実行環境の定義、接続設定、ログオン時に走る処理 |
| 初期化・実行順 | マイグレーションの適用順、初期化スクリプト | マイグレーションのファイル名・履歴テーブル |
| seed・fixture | 公式の seed、テストデータ、サンプルデータ | 既存テストのフィクスチャ |
| データ辞書・コード値 | コード表、状態遷移、区分値の定義 | enum、定数、バリデーション、SQL の条件式 |
| 生成元の定義（現行コードが生成物の場合） | コードの生成元になったモデル・定義ファイル・設定 | — |
| 業務シナリオ | 代表的な業務フロー、画面・帳票仕様 | 既存 E2E テスト、API 例 |
| アプリの起動要件 | ランタイム・依存パッケージ・設定ファイル・環境変数の一覧 | 実行構成、コンテナ定義、依存定義ファイル |
| 認証 | ログイン方式、初期ユーザーの作り方 | 認証まわりのコード、マイグレーション |
| ファイルストレージ | バケット・ディレクトリ構成、アップロード経路 | 設定、ストレージクライアントの呼び出し |

- **アプリの起動要件と認証を落とさない。** DB だけ復元できても、起動できず・ログインできない環境は比較基準にならない
- **現行コードが生成物なら、生成元の定義を独立したカテゴリとして立てる。** 生成コードだけでは意味論の根拠にならない場面がある（生成器が補った既定値と業務上の決定が区別できない。[`data-semantics.md`](data-semantics.md)）
- `uses_storage: true` のときはストレージのカテゴリも分類する（工程 7 で入れ物の存在を確認する）

## 停止条件

- `current.received_assets` が空・欠落・解決できないパス → 受領資産の所在をユーザーに確認して停止する
- 走査した結果、**DB スキーマとその導出元がどちらも無い**（`dataset_mode: db` の場合）→ 追加受領の依頼を出して停止する
- **来歴不明の DB dump しか無い** → 中身を見る前に来歴と利用許可の確認を依頼して停止する（[`data-semantics.md`](data-semantics.md)「来歴と利用許可」）
