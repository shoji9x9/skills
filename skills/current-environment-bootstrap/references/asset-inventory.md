# 受領資産の棚卸しと分類（工程 1・2）

受領資産から現行環境を再構築できるかは、何が足りないかで決まる。
そのため、棚卸しでは資産の一覧を作ることよりも、**不足を 1 つずつ検出して見えるようにすること**を目的にする。

結果は `.replace/bootstrap/assets-inventory.md`（テンプレート: [`../assets/assets-inventory-template.md`](../assets/assets-inventory-template.md)）に記録する。

## 工程 1: 棚卸し

`current.received_assets` の各パスと `current.repo` を走査し、実在するものだけを一覧にする。

- 「あるはず」のものを一覧に載せない。ファイルを開いて中身の種別まで確かめたものだけを「受領済み」にする。アーカイブは展開して中身を見る
- 各資産に、出所（誰から・いつ・どの受領物に含まれていたか）と、利用許可の有無を付ける。
  判定できないものは「出所不明」と書く（禁止事項 4 の判断材料）
- 受領資産に本番の接続情報・認証情報が含まれていたら、値は報告に書かず、所在だけを報告する（禁止事項 7・10）
- 現行コードがある場合は、そこから導出できる可能性のあるもの（マイグレーション・ORM 定義・enum・バリデーション・定数・SQL・既存テスト）の所在を控える。
  導出そのものは工程 3・4 で行う

## 工程 2: 必要資産の分類

再構築に要る資産を、次の 3 区分に 1 つずつ分類する。まとめて「だいたい揃っている」と扱わない。

| 区分 | 意味 | 扱い |
|---|---|---|
| **受領済み** | そのまま使える資産が届いている | 根拠として使う（出所と利用許可は別に確かめる） |
| **導出可能** | 受領コードなどから、決定論的に、欠けなく復元できる | 復元して使う。復元の根拠を記録する |
| **不足** | 届いておらず、決定論的にも復元できない | 質問票と追加資産の依頼に回す |

- 「導出可能」は、欠けなく復元できる場合だけの区分である。一部しか復元できないものと、複数の解釈が成り立つものは「不足」に置く。
  「マイグレーションがあるから DDL は導出可能」とまとめて判定しない。実際に流して最終のスキーマが得られることを確かめてから「導出可能」にする
- 不足は細かい粒度のまま書く。「データ辞書が無い」ではなく、「`orders.status` の取りうる値と遷移が不明」まで分ける（そのまま質問票を作れる粒度）

## 少なくとも確かめる資産のカテゴリ

次のカテゴリは、必ず 3 区分のどれかに分類する。該当しなければ「該当なし」と書き、空欄で残さない。

| カテゴリ | 具体例 | 主な導出元 |
|---|---|---|
| DB スキーマ | DDL、スキーマダンプ、テーブル定義書 | マイグレーション、ORM 定義 |
| DB エンジン・設定 | エンジンの種別とバージョン、文字コードと照合／ソート順（**階層ごと。セッション／接続を含む**）、タイムゾーン、バージョン互換パラメータ、追加オプション | スキーマダンプのヘッダ、実行環境の定義、接続設定、ログオン時に実行される処理 |
| 初期化・実行順 | マイグレーションの適用順、初期化スクリプト | マイグレーションのファイル名・履歴テーブル |
| seed・fixture | 公式の seed、テストデータ、サンプルデータ | 既存テストのフィクスチャ |
| データ辞書・コード値 | コード表、状態遷移、区分値の定義 | enum、定数、バリデーション、SQL の条件式 |
| 生成元の定義（現行コードが生成物の場合） | コードの生成元になったモデル・定義ファイル・設定 | — |
| 業務シナリオ | 代表的な業務フロー、画面・帳票仕様 | 既存 E2E テスト、API 例 |
| 現行 UI が使う市販部品のベンダー資料 | 機能一覧、非互換検証用の試験仕様書、公式サンプルの所在と対象版 | 依存定義、ライセンス台帳、UI ソース、受領資料 |
| アプリの起動要件 | ランタイム・依存パッケージ・設定ファイル・環境変数の一覧 | 実行構成、コンテナ定義、依存定義ファイル |
| 認証 | ログイン方式、初期ユーザーの作り方 | 認証まわりのコード、マイグレーション |
| ファイルストレージ | バケット・ディレクトリ構成、アップロードの処理の流れ | 設定、ストレージクライアントの呼び出し |

- アプリの起動要件と認証を分類から外さない。DB だけ復元できても、起動できない環境やログインできない環境は、比べる基準にならない
- 現行コードが生成物なら、生成元の定義を独立したカテゴリとして立てる。
  生成コードだけでは、意味論の根拠にならない場面がある。生成ツールが補ったデフォルト値と、業務上の決定を区別できないからである（[`data-semantics.md`](data-semantics.md)）
- 市販部品の資料は、使っているかどうかを現行コードと依存定義で確かめてから分類する。
  - 使っていなければ「該当なし」にする。
  - 使っているのに、対象版の機能一覧・試験仕様書・公式サンプルの所在を確かめられなければ「不足」にし、対象版と入手窓口を質問票に回す。
  - 実際の UI から列挙した結果は、受領資料の代わりにしない。現行が使っていない操作を検出できないからである。
  - 不足資産の一覧には、次のことを書く。`parity-suite` の状態の網羅（網羅表の項目集合）を規範となる資料から完成できず、`app-ui` に切り替えても測れない操作が残る
- `uses_storage: true` のときは、ストレージのカテゴリも分類する（入れ物が在るかは工程 7 で確かめる）

## 止まる条件

- `current.received_assets` が空・欠けている・解決できないパスのときは、受領資産の所在を利用者に確かめて止まる
- 走査した結果、DB スキーマとその導出元のどちらも無いとき（`dataset_mode: db` の場合）は、追加の受領を依頼して止まる
- 出所が不明な DB dump しか無いときは、中身を見る前に、出所と利用許可の確認を依頼して止まる（[`data-semantics.md`](data-semantics.md)「出所と利用許可」）
