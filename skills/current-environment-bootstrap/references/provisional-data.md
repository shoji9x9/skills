# 暫定起動データの構築（工程 6）

ここで作るのは、現行アプリを起動し、ログインし、主要な画面を探索できるようにするための最小限のデータである。比較の正解ではない。
ゴールデンデータセットは、`replace-strategy` の測定と機能インベントリが終わった後に、`golden-dataset` が確認済みの意味論を基に別に作る（禁止事項 6）。

## 暫定起動データとゴールデンデータを分ける

| | 暫定起動データ（このスキル） | ゴールデンデータセット（`golden-dataset`） |
|---|---|---|
| 目的 | 現行アプリを起動・探索できるようにする | 現・新の比較を成り立たせる |
| 前提 | 機能インベントリはまだ無い | 機能インベントリ・測定・戦略が確定している |
| 網羅 | 起動に要る最小限 | エッジケースを意図して含む代表データ |
| 根拠 | 確定済みの意味論だけ。確認待ちは含めない | 確定済みの意味論だけ |
| ツール | `<bootstrap_tool_dir>`（デフォルトは `bootstrap/`） | `<dataset_tool_dir>`（デフォルトは `seed/`） |

- 暫定起動データを、ゴールデンデータに自動で格上げしない。「暫定データで十分に見えるからゴールデンデータにする」ことはしない。
  網羅の設計の基準が違うので、流用すると代表性の検討を飛ばすことになる
- ツールも分ける。同じディレクトリや同じエントリに同居させない。
  `golden-dataset` のフェーズ A の事前削除が暫定データを消すのは正常な動作で、同居させると再構築を再実行できなくなる
- `golden-dataset` のフェーズ A は、暫定起動データを置き換える。そのため、起動に要る前提（認証ユーザー・マスタ・コード表など）は、確定の根拠に基づいてフェーズ A のデータ設計に含める必要がある。
  この引き継ぎ事項は、`metadata.json` の `handoff.boot_requirements` に列挙する（[`verification-handoff.md`](verification-handoff.md)）

## 作り方

- 決定論的で冪等にする。ID・連番・UUID・基準時刻を固定する。
  削除（FK の依存の逆順）してから投入（依存順）する構造にして、何度実行しても同じ状態になるようにする
- 確定済みの意味論だけを使う。確認待ちの値を「とりあえず」で埋めない
- ツールは対象プロジェクトのコードなので、`references.coding_conventions` に従って書く。
  未整備でも止まらないが、推測で自分の流儀を持ち込まず、既存のコードとリントの設定から読み取る
- 生成・更新したら、設定の `verification_commands.full`（全体を走査する列）を通す。
  設定に無いときも、リスト形式で実行する範囲が宣言されていないときも止まらず、その旨を `verification.md` に記録して進む
- 投入した値は、1 件ずつ根拠と一緒に `semantics.md` に記録する。どの値がどの根拠で入っているかを後から辿れない環境は、引き渡しても比べる基準にならない

## 投入の前のチェック

投入の前に、次の 2 つのチェックを通す。どちらか一方でも通らなければ投入しない。

1. 設定によるチェック: 投入先の target が `db.seedable: true` であること。`dataset_mode: static` なら、書き込み先がすべて `dataset_static_paths` の下に収まること。
   許可が無ければ設定の修正を促して止まる。自分で `seedable: true` を足さない
2. 自己申告のチェック: 接続先の環境変数の**名前**を示し（値は表示しない）、テスト環境であることを利用者に確かめる

加えて、投入するデータそのものに、出所か利用許可が不明なものが 1 件でも含まれていたら投入しない（禁止事項 4。判定は [`data-semantics.md`](data-semantics.md)「出所と利用許可」）。

## 起動に必須の項目を確かめられないとき

値を作り出さずに止まる。起動・ログインに必須な項目の意味を確かめられない場合は、その項目を質問票の**最優先**に立て、`status: blocked` として止まる。
必須な項目とは、NOT NULL でデフォルト値が無い項目か、認証・権限の判定に使われる項目である。

- 起動に必須でない未確認の項目は、止まる理由にしない。台帳に「確認待ち」として残し、影響（どの機能が検証できないか）を書いて進む。
  この区別が付かないと、確認待ちが 1 件あるだけで、環境をいつまでも作れなくなる
- 「NULL にしておけば動く」で埋めない。NULL も値の 1 つの選び方で、根拠の無い選び方である。NULL を選ぶことにも根拠が要る
