# フェーズ B（新側への変換・投入・現新一致検証）

フェーズ B は、対象の機能の `parity-replace` が新側の受け皿を作った後に、slug ごとに再実行して進める。
フェーズ A の論理データが共通の原本である。フェーズ B はそれを新側の形に変換するだけで、新しいデータを作らない（`version` の運用は [`versioning.md`](versioning.md) で定義する）。

「新側の受け皿」は、設定の `dataset_mode` によって変わる。`db`（デフォルト）では新側の DB スキーマ、`static` では新側のリポジトリの静的データの形式である。

## 前提

- 対象の slug の新側の受け皿（`parity-replace` が実装したスキーマや静的データの形式）があること。無ければ停止する。
- 投入先の target（`side: new`）が書き込みを許可されていること。
  `--target` の選び方は、`replace-strategy` の `references/project-config.md`「実行対象環境」の「選択規則」で定義する。取り決めの原本も同じファイルにある。
  - `dataset_mode: db` では、対象は `db.seedable: true` の `side: new` の target だけである。
    `db` を書かない target（DB に触れない）と、`env_vars` だけの target（読み取り専用）は投入の対象外で、フェーズ B の記録も作らない（`parity-diff` がその target を「データ整合未検証」として扱う）。
    `db.env_vars` の接続を確かめる。値は出さずに有無だけを確かめ、`secrets.wrapper` を前に付けて実行する。
  - `dataset_mode: static` では `db` を求めない。`dataset_static_paths` の下が、新側のリポジトリで書き込めることを確かめる。
- `references.db_semantics` の reference があること（`static` では、静的データの形式の対応と意味論の差を書いた、同じキーの reference）。
  キーの欠落・空の値・解決できないパスは、どれも「未整備」として停止し、整備を促す。
  `setup` はこのキーを空の値で作ることがある。三値の `dependency_policy` と違い、空の値は「無いことを確かめた」という意味ではない。
  扱いの原本は、`replace-strategy` の `references/project-config.md`「references（知識の注入）」である。

## 論理データから新側への変換

現行と新側は、型や意味論が違うことがある。変換の層がこの差を吸収する。

- `references.db_semantics` の型の対応づけと意味論の差を当てる。
  現行から新側への型の変換、空文字と NULL の扱い、collation による並び順などである。`static` では、フィールドの構成・エンコーディング・日付の書き方・ファイルの分け方の差である。
- 意図的差異のレジストリ `intentional_diffs.may_change`（型の変換に伴う差など）に当たる差を、変換で吸収する。
- 論理データの意味は保つ。変換は表現の形式を変えるもので、値の意味を変えるものではない。

## 新側投入

投入ツールに新側の投入先を足す（[`seeding-tool.md`](seeding-tool.md)）。フェーズ A と同じ 2 つのチェック（設定によるものと、自己申告）を通してから投入する。
`db` では、選んだ新側の target の `db.env_vars` の接続先に投入する。`static` では、新側のリポジトリの `dataset_static_paths` の下に生成する。
削除・投入・検証の構造は共通で、書き込み先と変換の層だけが新側向けになる。

フェーズ B は、新側の target ごとに実行する。同じ DB を複数の target が共有する場合も、target ごとに実行して記録を残す（投入ツールは冪等なので、再実行しても安全である）。
`static` では、生成物は target をまたいで同じになる。そのため、target ごとに意味を持つのは投入した後の検証（その target が実際にゴールデンデータを配信しているか）である。検証も記録も target ごとに行う。

## 現新一致検証

新側に投入した後、新側の整合性に加えて、現行と新側に同じ論理データが入っていることを確かめる。ここが成り立たないと、パリティの比較の前提が成り立たない。

検証は、差を列挙し、それが宣言と過不足なく一致するかで判定する形にする。
新側の実データと論理データを突き合わせて、差のある箇所を列挙する。
その差が、宣言済みの差の一覧（`db_semantics` の型の対応づけ・意味論の差と、`intentional_diffs.may_change` の該当する項目）と過不足なく一致するかを判定する。宣言にない差が 1 件でもあれば、失敗として扱う。

- 逆変換（新側から論理データへ）で往復させない。
  「新側を論理データに戻して比べる」形は、前向きの変換と同じ表を使う限り `map∘unmap = id` になる。そのため、宣言していない正規化を足しても検証が通る（検証が何も確かめていない）。
  差の列挙は変換の表を通さずに行い、判定は宣言の一覧との突き合わせだけで決める。
- 検証そのものの強さを確かめる。宣言していない正規化を 1 件足したときに、検証が失敗することを確かめ、結果を `verification.md` に記録する。
  失敗しなければ、検証は何も確かめていない。この確認を省くと、通ったことが何の証拠にもならない。
  - 足す正規化は、実データに当たるものを選ぶ。
    何も抑えない正規化（例: 前後の空白を除くが、データに前後の空白が無い）は列挙の結果を変えないので通ってしまい、正しく動く検証を「何も確かめていない」と誤って判定する。
    宣言済みの差を 1 件抑える正規化（列挙 ⊂ 宣言 になって失敗する）を選ぶ。選べなければ、新側のデータに宣言にない差を 1 件入れる（列挙 ⊃ 宣言 になって失敗する）。入れたものは、確かめた後に必ず戻す。
- 説明できない不一致は失敗として扱い、直す（変換の誤り・投入の抜け・設計の食い違い）。失敗を意図的差異の中に紛れ込ませない。

## ストレージ・ファイル実体の扱い

- ストレージの実体への投入は、スコープの外である。`storage.seedable: true` でも投入しない（原本は `replace-strategy` の `references/project-config.md`「ファイルストレージ」）。
  新側のストレージにゴールデンデータのファイルが無い前提で進める。ストレージの実体に依存する検証は、「未投入のため未検証」として `verification.md` のフェーズ B の節に書く（説明済みのデータの差として扱わない）。
- アップロード用の入力ファイルは、変換の対象外である（同じバイト列を、現行と新側の両方でそのまま使う）。
  ただし、保存した後のパスの命名規則が新側で変わる場合は、意図的差異である。
  宣言が無ければ、`intentional_diffs.pending` に追記して利用者の確認に回す（下記の「新規の意図的差異の扱い」と同じ扱い）。
- 新側の受け皿がファイルの形式（`dataset_mode: static`）の場合、変換はこのファイルの変換の設計に従う（ストレージの実体の話とは別のことである）。

## 新規の意図的差異の扱い

変換や検証の途中で、レジストリに登録されていない意図的差異（新しく分かった型・意味論の差）を見つけたら、次のようにする。

- 自分で確定しない。設定の `intentional_diffs.pending` に、既存の内容を消さずに追記し、利用者の確認に回す。
- 追記した元が分かる形で書く（要素の形の原本は `replace-strategy` の `references/project-config.md`「`pending` 要素の形」）。`added_by: golden-dataset` と、`added_at` に追記した日を書く。
  ただの文字列で追記すると、どこから来たかが分からなくなり、どの機能の棚卸しでも提示され続ける。
- `slug` は、どの機能に帰属できるかで決める。その差が `--feature` で渡した特定の slug の変換でだけ起きるなら、その slug を書く（`--feature` が 1 件ならその slug）。
  複数の slug を対象にした実行で、どの機能にも固有でない差（DB 全体の型・意味論の差など）と、機能のスコープを持たない工程（フェーズ A）は `cross-cutting` にする。
  帰属できるものを `cross-cutting` にしない。閉じる担当が決まらず、どの機能の棚卸しにも出続ける。
- 確認が済むまでは、`verification.md` に「保留（pending）」として残す。

## 成果物

`metadata.json` の `phase_b.<slug>.<target>`（`<target>` は投入先の新側の target 名）を更新する。
書くのは `dataset_version`（新側に投入した version）・`seeded_at`・`verified_at` である。
他の target の記録は残し、投入した target のキーだけを更新する。検証の結果は、`verification.md` のフェーズ B の節（slug ごと）に記録する。
