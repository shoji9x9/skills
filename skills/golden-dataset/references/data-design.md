# データ設計（フェーズ A）

データセットは一から作るので、何を含めるかで品質が決まる。
データ設計は、現行と新側の値を比べられるようにするための基になる。設計は `.replace/dataset/design.md` に記録する（テンプレートの原本は [`../assets/design-template.md`](../assets/design-template.md)）。

## 起点は DDL と機能インベントリ

- DDL の制約を起点にする。テーブル、必須項目、型、一意制約、外部キーを読み、各テーブルの必須・一意・FK を満たす最小の構成をまず作る。
- 機能インベントリ（`.replace/features.md`）から、どのテーブルが対象か、どのリソースドメインに属するかを読む。対象のテーブルは features.md の記録に従い、推測で足さない。
  テーブルは 3 つの表に分かれて記録されているので、3 つとも読む。機能一覧の「テーブル」列、横断 API の「参照テーブル」列、バッチの「参照テーブル」列である。
  機能一覧だけを見ると、横断 API からしか参照されないテーブル（マスタ・設定・URL の解決など）が対象から外れる。
  その結果、fan-out 先のすべての機能で「画面の値の一部をゴールデンデータで制御できない」状態になる。
- 横断 API の行の「参照テーブル」が空欄のとき、または「参照テーブル」列そのものが無いとき（列を持たない版のテンプレートで作った features.md）は、対象なしと解釈しない。
  `replace-strategy` 側の記録の抜けを疑う。空欄や列の欠落を、「参照テーブル無し」と同じに扱わない。判断できなければ利用者に確認し、埋めてから設計に進む。
- 「読むテーブル無し」の印は `-` に統一する（書き方は `replace-strategy` で定義する）。`-` と書いた行だけを 0 件として扱う。
  それ以外の書き方は、空欄と同じく記録の抜けとして確かめる。書き方が増えると、下流で解釈がぶれて判定があいまいになる。
- `dataset_mode: static` では、DDL の代わりに現行の静的データの形式を起点にする。ファイルの配置・フィールドの構成・型・ファイル間の参照である。
  以降の設計の規律（エッジケース・現実的な値・未カバー領域の記録）はモードに依らず同じで、「テーブル」を「静的データの単位」と読み替える。

## 消費側から必要な値と量を導く

テーブル名だけでは、検索できる値・順序を識別する値・ページの境界を越える件数を決められない。
各機能・横断 API・バッチについて、対象のテーブルを読むコードと現行 target の観測から、次のことを調べる。
絞り込みの列と条件、並び替えの列・方向・同じ値のときの順序、ページサイズと切り替えの候補である。調べた結果は、`design.md` の「消費側パラメータ」に根拠を付けて記録する。

- 候補の列を、DDL の型や列名だけから推測しない。現行のコードを読み、UI に現れる条件・操作は現行 target で確定する。
- 絞り込みの条件ごとに、一致・不一致・境界のデータを置く。ソートには、主キーの順にたまたま一致しない値を置く。
- ページサイズを想定の値で固定しない。実測した値と、切り替えの候補ごとに必要な件数を算出する。
- 調べられないパラメータは、デフォルト値をでっち上げずに未カバーとして残す。後の `parity-suite` で不足が分かったら、version を上げて追加する。

## 参照表の役割と行数は、消費側の全部から決める

検証の段で数えるのは「入れたものが入ったか」であり、「入れたもので現行のどの分岐を踏めるか」は数えない。
踏めない分岐は、下流（`parity-suite` の特性化、`parity-replace` の実装）が「観測できない」に当たって初めて分かる。
そのときにはベースラインを採り終えているので、行を足すと version が上がり、交差する slug の採取物が古くなる（[`versioning.md`](versioning.md)）。
設計の段で数えるほうが安い。そのための表が、`design.md` の「`述語ごとの分岐網羅`」である（表の名前は同梱の検査スクリプトが読むので変えない）。

旧称: この表は「述語ごとの分岐被覆」と呼んでいた。既存の design.md の旧称の見出しは、同梱の `predicate-coverage-check.mjs` が同じ表として読むので、書き直さなくてよい。

### 役割は「消費するか」で決める（引き方では決めない）

対象テーブルの行には、役割（`投入する` / `読み取りだけ` / `FK 親のみ`）を付ける。判定の入力は `.replace/features.md` の 3 つの表である。
消費側の slug が 1 つでもあれば `投入する` にする。

- `FK 親のみ` は、どの機能も直接読まないが、FK を満たすために投入が要る親の表である（`orders` の背後の `customers` など）。
  `投入する` にすると「消費側がいない」で失敗し、`読み取りだけ` にすると投入の対象から外れて FK を満たせない。そのため、別の語として書き分ける。
  この役割の表は、述語の 0 件・1 件の判定には入らない（消費側が絞り込まないため）。ただし、0 件だと子の行の FK を満たせないので失敗にする。
- `JOIN` で読むか、`FROM` の母集合として読むかで役割を変えない。
  「結合しない表は読み取りだけ」と判定すると、マスタを `FROM` の母集合として読む形（`SELECT ... FROM roles WHERE ...` を一覧の元にする、など）が見えなくなる。
- 3 つの表から design.md への転記は人が行うので、集合の差で突き合わせる。転記で slug が 1 つ抜けると、「どの機能もこの表を読まない」と読める状態になり、役割が `読み取りだけ` と判定されてしまう。
  `読み取りだけ` に分類した表は、投入の対象ではないので、行数を増やす検討に入らない。そのため、転記の抜けは後で「踏めない分岐」として現れる。
- 突き合わせは、同梱の [`../scripts/predicate-coverage-check.mjs`](../scripts/predicate-coverage-check.mjs) が行う（後述）。

### 述語ごとに、真の側と偽の側の両方を踏める行数を数える

参照表ごとに、消費側が読む述語を列挙する。述語とは、`WHERE` の列と、その列で分かれる値である。
列挙の入力は「消費側パラメータ」表の絞り込みの列である。絞り込みがある (slug × テーブル) に対応する述語の行が無ければ、その分岐は数えていない。

述語の値は、設計者が書いた値ではなく、消費側が述語に渡す値で書く。
消費側が値を述語に渡す前に変換する（整数への変換・桁の切り詰め・型の上限）と、設計者の値では真でも、消費側が読む行は 0 件になる。
述語の行には「値の出どころ」（どのコードで作る値か。変換を含む）を書き、変換がある列では、変換した後の値で真・偽の行数を数える。
データセットが自分で決める識別子の値は特にずれやすいので、後述の「識別子の値は、消費側の変換を通した後で確かめる」で列挙する。

述語ごとに、真の側と偽の側にそれぞれ何行入るかを数える。

| 形 | 何が起きるか |
|---|---|
| 行が 0 件の参照表（または述語の真の側が 0） | 真になる分岐に入れない。「偽のときだけ測った」ことに気づかないまま、スイートが緑になる |
| 行が 1 件の参照表 | 絞り込みを外しても結果が変わらないので、絞り込みが機能していることを観測できない |

**後者のほうが危ない。** 前者は「押せない」という形で見える。後者は緑のまま通り、新側が絞り込みを落としても現行と一致したままになる。

### 踏めない分岐は「足す」「gaps に記録」を設計の段で選ぶ

踏めないと分かっても、すぐにデータを足さない。足すと `version` が上がり、交差する slug の採取物が古くなる。

- 足す: その分岐を消費側が本当に使う（UI の操作・API の条件として現行にある）とき。
- gaps に記録: 消費側が使わない、または現行に到達する手段が無いとき。根拠を空欄にしない。後から「なぜ足さなかったか」が読めないと、下流で同じ判断をやり直すことになる。

判断の材料は、足しやすさではなく、その分岐を消費側が本当に使うかである。

### 識別子の値は、消費側の変換を通した後で確かめる

データセットは識別子の値を自分で決める（他の環境・他の作業と混在しないよう、専用の採番帯を使う）ので、値が実運用の範囲の外に出やすい。
その値が消費側の変換で別の値になると、述語は設計どおりに真でも、消費側が実際に読む行は 0 件になる。
このとき、「`述語ごとの分岐網羅`」表は「踏める」のままで、`verification.md` の該当行数も設計者の値で実行するので正しい件数が出る。どこにも現れない。
実測した例を挙げる。12 桁の採番帯の ID を、移行元の書き出し処理が 32 ビット整数に変換して明細を読んだ。変換できない値が 0 になり、どのレコードにも値が 1 つも載らなかった。
書き出したファイルの全文を比べるまで、気づかなかった。

「桁数の大きい数値など、実運用で現れる形を代表させる」（後述の「現実的な値の規律」）は、表示を比べるための規律である。識別子が消費側の変換を通るかは見ていない。
そのための表が、`design.md` の「識別子の値の範囲」である。

- 消費側の (slug × テーブル) ごとに、識別子を受け取る型と変換を列挙する。
  受け取る変数・引数の型（整数・桁の決まった文字列など）と、変換の関数（`int.Parse`・`Convert.ToInt32`・プラットフォームの組み込みの変換など）を、現行のコードから読む。
  表ごとに 1 行で済ませない。変換する消費側が 1 つでもあることが、別の消費側で値が届いたことに隠れるからである。
  識別子の列が複数あれば、列ごとに行を立てる。FK の列も親の帯の値を持つので、子の表を読む消費側が親の識別子を受け取るなら、FK の列の行も立てる。
- データセットの値の範囲と、実運用の値の範囲（最大の桁数・型の上限）を並べて書く。帯が実運用の範囲の外なら、その理由と、外にあることで変わる処理の流れを根拠に書く。
- 帯の値が、変換の後も同じ値で届くかを判定する。根拠は、届く行にも書く（変換に整数変換を書いて「届く」とするなら、帯がその型の上限に収まること）。
  届かない処理の流れには、次のどれかを選ぶ。判断の材料は、「`述語ごとの分岐網羅`」と同じく、その処理の流れを消費側が本当に使うかである。
  - 帯を変える: 変換を通る範囲に帯を移す。表は、変えた後の帯で書き直す（`届く` になる）。
  - 行を足す: その処理の流れのために、届く値の行を足す。帯の外になるなら利用者が判断する（採番帯の規則から外れるため）。根拠に判断を残す。
  - gaps に記録: その処理の流れは、現行と比べられないものとして記録する。その列の述語は、変換した後の値で数え直す（届かない値では真が 0 件なので踏めない）。
- 帯の値を持つ列が無い表（主キーも FK も持たない設定表など）だけ、列を `-` にして根拠を書く。
  `-` は、検査が真偽を読めない自己申告である。そのため、同じ表に実際の列の行と並べて書くと失敗にする。
  投入ツールは ID を固定の値で決める（[`seeding-tool.md`](seeding-tool.md)）ので、「DB の採番に任せる」は `-` の理由にならない。

既存の `design.md` にこの表と「値の出どころ」列を足すだけなら、論理データは変わらないので `version` を上げない。届かない処理の流れのために行を足したら、上げる（[`versioning.md`](versioning.md)）。

### 検証の段でも数える

投入した後に述語を 1 つずつ実行し、該当行数を `verification.md` の「述語ごとの該当行数」に残す。0 件と 1 件が報告に出る形にする。
設計の数と実測がずれる原因には、投入ツールの条件の抜け・FK 制約による間引き・`base_time` からの相対のずれなど、設計だけでは見えないものがある。

### 機械検査

```bash
node <skill>/scripts/predicate-coverage-check.mjs \
  --features .replace/features.md \
  --design .replace/dataset/design.md \
  [--verification .replace/dataset/verification.md]
```

終了コードは 3 つある。0 は条件を満たす、1 は不備が残る（設計に戻す）、2 は使い方の誤りか表を読めない、である。次の 4 つを失敗にする。

- 転記の抜けと、転記しすぎ。features.md の 3 つの表と、design.md の「対象テーブル」表の (テーブル, slug) の集合の差である。
  features.md の参照テーブルの欄が空欄なら、合格として扱わない（空欄は未調査である）。
- 役割の矛盾。消費側の slug があるのに `読み取りだけ` / `FK 親のみ` にしている、消費側の slug が無いのに `投入する` にしている、`FK 親のみ` なのに 0 件である。
- 踏めない分岐。次のものを失敗にする。
  - 表の件数が 0 / 1、述語の真・偽のどちらかが 0、判定と件数の不一致、扱いの空欄・語彙の外、`gaps に記録` の根拠の空欄
  - 絞り込みがあるのに述語の行が無い
  - 1 行に並んだ絞り込みの列のどれかに、対応する述語の行が無い。
    `status, owner_id` のように複数並ぶとき、述語 1 本ですべてを満たしたことにしない。
    突き合わせは、述語の文面に列名が現れるかで行うので、`status = 'shipped'` のように列名で始まる形で書く。
    照合は識別子の境界で行うので、`owner_id` の述語が列 `id` を満たすことはない。
    列ごとに別の述語の行が要る。`status = 'shipped' AND owner_id = :me` の 1 行で 2 列を兼ねると、真・偽の行数が結合した条件のものになる。
  - 真・偽の合計が、その表の件数を超える。真・偽はその表の行を分けたものなので、超える数はその表から出ない。
    三値論理で真でも偽でもない行はありうるので、等号は求めない。
  - 絞り込みが書いてあるのに、slug かテーブルが空である。数える相手が決まらない行を、絞り込みの無い行と同じに扱わない。
  - 絞り込みの列・条件が空欄である（未調査）。絞り込みが無いなら `-` と書く。features.md の参照テーブル列と同じ書き分けである。
  - features.md でテーブルを挙げているのに、slug が空である。その参照が、転記の抜けの突き合わせに入らない。
  - 「消費側パラメータ」表そのものが無い。絞り込みの一覧が読めないと、数え忘れが 0 件と同じに見える。
  - `--verification` を渡した実行では、設計値と実測値の不一致・投入した後も 0 件の分岐・実測表の述語 id の重複も失敗にする。
    渡した中身が空なら、「実測表が無い」として失敗にする。未指定と同じに扱うと、空の `verification.md` を作った実行が「実測して問題なし」と同じ出力になる。
    扱いを `gaps に記録` と決めた分岐は、投入した後に 0 件でも失敗にしない。設計が受け入れた判断を検証が覆すと、足す以外の選択肢がなくなる。
- 変換で値が変わる識別子。次のものを失敗にする。
  - 述語の「値の出どころ」列が無い・空欄・`-`
  - 「識別子の値の範囲」表が無い
  - `投入する` 表を読む消費側の (slug, テーブル) の組に、行が無い。その表の列が `-` なら求めない。`-` と実際の列の行を並べて書いたら失敗にする
  - 範囲の空欄・`-`、変換・届くかの空欄・語彙の外、根拠の空欄・`-`（届く行も）
  - 列のセルに複数の列を並べた行、列が `-` の行に範囲・消費側・変換・判定を書いた行、同じ (テーブル, 列, slug) の重複した行
  - 届かないのに、扱いが `行を足す` / `gaps に記録` 以外である
  - `gaps に記録` とした列の述語を、その消費側で「踏める」と数えている。照合は、述語の文面に列名が識別子の境界で現れるかで行う。
    変換の意味そのもの（その関数でその値が届くか）は読めないので、判定が正しいかは設計者が確かめる。

## エッジケースのチェックリスト

表示や挙動を比べたときに差が出る箇所を、意図して含める。各項目について、「含めた」か「含めなかった（理由）」かを design.md に残す。

- null（null を許すカラムに、実際に null が入る行）
- 境界値（数値・日付の下限と上限、0・空文字と null の区別）
- 最大長（カラム定義の最大長ちょうどの値。表示の折り返し・省略に影響する）
- 権限・ロールのパターン（各ロールが少なくとも 1 件）
- 状態遷移の各状態（取りうるすべてのステータスを、それぞれ 1 件以上）
- 空のリストになるケース（フィルタの結果が 0 件になる条件を作れるデータの配置）
- ページネーションのすべての操作を区別できる量。
  対象の一覧ごとに、現行の 1 ページの表示件数 `P` と、操作（次・前、ページ番号、先頭・最終、表示件数の切り替え）を確かめ、操作ごとに必要なページ数 `K` を決める。
  `K` ページを成り立たせる最小の件数は `(K - 1) × P + 1` である。単に 2 ページにはせず、最終ページへの直接の遷移や中間のページの確認があるなら、3 ページ以上を作る。
  表示件数を切り替える場合は、検証の対象の各 `P` で必要な件数を算出し、その最大値を採用する。
- ソートの順が判別できる並び（同じ値で順序が変わらない、順序が目で分かる値の散らばり）

ページネーションは `design.md` の表に残す。対象の一覧・確かめた操作・各表示件数・必要なページ数・採用した件数・算出の根拠である。
仕様は、選んだ現行 target で確かめる。対象の版・採取の時点・条件をたどれる実行ログや観測の記録、ソースコード、API、UI の順に、十分な証拠が得られるところまで進める。
この順にするのは、調べるコストが実行ログ・観測の記録、ソースコード、API の操作、UI の操作の順に高くなるからである。必要な証拠が得られた時点で止め、API や UI の操作は不足する場合だけ行う。
設計書・仕様書・受け取ったログを含む受け取った資料は、調べる候補を挙げるのにだけ使い、現行の挙動を確定する根拠にはしない。
UI に現れる操作があるかは、UI で確定する。確かめられない操作は、想像でデータを増やさず、未カバーとして残す。

## 現実的な値の規律

表示の検証に影響する項目に注意する。文字幅・桁数・改行の有無は、レイアウトの比較に影響する。

- 現実的な長さと文字種にする（`テスト1` のような値ばかりにしない）。
- 全角・半角の混在、改行を含む値、桁数の大きい数値など、実運用で現れる形を代表させる。
  これは表示を比べるための規律である。識別子の値が消費側の変換を通るかは、別に確かめる（前述の「識別子の値は、消費側の変換を通した後で確かめる」）。
- ただし、非現実的な値ばかりにもしない（禁止事項 6）。現実的な分布の中に、エッジを混ぜて置く。

## 未カバー領域の記録

「代表性がある」ことは証明できない。何を含め、何を含めなかったかを記録し、未カバーの領域をはっきり書く（確認済みにしない）。

- design.md の「未カバーの領域と理由」の節に、含めなかったパターンとその理由を残す。
- `parity-suite` の探索で不足が分かったら追加する、という前提で作る（フェーズ A の再実行。[`versioning.md`](versioning.md)）。

## 基準時刻の決め方

時刻に依存するデータは、基準時刻（`base_time`）を固定し、そこからの相対で作る。

- 「今週」「先週」の判定など、週や日の境界のロジックを持つ機能では特に重要である。境界の内と外になる相対時刻を、意図して配置する。
- `base_time` は `metadata.json` に記録する。投入ツールは値を固定で書かず、ここから相対時刻を計算する。
- 基準時刻の変更は、バージョンアップとして扱う。論理データが変わるからである（[`versioning.md`](versioning.md)）。
