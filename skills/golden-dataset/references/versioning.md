# バージョン運用・陳腐化・parity-suite との往復

データセットの `version` は、`parity-suite` と `parity-diff` の成果物が「どのデータで取得したか」をたどるための鍵である。
基になるデータが変わったベースラインを、古くなったもの（陳腐化）として検出するのに使う。

## version のセマンティクス

`metadata.json` の `version` は、1 から始まって増えるだけの整数である。

- 上げるのは、論理データが変わったとき（行の追加・変更、エッジケースの追加、`base_time` の変更）だけである。1 回の変更で 1 上げる。
- フェーズ B では上げない（どの target に投入しても同じである）。フェーズ B は論理データを新側のスキーマの形に変換するだけで、論理データそのものは変えないからである。
  フェーズ B が記録するのは投入した version（`phase_b.<slug>.<target>.dataset_version`）であり、`version` の値は変えない。
- `base_time` の変更は、論理データの変更として扱う（時刻に依存するデータがすべて変わるので、1 上げる）。

`changes` は version ごとの変更の履歴で、`1..version` の各整数を 1 件ずつ、欠けも重複もなく持つ。
各要素は `{ version, affects }` とし、`affects` には、その版で論理データを変えたテーブル名（`static` では静的データの単位）を重複なく並べる。

- 複数のテーブルを変えた版は、すべて並べる。空の配列にしない（version を上げる変更なら、影響する先がある）。
- `base_time` の変更と、影響するテーブルを安全に絞れない変更だけは、印の `*` を単独で記録する。`*` と個別の名前を混在させない。
- 過去の要素は上書きも削除もしない。ベースラインが複数の version をまたぐとき、その間のすべての変更の和集合で影響を判定するので、履歴が要る。
- 古い metadata に `changes` が無い、または履歴に欠け・重複・不正な `affects` がある場合は、影響なしと判定せず、すべての slug に影響するものとして扱う。
  次のフェーズ A の実行で、根拠を確かめられる履歴だけを、既存の内容を消さずに補う。推測で過去のテーブルを割り当てない。

既存の metadata を更新するフェーズ A は、`changes` 列を既存の内容を消さずに追加する。
過去の版ごとの変更の根拠がそろうなら `1..version` を作り直し、そろわない版はその版の `affects` を `["*"]` として埋める。形式を合わせるためだけに、過去の個別のテーブルを推測しない。

## slug が読むテーブルの導出

陳腐化の判定では、`.replace/features.md` から slug が実際に読むテーブル（実効参照テーブル）を導く。
`dataset_mode: static` では、「テーブル」「参照テーブル」列の値は静的データの単位を指す（`changes[].affects` と同じ読み替え。上の「version のセマンティクス」を参照）。
そのため、実効参照テーブルはモードに依らない考え方として扱う。

- 機能: 機能一覧の「テーブル」と、その slug を fan-out に含む横断 API の「参照テーブル」
- 横断 API のリソース: その行の「参照テーブル」
- バッチ: その行の「参照テーブル」
- `-` は空の集合である。空欄・列の欠落・知らない slug は「テーブル無し」ではなく判定できない状態なので、影響ありと判定する。

記録した version を `V`、今の version を `C` とする。まず、両方が整数で `1 <= V <= C` を満たすことを確かめる。
`V > C` は、metadata の破損か、古いデータセットの metadata に戻したときにしか起きない、ありえない状態である。変更の区間が空であることを「影響なし」と解釈せず、停止する。
範囲の外・整数でない・欠けているときは、どれも判定できないものとして失敗にする。

version の範囲が妥当な場合だけ、`V < change.version <= C` のすべての `affects` と、実効参照テーブルが交わるかを調べる。範囲の中に `*` があれば、必ず陳腐化する。
交わらなければ、version の数値が古くても、その slug の成果物は有効である。成果物の `dataset_version` は書き換えずに、「影響なし」と判定する（書き換えると、後から履歴を監査できない）。

## 陳腐化検出の全体像

下流の各成果物が `version` を記録する。記録した後の `changes[].affects` と、slug の実効参照テーブルを突き合わせて、陳腐化を検出する。

| 読み手 | 記録する場所 | 検出 |
|---|---|---|
| `parity-suite` | `.replace/parity/<slug>/metadata.json` の `dataset_version` | ベースラインを採った後の変更がその slug に影響するときだけ、取得し直すと宣言する |
| `parity-diff` | 同上を参照する | 古くなったベースラインで比べるのを避ける |
| `parity-component` | `.replace/components/<slug>/metadata.json` の `dataset_version` | データに依存する部品では、採った基準と、現行から抜いた実データの両方が古くなる（抜いたデータを見本の入力に使うため。データの出所の確認も同じ値で行う）。部品の slug は `.replace/features.md` に無いので、実効参照テーブルを直接読めない。下記の導出の規則で求める |
| `replace-strategy status` | 上をまとめる | 記録した後の変更がその slug に影響するときだけ、「要再取得」と報告する |

### 部品 slug の実効参照テーブル（`parity-component`）

部品の slug は `.replace/features.md` に無いので、機能の slug と同じ方法では読めない。インスタンスのページを経由して導く。

1. `.replace/components.md` の対象の行から、その部品のインスタンスのページを並べる。
2. `.replace/features.md` のページの一覧で、そのページに載る機能の slug を読む。
3. 読んだ機能の slug それぞれの実効参照テーブルの和集合を、その部品の実効参照テーブルにする。

- データに依存しない部品（`データ依存: false`）は、実効参照テーブルを持たない。データが変わっても見た目は変わらないので、古くならない。
- 導けない場合は、すべてに影響するものとして扱わず、停止する。
  ページの一覧を持たない `features.md`、ページの一覧に無いページ、機能の slug を読めないページが当たる。
  すべてに影響するとして扱うと、毎回の取得し直しを強いることになる。「影響なし」と判定すると、陳腐化を見逃す。
  どちらにもせず、導けない理由を `gaps.md` に残して、利用者に判断を求める。

**slug が読むデータを作り直すと、その変更より前に取得した視覚のベースラインと特性化の結果は無効になる。**
version は順序を、`changes[].affects` は影響の範囲を、機械的に検出できるようにする。関係のないテーブルだけの変更や、実効参照テーブルが `-` の slug では、取得し直さない。

## parity-suite の gaps.md「データ不足」からの戻りループ

`parity-suite` が現行のアプリを探索する途中で、シードに足りないケースが必ず見つかる。
たとえば、このパターンのデータが無いと空のリストしか確かめられない、ページネーションが 1 ページで終わる、などである。
これは `gaps.md` に「データ不足」として記録され、このスキルに戻る起点になる。

戻ってきたら、フェーズ A を次の順で再実行する。

1. 設計に追記する。`design.md` に足りないパターンを追加し、何を追加したかを「gaps 由来の追加履歴」に version と一緒に残す。
2. ツールを更新し、投入し直す。追加した分を含めて投入ツールを更新し、現行に投入し直す（冪等なので全体を入れ直す。`dataset_mode: db` では現行のテスト環境の DB、`static` では `dataset_static_paths` の下）。
3. 検証し直す。FK の整合・必須項目・件数・カバレッジ（`static` では参照の整合・必須フィールド・型・件数・カバレッジ）を確かめ直す。
4. `version` を 1 上げる。`metadata.json` を更新し、同じ version と実際に変えたテーブルを `changes` に追記する（`static` では `current.fingerprint` も計算し直して更新する）。
5. 影響するベースラインの取得し直しを案内する。変えたテーブルと実効参照テーブルが交わる `parity-suite` だけが古くなる。当たる slug に限って、`parity-suite` の再実行を案内する。

このループは 1 回では終わらず、探索が進むたびに繰り返す前提で運用する。

このループは、`dataset_mode` に関わらず回す。DB を持たないプロジェクト（`static`）でも、投入先の target に `db` を求めない。
そのため、フェーズ A の再実行は「投入先が無い」ことを理由に停止しない。停止するとループが止まったままになり、`parity-suite` の「データ不足」をいつまでも解消できなくなる。
