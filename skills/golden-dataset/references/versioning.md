# バージョン運用・陳腐化・parity-suite との往復

データセットの `version` は、`parity-suite` / `parity-diff` の成果物が「どのデータで取得したか」を追跡し、土台のデータが変わったベースラインを陳腐化として検出するための鍵である。

## version のセマンティクス

`metadata.json` の `version` は **1 始まりの単調増加の整数**。

- **上げるのは論理データが変わったときだけ**（行の追加・変更、エッジケースの追加、`base_time` の変更）。1 回の変更で +1
- **フェーズ B では上げない**（どの target へ投入しても同じ）。フェーズ B は論理データを新側スキーマへ写像するだけで、論理データ自体は変えないため。フェーズ B が記録するのは投入した version（`phase_b.<slug>.<target>.dataset_version`）であり、`version` 自体は動かさない
- `base_time` の変更は論理データの変更として扱う（時刻依存データが全部変わるため → +1）

`changes` は version ごとの変更履歴で、`1..version` の各整数を 1 件ずつ欠番・重複なく持つ。各要素は `{ version, affects }` とし、`affects` にはその版で論理データを変更したテーブル名（`static` では静的データ単位）を重複なく列挙する。

- 複数テーブルを変えた版はすべて列挙する。空配列は禁止（version を上げる変更なら影響先がある）
- `base_time` の変更や、影響テーブルを安全に限定できない変更だけは sentinel `*` を単独で記録する。`*` と個別名を混在させない
- 過去の要素は上書き・削除しない。ベースラインが複数 version を跨ぐとき、間の全変更との和集合で影響を判定するために履歴が必要になる
- 旧 metadata に `changes` が無い／履歴に欠番・重複・不正な `affects` がある場合は、影響なしへ倒さず **全 slug に影響するものとして扱う**。次のフェーズ A 実行で、根拠を確認できる履歴だけを非破壊で補う。推測で過去のテーブルを割り当てない

既存 metadata を更新するフェーズ A は `changes` 列を非破壊で追加する。過去版ごとの変更根拠が揃うなら `1..version` を復元し、揃わない版はその版の `affects` を `["*"]` として埋める。形式だけ合わせるために過去の個別テーブルを推測しない。

## slug が読むテーブルの導出

陳腐化判定では `.replace/features.md` から slug の実効参照テーブルを導く。

- 機能: 機能一覧の「テーブル」＋その slug を fan-out に含む横断 API の「参照テーブル」
- 横断 API リソース: その行の「参照テーブル」
- バッチ: その行の「参照テーブル」
- `-` は空集合。空欄・列欠落・未知の slug は「テーブル無し」でなく判定不能なので、影響ありに倒す

記録済み version を `V`、現在を `C` とすると、まず両方が整数で `1 <= V <= C` を満たすことを確認する。`V > C` は、metadata の破損や古い dataset metadata への巻き戻しでしか生じない不可能な状態であり、変更区間が空であることを「影響なし」と解釈せず停止する。範囲外・非整数・欠落はいずれも fail-closed とする。

version の範囲が妥当な場合だけ、`V < change.version <= C` の全 `affects` と実効参照テーブルに交差があるかを調べる。範囲内に `*` があれば必ず陳腐化する。交差が無ければ version 数値が古くてもその slug の成果物は有効であり、**成果物の `dataset_version` を書き換えず**「影響なし」と判定する（書き換えると後から履歴を監査できない）。

## 陳腐化検出の全体像

`version` を各下流成果物が記録し、記録後の `changes[].affects` と slug の実効参照テーブルを突き合わせて陳腐化を検出する。

| 読み手 | 記録する場所 | 検出 |
|---|---|---|
| `parity-suite` | `.replace/parity/<slug>/metadata.json` の `dataset_version` | ベースライン採取後の変更がその slug に影響するときだけ再取得を宣言 |
| `parity-diff` | 同上を参照 | 陳腐化したベースラインでの比較を避ける |
| `replace-strategy status` | 上記を集約 | 記録後の変更がその slug に影響するときだけ「要再取得」と報告 |

**slug が読むデータを刷新すると、その変更より前に取得した視覚ベースラインと特性化結果は無効になる。** version は順序を、`changes[].affects` は影響範囲を機械的に検出させる。無関係なテーブルだけの変更や、実効参照テーブルが `-` の slug は再取得しない。

## parity-suite の gaps.md「データ不足」からの戻りループ

`parity-suite` が現行アプリを探索する過程で、シードに足りないケースが必ず見つかる（このパターンのデータが無いと空リストしか確認できない、ページネーションが 1 ページで終わる、等）。これは `gaps.md` に「データ不足」として記録され、本スキルへ戻る入口になる。

戻ってきたら（フェーズ A 再実行）:

1. **設計追記**: `design.md` に不足パターンを追加する（何を追加したかを「gaps 由来の追加履歴」に version 付きで残す）
2. **ツール更新・再投入**: 追加分を含めて投入ツールを更新し、現行へ再投入する（冪等なので全体を入れ直す。`dataset_mode: db` は現行テスト環境の DB、`static` は `dataset_static_paths` 配下）
3. **再検証**: FK 整合・必須項目・件数・カバレッジ（`static` では参照整合・必須フィールド・型・件数・カバレッジ）を再確認する
4. **`version` を +1**: `metadata.json` を更新し、同じ version と実際に変更したテーブルを `changes` に追記する（`static` では `current.fingerprint` も再計算して更新する）
5. **影響ベースラインの再取得を案内**: 変更したテーブルと実効参照テーブルが交差する `parity-suite` だけが陳腐化する。**該当 slug に限って `parity-suite` の再実行を案内する**

このループは一度きりではなく、探索が進むたびに繰り返される前提で運用する。

**`dataset_mode` に関わらずこのループは回る。** DB を持たないプロジェクト（`static`）でも投入先 target に `db` を要求しないため、フェーズ A の再実行は「投入先が無い」を理由に停止しない（停止すればループがデッドロックし、`parity-suite` の「データ不足」を永久に解消できなくなる）。
