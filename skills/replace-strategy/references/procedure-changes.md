# 手順・観点の変更を既に閉じた機能へ当て直す（`.replace/procedure-changes.md`）

機能は 1 つずつ Issue にして閉じる。
後の機能で、確かめる軸の抜け（0 件のときの表示・送っている間の押し直し・入力の重複など）が見つかることがある。
そのとき軸は、その機能の網羅表とスイートと、手順（スキルか、プロジェクトの観点の決まり）には足される。
しかし、それより前に閉じた機能へ遡って当てる工程が無いと、前の機能は旧手順のまま、収束した扱いで残る。

古くなったことを検出する仕組み（データセットの版・採取ツールの版）は、どれも「手順が変わった」ことには当たらない。
スイートは緑で、`parity-diff` は収束したままなので、差は人が監査で見つけるまで残る。

そこで、軸を足した変更ごとに、それより前に特性化を終えた機能を機械的に列挙し、機能ごとに「当て直した／当てない」の判断を記録させる。

## 変更の出所は 2 つ

| 出所 | 記録する場所 | 対象になる機能 |
|---|---|---|
| スキル側の手順の改訂 | `parity-suite` の `assets/procedure-revisions.json`（スキルに同梱する。プロジェクトは書かない） | `.replace/parity/<slug>/metadata.json` の `run.procedure_revision` がその改訂より小さく、`mode` が改訂の `affects` に入る機能。キーが無い成果物は改訂番号を導入する前のものなので、すべての改訂の対象になる |
| プロジェクト側の観点の追加 | `.replace/procedure-changes.md` の「観点の追加」表 | 同じ `metadata.json` の `run.finished_at` に書かれた日付が追加日以前（同じ日を含む）で、`mode` が「対象の種類」に入る機能。日付はオフセットを UTC に換算せずに読む（下の注を参照） |

- `run.finished_at` の日付は、オフセットを UTC に換算しない。換算すると、UTC より遅れた地域の終了日時が翌日になり、同じ日の追加の対象から外れる。
- `finished_at` も `procedure_revision` と同じく、特性化を全体でやり直したときだけ書き換える。
  部分的な再取得や当て直しで新しい日付にすると、閉じた機能が警告なしに追加の対象から外れる。
- `metadata.json` の無い slug は、特性化の前なので対象にしない。着手したときに新しい手順で作られる。
- 改訂の一覧を持つのは `parity-suite` だけである。
  他のスキル（`parity-replace` / `parity-diff` など）の手順の更新で確かめる軸が増えたら、プロジェクト側の台帳に行を足す。
- Issue が open か closed かは見ない。成果物があれば、閉じていなくても旧手順で特性化されている。

## 台帳（`.replace/procedure-changes.md`）

テンプレートは [`../assets/procedure-changes-template.md`](../assets/procedure-changes-template.md) である。台帳が無ければ、最初に書く工程がテンプレートから作る。

- 更新は非破壊（追記だけ）にする。チェックは [`../assets/append-only-manifest.json`](../assets/append-only-manifest.json) の `procedure-changes` で行う。
- 表の列名を変えない。チェックは列名で表を探し、見つからなければ exit 2 で失敗にする。列名を変えた台帳を「変更なし」と読まないためである。
- 表の途中に空行を挟まない。Markdown の表は空行で終わり、以降の行は表の外になる。チェックは表の外にある表の行を数え、exit 2 で失敗にする。
- HTML コメントは、行頭の `<!--` で始め、行末の `-->` で閉じる（1 行で閉じるか、開始の行と終了の行に分ける）。
  - 散文の後ろの `<!--`、行の途中の `-->`、1 行に 2 つのコメント、閉じないコメントは、チェックが exit 2 で失敗にする。
    中の表を生きた表として読むか、以降の表を読み飛ばすことになるからである。
  - セルとインラインコードにも `<!--` / `-->` を書かない。矢印は `→` を使う。
- セルの中の縦棒は `\|` で書く（GFM と同じ）。

### 行を足すきっかけ

確かめる軸を足す変更は、次のどれであっても、同じ作業の中で「観点の追加」に 1 行足す。

- 機能 Issue の中で、他の機能にも要ることがある軸を見つけて、手順に足したとき（網羅表の候補・プロジェクトの観点の決まりなど）。
  見つけた機能の網羅表とスイートに足すだけで終えると、直しは見つけた機能にしか入らない。
- プロジェクトの観点の決まり（ドキュメント・設定）に項目を足したとき。
- kaizen の apply で、成果物を作る手順に確かめる軸を足したとき。手順に反映しただけでは、既存の成果物には当たらない。

「足すかは次の画面で使ってから決める」として、手順に足さずに置いた軸も、置いた時点で行を足す。次の画面が無いと、その軸は最後の機能の記録にしか残らない。
コードの TODO に残さない。TODO はどのチェックにも数えられない。

### 列

| 列 | 値 |
|---|---|
| `ID` | `PC-001` のような一意の名前。`#` を含めない（`parity-suite#<改訂>` はスキル側の改訂の ID のために取ってある） |
| `追加日` | `YYYY-MM-DD`。この日以前に特性化を終えた機能が対象になる |
| `足した軸` | 何を確かめるようにしたか（1 文） |
| `由来` | どこで見つけて、どこに足したか（`project-rule: <パス>` ／ `kaizen: <学びファイル>` ／ `issue: #<番号>`） |
| `対象の種類` | `*` か、`feature` / `api-resource` / `batch` の列挙（`metadata.json` の `mode`） |
| `見直しの置き場` | `この変更の完了条件` か `#<Issue 番号>`。前者なら、対象の機能の当て直しを、その変更の完了条件に入れる。後者なら、別の Issue を起票するところまでを、その変更の完了条件にする（起票した番号を書く。空欄や「後で」はチェックが失敗にする） |

### 判断の語彙（「既に閉じた機能への当て直し」表）

対象になった `変更 ID` × `slug` ごとに 1 行足す。
同じ組み合わせの行が複数あれば、後の行が現在の判断である。追記だけなので書き換えず、判断が変わったら行を足す。

| 判断 | 意味 | `根拠・理由` に書くもの |
|---|---|---|
| `当て直し済み` | その機能で軸を測り、網羅表・スイートに足し、差を直して流し直した | PR・commit・更新した成果物 |
| `当てない` | その機能には当てないと決めた | 当てない理由（その機能に軸の対象が無い、など）。「時間が無い」は理由にしない。後で払う費用が見えなくなるだけなので、`見直し中` と置き場で残す |
| `見直し中` | 当て直しを置き場で追っている | 置き場（`#<Issue 番号>` で始める。チェックが形を確かめる）。未解決として数え続ける |

- 当て直すときは、移行元で測るところからやり直す。
  手順は「移行元で測る → 網羅表とスイートに足す → 差を直す → 両側のスイートと `parity-diff` を流し直す」である。
  スイートに assertion を足すだけでは、移行元の振る舞いを確かめていない。
- 当て直しで `run.procedure_revision` を上げず、`run.finished_at` も書き換えない。
  上げてよいのは、特性化を全体でやり直したときだけである。1 つの軸を当て直しただけで上げると、同じ改訂に含まれる他の軸まで当てたことになる。
  当て直しは台帳の行で記録する。
- 後で作る機能で、前の機能のテストの形をまねるときは、まねる元の機能の未解決の行を先に確かめる。テストの浅さも一緒に引き継がれるからである。

## チェック

```bash
node <replace-strategy>/scripts/procedure-staleness-check.mjs \
  --revisions <parity-suite>/assets/procedure-revisions.json \
  [--ledger .replace/procedure-changes.md] [--parity-dir .replace/parity] [--change <変更 ID>]
```

- `--change` は、1 つの変更の当て直しを完了条件に持つ工程（機能 Issue の受け入れ条件・kaizen の適用）で使う。
  - 名指した変更の組み合わせだけで判定し、他の変更の未判断では止めない。成果物を読めない機能は、その変更の対象かどうかも決められないので残る。
  - 実在しない変更 ID は exit 2 にする。
  - 置き場が `#<Issue 番号>` の変更は、対象の機能ごとに、置き場の番号で始まる `見直し中` を書けば受け渡し済みとする（出力の `handed_off`。exit 0 を妨げない）。
    置き場と違う番号と、未判断は残る。
  - `--change` なしの判定と `status` は、`見直し中` を未解決として数え続ける。
- `--parity-dir` が無いとき、またはディレクトリでないときは exit 2 にする。cwd の誤りや綴りの違いを、「旧手順の機能が無い」と読まないためである。
  特性化の前のプロジェクト（空の `.replace/parity/`）は exit 4 で、当て直す対象が無いことを表す。
- `--revisions` には、インストール済みの `parity-suite` の同梱物を渡す。プロジェクトへコピーしない。コピーすると、新しい改訂が届かない。
- デフォルトの置き場に台帳が無いのは、「プロジェクト側で軸を足していない」と読み、スキル側の改訂だけで判定する（出力の `ledger_exists: false` で区別できる）。
  `--ledger` で明示したパスが無いときは exit 2 にする。綴りの違いで、台帳の未判断を消さないためである。
- 終了コードは次のとおりである。
  - 0: 対象の組み合わせが、すべて判断済み。
  - 1: 未判断か見直し中が残る（`unresolved`）。
  - 2: 入力の誤り。使い方の誤り、改訂の一覧・台帳・成果物の置き場を読めない、台帳の表や列の欠落、表の外の行、扱えない位置の HTML コメント、語彙の外の値、重複した ID、実在しない変更 ID、空の根拠、不正な改訂の一覧、`parity-suite` 以外の改訂の一覧がこれに当たる。
  - 3: 未判断は無いが、成果物を読めず、対象かどうかを決められない機能がある（`undeterminable`）。合格として扱わない。
  - 4: 対象外（特性化済みの成果物が 1 つも無い）。「旧手順の機能が無い」と「何も見ていない」を、同じ exit 0 にしないためである。
- `stray` は、対象でない組み合わせへの記録である（slug の綴りの違い、作り直して対象から外れた機能）。
  失敗にはしないが、綴りの違いなら、対象の組み合わせが未判断のまま残っている。
- 未判断を「旧手順で閉じた機能」として報告するのは、`replace-strategy status` である（[`status.md`](status.md)「導出する内容」の 14）。
