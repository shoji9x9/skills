# 呼び出し元の承認を引き継ぐ

呼び出し元のスキルが Issue の下書きをまとめて利用者に承認してもらい、承認された下書きを 1 件ずつ `issue-create` に任せるときの取り決め。
`issue-create` と、下書きを任せる側のスキル（`replace-strategy` の `issues` モードなど）が、同じこの文書に従う。
引き継げる条件を片方だけで変えると、同じ内容を 2 回承認させるか、承認していない内容で起票することになるからである。

## 引き継げる条件

次のすべてが成り立つときだけ、`issue-create` は呼び出し元の承認を自分の承認として扱い、承認を求め直さずに起票する。

1. 呼び出し元が、起票するすべての Issue について、対象のリポジトリ（`<owner>/<repo>`）・タイトル・本文の全文・ラベルを利用者に見せ、明示の承認を得た。
   見せ方と承認の受け取り方は、`references/user-confirmation.md` に従う。
2. 承認は、同じ実行の中で、下書きを確定した後に得た。前の実行で得た承認や、下書きを直す前に得た承認は引き継がない。
3. 呼び出し元が `issue-create` に、承認された下書き（リポジトリ・タイトル・本文・ラベル）と、1 と 2 を満たして承認を得たことを渡した。
4. `issue-create` が起票する内容が、承認された下書きと一致する。

`issue-create` は利用者と呼び出し元のやり取りを見られないので、1 と 2 は、3 で呼び出し元が渡した申告で判断する。
申告が無いときや、申告がどれかを満たさないと読めるときは、成り立たないとして扱う。

まだ起票していない Issue の番号は、下書きの中に `#<下書き N の番号>` の形の印で書く。
起票した後にこの印を Issue の番号に置き換えることは、4 の「一致する」を変えない。置き換えるのは、呼び出し元でも `issue-create` でもよい。
印のほかの文字列を変えたら、下書きを変えたことになる。

引き継ぐときは、`issue-create` の基本フローのうち、種別の見極め・テンプレートの読み込み・下書きの作成も行わず、渡された下書きをそのまま使う。
下書きの構成は呼び出し元が決め、利用者が承認している。テンプレートの節と違っても、節を足したり並べ替えたりしない。

## 引き継がないとき

次のどれかに当たれば、`issue-create` は承認を引き継がず、自分の手順（`issue-create` の基本フローの承認の段）で承認を求める。
返事をする人がいない実行では、起票せずに、求めるはずだった内容を報告して止まる。

- 上の条件のどれかが成り立たない
- 渡された下書きを変える（誤りに気付いて直すなど）。変えた後の下書きの承認を求める
- 重複の確認で、呼び出し元が利用者に見せていない重複や強く関連する Issue が見つかった

承認を引き継いだときも、重複の確認は省かない。省いてよいのは、利用者に同じ内容の承認を求め直すことだけである。
重複の確認ができない（一覧の取得に失敗したなど）ときは、起票せずに止まり、確認できなかったことを報告する。承認は求め直さない。
