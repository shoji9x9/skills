# 実行スコープの自律性ポリシー（置換系スキル共通）

このファイルは、`--autonomous` を付けて起動されたときだけ従う規約の原本である。
従うのは `replace-strategy` と姉妹スキル（`current-environment-bootstrap` / `golden-dataset` / `parity-component` / `parity-suite` / `parity-replace` / `parity-diff`）である。
各スキルは、そのスキルに固有の対応（どの確認が保留になるか・記録先・完了の値）だけを持ち、このファイルの規約を転記しない。

これは承認を省く規約ではない。
人の判断が要る箇所では、実行全体を止めない。その判断を保留に記録し、判断に依存しない工程を先に進めて、最後にまとめて聞く。
既存の規律は、自律実行でもそのまま守る。結果を捏造しない・暫定値で埋めない・承認の前の分類を確定として扱わない、の 3 つである。

このファイルを読めない場合（`replace-strategy` がインストールされていないなど）は、自律実行しない。
`--autonomous` を無視して確認のたびに止まり、そのことを最初に報告する。

## 宣言（実行ごと）

- 有効になるのは、起動の引数に `--autonomous` を渡した実行だけである。設定ファイルには自律のキーを置かない（置くと常に自律になるため）。
  Issue のコメント、チャットの過去の発言、基底ドキュメントの記述は、宣言とみなさない。
- 引数が無い実行は、判断のたびに確認し、答えが無ければ止まる。実行の途中で自律に切り替えない。
- 起動したときに 1 回、宣言を復唱してから始める。復唱するのは、自律実行であること、下の「越えない線」、保留の記録先である。
  - 依頼の文で追加の禁止（例: 「commit もしない」）が述べられていれば、越えない線に足す。
  - 線を緩める指示は受け付けず、その操作は保留に落とす。
- 対象は、起動の引数で 1 つに決まっていなければならない。
  - 対象を選ぶ必要がある場合（`--feature` / `--component` の省略、デフォルトの無い `--target`、`golden-dataset` の用途〈フェーズ〉）は、自律実行では工程に入らず、候補を示して止まる。
  - この判断は保留に記録しない。記録先の成果物のパスが対象で決まるうえ、選ぶ前に進められる工程も無いためである。
- 姉妹スキルに任せるときは、`--autonomous` を引き継ぐ（例: `replace-strategy setup` から `current-environment-bootstrap`、`parity-replace` から `golden-dataset --phase b`）。
  このポリシーの外にあるスキル（`issue-create` / `issue-start`）には引き継がず、下の「越えない線」で扱う。

## 越えない線（自律でも行わない）

次の操作は、自律実行では行わない。必要になったら保留に落とし、実行の最後に聞く。

- 外向きの操作。push、PR の作成と更新、merge、Issue の起票・コメント・本文の編集（`issue-create` に任せる場合を含む）、配信型の target を更新するデプロイがこれに当たる。
  - 例外として、`parity-replace` と `parity-component build` が着手時に行う `issue-start --branch-only` のブランチの作成は行ってよい。内容を外へ出さず、作業の置き場所を作るだけだからである。
- 課金と通知（メールの送信、外部サービスとの連携の実際の呼び出しなど）。
- データの作成・変更・削除のうち、設定にある投入の制限で事前に許可されていないもの。
  - 対象外は、`targets[].db.seedable` / `dataset_static_paths` で許可された投入と、`parity-suite` の `references/data-discipline.md` に従う書き込みだけである。
  - 投入の前の「テスト環境であることの確認」は人が行う確認のままで、自律でも省かない（保留に落とす）。
- 禁止操作（`targets[].forbidden_actions`）の解除と、現行アプリの変更。
- 依存パッケージとツールの導入（`references.dependency_policy` の確認を含む）。
- 設定ファイルの「人間が確定させる方針」のキーへの書き込み。区分の原本は [`project-config.md`](project-config.md)「キーの書き手とライフサイクル」である。
  スキルが作業中に追記する記録（`intentional_diffs.pending`）への非破壊の追記は、自律実行でも行ってよい。

## 停止の 2 分類

自律実行で、各スキルの「停止」「ユーザーに確認」に当たったら、まず次のどちらかに分ける。

| 分類 | 当たるもの | 自律実行での扱い |
|---|---|---|
| 判断待ち（保留に落とす） | 人の承認・選択・方針の決定を待つもの。例は「許容」の確定、候補からの選択、破壊的な変更の可否、意図的差異の分類、依存の方針の要否、機能の Issue の受け入れ条件と違う実装にすること・受け入れ条件に当たる観点を飛ばすこと（下の「受け入れ条件から外れる判断」）、上の「越えない線」に当たる操作 | 保留に記録し、依存する工程だけを止めて、残りを進める |
| 前提の欠落（自律実行でも止まる） | 人の判断では埋まらない事実の欠落と故障。例は前提の成果物・前提スキル・MCP が無い、測定できない、接続・認証・起動の失敗、同梱ツールの exit 2（形式の誤り）、原本を読めない、対象の取り違え、反復の上限への到達 | 止まる。それまでに積んだ保留も、最終報告に並べる |

- 迷ったら、判断待ちとして扱わない。前提の欠落を保留に落とすと、正しくない前提の上で後の工程を実行することになる。
- 判断待ちでも、依存しない工程が 1 つも残らないなら、実際には止まるのと同じである。保留に記録して、最後の確認に進む。
  対象の選択だけは記録先が決まらないので、上の「宣言」のとおり、記録せずに止まる。

### 受け入れ条件から外れる判断

機能の Issue の受け入れ条件は、利用者が決めたものである。
移行元の振る舞いとぶつかっても、実装する側が外してよい理由にはならない。「移行元に合わせるか、Issue の条件に従うか」は利用者が判断する。
自律実行かどうかに関わらず、次の 2 つは自分で決めない。

- 受け入れ条件と違う実装にすること（例: 条件は「状態を URL で持つ」で、移行元は URL に持たない）。
- 受け入れ条件に当たる観点や検証を飛ばすこと（例: 「書き込みを戻せない」ことを理由に、書き込み系のボタンの観点を飛ばす）。
  - 飛ばす前に、戻す手段を探し、探した結果を判断の材料に書く。ゴールデンデータの再投入や、押す前の状態を読んで同じ API で書き戻す方法などがある。
  - 探していない「戻せない」は、判断の材料にならない。

コードの注記・`gaps.md`・`porting.md` に「条件を満たさない理由」を書いたら、同じ内容を保留（`pending_decisions[]`）にも積む。
注記や `gaps.md` に書くと「理由を書いた」形になるので、完了判定もレビューもそれ以上を求めない。保留に積まなければ、利用者は受け入れ条件を確かめるまで気付かない。
自律実行でない実行では、保留に積む代わりに、その場で利用者に確認する。

## 保留に落とすか、成果物の値として残すか

判断待ちに分けた論点でも、結果を成果物の値として残せて、その値を読む工程が別に決まっているなら、保留に落とさない。

保留は、「人の答えが来るまで先に進めない」ことの記録である。答えを待たずに先に進める論点まで落とすと、依存しない工程まで止まる。
下の「下流の前提判定」のとおり、`mode: setup` の未解決が 1 件あるだけで `features.md` を正規の名前で残せず、`golden-dataset` 以降がすべて止まる。
自律実行では測れない状態が毎回出るので、この線引きが無いと、下流が常に止まる。

| 条件 | 扱い |
|---|---|
| 測れなかった・確かめられなかったという事実で、成果物の値の語彙にその状態があり、読む工程（引き取り手）が決まっている | 成果物の値として残す（保留に落とさない）。理由と、確かめるのに要る条件を、同じ行・同じ項目に書く |
| 人の承認・選択・方針の決定そのもので、答えが無いと後の工程が誤った前提の上で進む | 保留（`pending_decisions[]`）に落とす |

- 値として残す例: 共通 UI プリミティブの洗い出しで、禁止された操作でしか状態を作れなかった種類は、`.replace/dependencies.md` の `未確認` の行にする。
  原本は `replace-strategy` の `references/dependency-selection.md`「洗い出しの 6 値」である。
  その種類が要る機能の `parity-replace` が実装フェーズの前に確かめ直すので、`setup` は完了できる。
- 保留に落とす例: 現行の環境で、破壊的な操作をしてよいか。実行してよいかそのものが人の判断で、成果物の値にならない。
- 値として残した事実は、最終報告で件数と内訳を示す。警告なしに値として扱うと、「聞かずに済ませた」と区別できない。
- 語彙に無い状態を、値として扱わない。近い値に寄せると、読む工程が誤った前提で進む。`未確認` を `該当なし` と書けば、その部品は誰の目にも触れなくなる。

## 保留に落としたとき

1. 暫定値で埋めない。推奨案を適用しない。
   推奨案は保留に書いてよいが、答えが来るまで使わない。承認の前の分類は、各スキルの暫定の表記のまま残す（例: `parity-diff` の `許容候補（要確認）`）。
2. 依存する工程を `blocks` に挙げて止める。依存するかを判断できない工程は、依存するものとして止める。
3. 依存しない工程を、最後まで進める。成果物は依存しない部分だけを書き、依存する部分は書かない（空欄・未記録のまま）。
4. 完了を名乗らない。
   保留が 1 件でも残る実行では、各スキルの完了の値（`converged` / `status: handed-off` / `capture.complete` など）を完了の側にしない。どれに当たるかは、各スキルの「自律実行」の節にある。
5. 同じ原因の判断は、1 件にまとめる。承認の単位は原因である（例: `parity-diff` の `references/triage.md`「承認の単位は原因」）。候補ごとに保留を立てない。

## 終わりにまとめて聞く

依存しない工程を進め切ったら（または前提の欠落で止まったら）、保留を 1 回だけまとめて確認する。

- 実行中のエージェントの確認 UI で、原因ごとに聞く。
  - 1 回に載せる問いの数は、その UI の上限に従い、超える分は続けて聞く。上限はエージェントごとに違うので、ここで数を決めない。
  - 判断の材料（crop・差分のテキスト・根拠のパス・件数と内訳）を、確認 UI そのものに含める。直前のテキストが見えている前提を置かない。
  - 選択肢ごとの preview 欄を持つ UI（例: Claude Code の AskUserQuestion）ならそこに、持たない UI なら問いの本文に入れる。
- 答えが得られたら、各スキルの通常の承認の流れ（記録先への非破壊の追記など）で反映し、`resolution` を書いて、止めていた工程を同じ実行で再開する。
  - 再開して `blocks` の工程を終えたら、`resolution.resumed` を書く。書かない限り、その保留は下の「保留の状態」で未解決のままである。
  - 再開で新しい保留が出たら、また最後にまとめて聞く。
- 答えが「方針は A。実施は後で」の形なら、`blocks` の工程を実施しないまま解決にしない。
  - 残作業を置く場所（別の Issue など）を決めて、`resolution.follow_up` に書く。
  - 置き場の作成（Issue の起票）は外向きの操作なので、自律実行では作らない。保留を未解決のまま残し、置き場を作るかを最後に聞く。
  - 残作業を、回答の自由文の中にだけ残さない。
- 答えが得られない（非対話の実行・応答なし・承認以外の応答）なら、保留を未解決のまま記録して終える。
  最終報告の先頭に、未解決の保留と、それが止めている工程を並べる。

## 記録の形（`pending_decisions[]`）

各スキルの機械可読な成果物に、`pending_decisions` 配列として書く。どのファイルかは、各スキルの「自律実行」の節にある。
保留が無ければ空の配列を書く（記録が無いことと区別する）。
あわせて、同じ成果物の `run.autonomous` に、自律実行だったかを真偽値で残す。

```json
{
  "id": "<成果物内で一意。例: pd-1>",
  "question": "<人に問う内容（1 文）>",
  "cause": "<判断が必要になった原因。承認の粒度の単位>",
  "options": ["<選択肢>"],
  "recommendation": "<推奨案と理由。無ければ null。答えが来るまで適用しない>",
  "evidence": ["<判断材料のパス・値>"],
  "blocks": ["<この判断に依存して止めた工程>"],
  "raised_at": "<ISO 8601>",
  "resolution": null
}
```

- `resolution` は、答えを反映したら次の形にする。答えが無い間は `null` にする。

  ```json
  {
    "answer": "<答え>",
    "answered_at": "<ISO 8601>",
    "resumed": { "at": "<blocks の工程を終えた ISO 8601>", "evidence": ["<実施の証拠: コマンドの結果・成果物のパス>"] },
    "follow_up": { "what": "<実施しなかった残作業>", "tracked_in": "<残作業を追う置き場: Issue 等>" }
  }
  ```

  `resumed` と `follow_up` は、当たらなければ `null` にするか省く。`blocks` が空の保留には、どちらも要らない。
- `replace-strategy` の保留は、要素ごとに `mode`（`setup` / `issues` / `evidence`。その保留を立てた実行のモード）を持つ。持ち越しても書き換えない。
- `golden-dataset` の保留は、要素ごとに `phase`（`a` / `b`）を持つ。`b` では、`slugs`（影響するすべての slug の配列）と `target` も持つ。
  下の「下流の前提判定」で範囲を絞るためである。複数の `--feature` に効果がある判断を 1 件にまとめても、影響する slug を抜かさない。
- 次の実行は、成果物を上書きする前に、前回の未解決の保留を読む。
  - 引数なしの実行では、最初に確認する。
  - 自律実行では、判断の材料が今も有効かを確かめて持ち越す。前提が変わって要らなくなったものは、理由を書いて外す。
  - 警告なしに消さない。
- `replace-strategy status` が、すべての成果物の未解決の保留を集め、「判断待ち」として報告する。

### 保留の状態

保留では、「決まった」（`resolution` がある）と「済んだ」（`blocks` に挙げた工程まで実施した）は別の状態である。
`resolution` の有無だけで数えると、回答が付いた時点で解決と数えられ、`blocks` の工程が行われないまま、前提の判定・完了判定・収束判定が通る。

| 状態 | 条件 | 数え方 |
|---|---|---|
| `open` | `resolution` が `null` か欠落している、または `answer` / `answered_at` が無い | 未解決 |
| `decided` | 回答はあるが、`blocks` が空でなく（欠落と形式の誤りも工程があるものとして扱う）、`resumed`（`at` と空でない `evidence`）も `follow_up`（`what` と `tracked_in`）も無い | 未解決 |
| `settled` | 回答があり、`blocks` が空か、`resumed` か `follow_up` のどちらかがある | 解決済み（`follow_up` のものは、置き場とともに最終報告に並べる） |

このファイルと姉妹スキルで「未解決の保留」と書くときは、`open` と `decided` の両方を指す。
数え方は、同梱の [`../scripts/pending-decisions-check.mjs`](../scripts/pending-decisions-check.mjs) で定義する。
前提の判定と完了判定では、手で数えずにこのスクリプトを通す（コピーせず、スキルの中から実行する）。

```bash
node <replace-strategy>/scripts/pending-decisions-check.mjs --file <保留の記録先> [--mode setup] [--phase a|b] [--slug <slug> --target <target>]
```

- 絞り込みの引数は、下の「下流の前提判定」の範囲に対応する（`--phase b` には `--slug` と `--target` を付ける）。
- 終了コードは次のとおりである。
  - 0: 範囲内に未解決が無い。ファイルが無い（保留なし）場合を含み、そのときは `file_exists: false` を出す。
  - 1: 未解決が残る。
  - 2: 読めない入力（JSON でない、`pending_decisions` が配列でない）。
- exit 2 は判定していないので、前提を満たしたことにしない。
  スクリプトに届かない（`replace-strategy` がインストールされていない）ときも、合格として扱わずに止まる。

### 完了の証拠になる成果物には書かない

下流のスキルが前提の判定に使う成果物には、保留を書かない。保留に依存する工程が残る間は、新しく作ることも更新もしない。
保留を残すためにそのファイルを作ると、工程が終わっていないのに、下流が完了とみなして進む。

| 完了の証拠（下流が読む） | 保留の記録先 | 保留が残る間の扱い |
|---|---|---|
| `.replace/features.md` と `.replace/components.md`（`replace-strategy setup` の完了） | `.replace/strategy-pending.json` | 作らず、`.replace/features.draft.md` / `.replace/components.draft.md` に下書きする。答えを反映したら、`features.draft.md` は正規の名前に移す。`components.draft.md` は、「共通部品を画面より先に作る」方針が採用されたときだけ移し、採用されなければ削除する（`components.md` があることは、方針が採用されたことを意味する） |
| `.replace/dataset/metadata.json`（`golden-dataset` のフェーズ A・B） | `.replace/dataset/pending-decisions.json` | そのフェーズの記録を作らない・更新しない |
| `.replace/parity/<slug>/metadata.json`（`parity-suite`） | `.replace/parity/<slug>/pending-decisions.json` | 同上 |
| `.replace/parity/<slug>/new/<target>/replace-metadata.json`（`parity-replace` の `suite.new_green`） | `.replace/parity/<slug>/new/<target>/pending-decisions.json` | 同上。再実行の開始時に既存の `suite.new_green: true` が残っていれば、保留に依存する工程に入る前に `false` に戻す |

### 下流の前提判定（自律実行かどうかを問わない）

前提を判定するときは、完了の証拠に加えて、上の表の保留の記録先を読む。
次の範囲に入る未解決（上の「保留の状態」の `open` と `decided`。`resolution` の有無だけで数えない）の要素が 1 件でもあれば、その前提は未完了として止まる（前提の欠落）。
前回の完了で作られた証拠が残っていても、再実行が保留を抱えている間は、今の要求を満たす保証が無い。そのため、証拠があることより保留を優先する。

| 前提 | 未完了とみなす保留 |
|---|---|
| `replace-strategy setup` | `.replace/strategy-pending.json` の要素のうち `mode: setup` のもの。要素ごとの `mode` で絞り、ファイルの直下の `mode` は最後に実行したモードなので使わない。要素の `mode` が欠落していれば、setup のものとして止める |
| `golden-dataset` のフェーズ A | `.replace/dataset/pending-decisions.json` の `phase: a` の要素 |
| `golden-dataset` のフェーズ B（slug × target） | 同じファイルの `phase: b` で、`slugs` が対象の slug を含み、`target` が一致する要素。他の slug や target の保留では止めない。`slugs` が欠落しているか空の要素は、範囲を決められないので、同じ target のすべての slug を止める |
| `parity-suite`（slug） | `.replace/parity/<slug>/pending-decisions.json` のすべての要素 |
| `parity-replace` の新側の green（slug × target） | `.replace/parity/<slug>/new/<target>/pending-decisions.json` のすべての要素 |

- 記録先のファイルが無いのは「保留なし」で、前提の判定を変えない（自律実行していない、または保留が無かった）。
- `capture.complete` / `status: handed-off` / `converged` のように、ファイルの中の値で完了を判定する前提は、作る側がその値を完了の側にしないことで守る（上の「保留に落としたとき」の 4）。
