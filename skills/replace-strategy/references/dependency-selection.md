# 依存パッケージの導入判断（自前実装かパッケージか・選定基準・導入タイミング）

新側の実装で使う部品（UI コンポーネント・データ処理・フォントなど）について、自前で書くかパッケージを使うか、使うならどれを選ぶかを決める工程と判断材料を定める。
**決定そのものはプロジェクトが行う。** このファイルが定めるのは「何を見て決めるか」と「いつ決めるか」である。
スキル群（`replace-strategy` / `golden-dataset` / `parity-suite` / `parity-replace` / `parity-diff` / `parity-component`）が依存を足すときは、どのスキルもこの基準に従う。

アプリの骨格は、このファイルの対象外である。フレームワーク・レイヤやディレクトリの構成・API の設計方針・ホスティングの構成は事前に定義され、スキルは参照するだけである
（[`project-config.md`](project-config.md) の「新側アーキテクチャ」で定義する）。
このファイルが扱うのは、その骨格の上に載せる部品を採るかどうかである。スキルがこの基準で決め、`.replace/dependencies.md` に記録する。

移行元が配信している画像や書体のファイルをコピーして使うかも、このファイルの対象外である。
判断材料（再配布してよいか・出どころ・残る差）が違うので、[`static-assets.md`](static-assets.md) で定義し、`.replace/assets.md` に記録する。
「本文フォント」の行をここに置いても、アイコン用の書体や画像をコピーして使うかは決まらない。資産を同等のパッケージで置き換えると決めた場合だけ、そのパッケージを採るかをこのファイルの基準で決める。

避ける失敗は 2 つある。

- 既存のパッケージを検討せずに、自前で複雑な実装を始める（例: 表・日付の処理・仮想スクロール）
- 素性や再現の条件を確かめないまま導入し、実装がほぼ終わった段階で差し替えることになる

## いつ決めるか

| 部品の種類 | 決める工程 | 担当するスキル |
|---|---|---|
| プロジェクトで共通のもの（UI ライブラリ・フォント・状態管理・日付の処理など、複数の機能で使うもの） | `setup` の機能インベントリの後 | `replace-strategy` |
| 共通部品を画面より先に作る方針で、共通部品の実装に要るもの（`setup` で決めたものを除く） | `build` の手順 3（部品を採るかの決定。実装に入る前） | `parity-component` |
| 機能に固有のもの（その機能でしか使わないもの） | 実装のフェーズに入る前（ページを分けた後） | `parity-replace` |
| 実装の途中で必要と分かったもの | 気づいた時点（そのまま自前の実装で進めない） | `parity-replace` |
| 検証の側のツール（投入ツール・パリティスイート・差分ツールが使う依存） | そのツールを書き始める前 | `golden-dataset` / `parity-suite` / `parity-diff` |

- 実装を始めてから部品を探さない。差し替えのコストは、実装が進むほど上がる。
- すべてを事前に洗い出せることを前提にしない。実装の途中で増えるのは普通のことで、そのときも同じ基準で判断し、同じ場所に記録する。
- 決定は `.replace/dependencies.md` に記録する（テンプレートは [`../assets/dependencies-template.md`](../assets/dependencies-template.md)）。
  実装の途中で足したものも同じファイルに追記し、敵対的レビューの対象にする。

### 洗い出しの網羅（共通 UI プリミティブ）

「複数の機能で使う部品」は、基盤のライブラリの種類だけを指すのではない。
上の表の例（UI ライブラリ・フォント・状態管理・日付の処理）はどれもライブラリの種類なので、例だけを手がかりに洗い出すと、ライブラリの外にある個々の UI プリミティブが抜ける。
実際の案件では、最初に挙がったのはデータグリッド・共通ヘッダー・ボタンの 3 種だけだった。
指摘を受けてから、セレクト・テキストフィールド・ページネーション・ラジオボタン・チェックボックス・モーダルダイアログ・トースト通知が見つかった。

**次の種類を 1 つずつ、現行アプリのページを実際に開いて確かめる**（候補は `setup` の手順 9 のページの一覧から作る）。
ソースの grep だけで済ませない。ライブラリが描く部品は、アプリのマークアップに現れない。
アプリの側に出てくるのはライブラリのコンポーネントの名前だけで、その内部の部品は出てこない。現行のソースを入手できない場合は、grep そのものが使えない。

初期表示に出ない種類は、その状態を作ってから判定する。確認ダイアログ・トースト・バリデーションのエラー・読み込み中・空の状態・ツールチップは、ページを開いただけでは出ない。
状態を作る操作は、選んだ現行の target の `forbidden_actions` を確かめてから行う。
`forbidden_actions` が定義されていない target は読み取り専用で、空のリストはすべて実施してよい。適用の対象は、アプリへの UI と API の操作である
（[`project-config.md`](project-config.md)「`forbidden_actions` の適用範囲」で定義する）。

- 書き込みを伴わない手段を先に使う。絞り込みで 0 件にする（空の状態）、不正な値を入れて送信前の検証を出す（バリデーションのエラー）、要素にポインタを載せる（ツールチップ）。
- 破壊的な操作の確認ダイアログは、「開いて閉じるだけ」でも書き込みが無いとは数えない。開くには削除のボタンを押す必要があり、誤操作でそのまま実行に至るからである。
  その target でその操作が許可されているときだけ開く（破壊的でない確認ダイアログがあれば、それを先に使う）。
- 保存や削除の実行が要るのは、それ以外に状態を作れない場合（トーストなど）だけで、その操作が許可されている target に限る。
- `--autonomous` の実行では、書き込みを伴う手段を使わない。現行環境を破壊的に変えてよいかは、人の承認が要る判断である。
  `forbidden_actions: []` は「人が許可した」ではなく、「設定の上では実施してよい」というだけである。

確かめられなかった種類は、台帳に `未確認` の行として残す（下の「洗い出しの 6 値」）。
禁止されている操作でしか作れない種類や、状態を作れなかった種類を `該当なし` と書かない。
ページを開いただけで見つからなかったのは「無い」ではなく「まだ見ていない」で、`該当なし` にすると共通部品が台帳から消える。
理由と、確かめるのに要る条件（禁止された操作の名前を含む）を「理由・引き取り手」の列に書き、あわせてユーザーに報告する。
現行環境は比較の基準なので、状態を作るために、保護されたデータを書き換えない。

自律実行でも、`未確認` を保留（`pending_decisions`）にしない。
成果物の値として残せる事実の記録で、引き取り手（その部品が要る機能の `parity-replace`）が別にいるので、`setup` はこの種類を残したまま完了できる。
区分の根拠は [`autonomy.md`](autonomy.md)「保留に落とすか、成果物の値として残すか」にある。

| 区分 | 種類 |
|---|---|
| 入力 | テキストフィールド（1 行・複数行・検索ボックス）、セレクト・コンボボックス、ラジオボタン、チェックボックス、日付・時刻の入力、数値・金額の入力、ファイルの選択 |
| 操作 | ボタン（主・副・破壊的・アイコンだけ）、リンク、トグル・スイッチ、タブ |
| 表示 | テーブル・データグリッド、ページネーション、ラベル・バッジ・ステータスの表示、空の状態の表示、読み込み中の表示 |
| 通知・割り込み | モーダルダイアログ（確認・フォーム）、トースト・フィードバックの通知、フォームのバリデーションのエラーの表示、ツールチップ |
| 骨組み（画面に共通して現れる枠。冒頭の「アプリの骨格」、つまりフレームワークと構成とは別） | ヘッダー・グローバルナビゲーション、パンくず、フォームのレイアウト |

- 1 つの機能でしか使わないと確かめた種類は、この工程で採るかを決めない。`parity-replace` が実装のフェーズの前に、同じ基準で決める（上の「いつ決めるか」の「機能に固有のもの」の行）。
  `該当なし` にも、採る・採らないの決定にもせず、`機能固有` の行として残す。`該当なし` にすると、共通部品でないものが台帳から消える。
  採る・採らないを決めると、1 つの機能の材料だけで、全機能の分の決定をしたことになる。
- 「無い」と書けるのは、開いて確かめたときだけである。該当が無いと確かめた種類も、`.replace/dependencies.md` に `該当なし` と残す。
  行が無いと「まだ見ていない」と読めるので、確かめた結果としての不在を台帳に残す。
- どの種類にも行を作る。確かめた結果が採る・採らないの決定に至らなくても（内蔵・機能固有・未確認）値として残すので、台帳に行が無い種類は「まだ見ていない」と読んでよい（下の「洗い出しの 6 値」）。
- `該当なし` は、採る・採らないの決定ではない。下流（`parity-replace` の実装のフェーズの前の決定）は、`該当なし` の行を「`setup` で決めたもの」に数えない。
  その部品が必要になったら、現行にあるかを確かめ直して決める。`該当なし` は「現行に無いと確かめた」であって、「作らないと決めた」ではない。
- 採る候補のライブラリに内蔵される部品（例: データグリッドの行選択のチェックボックス、グリッドに内蔵のページネーション）を、単体の部品として重ねて洗い出さない。
  内蔵かどうかは、現行の実装ではなく、新側で採る候補で決まる。候補を採るかがまだ決まっていないうちは、内蔵と決めつけない。
  その部品を含む候補を採ると決めてから `内蔵` の行を書き、「採用したもの」の列にそのパッケージを書く（下の「洗い出しの 6 値」）。
- この一覧は網羅ではない。一覧に無い部品は一覧からは出てこないので、ページを開いて見つけた部品を足す。一覧を通したことを、実機での確認の代わりにしない。
- 共通部品を画面より先に作る方針なら、この洗い出しが `.replace/components.md` の部品の一覧の起点になる。
  インスタンスが 1 つしか無い部品は、先に作る対象にしない（`SKILL.md` の手順 10 で定義する）。

### 洗い出しの 6 値

洗い出した種類は、必ず `.replace/dependencies.md` の一覧に行として残す（テンプレートは [`../assets/dependencies-template.md`](../assets/dependencies-template.md)）。
採る・採らないの決定に至らない扱いを「報告するだけ」にすると、台帳に行が無いことが、「まだ見ていない」と「確かめたが、行にしない扱いだった」のどちらでもありうる状態になる。
そうなると、洗い出しがどこまで終わったかを台帳から読めない。値にすれば、行が無いことは、そのまま「まだ見ていない」を意味する。

| 決定 | 意味 | 書く工程 | 読む工程（引き取り手） |
|---|---|---|---|
| `パッケージ採用` / `自前実装` | 採るかが決まった | 決めた工程（`setup` / `parity-component build` の手順 3 / `parity-replace` の実装のフェーズの前） | 実装の側はこの行に従い、決め直さない |
| `該当なし` | 現行に無いと確かめた | 確かめた工程 | 「決めたもの」に数えない。その部品が必要になったら、現行にあるかを確かめ直して決める |
| `内蔵` | 新側で採る候補のライブラリに含まれる | その候補を採ると決めた工程 | `parity-replace` / `parity-component` は単体で実装しない。「採用したもの」の列のパッケージを実際に採ったかを確かめ、採らないことになっていたら、決定が覆ったものとして扱う |
| `機能固有` | 1 つの機能でしか使わないと確かめた | 確かめた工程（多くは `setup`） | 「適用範囲」の列の機能の `parity-replace` が、実装のフェーズの前に同じ基準で決め、覆った決定として追記する |
| `未確認` | 状態を作れなかったか、操作が許可されず、現行にあるかを確かめられなかった | 確かめようとした工程 | その部品が要る機能の `parity-replace` が、実装のフェーズの前に確かめ直す。処置しないまま残る件数は、`replace-strategy status` が未検証の領域として報告する（[`status.md`](status.md) で定義する） |

- `内蔵` は、現行の実装ではなく、新側で採る候補で決まる。候補を採るかがまだ決まっていないうちは書かない（書くと、その候補を採らなかったときに、誰も実装しない部品が残る）。
- `未確認` を `該当なし` にしない。「まだ見ていない」を「無い」と書くと、共通部品が台帳から消える。
- `機能固有` を、採る・採らないの決定にしない。1 つの機能の材料だけで、全機能の分の決定をしたことになる。
- `内蔵` / `機能固有` / `未確認` は、「理由・引き取り手」の列を空にしない。読む工程が、その行だけを見て次に何をするかを決められる必要がある。

#### 覆ったときの記録方法

決定が覆ったら（候補を採らないことになった・確かめられた・複数の機能で使うと分かった）、古い行を消さずに状態の列を書き換え、新しい行を追記する。

1. 古い行の `状態` を `取り消し済み（YYYY-MM-DD → 新しい行）` にする
2. 同じ `部品（用途）` のセルの文言で、新しい行を末尾に追記し、`状態` を `有効`、`決定時期` を覆した工程にする
3. 新しい行の「理由・引き取り手」に、覆した理由を書く

- 照合のキーは、`部品（用途）` のセルの文字列である。前後の空白を除いた完全一致で探す。文言を変えて追記すると別の部品として並ぶ。
  表記を変えたいときも、古い行と同じ文言で追記する（表記の変更は、台帳の書き換えではなく、次の追記で行う話でもない）。
- その場で更新してよいのは `状態` の列だけである（`append-only-check.mjs` の `mutable_columns`）。
  行の削除・他の列の書き換え・行の入れ替えは、追記専用の検査で失敗になる（[`../assets/append-only-manifest.json`](../assets/append-only-manifest.json) の `dependencies` で定義する）。
- `内蔵` が覆るのは、候補を採るかが変わったときだけではない。採ったライブラリの版を上げて、内蔵の部品が外れた場合も、同じ手順で覆す。

#### 列が無い台帳を読んだとき（本節の導入前に作られた台帳）

`状態` の列と `理由・引き取り手` の列は後から足したので、それより前に作られた `.replace/dependencies.md` にはこの列が無い。

- 次にこの台帳に追記するスキルが、既存のすべての行に列を非破壊で足して埋める（`setup` の再実行を待たない）。
  `状態` は `有効`、`理由・引き取り手` は根拠が残っていなければ `-` にする。列を足しても、追記専用の検査では新しい単位が増えるだけなので失敗にならない。
- 読む側は、`状態` の列が無い台帳のすべての行を `有効` として読む（列が無いことを `取り消し済み` と読まない）。
- `決定` の列に 6 値以外の値（導入前の自由記述）があれば、近い値に寄せず、その行を示してユーザーに確認する。
  寄せた先が `該当なし` なら台帳からその部品が消え、`パッケージ採用` なら、誰も確かめていない決定が決めたものになる。

#### 読む側の規則

- `状態` が `有効` の行だけを読む。`取り消し済み` は履歴で、今の決定ではない。
- 同じ `部品（用途）` で `有効` の行が 2 つあるのは、台帳の不整合である。先の行や後の行を選んで進めず、両方を示してユーザーに確認する
  （覆ったときの手順 1 を飛ばして、追記だけした形なので、どちらが今の決定かを台帳からは決められない）。
- その部品の行はあるのに `有効` が 1 つも無いのも、同じく不整合である（覆ったときの手順 2 の追記を飛ばし、状態の列だけ `取り消し済み` にした形）。
  `状態` はその場の更新を許される唯一の列なので、追記専用の検査は通ってしまい、読む側には「行が無い」のと同じに見える。
  「行が無いならまだ見ていない」という前提が成り立たなくなるので、行が無いのではなく、今の決定が失われているとして報告する。
- 行が無い種類は「まだ見ていない」である。実装の都合で値を推測せず、その種類を確かめてから行を足す。

## 決める順序

1. 要件を先に書き出す。「何が一致すれば現行と同じと言えるか」を書く。要件を書く前に候補を探すと、要件を満たさない候補に時間を使う。
   例: 本文のフォントでは、版とヒンティングの命令の有無の両方が、字形と送り幅に影響する。どちらか一方が一致しても、現行と同じ表示にはならない。
2. 自前で実装するかパッケージを使うかを決める。まず既存のパッケージを探す。
   探した結果として自前の実装を選ぶのはよい（要件が特殊、依存を増やす価値が無い、など）。探さずに書き始めない。自前の実装を選んだ理由も記録する。
3. リポジトリの方針を先に把握する（下の「方針の有無を前提にしない」）。
   方針は候補を絞る前提（ライセンスの拒否リスト・バンドルサイズの上限など）なので、比較を始めてからではなく、候補を絞る前に置く。
4. 候補を素性で絞る。配布元の素性（公式の配布か、第三者による再配布か）とライセンスを最初に確かめる。
   バンドルサイズや API の使いやすさといった詳しい比較は、その後に行う。方針があれば、ここで照らす。
5. 残った候補を判断材料（下記）で比べ、決定・採らなかった理由・方針との適合を記録する。
6. 導入する。実装に入る前に、依存として足しておく（実装の途中で必要になったものも、この順序を通してから使う）。

素性の確認を後回しにしない。「動くものが見つかった」時点で実装に進むと、非公式の配布やメンテナンスの終了といった素性の問題が、実装を終えた後に見つかり、差し替えのコストが最も大きくなる。

## 判断材料

しきい値ではなく、確かめて記録する項目である。しきい値と可否の線引きは、リポジトリの方針（下記）かユーザーが決める。

| 材料 | 見るもの | 確認の手段の例（npm レジストリ） |
|---|---|---|
| ライセンス | ライセンスの種類と、リポジトリの方針と合うか | `https://registry.npmjs.org/<pkg>/latest` の `license` |
| メンテナンスの状況 | 最終リリースの日付・未解決の Issue の傾向・メンテナーの数 | `https://registry.npmjs.org/<pkg>` の `time` / `maintainers`、上流のリポジトリの Issue |
| 採用の規模 | ダウンロード数・依存元 | `https://api.npmjs.org/downloads/point/last-month/<pkg>` の `downloads` |
| 配布元の素性 | 公式の配布か、第三者による再配布か | `latest` の `repository` / `homepage` を、上流の公式のサイトやリポジトリと突き合わせる |
| バンドルサイズ | 配布物のサイズ、tree-shaking ができるか | `latest` の `dist.unpackedSize` |
| 型定義 | 同梱か、`@types/*` か、無いか | `latest` の `types` / `typings`、`@types/<pkg>` があるか |
| 実行基盤との両立 | 新側の実行ランタイムで動くか（ネイティブのバイナリ・ファイルシステムへの書き込み・Node の標準の API への依存） | `latest` の `engines` / `os` / `cpu` / `scripts.install`（インストールのときにバイナリを取得するか）、上流のランタイムごとのサポート表 |
| 代わりの候補 | 何と比べたか、なぜ採らなかったか | — |

- レジストリの API の一次情報は <https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md> ・ <https://github.com/npm/registry/blob/main/docs/download-counts.md> である。
- スコープ付きのパッケージは、URL のパスのセグメントで `/` を `%2F` にする（`@scope/name` → `@scope%2Fname`）。
- 新側のスタックが TypeScript なので例は npm レジストリだが、他のエコシステムでも見る項目は同じである（確認の手段だけが変わる）。
  候補は、新側のスタック（設定の `new.stack`。フレームワーク・ORM・実行ランタイムなど）と両立するものに絞る。空か欠けていれば、推測せずユーザーに確認する。
- 実行基盤の制約は、詳しい比較ではなく「候補を絞る条件」である（上の「決める順序」の 4 で、素性・ライセンスと同じ段に置く）。
  サーバレスやエッジには、ネイティブのバイナリを持つ依存が動かない・ファイルシステムに書けない・Node の標準の API が一部欠ける、といった制約があり、候補を外す理由になる。
  基盤は設定の `references.architecture`（実行基盤と、使うマネージドサービスを含む決定の記録）から読む。整っていなければ、推測せずユーザーに確認する。
  比較を終えてから「その基盤では動かない」と分かると、順序 5 の作業がすべて無駄になる。
- 非公式の配布がいつでも不可という意味ではない。公式の配布に要件を満たすものが無く、再配布を採ると判断することはありうる。
  要件は、導入の前に素性を確かめ、記録してユーザーと合意することである。
- 検証の側のツール（投入ツール・パリティスイート・差分ツール・ファイルの解析ツール）では、バンドルサイズより、CI に入れるコストと出力の決定論性を重く見る。
  ブラウザに配信されないので、配布するサイズの意味は薄い。代わりに、次の 2 点が影響する。
  (i) プラットフォームごとのネイティブのバイナリやランタイムが要るか、インストールのときに取得が起きるか。(ii) 同じ入力に同じ結果を返すか（抜き出す順・空白・改行が安定しているか）。
  しきい値の線引きは、上のとおりリポジトリの方針かユーザーが決める。
  xlsx と PDF の解析ツールの候補の実測値と記録先は、[`file-io.md`](file-io.md)「xlsx / PDF の解析ツール」にある。

## 方針の有無を前提にしない（重要）

ライセンスの拒否リスト・供給網の方針・バンドルサイズの上限・公開からの経過日数による採用の遅延・依存のレビューの自動化は、持つリポジトリと持たないリポジトリがある。
持っていると決めて進めると、持たないリポジトリでは工程が先に進まない。

設定 `references.dependency_policy` は 3 つの値として読む（`none` と欠落を同じに扱わない）。
3 つの値それぞれの意味と、スキルの振る舞いは、[`project-config.md`](project-config.md) の「依存導入の方針」で定義する。ここへ転記しない。

このファイルが足すのは、確認していない（キーが無い）ときの確認の手順だけである。

- README・CONTRIBUTING・基底ドキュメント（`AGENTS.md` / `CLAUDE.md` / `.github/copilot-instructions.md` など）・CI の設定に、方針が無いかを先に探す。
- 見つからなければ、方針が要るかどうかそのものをユーザーに確認し、確認した結果を設定の `references.dependency_policy` に記録する。
  記録するのは、方針のドキュメントのパスか、方針を持たないと確認したなら `none` である。記録するのは確認したスキルである（`setup` を待たない）。
- スキルの側のデフォルトの拒否リスト・しきい値・待機日数を持ち込まない。
- 方針が無いまま進める場合も、判断材料の確認と記録は省かない。記録が残っていれば、後から方針ができたときに判定し直せる。

## 記録（`.replace/dependencies.md`）

- 場所は、対象のプロジェクトの `.replace/dependencies.md` である。他のテキストの成果物と同じく、Git で管理する。
- 無ければテンプレートから作る。このファイルの導入より前に `setup` を終えたプロジェクトには無いので、最初に追記するスキルが作る（`setup` の再実行を待たない）。
- 追記は非破壊にする。既存の決定を書き換えない。
  覆ったときは、古い行の `状態` だけを `取り消し済み` にし、新しい行を追記して、そこに覆した理由を書く（手順は上の「覆ったときの記録方法」）。
  古い行の `理由・引き取り手` を書き換えると、追記専用の検査が失敗する。同じ失敗を繰り返さないための理由を、後から読めるようにするためである。
- 敵対的レビューでは、差分に新しい依存（`package.json` など）が入っていたら、この記録があるかを見る（レビューの観点は `parity-replace` の `references/adversarial-review.md` で定義する）。
