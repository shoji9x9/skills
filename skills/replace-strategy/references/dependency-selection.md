# 依存パッケージの導入判断（自前実装かパッケージか・選定基準・導入タイミング）

新側実装で使う部品（UI コンポーネント・データ処理・フォント等）について、**自前で書くかパッケージを使うか**、使うならどれを選ぶかを決める工程と判断材料を定める。
**決定そのものはプロジェクトの裁量**であり、本ファイルが定めるのは「何を見て決めるか」と「いつ決めるか」。スキル群（`replace-strategy` / `golden-dataset` / `parity-suite` / `parity-replace` / `parity-diff`）が依存を追加するときは、どのスキルでもこの基準に従う。

**アプリの骨格は本ファイルの対象外。** フレームワーク・レイヤ／ディレクトリ構成・API 設計方針・ホスティング構成は**事前定義でスキルは参照のみ**（正本: [`project-config.md`](project-config.md) の「新側アーキテクチャ」）。
本ファイルが扱うのは、その骨格の上に載せる**部品の採否**——スキルがこの基準で決めて `.replace/dependencies.md` に記録するもの——である。

避ける失敗は 2 つ。

- 既存のパッケージを検討せず、自前で複雑な実装を始める（例: 表・日付処理・仮想スクロール）
- 素性や再現条件を確認しないまま導入し、実装がほぼ終わった段階で差し替えになる

## いつ決めるか

| 部品の種類 | 決める工程 | 担当スキル |
|---|---|---|
| プロジェクト共通（UI ライブラリ・フォント・状態管理・日付処理など複数機能で使うもの） | `setup` の機能インベントリの後 | `replace-strategy` |
| 機能固有（その機能でしか使わないもの） | 実装フェーズに入る前（ページ分割の後） | `parity-replace` |
| 実装中に必要と判明したもの | 気づいた時点（そのまま自前実装で進めない） | `parity-replace` |
| 検証側の道具立て（投入ツール・パリティスイート・差分器が使う依存） | その道具を書き始める前 | `golden-dataset` / `parity-suite` / `parity-diff` |

- **実装を始めてから部品を探さない。** 差し替えコストは実装が進むほど上がる
- **事前にすべてを洗い出せる前提を置かない。** 実装中に増えるのは正常であり、そのときも同じ基準・同じ記録先で判断する
- 決定は `.replace/dependencies.md` に記録する（テンプレート: [`../assets/dependencies-template.md`](../assets/dependencies-template.md)）。実装中に追加したものも同じファイルへ追記し、敵対的レビューの対象にする

## 決める順序

1. **要件を先に書き出す**——「何が一致すれば現行と同じと言えるか」。要件を書く前に候補を探すと、要件を満たさない候補に時間を使う
   （例: 本文フォントでは、版とヒンティング命令の有無の両方が字形・送り幅に効く。どちらか一方が一致しても現行と同じ表示にはならない）
2. **自前実装かパッケージかを決める**: **まず既存パッケージを探す**。探した結果として自前実装を選ぶのは可（要件が特殊・依存を増やす価値が無い等）。探さずに書き始めない。自前実装を選んだ理由も記録する
3. **リポジトリの方針を先に把握する**（下記「土台の有無を前提にしない」）。方針は候補を絞る前提（ライセンス拒否リスト・バンドルサイズ上限等）なので、比較を始めてからではなく**候補を絞る前**に置く
4. **候補を素性で絞る**: **配布元の素性（公式配布か第三者による再配布か）とライセンスを最初に確認する。** バンドルサイズ・API の使い勝手といった詳細比較はその後。方針があればここで照らす
5. **残った候補を判断材料（下記）で比較し、決定・不採用理由・方針との適合を記録する**
6. **導入する**: 実装に入る前に依存として追加しておく（実装中に必要になったものも、この順序を通してから使う）

素性の確認を後回しにしない。「動くものが見つかった」時点で実装へ進むと、非公式配布・メンテナンス終了といった素性の問題が実装完了後に発覚し、差し替えコストが最大になる。

## 判断材料

**閾値ではなく、確認して記録する項目**。閾値・可否の線引きはリポジトリの方針（下記）かユーザーが決める。

| 材料 | 見るもの | 確認手段の例（npm レジストリ） |
|---|---|---|
| ライセンス | ライセンス種別と、リポジトリの方針との整合 | `https://registry.npmjs.org/<pkg>/latest` の `license` |
| メンテナンス状況 | 最終リリース日・未解決 Issue の傾向・メンテナー数 | `https://registry.npmjs.org/<pkg>` の `time` / `maintainers`、上流リポジトリの Issue |
| 採用規模 | ダウンロード数・依存元 | `https://api.npmjs.org/downloads/point/last-month/<pkg>` の `downloads` |
| 配布元の素性 | 公式配布か、第三者による再配布か | `latest` の `repository` / `homepage` を上流の公式サイト・リポジトリと突き合わせる |
| バンドルサイズ | 配布物のサイズ、tree-shaking の可否 | `latest` の `dist.unpackedSize` |
| 型定義 | 同梱か `@types/*` か、無しか | `latest` の `types` / `typings`、`@types/<pkg>` の存在 |
| 実行基盤との両立 | 新側の実行ランタイムで動くか（ネイティブバイナリ・ファイルシステム書き込み・Node 標準 API への依存） | `latest` の `engines` / `os` / `cpu` / `scripts.install`（インストール時にバイナリを取得するか）、上流のランタイム別サポート表 |
| 代替候補 | 何と比べたか、なぜ採らなかったか | — |

- レジストリ API の一次情報（2026-07-29 確認）: <https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md> ・ <https://github.com/npm/registry/blob/main/docs/download-counts.md>
- **スコープ付きパッケージは URL のパスセグメントで `/` を `%2F` にする**（`@scope/name` → `@scope%2Fname`）
- 新側スタックが TypeScript のため例は npm レジストリだが、**他のエコシステムでも見る項目は同じ**（確認手段だけが変わる）。
  **候補は新側スタック（設定の `new.stack`。フレームワーク・ORM・実行ランタイム等）と両立するものに絞る**（空・欠落なら推測せずユーザーに確認する）
- **実行基盤の制約は詳細比較ではなく「候補を絞る条件」である**（上記「決める順序」の 4 で素性・ライセンスと同じ段に置く）。
  サーバレス／エッジではネイティブバイナリを持つ依存が動かない・ファイルシステムに書けない・Node 標準 API が一部欠ける、といった制約が候補を落とす。
  基盤は設定の `references.architecture`（実行基盤と利用マネージドサービスを含む決定記録）から引き、**未整備なら推測せずユーザーに確認する**——
  比較を終えてから「その基盤では動かない」と分かると、順序 5 の作業がまるごと無駄になる
- **非公式配布が常に不可という意味ではない。** 公式配布に要件を満たすものが無く再配布を採る判断はありうる。要件は「導入前に素性を確認し、記録してユーザーと合意すること」
- **検証側の道具立て（投入ツール・パリティスイート・差分器・ファイル解析ツール）では、バンドルサイズより「CI 導入コスト」と「出力の決定論性」を重く見る**——
  ブラウザへ配信されないため配布サイズの意味が薄く、代わりに (i) プラットフォーム別ネイティブバイナリ／ランタイムの要否とインストール時の取得の有無、
  (ii) 同じ入力に同じ結果を返すか（抽出順・空白・改行の安定性）が効く。閾値の線引きは上記のとおりリポジトリ方針かユーザーが決める。
  xlsx / PDF 解析ツールの候補実測値と記録先は [`file-io.md`](file-io.md)「xlsx / PDF の解析ツール」

## 土台の有無を前提にしない（重要）

ライセンス拒否リスト・供給網ポリシー・バンドルサイズ上限・公開からの経過日数による採用遅延・依存レビューの自動化は、**持つリポジトリと持たないリポジトリがある**。決め打ちすると、持たないリポジトリでは工程が空回りする。

設定 `references.dependency_policy` は**三値**として読む（`none` と欠落を同一視しない）。三値それぞれの意味とスキルの挙動の正本は [`project-config.md`](project-config.md) の「依存導入の方針」——**ここへ転記しない**。

本ファイルが足すのは、**未確認（キーが無い）ときの確認手順**だけ。

- README / CONTRIBUTING / 基底ドキュメント（`AGENTS.md` / `CLAUDE.md` / `.github/copilot-instructions.md` 等）・CI 設定に方針が無いかを先に探す
- 見つからなければ**方針の要否そのものをユーザーに確認**し、確認結果を設定の `references.dependency_policy` へ記録する（方針ドキュメントのパス、または方針を持たないと確認したなら `none`）。
  記録するのは**確認したスキル**（`setup` を待たない）
- **スキル側の既定の拒否リスト・閾値・待機日数を持ち込まない**
- 方針が無いまま進める場合も、判断材料の確認と記録は省略しない（記録が残っていれば、後から方針ができたときに再判定できる）

## 記録（`.replace/dependencies.md`）

- 場所は対象プロジェクトの `.replace/dependencies.md`。他のテキスト成果物と同様に Git 管理する
- **無ければテンプレートから作成する**（本ファイルの導入前に `setup` を終えたプロジェクトには存在しないため、最初に追記するスキルが作る。`setup` の再実行を待たない）
- **追記は非破壊**: 既存の決定を書き換えない。差し替えたときは新しい決定を追記し、前の決定に差し替え理由を書く（同じ失敗の再発防止が読めるようにするため）
- 敵対的レビューでは、差分に新しい依存（`package.json` 等）が入っていたらこの記録の有無を見る（レビュー観点の正本は `parity-replace` の `references/adversarial-review.md`）
