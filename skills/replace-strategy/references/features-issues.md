# 機能インベントリと Issue 起票

`setup` モードのステップ 9（インベントリ作成）と `issues` モード（起票）の詳細。インベントリの正本は `.replace/features.md`（テンプレート: [`../assets/features-template.md`](../assets/features-template.md)）。

## 機能インベントリ（`.replace/features.md`）

現アプリを機能単位に分解し、次を記録する。

- **機能一覧**: 各機能が持つページ・API・テーブル・副作用出力（所有者として記録。対象／スコープ外の別も）
- **依存順**: 「依存の浅い順」とは具体的に、**横断 API の Issue を機能 Issue より先に**、という意味になる。ゴールデンデータセット Issue は 4 種の中では全 Issue の前提として先頭（ただし「その他の Issue」表の行が「ゴールデンデータセットより前」を明記していればその行が先）
- **横断 API**: API 単位で**利用側の機能一覧（fan-out）**を持ち、2 つ以上の機能から使われる API に「横断」の印を付け、**リソース単位でグルーピング**する。**参照テーブルも記録する**（下記「テーブルの記録先」）
- **バッチ**: バッチ・スケジュール実行の単位（画面を持たない）。入力・出力（DB 状態・生成ファイル）を記録する
- **slug**: 下記規則で採番し記録する
- **Issue 化の状態**: 起票済みの Issue 番号（`issues` モードが書き戻す）
- **その他の Issue**: 4 種のどれにも当てはまらない Issue（下記「その他 Issue」）。表を持つので、ヘッダに独自項目を足したり記録を諦めたりしない
- **ページ一覧**: ページ（パス）× **そのページに乗る機能 slug**。機能一覧の「ページ」列からの逆引きを表として持つ（下記「ページ一覧」）

### ページ一覧（機能をまたぐ在席の根拠）

**機能単位に分けて 1 機能ずつ green にしていく設計の裏返しとして、同じページに乗る別機能のセクションが丸ごと欠けていても、どのスイートも赤くならない**（移行済み機能のスイートは自分の担当範囲しか見ないため）。これを捕まえるにはページ単位の在席リストが要る。

- 1 ページに複数機能が乗る場合、**その全 slug を列挙する**（機能一覧の「ページ」列だけでは、あるページに何が乗るかを逆引きできない）
- `parity-suite` はこの表を根拠に、対象機能のスイートへ**同じページに乗る他機能の在席チェック**を置く（新側で未実装の機能はスキップ扱いにし、実装が済んだ時点で `parity-replace` がスキップを外す）
- `parity-suite` は同じ表から、別機能の未実装領域を `capture_conditions.cofeature_masks` の候補として記録する。`parity-diff` は同じ target の green 証跡と突き合わせ、未実装の間だけ現側・新側へ対称にマスクする
- 機能を追加・分割したらこの表も更新する（更新しないと在席チェックの対象から漏れる）

### 機能の分解基準

- **利用者目的（誰が何を達成するか）・データ境界（所有するテーブル群）・依存関係・副作用の所有者**で分解する。画面内の表示セクション（一覧・追加フォーム・絞り込み・完了済み等）単位で分けない。
  表示セクションで割ると、目的もデータ境界も依存関係も共通の要素まで別 Issue に分かれ、実装と検証の単位が不必要に細かくなる
- **複数ページを持つ機能は 1 行・1 Issue にまとめる**（例: 注文一覧＋注文詳細 → `order` の 1 行）。ページ単位の作業分割は Issue 内のフェーズで行う（後述の「機能 Issue」）。
  大規模アプリでもページ数に比例して Issue を増やさない
- **単一機能からしか利用されない API は横断 API にせず、その機能の「新規実装 API」へ含める**。横断 API 表に載せるのは、2 つ以上の機能が利用するリソースだけ

### テーブルの記録先

**インベントリに現れるテーブルの記録先は 3 つの表しかない**——機能一覧の「テーブル」列、横断 API の「参照テーブル」列、バッチの「参照テーブル」列。
下流の `golden-dataset` は対象テーブルをこの 3 列から引く（正本は `golden-dataset` スキルの「起点は DDL と機能インベントリ」）。**どの列にも書かれていないテーブルは、ゴールデンデータセットの対象から落ちる。**

- **横断 API からしか参照されないテーブルは、横断 API 表の「参照テーブル」列だけが置き場所**。機能一覧の「テーブル」列は機能が所有するテーブルなので、そこには現れない
- 横断 API の参照テーブルが落ちると、その API が返す値をゴールデンデータで制御できず、**fan-out 先の全機能**（マスタ表示・プルダウン・遷移先解決など）が現新比較の対象外になる。
  fan-out が広いほど被害が大きいので、横断 API 行を書いたら参照テーブルを空欄のまま残さない
- **参照テーブルが本当に無い横断 API は空欄にせず `-` と書く**。空欄は下流で「記録漏れの疑い」として扱われ確認待ちになるため、「まだ調べていない（空欄）」と「調べた結果テーブルを読まない（`-`）」を書き分ける
- **既存の `.replace/features.md` に「参照テーブル」列が無い**（この列を持たない版のテンプレートで作られた）場合は、非破壊更新で**列を追加して埋める**。列が無いことを理由に記録を諦めない（下記「features.md の更新は非破壊」は削除を禁じるもので、列の追加は妨げない）
- 同じテーブルが機能一覧と横断 API の両方に現れてよい（所有者は機能側、参照は横断 API 側）。**重複を嫌って片方から消さない**

### slug の採番（成果物パスの識別子）

- 各機能・各横断 API リソース・各バッチに、**ASCII の kebab-case（`[a-z0-9-]`）で一意な `slug`** を付ける
- 日本語の機能名は転写せず、作業内容を表す短い英語に要約する（例: 注文一覧＋注文詳細 → `order`）
- 下流スキルの成果物パス `.replace/parity/<slug>/` はこの slug を使う。**下流スキルは slug を自分で作らず、features.md から引く**（別々に採番すると成果物が合流しない）
- 一意性はインベントリ全体（機能・横断 API リソース・バッチ・その他 Issue の間）で保つ
- **その他 Issue の slug は `.replace/parity/<slug>/` を持たず、下流スキル（`golden-dataset` / `parity-suite` / `parity-replace` / `parity-diff`）の対象にならない。**
  下流スキルが features.md から引くのは機能・横断 API リソース・バッチの slug だけで、その他 Issue の slug を対象に指定されたら「下流の対象外」として停止する（名前空間は共有するが対象範囲は共有しない）

### 横断 API のグルーピング

- **リソース単位で Issue にまとめる**: 同じリソースを扱う横断 API は 1 つの Issue にする（例: ユーザー一覧取得とユーザー詳細取得は「ユーザー」の Issue）。**全横断 API を 1 Issue にまとめない。API ごとに 1 Issue も作らない。粒度の基準はリソース**
- 横断 API はバックエンドのみで、パリティスイートの作り方も画面駆動ではなく API の record/replay になり、機能 Issue とワークフローが異なる（`parity-suite` / `parity-replace` の API モード）

## Issue の種類（5 つ）

| 種類 | 単位 | 記録先（`.replace/features.md`） | 依存順 |
|---|---|---|---|
| ゴールデンデータセット Issue（`golden-dataset`） | 全機能横断で 1 本（規模が大きければリソースドメインで分割） | ヘッダの「ゴールデンデータセット Issue」 | **4 種の先頭**（他の 3 種すべての前提。その他 Issue の行が「ゴールデンデータセットより前」を明記していればその行が先） |
| 横断 API Issue | リソース単位 | 「横断 API」表 | 機能 Issue より先 |
| 機能 Issue | 機能単位。バックエンドとフロントエンドの両方を含む | 「機能一覧」表 | 横断 API の後、依存の浅い順 |
| バッチ Issue | バッチ・スケジュール実行の単位 | 「バッチ」表 | 入力データと参照テーブルが揃った後 |
| その他 Issue | 上の 4 種に還元できない作業の単位 | 「その他の Issue（4 種以外）」表 | 行の「依存順」列に記す（先頭〜任意の位置） |

### 本文に含める内容（共通）

- 対象の slug と `.replace/features.md` への参照（正本はインベントリ。本文へ全転記しない）
- 使用する姉妹スキルと順序
- 受け入れ条件（スイート green・強度記録・gaps 記録など、種類に応じて）

### 機能 Issue

- ページ・API・テーブル・副作用出力の一覧
- **「この機能が新規に実装する API」と「依存する横断 API（どの Issue で実装されるか）」を分けて書き**、再実装しない
- Issue 内は**ページ単位でフェーズを分ける**（1 ページを作り切って比較してから次へ）
- ワークフロー: `parity-suite` → `parity-replace` → `golden-dataset`（フェーズ B）→ `parity-diff`（`parity-replace` と往復）

### 横断 API Issue

- 対象リソースと API 一覧、利用側の機能（fan-out）、**参照テーブル**
- 画面が無くても旧 API の実応答が正解になるため、消費側の機能を待たずに仕様は確定する。**パリティスイートは一度だけ書いて共有する**（機能ごとに重複して書かない）
- 新側の検証（`parity-replace` の green 化・`parity-diff`）の前に、対象リソースのテーブルへ `golden-dataset`（フェーズ B）で投入されていること（新側 DB が未シードのままでは値の比較が成立しない）

### バッチ Issue

- 対象バッチ、入力（ゴールデンデータセット＋入力ファイル）、比較する出力（DB 状態・生成ファイル）
- ワークフロー: 姉妹スキルのバッチモード（`parity-suite` が現行出力をベースライン捕捉 → `parity-replace` が新側実装 → `golden-dataset`（フェーズ B）で新側へ投入 → `parity-diff` が決定論的比較）

### その他 Issue

4 種は「機能・リソース・バッチ・データセット」という**成果物の所有者**で切られている。所有者を 1 つに定められない作業——複数機能のテーブルにまたがる設計や、
どの機能にも帰属しない前提整備——は 4 種のどれにも入らない。**これを記録する場所が無いと、ヘッダへの独自追記か Issue 本文だけの記録になり、次の書き直しで落ちる。**
そのための枠が `.replace/features.md` の「その他の Issue（4 種以外）」表であり、**4 種と同じく `issues` モードの起票候補・書き戻し先・`status` モードの報告対象**になる。

- **4 種に還元できるものはここに置かない。** 機能・リソース・バッチに帰属する作業は必ずその表に置く（この表を受け皿にして分解を省くと、依存順も fan-out も成果物パスも失われる）
- 各行に **`4 種に当てはまらない理由`** と **`影響範囲`**（波及するテーブル・機能 slug 等）を書く。理由を書けないなら 4 種のどれかに当てはまる
- **依存順は行に明記する**（`先頭` / `ゴールデンデータセットより前` / 数値）。4 種の依存順は種類で決まるが、その他 Issue は行ごとに違う
- **slug を採る**（インベントリ全体で一意）。ただし `.replace/parity/<slug>/` の成果物は持たず、下流スキルの対象にもならない（上記「slug の採番」。`status` モードでの扱いは [`status.md`](status.md) の「その他の Issue（4 種以外）の状態」）
- 本文には共通項目（対象・受け入れ条件）に加え、**この Issue が前提になる下流の Issue（または「下流なし」）**を書く
- 例: **新側スキーマを先に作る Issue**。既定では新側スキーマは `parity-replace` が機能ごとに作るが、外部キー・一意キーの設計はテーブルをまたぐため、
  機能ごとに小分けにすると両端が揃うまで FK を張れず、型の写し方の判断も Issue ごとに散る。1 本へ前倒しするかは**利用側の判断**であり、スキルは既定を変えない（前倒しした場合の置き場所がこの表）

## features.md の更新は非破壊

**`.replace/features.md` の書き直しで、既にある記述を落とさない。** テンプレート（[`../assets/features-template.md`](../assets/features-template.md)）は
**初期生成の雛形であって、更新時に許される項目の上限ではない**。

- `issues` / `setup` の更新は、**変える行・列だけを書き換える**。全文を再生成してテンプレートに揃え直さない
- **テンプレートに無いヘッダ項目・節・列・行を見つけても削除しない。** 意味が判断できないものはそのまま残す（利用者が意図して足した記録である可能性のほうが高い）
- テンプレートに無い項目が**「その他の Issue（4 種以外）」表で表現できる**なら、削除ではなく**その表への移動を提案し、承認を得てから移す**（黙って移さない・黙って消さない）
- 更新のたびにヘッダの `最終更新` を更新する

## issues モードのフロー

1. `.replace/features.md` を読み、**未起票**（Issue 番号が空）の機能・横断 API リソース・バッチ・その他 Issue を列挙する。`--feature <slug>...` があればそれで絞り、無ければ対話選択させる。
   **未起票候補の全選択を既定にしない**（黙って全件を起票対象にしない）。
   features.md が無い場合は `setup` 未完了として起票せず停止し、`setup` の実行を促す
2. ゴールデンデータセット Issue が未起票なら、選択に関わらず**最初の起票対象として提案する**（すべての前提のため）。
   ただし「その他の Issue」表に**依存順が「ゴールデンデータセットより前」の未起票行**があれば、その行を先に提案する（後続の本文から先行 Issue 番号を参照できなくなるため）
3. 起票対象の一覧（種類・slug・タイトル案・依存関係）と**各 Issue の本文ドラフト**を提示する。
   機能 Issue はページ一覧で共同居住関係を連結成分にまとめ、同じページ束の機能を連続する順序で提案する（横断 API 等の実依存は優先し、束のために逆転させない）。
   提案順を左から実装すると仮定し、後続 slug が green になるたび、その slug とページを共有する着手済み slug の `parity-diff` が 1 回必要として数える（同じ 2 slug が複数ページを共有しても 1 回）。
   各 slug の再実行回数と束の合計を示し、各 slug について最後の共同居住マスクが外れる再実行を「全面比較」と明記する。ページ一覧が未導出・不整合なら回数を捏造せず「算出不能」として setup へ戻す。そのうえで対象選択と**明示承認**を得る
4. **明示承認が得られない場合——利用者が不在（非対話実行）・無応答・応答が承認以外——は起票せず停止する。** `gh issue create` を実行せず、`issue-create` への委譲も行わない。
   起票は外部への副作用であり、承認なしに実行しない。非対話実行では候補・依存関係・本文ドラフトの提示（または保存）までで止め、承認待ちであることを明示する
5. 承認後、**1 件ずつ `issue-create` スキルへ委譲する**（本文ドラフトは上記構成で本スキルが用意する）。依存順に起票し、後続の本文から先行 Issue 番号を参照できるようにする
6. 起票された Issue 番号を `.replace/features.md` の**該当する表・ヘッダ項目**（機能一覧／横断 API／バッチ／その他の Issue／ヘッダのゴールデンデータセット Issue）へ書き戻す。
   起票していない行の Issue 列は「未起票」のまま変えない。書き戻しは上記「features.md の更新は非破壊」に従う（他の記述を巻き込んで再生成しない）
7. 重複チェック（既存 Issue の確認）は**ページネーションに留意する**。issue-create 側の重複チェックが既定件数で打ち切る場合に備え、本モードでも起票前に全件を確認する:

   ```bash
   gh api "repos/$OWNER/$REPO/issues?state=all&per_page=100" --paginate \
     --jq '.[] | select(.pull_request | not) | [.number, .title] | @tsv'
   ```

8. 完了時、起票した Issue の実施に必要な姉妹スキル（`golden-dataset` / `parity-suite` / `parity-replace` / `parity-diff`）が未インストールなら `gh skill install` の手順を案内する
