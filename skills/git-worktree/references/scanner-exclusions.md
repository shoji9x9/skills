# 検査ツールからの除外

worktree をリポジトリの中に置くと、その中身が共有ツリー側のチェックの対象になる。
中身は別の branch の作業中の状態で、[運んだ `.env`](carry-in.md) があれば本物の資格情報が入っている。
除外が無いと、自分の変更と関係の無い理由で、共有ツリー側のチェックが失敗する。

## 1 か所では足りない

`.gitignore` に足せば済むとは限らない。**`.gitignore` を読まないチェックがある。**
除外を入れる先は、「`.gitignore` に書いたか」ではなく、「どのチェックがそのディレクトリを読むか」で挙げる。

除外が要るチェックの例を次に挙げる。

| 検査 | 除外の書き方の例 | `.gitignore` を読むか |
| --- | --- | --- |
| `.gitignore` 本体 | `.claude/worktrees/` | — |
| Markdown linter（独自 glob） | `globs:` に `"!.claude/worktrees/**"` | 読まない |
| シークレットのスキャン | 設定ファイルの `[allowlist] paths` など | 読まない |
| 脆弱性スキャナ | スキャナ側の ignore 設定 | 読まない |

**必ず自分のリポジトリで挙げ直す。** 上の表は例で、すべてではない。

### 列挙のしかた

pre-commit の hook（lefthook など）と CI のワークフローの設定を開き、
リポジトリ全体を読むジョブ（対象のファイルを引数で受け取らないもの）をすべて挙げる。
それらが除外を入れる先の候補になる。ファイルを引数で受け取るジョブは staged の差分しか見ない。
worktree の中のファイルはもともと staged にならないので、問題にならない。

## 検出されることを先に確かめる

除外が機能したことは、「何も出なくなった」ことでは確かめられない。
本当に無い場合と、チェックが動いていない場合は、同じ出力になる。

**検出されるはずの文字列を除外の対象の外に置いて、検出できることを確かめる。**
除外の対象の中に置いた確認では、何も確かめられない。

```bash
# 1. 検出されることの確認: 除外されない場所へ検出させたいパターンを置き、チェックが検出することを確かめる
# 2. 除外されることの確認: 同じパターンを worktree のディレクトリへ置き、検出されないことを確かめる
# 1 で検出できなければ、2 の結果には意味が無い
```

打ち切り（`timeout`）と 0 以外の終了は、合格として扱わず FAIL にする。

## 除外パターンはルート起点

除外のパターンは、リポジトリのルートを起点に固定され、入れ子の中には届かないことが多い。

この点は、置き場所の判断に直接かかわる。
worktree の中にさらに設定ファイルがある構造では、外側の除外が内側のチェックに反映されないことがある。
除外の手間と見逃しを避けたいなら、worktree をリポジトリの外に置く。
ただし、代償が 2 つある。[ファイルが自動で運ばれなくなる](carry-in.md)ことと、
`.claude/worktrees/` の外のパスへセッションを移すたびに、利用者の承認が要ることである
（[isolation.md](isolation.md)。無人の実行ではここで止まる）。

| 判断材料 | リポジトリ内（`.claude/worktrees/`） | リポジトリ外 |
| --- | --- | --- |
| チェックからの除外 | リポジトリ全体を読むすべてのジョブに要る | 要らない |
| ファイルの自動の運搬 | 行われる（新しく作るとき） | 行われない |
| セッションを移すときの承認 | 要らない | 毎回要る |
| worktree の間の移動（複数の worktree を行き来する） | できる | できない（起動したディレクトリからの 1 回だけ。[isolation.md](isolation.md)「入れ子と再入場」） |
