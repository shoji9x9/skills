# 受け入れ条件の突き合わせ

Issue の受け入れ条件を 1 項目ずつ根拠と突き合わせた表（突き合わせ表）を作り、同梱の検査で確かめてから、完了にしたり push したりする。その手順をこのファイルで定義する。
使うのは、`--acceptance` モード、`--pr` の push の前（基本フローの step 10）、実装を自分で持つスキル（`parity-replace` など）の完了の判定である。

テスト・リント・スイートが通ることは、成果物の形を確かめたにすぎない。
Issue にだけ書かれた条件（「状態を URL で持つ」「失敗したときにログを書く」など）は、どの工程も確かめない。
長い作業では途中で文脈が要約されるので、着手したときに読んだ受け入れ条件を、完了の前に読み直すきっかけも無い。
**完了の前に Issue を読み直して表にする**のが、この手順の役割である。

## 前提

- Node.js（同梱の `scripts/acceptance-check.mjs` を実行する）。無ければ、突き合わせを合格として扱わず、その旨を報告して止まる
- 表の様式は [`../assets/acceptance-template.json`](../assets/acceptance-template.json)、検査は [`../scripts/acceptance-check.mjs`](../scripts/acceptance-check.mjs) で定義する。どちらもコピーせず、スキルの中のものを使う

## 手順

1. **Issue を取得し直す**（着手したときの記憶で書かない）。本文とコメントに加えて、GitHub が本文を描画した HTML（`bodyHTML`）を取得する。
   検査は、チェックリストの項目をこの HTML のチェックボックスから数える。画面にチェックボックスとして表示されたものだけが項目になり、
   コードフェンスや HTML コメントの中の `- [ ]` は数えない。`gh issue view --json` は `bodyHTML` を返さないので、GraphQL で取得する

   ```bash
   gh issue view <番号> --repo <owner>/<repo> --json number,url,title,body,comments > <作業ディレクトリ>/issue.json
   gh api graphql -f owner=<owner> -f name=<repo> -F number=<番号> \
     -f query='query($owner: String!, $name: String!, $number: Int!) { repository(owner: $owner, name: $name) { issue(number: $number) { body bodyHTML } } }' \
     --jq '.data.repository.issue' > <作業ディレクトリ>/issue-html.json
   ```

   2 つの取得の間に本文が編集されると、検査は本文が一致しないとして exit 2 で失敗する（両方を取得し直す）。
   `issue.json`・`issue-html.json` と、置き場所（`--out`）が指定されていないときの表は、作業ツリーの外の一時ディレクトリに置く（リポジトリに commit しない）。
2. 条件を挙げる
   - 本文のチェックリストの項目は、すべて `source: checklist` の行にする。`criterion` には、検査の出力の `checklist_items` の文言をそのまま転記する。
     描画した後の文言なので、Markdown の記号・リンクの URL・タグは除かれている。本文の Markdown から転記したり言い換えたりすると、検査が別の項目として数える。
     最初は行の無い表で検査を 1 回通し、`checklist_items` と `expected_fingerprint` を得てから書く
   - チェックリストに無い条件（文章で書かれた要件、コメントでの追記や改訂）は、`source: body` か `comment` の行にし、`quote` に原文を一字一句転記する。
     要約すると、検査が引用を見つけられない。
     本文が空で、タイトルだけが条件を述べる Issue は、`source: title` の行にする
   - コメントが条件を改訂したり撤回したりしていれば、最新の決定に従う。撤回されたチェックリストの項目も行は残し、`waived` にして、`approval.ref` に撤回したコメントを書く
   - **検査が保証するのは、「チェックリストの項目と行が 1 対 1 で対応する」ことと、「文章の行の引用が Issue に在る」ことまでである。**
     文章で書かれた条件をすべて拾ったかは保証しない。本文とコメントを最後まで読んで拾う
3. 1 行ずつ根拠を付ける。`status` は次のどれかにする

   | `status` | 意味 | 要るもの |
   |---|---|---|
   | `met` | 満たした | `evidence`（`command` なら `command` と `result`、`file` なら `ref` に `パス:行` か `パス:開始-終了`）と `strength`（`measured` は結果を記録したコマンドを 1 件以上持つ、`read` は読んだだけ） |
   | `unmet` | 満たしていない | —（完了にしない） |
   | `pending-decision` | 利用者の判断待ち | `decision_ref`（判断待ちの記録の id）。完了にしない |
   | `waived` | 利用者が外すと決めた | `approval`（`by`・`at`・`ref`。`ref` は決定の記録） |
   | `deferred` | 利用者が別の作業に回すと決めた | `approval` と `tracked_in`（残りの作業の置き場所）。Issue は閉じない |
   | `later` | 同じ流れの後の工程が満たす（呼び出し元のスキルが使ってよいと決めた条件だけ。例: `parity-replace` の完了の時点での `parity-diff` の収束） | `owner`（満たす後の工程。呼び出し元が `--allow-later` で許した名前と完全一致する。許されていない実行では使えない）。Issue は閉じない。後の工程が済んだら、表を作り直して `met` にする |

   - **満たせない条件を、自分で外したり飛ばしたりしない。** `waived` と `deferred` は、利用者が決めたときだけ書く（承認の無い行は、検査が失敗にする）。
     決まるまでは利用者に確認する。呼び出し元が判断待ちの記録を持つなら、`pending-decision` にして記録に積む
   - `file` の根拠は `--root`（デフォルトは作業ディレクトリ）を起点に解決し、ファイルが在ることと行の範囲を検査が確かめる
4. 根拠を取った版を固定する。commit していない変更が残っていると、HEAD が根拠の版を表さない。そのため、`git status --porcelain` が空のときだけ、`commit` に HEAD の完全な SHA を書く。
   判定はリポジトリ全体に対して行う。サブディレクトリから `.` で絞ると、その外の commit していない変更が見えない。
   表をリポジトリの中（`--out`）に置く場合は、表自身のパスを除いて判定する
   （`git -C "$(git rev-parse --show-toplevel)" status --porcelain -- . ':(exclude)<リポジトリのルートからの表のパス>'`）。
   表は書いた時点で commit していない変更になる。表を commit すると HEAD が進んで `stale-commit` になるので、除かないと突き合わせがいつまでも通らない。
   表を commit した後で検査をやり直すときは、表を書き直して、`commit` をその時点の HEAD にする。
   空でなければ、`--pr` では規約どおり commit してから取る。`--acceptance` は commit しないので、commit していない変更があることを報告して、呼び出し元に返す
5. 検査を通す

   ```bash
   node <issue-start>/scripts/acceptance-check.mjs --issue <issue.json> --issue-html <issue-html.json> --table <acceptance.json> \
     --head "$(git rev-parse HEAD)" [--root <ファイル:行 の起点>] [--decisions <pending_decisions を持つ JSON>] \
     [--allow-later <後工程名,...>]
   ```

   - `source_fingerprint` は手で書かず、最初の出力の `expected_fingerprint` を転記する。
     **表を書いた後に Issue の本文かコメントが変わると、`stale-issue` で失敗する。** 条件を読み直して、表を直す。
     チェックを付けただけのときや、下の結果のコメントを投稿しただけのときは、変わらない
   - 終了コードは次のとおりである。1 と 2 は完了にしない
     - 0: すべての行が `met`・`waived`・`deferred`・`later` のどれかで、Issue と対応している
     - 1: 満たしていない条件や、食い違いが残る（`findings` を直す）
     - 2: 入力の誤り（別の Issue の表、短縮した SHA、JSON でない、`issue.json` と `issue-html.json` の本文が違う）
   - `checklist-item-empty` は、文言の無いチェックボックス（画像も代替のテキストも無いものなど）で、行と対応づけられない。Issue の本文に文言を足すか、利用者に確かめる
   - 出力の `closable` が `false`（`deferred` か `later` がある）なら、PR で Issue を閉じない（`Closes #<番号>` ではなく `Refs #<番号>` と書く）
6. **受け入れ条件を変えたなら、似た Issue を見直すかを利用者に確かめる**（下の「受け入れ条件を変えたとき」）。
   次のどれかに当たれば行う。
   - 表に `waived` か `deferred` の行がある
   - コメントが条件を改訂したり撤回したりした（`source: comment` の行のうち、条件を足しただけでなく、既存の条件を変えたもの）
   - 本文の条件が、着手したときから書き換わった。着手したときに読んだ本文と、手順 1 で取得し直した本文とで、チェックリストや条件の文言が違う。
     着手したときの本文は、`gh issue view --json body` の結果を残しておくか、編集の履歴（`userContentEdits`）で確かめる

   自律実行の呼び出し元では確かめられないので、候補の一覧を添えて、呼び出し元の保留に積む。
   保留の置き場所を持たない呼び出し元は、検査が exit 0 でも push せずに止まる。
   この手順は、結果の投稿（手順 7）より前に行う（結果のコメントに判断を載せるため）
7. **結果を Issue に残す**（外向きの操作）
   - 表を Markdown にしたコメントを投稿する。**本文の先頭に目印 `<!-- issue-start:acceptance -->` を入れる**（検査は、このコメントを fingerprint の計算から外す）
   - 本文のチェックリストのうち、`met` と `waived` の項目にチェックを付ける。
     本文を取得し直し、該当する行の `[ ]` だけを `[x]` にしたファイルを差分で確かめてから、`gh issue edit <番号> --body-file <path>` で書く
   - `--pr` の実行では、任された範囲の中として行う。`--acceptance` だけの実行では、投稿の前に利用者に確認する。
     自律実行の呼び出し元（`parity-replace --autonomous` など）では、越えてはいけない線に当たるので行わず、呼び出し元の保留に積む

## 受け入れ条件を変えたとき（類似 Issue の見直し）

条件の変更（「移行元に合わせず URL で状態を持つ」と決めた、条件を撤回した、`waived` や `deferred` にした）は、着手中の Issue にしか書かれない。
同じ前提を持つ別の Issue（同じ種類の画面や、同じ部品を使う機能）の条件は古いまま残る。
その結果、後から着手する Issue で同じ判断をやり直すか、食い違った実装になる。
**変えた条件ごとに似た Issue の候補を挙げ、見直すかを利用者に確かめる。**

1. 候補を探す。似ているかの基準は次の 3 つで、どれか 1 つに当たれば候補にする（当たった基準を候補ごとに残す）
   - 同じラベルを持つ open な Issue。`bug` や `enhancement` のように、すべての Issue に付く種類のラベルは基準にしない。
     当てるとすべての Issue が候補になり、見直しが形だけになる
   - 変えた条件に現れる識別子（バッククォートで囲まれた語・slug・パス・画面や部品の名前）を、本文かコメントに含む open な Issue
   - 変えた条件と同じ文言の条件（空白をまとめて比べる）を持つ open な Issue

   ```bash
   # 検索 API はデフォルトで 30 件で切るので --paginate で全ページをたどる。基準ごとに別の検索を実行する
   # 同じラベル: 変えた Issue のラベルごとに 1 回（種類のラベルは除く）
   gh api -X GET search/issues --paginate \
     -f q='repo:<owner>/<repo> is:issue is:open label:"<ラベル名>"' \
     --jq '.items[] | [.number, .title] | @tsv'
   # 識別子・同じ文言の条件: 語ごとに 1 回（<語> は識別子か、条件の文言）。範囲はコメントまで含める
   gh api -X GET search/issues --paginate \
     -f q='repo:<owner>/<repo> is:issue is:open in:body,comments "<語>"' \
     --jq '.items[] | [.number, .title] | @tsv'
   ```

   本文の語の検索だけで済ませない。条件の語を本文に含まない、同じラベルの Issue が候補から外れる。
   語の検索の範囲をコメントまで広げるのは、コメントで改訂した条件の語が、変えた Issue 自身の本文には無いからである。
   本文だけを検索すると、下の「自身が出ることの確認」で自身が出ない。
   コメントで語に触れただけの Issue も候補に入るが、候補は利用者に示して判断してもらうので、除かない。

   - **候補が 0 件のことを「似た Issue は無い」の根拠にしてよいのは、その検索で自身が出ることを確かめたときだけである。**
     同じ検索を `is:open` を外して実行し、変えた Issue 自身が結果に出ることを、検索ごとに確かめる（条件を本文から消した後の代わりの方法は次の項）。
     出なければ、その検索は機能していない（語の引用の誤りや、索引の遅れ）。判定できないものとして利用者に伝え、「似た Issue は無い」と書かない
   - **自身が出ることの確認は、候補を探したのと同じ検索（同じ語・同じラベル）で行う。** 別の語で自身が出ても、その語の検索が機能している証拠にはならない。
     コメントで条件を改訂したときは、改訂のコメントを投稿した後に同じ検索で、自身が出ることを確かめる。
     新しく使い始めた語も、そのコメントで自身に当たる。
     条件を撤回したり削除したりするときは、本文から消す前に、その条件の語で検索して自身が出ることを確かめてから消す。
     消した後は、語が自身のコメントに残っていなければ、自身が出ないのが正しい。そのため、検索が機能しているかを区別できない。
     消した後で気付いた場合は、同じ語を本文かコメントに今も含むことを取得して確かめた Issue（自身でもよく、閉じていてもよい）が、同じ検索に出ることで代える。
     **どれもできなければ、その検索の 0 件を「似た Issue は無い」とせず、判定できないものとして利用者に伝える。**
     その検索で当たった候補は、候補として示してよい。
     本文を編集したりコメントを投稿したりした直後は、索引が追いつかず、今ある語でも自身が出ないことがある。時間を置いて検索し直す。
     コメントは数十分以上出ないことがある（実測で 40 分以上）。改訂のコメントは条件を決めた時点で投稿し、
     出るまでは「似た Issue は無い」と書かない
   - 候補から、変えた Issue 自身を除く。閉じた Issue は候補にしない（条件を書き換えても、実装は変わらない）。
     閉じた Issue の実装に当て直すかは、プロジェクトにその工程があれば、そちらで扱う（例: `replace-strategy` の `.replace/procedure-changes.md`）
2. 利用者に示す。候補ごとに、番号・タイトル・当たった基準・その Issue の該当する条件の原文・変えた条件（変更の前と後）を並べ、
   見直しが要るかを 1 件ずつ確かめる。確認の UI に判断の材料を含める（直前のテキストが見えている前提を置かない）
3. **他の Issue を変えるのは、承認を得た後だけである**（外向きの操作）。本文を書き換えるか、コメントで追記するかも、利用者が決める。
   本文を書き換えるなら、取得し直した本文を差分で確かめてから、`gh issue edit <番号> --body-file <path>` で書く。自動では書き換えない
4. 結果を、着手中の Issue の突き合わせのコメント（手順 7）に書く。書くのは、候補の一覧・当たった基準・利用者の判断（見直す、見直さない）である。
   候補が 0 件なら、自身が出ることを確かめたことも書く

## 呼び出し元が表の置き場を持つ場合

実装を自分で持つスキルは、`issue-start <番号> --acceptance --out <path>` で任せ、表を自分のスキルの成果物の場所に置く。
例えば、`parity-replace` は `.replace/parity/<slug>/new/<target>/acceptance.json` に置く。
判断待ちの記録を持つなら `--decisions <path>` を渡し、`pending-decision` の行がその記録を指していることまで検査させる。
`later` を使わせる呼び出し元は、`--allow-later <後工程名>` を渡す。`--pr` と、`--acceptance` だけの実行では渡さないので、`later` は失敗になる。
