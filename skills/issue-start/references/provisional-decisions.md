# 実装の途中で仮に決めたことの記録

実装の途中で、Issue に書かれていないことを仮に決めて進めることがある（あいまいな条件の解釈・デフォルトの値・対象から外した形・選んだ設計の案など）。
これを記録しないと、PR をレビューする人は、エージェントが決めたことと、Issue や人が決めたことを区別できない。そのため、差分の全体を同じ注意で読むことになる。
そこで、仮に決めたことを PR の本文の「仮に決めたこと」の節に置き、レビューする人が確かめる箇所をそこから選べるようにする。

## 記録するもの

Issue の本文・コメント・リポジトリの文書から導けず、自分で選んで進めたことを記録する。
受け入れ条件の突き合わせの表に `met` と書いた行でも、その途中で解釈を選んだなら記録する。
次のものは記録しない。Issue やコメントに書かれた決定・リポジトリの規約がそのまま決めていること・別の案が無いこと（打ち間違いの修正など）である。
作業の範囲が変わるほどあいまいな要件は、仮に決めて進めない。`SKILL.md` の「追加確認が必要な条件」のとおり、実装に進む前に確認する。ここで記録するのは、範囲を変えない解釈や値の選択である。

1 件ごとに、次の 5 つを書く。

| 項目 | 書くこと |
| --- | --- |
| 識別子 | PR の中で一意な短い名前（`P1`・`P2` など）。レビューの返信で指すのに使う |
| 出どころ | どの条件・本文の箇所・指摘から生じたか（受け入れ条件の文・ファイルと行など） |
| 決めた内容と理由 | 選んだもの、ほかに考えた案、選んだ理由 |
| 人への問い | レビューする人に確かめてほしいこと（「この解釈でよいか」など）。確かめることが無ければ「無し」 |
| 覆すときに戻る工程 | 決定を変えるときにやり直すこと（直すファイル・やり直す検査）と、手戻りの大きさ（大・中・小） |

## 置き場所

PR の本文に `## 仮に決めたこと` の節を置き、表か箇条書きで 1 件ずつ並べる。0 件でも節を置き、「無い」と書く。
節が無いと、記録が無いのか、記録し忘れたのかをレビューする人が区別できないからである。
この節が扱うのは、PR を作るまでに決めたことである。PR を作った後のレビューへの対応で解釈を選んだときは、その指摘への返信に、選んだ案と根拠を書く。

## 人に回すかの判断

仮に決めたことのうち、merge する前に人の答えを求めるかは、PR のレビューの指摘を人に回すかと同じ基準で決める。
基準の原本は、`pr-finalize-loop` と `pr-review-handle` が同じ内容で持つ `references/review-response.md` の、人に回すかの基準の節である。ここへ転記しない。
インストール先のスキルのディレクトリ（`issue-start` と同じ置き場所）に、どちらかのスキルがあれば、その節を読んで決める。
その節のうちプロジェクトの基準は、同じ節にある、PR がまだ無いときの手順で当てる。ベースブランチには、`SKILL.md` の「ブランチ運用・commit 規約の参照」で決めたものを使う。
次の 3 つの場合は、人に回すかを自分で決めず、仮の決定をすべて利用者に確認する（呼び出し元が判断待ちの記録を持つなら、そこに積む）。確認の答えが出るまで、その決定に沿った実装・push・PR の作成に進まない。

- プロジェクトの基準の手順が止まった（ベースブランチを決められない・取得できない、作業ツリーの設定か基準の文書がベースブランチの先端と違う、設定の誤り、基準の文書を読めない、など）
- どちらかのスキルがあるのに、その節を読めない。または、その節に PR がまだ無いときの手順が無い（古いバージョンのスキル）
- どちらのスキルも無い
人に回すかは、決めた時点で判断する。人に回すものは、その決定に沿って実装する前に確認する。元に戻す手段が無い影響を伴う決定を、実装して push した後で確認しても遅いからである。
人に回して答えを得た決定も、節に載せる（人への問いには、得た答えを書く）。
