# スキルセットアップガイド

スキルの書き方と設計の方針は、`skill-creator` スキルにある。

## ディレクトリ構造

```text
.agents/skills/<name>/SKILL.md   実体（Codex が直接参照）
.claude/skills/<name>            Claude Code 用シンボリックリンク（ディレクトリへのリンク）
```

Copilot は `.agents/skills/` と `.claude/skills/` の両方を参照するので、追加の対応は要らない。

## 初期セットアップ

プロジェクトにマルチエージェントに対応した基本の構成を入れるときは、`references/docs.md` を使って次を作成・更新する。

- `AGENTS.md`
- `CLAUDE.md`
- `.github/copilot-instructions.md`
- `README.md`

ファイルがすでにあれば上書きせず、更新するかをユーザーに確かめる。
共通の内容は `AGENTS.md` にまとめ、`CLAUDE.md` と `.github/copilot-instructions.md` には、各エージェントに固有の差分だけを書く。

## SKILL.md frontmatter

```yaml
---
name: <skill-name>          # 必須: 小文字英数字とハイフンのみ、最大64文字
description: <description>  # 必須: スキルの説明とトリガー条件、最大 1024 バイト（UTF-8。日本語はおよそ 340 文字）
argument-hint: "<hint>"     # 任意: スラッシュコマンド実行時に表示する引数ヒント、引用符で囲む
---
```

`argument-hint` は、Agent Skills の標準仕様（agentskills.io）の外にある拡張のフィールドである。
Claude Code と VS Code（Copilot の Agent Skills）は、補完のときのヒントの表示に使う。Codex CLI と Copilot CLI は知らないフィールドとして無視する（エラーにはならない）。
値が `[` で始まると、YAML の flow sequence と誤って解釈されるので、引用符で囲む（シングルとダブルのどちらでもよい）。

## スキル作成手順

スキルを書く前と書いた後に、同じ依頼をエージェントにさせて、振る舞いを比べる。
書く前の確認で、スキルが要るか（スキルが無いと期待する振る舞いが起きないか）を決める。書いた後の確認で、書いた指示が振る舞いを変えたかを確かめる。
書いた後に確かめるだけでは、スキルが無くても同じ振る舞いになる場合（スキルが要らない場合）に気づけない。

1. 依頼と、期待する振る舞いを決める。
   スキルを使う場面の依頼文を 1 つ書き、期待する振る舞いを 1〜3 項目で書く。
   利用者の依頼に期待する振る舞いが書かれていなければ、自分で決めずに利用者に確かめる。
   自分で決めると、モデルがスキル無しでも取る振る舞いを選びやすく、2 で「スキルは要らない」と誤って判断する。
   利用者に確かめられない実行（非対話の実行など）では、項目の候補を示して止まり、2 以降に進まない。
   項目は、応答やファイルを見て、起きたか起きなかったかを判定できる形にする（「`gh issue create` の前に下書きの全文を見せる」など）。
   依頼が外向きの操作（Issue や PR の作成、push、外部 API への書き込みなど）を含むなら、その操作の直前で止めて、実行せずに報告するよう求める文を依頼文の末尾に入れる。
   2 と 4 では、この文を含めた依頼文をそのまま使う。
2. スキルが無い状態で依頼させ、結果を記録する。
   実行させる場所は、作業ツリーとは別のコピーにする。
   コピーは、実行のたびに同じ初期状態から始まるようにする。前の実行が作ったファイルが残ると、それを見て項目が起きたと誤って判定する。
   2 では、書こうとしているスキルをコピーに含めない。
   コピーを作る前に、作り方・利用者の環境との違い・片付けの方法を利用者に示して確かめる。
   環境との違いには、持ち込まないファイル（`.gitignore` の対象など）・読まれる指示の文書（祖先のディレクトリの `CLAUDE.md` など）・利用者のレベルのスキル（`~/.claude/skills/` など）を含める。
   違いはそのまま 2 と 4 の結果に影響するので、どこまで揃えるかを利用者が決める。
   利用者の依頼で既に決まっていれば、確かめ直さない。決まっておらず、利用者に確かめられない実行では、この案を示して止まる。

   そのコピーを作業ディレクトリにして新しいセッションを起動し、1 の依頼文を実行させる。
   使い終わったコピーは、確かめた片付けの方法で消す。
   subagent は、作業ディレクトリをそのコピーに指定して起動できるときだけ使う。多くの subagent は親のセッションの作業ディレクトリを引き継ぐので、コピーを渡しても親の作業ツリーで動く。
   今の会話の中で自分で試さない。スキルを作る意図を知っているので、期待する振る舞いを自分から取ってしまう。
   自分で新しいセッションを起動できないエージェントでは、コピーの中での実行を利用者に頼み、結果を受け取る。
   記録するのは、依頼文と、項目ごとに起きたか起きなかったかと、起きなかった項目で実際に取った振る舞いである。
   すべての項目が起きたら、同じ方法でさらに 2 回実行する。LLM の振る舞いは実行ごとに変わるので、1 回だけでは要らないと決めない。
   3 回とも全項目が起きたなら、スキルは要らない。スキルを書かずに結果を利用者に示し、それでも作るかを確かめる。
   作ると決めたら、3 では利用者が求める内容を書く。
3. スキルを書く（下のコマンド）。
   本文には、2 で起きなかった振る舞いを起こす指示を書く。
   2 で既に起きた振る舞いの指示は書かない。モデルが既に従う指示は、読む量を増やすだけで振る舞いを変えない。
4. スキルを入れた状態で、2 と同じ方法・同じ初期状態・同じ依頼文で実行させ、1 で決めたすべての項目が起きるかを確かめる。
   2 で起きなかった項目が起きるようになったことに加えて、2 で起きていた項目が、書いた指示に妨げられずに起き続けることも確かめる。
   書いたスキルの実体と、各エージェント用のリンク（`.claude/skills/<name>` など）の両方を 4 のコピーに置いてから実行する。
   スキルを置く前から動いているセッションが、置いたスキルを読み込むとは限らない。そのため 4 は、スキルを置いた後に起動したセッションで実行する。
   起きない項目があれば、スキルが読まれたか（`description` が依頼文に当たったか）と、指示がその振る舞いを求めているかを確かめて直し、4 をやり直す。
   エージェントが指示を守らずに済ませる別のやり方を見つけていたら、そのやり方を禁じる指示を足して、4 をやり直す。
   すべての項目が起きたら、2 と同じく同じ方法でさらに 2 回実行し、3 回とも起きたときに確認を終える。1 回だけの成功は偶然のことがある。
   追加の実行で起きない項目が出たときも、直して 4 をやり直す。直した後は、全項目が起きた回数を 0 から数え直す（やり直した回数は数え直さない）。
   スキルを直してやり直した回数が 3 回に達しても起きない項目が残るなら、やり直しを止め、残った項目と各回の結果を利用者に示して進め方を確かめる。
   手順 2 と 4 の確認は、`skill-creator` が使えないときも飛ばさない。
5. 2 と 4 の結果を利用者に示す。

```bash
# ディレクトリ作成
mkdir -p .agents/skills/<name>

# SKILL.md を作成する（frontmatter + 本文）

# Claude Code 用シンボリックリンク
mkdir -p .claude/skills
ln -s ../../.agents/skills/<name> .claude/skills/<name>
```

常に参照させたいときは、`AGENTS.md` の「参照スキルガイド」の節に追記する。

```markdown
## 参照スキルガイド

- `<name>`: <スキルの用途説明>
```

## スキル更新手順

`.agents/skills/<name>/SKILL.md` を直接編集するだけでよい。シンボリックリンクを通して、自動で反映される。

## スキル削除手順

```bash
rm -rf .agents/skills/<name>
rm .claude/skills/<name>
```

`AGENTS.md` に参照があるときは、その行も削除する。

## スキル検証

`skill-creator` スキルが使えるときは、「スキル作成手順」の 2 と 4 に加えて、複数の依頼文でスキルを使う場合と使わない場合を比べる評価と、その結果に基づく改善を提案する。
