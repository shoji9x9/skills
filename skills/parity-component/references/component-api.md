# 固定と可変の切り分け・引数の設計

共通部品の引数は「どこが可変か」を決めてから設計する。**可変の判断を目視に委ねない**——
現行に 6 種あるバリアントを 3 種で作る、ページャを汎用ボタンではなく専用の見た目と仮定する、といった取りこぼしは
実装が終わってから人が現行と見比べるまで出てこない。

**採取物が揃っていれば、固定と可変は機械的に決まる**——インスタンス間で値が割れた軸が可変、割れない軸が固定である。
割り出しは `scripts/axis-diff.mjs` が行い、**どれを引数にするかの判断だけ**を人・エージェントが行う。

## 割り出しの実行

```bash
node <skill>/scripts/axis-diff.mjs <manifest.json> --out .replace/components/<slug>/axes.json
```

- **コピーせずスキル配下のスクリプトをそのまま実行する**（`gh skill update` の自動更新を効かせる）
- マニフェストは採取物から組み立てる。形はスクリプト冒頭のコメントが正本（`component` と `instances[].states[].traits`。`traits` は trait-capture.mjs の返り値の形をそのまま入れる）
- **exit 0 になるまで採取へ戻る。** 落ちる条件は「インスタンスが 2 件未満」「状態集合が揃っていない」「一部インスタンスでしか採れていない軸」「id の欠落・重複」で、
  いずれも**未測定を固定側へ倒さないための停止**である。`problems` を残したまま `fixed` だけを読まない

## 割り出し結果の読み方

| 出力 | 意味 | 既定の扱い |
|---|---|---|
| `variable` | インスタンス間で値が割れた軸 | **引数の候補。** 引数にしないなら理由を書く |
| `fixed` | 全インスタンスで同じだった軸 | 実装の定数。引数にしない |
| `problems` | 突き合わせられなかった軸・状態 | 採取へ戻す。**空欄のまま先へ進まない** |

- **`fixed` は「このアプリのこの部品では割れなかった」という意味**であって、「部品として不変であるべき」ではない。
  インスタンスを増やせば割れる可能性があるので、**`fixed` を根拠に将来の引数追加を拒まない**
- **`variable` を機械的に全部引数にしない。** 割れ方には 3 種類あり、扱いが違う

| 割れ方 | 見分け方 | 扱い |
|---|---|---|
| 意図された差 | 割れた値が意味のある区分になっている（主ボタンと副ボタンの色） | **引数にする。** 値の集合を `component-api.md` に列挙する |
| 文脈で決まる差 | 寸法が中身に追従している（`rect/width` が文言の長さで変わる） | 引数にしない。**中身（`children` 相当）から決まる**ことを書く |
| 現行の不整合 | 割れているが区別する理由が見つからない（同じ用途で余白が 1px 違う） | **自分で揃えない。** 差を提示してユーザーに確認し、揃えるなら `intentional_diffs.pending` へ非破壊追記する |

- **判別できない割れ方を「現行の不整合」に倒さない。** 用途の違いを見つけられていないだけのことがある。
  判別できないものは `component-api.md` に「未判別」として残し、ユーザーに上げる

## 状態を表す引数

`hover` / `active` / `focus` は**利用側が渡すものではなく CSS が引き受ける**。引数にするのは、**利用側が決める状態**だけである。

- 引数にする: `disabled`、`checked` / `selected`、`readonly`、`error`（バリデーション結果の表示）、`loading`——いずれも利用側が制御する
- 引数にしない: `hover` / `active` / `focus-visible`——**採取した状態別の値は、引数ではなく実装のスタイル規則へ落とす**
- **採取した状態のうち、実装のどこにも落ちていないものが無いことを確かめる。** `component-api.md` の状態表に「採取した状態 × 落とし先（引数かスタイル規則か）」を書き、空欄を残さない

## 擬似要素で描いているかどうかは軸である

`::before` / `::after` の有無は `axis-diff.mjs` が `::before/<present>` という軸で出す。
**現行が標準コントロールを使っているのか擬似要素で描いているのかは、実装方式そのものを決める**ので、値の差より先に見る。

- 現行が標準の `select` / `checkbox` を使っているなら、**新側も標準要素で作る**のが既定。自前描画に置き換えるのは仕様変更に近く、ユーザー確認が要る
- 逆に現行が擬似要素で描いているなら、標準要素で作り直すと採取値と揃わない。**現行の方式を写す**（振る舞い保存と品質改善を同じフェーズで狙わない）

## 記録

割り出しと判断は `component-api.md`（テンプレート: `assets/component-api-template.md`）に残す。**`axes.json` を貼り直さない**——
残すのは「割り出しの結果どう判断したか」であって、ツール出力そのものはファイルとして併存させる。

- 引数ごとに「対応する軸」「値の集合」「既定値」「既定値の根拠となったインスタンス」を書く
- **引数にしなかった `variable` の軸は、理由とともに全件残す**（後から「なぜこの差を吸収したのか」を追えるようにする）
- ユーザー確認へ回した差は `intentional_diffs.pending` の追記と対応づける（`slug` / `added_by` / `added_at` の形は `replace-strategy` の `references/project-config.md` が正本）
