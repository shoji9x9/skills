# 部品の一生の順番で起きる不具合の実行パス

見本の照合・操作の突き合わせ・パリティスイートは、毎回同じ順番で部品を描いて操作する。
部品の一生の順番（付ける → 片付ける → 付け直す、初期化の後に引数が変わる）で起きる不具合を、どの工程も一度も通らない。
このファイルでは、部品の一生の中で処理が通る道筋を「実行パス」（`build-metadata.json` では `path`）と呼ぶ。

市販部品を初期化のコールバック（`initialized` など）で命令的に結び、effect の片付けで外す部品で、実際に次の 3 件が起きた。
どれも、パリティスイートと `parity-diff` は両側で緑で、利用者が開発サーバーで確かめた画面でだけ不具合が出ていた。

- 開発時の結び直しで、1 つのグリッドに列のフィルターが 2 つ付いた（絞り込んでも見出しに印が付かない）
- 開いたまま列の定義が差し替わると列が作り直され、フィルターの種別がデフォルトに戻った（フィルターを持たない列にボタンが出る）
- 行のデータが差し替わると、フィルターが種別ごと捨てられた

直した処理が後で消えても、どの検査も失敗しない。
そこで、`build` で対象かどうかを判定し、不具合が起きる実行パスを見本で強制して確かめる。

## 対象の判定（build の手順 4 の実装の後）

次の 3 つがすべて当てはまる部品を対象にする。
判定と根拠を、`build-metadata.json` の `lifecycle.applies` と `lifecycle.reason` に書く（当てはまらない部品も、どれが外れたかを書く）。

1. 部品が初期化を 1 度しか通らず、後から来る変化を自分で受け直す形である（初期化のコールバックで命令的に結ぶ・effect の片付けで外す・引数の変化を部品の側で購読して反映する）
2. その実行パスを、既存の検査が通らない（見本の照合・操作の突き合わせ・E2E は、毎回同じ順で描く）
3. 不具合を起こす処理を名指しできる（「フィルターを付ける処理」「列の作り直しの後にフィルターの種別を戻す処理」のように）

## 4 つの実行パス

対象の部品では、次の 4 つの実行パスのそれぞれについて書く。
不具合を起こす処理を名指しできるものは `lifecycle.paths[]` に、名指しできないものは理由と一緒に `lifecycle.not_applicable_paths[]` に書く。

| `path` | 何が起きるか | 典型的な不具合 |
|---|---|---|
| `strict-rebind` | 開発時の結び直し（React の `StrictMode` などで、effect が 付ける → 片付ける → 付ける） | 二重に付く・片付けの後に古い参照を使う |
| `prop-identity` | 開発サーバーの差し替えで、同じ内容の引数が別のオブジェクトになる | 同じ内容で作り直して、状態がデフォルトに戻る |
| `remount` | 外して付け直す | 片付けの忘れ・前回の状態の持ち越し |
| `prop-change-after-init` | 初期化の後に引数が変わる（一覧が後から届く・もう一度取得する・列の定義や行のデータの差し替え） | 初期化したときの値のまま・差し替えで、付けた処理が捨てられる |

## 順番を強制する見本

実行パスごとに、その順番を強制する見本を置く。
React の場合の例を次に挙げる。カタログの実体は `references.component_catalog` に従う。

- 結び直し: 自前の `createRoot` を `act` の外で作って `StrictMode` で描く。遅延 0 の `setTimeout` をその場で呼び、初期化のコールバックを effect の 2 回目より先に実行させる
  （Storybook の描画に載せたままでは、effect の 2 回目が実行されない）
- 引数が変わる実行パス: 見本に「列を作り直す」「行のデータを差し替える」のような、その変化を起こすボタンを置く
- **見本は実行パスに入った回数を `data-*` 属性で出し、検査は「実行パスに入った」ことを先に確かめてから症状を見る。**
  入らないまま症状だけを見ると、直した処理が消えても（実行パス自体に入っていないので）緑になる

検査は Playwright などで見本を開いて行い、コマンドと結果を `lifecycle.paths[]` に記録する。
**直した処理を 1 つずつ外すと、その実行パスの検査だけが失敗することを、1 度確かめる**（`fix_removal_verified`）。
検査が実行パスの症状を実際に捉えている証拠は、これしかない。

- この見本は、見た目の照合の見本ではない。`catalog.stories` の対応表に載せず、見た目の基準も採らない。
  カタログにしか無い見本として `parity.unbaselined_stories` に数えない根拠は、`lifecycle.paths[].story` に載っていることだけである
  （[`catalog.md`](catalog.md)「現行に無い見た目を見本に作らない」）
- 対象でない部品に、この種類の見本を置かない（置くと、照合されない見本がカタログに残る）

## 完了判定

`lifecycle.applies: true` の部品は、次の 4 つを完了の条件にする。

- `lifecycle.paths[]` のすべてで検査が通っている（`result: pass`）
- 各検査が、実行パスに入ったこと（`data-*` 属性の回数が 1 以上）を、症状より先に確かめている
- `fix_removal_verified` が真である
- 順番の見本が `catalog.stories` に無く、`parity.unbaselined_stories` にも数えていない（`lifecycle.paths[].story` に載っているものだけを除く）

名指しできない実行パスが、`not_applicable_paths[]` に理由と一緒に残っていることも確かめる（空の実行パスを、警告なしに省かない）。

判定は、同梱の [`../scripts/lifecycle-check.mjs`](../scripts/lifecycle-check.mjs) が行う（コピーせずに、スキル配下から実行する）。次のことを確かめる。

- 4 つの実行パスが、`paths` と `not_applicable_paths` のどちらかに、ちょうど 1 回ずつ現れる
- `paths` の各行で、検査が通り、実行パスに入った回数が 1 以上で、`fix_removal_verified` が真である
- 順番の見本が `catalog.stories` に載っていない
- 対象でない部品が `paths` を持たない

結果の終了コードを、`lifecycle.check_exit` に書く。

```bash
node <skill>/scripts/lifecycle-check.mjs \
  --build-metadata .replace/components/<slug>/new/<target>/build-metadata.json
```

終了コードの意味は次のとおりである。

- exit 0: 条件を満たす（対象でない部品を含む）
- exit 1: 不足が残る
- exit 2: 使い方の誤りか、形の誤り（`lifecycle` が無い・`applies` が真偽値でない、など）

部品を改修したら、もう一度検査する（[`amend.md`](amend.md)「回帰は目視で確かめない」）。
完了報告には、対象にした実行パスと、`not_applicable_paths` の理由を、収束と並べて示す。
