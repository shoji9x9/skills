# 照合と収束

カタログの見本を現行と同じ条件で採り、`parity-suite` 同梱の差分ツールで基準と突き合わせる。
検出は決定論的なツールが行い、LLM は分類（要対応・許容・環境ノイズ）だけを行う。この分担は `parity-diff` と同じである。
差分ツール・しきい値・ノイズ基準値の意味の原本は、`parity-suite` の `references/baseline.md` と `parity-diff` の `references/detect.md` である。
ここでは、比較の対象が画面ではなく部品単体になることで変わる部分だけを定める。

## 同一条件の再現

`metadata.json.capture_conditions` に記録した条件を、そのままカタログ側へ当てる。

- ビューポート・DPR・アニメーションの無効化・撮影範囲（要素の矩形）は、現行と同じにする。記録した条件を読まずに撮り直さない
- カタログ側も、`parity-suite` 同梱の element-shot.mjs で撮る（[`capture.md`](capture.md)「ページ全体ではなく要素を撮る」）。
  `locator.screenshot()` へ戻すと、要素の矩形を外接する整数の矩形へ広げる丸めが片側にだけ入る。
  すると、同じ寸法の部品でも PNG の寸法が食い違い、画素で比較できなくなる。
  カタログが iframe で描くなら（Storybook など）、iframe の中の要素をそのまま渡してよい（ツールがフレームのオフセットを足す）。
  クロスオリジンのフレームと、平行移動以外の変形（拡大縮小・回転・反転）がかかったフレームでは、撮らずに失敗する。
  その場合は、その iframe の URL をページとして開いて撮る（[`capture.md`](capture.md) の同じ節）
- カタログ側の採取物は、`new/<target>/catalog/<instance>/<state>/` に、基準と同じファイル名（`element.png`・`element.shot.json`・`traits.json`）で置く。
  寸法の突き合わせ（shot-size-compare.mjs）は、この置き場所を基準の `baseline/<instance>/<state>/` と組で読む
- 差分ツール（trait-compare.mjs）がプロジェクト側に無ければ、採取と同じ手順で `parity-suite` から用意する。
  手順は [`capture.md`](capture.md)「`parity-suite` 同梱ツールの用意」で、既にあるコピーが同梱版と違えば止まる
- 採取ツールのバージョンを突き合わせる。trait-capture.mjs・element-shot.mjs・css-rules-capture.mjs の `VERSION` が `metadata.json` の記録値と違うなら、
  片側だけ新しい形で採った成果物になる。**比較へ進まず、両側を採り直す**（止まるのが正しい振る舞いである）
- カタログ側も、状態へ遷移したら、撮る要素の矩形が落ち着くまで待ってから撮る（[`capture.md`](capture.md)「状態への遷移は呼び出し側が行う」）
- カタログ側の自己ノイズも、同じ条件で 2 回撮って測る。現行のノイズ基準値を、そのままカタログへ当てない。描画する要素の数が違えば、揺れ方も違う。
  2 回目の採取物は `new/<target>/noise-pass2/` に置き、基準値を記録したら削除する。`new/<target>/catalog/` の中に置くと、寸法の突き合わせが母集合に無い組の見本として数えて止まる

## 比較方法の役割

| 比較 | 見るもの | 部品単体での注意 |
|---|---|---|
| 寸法 | 要素の PNG の幅と高さ（`element.shot.json` の `png`） | 画素の比較より先に、同梱の shot-size-compare.mjs で突き合わせる（下の「寸法の突き合わせ」） |
| 画素 | 要素の矩形の内側の見た目 | 要素の矩形で切るので、PNG の寸法が違うと比較できない（画素の比較のツールは寸法の不一致のエラーで止まる）。矩形の外に出る見た目（外側の `box-shadow`）と要素の置かれ方（`position` / `top` / `left`）は、画素の比較では検出できないので、特性の照合で見る |
| 特性の照合 | 固定のプロパティの集合の計算値。文字の持ち主（`text_owners`）の書体・大きさ・行の高さ・文字の寸法。スクロールする要素（`scroll`）のはみ出し・スクロールバーの厚みと見た目 | 現行で採った状態と同じ状態で採る。状態がずれた照合は、全項目が差分になる。文字の持ち主は並び順で突き合わせるので、現行が入れ子の `span` に文字を持ち、見本が要素自身に文字を置く実装でも差が出る（`kind: "text"`） |
| 当たっている CSS 規則 | 宣言・条件・`!important` | **合否の判定には使わない。** 差分が出た理由を調べるための材料である |

- CSS 規則の差を合否にしない。新側は別のライブラリ・別のクラス名で書くのが前提なので、規則が違うのは正常である。
  判定するのは計算値と画素で、規則は「なぜ計算値が違うのか」を追うために読む。
  読むときは、同梱の cascade-resolve.mjs で勝つ宣言を確定する（[`catalog.md`](catalog.md)「勝っている宣言を確定してから転記する」）
- **画素の比較が「実行不能」で返ってきたら、許容に数えない。** 寸法が食い違って比較できていないだけで、その組み合わせは画素の比較を欠いたまま進んでいる。
  寸法の差は、下の「寸法の突き合わせ」が差分として出す
- 画素の差分が出て、特性の照合の差がゼロのときは、名前の付かない内部要素か、フォントの実体の差を疑う。切り分けの手順の原本は、`parity-diff` の `references/font-diff.md`

## 寸法の突き合わせ

特性の照合（trait-compare.mjs）は、要素の対の関係だけを比べ、要素 1 つの幅や高さの差を出さない。
部品単体の照合では要素が 1 つのことが多いので、寸法の差は特性の照合に現れない。
そこで、画素の比較の前に、同梱の [`../scripts/shot-size-compare.mjs`](../scripts/shot-size-compare.mjs) で、比較の母集合のすべての組の PNG の寸法を突き合わせる。

```bash
node <このスキル>/scripts/shot-size-compare.mjs \
  --baseline .replace/components/<slug> \
  --catalog .replace/components/<slug>/new/<target>/catalog
```

- 判定は、両側の `element.shot.json` の `png` の幅と高さの完全一致である。差は `size-mismatch` として 1 件ずつ出る（exit 1）。
  `page_rect`（ページ全体の座標で測った矩形。element-shot.mjs はこれを丸めて切り抜く）の幅と高さは、差の大きさを読むための診断として添えられる。判定には使わない
- exit 2 は、判定できなかったという意味である。合格として扱わない。0 と 1 以外の終了コードも同じに扱う。
  主な例は次のとおりである。組の記録が片側に無い・読めない。`png` が正の整数でない。両側の element-shot.mjs のバージョンが違う。母集合に無い組の見本がある。
  `--catalog` が基準の `baseline/` か部品の成果物ディレクトリを指すとき（基準を基準と比べると全組が一致してしまう）と、基準の `baseline/` が無いときも当たる。
  `metadata.json` の `instances`・`capture.states`・`unreachable_states` が判定できない形のときも当たる。
  出力の `findings` のうち `size-mismatch` 以外の指摘が、判定できなかった理由である。`code` と `detail` に従って採取物・見本・`metadata.json` を直し、もう一度実行する。
  exit 2 の出力にも、比べ終えた組の `size-mismatch` が含まれる。比べた組の数は `counts.compared` にあり、全組を比べたとは限らないので、ここで分類を確定しない
- 寸法の差は、分類（下の「分類」）に 1 件ずつ載せる。画素の比較は、その組では寸法がそろうまで実行できない。
  宣言に結び付けて許容にした寸法の差の組は、画素で比べないまま残る。その組の見た目を確かめていないことを `gaps.md` に書き、完了報告でも示す
- `page_rect` の差が 1px 未満でも、PNG の寸法は違うことがある。element-shot.mjs は `page_rect` の幅と高さを軸ごとに四捨五入して撮るので、80.48px と 80.5px は 80px と 81px の PNG になる。
  この差も画素の比較を止めるので、寸法の差として扱う。見本の寸法を基準に合わせて直す

### 親の寸法に追従する部品

幅や高さを親から決める部品（`width: 100%`・幅が `auto` のブロック要素・`height: 100%` など）は、カタログで置いた入れ物の寸法がそのまま PNG の寸法になる。
実測では、同じ部品が、内側の幅 584px の入れ物で 584px、284px の入れ物で 284px の PNG になった。中身で幅が決まる部品は、入れ物の幅が変わっても同じ寸法だった。

- 現行の勝っている宣言（cascade-resolve.mjs で確定する。[`catalog.md`](catalog.md)「勝っている宣言を確定してから転記する」）で、寸法が親から決まると確かめた部品だけを、次のように扱う。
  宣言を確かめずに入れ物で寸法を合わせると、現行が固定の幅なのに新側を `width: 100%` で実装した誤りが、入れ物の幅で隠れる
- 見本は、部品の矩形が基準の `element.shot.json` の `rect` と同じ寸法になる入れ物に置く。寸法は基準の記録から読み、手で決めない。
  入れ物の寸法と、その根拠にした宣言を、部品の `component-api.md` に書く（形は [`../assets/component-api-template.md`](../assets/component-api-template.md)「見本を置く入れ物」）
- 入れ物を置かずに出た寸法の差を、許容や環境ノイズに分類しない。見本を直して採り直す
- 入れ物で一致しても、部品が親に追従することは示さない（固定の寸法で実装しても一致する）。
  追従するかは、画面に載せた後に、`parity-suite` の寸法の式（`dimension-fit.mjs`）が確かめる。部品の照合で確かめていないことを、完了報告に示す

## 分類

差分は 1 件ずつ、現行側と新側の対（crop の対）を並べて分類する。まとめて「だいたい同じ」と判断しない。

| 分類 | 条件 | 次の行き先 |
|---|---|---|
| 要対応 | 現行と違っていて、宣言した意図的な差異でも環境ノイズでもない | 実装（`build` の手順 4）へ戻す |
| 許容 | `intentional_diffs.keep` / `may_change` か、`component_diffs` の宣言に紐づく | `parity.md` に、宣言との対応を書く |
| 環境ノイズ | 差分量が `noise_baseline` と同じ程度 | `parity.md` に、基準値との比較を書く |

- **宣言に紐づかない差を「許容」にしない。** 宣言が無いなら、`intentional_diffs.pending` へ非破壊で追記し、ユーザーの確認へ回す（分類を先に決めてから宣言を作らない）
- 「差異を見る前に一括で分類する指示」（「全部 keep で」など）に従わない。内容を見ずに分類すると、レジストリが差異を握りつぶすために使われる
- 環境ノイズに分類するときは、そのインスタンス × 状態の基準値と比べる。別の組み合わせの基準値を使い回さない

## 収束

収束は、次の 6 つがすべてそろったときだけである。

1. 説明の付かない差分がゼロである。要対応が 0 件で、許容に分類した差がすべて宣言（`intentional_diffs` / `component_diffs`）に紐づいている
2. `verification_commands.full` が通る
3. 比較の母集合のすべての組み合わせに対応する見本があり、すべてを照合した。寸法の突き合わせ（shot-size-compare.mjs）が exit 0 であるか、exit 1 の `size-mismatch` が全件、分類に載っている
   逆向きに、母集合に対応しない見本（基準の無い見本）が 0 件である（[`catalog.md`](catalog.md)「現行に無い見た目を見本に作らない」）。
   母集合の定義は、`parity-component` の `SKILL.md`「前提」にある。宣言済みの `unreachable_states` は母集合から外れるが、
   外した事実と理由は `gaps.md` に残り、完了報告でも収束と並べて示す
4. 操作の結果の突き合わせ（`behavior-compare.mjs`）が exit 0 である。見た目の 3 つの条件は、操作した結果を 1 件も示さない。
   比べなかった操作と、列挙の外の挙動を引き受ける工程を、完了報告に示す（[`behavior.md`](behavior.md)）
5. 動きの突き合わせ（`motion-compare.mjs`）が exit 0 である。見た目の照合は動きを止めて撮るので、動きの欠落を 1 件も示さない（[`motion.md`](motion.md)）
6. 部品の一生の順番の検査（`lifecycle-check.mjs`）が exit 0 である。毎回同じ順で描く照合は、順番によって起きる不具合を通らない（[`lifecycle.md`](lifecycle.md)）

- **`gaps.md` に残した未検証（`inaccessible` / `unresolved` / 到達できない状態 / 採取環境への依存）は、収束を止めない代わりに消さない。**
  完了報告では、収束と未検証を並べて示す。未検証を書いたまま「差分ゼロで完了」とだけ報告すると、確認済みと読まれる
- 反復には上限を置き、超えたら止まってユーザーに上げる。同じ箇所で 3 回以上往復しているなら、原因は実装ではなく、採取物か分類の側にある可能性が高い。
  前の反復の結論を次の反復で訂正している場合は、特にそうである。採取の条件・状態の遷移・引数の割り当てを疑う
- 反復の回数と、その反復で描画に影響する変更を入れた範囲を、`new/<target>/build-metadata.json` に記録する

## 部品の収束は機能の収束ではない

このスキルが収束させたのは、カタログ上の部品単体である。画面に載せたときの差（親から継承する指定、周りの余白、隣の要素との重なり）は見ていない。
操作の結果も、列挙した操作についてだけ突き合わせている。列挙の外の操作と、ページのデータや他の部品と連動する挙動は見ていない。
それを引き受けるのは、機能単位の `parity-suite` の部品の網羅表と、`parity-replace` の新側の突き合わせである。

- 機能の実装で同じ部品を使ったときに差が出たら、それは部品の回帰ではなく、利用する側の問題であることが多い。
  切り分けずに部品を直すと、他の利用箇所を壊す（[`amend.md`](amend.md)）
- このスキルの収束を、`parity-diff` の収束の代わりにしない。機能の収束の判定の原本は、`parity-diff` の `references/convergence.md`
