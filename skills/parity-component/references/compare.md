# 照合と収束

カタログの見本を現行と**同一条件**で採り、`parity-suite` 同梱の差分器で基準と突き合わせる。
**検出は決定論的ツールの仕事、分類（要対応／許容／環境ノイズ）だけが LLM の仕事**という分担は `parity-diff` と同じで、
差分器・しきい値・ノイズ基準値の意味論は `parity-suite` の `references/baseline.md` と `parity-diff` の `references/detect.md` が正本。
ここでは、比較対象が**画面ではなく部品単体**になることで変わる部分だけを定める。

## 同一条件の再現

`metadata.json.capture_conditions` に記録した条件を、**そのままカタログ側へ当てる**。

- ビューポート・DPR・アニメーション無効・撮影範囲（要素の矩形）は現行と同じにする。**記録した条件を読まずに撮り直さない**
- **採取ツールのバージョンを突き合わせる。** trait-capture.mjs の `VERSION` と css-rules-capture.mjs の `VERSION` が `metadata.json` の記録値と違うなら、
  片側だけ新しい形で採った成果物になるので**比較へ進まず、両側を採り直す**（止まるのが正しい振る舞い）
- カタログ側の自己ノイズも**同一条件で 2 回撮って**測る。現行のノイズ基準値をそのままカタログへ当てない——描画する要素の数が違えば揺れ方も違う

## 3 つの経路の役割

| 経路 | 見るもの | 部品単体での注意 |
|---|---|---|
| 画素 | 要素の見た目全体 | 要素の矩形で切るため、**寸法が違うと全面差分になる**。先に特性照合で `rect/width` / `rect/height` の差を見る |
| 特性照合 | 固定プロパティ集合の計算値 | 現行で採った状態と同じ状態で採ること。状態がずれた照合は全項目が差分になる |
| 当たっている CSS 規則 | 宣言・条件・`!important` | **合否判定には使わない。** 差分が出た理由を調べるための材料 |

- **CSS 規則の差を合否にしない。** 新側は別のライブラリ・別のクラス名で書かれるのが前提なので、規則が違うのは正常である。
  判定するのは計算値と画素で、規則は「なぜ計算値が違うのか」を追うために読む
- 画素差分が出て特性照合がゼロのときは、**名前の付かない内部要素か、フォントの実体差**を疑う。切り分け手順は `parity-diff` の `references/font-diff.md` が正本

## 分類

差分は 1 件ずつ、**現行側と新側の対（crop 対）を並べて**分類する。まとめて「だいたい同じ」と判断しない。

| 分類 | 条件 | 次の行き先 |
|---|---|---|
| 要対応 | 現行と違っており、宣言された意図的差異でも環境ノイズでもない | 実装（`build` 手順 4）へ戻す |
| 許容 | `intentional_diffs.keep` / `may_change` か `component_diffs` の宣言に**紐づく** | `parity.md` に宣言との対応を書く |
| 環境ノイズ | 差分量が `noise_baseline` と同程度 | `parity.md` に基準値との比較を書く |

- **宣言に紐づかない差を「許容」にしない。** 宣言が無いなら `intentional_diffs.pending` へ非破壊追記してユーザー確認へ回す（分類を先に決めてから宣言を作らない）
- **「差異を見る前の一括分類指示」に従わない**（「全部 keep で」等）。内容を見ずに分類すると、レジストリが差異の握り潰しに変わる
- 環境ノイズに分類するときは、**そのインスタンス × 状態の基準値**と比べる。別の組み合わせの基準値を流用しない

## 収束

収束は次の 3 つが揃ったときだけである。

1. **未説明差分ゼロ**——要対応が 0 件で、許容に分類した差が全件、宣言（`intentional_diffs` / `component_diffs`）に紐づいている
2. **`verification_commands.full` が通る**
3. **比較の母集合の全組み合わせに対応する見本があり、全件を照合した**
   （母集合の定義は `parity-component` の `SKILL.md`「前提」。宣言済みの `unreachable_states` は母集合から外れるが、
   **外した事実と理由は `gaps.md` に残り、完了報告でも収束と並べて示す**）

- **`gaps.md` に残した未検証（`inaccessible` / `unresolved` / 到達できない状態 / 採取環境依存）は、収束を止めない代わりに消さない。**
  完了報告では**収束と未検証を並べて示す**——未検証を書いたまま「差分ゼロで完了」とだけ報告すると、確認済みと読まれる
- **反復には上限を置き、超えたら停止してユーザーに上げる。** 同じ箇所で 3 回以上往復しているなら、原因は実装ではなく採取物か分類の側にある可能性が高い
  （前の反復の結論を次の反復で訂正している場合は特に。採取条件・状態遷移・引数の割り付けを疑う）
- 反復回数と、その反復で描画に効く変更を入れた範囲を `new/<target>/build-metadata.json` に記録する

## 部品の収束は機能の収束ではない

本スキルが収束させたのは**カタログ上の部品単体**である。画面に載せたときの差（親から継承する指定、周囲の余白、隣接要素との重なり）は見ていない。

- 機能の実装で同じ部品を使ったときに差が出たら、それは**部品の回帰ではなく利用側の問題**であることが多い。切り分けずに部品を直すと、他の利用箇所を壊す（[`amend.md`](amend.md)）
- **本スキルの収束を `parity-diff` の収束の代わりにしない。** 機能の収束判定は `parity-diff` の `references/convergence.md` が正本
