# 部品カタログの契約と見本

実装した部品を現行の基準と突き合わせるには、**部品を単体で、状態ごとに、決まった URL で描画できる場**が要る。
この場を「部品カタログ」と呼ぶ。**実体は本スキルが決めない**——プロジェクトが選び、設定 `references.component_catalog` が指すドキュメントに書く。

## 契約（満たせば実体は問わない）

| 条件 | なぜ要るか |
|---|---|
| **1 インスタンス × 1 状態が 1 つの固定 URL で開ける** | 採取スペックが URL を組み立てて巡れる。手で操作して状態を作る場だと再現できない。**単位を「部品 × 状態」にしない**——インスタンスごとに引数の値が違う部品では、1 つの URL で両方を再現できず、片方の照合が別インスタンスの既定値を写した見本に対して行われる |
| **Playwright で到達でき、要素を論理名で引ける** | 現行と同じ差分器・同じ引き方を当てるため |
| **静的なデータを見本へ注入できる** | データ依存部品に現行から採った実データを与えるため |
| **アニメーション・トランジションを無効化できる** | 撮影条件を現行と揃えるため（`animations: 'disabled'` と同等） |
| **描画が外部サービスに依存しない** | ネットワーク状態で採取物が揺れると、ノイズ基準値が使えない |

- 実体の例（**既定を置かない**）: Storybook、Ladle、Histoire、アプリ内のカタログページ、採取専用の最小ルート
- **`references.component_catalog` が未整備なら `build` に入らず停止する。** カタログの実体・見本の書き方・URL の決まり方・データの注入経路を推測で決めると、
  後から別のカタログへ移した時点で見本と採取スペックの両方を書き直すことになる
- URL の baseURL は設定 `targets[].catalog_url`（固定文字列）または `targets[].catalog_url_command`（標準出力に URL を 1 行出すコマンド。実行ごとにポートが変わる環境向け）から解決する。
  **この 2 つは排他で、両方あるのもどちらも無いのも停止する**（`url` / `url_command` と同じ形。同じキーに両形を入れると、開くのか実行するのかが決まらない）。
  `catalog_url_command` の解決に失敗・空出力なら停止する（解決値は成果物に書かず `"runtime"` を記録する）

## 見本の粒度は採取の粒度に合わせる

**見本は「インスタンス × 状態」ごとに置く。** 採取したのにその組み合わせの見本が無いと、その組み合わせは照合されない——
`build` の完了判定が「**比較の母集合**の全組み合わせに対応する見本がある」を要求するのはこのためである
（母集合の定義は `parity-component` の `SKILL.md`「前提」——`instances[]` × `capture.states` から
宣言済みの `unreachable_states` を除いたもの。**そのインスタンスで作れない状態の見本は作らない**）。

- 見本の識別子は**採取物のパスと機械的に対応づける**（`baseline/<instance>/<state>/` ↔ 見本 ID）。対応表は **target 別の `new/<target>/build-metadata.json` の `catalog.stories`** に書く
  （`build` は `side: new` の target ごとに走るので、slug 直下の採取 `metadata.json` へ置くと
  2 つ目の target が 1 つ目の対応表を上書きし、先に行った照合を後から追えなくなる）
- **対応表は見本側の名前を書き写して作らない。** カタログから見本の一覧を取得し（多くのカタログが一覧を機械可読で持つ）、
  採取物の一覧と突き合わせて**両側に無いものを検出する**。手で書き写すと、名前を変えた見本が対応表の中だけ生き残る
- インスタンスによって引数の値が違うのが正しい姿なので、**見本ごとに `component-api.md` が決めた引数の値を明示的に渡す**（既定値に頼ると、既定値を変えた瞬間に見本の意味が変わる）

## データ依存部品の見本

`capture` が保存した `baseline/<instance>/data.json` を**そのまま**見本の入力にする。

- **件数を減らさない・並べ替えない・値を丸めない。** 採取時に写っていた範囲と同じ入力でないと、差分の原因が実装なのか入力なのか分けられない
- カタログが非同期でデータを読む作りなら、**採取前にデータが描画され終わったことを assertion で確かめる**（件数の `toHaveCount` 等）。
  読み込み中の状態を撮ると、現行との差が実装差に見える
- 現行の 1 ページが 100 件で採取範囲が先頭 10 件なら、**見本にも 10 件だけを与える**。100 件与えて上から 10 件を撮ると、
  スクロールバーの有無や仮想スクロールの挙動が入り込んで採取条件が変わる（変えるなら条件を記録して現行側も同じにする）

## 現行に無い見た目を見本に作らない

カタログは何でも表示できるので、**現行に存在しないバリアント・状態の見本を作れてしまう**。作ると、それは照合されないまま実装に残り、
利用側から呼ばれた時点で誰も現行と比べていない見た目が画面に出る。

- 見本の集合は**採取物の集合と一致させる**。採取していない見た目の見本は置かない
- 現行に無いが新側で必要だと判断した見た目（新しい状態の表示等）は**仕様変更**なので、実装せずユーザーに上げる
