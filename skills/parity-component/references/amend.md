# 共通部品の改修（機能の実装中に課題が出たとき）

機能を実装する段階になって、先に作った共通部品を変える必要が出ることがある。引数が足りない、その画面でだけ表示が乱れる、状態が足りない、といった場合である。
この取り決めの原本はこのファイルで、`parity-replace` はここに任せる。

改修が危ないのは、部品がすでにほかの場所で使われているからである。目の前の画面を直す変更が、別の画面の見た目を警告なしに変える。
そして、変わったことは、その画面のパリティスイートが作られるまで、どの検査も失敗として示さない。

このファイルを当てるのは、「先に作られた部品」だけである。`.replace/components.md` が在ることは、当てる条件にならない。同じファイルに「先に作らない部品」も並んでいるからである。
対象を部品一覧の行に当てはめ、その slug の `.replace/components/<slug>/new/<選択中の new target>/build-metadata.json` が在ることまで確かめてから、このファイルの取り決めに入る。
一覧に無い部品、「先に作らない部品」の表にある部品、build の成果物が無い部品には、採取物も見本も無いので、下の「全見本を採り直して差分ゼロ」を満たせない。その部品は、機能の実装として普通に作る。

## まず切り分ける

部品を直す前に、どちらの問題かを決める。

| 症状 | 疑う先 | 確かめ方 |
|---|---|---|
| その画面でだけ表示が乱れる | 利用する側 | カタログの見本では正しいかを見る。正しければ、親からの継承・周りの余白・幅の制約が原因である |
| どの見本でも同じように違う | 部品 | 現行の採取物と突き合わせる。採取物と違うなら、部品の実装の誤りである |
| 現行にその状態かバリアントが在るのに、部品に無い | 採取の抜け | `.replace/components.md` のインスタンスに、その画面のインスタンスが入っているかを見る |
| インスタンスも状態も採っていたが、その軸（プロパティ）を測っていなかった | 測っていない軸 | 部品インベントリの全インスタンス × 採っていた全状態で、その軸を現行と新側について測る |

- 採取の抜けだった場合は、部品を直す前に採取へ戻る。そのインスタンスを部品インベントリに足してもらい、`capture` をもう一度実行して軸を割り出す。
  抜けた状態を採らずに引数だけを足すと、その引数の正しい値を誰も知らないまま実装することになる。
- 測っていない軸だった場合は、下の「現行に合わせ直す修正」で直す。見つけた画面の 1 インスタンスだけを測って直すと、同じ軸が割れているほかのインスタンスを取りこぼす。
- 利用する側の問題を、部品の側で吸収しない。その画面のためだけの分岐が部品にたまり、ほかの利用箇所の振る舞いが読めなくなる。

## 他の利用箇所を壊さない直し方

この節は、利用する側の求めで新しい見た目を足す改修の取り決めである。部品が現行と違っていたのを直す改修は、次の節「現行に合わせ直す修正」に従う。

1. 既存の引数の意味とデフォルト値を変えない。足すのは新しい引数で、そのデフォルト値は改修の前の振る舞いにする。
   デフォルト値を新しい振る舞いにすると、その引数を渡していない既存の利用箇所が全部変わる。
2. スタイルを足すときは、既存の見本に影響しない形で足す。新しい引数が立っているときだけ当たる規則にし、既存の規則の値を書き換えない。
3. 削除と改名はしない。引数・クラス・トークンの削除や改名は、破壊的な変更として扱う（下の節）。

## 現行に合わせ直す修正

部品の値が現行と違っていたとき（切り分けで「部品」か「測っていない軸」だったとき）の直し方である。
前の節の「デフォルト値は改修の前の振る舞いにする」は当てない。据え置くと、現行と違うデフォルト値が残り、引数を渡していないすべての利用箇所で現行との差が出続ける。

1. 直す前に、全インスタンスにわたって測る。部品インベントリの全インスタンス × 採っていた全状態で、その軸を現行と新側の両方について測る。
   見つけた画面の 1 インスタンスから直すと、同じ差を持つほかのインスタンスが、次の画面でまた見つかる。
2. 現行でその見た目を出す処理を、すべて数える。現行のソースで、その値を与える処理（クラス・スタイル・スクリプト・呼び出し元）を全部読み、すべてが同じ値なのか、一部だけなのかを決める。
   すべて同じなら、デフォルト値をその値にする。一部だけなら、系統か引数で分ける。
   数える前にデフォルト値を決めると、読み進めた後でデフォルト値を変え直すことになる。出し入れの動きをデフォルト値なしで足し、全部を読んだ後でデフォルト値ありに変え直した実例がある。
3. 修正は系統の単位で行い、デフォルト値を現行の値にする。全インスタンスにわたる測定で値が変わったインスタンスが属する系統を、まとめて直す。
4. 影響範囲を変更の宣言に書く。書く先は `.replace/components/<slug>/changes/<change-id>.json`（ひな形は `assets/component-change-template.json`、`kind: align-to-current`）である。
   書くものは、影響するインスタンス・状態・プロパティ、新側で部品を使うページ、変えたファイル、改修の前と後の commit、全インスタンスにわたる測定の記録である。
5. 照合の合格条件は、「宣言した範囲の外は差分ゼロで、範囲の中は現行の値と一致する」ことである。
   全見本を採り直し、範囲の外は改修の前の見本と差分ゼロで、範囲の中は全インスタンスにわたる測定で採った現行の値と一致することを示して、`parity.md` に追記する（下の「回帰は目視で確かめない」）。

この修正は、「破壊的変更はユーザーが決める」の「デフォルト値の変更」と「既存の見本の出力が変わる実装の変更」に当たらない。
デフォルト値と見本の出力が変わるのは、現行との差を消す向きだけであり、それを上の 5 の照合（範囲の外は差分ゼロ）で示すからである。
範囲の外に差が出たとき、または全インスタンスにわたる測定で現行の値が処理ごとに割れてデフォルト値を決められないときは、破壊的な変更として判断を求める。

変更の宣言は、`parity-suite` の `scripts/component-impact.mjs` の入力になる。部品を使うページの側の再検証は、`parity-diff` の `references/component-change.md` に続く。

## 見本を変更に追従させる

- 足した引数には見本を足す。見本の無い引数は照合されず、現行と合っているかを誰も確かめていない状態になる。
- 足した見本の照合の相手は、現行から採った基準である。
  基準が無い（現行に対応するインスタンスや状態が無い）なら、それは現行に無い見た目を作ろうとしているので、実装せずにユーザーに上げる。
- 基準の無い見本を、カタログに残さない。足した状態の見本は、その状態の基準を現行から採ってから照合に入れる。
  母集合に入らない見本は、改修で状態を作れなくなっても、どの照合も失敗しない（扱いの原本は [`catalog.md`](catalog.md)「現行に無い見た目を見本に作らない」）。
- 既存の見本は変えない。既存の見本の出力が変わったら、それは破壊的な変更が起きた合図である。
  ただし、現行に合わせ直す修正で、変更の宣言の範囲の中が現行の値に変わるのは除く。

## 回帰は目視で確かめない

改修した後は、その部品の全見本を採り直して基準と照合し、操作の結果と動きも突き合わせ直し、一生の順番の検査も実行し直す。
`compare.md`・`behavior.md`・`motion.md`・`lifecycle.md` の手順を、そのまま実行する。
見た目が変わらない改修でも、イベントの扱いを変えれば操作の結果は変わり、初期化や片付けの処理を変えれば、順番で出る不具合が戻る。

- 「ほかの画面は見た目を変えていないはず」を根拠にしない。変わっていないことは、採り直して差分ゼロで示す。
- 差分が出た見本は、その差が意図した改修によるものでも、そのままにしない。
  意図した変更なら基準の側が古いので、現行を採り直してよいかを確かめる。現行が変わっていないのに基準と差が出たなら、それは回帰である。
- 照合の結果は、`parity.md` に改修として追記する。前の照合の記録は書き換えない。

## 破壊的変更はユーザーが決める

次のどれかに当たるなら、自分で決めずに判断を求める。

- 既存の引数の削除・改名・意味の変更
- デフォルト値の変更（引数を渡していない利用箇所の振る舞いが変わる）。現行に合わせ直す修正で、デフォルト値を現行の値にするのは除く（「現行に合わせ直す修正」）。
- 既存の見本の出力が変わる実装の変更
- 現行に無い見た目や状態を部品に足すこと

利用者が破壊的な変更をはっきり頼んだ場合も、頼まれたことを承認とみなさない。
頼んだ時点では、利用者は影響範囲も代替案もまだ見ていないので、下の 3 点を示してから確認する。
示したうえで改めて指示されたら、それに従う。この節は、頼みを断るための節ではない。
「頼まれた＝決まった」と読むと、この節はいちばん必要な場面、つまり利用者が破壊的だと気付かずに頼んだ場面で働かない。

判断を求めるときは、次の 3 つを示す。「破壊的な変更をしてよいか」だけを聞かない。

1. 影響範囲: その部品を使っている箇所の一覧と、変更の後に見た目が変わる見本の一覧
2. 代替案: 引数を足してデフォルト値を据え置く形で解けるか。解けないなら、その理由
3. やらない場合に残るもの: 回避のために利用する側に入れる分岐と、それがたまったときに何が読めなくなるか
