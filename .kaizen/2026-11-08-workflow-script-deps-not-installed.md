# 新しいワークフローが、起動するスクリプトの依存を入れていなかった

## 事象

Issue #939 の PR #945 で、週次のワークフロー `check-cost-metrics.yml` を足した。
マージした後に `workflow_dispatch` で実行すると、`check-cost-metrics.ts` が `typescript` を import できず、`ERR_MODULE_NOT_FOUND` で失敗した。
ワークフローは `pnpm install` のステップを持たず、mise で Node.js だけを入れてスクリプトを起動していた。
スクリプトが外部のパッケージ（`typescript`・`js-yaml`）を import するようになったのは、PR のレビューの反復の途中である。
最初のバージョンは Node.js の組み込みのモジュールだけを使っていたので、依存を入れなくても動く形だった。
手元のテストと本物のデータでの実行は、どれも `node_modules` のある作業ツリーで行ったので、この食い違いを見つけられなかった。
CI のテストも依存を入れてから実行するので、同じ理由で通った。

## 根本原因

- なぜ失敗したか → ワークフローが入れる依存（Node.js だけ）と、スクリプトが import するもの（外部のパッケージ）が食い違った
- なぜ気付かなかったか → 手元・CI のどの確かめ方も依存を入れた環境で実行し、ワークフローの実行環境（依存なし）を再現していなかった。`workflow_dispatch` はマージの前に使えない
- なぜ食い違いが生まれたか → レビューへの対応で import を足したとき、そのスクリプトを起動するワークフローの準備のステップを見直す対象に入れなかった。import を足す変更と、実行環境を決めるファイルが別にある

## 提案

ワークフローがリポジトリのスクリプトを `node` で起動するときは、スクリプトが外部のパッケージを import するかを確かめ、するなら依存を入れるステップを置く。

- `.agents/rules/github-actions-authoring.md` に「3. 起動するスクリプトの依存」を足す。スクリプトに import を足したときは、そのスクリプトを起動するワークフローを grep で挙げ、依存を入れるステップがあるかを確かめる、と書く
- マージの前に確かめる方法として、依存の無い使い捨ての作業ツリー（`git worktree add` だけで `pnpm install` をしないもの）でスクリプトを起動する手順を添える。今回の失敗は、この方法で再現できた
- 機構（ワークフローの `node scripts/...` を挙げ、依存を入れるステップが無ければ、スクリプトの import を辿って外部のパッケージが無いことを確かめるテスト）は、記録が 1 回なので作らない。同じ種類の失敗が繰り返したら、効果と費用を書いて検討する
