# 書き込みの結果を入力にする呼び出しを、その書き込みと同じまとまりで並列に出した

## 事象

PR #694 で、返信の本文のファイルを Write で書き直す呼び出しと、そのファイルを読んで返信と解決をするスクリプトの呼び出しを、同じまとまりで並列に出した。
Write は「読んだ後に変更された」として失敗し、スクリプトは前の回の本文のファイルを読んで実行された。
前の回のスレッドはすべて解決済みだったので、スクリプトは「未解決に無い」で何も投稿せずに終わり、外向きの副作用は起きなかった。

## 根本原因

- なぜ古い本文で実行されたか → 後段が前段（Write）の成功を前提にしているのに、前段の結果を見る前に後段を出した
- なぜ並列に出したか → 前回と同じ名前のファイルを上書きする形にし、後段のスクリプトがその固定のパスを読むようにしていた
- なぜ規則が働かなかったか → AGENTS.md の「前段の成功を前提にする操作は、呼び出しを分けて前段の成功を確かめる」は、シェルの `&&` の場面として読まれやすく、ツールの呼び出しの並列化には当てはめにくい
- KEDB: 2026-10-02-dependent-bulk-op-ran-after-failed-prep（applied）の再発

## 提案

ファイルを書くツールの結果を入力にするツールの呼び出しは、1 回の応答で書き込みと並列に出さず、書き込みの成功を見てから出す。

- applied の学び（2026-10-02-dependent-bulk-op-ran-after-failed-prep）の再発なので、恒久的な置き場所の AGENTS.md「外向きの操作と破壊的な操作」の箇条に、上の 1 行を足す
- 回ごとに入力のファイル名を変え（`replies2.json` など）、スクリプトにはパスを引数で渡す。固定のパスを上書きすると、書き込みに失敗したときに前の回の入力が使われる

## 再発の記録（#901）

2026-11-05、issue-batch の run の #901 で、eval の fixture を作る Bash の呼び出しと、その fixture を使う eval の起動を、同じまとまりで出した。
fixture を作る呼び出しは worktree の確認に拒否されたが、eval はバックグラウンドで起動し、fixture の無いディレクトリを渡されて失敗した。
失敗を確かめてから、fixture をファイル編集ツールで作り、eval を起動し直した。

同じ #901 で、PR の本文を直す編集と lint、push、`gh pr create` を同じまとまりで出した。lint は文の長さの指摘を 1 件残していたが、`gh pr create` は直す前の本文で PR を作った。
本文を直して `gh pr edit --body-file` で書き直した。外向きの操作の前提にする lint は、結果を確かめてから次の呼び出しを出す。
