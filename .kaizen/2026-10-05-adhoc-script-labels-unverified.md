# 使い捨ての集計スクリプトの判定も、既知の入力で確かめてから読む

## 事象

ミューテーションテストの expect_failing を測る使い捨てのスクリプトで、vitest の JSON の `numFailedTestSuites` を
「テストファイルの読み込みに失敗した」とみなして印字した。
実際はテストが 1 件でも落ちたファイルを数える値なので、すべての変異に `SUITE FAILED` と出た。
本当に読み込みに失敗した変異（DR-SEC-NOTFOUND。末尾のカンマで構文エラー）が、その中に紛れた。

再発（2026-10-07・Issue #567）: eval を直列で実行する使い捨てのドライバで、成功の status を `success` と決め打ちした（実際の値は `succeeded`）。
レートリミットの判定も、応答の本文の語に誤って一致した。
その結果、成功した run を失敗と判定し、失敗時の `rm -rf` で成果物を消した。本実行の前の 1 件の試しで気づいたので、失ったのは 1 run だけだった。

再発（2026-10-14・Issue #602）: Claude Code のログで、引き継いだセッションのコピーした行の `session_id` が元のセッションの ID だったのを 1 組だけ見た。
それを根拠に「`session_id` が元のセッションを指すので見分けられる」と利用者に説明し、直し方の案にした。
実装の前に全 112 ファイルを数えると、ほとんどのファイルで `session_id` は自分の ID と違い、元のセッションを示す欄ではなかった。
説明を訂正し、message id の重複の除去に方式を変えた。

再発（2026-11-06・Issue #708・PR #919）: high の学び 30 件を仕分けるとき、使い捨ての `awk` で各ノートの `###` で始まる見出しだけを再発の記録として数え、「再発あり」と「単発」に分けた。
ノートの多くは再発を `再発（日付、Issue）:` で始まる段落に書いていて、見出しの数は 0 になった。
そのまま「単発・影響が狭い」として 20 件を medium に下げる案を利用者に示し、承認を得た。
`2026-10-08-cross-file-test-not-run-before-push.md`（再発 3 回）など少なくとも 7 件が、再発の記録を持っていた。
PR の CI が同じノートの原因（`child-timeout.test.ts`）で落ち、KEDB 照合でそのノートを開いて誤りに気付いた。

## 根本原因

- 誤った理由: フィールドの意味を確かめずに、名前から推測した。
- 確かめなかった理由: 使い捨てのスクリプトは検証の対象外だと扱った。
- その理由: `docs/agent-workflow.md` の「使い捨てのスクリプトも検出されることを確かめる」は、検出・除外の走査を例にしている。
  結果の分類（ラベル付け）には当てはめなかった。
- 再発の理由: 判定に使う値（status の値・エラーの記録）を、書き手のソース（`scripts/eval/normalize-skill-eval-result.ts`）や過去の実際の記録で確かめずに書いた。
  失敗の分岐が成果物を消したので、誤判定の証拠も残らなかった。
- 再発（#602）の理由: 1 組の標本で見えた値の一致を、フィールドの意味として一般化した。
  意味を述べる前に、全件での値の分布（自分の ID と同じ・違う・無い）を数えなかった。
- 再発（#708）の理由: 再発の数え方（`###` で始まる見出しだけ）を、段落で再発を書いた既知のノートに当てて確かめなかった。
  その分類の結果を、利用者の承認を求める判断の材料にした。

## 根拠

同じ原因（使い捨てのスクリプトの分類を、既知の入力で確かめずに読んだ）での再発を、#708 で確かめたので high にした。

## 失敗の種類

- 種類: 規則を破る
- 理由: 検出の確認の規則を知っていたのに、使い捨ての分類は例外に見えて当てなかった

## 提案

使い捨てのスクリプトが出す分類のラベルも、各ラベルに当たる既知の入力を 1 件ずつ通してから読む。

- 既知の入力の例は、読み込みに失敗する変異と、普通に落ちる変異。
- 既存の規約の再発なので、文書に追記するのではなく、`scripts/mutation/check-mutation-proof.ts` の `--only` で
  本物のランナーを使う形に寄せる。
- 判定に使う値は、書き手のソースか実際の記録を grep してから書く。
- 失敗の判定で成果物を消さず、名前を変えて退避する。
- 検出の確認は、実際の失敗の記録（過去の run）と成功した run の両方で行う。
- 利用者に示す仕分けの基準（再発の有無など）を使い捨てのスクリプトで数えるときは、書き方の違う既知の例（見出し・段落・箇条）で数えられることを先に確かめる。
  確かめられないなら、件数を「見出しだけを数えた」のように数え方を添えて示す。
- ログや API のフィールドの意味を説明や設計の根拠にする前に、手元の全件で値の分布を数え、標本 1 件の一致で意味を決めない。
