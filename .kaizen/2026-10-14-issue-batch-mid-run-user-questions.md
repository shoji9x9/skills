# issue-batch の実行の途中で利用者に確認を挟んだ

## 事象

Issue #601・#600 の issue-batch run の途中で、利用者に 2 回確認した。

- 共有ツリーに未 commit で残した `skills.issue-batch` の設定を、どう取り込むか（利用者の指摘を受けて）
- #601 の範囲のコメントに入れた「期待するテスト名が実在するかの事前チェック」を、試した結果採らないので外してよいか（受け入れ条件の突き合わせで `waived` に承認が要った）

利用者から、issue-batch の途中で利用者に確認したことは、issue-batch の改善が要る点だと指摘された。
無人の実行を前提にするスキルで、確認を待つと、利用者が不在なら止まる。

## 根本原因

- なぜ確認したか → 実行の途中で、利用者の判断が要る状態が新しく生まれた
- なぜ途中で生まれたか
  - 設定: setup で書いた設定を commit せずに run を始め、worktree に設定が無い状態になった
  - 範囲: 範囲を決めるコメントを自分で書いたとき、試していない「候補」の機構を約束として書いた。
    試して採らないと決めた時点で、受け入れ条件を外す承認が要った
- なぜ防げなかったか → issue-batch は「利用者の確認が要る判断は BLOCKED にする」と定めるが、
  判断が要る状態を run の前に洗い出す手順と、自分で範囲を書くときに約束と候補を分ける取り決めが無い

## 提案

issue-batch の run は、利用者の判断が要る状態を preflight で洗い出して先に決め、途中で生じたものは確認せずに BLOCKED（判断待ち）として記録して次へ進む。

- preflight: setup の設定が commit 済みで、base branch に入っていることを確かめる（未 commit なら run を始めずに案内する）
- preflight: 提案に選択肢があるノートや、方針が書かれていない Issue は、run を始める前に決めてもらう
- 範囲を自分で書くとき: 試していない機構は「候補（試して採否を決める）」と書き、受け入れ条件に入れない
- 途中で生じた判断: 利用者に確認を送らず、その項目を判断待ちとして記録し、最終報告に載せる
