# Issue の下書きに「既存の扱いを残す」と書く前に、その扱いが入った commit の意図を確かめる

## 事象

Issue #926 の下書きで、golden-dataset が HTML コメントの中の表と見出しを読む扱いを「固有の扱いは残す」と、やることに書いた。
着手してから履歴を読むと、この扱いは意図して作ったものではなかった。コメントの中のフェンス行を直した PR #696 が、元の読み方をそのまま残しただけだった。
残すと、同じ見出しの下にコメントアウトした古い表があるときに、その表を突き合わせに使う。実装の前に利用者へ確認し直し、描画に合わせる方針に変えた。

## 根本原因

- なぜ「残す」と書いたか: コードコメント（「コメントの中の表と見出しは読む」）を、決めた仕様として読んだ。
- なぜ確かめなかったか: 元の意図を git 履歴で確かめる規約（`AGENTS.md`「確かめ方」）は、方針の選択肢を人に示す前を対象にしている。Issue の下書きの制約として書く場面を対象にしていない。
- なぜ同じ形が起きるか: レビューの指摘を退ける場面には、前の作業で `review-response.md` に同じ確かめ方を足した。しかし、Issue の下書きのように、既存の扱いを前提として書き出す場面は、どの規約も挙げていない。

## 根拠

確信度は medium である。1 回の観測だが、履歴を読まずに書いたという原因に絞れている。
Issue #926 の下書きを作ったのは PR #925 の作業中で、着手した後に `git log -S` で元の commit を読み、意図が無いことを確かめた。
KEDB 照合では「受け入れ条件・Issue・前提」で 3 件が当たったが、どれも Issue の下書きに既存の扱いを書く場面ではなかった。「意図・issue-create・コメント」では一致が無かった。

## 提案

Issue の下書きや計画に「既存の扱いを残す」「変えない」と書く前に、その扱いが入った commit を `git log -S` で読み、意図して作ったものかを確かめて添える。

- `AGENTS.md`「確かめ方」の「方針・配置の選択肢を人に示す前に」の箇条に、Issue の下書きと計画で既存の扱いを制約として書く場面を足す。
- 配布スキル `issue-create` の下書きの手順に、同じ確かめ方を 1 行で足すかを、apply のときに決める。
