# 切り離した仕事の生死は、出力ファイルではなくプロセスで判定する

## 事象

kaizen の回帰 eval 4 run を `nohup bash -c '... & ... & wait' &` の形で投げたところ、
呼び出し側には即座に「完了（exit 0）」が返り、ログファイルは 0 バイトのままだった。
これを「起動に失敗した」と判断し、出力先ディレクトリを `rm -rf` して別の
イテレーション番号で 4 run を再起動した。

実際には最初の 4 run は生きており、削除したディレクトリを作り直しながら走り続けていた。
同じ eval が二重に走り、API のセッション上限（429）に到達して、再起動側の 3 run が
途中終了した（取り直しで上限リセットまで待つことになった）。

## 根本原因

- なぜ二重に走ったか → 前の起動が生きているか確認せずに再起動した
- なぜ生きていないと判断したか → 判定材料を「ログファイルが 0 バイト」に置いた。
  起動直後は出力が空なのが正常であり、この材料は「まだ書いていない」と「死んだ」を
  区別しない（0 件を根拠にする判定の一種）
- なぜその材料を選んだか → ラッパーが即座に返した「完了」を、投げた仕事の完了と
  同一視した。実際に完了したのは `&` で切り離した親であって、仕事そのものではない
  ← 根本原因

横断スコープ確認: 同じ構図は「切り離した仕事の状態を、その仕事が書く成果物の有無で
推し量る」場面全般に効く（バックグラウンドのビルド・デプロイ・長時間スクリプト）。
`AGENTS.md` のワークフロー節には既に「パイプ越しの成否判定に末尾 `$?` を使わない」など
同種の**判定材料**の規律があり、そこへ並べるのが自然。

関連: [[2026-08-11-set-enumeration-needs-positive-control]]（0 件を根拠にする判定の別形態。
本件は「検出能力が無い検査」ではなく「まだ結果が出ていない状態」を失敗と読む形）。

## 提案

`AGENTS.md`「ワークフロー」節に以下を追記する:

- **切り離した仕事の生死は、出力ファイルではなくプロセスの実在で判定する。**
  `pgrep -af <識別できる文字列>` で確かめる。出力の有無・サイズは「まだ書いていない」と
  「死んだ」を区別しないため、起動直後の空ログを失敗の根拠にしない。
  ラッパーの終了は仕事の終了ではない。
- **失敗と判断して再起動する前に、前の起動が残っていないか確認して止める。**
  多重実行は課金・レート上限として跳ね返り、後続の作業ごと巻き添えにする。
- **出力先を `rm -rf` する前に、そこへ書いているプロセスがいないことを確認する。**
