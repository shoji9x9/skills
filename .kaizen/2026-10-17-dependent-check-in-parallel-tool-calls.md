# ベースブランチが進んでいないかを確かめる前に、push してしまう

## 事象

PR #673 のレビュー対応で、`git fetch`・`git rev-list --count HEAD..origin/main`・`git push` を 1 つの応答で並列に呼んだ。
件数は 1 だったが、push はその結果を待たずに実行された。
取り込んでいない commit（#670）は変更したファイルと重ならず、実害は無かった。

2026-11-09 に、PR #974（#942 の PR 2）を作るときに再発した。
`fetch && [ 件数 = 0 ] && push ; gh pr create` の形で書き、件数が 18 だったので push は実行されず、`;` の後の `gh pr create` だけが実行されて失敗した。
条件式は偽のときに何も出力しないので、失敗の理由を push が実行されなかったことと読めず、push だけを条件なしで実行し直した。
`main` の 18 commit を取り込まないまま push し、後から取り込んで push し直した。取り込んだ commit は変更したファイルと重ならなかった。

## 根本原因

1. なぜ確かめずに push したか → 確認と push を並列の呼び出しにした（2026-10-17）。確認が偽で止まった後、push だけを条件なしで実行し直した（2026-11-09）
2. なぜそうなったか → 確認が結果の値（0 かどうか）で後段を決めることが、呼び出しの形から見えにくい。偽の条件式は理由を出さないので、止まったことが別の失敗に見えた
3. なぜ見えにくいか → 手順（issue-start の step 11）が「確かめる」「push する」を別の文に書き、判定と push を 1 つにしたスクリプトが無い。呼び出すたびに手で組み立てるので、組み立て方の数だけ抜け方がある ← 根本原因

KEDB 照合: `前段`・`&&` で `.kaizen/2026-10-02-dependent-bulk-op-ran-after-failed-prep.md`（applied）に一致した。
applied なので追記せず、この記録を新しく作った。あちらはシェルの改行でつないだ形で、こちらはツールの並列の呼び出しである。

## 根拠

同じ原因（判定と push を 1 つにしたスクリプトが無く、手で組み立てた確認が push を止めなかった）で再発したので、high にした。
2026-10-17 は並列の呼び出し、2026-11-09 は `;` と条件なしの実行し直しで、組み立て方は違うが、どちらも確認の結果を見ずに push した。
KEDB 照合（`push`・`rev-list`）で、この記録だけが一致した。

## 提案

結果の値で後段を決める確認（件数・終了コード）は、後段の外向きの操作と手で組み立てず、判定と操作を 1 つにしたスクリプトで実行する。

- 反映先の候補: issue-start と pr-finalize-loop に、fetch・件数の判定・push をまとめた同梱のスクリプトを置く。0 件のときだけ push し、1 件以上なら取り込んでいない commit を表示して 0 以外で止まる
- step 11 の手順は、このスクリプトを呼ぶ形に書き換え、確認と push を別の呼び出しに書かない
- 効果: 同じ原因で 2 回起きた。どちらも取り込んでいない commit は変更と重ならなかったが、重なれば CI が古いベースで通り、マージの後の `main` が検証されない
- 費用: スクリプト 1 本とテスト。例外の一覧は要らない。実行時間は fetch の 1 回分で、今の手順と変わらない
