# push の前のベースの確認を、push と同じ応答の並列の呼び出しに入れ、確認の結果を見ずに push した

## 事象

PR #673 のレビュー対応で、`git fetch`・`git rev-list --count HEAD..origin/main`・`git push` を 1 つの応答で並列に呼んだ。
件数は 1 だったが、push はその結果を待たずに実行された。
取り込んでいない commit（#670）は変更したファイルと重ならず、実害は無かった。

## 根本原因

1. なぜ確かめずに push したか → 確認と push を並列の呼び出しにした
2. なぜ並列にしたか → どちらも短い定型のコマンドで、依存が結果の値（0 かどうか）にあることが見えにくかった
3. なぜ見えにくいか → 手順（issue-start の step 11）が「確かめる」「push する」を別の文に書き、判定と push を 1 つにしたスクリプトが無い ← 根本原因

KEDB 照合: `前段`・`&&` で `.kaizen/2026-10-02-dependent-bulk-op-ran-after-failed-prep.md`（applied）に一致した。
applied なので追記せず、この記録を新しく作った。あちらはシェルの改行でつないだ形で、こちらはツールの並列の呼び出しである。

## 提案

結果の値で後段を決める確認（件数・終了コード）は、後段の外向きの操作と同じ応答の並列の呼び出しに入れず、判定と操作を 1 つのスクリプトにする。

- 反映先の候補: issue-start と pr-finalize-loop に、fetch・件数の判定・push をまとめた同梱のスクリプト（0 件のときだけ push し、1 件以上なら 0 以外で止まる）を置く
- AGENTS.md「外向きの操作と破壊的な操作」の「呼び出しを分けて前段の成功を確かめる」に、同じ応答の並列の呼び出しは分けたことにならないことを足す
