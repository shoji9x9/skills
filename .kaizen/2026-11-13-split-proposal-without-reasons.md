# 作業中に見つけた問題を別の Issue に回すと提案するときに、今の作業に入れない理由を書かなかった

## 事象

Issue #1005 の box の eval を実行する前に、eval の sandbox の中からホームの認証情報（`~/.config/box/refresh_token`）が読めることを見つけた。
box の文書の変更を推奨したうえで、「sandbox から認証情報が読める点は別の Issue で扱う価値がある」と書いた。
今の作業（Issue #1005）に入れない理由は書かなかった。
利用者は「扱う価値があるなら #1005 で扱いたいが、難しいのか」と問い返した。
次の応答で、直す量は小さいが、隠す範囲の設計と CLI の起動の確認と検証の追加に手間がかかることを説明し、別の PR を勧めた。
その結果、別の Issue（#1008）にすると決まったが、判断の往復が 1 回増えた。

## 根本原因

- なぜ問い返されたか: 別の Issue に回す提案に、今の作業に入れた場合の量と分ける理由が無く、利用者は分ける必要があるかを判断できなかった。
- なぜ理由を書かなかったか: 見つけた問題が今の作業の受け入れ条件の外にあることを、分ける理由として十分だと考えた。利用者がそれを今の作業で扱いたいかを考えなかった。
- なぜそう考えたか（推測。transcript に、取り決めを参照した記録は無い）: 範囲の外の問題を別の Issue に回してよいという考え方を、利用者に提案する場面にも当てはめたと考える。近い取り決め（`pr-finalize-loop` の手順 4 の「直さない根拠」）は自律ループの中でレビューの指摘を見送る根拠で、利用者に選択肢を示す場面の書き方は決めていない。

## 根拠
