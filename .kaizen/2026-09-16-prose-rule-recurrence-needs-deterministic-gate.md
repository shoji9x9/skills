# 常時ロードの文章規約で防げなかった CLI フラグ誤用はフックで止める

## 事象

PR #379 のレビュー返信で `gh api ... --body-file <path>` を実行し `unknown flag: --body-file` で失敗した。
`-F body=@<path>` へ直して成功。これは [[2026-08-31-gh-api-has-no-body-file-flag]]（**`status: applied`**）の再発である。

## 根本原因

- なぜ再発したか? → 前回の恒久対策が `AGENTS.md` L118 への明記**だけ**だった
  - なぜそれが効かなかったか? → その行は正しく（`gh api` は `-F body=@<path>` か `--input <path>`、`--body-file` は `gh pr` / `gh issue` 側）、
    常時ロードされる基底ドキュメントにあり、今回もセッション文脈に入っていた。それでも違反した——**文章規約は確率的にしか効かない**
    - なぜ文章で止めようとしたか? → 前回の RCA が「**書かれていなかった**」を根本原因として止まり、
      「**書いても守られない**」層を測らなかった ← 根本原因（対策可能）

`SKILL.md`「基本原則」の「仕組みで解決する」（エージェントの挙動は確率論的なため決定論的なチェックを優先）に従えば、
**同じ規約の 2 度目の違反は、文章の追記ではなく決定論的なゲートへ上げる**のが正しい扱いになる。

横断スコープ: 配布スキル内の `gh` 例を走査し、`gh api` に `--body-file` を渡す記述が無いことを確認した（前回の確認結果を再検証）。
同型の「同じ用途でもコマンドごとにフラグ名・受理形が違う」危険は `--paginate`（`gh api` にはあるが `gh pr list` には無い）等にも残る。

## 提案

常時ロードの文章規約を破った失敗が再発したら、同じ規約を書き足さず決定論的なゲート（hook / lint）へ上げる。

- `PreToolUse(Bash)` フックを新設し、`gh api` を含む呼び出しで `--body-file` を検出したらブロックし、
  `-F body=@<path>` / `--input <path>` を案内する（`.claude/settings.json` の hooks。kaizen のコミット前ゲートと同じ配線）。
- **陰性コントロールと陽性コントロールの両方を実測する**——`gh api ... --body-file` がブロックされること、
  `gh pr create --body-file` / `gh issue create --body-file` が通ること。後者が通らないゲートは正当な用法まで塞ぐ。
- 判定は素朴な文字列一致にせず、同一呼び出し内に `gh api` が現れる場合だけに限定する
  （`gh pr create` と `gh api` を `&&` で繋いだ呼び出しでは、どちらのフラグかを引数の位置で判定する必要がある）。
- 自己設定ファイルの編集がガードでブロックされる場合は、適用内容を一時ファイルへ書き出してユーザーへ `cp` を依頼する
  （`AGENTS.md`「エージェントの自己設定編集について」）。
