# 識別子を取り出す正規表現の境界を、レビューの指摘ごとに 1 方向ずつ直し、4 回の反復を使った

## 事象

PR #691（#662）で、GHSA の id を取り出す正規表現の境界を、レビューの指摘を受けるたびに書き換えた。
最初は境界が無かった。`\b` を付け、先読みと後読みに替え、前の `-` を拒んでから、前の `-` を許す形に戻した。
どの回も、指摘された 1 つの形（後ろの `-`、`_`、前の `-`、数字）だけを直し、反対側（前と後ろ・ghsa_id の欄と via の文字列）を確かめなかった。
そのたびに次のレビューが反対側の食い違いを指摘し、pr-finalize-loop の反復の上限 5 回のうち 4 回をこの論点に使った。
上限で止まった後、利用者の決定で、文字の種類 × 位置 × 呼び出し元の表を PR に書いてから 1 回で直した。
前後の判定を同じ文字の集合（英数字・`_`・`-`）にそろえ、`via` の文字列だけは全体が id のときに読む形にした。

表を決めて直した後も、手元のレビューを 6 回繰り返した。
2 回目の指摘（`é` が隣にあると取り出す）を受けて、前後の判定を Unicode の文字の種類に広げた。
すると 3 回目で、`u` フラグによる `ſ` と `s` の照合、結合文字、全角のハイフンの食い違いが指摘され、ASCII に戻した。
4 回目からは、変異がどの文字まで確かめるかの指摘が続いた。

## 根本原因

1. なぜ反復が続いたか → 直した後の境界が、直していない側で新しい食い違いを生んだ。
2. なぜ食い違いを生んだか → 境界の文字の種類（英字・数字・`-`・`_`）と位置（前・後ろ）と呼び出し元（title・ghsa_id・via）を表にせず、指摘された 1 つの組だけを直した。
3. なぜ表にしなかったか → `.agents/rules/state-space-and-mutation-proof.md` の「入力を解析する処理は、入力の文法が許す形から状態を挙げる」は、新しく書く処理を想定した規則で、レビューの指摘で境界を足すときに当てる手順として読まなかった ← 根本原因
4. 表を決めた後に反復が続いたのはなぜか → 表に無い文字の種類（ASCII の外）を指摘されたとき、表に行を足して期待値を決める前に、指摘の形に合わせて実装を広げた。

## 提案

識別子を取り出す正規表現に境界を足すときは、境界の文字の種類（英字・数字・区切りの記号・`_`）× 位置（前・後ろ）× 呼び出し元の表を作り、各セルの期待値を決めてから 1 回で直す。

- 反映先の候補: `.agents/rules/state-space-and-mutation-proof.md` の §6「レビューの指摘は、同じ種類の誤りをまとめて探す」に、境界を変える指摘では反対側の位置と他の呼び出し元を同じ表で確かめる、と 1 行足す。
- 表を決めた後の指摘が表に無い軸（文字の範囲など）を持ち込んだら、実装を変える前に、その軸を表に足して期待値を決める。
  入力の実際の範囲（pnpm audit は ASCII）で範囲を閉じ、閉じたことを表に書く。
- KEDB 照合: `正規表現`・`境界`・`レビュー` で一致なし。
