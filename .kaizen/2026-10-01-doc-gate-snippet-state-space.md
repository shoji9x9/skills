# 手順書に埋め込むチェックのシェル断片も状態空間を先に列挙する

## 事象

PR #541 で parity-diff の preflight.md に「新側のバージョンの一致」の照合スクリプト（撮る前に止めるチェック）を書いた。
初版は 7 状態だけ実測して出し、Copilot レビューが 1 周ごとに別の抜けを 1 件ずつ見つけた。見つかった順に次のとおり。

1. 一括再検証の照合相手（commits.after）
2. 停止分岐が exit 0
3. 固定 URL target の commit_check
4. commit_check の出力先が無い
5. パイプで終了コードが隠れる
6. SHA 形式未検査・commit_check 無しの配信型

/pr-finalize-loop の上限 5 周を使い切り、2 回目のループが要った。途中、commit_check を
「url_command の target だけのキー」と消費側の文書（capture-new.md）から断定して見送り、定義の原本
（replace-strategy の project-config.md）で誤りと分かって訂正した。

再発（2026-10-18、PR #694）: issue-batch の orchestration.md に、Issue の間の依存の扱いを場合の表（依存の向き × 着手済みか × 判断が決まったか）から書いた。
push 前のレビューで、表の軸に無かった 2 つの場合が見つかった。依存先が複数あって状態が割れる場合と、依存先が merge の後に止まる場合である。
シェル断片ではなく文章の取り決めでも、軸に件数（1 件・複数）と時点（ある工程の前か後か）を入れなかったため、同じ形の抜けが出た。

同じ PR で、code-review --fix が「依存先の変更が base にあれば入力の順を確かめない」を 1 つの箇条にだけ足した。
着手の条件と表は依存先の状態だけを見たままで、次のレビューで同じ軸（変更が base にあるか）の抜けが 2 件出た。
状態の組み合わせを箇条ごとに足すと、新しい軸を 1 か所に足すたびに他の箇条と食い違う。判定の軸（ここでは「変更が base にあるか」）を 1 つの条件として先に置き、箇条はその例外として書くと揃う。

その後も、指摘を直すたびに規定を足した（base の再取得、PR を経ずに解決した依存先の案内、状態を進める時点）。
足した規定のそれぞれに新しい指摘が付き、反復ごとの指摘が 10・9・8・10 件と減らなかった。判定を「PR が base branch に MERGED か」の 1 つに削ると、足した規定から出た指摘がまとめて消えた。

再発（2026-10-18、PR #695）: 最終報告の前に読み直す記録に「manifest に残したローカルレビューの結果」を足したが、manifest に書いてよい項目の一覧にその項目は無かった。
参照を足すときに、参照先（manifest の項目の一覧）を開いて実在を確かめなかった。状態の列挙とは別の機序で、提案の最後の箇条はこの事象から来ている。

同じ PR #695 の 2 回目と 3 回目の反復でも、指摘に応えて文を足した（BLOCKED の条件、承認を得た形の並べ方）。次の回に、足した文から指摘が出た。

再発（2026-10-21、PR #745）: issue-batch の prepare.md に、prepare のコメントを決定として読む条件と、記録を覆す条件を書いた。
軸（書いた人の権限 × 記録の前か後か × コメントか本文か × 編集・削除）を先に表にせず、レビューの指摘ごとに規定を足した。
反復ごとの指摘は 10・10・10・4・6・2 件で、足した規定（編集の時刻で比べる・本文の中身と照合する）のそれぞれに次の指摘が付いた。
判定をコメントの作成者・作成日時・`lastEditedAt` と本文の `lastEditedAt` の時刻だけに絞ると、指摘が減った。

## 根本原因

- なぜ抜けが 1 件ずつ出たか → 入力の軸（target の種類 × 照合相手の出所 × コマンドの成否・出力形式）を書く前に列挙せず、思いついた状態だけを実測した
- なぜ列挙しなかったか → `.agents/rules/state-space-and-mutation-proof.md` は paths が `scripts/**` と `skills/*/scripts/**` に限られる。
  そのため、`skills/*/references/**` の Markdown に埋めたシェル断片の編集では読み込まれない
- なぜ断片を対象外にしていたか → チェックを「スクリプトファイル」として扱った。手順書の中の実行可能な断片も、判定できないときは失敗にするという同じ取り決めに従うことを想定していなかった
- 付随: 設定キーの適用範囲を、定義の原本ではなく消費側の 1 行から推した

- 付随（PR #695）: 参照を足すときに、参照先（manifest の項目の一覧）を開いて実在を確かめなかった

## 根拠

同じ原因での再発を確かめた（PR #694 と同じく、状態の軸を列挙する前に規定を箇条ごとに足し、判定を少ない軸に削るまで指摘が減らなかった）。
Issue #933 でも同じ原因で再発した（「再発の記録（#933）」）。

## 既存の規約

- 扱い: 強制なし
- 場所: `AGENTS.md`「確かめ方」（新しく作った分岐や、新しく受け付ける入力は、その状態を実際に作って確かめる）と `.agents/rules/state-space-and-mutation-proof.md`
- 照合した範囲: `AGENTS.md`・`docs/agent-workflow.md`・`.agents/rules/` を「状態を実際に作って」「状態を列挙」で検索した。規約は常に読み込まれる場所に言い切る形であり、同じ原因で再発を繰り返し、手順書のシェル断片の状態を確かめる機構は無い

## 提案

手順書（references/*.md）に停止・合否を決めるシェル断片を書くときは、書く前に入力の軸（対象の種類・比較相手の出所・外部コマンドの成否と出力形式）を表にし、各軸の「読めない」を含めて全状態を実測してから出す。

- state-space-and-mutation-proof.md の paths に skills/*/references/** を足す（または同ルールに「手順書のチェック断片も対象」と明記する）
- 設定キーの適用範囲（どの target が持つか等）を述べる前に、定義の原本（project-config.md 等）を読む。消費側の文書の記述から断定しない
- KEDB: 2026-09-21-check-written-to-fit-the-fixture（形式の原本から起こす）と同系
- 状態の扱いを決める文章の取り決め（依存・停止・除外）も対象にする。表の軸には、利用者が指定した軸に加えて、件数（1 件・複数）と時点（merge などの工程の前か後か）を必ず入れる
- 状態の組み合わせを箇条ごとに足さず、判定の軸（例: 依存先の変更が base にあるか）を 1 つの条件として先に置き、箇条と表はその条件を満たさないときの扱いとして書く。軸を足したら、その軸を参照すべき箇条・表・確認・状態図をすべて grep で挙げて同時に直す
- 指摘を直す反復で指摘の件数が減らないときは、規定を足す前に、判定を 1 つの条件に削れないかを先に考える。規定を足すと、その規定の分だけ次の指摘の範囲が広がる
- 参照を足すときは、参照先の一覧（manifest の項目・状態図）を grep で開いて実在を確かめる

## 再発の記録（#860）

2026-11-05、issue-batch の run の #860 で、issue-create の `references/split.md` に、失敗した起票で Issue が作られたかを確かめる `gh issue list` の断片を書いた。
入力の軸（対象のリポジトリ・前からある同名の Issue・件数の上限・タイトルの文字）を表にせずに書き、Copilot のレビューが 2 巡続けて直させた。
1 巡目は `--repo` が無い・前からある同名の Issue と区別できない・件数の上限、2 巡目は絞り込んだ後の件数で打ち切りを判定できない・タイトルを jq のプログラムに埋め込んだ、である。
どちらの巡の指摘も、断片の入力の軸を先に表にしていれば書く前に拾えた形だった。

## 再発の記録（#937）

2026-11-08、#937 で issue-create の `references/parent.md` に、子の Issue の親を確かめる `add_sub_issue` の断片を書いた。
親の状態（無い・同じ・別）の 3 つだけを実測して出し、親を識別する軸（リポジトリ・名前の大文字と小文字）と、外部コマンドの出力の軸（成功したときの標準エラー）を表にしなかった。
push 前の code-review が、番号だけで比べること・`--parent` の値の形・標準エラーが値に入ることを指摘し、直した後に大文字と小文字の抜けも見つかった。
同じ issue-create の references の断片で、#860 に続く再発である。
実測した状態は正しい入力の分岐だけで、「同じだと判定する条件」の軸は挙げていなかった。

## 再発の記録（#933）

2026-11-08、#933 で kaizen の `references/extract.md` に、既存の規約を照合する grep の断片を書いた。
終了コードの意味と `-r`・`-R` の違いを実測せずに書き、ローカルのレビューで 2 回直した。
1 回目は `-r` がシンボリックリンクをたどらないこと、2 回目は BSD grep の `-R` がたどらないことと、当たりなしと存在しないパスが同じ終了コードになることだった。
最後に `find -L` で 3 つの状態（当たりあり・当たりなし・パスが無い）を実測してから書き直した。
