# issue-batch の run を無人で始める前に、ホストがスリープしない設定かを確かめ、止まった時間を記録から見分けられるようにする

## 事象

issue-batch の run（#678 の PR #716 の反復 5）で、手元のレビューを任せたサブエージェントとメインのセッションが、2026-10-19 19:00 UTC から 22:58 UTC まで約 4 時間止まった。
サブエージェントの記録では、19:00:54 に API の応答が始まった直後（出力 3 トークン、stop_reason なし）から何も届かず、22:58:43 にハーネスが「応答が途中で切れた」として要求を送り直していた。
メインのセッションにも同じ時間帯の記録が無く、バックグラウンドの CI の待機の完了も届いていなかった。
Windows のイベントログには、19:00:55 にスリープに入った記録（Kernel-Power の Id 42）と、22:57:44 に復帰した記録（Power-Troubleshooter の Id 1）があった。
利用者は run の前に「しばらく応答できなくなる」と伝えていたので、その間は無人の実行が進む前提だった。

## 根本原因

- なぜ止まったか: ホストの PC が電源の設定でスリープし、WSL とその中のセッション・サブエージェント・バックグラウンドのコマンドがすべて止まった。
- なぜ事前に防げなかったか: issue-batch の preflight は、認証・権限・設定・transcript などのソフトウェアの前提を確かめるが、無人の実行を続けられる実行環境（スリープ・画面ロックでの停止）を確かめる項目が無い。
- なぜ原因の特定に時間がかかったか: 止まったことは、利用者が「サブエージェントが今動き始めた」と伝えるまで分からなかった。止まった理由を、記録の時刻の空白と Windows のイベントログを突き合わせて初めて特定した。エージェントは `powershell.exe` をガードで実行できず、利用者に実行してもらう必要があった。

## 提案

issue-batch の run を無人で始める前に、ホストがスリープしない設定かを確かめ、止まった時間を記録から見分けられるようにする。

- issue-batch の全体 preflight の「run の前に利用者の判断が要るもの」の確認に、無人で実行する間ホストがスリープしないか（電源につないだときのスリープの設定、PowerToys Awake などの使用）を 1 項目として足す。エージェントが設定を変えず、利用者に確かめてもらう。
- 最終報告に、セッションの記録で長い空白（例: 30 分以上）があった時間帯を載せる。利用者が止まったことに気付けるようにする。
- Windows の WSL では、スリープの記録を確かめるコマンド（`Get-WinEvent` の Kernel-Power の Id 42 と Power-Troubleshooter の Id 1）を、調べ方として参照できるところに置く。
