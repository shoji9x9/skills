# eval の without_skill ベースラインは read 汚染を防止・検知してから弁別を測る

## 事象

replace-strategy の回帰評価 iteration-5 で、without_skill（baseline）の 3 run すべてが、
使い捨てプロジェクト外にある本リポジトリの skills/replace-strategy/（SKILL.md・references・assets）を
自発的に発見・参照して回答した（eval-7/9 は result.json で明言、eval-8 は生成物の
テーブル見出しがテンプレートと一字一句一致）。全 assertion を baseline も満たし、
Pass Rate の Delta +0.00 は弁別測定として無効になった。

**2026-07-29 に再発（Issue #146 の回帰評価）。** replace-strategy eval-11 の without_skill run-1 が、
スキル未設置にもかかわらず `dependency_policy` の三値契約・各 references キーの読み手・空値の枠の目的を
正確に再現し 4/4 で pass した（弁別ゼロ）。使い捨てプロジェクトは空（`project-tree.txt` は `.` のみ）で、
ハーネスの設置漏れではない。

**このとき汚染経路を実測で確定した。** ハーネスの `SKILL_EVAL_RUNNER` に bwrap ラッパー
（`--dev-bind / / --tmpfs <リポジトリの親ディレクトリ>`）を渡して同一プロンプトを再実行すると、
baseline はスキル資産を発見できず 0/4 へ落ちた（`grep` でファイルシステム全体を探索した旨を自ら報告）。
汚染経路はローカル作業ツリーの read であり、隔離すれば弁別は回復する。

**2026-07-29 に 3 度目の再発（Issue #145 の回帰評価）。今回は遮断を最初から入れていたのに 2 経路で汚染した。**

- **経路 A: 並列実行中の兄弟 run。** 4 並列で回したため、`without_skill` の run から同時刻の `with_skill` の
  使い捨てプロジェクト `/tmp/skill-eval-<skill>-*/.claude/skills/<skill>` が読めた。baseline 10 本すべてが対象で、
  eval-5 は `/tmp` の同名ディレクトリ 4 件を列挙し、eval-15 は「スキルの同梱ドキュメントの規約に基づいて回答します」と
  明言して**未コミットの規約**をそのまま再現した（GitHub 経由では取得できない ＝ ローカル読み取りの確証）。
- **経路 B: WSL の `$HOME` ミラー。** `--tmpfs <repo の親>` で本リポジトリを隠しても
  `/mnt/wslg/distro/home/<user>/projects` から同じ木に到達できる。eval-15 はこの経路で別プロジェクトに
  インストール済みの**旧版**スキルを読み、旧規約を根拠に回答した（誤った baseline になる。単なる汚染より悪い）。

**2026-07-29 に 4 度目の再発。3 段の遮断を入れていたのに汚染した。**
parity-diff の回帰評価（Issue #147）の eval-7 baseline が、`normalize.md` の機械分類規則（`absorbed_T` の判定）・
`component_diff_exceptions` の全フィールド・別プロジェクトの実測値（フォントのサブセット差の実例と件数）を再現し、
「shoji9x9/skills#147 で起票済み」とまで述べた（Issue 本文は未コミットでローカルにしか無い）。
作業ツリー・`/tmp` の兄弟 run・WSL ミラーの 3 段は効いており、経路は **`~/.claude/projects`**（過去セッションのトランスクリプトとメモリ）だった。
遮断を広げて取り直した baseline は独自スキーマを創作し、契約とは逆の結論を出した（弁別が回復した）。

## 根本原因

- なぜ baseline がスキルを参照できたか? → run-skill-eval.sh の使い捨てプロジェクトは
  cwd と skill 設置有無を隔離するが、claude -p はマシン上の任意パスを read でき、
  prompt 中のスキル名から探索してリポジトリ本体を発見できる
- なぜ防げなかったか? → 公正性の根拠が「親に .claude/skills が無い」（docs/skill-development.md）
  のみで、read 面の隔離も汚染検知も設計されていない
- なぜ設計されなかったか? → 「エージェントが自発的にスキルソースを探索する」経路が
  想定・検証されていなかった ← 根本原因

3 度目（2026-07-29）で分かった、より深い層:

- なぜ遮断を入れたのに汚染したか? → 遮断対象を「リポジトリのパス 1 点」として設計した
  - なぜ 1 点で足りると考えたか? → 2 度目に確定した汚染経路（作業ツリーの read）を経路の**集合**ではなく
    経路そのものと同一視した
    - なぜ同一視したか? → 塞ぐべきは「対象資産へ到達できる全経路」で、経路はハーネス自身（並列 run が
      同時に作る一時ディレクトリ）も OS（bind mount ミラー）も作る、という視点が無かった ← 根本原因

4 度目（2026-07-29）で分かった、さらに深い層:

- なぜ 3 段でも足りなかったか? → 経路の集合を「**スキルソースの所在**」で列挙したから
  - なぜ所在で列挙したか? → 隠すべき対象を「ファイル」と捉えていた
    - なぜか? → 守るべきは**内容**であり、内容の二次的な保管庫（自エージェントの会話ログ・
      別エージェントのセッション記録）も経路である、という視点が無かった ← 根本原因

`AGENTS.md`「等値比較を『正規化』で直すときは、両辺がズレうる軸を列挙して同じ正規化を両辺に当てる」と同型の失敗
（片側・一軸だけの対処が、別の軸が効いた瞬間に同じ故障へ戻る）。

関連: [[2026-07-23-eval-assertion-discrimination]]（アサーション設計の弁別）とは別機構。
アサーションを skill 固有にしても read 汚染下では baseline が満たしてしまう。

## 提案

読み取りを遮断する隔離は、隠す対象をパス 1 点で決めず、**対象資産へ到達できる経路を列挙して塞ぎ、遮断できたことを実測で確認してから測る**。スキル eval の without_skill ベースラインはこの遮断（または汚染検知）を経てから弁別（Delta）を測り、汚染した run の Delta は無効として benchmark に明記する。

- run-skill-eval.sh: without_skill 実行時に使い捨てプロジェクトの settings で
  スキルソース（本リポジトリ配下）の Read を deny する、または実行後に result.json /
  生成物へスキルソース参照・テンプレ一致がないかの汚染検知を組み込む
- docs/skill-development.md: 「公正なベースライン」の記述に read 汚染の限界と
  汚染検知の採点手順を追記する
- 横断スコープ: 本ハーネスで測定する全スキルの benchmark に共通（過去の Delta も
  汚染有無は未検証）。採点者（grader）にも「baseline がスキル資産を参照した形跡」の
  確認を標準項目にする

2026-07-29 の実測を踏まえた具体化:

- **遮断は `SKILL_EVAL_RUNNER` で実装できる**（ハーネス本体を変えずに検証済み）。without_skill では既定で
  サンドボックス経由の runner を使い、リポジトリを `--tmpfs` で隠す。bwrap が無い環境はフォールバックし、
  遮断できなかったことを run に記録して汚染検知へ回す
- **汚染が疑われる baseline は、遮断した環境で再実行して切り分ける**（run を捨てる前に経路を確定させる）。
  汚染した run は `grading.json` を置かず集計から除外し、benchmark.md に経緯（汚染の根拠・再実行の結果）を残す
- **残る穴を明記する**: 対象リポジトリが PUBLIC の場合、`gh` / WebFetch 経由でスキル本文を取得する経路は
  ローカル遮断では塞げない。採点時に「baseline 応答がスキル固有の語彙・契約を再現していないか」を確認する項目は残す

2026-07-29（3 度目）の実測を踏まえた具体化:

- **ラッパーは 3 段で組む**（bwrap）: `--tmpfs <repo の親>`（作業ツリー）＋ `--tmpfs /tmp --bind "$PWD" "$PWD"`
  （並列実行中の兄弟 run を隠し、自分の使い捨てプロジェクトだけ残す）＋ `--tmpfs /mnt/wslg --tmpfs /mnt/c`（OS ミラー）。
  **`/mnt` 全体を覆ってはいけない**——`/etc/resolv.conf -> /mnt/wsl/resolv.conf` が切れて `API Error: ENOTIMP` になる。
- **並列実行するなら `/tmp` 隔離を必須にする。** 隔離しないなら configuration ごとに逐次実行する
  （`with_skill` の使い捨てプロジェクトはスキルの完全なコピーであり、同時刻に `/tmp` へ露出する）。
- **遮断の検証は 2 段**: (1) サンドボックス内で対象パスを `ls` して 0 件であること、(2) run 後に応答・成果物へ
  スキル固有マーカー（`references/<name>` / 同梱スクリプト名 / `SKILL.md` 等）を grep して 0 件であること。
  (1) だけでは別経路を見落とす（3 度目はこれで見落とした）。
- **旧版を読む汚染は「弁別ゼロ」より悪い**。別プロジェクトのインストール済みコピーは変更前の規約を持つため、
  baseline が旧規約を根拠に「正しい」と答え、**変更を否定する誤った対照**になる。

2026-07-29（4 度目）の実測を踏まえた具体化:

- **ラッパーは 4 群で組む**（bwrap）。既存 3 群に「**エージェントの記録**」を足す:
  `--tmpfs ~/.claude/{projects,sessions,file-history,shell-snapshots,plans,tasks,paste-cache,backups,downloads,cache}`
  ＋ `--ro-bind /dev/null ~/.claude/history.jsonl` ＋ `--tmpfs ~/.codex` ＋ `--tmpfs ~/.copilot`
  ＋ `--tmpfs ~/.agents` ＋ `--tmpfs ~/.vscode-server`。
  `~/.claude/{settings.json,.credentials.json,plugins,skills,session-env}` は残す（消すと CLI が起動しない）。
- **遮断の検証はパスの列挙ではなく内容の grep で行う。** サンドボックス内で
  `grep -rl "<スキル固有の語>" ~` が 0 件になるまで塞ぐ（今回はこれで `~/.codex` → `~/.copilot` の順に発見した）。
  列挙して確認する方式は、**列挙から漏れた経路を原理的に検出できない**（3 度目の (1) はこれで見落とした）。
- **横断スコープ**: 同じ穴は「ローカルの記録を読ませずに測る」全ての比較測定（プロンプト A/B・モデル比較・
  エージェント間比較）に効く。会話ログを持つエージェントを増やすたびに遮断対象も増える。
