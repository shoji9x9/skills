# `pkill -f` は自分の呼び出しコマンドラインにも一致する

## 事象

止まった headless Chrome を落とすために `pkill -f "dump-dom"; ...; pgrep -af "dump-dom"` を実行したところ、
ツール呼び出しが exit 144 で失敗した。`pkill -f` の照合対象は full command line で、
このコマンドを実行している `bash -c ...` の行にも `dump-dom` が含まれていたため、pkill が自分のシェルごと殺した。

同じセッションで起動した python http.server は PID を保存し `kill $(cat $SB/p1)` で止めており、そちらは問題なく終了している。
プロセスを指す手段が、片方は PID、もう片方はパターンで揃っていなかった。

## 根本原因

AGENTS.md には「破壊的操作は allowlist で対象を定め、破壊フラグなしで対象と件数を確認してから実行する」があるが、
プロセス終了系がこのクラスだと結び付かなかった。規律が想起させるのは `rm` や API の一括削除で、
`pkill` の「破壊フラグなしの確認」にあたる `pgrep` との対応が書かれていない。
さらに `pkill -f` 固有の性質（自分のコマンドラインにも一致する）はどこにも明文化されていなかった。

横断スコープ確認: リポジトリ内のコミット済みスクリプト（`scripts/**` / `skills/**`）に `pkill` / `killall` の使用は無い（grep で 0 件）。
射程は検証時にその場で組むコマンドであり、決定論的な lint ではなく基底ドキュメントの規律で塞ぐ。

## 提案

プロセスを落とすときは、自分で起動したものは PID を保存して `kill "$PID"` で撃ち、パターンで撃つ場合は先に `pgrep -af` で対象と件数を確認する。

AGENTS.md の「破壊的操作は allowlist で対象を定め、破壊フラグなしで対象と件数を確認してから実行する」の直後へ次を足す。

- **プロセス終了（`pkill` / `killall`）も破壊的操作として扱う**。自分で起動したプロセスは起動時に PID を保存し
  `kill "$PID"` で落とす。パターンで撃つのは PID を保持していない場合だけにし、その前に `pgrep -af <pattern>` で
  対象と件数を確認する。**`pkill -f` の照合対象は full command line なので、そのコマンドを実行している自分のシェルにも一致する**。
  症状は非 0 終了だけで、対象が死んだのか自分が死んだのかは出力から読めない。
  パターンが自分のコマンドラインに現れない形（`[d]ump-dom` 等）にするか、PID 指定へ切り替える。

## 再発（2026-09-12）

同じセッションで、`pkill -f 'remote-debugging-port=9222'` を使って headless Chrome を落とそうとし、
再び自分のシェルごと落ちた（exit 144）。直前まで PID を保存して `kill "$CHR"` で止めていたのに、
まとめて片付ける段で手段がパターンへ戻った。

- なぜ 1: 「後片付け」は対象を列挙せず一括で済ませたくなる。
- なぜ 2: PID を保存していたのは同じコマンド内の起動だけで、片付けは別のツール呼び出しに分かれていたため
  変数が残っておらず、パターンで撃つしか無いように見えた。
- なぜ 3: 起動と後片付けが別呼び出しに分かれる場合に PID をどこへ残すかの規律が無い。

提案を強化する: 起動と後片付けが別のツール呼び出しに分かれるなら、PID をファイルへ残して
`kill "$(cat <file>)"` で撃つ。パターンで撃つ場合は `pgrep -af` で対象と件数を確認し、
**自分の呼び出しが一致しないことまで確かめてから** `pkill` を使う。
