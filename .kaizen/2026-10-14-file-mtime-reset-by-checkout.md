# git で管理するファイルの古さを、ファイルの更新時刻で判定しない

## 事象

Issue #630 で、collect が読む記録のファイルを「名前の時刻か更新時刻が範囲の中」で選ぶ修正を、`/code-review --fix` が入れた。
測り直すと、clone や worktree を作った直後はすべてのファイルの更新時刻が今になり、古いファイル 4,000 個でも旧版と同じ 1,350ms かかった。
issue-batch は Issue ごとに worktree を作り直すので、この使い方では上限が機能しない。
最後の行の `observed_at`（ファイルの末尾だけを読む）で判定する形に替え、261ms になった。

## 根本原因

1. なぜ更新時刻を使ったか → 「checkout や merge は今の時刻にするので、更新時刻は中の行を書いた時刻より前にならない」という性質だけを見た。
2. なぜ足りなかったか → 判定の向き（新しすぎる側の誤り）を確かめず、clone・worktree の作成で全ファイルが今の時刻になる状態を、測定の入力に入れていなかった。
3. なぜ入れなかったか → 測定の fixture をその場で作ったので、更新時刻はいつも「今」になり、古い更新時刻の場合だけが測られていた ← 根本原因

## 提案

git で管理するファイルの古さや新しさは、更新時刻ではなく、ファイルの名前か中身（記録した時刻）で判定し、clone した直後の状態を測定の入力に入れる。

- 横断スコープ: `skills/agent-usage/scripts/lib/collect.mjs` のキャッシュの指紋も更新時刻を使うが、ログのファイル（git の管理外）なので当たらない。
