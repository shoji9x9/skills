# 変異実証は「書いたテストが効く」しか示さないので、列挙の実証にはならない

## 事象

`auto-wait-check.mjs` の字句層と受け側解決層を書き直し、テスト 51 件 green と
判定行 9 箇所の変異実証（全 RED）を通して「検証済み」としたが、その後 2 つの独立した
レビューが **9 件の実在する silent under-report** を出した。

- 字句: 制御構文の頭を閉じる `)` の後の正規表現、値で終わる `}` の後の正規表現（JSX）
- 照合: チェーン**途中**の関数呼び出し、添字アクセス、引数に関数型を持つ戻り値注釈
- 集計: 重複引数で走査ファイル数が二重計上

## 根本原因

1. なぜ取りこぼしたか → テストの状態空間を、3 つの Issue が挙げた形と自分が思いついた
   壊れ方から作った。
2. なぜそこから作ったか → **変異実証を「検証が十分である証拠」として扱った。**
   変異実証は**書いたテストが効いている**ことだけを示し、**書かなかった入力クラス**は測らない。
3. なぜ混同したか → 既存ルールは「文法が許す形から列挙する」と定めているが、
   **列挙したことをどう示すか**を定めていない。変異実証には示し方（RED になる）が
   あるので、そちらだけが実証の形として残った。← 根本原因

KEDB 照合: `.kaizen/2026-09-12-parser-state-space-from-grammar.md`（**applied**）が
横断スコープで `scripts/auto-wait-check.mjs` を名指ししており、**予告されたファイルでの再発**。
今回の 9 件のうち 6 件は「前トークンで分岐する字句」と「チェーンの位置で分岐する照合」で、
**分岐の軸が「値」ではなく「位置」**だったのに、テストは値（入力の形）だけで並べていた。

横断スコープ: 同じ形の器が `scripts/lint-pagination.js`（シェル文法）、
`parity-component/scripts/css-rules-capture.mjs`（CSS セレクタ）、`coverage-expand.mjs` にもある。

## 提案

位置で分岐する走査器・照合器は、分岐の軸ごとに取り得る位置を表にして各セルに 1 件ずつ入力を置き、その表をテスト側に残す。変異実証を列挙の代替にしない。

反映先: `.agents/rules/state-space-and-mutation-proof.md` の「3. テストが効いていることの示し方」へ
次の 2 点を追加する。

- **変異実証は列挙の実証ではない。** 全変異が RED になっても、それは書いたテストが判定行に
  到達している証拠でしかない。書かなかった入力クラスはどの変異でも赤くならない。
- **分岐が「入力の値」ではなく「入力の位置」で決まる器は、位置の軸を先に列挙する。**
  字句なら「直前に来られるトークンの種類を全部」、チェーン照合なら「先頭・途中・末尾」。
  軸を表にして `test.each` の第 1 引数へ残すと、埋まっていないセルが読める。

## 再発（2026-09-17, claude-code, #331 / #347 の PR レビュー 2 巡目）—— 表を書いても軸の値が欠けていた

### 再発の事象

`pending-triage-check.mjs` に `parity-component` の帰属検査を足すとき、**本記録の提案どおり
状態空間の表を書き、変異実証も 2 通り（分岐を殺す / 全スキルへ広げる）行った**。それでも codex レビューが
同じ関数の穴を出した——`added_by` が**読めない**要素（欠落 / `unknown` / 未知のスキル名）は検査を素通りし、
機能 slug でない `slug` がそのまま帰属として信用され、全機能で `warn` のみ・exit 0 のまま永久に棚卸しされない。

同じ巡で `baseline.md` にも同型の指摘が出た。`name` の一意性を**兄弟の範囲（同じ `parent`）でだけ**要求していたため、
祖父が違えば同名の器を 2 行書け、その子の `parent` 文字列が曖昧になる（3 段目以降で `parent` を持たせた意味が失われる）。

### 再発の根本原因

- なぜ表を書いたのに漏れたか → 表の軸を `added_by ∈ {parity-component, その他のスキル}` × `slug` で引いた。
  **`added_by` が「読めない」は軸の値として立てていない**（欠落は `slug` の軸でだけ列挙していた）
  - なぜ立てなかったか → 帰属を決める入力を `slug` だと思っており、`added_by` は
    「形の不備として報告する項目」の扱いだった。**判定に効く入力なのに、軸ではなく検査項目として見ていた**
    - なぜそう見えたか → 本記録の提案が「位置の軸」を例に挙げているため、
      **軸＝判定に使う全入力**という一般形まで戻らず、例に当てはめて終わった ← 根本原因

`baseline.md` の方も同型で、一意性の**スコープ**という軸（兄弟 / 機能全体）を立てずに、
「重複」という値の軸だけを列挙していた。

### 再発への提案

**状態空間の軸は「判定に使う全ての入力」で引き、各軸に必ず「読めない（欠落・空・型崩れ・未知の値）」を含める。**

- 片方の入力の欠落だけを列挙して、もう片方の欠落を落とさない。
  **判定式に現れる識別子を機械的に列挙して軸にする**（`slug` だけでなく `added_by` も）
- **一意性・スコープを要求する規則は、その「範囲」自体を軸にする**（兄弟 / 親 / 全体）。
  部分スコープの一意性は、参照が名前で行われる限り深さが増えた瞬間に壊れる
- 反映先: `.agents/rules/state-space-and-mutation-proof.md`「1. 状態空間に入れるもの」へ上の 2 点を足す
  （「3. テストが効いていることの示し方」ではなく列挙側の節。表を書く前に軸を決める話なので）

## 3 件目（2026-09-18, claude-code, #377 の PR レビュー 3 巡目）—— 変異で赤くなった件数を数えていなかった

### 3 件目の事象

レビュー指摘に沿って「複合コマンドからは読み取りの証拠を採らない」判定を足し、**除外側のケースを 5 件書いて**
全 green、さらに判定行を殺す変異も実行して「RED になった」ので実証済みとした。

**赤くなったのは 5 件中 1 件だけだった。** 残り 4 件（`test -f X && cat X || echo absent`、
`printf '%s' 'note; cat X'`、`echo $(cat X)`、`test -e y && cat X`）は**先頭語が `test` / `printf` / `echo` で、
制御フロー判定の手前にある「先頭コマンドが読み取りユーティリティか」の規則で落ちていた**。
つまり、新しい判定行を守るテストは実質 1 件しか無く、レビュー指摘そのものの形は 1 つも守っていなかった。
先頭語が読み取りユーティリティで**かつ**制御フローを含む形（`cat X && echo done` / `cat X; echo done`）を
足して初めて 3 件が赤くなった。

### 3 件目の根本原因

- なぜ気づかなかったか → 変異の結果を**真偽（赤が出たか）**で読み、**どのテストが赤くなったか**を見なかった
  - なぜ真偽で読んだか → 本記録の既存の提案は「変異は書いたテストが効く証拠でしかない」と
    **変異の限界**を述べるが、**変異の出力から何を読むか**を定めていない
    - 結果として「RED が 1 件でも出れば実証」という運用になり、**判定行より手前の規則で落ちているケース**を
      その判定行のテストだと誤認した ← 根本原因（対策可能）

判定が直列に並ぶ器（前段のフィルタ → 新設の判定）では、前段で落ちる入力を後段のテストとして書いても、
後段を殺す変異では赤くならない。**green も RED も同じに見える**ので、件数を突き合わせないと気づけない。

### 3 件目の提案

**変異実証は「赤が出たか」ではなく「どのテストが何件赤くなったか」で読む。** 判定行を守るつもりで書いたケース数と
赤くなった件数が一致しないなら、差分のケースは別の規則で落ちている。

- 反映先: `.agents/rules/state-space-and-mutation-proof.md`「3. テストが効いていることの示し方」へ足す
- 文面の骨子: 変異を当てたら**赤くなったテスト名を列挙して、その判定行のために書いたケースと突き合わせる**。
  一致しないケースは**前段の規則で落ちている**ので、前段を通過してその判定行に到達する入力を作り直す
- **直列に並ぶ判定は、後段のテストに「前段を通過する」条件を明示的に持たせる**
  （本件なら「先頭語が読み取りユーティリティであること」）
