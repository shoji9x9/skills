# 振る舞いの比較の入力を、テストの入力だけから作らない

## 事象

Issue #759 で github.mjs の `collectExternalCi` を分けたとき、check run の行と commit status の行を 1 回の `push` にまとめた。
旧版は check run の行を足してから statuses を取得していたので、statuses の取得だけが失敗しても check run の行は残っていた。
新版では、statuses の取得が失敗すると `push` まで進まず、その PR の check run の行も消える。
サブエージェントは旧版と新版を同じ入力で 509 回比べて「すべて一致」と報告した。
しかし入力はテストの入力で、statuses の取得だけが失敗する状態は一度も作っていなかった。
commit の前に、別のサブエージェントがコードを読んでレビューしたときに見つけた。

## 根本原因

- なぜ比較で見つからなかったか → 比較の入力をテストの入力から作ったので、テストの無い分岐（取得の途中での失敗）を通らなかった
- なぜテストの入力から作ったか → 指示書は「担当のテストが使う入力をすべてと、引数や入力の誤りを含む呼び出し」と書いていた。外部の呼び出しが途中で失敗する状態を入力の軸に挙げていなかった
- なぜ軸に無かったか → 関数を分ける作業では、例外を捕まえて処理を続ける範囲（`attempt`・`try`）の中で、副作用（行の追加）と失敗しうる呼び出しの順序が振る舞いになる。この点を指示書の型（#758 から使っているもの）に書いていなかった ← 根本原因

## 根拠

- 旧版: `git show 6a6bb872:skills/agent-usage/scripts/lib/sources/github.mjs` の 560〜620 行。外側の `rows` に check run の行を足した後で `statuses` を取得する
- 新版で足したテスト「外部の CI: commit status の取得だけが失敗しても、取得できた check run の行は残し、失敗を記録する」は、直す前のコードで `expected [] to deeply equal [ 'ci-ext:2' ]` で失敗した

## 提案

関数を分ける作業の指示書の「振る舞いの比較」に、例外を捕まえて処理を続ける範囲（`attempt`・`try`）ごとに、範囲の中の外部の呼び出しを 1 つずつ失敗させる入力を作って比べることを足す。

- 指示書の型は scratchpad にしか無く、セッションが終わると消える。#760 の前に、型を `docs/`（関数の大きさの違反を直す手順）に置くかを決める
- テストが無い分岐を見つけたら、比較だけで済ませずテストも足す（今回はテストを足した）
