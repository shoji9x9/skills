# エージェントが issue-batch の判断待ちを Issue の語のまま示したので、利用者が選択肢の意味を 3 回聞き返した

## 事象

issue-batch の最終報告で、#733 の判断待ちを「A: 一般の規則にする」「B: Kaizen の記録の特例を残す」と示した。
利用者は、レビューの範囲をなぜ最後だけ指定するのか、「一般の規則」「別の commit にする」「Kaizen の記録の特例」が何を指すのかを聞き返した。
さらに、Issue が扱うレビューを `pr-finalize-loop` のレビューと取り違えていた。
3 回の説明の後、利用者は A と B のどちらでもない案（Kaizen の学びだけを例外にする）を選んだ。

2026-11-11 に、Issue #565 の設計で同じ形が再発した（確認のツールは AskUserQuestion）。
エージェントは tester.army/e2e の扱いを 3 回続けて聞いた。
1 回目は「見送る」「任意にする」の 2 択で、見送ったときに E2E を何で書くかを書かなかった。
2 回目は、Playwright と chrome-devtools MCP がこのリポジトリでどう位置付けられているか（必須の前提か、設定を配るか）を調べずに聞いた。
3 回目は、「スイートが 2 つになる」理由と、e2e を必ず使う選択肢を示さずに聞いた。利用者は質問を却下し、内容を明確にしたいと答えた。
その後、利用者は、スタイルを再現しないリプレイスでは e2e を使い、従来のリプレイスは Playwright のままにする住み分けを自分で示した。

## 根本原因

- なぜ聞き返されたか → 選択肢の名前が、Issue の本文と manifest の中でだけ通じる語だった
- なぜその語のままだったか → 最終報告の判断待ちを、manifest の `pending_decisions` の `topic` と `options` から書き写した。
  manifest は作業中の自分が読むための記録で、今の手順（何をどの順でしているか）を前提に書いている
- なぜ前提が抜けたか → issue-batch の最終報告の取り決めは「論点・選択肢・推奨・決まった後に残る作業」を求めるだけで、選択肢が変える手順の前後を書くことを求めていない
- なぜ別の案が出なかったか → 選択肢を Issue が挙げた形から作り、利用者が今の手順を知った上で別の形を考えられる材料（今の順序と、それぞれの段の理由）を示さなかった
- 2 件に共通する原因 → 選択肢を示す前に、選択肢ごとに「選ぶと何がどう変わるか」と、推奨の理由になる事実を書くことを求める取り決めが無い。
  確認の手順（各スキルの `references/user-confirmation.md`）は判断の材料を確認の中に入れることを求めるが、材料に何を含めるかは各スキルに任せている。
  #565 では加えて、利用者が比べる相手にしている既存のツールの位置付けを調べていなかった。利用者がそのツールを使いたいのか、評価だけを求めているのかも、先に確かめていなかった

## 根拠

利用者の 3 回の質問が、すべて語の意味と今の手順を尋ねていた。今の手順を 6 段の順序で示した後に、利用者が自分で別の案を出した。
KEDB 照合（「判断待ち」「最終報告」「選択肢」）で一致したのは `2026-10-14-issue-batch-mid-run-user-questions.md` だけだった。これは run の途中の確認を扱う別の学びである。

確信度を high にした理由: 2026-11-11 の再発を、この学びの根本原因（選択肢が変えることを書かずに示した）と読み比べ、同じ原因だと確かめた。
Issue #565 での再発は、利用者が 3 回目の質問を却下し、その後に自分で住み分けの案を示したことで観測した。
KEDB 照合（「選択肢」と「AskUserQuestion」・「推奨」・「位置付け」）では、この学びのほかに 2 件が当たった。
`2026-10-16-ask-user-question-language-unchecked.md` は確認の文の言語を扱い、原因が違う。
`2026-09-23-recommend-before-precedent-survey.md` は applied で、前例を調べずに推奨したことを扱う。

## 既存の規約

- 扱い: なし
- 場所: なし。近い規約は 2 つある。`AGENTS.md`「確かめ方」の「方針・配置の選択肢を人に示す前に、公開済みの解と元の意図を調べて添える」は、前例を調べることを求める。各スキルの `references/user-confirmation.md`「確認のツールで聞く」は、判断の材料を確認の中に入れることを求める。どちらも、選択肢ごとに選ぶと何が変わるかを書くことは求めていない
- 照合した範囲: 「選ぶと」「選んだ後」「選択肢ごと」「判断の材料」で検索した。
  対象は `AGENTS.md`・`docs/`・`.agents/rules/`・`skills/issue-start/`・`skills/issue-batch/`・`skills/kaizen/references/user-confirmation.md` である

## 提案

選択肢を人に示すときは、選択肢ごとに「選ぶと何がどう変わるか」と推奨の理由になる事実を書き、比べる相手の既存のツールの位置付けを調べて添える。

- 置き場所の候補は 2 つある。`AGENTS.md`「確かめ方」の選択肢の箇条に足すか、各スキルの `references/user-confirmation.md`「確認のツールで聞く」の判断の材料の項に足す
- issue-batch の最終報告の判断待ちでは、今の手順と選んだ後の手順の違いを選択肢ごとに書く。Issue を読まなくても分かる文にする
- 利用者が名前を挙げたツールの扱いを聞くときは、使いたいのか評価だけかを先に確かめる

書いた後に、`writing-style` の規則 10（名詞句と総称が何を指すかがその文の中にあるか）で、選択肢の名前を読み直す。
