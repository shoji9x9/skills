# 別のスクリプトからコピーしたコメントの主張を、新しい出力先で成り立つか確かめずに残した

## 事象

Issue #870 で、`kaizen-context-inject.sh` のパスの書き分け（`\` を `\\` と書く）と、そのコメント「表示から元の値を一意に戻せる」を `kaizen-schedule-report.sh` に持ち込んだ。
新しい出力先は GitHub の表で、コードスパンの外のセル（優先度・種別・記録日）にも同じ関数を当てていた。
コードスパンの外では GitHub が `\\` を `\` と表示するので、コメントの主張はこの 3 列で成り立たない。
code-review が指摘し、コメントを直した。

## 根本原因

1. なぜ誤ったコメントが残ったか → 元のスクリプトのコメントを、主張ごとコピーした
2. なぜ確かめなかったか → 元の出力先（コードスパンの中の 1 行）と新しい出力先（表のセル。コードスパンの中と外がある）の違いを挙げなかった
3. なぜ挙げなかったか → rule の「既存の実装から条件をコピーするときは出力の性質を突き合わせる」を、条件にだけ当て、コピーしたコメントの主張には当てなかった ← 根本原因

## 根拠

確信度の理由: 1 回の観測だが、コピーしたコメントを新しい出力先で確かめなかったことに原因を絞れている。
code-review（`--fix`）が、表のコードスパンの外の 3 列でコメントの主張が成り立たないことを指摘した。
KEDB 照合: 「コピー」「コメント」「出力の性質」で一致なし。「書き写」「コメント」は `2026-10-14-worktree-bash-literal-guard-recurs.md` に当たったが、別の事象である。

## 提案

既存の実装から処理をコピーするときは、条件に加えて、一緒にコピーするコメントの主張（「一意に戻せる」「1 行に収まる」など）も、新しい出力先の性質ごとに成り立つかを確かめる。

- 適用先: `.agents/rules/state-space-and-mutation-proof.md` の「既存の実装から条件をコピーして揃えるときは…」の節に 1 文を足す
- 出力先が複数の性質を持つ（Markdown のコードスパンの中と外など）なら、性質ごとに主張を確かめる
