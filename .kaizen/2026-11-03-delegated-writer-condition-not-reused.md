# 「別の書き手が書く」として処理を外す条件を、書き手が実際に書く条件から作らなかった

## 事象

Issue #871 で、collect が別の作業ツリーのブランチの行を外す条件を、PR が閉じたか（GitHub の状態）から作った。
local レビューが、取得の範囲より前に merge したブランチ・GitHub でない origin・同じ名前の別の PR・判断の無いブランチで、行がどの記録にも書かれないことを指摘した。
外した行を書くのは別の作業ツリーのコミットの前の確認で、その確認は判断（decisions.json）と branchMerged で記録するかを決めている。条件をそこから作り直して直した。

同じ PR #873 の反復 4 で、外す条件を gate の判定から作り直したときに、gate が判断を決める順（ブランチの判断、defaultDecision、人の設定の有無）のうち、ブランチの判断だけを使った。
このリポジトリは defaultDecision: record で動き、decisions.json にブランチの判断が無いので、修正が実際には機能していなかった。
local レビューが、この PR の記録に #868 の行が入ったことで指摘した。

再発（2026-11-06、Issue #708・PR #919）: `reinstall-skill.sh` に、ミューテーションテストのランナーのロックの持ち主が生きているかを確かめる判定を足した。
ランナーの判定（`readLockPid`・`alive`・`lockOwnerAlive`）を呼べないので、シェルで書き直したが、ランナーの分岐を表にしなかった。
手元のレビューが、復元情報（1 回目の前）・PID 0（1 回目）・桁あふれの PID（2 回目）・EPERM（3 回目）の食い違いを 1 つずつ指摘した。
EPERM は最初「起きにくい」として見送ったが、3 回目に同じ指摘が出て、`ps -p` で判定する形に直した。

## 根本原因

1. なぜ取りこぼしたか → 外す条件が、外した行を書く側（別の作業ツリーのコミットの前の確認）の条件と一致していなかった
2. なぜ一致しなかったか → 書く側が記録しない場合を、利用者に示した選択肢（merge 後に記録しない）から 1 つずつ足し、書く側のコードを読まなかった。
   読んだ後も、書く側の関数を呼ばず、読んだ内容から条件を書き直したので、分岐の一部（defaultDecision）を落とした
3. なぜ読まなかったか（1 回目） → state-space-and-mutation-proof.md の「判定を他に任せて自分では落とさない緩和は、任せる先も挙げて判定の式に含める」は、実装の途中で設計を決める会話の段では参照されない ← 根本原因
4. なぜ呼ばなかったか（2 回目） → 書く側の判定（gate.mjs の resolveDecision）が、記録するかと Hook の出力（止める理由の文）を 1 つの関数で返し、判定だけを呼べる形になっていなかった ← 根本原因

## 根拠

確信度は high（同じ PR の中で、同じ原因で 2 回起きた）。
PR #873 の local レビューの 1 回目の 1・4・5 件目の指摘が、どれも書く側の判定（branchMerged・判断）との食い違いから出た。branchesRecordedElsewhere に置き換えて 3 件を同時に直した。
4 回目の 1 件目の指摘も、書く側の判定（gate.mjs の resolveDecision の defaultDecision）を落としたことから出た。
KEDB 照合は「既存の判定」「agent-usage」と「任せる先」「判定」で、どちらも一致なし。

- 2026-11-06: 同じ原因（呼べない既存の判定を、分岐を表にせずに書き直した）での再発を #708 で確かめた。

## 提案

処理を「別の書き手が後で書く」として外すときは、その書き手が実際に書くかを決める既存の関数をそのまま呼ぶ。呼べなければ、その関数の分岐をすべて表にしてから条件を作る。

- 反映先の候補: state-space-and-mutation-proof.md の「判定を他に任せて自分では落とさない緩和」の節に、選択肢を示す前（設計の段）にも当てることを 1 行足す
- 反映先の候補（根本原因 4）: 判定と出力を 1 つの関数で返している書き手は、判定だけを返す関数を切り出し、出力はそれを呼ぶ側で作る。agent-usage では、gate.mjs の resolveDecision・status の branchDecisionText・merged.mjs の decidedToRecord が同じ判定を別々に持つ
