# 止まっている子プロセスは経過時間で判断せず、stderr と出力サイズで待機理由を確定する

## 事象

parity-suite の eval 実行が 3 回連続でハングし、約 25 分を消費した。
前景 Bash のツール timeout 2 回（6分40秒 / 10分）で切り捨てられ、3 回目で `kill -9` して
ようやく stderr を開いた。そこに答えが 1 行で出ていた:

```text
Reading additional input from stdin...
```

raw trace は 0 バイト。codex は起動しており「生きて」いたが、stdin から追加入力を
読もうとして EOF を待ち続けていた。プロンプトは引数で渡していたので入力は不要だった。

## 根本原因

- なぜ待ち続けたか → `scripts/run-skill-eval.sh` が executor の stdin をリダイレクトせず、
  呼び出し側の stdin をそのまま継承した。バックグラウンド Bash / エージェント経由では
  EOF しないパイプなので、codex は永久に待つ
- なぜ今まで顕在化しなかったか → 対話 TTY からの手動実行では stdin が TTY で即座に扱われ、
  この経路でしか再現しない ← 根本原因（`run-skill-eval.sh` の欠陥。`</dev/null` を追加して修正済み）
- なぜ診断に 25 分かかったか → 「重い run なのだろう」と経過時間で解釈し、待機・再投入を
  繰り返した。stderr と出力サイズを見たのは 3 回目 ← 第二の根本原因（診断手順が無い）

既存の [[2026-08-25-background-job-liveness-not-output-file]] は「生きているか死んでいるか」を
扱うが、本件は**生きているが永久にブロックしている**形。`pgrep` は「実行中」と答え、
経過時間は「遅い」としか言わないため、どちらの材料でも区別できない。
[[2026-08-31-detached-launch-exit-code-and-source-of-truth]] も近縁だが、あちらは
終了コードが仕事の成否を表さない形で、本件は終了しないこと自体が症状。

横断スコープ: `scripts/` で子プロセスを起動するのは `run-skill-eval.sh` だけで、修正済み。
`eval-sandbox.sh` はその子として起動されるため、上位の `</dev/null` で覆われる。

## 提案

`AGENTS.md`「ワークフロー」節の「切り離した仕事の生死は…プロセスの実在で判定する」の直後に追記する。

- **止まって見える子プロセスを経過時間で判断しない。** 生死（`pgrep`）は「動いているか」しか
  答えず、ブロックと処理中を区別しない。最初に見るのは stderr の最終行と出力サイズで、
  「何を待っているか」を確定してから待つ・落とす・直すを選ぶ。
  出力 0 バイトのまま無応答は、処理中ではなく入力待ちの疑いが濃い。
- **切り離して起動する子プロセスの stdin は明示的に `/dev/null` へ倒す。**
  引数でプロンプト・入力を渡していても、CLI が stdin も読む実装は珍しくない。
  対話 TTY では即座に EOF/TTY 扱いになり顕在化せず、非対話・背景実行でだけ無限待機になる。
