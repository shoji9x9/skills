# 外向きの操作の前提にする lint は、出力を tail に通した終了コードで判定せず、lint 自身の終了コードを保存してから分岐する

## 事象

Issue #677〜#681 を起票するとき、本文の lint と起票のスクリプトを `lint-prose.ts <files> 2>&1 | tail -2 && bash issues-create.sh` とつないだ。
lint は指摘 1 件で 0 以外を返したが、`&&` が見たのは `tail` の終了コード 0 だったので、指摘が残ったまま 5 件の Issue を起票した。そのうち #678 の本文を、起票した後で直すことになった。

2026-11-16 に PR #1066 を作るとき、同じ形で再発した。
PR の本文の lint・ベースの遅れの確認・push・`gh pr create` を `lint-prose.ts <本文> 2>&1 | tail -1 && ... && gh pr create` とつないだ。
lint は長すぎる文の指摘 1 件で 0 以外を返したが、`&&` が見たのは `tail` の終了コードだったので、push と PR の作成まで進んだ。PR の本文を、作った後で直した。

## 根本原因

- なぜ指摘が残ったまま外に出たか → `&&` の左辺の終了コードは、パイプの最後のコマンド（`tail`）のものだった
- なぜ tail に通したか → 出力を短くしたかった。AGENTS.md「シェルの書き方」の「パイプでつないだ検証の成否は `${PIPESTATUS[0]}` か `set -o pipefail` で取る」を、外向きの操作の前提の判定に当てていなかった
- なぜ当てなかったか → 外向きの操作を `&&` でつなぐ規約（「外向きの操作と破壊的な操作」）だけを意識し、前のステップがパイプのときの判定を同じ箇条で思い出す手がかりが無かった ← 根本原因（対策可能）

## 根拠

確信度は high である。同じ原因（lint の出力を `tail` に通し、`&&` で外向きの操作につないだ）での再発を、このノートの根本原因と読み比べて確かめた。
2 回目は、PR を作った後に lint を単独で実行し直して、終了コード 1 と指摘 1 件を確かめた。PR の本文はその後に直した。
KEDB 照合では「tail・PIPESTATUS」「パイプ・終了コード・&&」で照合し、このノート（forgotten）が一致した。忘却の前提が成り立たなくなったので pending に戻す。

## 既存の規約

- 扱い: 強制なし
- 場所: `AGENTS.md`「シェルの書き方」の「パイプでつないだ検証の成否は、`${PIPESTATUS[0]}` か `set -o pipefail` で取る」と、`docs/agent-workflow.md` の同名の節
- 照合した範囲: `AGENTS.md`・`docs/agent-workflow.md`・`scripts/hooks/bash-command-guard.sh` を「PIPESTATUS」「tail」で読んだ

## 食い違い

- 相手: なし
- 判断: なし

## 提案

外向きの操作（Issue・PR・コメントの作成、push）の前提にする lint は、`lint >log 2>&1; rc=$?` で終了コードを保存し、`if [ "$rc" = 0 ]` で分岐してから外向きの操作に進む。

- 適用先: `AGENTS.md`「外向きの操作と破壊的な操作」の「順序のある外向きの操作は `&&` でつなぐ」の箇条に、前のステップがパイプなら終了コードを保存してから分岐することを足す。外向きの操作を書く時点で読む箇条に置き、「シェルの書き方」の規約を思い出す手がかりにする。
- 機構の効果と費用: 効果は、同じ形で 2 回外に出たこと。費用は、パイプと `&&` の組み合わせをシェルの構文を解析せずに見分ける規則になる。
  `scripts/hooks/bash-command-guard.sh` は「この Hook に規則を足さない」と決めており、誤検知と見逃しが書き方の数だけ出る。
  そのため、Hook は作らず文書の追記で終える。3 回目が起きたら、外向きの操作のスクリプトの中で本文の lint を実行する形を検討する。
