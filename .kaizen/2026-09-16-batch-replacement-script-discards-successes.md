# 一括置換スクリプトは、不一致がどこか分かり成功分を捨てない形で書く

## 事象

PR #390 のレビュー対応で、`coverage-expand.mjs` へ 5 件の置換を行う python スクリプトを書いたところ、
`oxfmt` が `??` 演算子を複数行へ折り返していたため 1 件が不一致で AssertionError。
書き込みが末尾にあったので、成功していた 4 件も含め全置換が破棄された。
`assert` にラベルが無く、エラーは行番号だけだったので、`sed` でスクリプトを読み返してどの置換かを
特定する必要があった。最終的に、先に問題の 1 件を実ファイルから取り直して適用し、
残りをラベル付き `assert` で書き直して通した。

2026-09-18 に再発。今回は **`assert` にラベルを付けていた**（`assert s.count(old) == 1, (old[:50], s.count(old))`）ので
どの置換が落ちたかは即座に分かったが、書き込みが末尾 1 回のままだったため**先行する 8 件の置換がすべて破棄**され、
全件を書き直して再実行した。不一致の原因は前回と同じく `oxfmt` の整形で、1 行だった `BAD_CONFIGS` の要素が
複数行オブジェクトへ展開されていた。

## 根本原因

- なぜ置換が一致しなかった? → 直前の `oxfmt` が `??` を折り返し、自分が書いた字面と変わっていた
  - なぜ気付かなかった? → 整形後に読み直さず、記憶から置換元を組み立てた
    （KEDB 直撃: [[2026-09-12-format-then-patch-stale-string]]、`status: applied`、`AGENTS.md` に反映済みの再発）
- なぜ 1 件の不一致が全体の手戻りになった? → 複数の置換を 1 スクリプトにまとめ、
  書き込みを末尾 1 回にしていた——途中で落ちると成功分もメモリ上で消える
  - なぜどこで落ちたか即座に分からなかった? → `assert` にラベルを付けていなかった
    ← 根本原因（対策可能。整形だけでなく、他のセッションの編集・レビュー適用でも起きる）
- なぜラベルを付けても損失したか（2026-09-18 の再発）→ 提案が 2 つの対策を**並列**で示していたため、
  安い方（ラベル）だけを守り、高い方（書き込みの粒度）を「今回は不一致しないだろう」と判断して飛ばした
  ← 根本原因（選択肢を並べる規約は、安い方だけを採る道を残す）

横断スコープ: 本セッションで同じ形の python スクリプトを 6 回使っており、うち 2 回が同じ形で落ちた。
対象は特定パスに閉じない（全ファイル編集）ので rule ではなく基底ドキュメント向き。

## 提案

複数の文字列置換を 1 スクリプトにまとめるなら、**置換ごとに書き込む形を既定**にする（末尾 1 回の書き込みは、全件が一つの原子単位であるべき場合に限る）。

2 つの対策を並列に置いた前回の提案は効かなかった（安い方だけが守られた）ので、既定と例外の形に書き替える。
`AGENTS.md` の「文字列一致で編集するときは〜」の項目へ次を追加する:

- **置換ごとに書き戻す**（`p.write_text(s)` を各置換の直後に置く）。落ちても成功分は残り、再実行は
  残りだけで済む。末尾 1 回の書き込みにしてよいのは、**途中状態がファイルとして不正になる**など
  全件が一つの原子単位であるべき場合だけで、そのときは理由を 1 行書く
- 各 `assert` にはどの置換か分かるラベルを付ける（`assert s.count(old) == 1, '<置換名>'`）。
  行番号だけの AssertionError は、どの置換が古いのかをスクリプトを読み返すまで特定できない
- 「今回は不一致しないだろう」で粒度を落とさない。**整形を挟んだ直後は特に外れる**
  （[[2026-09-12-format-then-patch-stale-string]] が `applied` でも再発している）
