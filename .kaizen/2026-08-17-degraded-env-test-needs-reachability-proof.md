# 人工的に劣化させた環境で縮退経路を検査するときは、到達性と「その終了コードになった理由」まで主張する

## 事象

Issue #202 で、jq / python3 が無い環境の縮退経路を検査する vitest を追加した。
制限 PATH を作る際にスクリプトが使う dirname を入れ忘れたため、ゲートは
commit 判定に到達する手前で「bundled kaizen-status-check.sh is unavailable」として
exit 2 していた。期待値 2 のケースは全て pass したが、主張は空だった
（.pending-extract を置いたセットアップは死んでいた）。コードレビューで発覚。

実測: dirname なし exit=2（unavailable）/ dirname あり exit=2（本来の kaizen ブロック）。

## 根本原因

- なぜ空の主張が pass したか → exit code 2 だけを見て、ブロックの理由を見なかった
  - なぜ理由を見なかったか → 終了コードが目的の分岐に固有だと暗黙に仮定した。
    実際には fail closed のゲートは複数の地点で 2 を返す
    - なぜ仮定したか → 「環境を作れたこと」の陽性コントロール（jq/python3 が
      見えないこと）は書いたが、「作った環境で対象コードが目的地点まで到達したこと」の
      検証を書かなかった。既存規律は陽性コントロールを検出器の検出能力について
      述べており、人工的に劣化させた環境の到達性は射程外 ← 根本原因（対策可能）

横断スコープ: 同ファイル内の他 2 例は到達性を主張できていた——sed シムは callLog で
代理が実際に使われたことを、スクリプトスタブは固有 stderr を確認している。
正しい前例が 20 行上にあったが規律として一般化されていなかった。
scripts/*.test.js 内で欠陥があったのは今回追加した箇所だけ。

KEDB 照合: [[2026-08-03-detector-nonzero-hits-not-proof]]（applied）と同型で、
「観測値が出た＝証拠」の代用。当該ノートは検出器の件数を扱い、
本件は多義的な終了コードと人工環境の到達性という派生形。applied のため追記せず恒久側を強化する。
[[2026-08-12-eval-prompt-change-breaks-assertion-reachability]]（pending）も到達性だが、
射程は skills/*/evals/** のプロンプト編集で、機構が異なる。

## 提案

人工的に劣化させた環境（PATH シム・スタブ・モック）で縮退経路を検査するときは、環境を
作れたことに加え、対象コードがその環境で目的の分岐まで到達したことを主張する。終了コードの
ように複数の理由で同じ値になるシグナルは、理由（stderr の識別可能なメッセージ等）まで固定する。

AGENTS.md ワークフロー節の陽性コントロール行を拡張する:

- 環境を削って縮退経路を通す検査は、削った依存の欠落が対象コードを目的地点より
  手前で落とし、期待どおりの終了コードを別の理由で出す。削ってよいのは検査対象の
  依存だけで、対象コードが使う他の依存は通す。
- fail closed の仕組みは複数地点で同じ非ゼロ終了コードを返す。「止まったこと」ではなく
  「意図した地点で止まったこと」を、識別可能な出力で主張する。
