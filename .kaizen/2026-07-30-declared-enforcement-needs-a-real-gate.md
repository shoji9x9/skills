# 「規約ではなく仕組みで縛る」と書いたら、その強制点を実装して破れないことを実証する

## 事象

Issue #160 で `parity-diff` のインスタンス例外に「件数を畳まない」規律を入れた。
`references/normalize.md` にはこう書いた——**「命名規約ではなくスキーマで縛る」**（守られなくても検出手段が無い規約は実際に守られなかった、という反省を根拠として明記した）。
そのうえで「インスタンス件数を畳まない」を SKILL.md・`normalize.md`・`diff-template.md`・テンプレート `_note` の 4 箇所に書いた。

ところが**強制点を実装していなかった**。`/code-review` が検出した実態は次のとおり。

- `matchException` は `page` / `state` / `viewport` の欠落を「どの値にも合う」と解釈し、`element: "none"` を match-all として扱っていた
- そのため `page` / `viewport` を省き `element: "none"` にした**1 エントリが、別ページ・別状態の 2 件を警告なしで吸収**した（実測で再現）
- つまり「スキーマで縛る」と宣言した当の規律が、スキーマ側（コード）からは破れる状態で出荷されかけた

同じ PR にはもう 1 件、同型の抜けがあった（こちらも `/code-review` が検出）。
`validateExceptions` は「`slug` 不一致は照合に使わない」という fail-closed を**実装はしていたが警告を出さず**、
`accepted_exceptions.unresolved` に 0 が記録され `diff.md` にも不整合が載らなかった——
`normalize.md` が「黙って吸収しない・黙って捨てない」と宣言していたのに、黙って捨てていた。

## 根本原因

- なぜ穴が開いたか? → 規律を**散文で 4 箇所に書いたこと**を「縛った」と見なした
  - なぜそう見なしたか? → 記述量（4 箇所）を強度の代理指標にしていた。実際に効くのは 1 箇所のコードだけである
    - なぜ強制点を確かめなかったか? → 「規約ではなく仕組みで縛る」と**宣言した側の文章を、自分の実装の検査項目に落としていない**。
      宣言は意図の表明であって、強制の有無とは独立に書けてしまう ← 根本原因

`docs/skill-development.md`「push 前の整合パス」項目 3 は「ルール記述 ↔ 強制ゲートのスコープ一致」を扱うが、
**強制ゲートが既に存在する前提**で走査スコープ（glob・条件）の一致だけを見る。
今回は「強制ゲートを実装しないまま宣言だけした」ケースで、項目 3 の網に掛からなかった。

KEDB 照合: [[2026-07-30-negative-result-checks-need-positive-control]]（applied）が「陰性結果を合格根拠にしない」を、
[[2026-06-09-intra-doc-consistency-pass]] が同一ドキュメント内の自己整合を扱う。
本件は「**宣言と強制の乖離**」で、どちらの網の外側にある新しい穴。

## 提案

**規律を「仕組みで縛る」と宣言したら、宣言と同じ変更の中で強制点を 1 つ特定し、陽性・陰性コントロールで実証してから確定する。**
散文の箇所数は強度ではない——効くのは強制点だけである。

1. **強制点を名指しする**。「この規律を破ろうとしたとき、どのコード・lint・hook が落とすか」を 1 つ挙げられるか確かめる。
   挙げられないなら、それは規約であって仕組みではない。散文にそう書く（「規約なので守られなくても検出できない」）か、強制点を実装する
2. **陰性コントロールで破ってみる**。規律に違反する最小入力を作り、実際に落ちる（＝吸収されない・警告が出る・非ゼロ終了）ことを実測する。
   **同時に陽性コントロールも通す**——正当な入力が通ることを確かめないと「全部落とすだけの検査」と区別できない
3. **fail-closed は「落とす」だけでなく「見える」まで作る**。黙って捨てる実装は、機械可読値（件数・カウンタ）に 0 を記録し、
   レポートにも載らないため、収束判定や status の側から検証不能になる。落とした事実を stderr / カウンタ / レポートのいずれかに必ず出す
4. **既存の宣言も棚卸しする**。「〜で縛る」「〜しない」と書いた箇所を grep し、強制点の有無を 1 件ずつ確認する（横断スコープ確認）

**適用済み**: `docs/skill-development.md`「push 前の整合パス」項目 3 を拡張し、スコープ一致の前に「強制点が実在するか」「陰性・陽性コントロールで実証したか」「fail-closed が見えるか」を確かめる段を足した。
`.agents/rules/` にはしない——対象を特定パスに絞れない一般規律であり、パス限定ルールでは確定ロードされないため。
