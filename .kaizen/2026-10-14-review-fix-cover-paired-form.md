# レビューの指摘を直すときは、指摘の例の対になる形も当て、既存の字句の解析を通して直す

## 事象

PR #627 の 5 回目の指摘（二重引用符の中の `$(git commit)` を見逃す）を、生の文字列への正規表現で直した。
そのため単一引用符の中（展開されない）も git commit と判定し、grep や gh の本文で Hook が止める回帰を入れた。
同じ反復で `pushd` を `cd` と同じに当てたが、`popd` を戻さず、`pushd x && popd && git commit` の cwd を誤った。
差分だけのレビューで両方が見つかった。

## 根本原因

- なぜ回帰したか: 指摘の例（二重引用符・`pushd`）だけを通す形で直した
- なぜ例だけを通したか: 対になる形（単一引用符・`popd`）を挙げず、既存の `splitCommands` が持つ引用符の文脈を使わずに、外から正規表現を足した
- なぜ挙げなかったか: rule の §6 は「同じ種類の誤りを探す」とは言うが、「直す変更が新しく通す・新しく当てる入力（対の形）を挙げる」とは指摘の修正の節で言っていない。
  §3 の「誤検知を直す変更は緩和の新設」は誤検知の側だけである

## 提案

レビューの指摘を直すときは、指摘の例と対になる形（引用符の種類・push と pop・開始と終了）を挙げてテストにし、同じモジュールに既存の字句の解析があれば、新しい判定をその中に置く。

- 記述先: `.agents/rules/state-space-and-mutation-proof.md` の §6 に 1 項目足す
- 関連: `2026-10-13-source-lexing-use-existing-parser`（applied）
