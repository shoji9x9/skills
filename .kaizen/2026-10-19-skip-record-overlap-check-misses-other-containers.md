# 新しいレコードを読み飛ばす根拠に「本文が他のレコードと重なる」を使うときは、同じ本文を運びうる入れ物をすべて比べる

## 事象

issue-batch の #710 で、kaizen の候補のスキャナに Claude Code の `api-request-blob` を読み飛ばすレコードとして足した。
読み飛ばしてよい根拠として、blob の `user` の本文を `user` レコードの本文と比べ、重ならない分は `<system-reminder>` で始まるシステムの本文だと確かめた。
PR #711 の手元のレビューが、作業中に利用者が送った発話は `user` レコードにならず、`attachment` の `queued_command` と blob にだけ残ることを見つけた。
blob を読み飛ばすと、その発話の修正の指示が候補から外れていた。
`attachment` はすでに読み飛ばすレコードに入っていたので、blob がその発話を読む最後の入れ物だった。

## 根本原因

1. なぜ取りこぼしたか → 重なりを比べた相手が `user` レコードだけで、同じ本文を運ぶ別の入れ物（`attachment` の `queued_command`）を比べなかった。
2. なぜ比べなかったか → 「重ならない分はシステムの本文」と判断したのは、本文の先頭が `<system-reminder>` だったからで、その中に利用者の発話が包まれている形を想定しなかった。
3. なぜ想定しなかったか → 読み飛ばす変更を、これまでに読み飛ばしていたレコード（`attachment` など）が何を運んでいるかと合わせて確かめる手順が無かった ← 根本原因

## 提案

レコードやフィールドを読み飛ばす変更の根拠に「同じ本文が他にある」を使うときは、すでに読み飛ばしている入れ物も含めて、同じ本文を運びうるレコードの種類を一覧にし、各種類の中身を実データで確かめてから決める。

- 反映先の候補: `.agents/rules/state-space-and-mutation-proof.md` の「誤検知を直す変更は、それ自体が緩和の新設である」の節に、読み飛ばす変更の確かめ方として 1 行足す。
- 確かめ方の例: 比べる側の本文を部分一致で探し、どの種類のレコードに同じ本文があるかを数える。一致しない本文は、包む書式（`<system-reminder>` など）を外してからもう一度探す。
- KEDB 照合: 「重複」+「transcript」、「読み飛ば」+「scanner」で照合し、一致は無かった。
