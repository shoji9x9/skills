# 自分のツールが書く記録を読む検査は、書き手の不変条件を全部列挙して読み手で検証する

## 事象

PR #472（Issue #468）で、checkpoint.mjs の verify が読む checkpoints.json について、
Codex レビューが 6 巡にわたり 1 つずつ穴を指摘した: 対象 0 件の記録 / 前段を欠いた・順の違う記録 /
前の区切りから何も作っていない記録 / 削除だけで進んだ記録 / 定義と違う next_step / 重ねた引数の後勝ち。
いずれも record が決して作らない形を verify が受けていた。

## 根本原因

- なぜ 6 巡かかったか? → 1 巡ごとに指摘された 1 形だけを塞いだ
- なぜ 1 形ずつだったか? → 読み手の検証を「思いついた壊れ方」から書き、書き手（record）が保証する不変条件
  （順序・next_step・根の引き継ぎ・非空・進み）を列挙して読み手へ写す手順を踏まなかった
- なぜ踏まなかったか? → 読み手が「書き手と同じスクリプトの出力を読むだけ」なので形は信頼できると置いた。
  実際は手で直した・壊れた記録も同じ経路で読まれ、fail-closed なゲート（--from の再開判定）になる ← 根本原因

横断スコープ: 同 PR の table-upsert.mjs（引数の重複）も同じ形。
reaction-check / coverage-expand の conformance を読む --recorded 経路も、書き手の不変条件の写しになっているか要確認。

## 提案

ゲートが読む記録の検証は、書き手の不変条件を 1 行ずつ列挙し、全部を読み手で検査してから書く。

- 適用先: `.agents/rules/state-space-and-mutation-proof.md` §3（paths: `scripts/**` / `skills/*/scripts/**`）
- 書き手のコードから「必ずこうなる」を列挙（順序・列挙値・非空・前段との関係・派生値）し、
  各行に「読み手でどう落とすか」とテスト 1 件を対応づける。派生値（next_step 等）は保存値を信じず再計算して突き合わせる
- 引数パーサは値を持つ引数の重複を拒否するのを既定にする
- レビューが同じファイルの同じ読み手を 2 巡続けて指摘したら、個別修正をやめて不変条件の表を作り直す
