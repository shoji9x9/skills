# 規約の語彙は、事例の表面ではなく機序から作る

## 事象

Issue #376 の具体的な失敗は **`PATCH` / `DELETE` の要求単位**（移行元が選んだ行を 1 要求で送り、失敗すると全部戻す。
`:id` を経路に持つ口を子ごとに呼ぶ形では再現できない）だった。にもかかわらず、PR #379 で導入した「要求単位の根拠」の語彙を
**読み取り経路だけ**から作った——`実測` のソース形は `<読んだ入口の問い合わせ>＋<応答への写像>（母集合=… / 1 行=…）` の 1 つだけ。

結果、**書き込みの口の要求単位をフロント／ハンドラのソースで確定しても `実測` と書ける形が無く**、`推定` に留まるか、
より高価な実動作の観測へ押し上げられる（`SKILL.md`「厳守の制約」の階梯＝ソース < API 操作 < UI 操作に逆行）。
codex レビュー第 5 ラウンドで検出し、書き込みのソース形
（`実測: <読んだ要求の組み立て>＋<ハンドラの受け取りとトランザクション境界>（1 要求が扱う対象=… / 失敗時の巻き戻し範囲=…）`）を追加した。

### 2026-09-22 の再発（反対のツール側で同じ穴）

**規約がツール名で書かれていたため、同じ危険を持つ対の相手が素通りした。** AGENTS.md は
「oxfmt にディレクトリを渡さず対象ファイルを列挙する」「oxfmt には Markdown を渡さない」を持つが、
**対称側（`markdownlint-cli2` にディレクトリを渡す）は書かれていない**。

`pnpm exec markdownlint-cli2 --fix skills/parity-component/ skills/parity-suite/` を実行したところ、
markdownlint-cli2 はディレクトリ引数を配下の**全ファイル**へ展開するため、`.md` 以外まで `--fix` で書き換えた——
`.mjs` 10 本（JSDoc の開きが崩れ、乗算演算子の空白も詰められて構文が壊れた）、
`element.png` 16 枚（fixture の検査が「element.png が PNG でない」で 3 件 fail）、
eval fixture の `skills.yml` 8 本（MD034 でベア URL が角括弧付きに）。
`git restore` で全て戻したが、その前に `reinstall-skill.sh` を走らせていたため installed copy へも伝播していた。

**oxfmt 側の記録（`.kaizen/archive/2026-09-12-oxfmt-also-formats-markdown.md`、`status: applied`、同型 4 回）が
既にあったのに防げなかった**のは、そこで確定した規約が「oxfmt は」で始まっており、
機序（**整形ツールは引数で与えられた範囲を自分の判断で整形する**）に一般化されていなかったため。

## 根本原因

- なぜ片側だけの語彙になったか? → Issue が例として挙げた「入口の問い合わせを読んで母集合と 1 行の単位を書き出す」を、そのまま規約の語彙にした
  - なぜそうしたか? → 事例の**表面**（画面の入口クエリ）を抜き出し、**機序**（1 要求が何を原子的に変え、失敗時にどこまで戻すか）を抜き出さなかった。
    Issue 本文が機序まで書いていても、手順として真似しやすいのは表面のほう
    - なぜ気付かなかったか? → **読み取り側の例では規約が一応成立してしまう**ため、書き込み側を当てない限り穴が見えない ← 根本原因（対策可能）

KEDB: [[2026-09-01-matching-key-material-state-space]]（applied）は状態空間の列挙漏れで軸が近いが、あちらは**値とキーの材料**の話。
本件は**規約が導入する語彙そのものが片方向**だったケースで、列挙の対象が「入力の状態」ではなく「語彙の適用先」にある。

横断スコープ: `replace-strategy` の他の記録様式を当たった。「ページ要素の帰属」（対象／スコープ外の 2 値）・「静的資産の方針」（写す／同等物／写さない）・
「テーブルの記録先」（3 表）はいずれも反対側を持つ軸を明示して列挙しており、同型の片方向は見つからなかった。

## 提案

規約に語彙（根拠の形・記録項目・判定軸）を導入するときは、元になった事例の表面ではなく機序から作り、対称な反対側（読み取り↔書き込み、取得↔削除、成功↔失敗）を 1 件ずつ当ててから確定する。

- 当てた結果「**書ける形が無い**」側が出たら、それは**語彙の欠落**であって利用者の問題ではない。形を足すまで確定しない。
- 反対側を当てる作業は、事例が片側しか持っていなくても行う（事例に無いことは、その側が存在しない根拠にならない）。
- 語彙が階梯・優先順位を含むなら、**反対側でも同じ階梯が成立するか**を確かめる
  （本件は読み取り側のソース形しか無かったため、書き込み側だけが「ソースで足りるのに実動作の観測へ上がる」逆転を起こしていた）。

### 2026-09-22 の再発を受けた追加の提案

**規約を特定のツール名・特定の方向で書いたら、同じ危険を持つ対の相手を 1 件挙げてから確定する。**
挙げられないなら、それは対称側が無いのではなく確かめていない。

- AGENTS.md「リント／フォーマット」節の oxfmt 固有の注意を**整形ツール全般**へ一般化する——
  「整形ツールにディレクトリを渡さず対象ファイルを列挙する。ツールは引数で与えられた範囲を
  自分の判断で整形するので、対象外の種別が黙って書き換わる」。実例は両方向にある
  （oxfmt が `.md` の表を桁揃えし、markdownlint-cli2 が `.mjs` / `.png` / `.yml` を書き換えた）
- `scripts/bash-command-guard.sh` に 3 形目として**整形コマンドへのディレクトリ引数**を足す。
  既存 2 形（`gh api` に無いフラグ `--body-file`、文字クラスで自分を避けない `pkill -f`）と同じく、
  文章規約で防げず再発した形なので PreToolUse で止める。対象は `oxfmt` / `markdownlint-cli2` の
  書き込みを伴う呼び出しで、**通さねばならない入力**（ファイル列挙・`--check` のみ・
  lefthook が渡す staged file 列）を同数の陰性コントロールで固定する
