# 証拠を「取れる文字列を全部集める」形で設計したため、1 つの検出器に 3 つの誤判定が同居した

## 事象

Issue #377 で「with_skill の run が対象スキルを実際に読んだか」を判定する検出器
（`scripts/normalize-skill-eval-result.js` の `collectToolInputText` / `collectSkillPaths`）を書いた。
証拠の集め方を「ツール入力に現れる文字列を再帰的に全部集め、スキル配下のパスに一致するか」で設計したところ、
**1 つの関数に 3 つの別々の誤判定が同居した**。

| 誤判定 | 内容 | 見つけた経路 |
| --- | --- | --- |
| 偽陽性 | `Write` の `content` に書いたパスが「読んだ証拠」になる（baseline が計画文にパスを書くと `unexpected_read`） | commit 前のレビュー |
| 偽陽性 | スキル名の前方一致（`box` が `.claude/skills/boxes/` に一致） | 自分で状態空間を数え直したとき |
| 偽陰性の裏返し | ツール記録を持たない trace で `toolInputTexts: []` を返し、「測れなかった」が「読まなかった」と**測定された**値になる | 自分のテストが赤くなったとき |

3 件とも実装直後のテストは green だった。私が書いたテストが、私が想定した軸しか通っていなかったため。

## 根本原因

1. なぜ 3 つ出たか → 証拠の集め方を「取れるものを全部集めてから照合する」で設計し、
   各フィールドの**意味**（著述なのか読み取りなのか、名前なのか名前の前方一致なのか、
   記録が無いのか記録された不在なのか）で絞らなかった。
2. なぜそう設計したか → 検出したい事象「スキルを読んだか」を、観測が容易な代理指標
   「スキル配下のパス文字列が現れたか」へ置き換えた時点で、**その近似が持つ誤りの向きを列挙しなかった**。
3. なぜ列挙しなかったか → `.agents/rules/state-space-and-mutation-proof.md` は**入力の状態空間**を
   列挙せよと定めるが、**「証拠として採用するフィールドの意味論」を列挙せよとは書いていない**。
   変異実証も自分が書いたテストが到達する軸しか守らないので、採用フィールドを取り違えた誤りは
   変異させても緑のまま通る ← 根本原因（対策可能）

あちらは「同じ箇所を作り直した（手戻り）」を「同一パスへの編集回数」という代理指標に置き換えて
正常系と弁別できなくなった件で、**代理指標への置換という機序が同じ**。applied なので追記せず恒久側を強化する。
[[2026-08-03-detector-nonzero-hits-not-proof]]（applied）も同族（不在を証拠にした側）。

横断スコープ: 同じ形は「集めてから照合する」検出器すべてに効く。本リポジトリでは
`scripts/run-skill-eval.sh` の汚染スキャン（マーカーを raw 全文に grep）が同型で、
stream-json 化で走査面が広がったぶん偽陽性の余地が増えている（別 Issue 化を検討中）。

## 提案

証拠を集めて判定する検出器は、集める前に「どのフィールドを証拠に採るか」をフィールドの意味論で列挙し、採用外のフィールドにも標的インスタンスを 1 件置いて弁別できることを示す。

- 反映先: `.agents/rules/state-space-and-mutation-proof.md` の「1. 状態空間に入れるもの」へ 1 項目追加する
  （`paths` は既に `scripts/**` / `skills/*/scripts/**` / `skills/*/evals/**` を含むので変更不要）
- 文面の骨子: **「取れる文字列を全部集めて照合する」形は、書いた内容と読んだ内容・名前と名前の前方一致・
  記録の不在と記録された不在を、同じ証拠として扱う。** 採用するフィールドと採用しないフィールドを表にし、
  **採用しない側にも標的インスタンスを 1 件ずつ置く**（採用側だけのテストは、取り違えを変異させても緑のまま通る）
- 検出したい事象を代理指標へ置き換えたら、**その近似が生む誤りの向き（偽陽性・偽陰性）を 1 行ずつ書き出してから実装する**
- 変異実証の限界も同じ項目に添える: 変異は**自分が書いたテストが到達する軸**しか守らない。
  軸そのものを取り違えた誤りは変異させても緑なので、軸の列挙は変異実証の前段に置く

## 2 件目（同一 PR のレビュー 4 巡目）—— 指摘された 1 例を近似で塞ぎ、条件そのものに戻さなかった

### 2 件目の事象

レビュー 2 巡目で「`box` が `.claude/skills/boxes/` に一致する」と指摘され、
skill 名の直後に `(?![\w-])`（単語文字でもハイフンでもない）という否定先読みを足して塞いだ。テストも足して緑にした。

**4 巡目で同じ箇所が再び指摘された** —— `.` も `@` も単語文字ではないので、
`box.old/SKILL.md` と `box@backup/SKILL.md` が `box` の read として記録されていた。

本来の条件は「**skill 名がディレクトリ区切りの 1 区画であること**」で、正しい実装は
「直後が `/` かパスの終端」。`(?![\w-])` はその**近似**で、報告された 1 例（`boxes`）だけを外す形だった。

### 2 件目の根本原因

- なぜ再発したか → 指摘された**具体例**を外す条件を書き、**条件そのもの**（区画境界）に戻さなかった
  - なぜ具体例で足りると思ったか → 追加したテストも `boxes/` という**報告された例の変形**だけで、
    境界文字の集合（`.` `@` `+` `~` 等、名前に使えてパス区切りではない文字）を列挙しなかった
    - なぜ列挙しなかったか → 本記録の提案は「**証拠に採るフィールド**を意味で列挙する」と書いており、
      **判定に使う文字集合・境界条件を意味で列挙する**という同じ話が、フィールドの語で狭く読めた ← 根本原因

### 2 件目の提案

**「〜でない」で書いた境界は、本来の条件を肯定形で書けるか確かめてから採る。** 肯定形で書けるなら近似を使わない。

- 反映先は同じ `.agents/rules/state-space-and-mutation-proof.md`。上の項目に次を足す
- 文面の骨子: **報告された 1 例を外す条件で塞がない。** 指摘は条件の破れ方の 1 例であって条件ではないので、
  塞ぐ前に「本来満たすべき条件」を 1 行で書き、それを肯定形で実装する
  （`(?![\w-])`〈単語文字でない〉ではなく `(?:/…)?(?!<パス文字>)`〈区画の終わり〉）
- **否定形の境界を書いたら、否定に含まれない文字を 3 つ挙げてテストにする**
  （名前に使えてパス区切りでない文字: `.` `@` `+` `~` 等）。挙げられないなら、その否定形は条件を表していない
