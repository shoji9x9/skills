# 解析器の状態空間は想定した故障モードではなく文法から列挙する

## 事象

`css-rules-capture.mjs` と `axis-diff.mjs` に対し、ユニットテスト（29 件）・判定行を無効化する変異実証（3 件）・
実ブラウザでの陽性コントロールまで通したうえで PR を出したが、レビューが 3 件の実在する取りこぼしを出した。

- 入れ子セレクタの `&` を素朴に置換していたため、引用符・属性値の中の `&`（`& [data-label="A&B"]`）まで
  書き換えて不正なセレクタになり、当たるはずの規則が静かに落ちる
- `@scope` の配下を無条件グループとして降り、スコープ根の外の要素にも「当たった」と報告する
- 状態名が `null` / 非文字列 / 空文字の採取を捨ててから突き合わせるため、全インスタンスの状態名が
  壊れた入力が「状態 0 件・軸 0 件・問題 0 件」で `ok: true` になる

## 根本原因

1. なぜ取りこぼしたか → テストの状態空間を、Issue が報告した 2 つの CSSOM の落とし穴と、
   自分が思いついた壊れ方から作った。
2. なぜそこから作ったか → 「報告された欠陥を塞ぐ」ことを検証の目的に置き、
   「この器が食う入力の文法が許す形を全部当たる」を目的に置かなかった。
3. なぜ気づけなかったか → 3 件とも**取りこぼしても例外が出ない**経路（`matches()` は throw せず false、
   捨てた採取は出力に現れない）なので、テストが緑でも見えていないことが分からない。
   既存ルールは「入力の状態空間から逆引きする」と書いていたが、**その状態空間をどこから取るか**を定めていなかった。

KEDB 照合では `.kaizen/2026-09-01-matching-key-material-state-space.md`（applied）が最も近い。
同記録は照合キーの材料（欠落・重複・型崩れ）を状態空間へ入れることを定めており、今回の 3 件目はその再発。
1・2 件目は文法由来の形で、既存ルールの射程外だった。

横断スコープ: 同じ形の器がリポジトリに複数ある。`scripts/lint-pagination.js`（シェルの文法を走査）、
`scripts/auto-wait-check.mjs`（スイートのコードを走査）、`coverage-expand.mjs`（構造化入力を照合）。
いずれも「取りこぼしても例外が出ない」性質を持つ。

## 提案

入力を解析する器（パーサ・走査器・セレクタ照合・設定リーダ）の状態空間は、想定した故障モードではなく「その入力の文法が許す形」から列挙する。

引用符・エスケープ・括弧の中に現れる区切り文字、入れ子、スコープを持つ構文、名前が空・非文字列・重複の退化形を、
文法の仕様から順に当たる。捨てる分岐には必ず件数か理由を出力へ残し、「見えていない」ことがテストの緑に隠れないようにする。

反映先: `.agents/rules/state-space-and-mutation-proof.md`「1. 状態空間に入れるもの」へ項目を追加済み。
