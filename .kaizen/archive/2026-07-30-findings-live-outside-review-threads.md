# レビュー指摘の在り処をスレッド 1 経路で列挙すると、本文の指摘を取りこぼす

## 事象

PR #164 で `pr-finalize-loop` を回し、「CI 全成功・未解決スレッド 0 件・HEAD レビュー済み」を根拠に
**収束したと報告した**。実際には Copilot のレビューが `Not ready to approve` で、指摘 3 件が
**レビュー本文の `<details>` 内**（`### Comments suppressed due to low confidence (N)`、ヘッダは
`Comments generated: 0 new`）に格納されていた。ユーザーの指摘で気づいた。

取りこぼした 3 件のうち 2 件は本物の欠陥だった。

- `--verify` の陽性コントロールが `grep -q` の終了コードに依存しており、走査根に読めないパスが 1 つあるだけで
  「この根は走査されていない」と誤 FAIL する（この環境の `grep` は ugrep で、GNU が文書化している
  「`-q` かつ一致なら 0」の例外を実装していない。実測で一致していても rc=2）。**「陽性コントロールを入れた」と
  報告した検査自体が壊れていた**
- pnpm の親 re-add 手順が `pnpm add -D` 固定で、production dependency を `devDependencies` へ移す
  （`--prod` インストールやデプロイで依存が欠落する）

3 件目は事実誤認（`node -e` の `process.argv[1]`）で、実測を根拠に見送った。

## 根本原因

- なぜ取りこぼしたか? → 収束判定を `reviewThreads` と `comments.totalCount` の 2 指標で組み、どちらにも
  現れない経路（レビュー本文）を見ていなかった
  - なぜ見なかったか? → 「指摘＝インラインコメント＝スレッド」という API 表現上の 1 形態を、指摘の集合と同一視した
    - なぜ同一視したか? → **指摘が載り得る場所を列挙する**という観点が手順に無く、
      「スレッドを全ページ取得する」（1 経路の網羅）で列挙を果たしたつもりになっていた ← 根本原因

KEDB 照合: [[2026-07-30-isolation-requirements-beyond-read]] と同型（列挙の軸を 1 つに閉じた）。
[[2026-07-28-eval-baseline-read-contamination]] の「経路の集合を列挙する」を、レビュー指摘という別ドメインで繰り返した。
`comments.totalCount` による整合検証は**スレッド反映ラグ**を捕まえる仕組みで、本文経路には原理的に反応しない
（`totalCount` が 0 のため）。既存の安全弁が効かない盲点だった。

横断スコープ: GitHub のレビューを機械的に処理する全スキル。ツール側が「自信度の低い指摘を本文へ落とす」等の
挙動を持つ限り、スレッドだけを見る実装は静かに指摘を落とす。

## 提案（適用済み）

**指摘の在り処を列挙する。** レビューの取得は「スレッドを全部取る」で終えず、`reviews[].body`（総合判定・
suppressed な指摘）も毎回読む。スレッド 0 件・生成コメント 0 件は「指摘なし」の根拠にならない。
本文の指摘は返信先スレッドが無く `resolve` もできないため、トップレベルの PR コメントで判断と根拠を返し、
それを唯一の証跡として扱う。

- `skills/pr-finalize-loop/SKILL.md`: 状態取得に本文取得を追加、収束条件に「本文に未対応の指摘が無い」を追加、
  手順 4 に本文指摘の返し方を追加、停止条件の報告項目に本文の指摘・総合判定を追加、
  gh メカニクスに「レビュー本文に埋め込まれた指摘」節（実測した Copilot の格納形式と取得コマンド）を新設
- `skills/pr-review-handle/SKILL.md`: 同じ節と手順を追加（姉妹スキルで同じ盲点があった）
- 両スキルの `evals/evals.json` に回帰 eval を追加（未測定。次回の iteration で測る）
