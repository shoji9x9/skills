# 自作検出器は「件数が非ゼロ」では検出能力を実証できない。標的パターンの既知インスタンスで陽性コントロールを取る

## 事象

Issue #167（box OAuth 手順のリストインデント）の横断スコープ確認で、
「リスト項目内のインデント段落の直後に来る col 0 の遅延継続行」を探す
使い捨て走査スクリプトを書き、`skills/` 全体で 10 件ヒットした。

出力が非ゼロだったため走査器は動いていると判断しかけたが、10 件はすべて
コードフェンス内の行（フェンス追跡が無い）＝誤検知で、標的パターンの
真陽性は 0 件だった。走査器は空行で `inList` を false に落としており、
実際に修正した `oauth-setup.md:29` を修正前ファイルに当てても `hits=0` だった。

## 根本原因

- なぜ壊れた走査器を信用しかけたか → 出力が非ゼロだったため「動いている」と読んだ
  - なぜそう読んだか → 検出能力の証拠を「何か出たか」で代用し、
    「標的パターンを出せるか」で測らなかった
    - なぜ代用したか → 既存規律（`AGENTS.md`）の発動条件が
      「何も出ないことを合格根拠にする検査」に限定されており、
      件数が出る走査器は自分がその条件に該当すると認識されなかった ← 根本原因

KEDB 照合: [[2026-07-30-negative-result-checks-need-positive-control]]（applied）と同型。
当該ノートは「陰性＝合格」の検査を扱うが、本件は非ゼロ出力で陰性性が隠れる派生形。
applied のため追記せず、恒久側（`AGENTS.md`）を強化する。

横断スコープ: 同じ穴は kaizen の「横断スコープ確認」で毎回書かれる使い捨て grep /
スクリプト全般にある。テスト付きの `scripts/lint-pagination.js`（vitest）とは異なり、
使い捨て走査器には検出能力の担保が無い。

## 提案

自作の走査器・grep で「他に該当なし」を主張する前に、標的パターンの既知インスタンスを
食わせて検出できることを実証する。件数が非ゼロでも検出能力の証拠にはならない
（誤検知だけで埋まり真陽性 0 の状態が非ゼロ出力に化ける）。

- 陽性コントロールは「何か出るか」ではなく「標的パターンが出るか」で取る。
  修正済みなら修正前の版を入力にする
- 除外ロジック（フェンス・コメント等）を持つ走査器は、除外内と除外外の両方に
  標的インスタンスを置き、弁別できることまで確認する
- 反映先: `AGENTS.md` ワークフロー節の陽性コントロール行を、
  発動条件が「陰性＝合格の検査」に閉じないよう拡張する
