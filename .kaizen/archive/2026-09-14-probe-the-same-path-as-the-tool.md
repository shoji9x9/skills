# プローブで実証した経路と、作ったツールが使う経路が違った

## 事象

Issue #354 で fixture 生成スクリプトを headless Chrome + CDP で作った。
事前の実測プローブは `Page.setDocumentContent` で文書を流し込む経路だけを確かめたが、
スクリプト本体は `Page.navigate` で http のページを開く経路で書いた。
この環境では http(s) へのナビゲーションが開始すらせず、`Page.navigate` が応答しないまま
スクリプト全体の timeout に切られた。出力はパイプの tail に溜まったまま消え、
どの呼び出しで止まったかが分からず、トレース版・sandbox 外実行・フラグ変更・
別バイナリと 8 回ほど試してから文書流し込みへ切り替えた。

## 根本原因

- なぜ止まった? この環境の Chrome は http ナビゲーションを開始しない（data: は通る）
- なぜ気付くのが遅れた? 本体を書く前のプローブが、本体と別の経路（setDocumentContent）しか通していなかった。
  「Chrome を CDP で動かせた」を「本体の全呼び出しが動く」と読み替えた
- なぜ切り分けに時間を使った? 呼び出し単位のタイムアウトが無く、スクリプト全体を timeout で切り、
  出力をパイプ越しに読んでいたので、止まった呼び出しが出力に残らなかった

## 提案

外部プロセス（ブラウザ・CLI・サーバ）を駆動するツールを書く前に、本体が使う能力（ナビゲーション・ネットワーク・ファイル I/O 等）を 1 つずつ最小プローブで実測し、本体では各呼び出しに個別のタイムアウトとどの呼び出しかを示す stderr を付ける。

反映先の候補: `AGENTS.md`「ワークフロー」の「止まって見える子プロセス」の項に、
(1) プローブは本体と同じ経路・同じ呼び出しで取る、
(2) 全体 timeout にせず呼び出し単位で切り、ファイルへ出力して止まった位置を残す、を追記する。
横断スコープ: `scripts/` の CDP を使う他ツールは現状なし（今回の `generate-parity-component-fixtures.js` のみ）。
