# 検出器は合成 fixture ではなく実データのラベルで分離力を測ってから出荷する

## 事象

Issue #341 の「決定論的な対策を提案したのに doc だけで閉じたノート」の警告を、Issue が指定した
語リスト方式（`## 提案` に `lint` / `hook` / `script` / `CI` / `検査` / `起票` 等を照合）で実装した。

合成 fixture で陽性 4 件・陰性 7 件を作り、判定行の変異 3 通りで赤くなることまで実測して green にした。
実データ（`.kaizen/` の applied 131 件）に当てると 16 件が出たので、そのうち 1 件だけ開き、
「`検査` が当たっていて `applied-to` が `AGENTS.md` だけ」であることを確認して真陽性と判断し、
「16 件 / 131 件 = 12%、雑音にならない水準」とユーザーへ報告してコミットした。

コミット後のレビューで 6 件を読まれ、**6 件すべて偽陽性**と指摘された。
`applied-to` に機構（`.md` 以外）が入っているかを正解ラベルにして測り直すと、語の照合は
**機構を適用したノートへ 38%（6/16）、doc だけのノートへ 33%（15/45）**で、2 クラスをほとんど
分離していなかった。一致 16 件はすべて `検査` 9 / `ゲート` 3 / `スクリプト` 3 の 3 語で、
`lint` / `hook` / `script` / `CI` / `起票` は 1 件も当たっていない——検査とゲートが主題の
リポジトリでは、この 3 語は「提案が何について述べているか」を指すだけだった。

## 根本原因

1. なぜ分離しない検出器を出荷手前まで進めたか → 合成 fixture の陽性・陰性コントロールが green で、
   変異実証も通っていたので検証済みと判断した。
2. なぜ合成 fixture で足りると考えたか → 陽性/陰性コントロールと変異実証という既存の規律
   （[[2026-08-03-detector-nonzero-hits-not-proof]]、`.agents/rules/state-space-and-mutation-proof.md`）を
   満たしており、**その規律が「実装が仕様どおりか」までしか測らない**ことを意識していなかった。
   合成 fixture は自分が想定した陽性・陰性なので、仕様そのものが現実を分離するかには答えない。
3. なぜ実データ 16 件を見ても気づかなかったか → **検出器が出した側**だけを 1 件開き、
   判定条件が成立していることを確かめた。これは定義の確認であって分離力の測定ではない。
   **出していない側**（機構を適用したノート＝真陽性であるべき集合）を 1 件も見ていないので、
   再現率は測りようがなかった ← 根本原因（対策可能）

KEDB 照合: [[2026-08-03-detector-nonzero-hits-not-proof]]（`status: applied`）が最も近い。
あちらは「件数が非ゼロでは検出能力の証拠にならない。標的パターンの既知インスタンスで陽性コントロールを取る」で、
**陽性コントロールの取り方**の話。本件は陽性コントロールを取ったうえで、それが合成データだったために
**現実のクラス分離を測れていなかった**という次の層なので、追記せず新規に記録する。

横断スコープ: 実データに対する分類・判定を出力する検査すべて。
`kaizen-precommit-gate.sh` の候補走査（transcript から学び候補を拾う）、`scripts/lint-pagination.js`、
`scripts/check-*.js` は、いずれも合成 fixture のテストだけを持ち、実データでの分離力は測っていない。

## 提案

実データへの判断を出す検出器は、合成 fixture の陽性・陰性コントロールに加えて、**実データへラベルを付けて再現率と誤検知率を測ってから出荷する**。

- ラベルは既存の構造から機械的に取る（本件では `applied-to` に `.md` 以外が入っているか）。
  構造から取れないなら標本数を決めて人が読む
- **「検出器が出した側」だけを読まない。「出していない側」も同数読む。**
  出した側だけを読むと、測れるのは判定条件が成立しているかだけで、再現率は永久に見えない
- 件数と割合を出す。「12% は雑音にならない水準」のような印象で判断しない
- 分離しなければ**仕様を疑う**。Issue やレビューが方式を指定していても、測定結果を添えて方式変更を提案する
  （本件は `type: hook` × 適用先が `.md` だけ、という宣言ベースの判定へ置き換えて 131 件中 1 件・真陽性になった）

反映先: `.agents/rules/state-space-and-mutation-proof.md` の「3. テストが効いていることの示し方」。
同節は既に変異実証を要求しているので、**その green が何を意味しないか**（合成 fixture は仕様の妥当性を測らない）を
1 項目足し、実データのラベル測定を要求する。`paths` は同ルールの現行スコープ
（`scripts/**` / `skills/*/scripts/**` / `skills/*/evals/**`）のままでよい。
