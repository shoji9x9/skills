# 検査の入力を自由記述にすると、穴は入力形式の数だけ出る

## 事象

PR #402 で新設した 3 つの検査に、codex のレビューが **7 巡で 20 件**の欠陥を指摘した
（P1 13 / P2 7）。内訳を数えると、**16 件が「入力の形式を自由記述にしたこと」に由来**する。

- 区切り: `|` `#` を含む名前で鍵・id が潰れる（4 件）
- 境界: 列名の部分文字列一致、括弧つき条件でトークンが空、条件内のカンマで分割（3 件）
- 重複: 同じ鍵・同じ名前が 2 つ（4 件）
- 空欄・型崩れ: slug 空・絞り込み空欄・`mode` 欠落・寸法 0・空白の target（5 件）

これらは **Markdown の表セルと連結文字列を解析しているから存在する**。
同じ情報を構造化していれば（列を配列で持つ、鍵をタプルで持つ）、区切り・境界・分割の
穴は最初から無い。

残る 4 件（`gaps に記録` の扱いを検証が覆す・真偽の合計と表の件数・被覆表 slug の欠落・
述語行の使い回し）は形式ではなく**判定規則**の穴で、これは自由記述でも構造化でも起こる。

## 根本原因

- なぜ 20 件も出た? → 検査の入力が人間が書く自由記述だった
  - なぜ自由記述にした? → 既存の成果物（`design.md` / `metadata.json`）の書き方に合わせた
    - なぜ合わせるだけで止めた? → 「機械検査を新設するときは、その入力を構造化するかを
      先に決める」という判断点が手順に無い ← 根本原因（対策可能）

KEDB 照合: [[2026-09-08-overdetection-fix-is-itself-a-relaxation]]（`status: pending`）は
受理条件の列挙不足、[[2026-09-18-matching-granularity-must-be-declared]]（`status: pending`）は
照合の粒度で、どちらも**個々の穴の直し方**を扱う。本記録は**穴の総数を決める上流の選択**（入力形式）なので別の軸。

横断スコープ: 同じ形は `parity-suite` / `parity-diff` の既存検査（`coverage-expand.mjs` は JSON を
読むので構造化側、`reaction-check.mjs` の `opened_by` は `<関数名>(<論理名>)` の文字列解析で自由記述側）にもある。
`opened_by` は既に表記の正規化・移行の規定を抱えており、この記録の裏付けになっている。

## 提案

機械検査を新設するときは、実装前に「入力を構造化するか」を決め、自由記述を解析するなら 4 軸を表にする。

- 4 軸は**区切り・境界・重複・空欄**（本件の 16 件はすべてこのどれか）
- **人が読む表と、検査が読む構造を分ける選択肢を検討する**（表は人向けの写し、JSON を正本にする等）。
  分けるコスト（二重管理）と、解析の穴を塞ぎ続けるコストを比べて決める
- レビューが同じクラスを 3 巡以上指摘したら、個別の修正ではなく**入力形式を疑う**
  （本件は 7 巡目で初めてこの視点に至り、それまでは 1 件ずつ塞いでいた）
