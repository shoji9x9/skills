# 過剰検知の修正は「緩和経路の新設」であり、新たに通る入力クラスを列挙する

## 事象

`kaizen-precommit-gate.sh` の誤検知（引用の内側にあるリテラルの `(` を区切りと誤読して
読み取り専用コマンドをブロックする）を直すため、コマンド文字列の**引用の内側**を同じ長さの `_` へ
潰す `mask_quoted()` を新設した。5 件の弁別する回帰ケースを足し、変異（修正を戻す）で全て赤くなることまで
実測して green にした。既存 145 件も通っていた。

`/code-review` が、その状態空間の外にある **fail-open** を検出した。マスク器はコマンド全体を
シェルの引用規則で読むが、**シェル引用が働かない領域**（`#` コメント、heredoc 本文）に現れた
アポストロフィが「開き引用符」として本物の `git commit` を跨いでペアリングし、commit ごとマスクされる。
fail-closed を目的に作ったゲートが素通りする。実測（HEAD と修正版の対比）:

```text
# don't
git commit -m x        修正前: exit 2  →  私の版: exit 0（素通り）
# won't
```

```text
cat <<EOF > f
don't
EOF
git commit -m x        修正前: exit 2  →  私の版: exit 0（素通り）
```

どちらも **kaizen が日常的に生成する形**（heredoc でメモを書いてから commit する）で、
元の誤検知より重大な退行だった。

同じレビューが 2 つ目の欠陥も検出した。マスク器が 1 文字ずつ走査する（`${s:0:1}` / `s=${s:1}` /
`${#s}` を文字ごとに評価）ため **O(n²)** で、全 Bash 呼び出しの前段に乗る hot path が
payload サイズで破綻する。実測: 2 KB 0.08s / 8 KB 0.64s / 20 KB 3.56s / **50 KB 22.21s**
（修正後はそれぞれ 0.08 / 0.09 / 0.10 / 0.17s）。

## 根本原因

1. なぜ fail-open が入ったか → マスク器がコマンド全体をシェルの引用規則で読み、
   **引用規則が効かない領域**（`#` コメント・heredoc 本文）にも同じ規則を当てた。
2. なぜその領域を列挙しなかったか → 直そうとした欠陥（引用の内側の区切り）から状態空間を逆引きし、
   「引用の内側 / 外側」の 2 分割で列挙を終えた。第 3 のクラス
   （**引用文字が現れるが、シェル引用ではない領域**）を置かなかった。
3. なぜ 2 分割で終えたか → **過剰検知を直す変更**だったため、列挙の関心が「いま落ちている入力を通すこと」
   に寄り、「この変更で**新たに通ってしまう**入力クラス」を同じ粒度で列挙しなかった ← 根本原因

性能の側も同じ形で、**正しさの状態空間だけを列挙し、入力サイズを軸に入れなかった**。
ゲートが「全 Bash 呼び出しの低コストな第一段」であることはスクリプト冒頭のコメントに書いてあるのに、
実装時に計測へ結び付けていない。

KEDB 照合（陽性コントロールとして `引用 ゲート` で 2 件ヒットすることを確認したうえで）:
[[2026-09-01-matching-key-material-state-space]] が最も近い——「fail-closed に緩和経路を置くなら
通す入力クラスを閉じた集合として列挙する」。ただしあちらは**後方互換・免除・スキップ**という
明示的な緩和経路を扱っており、本件の「**誤検知修正そのものが緩和経路である**」という軸は覆っていない。
[[2026-09-08-quoted-separator-must-not-trigger-command-gate]] は本件が直そうとした元の欠陥。
[[2026-08-30-new-state-branches-need-fixtures]]（変異で赤くなることを実証）は**実施済みで、なお防げなかった**
——変異テストは「書いたケースが効くこと」しか示さず、**書かなかったケース**は照らさない。

横断スコープ: コマンド文字列に字句規則を当てる実装は `kaizen-precommit-gate.sh` と
`git-worktree-branch-guard.sh` の 2 本。後者はトークン分割と `unquote` で判定しており、
陽性コントロール付きで実測したところ同型の誤発火・素通りは無かった。
より広くは、**検出器の誤検知報告を受けて判定を緩める全ての変更**が対象。

## 提案

反映先は `.agents/rules/state-space-and-mutation-proof.md` の「fail-closed に緩和経路を置くなら」の項。次の 3 点を足す。

- **検出器の過剰検知を直す変更は、それ自体が緩和経路の新設である。**
  「いま落ちている入力を通す」だけでなく、**その変更で新たに通る入力クラスを閉じた集合として列挙**し、
  代表を **BLOCK 期待**の回帰ケースとして同じ変更に足す。
  変異テスト（判定行を無効化して赤くなること）は**書いたケースが効くこと**しか示さず、
  書かなかったケースは照らさない——緩和側の変更では、緑になったケースより
  **「通るようになった入力の集合」**を数え上げるほうが検出力が高い。
- **コマンド文字列に字句規則（引用・エスケープ）を当てるなら、その規則が効かない領域を先に列挙する。**
  `#` コメント、heredoc 本文、`case` パターン、`[[ ]]` 内などはシェルの引用規則が
  そのままは働かない。領域の範囲を確定できないなら **fail-closed に倒す**（判定不能を成功扱いにしない）。
- **hot path に入るフック・ゲートは、正しさに加えて入力サイズ軸で実測する。**
  文字単位のループ（`${s:0:1}` / `s=${s:1}` の反復）は O(n²) になる。
  数 KB〜数十 KB の payload でレイテンシを測り、特殊文字までまとめて進むチャンク走査にする。
