# 外部ツールのフラグを判定の根拠にするなら、そのフラグが判定対象に効くかを実測する

## 事象

Issue #221（kaizen コミット前ゲートが外部リポジトリ宛ての `git commit` もブロックする）の修正で、
コマンド行の `-C` / `--git-dir` / `--work-tree` を「コミット先が外部だと確定する根拠」に使った。
このうち `--work-tree` は根拠にならない。`--work-tree` は作業ツリーを差し替えるだけで、
リポジトリは cwd からの探索で決まるため、`git --work-tree=<外部dir> commit` は
**プロジェクトのリポジトリへコミットされる**（実測: proj 内から実行すると proj の log に入り、
外部 dir は repo ですらない）。結果としてゲートは fail open になり、プロジェクト宛ての commit を
素通しさせていた。コードレビューの指摘で発覚した。

書いた分岐には回帰テストも付けていたが、テストが自分の誤った意味論をそのまま符号化していたため
全て green だった（`--git-dir=X/.git --work-tree=X` → exit 0 を「正しい」として固定していた）。

## 根本原因

- なぜ fail open になったか? → `--work-tree` がコミット先リポジトリを変えると解釈した。
  - なぜそう解釈したか? → オプション名から効果を推定し、`git --work-tree=<外部> commit` を
    実際に走らせてコミットがどちらの repo に入るかを一度も測らなかった。
    - なぜ測らなかったか? → 実測したのは「正規表現が commit を取りこぼさないか」という**構文・到達性**で、
      「そのフラグが判定材料として成立するか」という**効果**は検証対象に入っていなかった。
      既存規律（[[2026-07-29-verify-the-branch-you-document]] / [[2026-08-10-verify-branches-you-add]]）は
      「書いた分岐をその状態で実測する」までで、**分岐の前提に置いた外部ツールの効果**を名指ししていない。
      ← 根本原因（対策可能）

同じスクリプトの直上には `--exec-path` が次の引数を消費するかを実測で決めたコメントがあり、
「引数を消費するか」という軸は測っていた。測っていなかったのは「コミット先を変えるか」という別の軸。

横断スコープ: `gitoptval_opt` の他のオプション（`--namespace` / `--super-prefix` / `--attr-source`）も
同じ軸では未検討だったため、今回 `-C` / `--git-dir` のみに限定した。他スキルでも `gh` 等の
フラグを分岐の根拠にする箇所は同型のリスクを持つ。

KEDB 照合: [[2026-07-29-verify-the-branch-you-document]] は applied（適用先は
`.agents/rules/external-tool-format-verification.md`）。[[2026-08-10-verify-branches-you-add]] は pending だが、
軸が「修正が増やした経路を入力に起こしたか」であるのに対し、本件は「**分岐の前提に置いた効果を測ったか**」
のため追補として別に記録する。

## 提案

`.agents/rules/external-tool-format-verification.md`（`paths: skills/**`）に次を追加する:

- **外部ツールのフラグ・オプションを判定の根拠（分岐の前提）にするなら、そのフラグが
  判定したい対象に実際に効くかを実測する。** 名前から効果を推定しない。`--help` / SYNOPSIS は
  「何を指定するか」は書くが「何に効かないか」は書かない。
  検証は**判定したい軸そのもの**で取る（例: 「引数を消費するか」を測っても「コミット先が変わるか」は測れない）。
  ゲート・遮断・スコープ判定でこれを外すと、効かないフラグを根拠に通してしまう（fail open）。
  自分で書く回帰テストは誤った意味論をそのまま符号化して green になるため、テストの green は
  この実測の代わりにならない。
