# 合格を「問題が無いこと」で定義すると、測っていない入力が合格になる

## 事象

`axis-diff.mjs` の合否は `ok: problems.length === 0` で表していた。この形は**何も測れなかった入力**を
合格にするため、同じクラスの fail-open が 1 つのツールから 3 回出た。しかも 3 回とも別々の経路で報告された。

1. インスタンスが 1 件（自分で気づき、早期 return を足した）
2. 全インスタンスの状態名が `null` / 空文字（レビュー 1 巡目の指摘）
3. `traits: {}` で軸が 1 つも立たない（レビュー 2 巡目の指摘）

どれも「表が空 → 突き合わせる相手が無い → problems も空 → `ok: true`」という同じ筋である。
`build` は `axes.ok` だけを前提に進むので、突き合わせていないベースラインが実装の根拠として通る。

ユニットテスト・判定行の変異実証・実ブラウザの陽性コントロールはいずれもこれを捕まえられなかった。
どれも「壊れた入力を 1 つずつ用意して赤くなるか」を見る形で、**用意しなかった退化形は検査に現れない**ため。

## 根本原因

1. なぜ 3 回出たか → 退化形を 1 件ずつ塞いだから。報告されるたびに分岐を足し、次の退化形は残った。
2. なぜ 1 件ずつ塞いだか → 合否の定義が「問題の不在」なので、塞ぐ対象が**問題を挙げる分岐の列挙**になる。
   列挙は網羅を保証しないため、足し続ける形になる。
3. なぜその定義にしたか → 検査器は「問題を見つけて報告するもの」と捉え、
   「測れたことを証明するもの」と捉えなかった。**不在は証明ではない**という規律を合否の式に落としていなかった。

KEDB 照合（`合格` / `問題` / `不在`、`fail-closed` / `scripts` / `0 件`）では
`.kaizen/2026-09-01-matching-key-material-state-space.md`（applied）が近いが、あちらは
**照合キーの材料**を状態空間へ入れる話。こちらは**合否の式そのものの形**の話で、
状態空間をどれだけ広げても式が「不在＝合格」である限り未列挙の退化形は通る。

横断スコープ: 同じ形の式を持つ検査器がある。`coverage-expand.mjs` の `ok`、
`scripts/lint-pagination.js` の指摘 0 件、`auto-wait-check.mjs` の違反 0 件。
いずれも「走査対象が 1 件以上あること」を別に確かめているかが分かれ目になる
（`parity-suite` の `SKILL.md` は auto-wait-check について「走査対象が 1 件以上かつ違反 0 件」を要求しており、この形が正しい）。

## 提案

検査器の合格は「問題が無いこと」ではなく「測れたことの積極的な証拠（対象件数が 1 以上）」で定義する。

`ok: problems.length === 0` の形を見たら、`ok: problems.length === 0 && measured > 0` に相当する条件が
あるかを確かめる。無ければ、退化形を 1 つずつ塞ぐのではなく式そのものを直す。
報告にも測れた件数を必ず出し、0 件が合格として通らないようにする。

## 適用（2026-09-12）

`axis-diff.mjs` の合否を `ok: problems.length === 0 && measured > 0` に変え、突き合わせられた軸が 0 件なら problems へ落とすようにした（`measured` を出力にも足した）。
条件を無効化する変異でテストが赤くなることを実測済み。fixture の `axes.json` も実出力へ取り直した（`measured: 72`）。横断スコープに挙げた他の検査器への適用は未着手。
