# 自前の解を設計する前に、公開済みの解決手段を調べる

## 事象

`skill-creator` の評価工程が Claude Code 依存で Codex では回せない、という相談に対し、
新規スキル `skill-eval`（executor 選択・出力の正規化・採点集計）の構成案を提示した。
ユーザーから差し戻された:

> 了解です。ただ、もう少し幅広く検討して下さい。
> 同じようにスキルを Codex で評価したいが skill-creator が Claude Code に依存している部分があり
> 困っている人は他にもいそうです。そのため、既に解決手段が公開されていたり、
> Codex 用のスキルが公開されているかもしれません。これも調査して下さい。

「他にも困っている人がいそうな問題」であり、先行事例の有無は
「自前で作る／既存を採る／上流へ出す」という設計判断そのものを変えうる。

## 根本原因

- なぜ調べなかった? → 「このリポジトリで何を作るか」という内部設計の問題として受け取った
  - なぜ? → 外部に既解がある可能性を選択肢に入れていなかった
    - なぜ? → `AGENTS.md`「コンポーネント選択基準」は skill / rule / hook / ドキュメントの
      **どれに落とすか**は規定するが、その前段の**そもそも自前で作るか既存を採るか**を
      問う段が無い ← 根本原因（対策可能）

横断スコープ: 「コンポーネント選択基準」は作業対象に依らず常に効かせたい一般規律なので、
`.agents/rules/`（paths で絞れない）ではなく基底ドキュメント `AGENTS.md` が置き場になる。

KEDB 照合: 「調査」「既存」「先行」「公開」「設計」「上流」で照合したが、
先行事例の調査を扱う既存の学びは無かった（ヒットしたのは無関係な 3 件）。

## 提案

`AGENTS.md`「コンポーネント選択基準」の冒頭に追記する:

- **新しい仕組みを設計する前に、同じ問題の公開済みの解を調べる**（上流の対応状況・
  他者が公開しているスキル・既存 Issue）。「他にも困っている人がいそうな問題」は特に
  先行事例がある。調べた結果は**見つからなかったことも含めて**提案に添える
  （調べていないのか、調べて無かったのかを読み手が区別できるようにする）。
