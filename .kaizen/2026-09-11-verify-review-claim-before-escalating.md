# 裏取りしていないレビュー指摘を「対応するか」としてユーザーへ上げない

## 事象

新しいレビュー指摘（状態ごとの証拠で `hidden_by` のキー省略が通る、という主張）について、妥当性を検証せず「対応してよいか指示をください」と作業を止めた。ユーザーから「指摘が妥当であれば修正して下さい」と修正指示を受けた。実際に検証すると該当コードは既に未測定へ倒しており（`state.hidden_by !== null` はキー欠落の `undefined` でも真になり型検査で落ちる）、指摘は誤りだった。裏取りしていれば「誤指摘なので対応不要」と即答でき、確認自体が不要だった。

## 根本原因

1. なぜ止めたか → PR のスコープが膨らみ続けていたため、追加対応の可否を人の判断へ委ねようとした。
2. なぜ委ねたか → 直前に同種の質問で承認を得ており、「新しい指摘＝都度確認」というパターンに固定した。
3. なぜ固定したか → スコープ判断（この PR でやるか）と妥当性判断（そもそも直すべき指摘か）を分離していなかった。妥当性は自分で裏取りできるのに、未検証のまま確認へ上げた ← 根本原因

KEDB 照合（`レビュー` / `妥当性` / `確認` と `指摘` / `裏取り` / `pr-review-handle` で陽性ヒットを確認したうえで）:
[[2026-06-05-verify-review-claims-against-source]] が同系統だが `status: applied`。
既存は「未検証の指摘を**適用**しない」軸で、「未検証のまま**ユーザーへ上げない**」軸は覚えていない。
applied ノートには追記せず恒久側を直接強化した。

横断スコープ: 同型は確認 UI を持つ全スキル（`pr-finalize-loop` / `issue-batch` 等）で起こりうる。人へ上げる前に自分で決められる材料を使い切ったかを問う点は共通。

## 提案

確認へ上げる前に妥当性の裏取りを済ませる。裏取りしていない指摘を「対応するか」としてユーザーへ上げない。誤指摘なら確認自体が不要で、人の判断を消費する。確認するのは、妥当と裏取りしたうえでなおスコープ・修正方針が分かれる場合だけ。

`pr-review-handle` の「妥当性の判断ガイド」へ適用した。
