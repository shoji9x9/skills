# 範囲の外と書く前に、Issue の受け入れ条件と同じ失敗の条件に当たるかを確かめる

## 事象

Issue #1101（元の作業ツリーに書けないと抽出を完了できない）の実装を終えた報告で、エージェントは、書き込めないツリーに残った抽出完了マーカーを SessionStart が消せない点を「範囲の外で、起きるかも確かめていない」と書いた。
利用者が確かめるよう求めたので再現したところ、同じ session id で再開すると、そのマーカーが新しいセンチネルを覆い、学びの候補があっても commit 前のチェックが exit 0 で通した。
同じ Issue の中で、SessionStart・チェック・`kaizen-extract-done.sh` を直し、テストとミューテーションテストの定義を足し直した。

## 根本原因

- なぜ範囲の外と書いたか: 直す対象を、Issue が名前を挙げた `kaizen-extract-done.sh` の書き込みに限って考えていた。
- なぜそう限ったか: 「元のツリーに書けない」という失敗の条件を、そのファイルを書く側と消す側（SessionStart の削除）のすべてに当てて列挙しなかった。
- なぜ列挙しなかったか: 見つけた点を範囲の外とする前に、Issue の受け入れ条件（古いファイルが新しい記録を隠さない）と照らす手順が無い。AGENTS.md は「確かめていない懸念はコメントで残す」とだけ書いており、受け入れ条件に当たるかを先に確かめることを求めていない。

## 根拠

原因を再現して確かめた（書けないツリーでは exit 0、書けるツリーでは同じ手順で exit 2）が、観測はこの 1 回なので medium にする。
完了報告の後、利用者の求めで再現のスクリプトを書き、修正前後で終了コードを比べた。KEDB 照合（「範囲の外」と「SessionStart」、「書き込めない」と「.kaizen」、「失敗の条件」と「後片付け」、「懸念」と「完了報告」）で一致した学びは無い。

## 既存の規約

- 扱い: なし
- 場所: なし（近いものとして AGENTS.md「確かめ方」の対称な反対側を当てる箇条と、「外向きの操作と破壊的な操作」の範囲の外の点の箇条がある。前者は規約に語彙や判定軸を足すとき、後者は Issue にするかの基準で、範囲の外と判断する前の照合は扱っていない）
- 照合した範囲: AGENTS.md・docs/agent-workflow.md・.agents/rules/ を「対称な反対側」「確かめていない懸念」で検索した

## 食い違い

- 相手: なし
- 判断: なし

## 提案

作業の途中で見つけた点を範囲の外とする前に、Issue の受け入れ条件と、直している失敗の条件（書けない・読めない・消せないなど）に当たるかを確かめ、当たるなら再現してから同じ Issue で扱う。

- AGENTS.md「外向きの操作と破壊的な操作」の範囲の外の点の箇条の前に、上の 1 文を足す。理由と実例（Issue #1101 の SessionStart のマーカー）は docs/agent-workflow.md の対応する節に書く。
- 失敗の条件は、直したファイルの書き手と消す側（Hook・後片付けの処理）のすべてに当てる。
