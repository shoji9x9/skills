# 後の作業で確かめると約束した事柄を、応答にだけ書いて Issue に書かなかった

## 事象

PR #1000 の作業中に、エージェントは利用者への応答で、これから作る Issue（#998。記録の形を変える）の実装のときに破壊的変更に当たるかを PR に書いて確認する、と述べた。
その事柄を Issue の本文には書かなかった。利用者は、Issue の本文に書かないと実装のときに忘れる、と直した。
エージェントは #998 の本文に「リリースのバージョン」の節と、受け入れ条件を 1 項目足した。

## 根本原因

- なぜ利用者が直したか: 後の作業で要る確認を、応答の中でだけ約束した。
- なぜ応答にだけ書いたか: 約束した時点のセッションが、後の実装も行うかのように扱った。実際の実装は、別のセッションか別のサブエージェントが Issue を読んで始める。
- なぜそう扱ったか: 後の作業へ渡す判断や注意を、その作業が読む記録（Issue の本文・受け入れ条件）に書くという規約が、基底ドキュメントに無い。`issue-batch` の `prepare` は決定を Issue に記録するが、その手順の中だけの取り決めである。

## 根拠

確信度の理由: 1 回の観測だが、応答だけに書いて記録に書かなかったという原因に絞れている。
main のセッションの応答で約束し、利用者がその直後に Issue の本文に書くよう指示した（transcript の user correction の 1 件）。
KEDB 照合では、「Issue の本文」「後の作業」「別のセッション」「受け入れ条件」「忘れ」を組み合わせて照合し、同じ原因の学びは無かった。
当たったのは言語の確認や worktree の学びで、原因が違う。

## 既存の規約

- 扱い: なし
- 場所: なし（近いものは `skills/issue-batch/references/prepare.md` の「Issue に残すコメント」で、`prepare` の手順の中だけで決定を Issue に記録する）
- 照合した範囲: `AGENTS.md`・`docs/`・`.agents/rules/` と、`skills/` の `issue-create`・`issue-start`・`issue-batch`・`writing-style` を検索した。
  語は「Issue の本文に書」「後のセッション」「Issue に記録」「応答にだけ」である

## 食い違い

- 相手: なし
- 判断: なし

## 提案

後の Issue・PR の作業（別のセッションやサブエージェントが行うもの）で確かめると利用者に述べた事柄は、その場で対象の Issue の本文に書き、確かめられるものは受け入れ条件にする。

- 置き場所は基底ドキュメント（`AGENTS.md`「ワークフロー」）の 1 行にする。特定のパスの作業で閉じないので、rule にはしない。
- `skills/issue-create/SKILL.md` の「実装の詳細は Issue の本文に書きすぎない」とは対象が重ならない。書くのは実装の詳細ではなく、後の作業で要る確認と判断である。
- 機構は作らない。応答の中の約束を検出する方法が無く、1 回の観測では費用に見合わない。
