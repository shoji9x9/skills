# テスト名を変えたとき、その名前を参照する expect_failing を合わせなかった

## 事象

issue-batch の run の #767 で、lint-prose が指した 710 か所の単独の `版` を、位置を指定して「バージョン」に置き換えた。
置き換えの前に確かめたのは、ミューテーションテストの定義の `find` の出現数と、eval の reachability だけだった。
テスト名（`test("...")` の文字列）も置き換えの対象に入っていたが、6 つの定義ファイルの `expect_failing` 16 件が古い名前のまま残った。
手元の vitest は緑で、ローカルレビューが見つけた。CI の `Mutation proof (PR)` は、実在しないテスト名で exit 2 になるところだった。

2026-11-20 に再発した（Issue #1095・PR #1098）。一括の置き換えではなく、指標を 1 つ足したのに合わせて、テスト名「3 つの指標を集める」を手で「4 つの指標を集める」に変えた。
`check-cost-metrics.mutations.json` の `expect_failing` が古い名前のまま残り、push した後の CI の `Mutation proof (PR)` が exit 2 で失敗した。
手元の vitest・pre-commit・`/code-review` のどれもこれを検出しなかった。

## 根本原因

- なぜ残ったか: 置き換えの対象を lint-prose の指摘から作り、その指摘がテスト名の文字列に当たることを、鍵を持つ側（`expect_failing`）から挙げ直さなかった。
- なぜ挙げ直さなかったか: `AGENTS.md`「編集」の一括の書き換えの規約は、内容のハッシュ・テスト名の参照・`find` の出現数の 3 つを挙げている。そのうち `find` だけを確かめ、規約の一覧と突き合わせなかった。
- なぜ手元で気付かなかったか: `mutations-declaration.test.ts` は定義の形を見るが、テスト名の実在は見ない。実在はランナーの実行でしか分からない。

2026-11-20 の 2 回目の原因は、次のとおりである。

- なぜ残ったか: 指標を 1 つ足したのに合わせてテストの名前を 1 件だけ手で変え、その名前を鍵にする `expect_failing` を挙げ直さなかった。
- なぜ手元で気付かなかったか: 変えたテストファイル（`check-cost-metrics.test.ts`）を `test_file` に持つ定義ファイルを、ランナーで実行し直さなかった。
  実行していれば、実在しない名前は exit 2 で見つかった。
- なぜ実行し直さなかったか: `.agents/rules/state-space-and-mutation-proof.md`「assertion を書き換えたら」は、`test_file` を持つ定義ファイルを全件実行し直すよう求めている。
  対象は、assertion を書き換えたとき・テストを足したとき・判定を足したときである。
  2 回目は指標のテストを足したので、この規約に当たる。テストの名前を変えただけのときは、規約は言い切っていない。
  この rule は `scripts/**` を触ると読み込まれ、言い切る形で書かれている。
  それでも、新しく足した判定には定義を作らない（`docs/testing.md`「定義を作る対象」の条件に当たらない）と決めたことを、既存の定義ファイルをランナーにかけ直さなくてよい理由と取り違えた。

2 回に共通するのは、読み込まれていて言い切る形の規約（1 回目は `AGENTS.md`「編集」の 3 つの鍵、2 回目は rule の全件の再実行）があったのに、その一部だけを当てて終えた点である。
どちらの回も、名前の変更そのものではなく、規約に当たる作業（1 回目は一括の書き換え、2 回目はテストの追加）をしていた。
1 回目は 3 つの鍵のうち `find` だけを確かめ、2 回目は定義を作るかだけを判断して、既存の定義の再実行を省いた。

## 根拠

2 回の観測（2026-10-29・2026-11-20）。どちらも、読み込まれていた規約の一部だけを当てて、`expect_failing` の古い名前を残したので、原因を 1 つに絞れている。
ただし、規約を一部だけ当てた理由は回ごとに違うので、同じ原因の再発には数えず、確信度は medium にした。
1 回目は一覧と突き合わせなかった。2 回目は、定義を作らない判断を、再実行を省く理由と取り違えた。
2 回目にランナーを実行しなかったことは、このセッションで実行したコマンドで確かめた。push の前にランナー以外で実行したのは、vitest・pre-commit・`/code-review`・`fallow audit`・`/security-review` で、`check-mutation-proof.ts` は CI が失敗した後に初めて実行した。
1 回目にどう考えて `find` だけを確かめたかは、当時の記録に無い。
KEDB 照合は「一括」「expect_failing」「テスト名」で行った。`docs/agent-workflow.md`「一括で書き換える前に、その文字列を鍵にする他のチェックを挙げる」が同じ事例（テストの名前を変えて別の定義の参照を見落とした）を持つ。

## 既存の規約

- 扱い: 明確
- 場所: `AGENTS.md`「編集」の一括の書き換えの箇条（内容のハッシュ・テスト名の参照・`find` の出現数を grep で挙げる）。`.agents/rules/state-space-and-mutation-proof.md`「assertion を書き換えたら、それに対する過去のミューテーションテストの結果は使えない」
- 照合した範囲: `AGENTS.md`「編集」、`.agents/rules/state-space-and-mutation-proof.md`、`docs/testing.md`、`docs/agent-workflow.md` を「テスト名」「expect_failing」「全件」で読んだ。
  どちらの規約も、失敗した作業で読み込まれる場所にある。`AGENTS.md`「編集」は一括の書き換えで 3 つの鍵を挙げることを言い切っており、1 回目はこれに当たる。
  rule は、テストを足したときの全件の再実行を言い切っており、2 回目はこれに当たる。名前を変えただけのときは、どちらの規約も言い切っていない。
  `docs/testing.md` の箇条はテストを消すときを扱うので、どちらの回にも当たらない

- 相手: なし

## 提案

テストを足す作業と一括の書き換えで、`expect_failing` を確かめる手順（定義ファイルの再実行・3 つの鍵の grep）を省く言い訳を、`state-space-and-mutation-proof.md` と `AGENTS.md`「編集」に書き、それでも従う理由を添える。名前を変えるだけの作業は、規約が言い切っていないので扱わない。

- 適用先の候補: `.agents/rules/state-space-and-mutation-proof.md`「assertion を書き換えたら」に、次の言い訳と理由を足す。
  「新しい判定には定義を作らないので、ランナーを実行しなくてよい」。定義を作るかと、変えたテストを `test_file` に持つ既存の定義ファイルをランナーにかけ直すかは別の判断である。
  2 回目はテストを足したので、この規約に当たっていた。規約の対象は広げず、規約に当たる作業で再実行を省いた理由への対策だけを足す。
- 適用先の候補: `AGENTS.md`「編集」の一括の書き換えの箇条に、3 つの鍵の件数をそれぞれ書いてから置き換える、と足す。1 回目の言い訳は記録に無いので書かず、手順だけを足す。
- 機構の候補（作るかは apply で決める）: pre-commit で、stage した `*.test.ts` の隣の `*.mutations.json` の `expect_failing` が、そのテストファイルに実在する名前かを確かめるチェック。
  効果は、2 回起きたこと。1 回目はローカルレビューが CI に届く前に見つけ、2 回目はローカルレビューが見つけず、CI の `Mutation proof (PR)` が exit 2 で止めた。
  どちらも merge される前に気付けたが、ローカルレビューは当てにできない。CI が止めたときに失うのは、push から CI の失敗までの 1 往復（数分）で、2 回目にだけ当たる。
  費用は、pre-commit でテストの一覧（`vitest list` など）を取る実行時間（対象のテストファイルごとに数秒）と、`test.each` で組み立てる名前を一覧と同じ形で扱う処理である。例外の一覧は要らない。
  言い訳を規約に書いた後で 3 回目が起きたら作る、という順序を推奨する。
