# 変異実証の合格を終了コードで判定すると、対象テストが走らない変異が「赤」に化ける

## 事象

Issue #404〜#410 の修正 7 件について、判定行を変異させてテストが赤くなることを
1 本のスクリプトで一括実証した。出力は 7 件すべて `exit=1`（＝赤）で、そのまま
「7 件とも変異で赤くなることを実証」と報告する直前だった。

ところが #405 の変異だけは、置換後のコードが構文エラーになる形
（`const realBase = baseDir;` ＋ 宙に浮いた `if (false)`）で、vitest の出力は
`Failed Suites 1` / `Tests no tests` だった。**対象のテストは 1 件も走っていない。**
スイートが起動できずに終了コードだけが非 0 になっており、
「テストが欠陥を弁別する」証拠には一切なっていなかった。

他の 6 件は `Tests N failed` が出ていたので実証として成立していたが、
合否を `exit code != 0` だけで見ていたため、成立している 6 件と成立していない 1 件が
同じ表示（`exit=1`）に潰れていた。#405 は変異を書き直して再実行し、
`× baseline_dir の外を指すシンボリックリンクを落とす` が赤くなることまで確かめた。

### 2 件目（2026-09-20・反対方向）

PR #418 で**変異が当たらないまま**テストが通り、「変異が生き残った＝assertion が
効いていない」と読みかけた。変異を当てるヘルパをこう書いていた:

```python
if s.count(old) == 1:
    io.open(p, "w").write(s.replace(old, new))
```

`old` のインデントを 14 スペースと書いたが実際は 12 だったため 0 件マッチ。
**何も言わずスキップ**し、未変異のコードで 20 passed を出した。
今回は違和感で気づき diff で確かめてやり直したが、
「赤くならなかった→assertion を足そう」へ進むと不要な検査を増やす。

同じセッション内では diff で確かめてもいる。規約を知らなかったのではなく、
ヘルパを書いたときだけ抜けた。

## 根本原因

1. なぜ実証になっていない変異を合格と読んだか → 合格の判定に終了コードだけを使ったから。
2. なぜ終了コードだけにしたか → 変異実証の目的を「テストランナーが失敗すること」と取り違えていた。
   目的は「**その変異を入れると、狙った assertion が落ちること**」であって、ランナーの失敗ではない。
3. なぜ取り違えたか → 正本（`.agents/rules/state-space-and-mutation-proof.md` §3）が
   「判定行を無効化する変異で赤くなることを実証してから green を根拠にする」と書いており、
   **「赤」の中身（対象テストが走ったか・狙ったテストが落ちたか）を定義していない**から ← 根本原因

横断スコープ: 同じ形は「陽性コントロール」全般に効く。非 0 終了・打ち切り・
起動失敗を「検出できた」に倒す経路は、`scripts/*.test.js` の変異実証だけでなく
`skills/*/evals/**` の故障注入・`skills/*/scripts/**` の強度ゲートにも同じ筋で現れる。

## 提案

変異実証の合格は終了コードではなく「対象のテストが走り、狙った assertion が落ちたこと」で判定する（構文を壊す・スイートを起動不能にする変異は実証にならず、非 0 終了が同じ表示に潰れる）。

`.agents/rules/state-space-and-mutation-proof.md` の「3. テストが効いていることの示し方」へ次を追加する。

- **変異実証の合格は終了コードで測らない。** 変異を入れた実行の出力から
  **走ったテスト件数と落ちたテストの名前**を取り、狙った assertion が落ちていることまで確かめる。
  `Failed Suites` / `no tests` / 収集エラー / import 失敗は「テストが効いた」ではなく
  **「実証できていない」**なので、変異を書き直して取り直す。
- **変異は対象の判定だけを無効化する最小の書き換えにする**（式を `false` に、比較を恒真に）。
  文の構造を壊す書き換えはスイートの起動を壊し、実証と起動失敗が同じ非 0 に潰れる。
- **複数の変異をまとめて回すときは、件ごとに「走ったテスト数」「落ちたテスト名」を出す。**
  終了コードだけを一覧にすると、成立した実証と起動失敗が同じ表示になり弁別できない。

### 2 件目の根本原因（なぜを 3 階層）

1. なぜ未変異のコードで測った? → 置換が 0 件マッチで無言スキップした
2. なぜ無言にした? → ヘルパを**複数ファイルに同じ変異を当てる**形にしたとき、
   一部のファイルにその文字列が無いのを正常としたかった
3. なぜそれが危険か? → 「当てたファイルが 0 件」と「全部に当たった」が
   **同じ出力（無出力）になる**。変異実証は「変異を当てた」を前提に
   結果を読むので、前提が黙って崩れると結果の読みが丸ごと反転する ← 根本原因

### 2 件目を受けた追加の提案

変異実証は「結果の読み方」だけでなく**「変異が当たったこと」を先に証拠化する**。

- 変異を当てる処理は `if match: replace` ではなく **`assert` で落とす**。
  複数ファイルへ当てる場合は、当てたファイル名と件数を印字し、0 件を FAIL に倒す
- テストを走らせる前に `diff` で差分を見る。差分が空ならその回は実証ではない
- `.agents/rules/state-space-and-mutation-proof.md`「3. テストが効いていることの示し方」へ:
  **変異実証は両方向に壊れる。** 変異がスイートを壊すと「偽の赤」に、
  変異が当たらないと「偽の生存」になる。当たったこと（diff）と
  落ちた assertion の名前を、毎回両方確かめる
