# 方針の選択肢を人に出す前に、前例と元の意図を調べる

## 事象

Issue #438（evals/ の配布方針）で 3 案を提示し、変更量の小ささから
案 3（据え置き）を推奨した。ユーザーが公開スキル集の前例と、evals/ を
配っていたのは意図的かを問い、調べると主要 7 リポジトリはスキル内に
evals を置かず、配置は skill-creator 既定の踏襲で意図は無かった。
推奨は案 1（移設）に反転し、判断の往復が 1 回増えた。

### 2026-10-15 の再発（#595、検出の方式の選択）

PR #639 で「〜する残り」の検出の抜けをレビューが 3 回続けて指摘した。
3 案（辞書のまま品詞で広げる／専用のチェック／機械の検出をやめる）を示し、変更量の小ささから案 1 を推奨した。
利用者に「漏れやすく辞書も増える」と問われて案 2 に変え、さらに「2 も都度改修にならないか」と問われて案 3 に変えた。
推奨が 2 回変わり、判断の往復が 2 回増えた。

### 2026-10-22 の再発（#757、変異の差分選択の範囲）

PR #770 のレビューで、差分選択がたどる import の範囲について、「広げる」と「狭める」の指摘が出た。
3 案を示して利用者に尋ねたが、open の Issue #747 が「共有ライブラリや依存の版の変更で影響を受ける定義は週次で確かめる」と、変異の定義を作る基準をすでに決めていた。
利用者に #747 を示されて方針が決まり、前の commit で足した変異の定義 2 件も消した。

## 根拠

同じ原因（open の Issue を調べずに選択肢を示した）で 3 回目である（2026-09-23・2026-10-17・2026-10-22）。

## 根本原因

- なぜ推奨が反転したか → 推奨の根拠が変更コストだけで、外部の前例と元の意図という判断材料が欠けていた
- なぜ欠けたか → 「公開済みの解を調べる」規律が AGENTS.md の「コンポーネント選択基準」節にあり、
  既存構造の配置・配布方針の判断には当たらないと読んだ
- なぜそうなったか → 規律の発動条件が「新しい仕組みを設計する前」と書かれ、既存の方針を決め直す場面を含まない
- （2026-10-15）なぜ推奨が 2 回変わったか → 各案を「問題の機序（分かりにくさは意味の問題）を満たせるか」で比べず、変更量で比べた
- （2026-10-15）なぜ機序で比べなかったか → 同じ種類の指摘が 3 回続いたら入力の形式を疑う規律（`.agents/rules/state-space-and-mutation-proof.md`）を、「方式を変える」とだけ読み、「そもそも機械で判定できる問題か」を問わなかった

## 提案

方針・配置を決める選択肢を人に提示する前に、同じ問題の公開済みの前例と、現状がそうなった元の意図（git 履歴・初出 commit）を調べて選択肢に添え、変更コストだけで推奨しない。

- AGENTS.md の「公開済みの解を調べる」規律を、コンポーネント選択基準の節から
  「新しい仕組みの設計と、既存の方針・配置の決め直し」の両方に機能する位置へ一般化する
- 前例が見つからなかった場合も「調べて無かった」と添え、未調査と区別する
- （2026-10-17）前例を調べる範囲に、実装済みのコードだけでなく open の Issue（計画済みの方針）を入れ、調べた範囲を回答に書く。
  Issue #611 の作業で、配布スキルに公開パッケージを同梱する前例を `skills/` だけで探して「無い」と答えた。
  open の #625 が `jsonc-parser` を同梱する形をすでに決めていて、利用者に指摘された
- 選択肢を比べるときは、各案が問題の機序をどこまで解決するか（残る見逃し・誤検知と、それが直し続ける必要を生むか）を先に書き、変更量はその後に比べる
