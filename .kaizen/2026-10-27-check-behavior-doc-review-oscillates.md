# チェックの挙動と判断の理由を文書に書く PR で、レビューの指摘に合わせて条件を足し引きし、前の回と逆の修正を求められ続けた

## 事象

issue-batch の #717（PR #790）と #677（PR #791）で、kaizen と agent-usage のコミット前のチェックが止める条件と、`if` を付けるかの理由を setup の文書に書いた。
レビューは毎回、実装と食い違う条件や抜けた場合を挙げた。条件を足すと次の回で「挙げ切る形が実装と合わない」と指摘され、消すと次の回で「消した情報がどこにも無い」と指摘された。
PR #791 では「いずれ要る抽出」を 4 回目で消し、5 回目で「消したので根拠が無くなった」と戻すよう求められた。`defaultDecision` の条件も同じように消してから戻した。
PR #790 は high 5 回・medium 2 回・low 1 回、#791 は high 5 回まで反復した。

## 根本原因

文書の一文に、実装のすべての分岐（設定の誤り・締め切り・lifecycle・ラッパー・引用）を正しく反映しようとした。
分岐の数だけ書き方があり、どこで切っても「書いていない分岐」と「書いた分岐と実装の差」のどちらかが残る。
それをレビューの 1 回ごとに局所的に直したので、前の回の判断の根拠（なぜその文を消したか）が次のレビューに伝わらず、同じ箇所を往復した。

## 提案

チェックの挙動を文書に書くときは、最初に、文書に置く粒度を決めて PR の本文に書く。

例えば「主な例だけを挙げ、網羅しないと明記する」「判断の根拠は 1 つの比較に絞り、ほかの止まり方は既存の節を参照する」と決める。
レビューがその粒度より細かい分岐を挙げたら、直さずに PR の本文の決定を引いて返信する。前の回に消した文を戻す指摘は、消した理由を返信に書いて見送る。
