# 偽の CLI を PATH に置いてエージェントを試すと、エージェント自身の起動もその偽物を使って失敗した

## 事象

Issue #855 の確認で、偽の `gh`（呼び出しを記録して起票しない）を PATH の先頭に置き、Copilot CLI を `-p --no-ask-user` で起動した。
Copilot CLI は自分のログインに `gh auth token --hostname github.com` を呼ぶので、偽物が JSON の空配列を返して認証に失敗し、スキルを読む前に終わった。
この実行は利用者に `!` で起動してもらっていたので、利用者にもう一度実行してもらう手戻りになった。
直した後に利用者へ示した対話の起動のコマンドでも、`PATH=<偽物> ... COPILOT_GITHUB_TOKEN=$(gh auth token) copilot` と書いたため、トークンは偽物から取得された。

## 根本原因

1. なぜ起動が失敗したか → 偽の `gh` が、試す対象の Copilot CLI 自身の認証の呼び出しにも応答した
2. なぜ偽物が認証に応答したか → 偽物の影響の範囲を、試す対象（スキル）が実行するコマンドだけだと考え、エージェント本体が同じ CLI を使うかを確かめなかった
3. なぜ確かめなかったか → 隔離の仕組みを書いた後、本番と同じ呼び出しで小さく起動して確かめずに、旧版と新版の本番の実行を始めた。`docs/agent-workflow.md` の「本番と同じ呼び出しで先に小さく試す」は、外部プロセスを動かすツールを書く場面として読み、偽物で隔離する場面に当てなかった ← 根本原因

## 根拠

失敗の原因を偽の `gh` の記録（`gh auth token` の行だけが並んだ）と Copilot の stderr（認証の方法の案内）で 1 つに絞れたが、観測は 1 回なので medium にした。
Codex の `codex exec` は同じ偽物で動いた（Codex は自分の認証に `gh` を使わない）。偽物を置く前に本物から取得したトークンを `COPILOT_GITHUB_TOKEN` で渡す形に直した後、Copilot の旧版と新版は起動できた。
KEDB 照合: `偽`・`gh`・`PATH` と `stub`・`PATH` は一致なし。`copilot`・`auth` は 3 件に一致したが、どれも Copilot のレビューや Actions の話で、原因が違う。

## 提案

偽の CLI（stub）を PATH の先頭に置いてエージェントや外部ツールを試すときは、試す対象の本体がその CLI を自分の起動や認証に使うかを、本番と同じ呼び出しで 1 回起動して確かめてから本番の実行に進む。

- 反映先の候補: `docs/agent-workflow.md`「外部プロセスを動かすツールは、本番と同じ呼び出しで先に小さく試す」に、偽の CLI で隔離する場合の 1 段落を足す
- 偽物に渡したくない値（認証のトークンなど）は、偽物を PATH に置く前に本物から取得し、試す対象だけが読む変数（Copilot CLI なら `COPILOT_GITHUB_TOKEN`）で渡す
- 前置きの代入（`PATH=<偽物> VAR=$(cmd) prog`）の中のコマンド置換は、同じ行の `PATH` の代入の後に評価されるので、偽物の側で実行される。本物の値が要るなら、別の行で先に取得する
- 機構は作らない。記録は 1 回で、試しの起動で気付ける
