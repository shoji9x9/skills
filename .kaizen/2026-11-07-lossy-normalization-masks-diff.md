# 比べる処理に正規化を当てるときは、正規化が情報を落とすかと、2 回当てても同じ値かを、それが成り立たない入力で確かめる

## 事象

PR #932 で、golden-dataset の表の読み方を GitHub の描画と比べるテストを書いた。
読んだ側と描画の側の両方に `normalizeCell`（バッククォートとアスタリスクを落とす処理）を当ててから比べた。
そのため、`count(*)` のアスタリスクが読み取りで消える食い違いを、テストが検出できなかった。ローカルレビューの指摘で初めて分かった。

追記（2026-11-09、Issue #929）: `parity-suite` の `runtime-errors.mjs` の `compare` が、基準の署名の id を作り直すときに、保存済みの正規化した欄へ正規化をもう一度当てていた。
正規化は 2 回当てると値が変わることがあった（`blob:` の URL、上限で切って末尾が空白になる本文）。そのため、正しい基準でも id が合わずに exit 2 になった。code-review の指摘で初めて分かった。

## 根本原因

- なぜ検出できなかったか: 両辺に同じ正規化を当てたので、正規化が落とした文字の差は両辺から同じように消えた。
- なぜその比べ方にしたか: 読んだ側の値が `normalizeCell` を通った形なので、描画の側も同じ形にそろえれば比べられると考えた。正規化が情報を落とすかは確かめなかった。
- なぜ確かめなかったか: `AGENTS.md`「確かめ方」の正規化の箇条は「両辺に同じ正規化を当てる」ことを求めているが、正規化が情報を落とすときに差が見えなくなることは書いていない。

Issue #929 で分かった原因は次のとおりである。

- なぜ id が合わなかったか: 保存した欄は正規化済みなのに、id を作る関数が正規化から始めていた。
- なぜその作りにしたか: 「欄から id を作り直す」を、署名を作る関数をそのまま呼ぶ形で書いた。
- なぜ気付かなかったか: テストの入力が、正規化を 2 回当てても変わらない形だけだった。
- 2 つの事象に共通する原因: 比べる処理に使う正規化の性質（情報を落とすか、冪等か）を、その性質が成り立たない入力で確かめていない。

## 根拠

確信度は medium である。2 つの事象とも、正規化の性質を確かめなかったという原因に絞れているが、性質は別（情報を落とす、冪等でない）なので同じ原因での再発とは数えない。
`count(*)` の入力を足して `normalizeCell` を直した後も、両辺に `normalizeCell` を当てる比べ方のままでは、記号を落とす形に戻してもテストが通った。
描画の側にテストの中で書いた畳み方を当てると、記号を落とす形で 4 件が落ち、今の形で 51 件が通った。
KEDB 照合では「正規化・テスト・両辺」と「normalize・比較」で照合し、一致は無かった。
Issue #929 では、`blob:` の URL と上限で切った本文の回帰テストが、修正前の実装で落ち、修正後に通ることを確かめた。KEDB 照合では、「正規化・冪等」は一致が無く、「正規化・id」はこのノートと 2026-11-05-judgment-state-placed-in-run-scope.md に当たった。読み比べて、このノートが同じ系統だと判断した。

## 既存の規約

- 扱い: なし
- 場所: `AGENTS.md`「確かめ方」の正規化の箇条（等しいかを比べる処理を正規化で直すとき）。両辺をそろえることだけを求め、正規化の性質（情報を落とす・冪等）には触れていない
- 照合した範囲: `AGENTS.md`・`docs/`・`.agents/rules/`・`skills/parity-suite/SKILL.md` を「冪等」で検索した（golden-dataset の投入ツールの冪等性だけが当たった）

## 提案

比べる処理に正規化を当てるときは、正規化が情報を落とすかと、2 回当てても同じ値か（冪等か）を確かめ、それが成り立たない入力をテストに足す。

- 保存した正規化済みの値から派生値（id・ハッシュ）を作り直すときは、正規化を当て直さず、派生の段だけを当てる。
- 適用先の候補: `AGENTS.md`「確かめ方」の「等しいかを比べる処理を正規化で直すときは」の箇条に、正規化が情報を落とすと差も消えることと、冪等でない正規化を当て直すと一致しなくなることを足す。
