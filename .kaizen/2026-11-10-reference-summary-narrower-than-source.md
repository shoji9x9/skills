# 原本を参照する側に書いた要約が、原本より狭い条件になった

## 事象

Issue #917 で、issue-batch の `references/orchestration.md` に、`pr-finalize-loop` の `references/review-response.md` の「人に回すかの基準」を読むと書いた。
その際、原本の止まる条件と当てる対象を要約で書き添えたところ、push 前のローカルレビューで 5 件の指摘を受けた。
1 つ目は、止まる条件の例が原本より狭かったことである（base 側で設定が変わった場合と base を決められない場合が抜けた）。
2 つ目は、「PR がまだ無いとき」の手順を仮の決定だけに当て、PR の前に出るローカルレビューの指摘を外したことである。
3 つ目は、`SKILL.md` の要約で、基準を読めないときだけを判断待ちの条件にしたことである。

## 根本原因

- なぜ要約が原本より狭くなったか: 原本の節を読んだ後、要約を記憶から組み立て、原本の条件の一覧と 1 件ずつ突き合わせなかった。
- なぜ突き合わせなかったか: 要約は「例」や「など」で書くので、網羅しなくてよいと考えた。しかし、例として選んだ条件が、読み手にとっては適用の範囲を決める。
- なぜそれが規約で防げなかったか: `.agents/rules/doc-altitude.md` は「参照する側には要約と原本の節名だけを置く」と定めるが、要約が原本の範囲（条件・対象）を狭めないことを確かめる手順を持たない。

## 根拠

確信度が medium なのは、1 回の観測だが、指摘の 5 件がすべて「原本と突き合わせずに要約した」ことに帰着するからである。
ローカルレビュー（`/code-review --fix`）が、止まる条件・当てる対象・`SKILL.md` の要約の 3 か所で、原本より狭いことを指摘した。
KEDB 照合（「原本」「references/」「要約」、「止まる条件」「review-response.md」、「参照する側」「例」「狭」）では、同じ原因の学びは無かった。一致した `2026-10-14-worktree-bash-literal-guard-recurs.md` は別の事象である。

## 既存の規約

- 扱い: なし
- 場所: なし（`.agents/rules/doc-altitude.md`「文書に載せる粒度と、文書の階層」は、参照する側に要約を置くことを定めるが、要約の範囲を確かめることは定めない）
- 照合した範囲: `AGENTS.md`・`.agents/rules/`・`docs/`・`skills/writing-style/` を「原本の節名」で検索した

## 食い違い

- 相手: なし
- 判断: なし

## 提案

原本を参照する側に要約や例を書いたら、原本の条件・対象の一覧と 1 件ずつ突き合わせ、要約が原本より狭くならないこと（例は「など」で終え、対象と止まる条件は原本と同じ範囲にする）を確かめてから commit する。

- 置き場所: `.agents/rules/doc-altitude.md` の「重複を原本への参照にまとめるとき」に、4 番目の確認として足す。
- 突き合わせるのは、止まる条件・当てる対象（どの段階・どの種類の入力か）・例外の 3 つである。
- 要約を 2 か所（`SKILL.md` と `references/`）に置くなら、両方を同じ範囲にする。
