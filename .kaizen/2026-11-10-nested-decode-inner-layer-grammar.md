# 符号化を 1 段だけ外して既存の判定に渡すときは、外した後の層の文法の形も挙げる

## 事象

Issue #916 で、kaizen の commit 前のチェックが jq も python3 も無いときに使う生の JSON の判定に、Copilot の `toolArgs`（JSON の文字列）を 1 段だけ復号する処理を足した。
外側の文字列のエスケープ（`\"`・`\\`・`\uXXXX`）は状態として挙げてテストにしたが、復号した後の内側の JSON に残る `\u0063ommit` のような ASCII の `\u00XX` は挙げなかった。
push 前のローカルレビューも見落とし、PR #988 の Codex のレビューが指摘した。jq と python3 は内側の JSON も解析して `git commit` と読むので、生の JSON の判定だけが commit を通していた。
修正の commit と、変異の定義 2 件の追加で手戻りした。

同じ PR で、同じ種類（生の JSON の判定が JSON の `\u` を読まない）の指摘がさらに 2 回続いた。
外側のキーを `tool\u0041rgs` と書く形と、最初の絞り込みが `git \u0063ommit -m x` を jq に渡す前に通す形である。後者は main の jq がある環境でも通していた。
2 回目からは、層ごとに分岐を足さず、入力の全体に ASCII の `\u00XX` があれば止める形と、絞り込みで `\u` を含む入力を次の段に渡す形にした。
最初に「この判定は JSON の `\u` をどの層でも読まない」と 1 行で書いていれば、3 回の往復は 1 回で済んだ。

## 根本原因

- なぜ内側の `\u` を見落としたか: 復号した結果を「既存の正規表現がそのまま扱える JSON」とみなし、新しく書いた層（外側の文字列）の文法だけを列挙した。
- なぜそうみなしたか: 復号した結果を渡す先の既存の判定（`"command"` を探す正規表現）が、もともと JSON の `\u` を読まない近似であることを確かめなかった。既存の判定が扱えない形は、新しい層を足すと、その層の中にもそのまま現れる。
- なぜ確かめなかったか: 規約の「入力の文法が許す形から状態を挙げる」を、自分が書いた処理の入力にだけ当て、処理の出力を受け取る既存の判定の入力（外した後の層）には当てなかった。基準にする実装（jq）は全段を解析するので、比べる相手は「全段を解析した結果」である。

## 根拠

確信度は medium である。1 回の観測で、原因を「外した後の層の形を挙げなかった」の 1 つに絞れている。
レビューの指摘の後、内側の `\u0063ommit` を入れた入力で生の JSON の判定が exit 0 になることを確かめ、修正後に exit 2 になることと、変異で落ちることを確かめた。
KEDB 照合（「エスケープ」「jq」「復号」）では、一致する学びは無かった。

## 既存の規約

- 扱い: 明確
- 場所: `.agents/rules/state-space-and-mutation-proof.md`「入力を解析する処理は、入力の文法が許す形から状態を挙げる」（エスケープと入れ子を挙げている）
- 照合した範囲: `AGENTS.md`・`docs/agent-workflow.md`・`.agents/rules/` を「文法が許す形」「入れ子」「1 段」「正規化」で検索した。`AGENTS.md`「等しいかを比べる処理を正規化で直すときは、ずれうる軸をすべて挙げ」は、比べる処理を直す場面の規約で、別の判定の入力を作る今回の場面には当たらない

## 食い違い

- 相手: なし
- 判断: なし

## 提案

符号化（JSON の文字列・URL・引用）を 1 段だけ外した結果を既存の判定に渡すときは、外した後の層の文法の形も挙げ、既存の判定が読めない形を判定できないとして扱うかを、全段を解析する基準の実装と同じ入力で比べて確かめる。

- `.agents/rules/state-space-and-mutation-proof.md`「入力を解析する処理は、入力の文法が許す形から状態を挙げる」の段落に、上の 1 文を足す。理由は、規約が明確でも、自分の書いた層の入力にだけ当て、出力を受け取る判定の入力に当てなかったことである。
- 機構は足さない。記録は 1 回だけで、`check-cost-benefit.md` の基準では規約の追記で閉じる。
