# 共有契約の変更は消費側を逆引きしてからコミットする

## 事象

レビューツールの設定解決へ CLI と環境変数を追加したが、初回コミット前に issue-batch の handoff と基底ドキュメントの旧 YAML 前提を更新できなかった。また、ソースリポジトリ固有の mise 設定が配布先にも効くように読める README 記述を残し、Codex レビューで 3 件の手戻りになった。

## 根本原因

定義元の pr-finalize-loop と pr-review-handle の整合だけを確認し、設定値を読む箇所ではなく名前が既知の姉妹スキルだけを対象にした。これは共有契約の「定義」を直せば完了と考えたためであり、さらに配布境界をまたいだときにルート設定が同梱されるかというライフサイクルを通していなかったことが根本原因である。

## 提案

共有設定の解決規則を変えたら、commit 前に設定名・handoff 先・要約文を横断検索し、定義元だけでなく全消費側と配布境界を通した代表フローを突き合わせる。

grep は新しい設定名だけでなく変更前の設定名と委譲先スキル名でも行う。ルート設定に依存する説明は、配布物へ同梱されるかを確認し、同梱されないならソースリポジトリ固有と利用側手順を分けて書く。

## 再発（2026-09-14, claude-code, #361 / #360）

### 再発の事象

parity-diff の `references/capture-new.md` に「`popup_inventory` が不整合なら停止」という新ゲートを足したが、同じ条件を構造化して再掲する箇所
（同ファイルの「5 キー」表・`assets/diff-metadata-template.json` の `capture_conditions_verified`・`assets/diff-template.md` の「5 項目」行・停止条件の総括文）と、
待ちの契約を迂回しうる parity-replace の操作アダプタ分岐・parity-component の主採取経路が追随しなかった。コミット前の Sonnet サブエージェントレビューで 4 件検出し手戻り。

### 再発の根本原因

- なぜ漏れた? → 足した語（`popup_inventory`）でしか grep しなかった
- なぜ既存要素名で grep しなかった? → `docs/skill-development.md` 整合パス項目 5 に書かれているが、実装完了を報告する前にパスを実行していない
- なぜ実行しない? → 整合パスは rule から参照される散文で、完了報告の前に通過を示す強制点が無い ← 根本原因（規約止まり）

### 再発への提案

既存の条件リスト（停止条件・検証キー表）へ項目を足したら、足した語ではなく隣接する既存要素名（例: `masks / states`）で `skills/` 横断 grep し、
テンプレート・表の件数（「N キー」「N 項目」）まで直してから完了報告する。
強制点候補: issue-start の完了報告前に整合パス実行結果（grep した既存要素名とヒット件数）の提示を必須にする。

## 再発（3 回目: 2026-09-16, claude-code, PR #379）

### 3 回目の事象

codex レビュー第 1 ラウンドの 2 件を直したが、第 2 ラウンドの 2 件は**いずれもその修正自身の取りこぼし**だった（レビュー 1 往復ぶんの手戻り）。

- P1: 根拠を行単位から口単位へ変えたが、`status` の検出は「`推定` があるか」のままで、
  **修正が新たに生んだ状態**（完全対応づけ／**部分対応づけ**／未対応づけ／空欄）のうち部分対応づけを拾えなかった
- P2: 根拠の形に「API / UI の実動作」を足したが、**その語彙を読む消費側**（Issue 本文の「読むべき入口の問い合わせを残す」）へ伝播させず、
  入口モジュールが受領資産に無い場合に実行不能な作業を渡す矛盾を、自分の修正の中に残した

### 3 回目の根本原因

- なぜ漏れたか? → 指摘されたインスタンスを直して終わり、「修正が新たに生む状態」と「新語彙の消費側」を列挙しなかった
  - なぜ列挙しなかったか? → 既存規約（`.agents/rules/state-space-and-mutation-proof.md` §4）は
    「**同じファイル・同じ関数内の同型インスタンス**を grep で掃き出す」軸だけで、今回の 2 軸（修正後の状態空間・語彙の消費側）を指定していない
    - なぜ気付かないか? → `AGENTS.md` の「新設した分岐・新たに受理する入力クラスは、その状態を作って**実測する**」は
      実行可能なコードを前提にしており、**文書契約**では「実測」に対応する行動が無いため、列挙工程ごと飛ばされる ← 根本原因

### 3 回目への提案

レビュー指摘を直したら、「その修正が新たに生む状態」と「新しく導入した語彙を読む消費側」を同じ変更の中で列挙してから返信する。
文書契約では「実測」の代わりに**全分割を表に書き出し、各行がどの記述で拾われるかを 1 行ずつ対応づける**（拾えない行が残るなら未完）。

## 4 回目（2026-09-17, claude-code, #331）—— 書き手を足すとき、書く値の名前空間を見ていない

### 4 回目の事象

共有レジストリ `intentional_diffs.pending` の書き手一覧へ `parity-component` を足した（Issue #331）。
書き手の列挙（表・スキーマ例・消費側の文書）は 3 箇所とも追随させたのに、**その書き手が `slug` に書く値が別の名前空間だった**。
`project-config.md` は `slug` を機能 slug（`.replace/features.md`）と定めるが、`parity-component` は部品 slug（`.replace/components.md`）を書く。
消費側 `pending-triage-check.mjs` の `inScope()` は機能 slug / `cross-cutting` / null しか対象に入れないため、
その追記は**どの機能の収束判定でも対象外**になり、exit 0 のまま永久に棚卸しされない（fail-open）。PR レビューで検出。

### 4 回目の根本原因

- なぜ漏れたか? → 「書き手一覧」というキーの**名前**の整合だけを追い、書き手が入れる**値の定義域**を突き合わせなかった
  - なぜ突き合わせなかったか? → 3 回目までの提案がすべて「語彙（名前）の消費側を列挙する」軸で、
    **値の定義域が書き手ごとに違いうる**という軸を持っていない
    - なぜ気付かないか? → 不一致の症状が「落ちる」ではなく「**対象 0 件で合格**」なので、
      テストも実行も緑のまま通る ← 根本原因（fail-open は列挙の漏れと同じ見え方をする）

### 4 回目への提案

共有レジストリに**書き手**を足すときは、その書き手が各キーへ入れる値が**キーの定義域と同じ名前空間か**を 1 キーずつ確かめ、
違うなら書き手側の契約で予約語へ寄せる（今回は `cross-cutting`）。

- 判定が「一致しなければ対象外」で表現されている消費側は、**知らない値を黙って対象外にする**ので、
  不一致を**検出して対象へ倒す**分岐を消費側に足す（`pending-triage-check.mjs` の
  `CROSS_CUTTING_ONLY_WRITERS`）。文書だけで縛ると、同じ fail-open が次の書き手で再発する
- 反映先: `.agents/rules/state-space-and-mutation-proof.md` に「識別子は値の一致だけでなく**出どころの名前空間**も状態空間に入れる」を足す
