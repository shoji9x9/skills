# 追跡 Issue の本文の「作成・更新・クローズします」を、無条件に閉じる意味に読んだ

## 事象

Issue #1131（費用の指標の追跡 Issue）で、4 件の候補をどれも変えないと決めた後、「ワークフローが閉じる取り決めなので任せる」と報告して Issue を開いたまま残した。
利用者から、ワークフローは閉じずに翌週に本文を書き換えるのではないか、完了した Issue が分かりにくくなるので閉じてほしい、と指摘された。
`.github/workflows/check-cost-metrics.yml` を読むと、閉じるのは候補が 0 件のときだけで、候補が残れば同じ Issue のタイトルと本文を書き換える。
人が閉じた後は、`tracking-issue-lib.sh` の `find_tracking_issues` が open の Issue だけを探すので、翌週は新しい Issue を作る。

## 根本原因

- なぜ誤って報告したか: Issue の本文の「この Issue は `Check cost metrics` ワークフローが作成・更新・クローズします」を、ワークフローの挙動の全体として読み、ワークフローを読まずに述べた。
- なぜその文を挙動の全体として読んだか: 文がクローズの条件（候補が 0 件のとき）を書かず、人が対応を終えたときにどうするかも書いていない。読み手は「対応を終えれば閉じる」と補ってしまう。
- なぜ条件の無い文が残っているか: 本文を作る 5 つのスクリプトが、同じ文を持っている。
  対象は `check-cost-metrics.ts`・`self-review-issue.ts`・`security-audit-issue.ts`・`ignored-advisories.ts`・`check-pricing-drift.ts` である。どのワークフローも、閉じるのは対応の要る項目が 0 件のときだけである。

## 根拠

確信度は、1 回の観測で、ワークフローの閉じる条件を読んで原因を 1 つに絞れたので medium にした。
Issue #1131 の対応を終えた報告の直後に、利用者がクローズの挙動を指摘した。`check-cost-metrics.yml` の分岐（`due` が 0 のときだけ `gh issue close`）と、`find_tracking_issues` の `--state open` で、指摘のとおりだと確かめた。
KEDB 照合（「クローズ」「追跡 Issue」、「閉じる」「check-cost-metrics」）は、どちらも一致なし（exit 1）だった。

## 既存の規約

- 扱い: 明確
- 場所: `AGENTS.md`「確かめ方」の最初の箇条（ツールの挙動は、述べる前に読むか、検索するか、実行して確かめる）
- 照合した範囲: `AGENTS.md`・`docs/`・`.agents/rules/` を「クローズ」「追跡 Issue」「作成・更新・クローズ」で検索した

## 食い違い

- 相手: なし
- 判断: なし

## 提案

ツールが自分の挙動を説明する文（Issue の本文・コメント・ログ）を挙動の根拠にせず、条件の分岐を持つ処理を読んでから述べ、説明の文の側にも条件を書く。

- 5 つのスクリプトの「作成・更新・クローズします」を、条件を書いた文に直す。例として、対応の要る項目が 0 件になった週に閉じること、項目を残したまま対応を終えたら人が閉じること、閉じた後に項目が残っていれば次の実行が新しい Issue を作ることを書く。
- 機構は作らない。文を直せば、読み手が補う箇所が無くなるからである。
