# 切り離した起動は失敗が終了コードに残る形で書き、入力は正本から読む

## 事象

ベースライン eval の再実行をバックグラウンド起動し、完了通知（exit code 0）を見て
ユーザーへ「再起動しました」と報告した。実際には 1 コマンドも走っていなかった。

投げたのは次の形:

```bash
PROMPT="$(cat <scratchpad>/eval15-prompt-v2.txt)" && python3 -c '...' && scripts/run-skill-eval.sh ... ; echo "rc=$?"
```

scratchpad のファイルはセッション再開でディレクトリごと変わっており存在しなかった。
先頭の `cat` が失敗して `&&` チェーンが短絡し、末尾の握り潰しがラッパーの終了コードを 0 にしたため、
通知は「completed (exit code 0)」になった。
出力ファイルを開いて初めて `cat: ... No such file or directory` を見つけ、
報告を訂正して起動し直した（1 往復の手戻りと、誤った状況報告）。

## 根本原因

- なぜ走っていないのに完了通知が出たか → 末尾に `|| echo "exit $?"` を置き、
  チェーン全体の失敗をラッパーの exit 0 へ化けさせた。成否を判定する器を自分で壊した
- なぜチェーンが短絡したか → 先頭の `cat` が失敗した。読んでいたのは正本ではなく
  scratchpad に写したプロンプトのコピーで、セッション再開でパスごと消えていた
- なぜ写しを読んでいたか → 同じ入力を複数回使うので一時ファイルに置いた。
  正本（`skills/parity-diff/evals/evals.json`）から毎回読めば消えようがなかった ← 根本原因

横断スコープ: 既存の `2026-07-05-pipeline-exit-code-masking`（パイプ越しの `$?`）と
`2026-08-25-background-job-liveness-not-output-file`（出力ファイルで生死を判定しない）が
近縁だが、いずれも別の故障形。今回は「起動コマンド自体が無言で短絡し、
握り潰しによって完了通知が成功に見えた」経路で、`AGENTS.md` に対応する規律が無い。

## 提案

切り離して起動するコマンドは失敗が終了コードに残る形で書き、入力に正本があるなら
セッション寿命の一時ファイルへ写さず正本から読む。`|| echo "exit $?"` のような
握り潰しを付けると、起動自体が短絡しても完了通知が成功に見える。

- 適用先候補: `AGENTS.md` のワークフロー節（「切り離した仕事の生死は出力ファイルではなく
  プロセスの実在で判定する」の直後）に 1 行追記する
- 起動前に入力の非空を確認する（`[ -n "$VAR" ]`）ことも同じ故障を塞ぐ
