# 再発を機構で防ぐときや、指摘で状態の扱いを足すときは、分岐を足す前に、原因の側で閉じるか、扱う状態を減らせないかを試す

## 事象

Issue #425 で 09-16 の学びを適用したとき、ノートの提案どおり `bash-command-guard.sh` に「整形ツールへのディレクトリ引数」を止めるルールを足した。
呼び出しの形をシェルの近似で読むので、PR #585 のレビューが 5 回続けて新しい誤検知と見逃しを指摘し（7→8→4→4→6 件）、自分の呼び出しも 3 回止めた。
最後に、原因の側（ツールが種類を問わず整形する）をツールの設定（`ignores`・`ignorePatterns` の許可リスト）で閉じてルールを外した。
設定は数行で、どの渡し方でも割り当て外の種類は変わらない（実物のツールで実測）。

同じ PR のランナーの後始末（`scripts/mutation/check-mutation-proof.ts`）でも同じ形が起きた。
レビューの指摘（元の内容に戻された・消された・書く前の失敗・途中の書き込みの失敗）のたびに分類と分岐を足し、3〜7 回目のレビューで指摘が続いた。
7 回目に、消された対象を作り直す処理をやめた（扱う状態を減らし、止めて復元情報を残す）。
それで、作り直しに伴う指摘 3 件（モード・親ディレクトリ・意図した削除）がまとめて不要になった。

2026-10-13（PR #615）で再発した。oxlint の `no-restricted-properties` を型ガードのファイルでファイル単位に外し、その分の検出を自前のチェック（`check-skill-lint-directives.ts`）で作り直した。
行の正規表現・構文木・行番号の比較と近似を変えるたびに、レビューが 5→3→2 件の別の形を指摘した。
指摘された形は、文字列の中の `//`、改行を挟んだ参照、文字列のキーの分割代入、2 回の束縛、同じ行の関数の前後である。
2 巡目で、判定を同じ規則の oxlint に任せる形（原因の側）に移し、書き方の列挙は不要になった。
ただし「型ガードの中か」を行番号で近似したため、もう 1 巡かかった。

## 根本原因

- なぜ 5 回かかったか → 呼び出しの形（シェルの文法）は列挙しても尽きず、直すたびに別の形が見つかった
  - なぜその形を選んだか → ノートの提案が書いていた機構（PreToolUse で止める）をそのまま作った
    - なぜ別の置き場所を検討しなかったか → kaizen の `references/apply.md`「決定性で選ぶ」は、文章より機構を優先すると書くが、
      機構の中でどこに置くか（原因を持つ側の設定か、呼び出し側の検査か）を選ぶ観点が無い ← 根本原因
- 呼び出し側の検査に限らず、指摘のたびに状態と分岐を足す直し方そのものにも、観点が抜けている。
  「その状態を扱わずに止める」という選択肢を検討する観点が無い

## 提案

再発を機構で防ぐときやレビューの指摘で状態の扱いを足すときは、分岐を足す前に、原因を持つ側で閉じるか扱う状態を減らして止められないかを実測で試す。

- 適用先: kaizen の `references/apply.md`「決定性で選ぶ」に 1 項目足す（配布スキル）
- 呼び出し側の検査が「別の形」の指摘を 2 巡続けて受けたら、直し続けずに原因の側へ置き場所を移す
  （2026-09-23-relaxation-evidence-grammar の「2 巡で許可リストへ」と対にする）
- 指摘が「この状態の扱いが足りない」の形で 2 巡続いたら、扱いを足す前に、その状態を扱わずに止める形（自動の回復をやめる）を候補に挙げる
- ツールの規則をファイル単位で外したら、その分の検出を自前で作らず、同じ規則をそのファイルに当てて結果を後で処理する（最初からそうすれば 3 巡は要らなかった）
- 位置を突き合わせるときは、行ではなく両者の文字位置を同じ単位（バイトか UTF-16）にそろえて比べる。単位は実測で確かめる（oxlint の offset は UTF-8 のバイトだった）
