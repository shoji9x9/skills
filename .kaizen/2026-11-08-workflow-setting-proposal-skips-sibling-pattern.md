# ワークフローの設定を直す案を、同じリポジトリのワークフローが持つ選び方を見ずに、値を固定する形で出した

## 事象

Issue #940 の週次のセルフ点検（`self-review.yml`）を Actions で初めて実行したところ、`claude-code-action` のデフォルトのモデルで点検が浅くなり、canary の判定で失敗した。
直す案として、`claude_args` に `--model claude-opus-5-5` を足して固定することを示した。
利用者は、モデルを選べるようにし、デフォルトは今のままにするよう指示した（Issue #953）。
同じリポジトリの `kaizen-schedule.yml` は、モデルを入力と設定（`KAIZEN_SCHEDULE_MODEL`）で選べる形を既に持っていた。

## 根本原因

- なぜ固定する案を出したか → 失敗した 1 回の実行を直すことだけを考え、手元で成功したモデルをそのまま書けば足りると考えた
- なぜ選べる形に気付かなかったか → 案を出す前に、同じ問題を持つ既存のワークフロー（エージェントを動かす `kaizen-schedule.yml`）の設定の持ち方を確かめなかった。
  `AGENTS.md`「確かめ方」の「方針・配置の選択肢を人に示す前に、同じ問題の公開済みの解と元の意図を調べる」を、ワークフローの設定の案に当てなかった
- 費用（使用量）や品質がモデルで変わる設定は、利用者が後から変えたい値で、固定するとワークフローを変える PR が毎回要る

## 提案

ワークフローの設定の値（モデル・runner・閾値など）を変える案を示す前に、同じリポジトリのワークフローが同じ種類の値をどう持っているか（リポジトリ変数・`workflow_dispatch` の入力・設定ファイル）を grep で確かめ、その形に合わせた案を先に出す。

- `.agents/rules/github-actions-authoring.md` に、利用者が後から変えたい値（モデル・runner）はリポジトリ変数などで選べる形にし、既存のワークフローの持ち方に合わせる、と足す
