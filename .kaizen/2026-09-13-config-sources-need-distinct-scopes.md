# 設定ソースは異なるスコープを担うものだけ追加する

## 事象

一時的にレビューツールを切り替える要件に対し、共有 YAML に加えて GitHub Repository Variable、clone ローカルの `.git/config`、環境変数を順に提案した。ユーザーの指摘を受け、ローカル用途には CLI・環境変数・共有既定だけで十分と整理し直したため手戻りが生じた。

### 2026-10-18 の再発（#625: 設定の層と環境変数の使い分けを説明せずに提案した）

設定の置き場所をそろえる Issue で、`SKILLS_REVIEW_TOOL` を「人ごとの層に置けるようにし、環境変数は一時的な上書きとして残す」と提案した。
ユーザーから「人ごとの層もリポジトリを汚さないので一時的な上書きである。使い分けは何か」と問われ、環境変数にしか無い利用場面を答えられなかった。
人ごとの層が全リポジトリに適用されることと、`.env.local` が「このリポジトリの自分だけ」に適用されることを区別しておらず、後者の層（`.local.jsonc`）が抜けていた。
続けて eval の隔離に `SHOJI9X9_SKILLS_USER_CONFIG_DIR`（人ごとの層の置き場所を変える変数）を提案し、「テスト目的でなく定義するとどうなるか」と問われた。
置き場所が 2 つになることを答えられず、「人ごとの層を読まない」変数に設計し直した。

## 根本原因

設定を永続化したいという表面的な要求から、技術的に利用可能な保存先を追加した。これは利用者・有効期間・共有範囲を先に分類しなかったためであり、さらに既存の設定ソースと新しい設定ソースが異なる責務を持つかを検証せず、選択肢の多さを柔軟性とみなしたことが根本原因である。

2026-10-18 の再発では、この学びは適用されないまま忘却されていて、提案の前に参照されなかった。
層を提案するときに、値を適用する範囲（全リポジトリ・このリポジトリの自分・全員）と、値を残すか 1 回だけかの 2 軸で表を作らなかった。
新しい変数を提案するときにも、意図した使い方（eval の隔離）の側だけを考え、目的の外で設定されたときの振る舞いを挙げなかった。
これは `docs/agent-workflow.md` の「対称な反対側を当てる」の、意図した利用者と意図しない利用者の対を当てなかったことに当たる。

## 提案

設定の層や環境変数を提案する前に、各層に固有の利用場面（値を適用する範囲 × 残すか 1 回だけか）を 1 行で書き、目的の外で設定されたときの振る舞いも 1 行で書いてから示す。

- 適用先は `docs/skill-development.md`「スキルの設定を足す」の手順 1（キーと `x-env` を足すとき）。
- 層と環境変数の基準そのものは、#625 で `skills/*/references/config-files.md`「どの層に置くか」「環境変数にする値」に書いた。
- 設定ソースを追加する前に利用者・有効期間・共有範囲・原本を列挙し、既存ソースと責務が重なるものは追加しない。
