# 「他が落とすから自分は落とさない」緩和は、その「他」の実在と実行を検査しないと fail-open になる

## 事象

`pending-triage-check.mjs` の緩和（Issue #347。**別機能に帰属すると読めている要素の形の不備は `warn:` だけにして、いま閉じたい機能を止めない**）に対し、
PR #397 のレビューが **3 巡連続で同じ fail-open を別経路から** 指摘した。いずれも「対象 0 件・exit 0」で閉じられ、その要素は永久に棚卸しされない。

| 巡 | 緩和を通り抜けた入力 | 委譲先が存在しない理由 |
|---|---|---|
| 1 | `added_by: parity-component` ＋ 部品 slug | 部品 slug は機能 slug と別の名前空間。その slug の収束判定は存在しない |
| 2 | `added_by` 欠落 / `unknown` / 未知のスキル名 ＋ 任意の slug | 書き手が読めないので slug がどの名前空間かも確認できない |
| 3 | `added_by: parity-suite`（正規）＋ 綴り違いの slug | インベントリに無い機能なので、その収束判定は一度も走らない |

3 回とも、指摘されたインスタンスを直して「同じ関数を掃き出した」と返信した直後に、次の経路が出た。

## 根本原因

1. なぜ 3 回とも残ったか → **緩和の正当化（「その要素はその機能の棚卸しが落とす」）を、条件ではなく前提として書いた。**
   条件なら検査できるが、前提は検査されない。
2. なぜ前提のままにしたか → 直した経路を状態空間の 1 セルとして埋めるだけで、
   **「委譲先が存在すること」自体を判定式に入れなかった**。
3. なぜ入れなかったか → 既存ルールは「緩和経路は閉じた集合として列挙する」（`state-space-and-mutation-proof.md` §1）と定めるが、
   列挙の対象を**入力クラス**と読んでいた。この緩和で列挙すべきだったのは入力ではなく
   **委譲先（誰がこの要素を落とすのか）**で、入力側をいくら列挙しても委譲先の不在は現れない ← 根本原因

KEDB 照合: `.kaizen/2026-09-08-overdetection-fix-is-itself-a-relaxation.md` は緩和の**向き**（過検出の修正が緩和になる）を扱う別事象。
`.kaizen/2026-09-17-mutation-proof-is-not-enumeration.md` の 4 回目は**軸の値**（「読めない」を軸に入れる）で、本記録は**軸そのもの**（委譲先）が無い話。

## 提案

判定を他所へ委譲して自分は落とさない緩和は、委譲先を判定式に含めて実在と到達可能性を検査し、確認できないものは緩和せず自分で落とす。

- 緩和を書くときは正当化の文（「その要素は〜が落とす」）から**主語を取り出し、それが検査されているかを見る**。
  検査されていなければ、その主語は前提であって条件ではない
- 委譲先が**名前で指されている**なら、その名前が実在することを確かめる入力（インベントリ・レジストリ）を判定へ渡す。
  渡されていない実行では緩和を適用しない（fail-closed）
- 委譲先が**将来の実行**（「その機能の次回の収束判定」）なら、実行されない場合の回収経路を出力に残す
  （件数の `note:` など。件数 0 と未実行を同じ見え方にしない）
- 反映先: `.agents/rules/state-space-and-mutation-proof.md`「1. 状態空間に入れるもの」の
  「fail-closed に緩和経路を置くなら」の項へ、**入力クラスに加えて委譲先を列挙する**ことを足す
