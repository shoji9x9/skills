# 照合・集計の状態空間には「値」だけでなく「キーの材料」を入れる

## 事象

Issue #274 で `parity-diff` に fail-closed の収束ゲート `scripts/coverage-check.mjs` を新設し、
被覆表のセル値（`present` / `absent` / `unmeasured`）・行の欠落・`evidence` 空・`covered_by` 空について
陽性／陰性コントロールを 16 件書いて全て green にした。

`/code-review` が、その状態空間の外にある fail-open を検出した。列挙側（`components[].items[]` /
`instances[]`）の要素に `id` が無いと `String(c.id)` が `"undefined"` へ潰れ、**全期待セルが同一キーに収束**する。
そこへ `component` だけを持つセル行が 1 件あれば `cells:2, present:2, unmeasured:0, problems:[]` で exit 0——
fail-closed を目的に作ったゲートが、1 件のデータで全件を満たして素通りする。`items` に同じ id が 2 つある場合も
期待セルが二重に数えられ、1 行で両方が `present` になった。

## 根本原因

1. なぜテストが捕まえなかったか → 状態空間の列挙を「セルが取りうる値」と「行の有無」に閉じ、
   **突き合わせに使うキーの材料**（`component` / `item` / `instance` の id）を状態空間に入れなかった。
2. なぜキーの材料が漏れたか → 「何を測るか（値）」は仕様（`coverage.md`）に列挙されているが、
   「何で突き合わせるか（キー）」は実装の内部事情で仕様に現れない。仕様から assertion を逆引きする手順では構造的に落ちる。
3. なぜ既知の故障クラスを参照できなかったか → **同じ故障クラスを 1 日前に同じスキルで直している**
   （Issue #273 / commit 2198c63: `component_diffs` の照合キー欠落が「どの要素にも合う」に化ける。
   その回帰テスト `scripts/diff-normalize-component-match.test.js` は本セッションで読んでいた）。
   KEDB 照合は「学びの抽出時」の手順であって、**実装の設計時に既知故障クラスを引く手順が無い**。← 根本原因

KEDB 照合（`照合` / `キー` / `fail-closed` × `parity-diff`）では
[[2026-07-30-negative-result-checks-need-positive-control]]（0 件を合格根拠にしない）と
[[2026-08-30-new-state-branches-need-fixtures]]（新設分岐の状態空間）が近いが、どちらも別軸——
前者は「検査が動いていない」、後者は「自分が足した分岐」を扱い、
本件の「キーが潰れて別対象が同一視される」は覆っていない。

横断スコープ: `trait-compare.mjs:139` の `new Map(entries.map((e) => [e.name, e]))` は
`name` 欠落の複数エントリが 1 キーへ潰れて後勝ちになる（同型）。
`json-normalize-diff.mjs` のドット記法パス解決、`component_diff_exception_causes[].id` ↔ `cause` の参照、
`replace-strategy status` の slug × target 集計も同じ構造を持つ。

## 提案

照合・集計・突き合わせを行うコードは、判定に使う**値**の状態空間だけでなく、
**キーの材料**（id・照合キー・論理名）の欠落・空文字・重複・型崩れも状態空間に入れ、
「キーが潰れて 1 件のデータが全件を満たさないこと」を陰性コントロールで実測する。
キーを文字列化して索引にする実装（`String(x)` / テンプレートリテラル / `Map` の key）は、
欠落が `"undefined"` という**有効なキー**に化けるため、欠落を先に弾いてから索引に入れる。

加えて、既知故障クラスの参照点を抽出時だけでなく**実装の設計時**にも置く——
同種の照合・集計を書く前に、そのスキル・スクリプトの直近の修正（KEDB と git 履歴）を引き、
同じ故障クラスの陰性コントロールを最初から移植する。

## 再発（2026-09-02・後方互換の緩和経路）

同じ PR の Copilot レビューが、同じスクリプトにもう 1 つの fail-open を検出した。
`readDeclaration()` が「`metadata.json` がオブジェクトでない」を**旧成果物と同じ `judged: false`** に倒しており、
`metadata.json` が `[]` でも exit 0 で収束条件を素通りできた（実測）。
加えて期待セル数の加算が定義（項目数 × インスタンス数）とずれ、`id` 欠落・重複の要素を 1 セルとして数えていたため、
件数が過小（3 項目中 1 件欠落 × 4 インスタンスで 12 が 9）にも過大（2 項目 × 1 インスタンスがすべて欠落で 2 が 3）にもなっていた。

なぜ 1: 入力クラスの列挙を「判定する／後方互換で判定しない」の 2 分割で終え、**型崩れ**という第 3 のクラスを置かなかった。

なぜ 2: 後方互換は「読めなかったら通す」方向の緩和なので、緩和条件を広く書くほど安全に見える——実際は逆で、
緩和経路は未列挙の入力クラスをすべて飲み込む。

なぜ 3: fail-closed を設計するとき「落とす条件」は列挙したが、**「通す条件」の列挙**を同じ粒度で行う規律が無かった。

提案を強化する: fail-closed なゲートに後方互換・免除・スキップの緩和経路を置くときは、
**通す入力クラスを閉じた集合として列挙し、それ以外を落とす**形で書く
（`if (壊れている) skip` ではなく `if (既知の免除条件) skip; else 判定`）。
緩和経路ごとに「これを通してよい理由」を 1 行で書けるか確認し、書けない入力が通る形になっていたら列挙漏れとみなす。
件数を報告する集計は、**定義式**（例: 項目数 × インスタンス数）をコード上の 1 箇所で表現し、
例外要素を個別に加算しない（加算が定義から乖離しても型検査も既存テストも通る）。

## 再発（2026-09-02・同型分岐の掃き出し漏れ）

前節の修正で `items` / `instances` 側の期待セル数を定義（項目数 × インスタンス数）へ直したが、
その 1 つ上の `components[].id` の分岐（**同じ関数内・20 行上**）に同じ修正を当てていなかった。
同じ Copilot レビューの次ラウンドがそれを検出し、レビュー 1 往復分の手戻りになった。
同じラウンドで `declared: false` の `reason` 未必須（理由の無い免除が通る）も指摘され、
前節の「緩和経路は閉じた集合で書く」が同じファイル内で未適用だったことが分かった。

なぜ 1: 指摘された地点を直し、同じファイル内の同型の分岐を探さなかった。

なぜ 2: レビュー指摘を「その行の欠陥」として受け取り、「**故障クラスの 1 インスタンス**」として扱わなかった。

なぜ 3: kaizen の「横断スコープ確認」は学びの抽出時の手順で、**レビュー指摘を直す場面**には同じ規律が置かれていなかった。

提案を強化する: レビュー指摘を適用するときは、直す前にその指摘を**故障クラスへ一般化**し、
同じファイル・同じ関数内をそのクラスで掃き出してから直す。
探した範囲と見つかった件数を返信に書く（1 箇所だけ直して「対応済み」としない）。

### 再発 4 件目（2026-09-02）

`readDeclaration()` に `Array.isArray()` を足したとき、同じファイルの `countCoverage()` 他 3 箇所の同型ガードに
同じ修正を当てず、次ラウンドのレビューで検出された。前節の提案（同じファイル内を故障クラスで掃き出してから直す）が
未適用のまま同じ形を繰り返した。今回は grep で 4 箇所を列挙してまとめて直し、探した範囲を返信に書いた。

## 再発（2026-09-03・非同期完了イベントの対象HEAD取り違え）

Issue #291 で、Claude Code のレビュー完了コメントを `created_at` / `updated_at` が直近 push 後という条件だけで
現在 HEAD のレビュー済み証跡として受理した。旧 HEAD で開始したレビューが新しい push の後に完了すると同じ条件を満たし、
未レビューの現 HEAD をレビュー済みとして収束できるとレビューで指摘された。

なぜ 1: レビュー完了コメントの時刻を、レビュー対象 commit の識別子として代用した。

なぜ 2: 「push 後」という値の範囲だけを確認し、その時刻を生成した処理がどの HEAD を入力にしたかという
相関キーの状態空間（現 HEAD / 旧 HEAD の遅延完了 / SHA 不明）を列挙しなかった。

なぜ 3: 新設したコメント経路の正常系と古いコメントは eval に入れたが、非同期処理に固有の
「旧対象で開始し、新対象の開始後に完了する」という交差状態を入れなかった。

KEDB 照合では本記録がヒットした。横断スコープはレビュー、CI、デプロイなど、開始対象と完了通知が別イベントになる
非同期処理全般。時刻は候補を絞る補助に留め、完了証跡は commit OID、run の `head_sha`、安定した対象 ID など
処理開始時の対象と直接相関するキーで結ぶ。直接相関できないコメントは単独証跡にしない。
