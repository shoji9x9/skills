# 配布スキルの成果物様式に列・節を足したら、旧様式で生成済みの既存インスタンスの扱いを同じ変更で規定する

## 事象

Issue #211 で `replace-strategy` のテンプレート（`assets/features-template.md`）の横断 API 表に
「参照テーブル」列を追加し、下流の `golden-dataset` にも 3 表から引くことを書いた。
しかし**その列を持たない版のテンプレートで既に生成済みの `.replace/features.md`** をどう扱うかを
書かなかった。下流プロジェクトの features.md は列を持たないまま残り、
`golden-dataset` は「列が無い＝参照テーブル無し」と読んで横断 API 専用テーブルを落とし続ける。
**Issue #211 が塞ごうとした故障が、既存プロジェクトではそのまま残る状態だった**（`/code-review` が検出）。

横断スコープ確認: 直前にマージした #209（PR #212、「その他の Issue（4 種以外）」表の新設）にも
同じ抜けがある。テンプレートには「該当が無ければ節を消さず『なし』と書く」とあるが、これは新規生成側の話で、
**節を持たない版で生成済みの features.md に節を足す**指示は無い。`status` モードはそれを「未導出」と報告し続ける。

## 根本原因

- なぜ既存インスタンスが漏れたか → 変更の影響範囲を「テンプレート（正本）とその読み手（下流スキル）」で閉じたため
  - なぜ閉じたか → 様式を直せば以後の生成物は正しくなる、と暗黙に仮定した。実際にはテンプレートは**新規生成にしか効かず**、
    既存インスタンスは下流プロジェクト側にあり、スキルを更新しても書き換わらない
    - なぜ仮定したか → 配布スキルの成果物は「スキル内の正本」と「下流に実在する既存インスタンス」の**2 母集団**に分かれるのに、
      その区別を持たず正本だけを直す前提でいた ← 根本原因
- 増幅要因: 非破壊更新の規約（「テンプレートに無い項目を削除しない」）が**列・節の追加まで禁じているように読める**ため、
  既存インスタンスの移行が「やってはいけないこと」に見える二重の落とし穴になっていた

関連: [[2026-07-29-new-contract-key-declaration-sites]]（新設キーは grep が空振るので義務づけた側から逆引きする）と
同じ「新設は既存の突合に現れない」系統だが、あちらは**消費側の宣言**の漏れ、今回は**既に生成された実体**の漏れで軸が異なる。

## 提案

配布スキルが下流プロジェクトに生成する成果物の様式（テンプレートの列・節、metadata のキー）を**増やしたら**、
その様式で**既に生成済みの既存インスタンス**をどう扱うかを同じ変更で規定する——(1) 生成側は既存ファイルに列・節を追加して埋めること、
(2) 読み手側は欠落を「値が無い」と解釈せず記録漏れとして扱うこと、の両方を書く。正本を直しても既存インスタンスは自動では直らない。
非破壊更新の規約がある成果物では、**「削除しない」は列・節の追加を妨げない**ことも明記する（禁止と読まれて移行が止まるため）。

`docs/skill-development.md`「push 前の整合パス」項目 5（新設キーの逆引き）に、既存インスタンスの移行という軸を追記する。
併せて #209 の「その他の Issue（4 種以外）」表にも同じ移行指示を補う（apply フローで適用）。
