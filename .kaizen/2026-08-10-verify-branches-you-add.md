# 修正で新設した分岐・受理する入力クラスは、その状態を作って実測する

## 事象

Issue #186（kaizen コミット前ゲートの 5 件）の修正に 23 件の回帰テストを付け、修正前スクリプトで
14 件が落ちる陽性コントロールまで取ったが、コードレビューで自分の修正が入れた欠陥が 2 件見つかった。

- 末尾改行なしのレコードを +1 して数える補正で、遅れて改行が届くと同じ行を二重計上し、
  根拠の行番号が恒久的に +1 ずれる（真の 11 行目を line 12 と報告）。
- `git` のグローバルオプションを許す正規表現の引数を非空白の連続に限ったため、
  `git -C "/tmp/a b" commit` が rc=0 で素通りする（狙っていた形そのもので fail open）。

## 事象（2026-08-16 追記・再発）

Issue #198（`aws-architecture-diagram` のエンジンが環境レジストリを `environments.mjs` 決め打ちで
読む）の修正で `.mjs` → `.js` のフォールバック探索を入れた。書いた分岐（`.js` だけがある /
どちらも無い）は fixture を作って実測し、修正前の版で `ERR_MODULE_NOT_FOUND` になる陽性コントロールも
取ったが、コードレビューで「両方あると先勝ちで `.js` が黙って無視され、無警告で古い図が出る」が
見つかった。同じ変更でドキュメントが `.js` へのリネームを勧めていたため、旧ファイルの消し忘れで
実際に踏む経路だった。再発のため priority を medium → high に上げる（今回の観測影響は手戻り）。

## 根本原因

- なぜ残ったか? → テスト入力を Issue の再現手順から起こし、修正で新設した分岐（空行レコード）と
  新たに受理した入力クラス（オプションの引数）が発火する状態を一度も作らなかった。
  空行分岐はコメントで「前レコードの改行が後から届いた等」と名指ししていたのに作っていない。
  - なぜ? → 「修正が効いたか」を陽性コントロールで確認した時点で検証完了とみなした。
    陽性コントロールが測るのは報告された欠陥だけで、修正が増やした経路は測らない。
    - なぜ? → 既存規律 [[2026-07-29-verify-the-branch-you-document]] は**外部コマンド**の分岐に閉じ、
      適用先も `.agents/rules/external-tool-format-verification.md`（`paths: skills/**`）。
      自作コードで新設した分岐には効かない。← 根本原因（対策可能）

- なぜ 2026-08-16 も残ったか? → 検証対象を「自分が書いた分岐」で列挙し、入力の状態空間で
  列挙しなかった。候補を順に探すフォールバックは、書いた分岐が 2 つでも状態は 0 件 / 1 件 /
  複数件 の 3 つあり、複数件は先勝ち（`find` / `[0]`）が暗黙に処理するのでコード上に分岐として
  現れない。
  - なぜ? → 本ノートの提案が「新設した分岐」と書いており、コードに分岐として現れない状態が
    対象外に読める。← 根本原因（対策可能）

横断スコープ: 特定パスに閉じない（`scripts/**` のテストでも `skills/**` のスクリプトでも
ワークフローでも起きる）ため、path で絞る rule ではなく基底ドキュメントへ置く。

KEDB 照合: [[2026-07-30-negative-result-checks-need-positive-control]]（「該当なし」は陽性コントロールで
検出能力を示す）はいずれも `applied`。今回は**その規律を守った上で**なお外した。軸が
「検出能力を示したか」ではなく「**修正が増やした経路を入力に起こしたか**」のため追補として記録する。

## 提案

修正で新設した分岐・新たに受理する入力クラスは、その状態を入力に起こして実測する。
陽性コントロール（修正前で落ちること）が測るのは報告済みの欠陥だけで、修正が増やした経路は測らない。

基底ドキュメント（`AGENTS.md`、無ければ `CLAUDE.md` / `.github/copilot-instructions.md`）の
検証方針に次の箇条書きを追加する（新規ルールは作らない）:

- **修正で新設した分岐・新たに受理する入力クラスは、その状態を作って実測する。** 陽性コントロール
  （修正前の版で落ちること）が測るのは報告された欠陥だけで、修正が増やした経路は測らない。
  コード中のコメントで名指しした故障シナリオ（「〜が後から届いた場合」等）はそのまま入力に起こし、
  受理する値は表記ゆれ（引用符・空白・改行の有無・引数の有無）を列挙して当てる。
- **列挙は「書いた分岐」ではなく「入力の状態空間」で行う。** 候補を順に探すフォールバック
  （拡張子・設定ファイル・探索パスの優先順位）は 0 件 / 1 件 / **複数件** の 3 状態を生み、
  複数件は先勝ちで暗黙に処理されるためコード上に分岐として現れない。曖昧性を黙って解消せず、
  どれを使いどれを無視したかを必ず知らせる。
