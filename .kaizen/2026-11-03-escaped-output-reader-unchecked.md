# 出力を書き分けたときに、その出力を読んで使う側が元の値に戻せるかを確かめなかった

## 事象

Issue #870 で、`kaizen-schedule-report.sh` の prompt の一覧のパスを、`\` を `\\` と、改行を `\n` と書き分けた。
prompt を読むのはエージェントで、一覧のパスでノートを開く。戻し方を prompt に書かなかったので、`\` を含む名前のノートを開けなくなった。
修正前はそのまま出していたので開けていた。PR のローカルのレビュー（`/code-review high --comment`）が指摘した。
同じレビューで、CRLF のノートで要約の列に CR が入り、表の行が分かれることも指摘された。

## 根本原因

1. なぜ開けなくなったか → 書き分けたパスを、戻し方を添えずに prompt に出した
2. なぜ戻し方を添えなかったか → 出力先を「1 行に収める」側だけで考え、その出力を読んで使う側（パスでファイルを開くエージェント）を挙げなかった
3. なぜ挙げなかったか → 出力の形を変えるときに、その出力の読み手と、読み手がその値で何をするかを列挙する手順が無い。`state-space-and-mutation-proof.md` の「読み手と書き手を同時に作るとき」は、記録を読むチェックを対象にしている ← 根本原因

## 根拠

確信度の理由: 1 回の観測だが、読み手を列挙しなかったことに原因を絞れている。
PR #872 のローカルのレビューが指摘し、prompt に戻し方を書く形で直した。直した後のテストは修正前のスクリプトで落ちることを確かめた。
KEDB 照合: 「エスケープ」「読む側」、「書き分け」「prompt」、「出力」「読み手」「戻」で、どれも一致なし。

## 提案

出力の形（書き分け・区切り・切り詰め）を変えるときは、その出力の読み手をすべて挙げ、読み手がその値で行う操作（ファイルを開く、表として描画するなど）が変えた後も成り立つかを確かめる。

- 適用先: `.agents/rules/state-space-and-mutation-proof.md` の「記録を読むチェックは…」の節の「逆向き」の段落を、チェックに限らず出力の読み手全般に広げる
- 入力の状態（CRLF・タブ・改行）は、書き分けた値だけでなく、同じ出力に入る他の列（要約など）にも当てる
