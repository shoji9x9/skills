# pr-finalize-loop の回帰テスト

テストケースは [`evals.json`](evals.json)。実行・採点・集計の共通手順は `docs/skill-development.md`「回帰テストを実行する」に従う。

## 前提条件

- テスト用の PR。`evals.json` の `prompt` は、実在する PR の URL を前提にする。
  CI の失敗と未解決のレビュースレッドを含む検証用の PR を用意し、必要なら `prompt` の URL を差し替える。
  破壊的な操作を避けるため、本番の PR ではなく使い捨ての検証用の PR を使う
- 場面を prompt に書いて手順を説明させる eval（eval 3・eval 26 など）は、実在の PR を使わない。

## 人に回すかの基準を確かめる eval

- eval 3 は、`references/review-response.md`「人に回すかの基準」の 1 と 2 を確かめる。
  直し方が 2 つあり設計の判断が絡むが、リポジトリの文書と Issue を調べれば決まるスレッド A と、送ると取り消せないメールを有効にするスレッド B を並べる。
  区別できるのは「答えを反映した後もループを打ち切らずに続ける」の 1 本である。without_skill は、判断待ちでループを止めて報告すると答えた。
  残りの 6 本は、prompt の場面から推測できるので without_skill も pass する。
  設計の判断が絡むことだけで人に回す扱いに戻った後退と、元に戻せない影響を人に回す基準が消えた後退を検出するために置く。
- eval 26 は、`common` の設定の `decision_policy_doc` から基準の文書を読む分岐を確かめる。fixture `decision-policy-doc` に、設定と、プロキシの設定の変更を担当者に確認するとした文書を置く。
  区別できるのは「PR が設定と文書を変えていないことを確かめてから読む」「base branch の commit から読む」の 2 本である。
  設定から文書の場所を読む・影響が小さく戻せてもプロジェクトの基準で人に回す・その 1 件を確認する・説明に留める、の 4 本は、fixture の設定と文書を読めば答えられるので without_skill も pass する。
  プロジェクトの基準を 1〜3 より弱く扱う後退を検出するために置く。

## 区別できない eval

- eval 20（`--defer-decisions`）のうち、確認を送らない・解決せずに残す・判断待ちとして報告する assertion は、フラグの名前から推測できるので without_skill も pass する。これらは判断待ちの扱いが消えたり食い違ったりした後退を検出するために置く。
- eval 21（最後の反復で規約の指摘を扱う）のうち、最後の反復であることを見送る理由にしない・返信してから解決する・push した HEAD が未レビューであると報告する・実行はせず説明に留める、の 4 本は、場面の説明から推測できるので without_skill も pass する。それぞれ、反復の残りを理由に指摘を見送る扱いへ戻った後退、返信と解決の順序が消えた後退、報告から未レビューの記述が消えた後退、説明に留める指示が消えた後退を検出するために置く。
- eval 22（影響と覆せるかで判断待ちを分け、effort を下げて反復を足す）のうち、次の 3 本は without_skill も pass する。
  影響の小さいスレッド A を推奨の案で解決する・影響と覆せるかで分ける・実行はせず説明に留める、である。
  前の 2 本は、prompt の場面（利用者に見えない、CI が新しく失敗する）から推測できる。それぞれ、影響の小さい指摘を判断待ちにする扱いに戻った後退、2 つの軸が消えた後退を検出するために置く。
  2 つの軸そのものは、判断待ちの印（`<!-- pr-finalize-loop:deferred -->`）を残す assertion と組み合わせたときだけ区別できる。
- eval 23（承認などを待つジョブの上限）のうち、10:35 で待ち続ける・environment と reviewers を報告する・実行はせず説明に留める、の 3 本は、場面の説明から推測できるので without_skill も pass する。
  それぞれ、上限の前に止める扱いへ戻った後退、報告から待っている相手が消えた後退、説明に留める指示が消えた後退を検出するために置く。

## review_tool が claude-code-action の eval

eval 27〜29 は、fixture `review-tool-claude-code-action` で、ワークフローの目印による完了の判定と、`workflow_dispatch` による依頼を確かめる。
区別できるのは、同梱のスクリプト `claude-review-action.sh` の使い方（`check` での突き合わせ、`request` に渡す `--since` と `--sha-file`）と、`@claude review` と取り違えないことである。
eval 29 の「10:03 に `findings=2` の指摘を集めて対応に進む」は、区別できる場合がある。iteration-24 では、without_skill の 3 run のうち 2 run が `open=0` を見て直す指摘は無いと結論して fail した。
次の assertion は、prompt の場面から一般の判断で答えられるので、without_skill も pass する（iteration-24）。

- eval 27: 目印でレビュー済みとしない・`workflow_dispatch` で依頼する・effort medium を渡す・説明に留める。
- eval 28: コメント A〜C を数えない・D でレビュー済みとする・`reviews[]` と check-run を根拠にしない・説明に留める。
- eval 29: 10:00 に待つ・10:01 に依頼しない・10:03 にレビュー済みとする・`@claude review` を投稿しない・説明に留める。

これらは、目印の判定や重ねない依頼の扱いが消えたり食い違ったりした後退を検出するために置く。
