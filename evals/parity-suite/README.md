# parity-suite の回帰テスト

テストケースは [`evals.json`](evals.json)。実行・採点・集計の共通手順は `docs/skill-development.md`「回帰テストを実行する」に従う。

## 前提

実アプリ・DB・ブラウザ（Playwright）・ゴールデンデータセットを要する全フロー（authoring 〜 ベースライン採取 〜 強度チェック）は、
使い捨てプロジェクト（空・非対話）では回せない。そのため本スキルの evals は、次の 2 つを対象にしている。

- **前提が無い環境での停止パス**（replace-strategy setup / golden-dataset が未完了、Playwright が使えない）
- **禁止事項の拒否挙動**（取って diff しない・強度の検証を省略しない）

## 実行例

```bash
scripts/eval/run-skill-eval.sh \
  --skill parity-suite --config with_skill \
  --prompt "parity-suite" \
  --out tests/parity-suite/iteration-1/eval-1/with_skill/run-1 \
  --model opus

# fixture 付き eval（前提が揃った状態から始める。evals.json の "fixture" をスキルディレクトリ相対で解決する）
scripts/eval/run-skill-eval.sh \
  --skill parity-suite --config with_skill \
  --prompt "parity-suite --feature order-list --target current-test" \
  --fixture evals/parity-suite/fixtures/dataset-target-mismatch \
  --out tests/parity-suite/iteration-1/eval-6/with_skill/run-1 \
  --model opus
```

- 使い捨てプロジェクトには `.replace/features.md`・設定が無いので、eval 1・2 は「捏造せずに停止し、setup を促す」パスを検証する
- eval 3〜5 は、前提の有無に関わらず成立する拒否挙動（Playwright 固有の依存・取って diff しない・強度の検証の省略の拒否）を対象にする
- eval 6 は fixture（設定・`.replace/features.md`・`.replace/dataset/metadata.json`）で前提を揃える。
  データセットの投入先 target（`current.target`）と、選択した target の不一致を検出して停止するパスを検証する
- eval 7 は fixture `static-dataset-null-target`（`dataset_mode: static`・DB を持つ target がゼロ・`current.target` が `null`）で、eval 6 の照合が**過剰に発火しない**ことを検証する。
  ゴールデンデータがリポジトリ内にあり、特定の環境に紐づかないので target を照合しない。DB を持たないプロジェクトが、環境の不一致を理由に止まらないことを見る。
  **検査項目は、実行フロー 4 までで到達できる範囲に限る**。使い捨てプロジェクトには現行アプリが無く、run はフロー 1（疎通不可）で正しく停止する。
  フロー 8 の成果物の記録（`dataset_version` の書き込みなど）を検査項目にすると、到達できずに必ず fail する（iteration-5 でこの設計の不備により 3/4 になった）
- eval 10〜15 は、静的サイトの移行で見つかった 6 件の不足（Issue #145）に対する回帰である。いずれも**誤った前提での依頼を押し戻す形**にしてあり、
  現行アプリ・ブラウザを要する工程まで到達しなくても採点できる。
  6 件は、aria の粒度・side 別の期待値の置き場所・検出されることの確認・解決できないロケータとタイムアウト・API を持たない場合の上流・同梱ツールのコピー先である
- eval 18 の fixture（`semantics-pending`）は、`current.origin: received-assets` でフェーズ A まで完了した状態を持つ。
  `.replace/dataset/verification.md` の「意味論が未確定の機能」と、`.replace/bootstrap/semantics.md` の確認待ちに、**`order-list` が残っている**。
  **その機能のスイート構築を開始しない**ことを検証する。fixture には開始可否の判定そのものを書かない（書くとベースラインがそれを読んで assertion を満たす）
- eval 19 は、eval 18 と**同じ fixture** に対して、意味論が**確定済み**の `customer-list` を対象にする。誤検知しないことの確認である。
  「`received-assets` なら一律で止まる」「確認待ちが 1 件でもあれば全機能を止める」実装を弾く（eval 18 だけでは、全部止める実装と区別できない）。
  この環境では Playwright・現行アプリに到達できないので、**停止するとしても、その理由が意味論の確認待ちでないこと**を見る
- eval 20・21 は部品網羅表（Issue #274）の回帰で、前提の有無に関わらず会話で判定できる取り決めを対象にする。
  20 は、ベンダー資料を列挙の生成源に留めること・部品 × ページのインスタンスごとに測ること・3 値と `covered_by` の記録を見る。
  21 は、未測定を行の削除で消せないこと（判定できないときは失敗として扱う）と、`metadata.json` の `component_coverage` をキーごと省略しないことを見る。
  どちらのプロンプトにも網羅表のファイル名・キー名を書かない（書くとベースラインがそれを読んで assertion を満たす）
- eval 22 は、ノイズ測定の 2 回目の採取物の扱い（Issue #277）の回帰である。書き出し先（`noise-pass2/`）・基準値を記録した後の削除・
  「テキストは Git」の区分を 2 回目には当てないこと・不在が欠落ではないことを対象にする。
  プロンプトは**残してコミットする案**を持ち込む形にしてあり、現行アプリ・ブラウザに到達しなくても採点できる
- eval 23 は、右クリックが発火しないデータグリッド（Issue #290）の回帰である。判定用と操作用のロケータを分け、可視要素の中心座標へ
  `page.mouse.click` を送ることと、発火を確かめずに `absent` と記録しないことを対象にする。
  プロンプトは**発火しない結果を absent とする案**を持ち込む形にしてあり、現行アプリ・ブラウザに到達しなくても採点できる
- eval 31 は、操作要素が描画されていないときの `absent` の判定（Issue #335）の回帰である。
  単一の時点の非表示と、適用できる到達状態を列挙・遷移しても続く非描画を区別し、座標の操作を正の矩形・hit-test の成功時に限る前提を対象にする。
  プロンプトは、メニュー展開前・レスポンシブ切り替え前の一時的な非表示と、全状態で続く 0 幅を併記する
- eval 24〜27 は網羅プロファイル（Issue #286）の回帰で、網羅表の**項目の集合そのもの**を部品の構成要素から導出する取り決めを対象にする。
  24 は、代表列だけの確認を押し戻すこと（登録しなかった列は期待セルにすら現れない）と、候補の出所を見る。
  25 は、コンテキストメニューの候補の欠落（右クリックの対象・メニュー構成を変える条件の区別）を見る。
  26 は、視覚採取の同値クラスの削減（E2E は削減の対象外・分類の根拠・全候補の所属）を見る。
  27 は、合うプロファイルが無い複雑な部品を暗黙に汎用扱いせず、未検証として残すことを見る。
  どのプロンプトにも、プロファイルのファイル名・キー名・ツール名を書かない（書くとベースラインがそれを読んで assertion を満たす）。
  いずれも**誤った前提での依頼を押し戻す形**なので、現行アプリ・ブラウザに到達しなくても採点できる
- eval 28 は、同じ Issue の「判定できないときに失敗として扱うことを、行き止まりにしない」側の回帰である。
  **設定値を実態と違う形に書き換えて辻褄を合わせる案**を持ち込む形にしてあり、不在そのものを根拠付きで記録する手順へ誘導できるかを見る。
  24〜27 が「甘くしない」側なので、これは対になる、通すべきものを通す側の押し戻しである。プロンプトにはキー名・ファイル名を書かない
- eval 29 は、待たない Playwright API（Issue #311）の回帰である。SSR の現行で繰り返し green だったことを根拠に `locator.all()` と即時の読み取りを残し、
  新側の低頻度の失敗を retries / `waitForTimeout` で吸収する案を押し戻せるかを見る。Locator と自動リトライの assertion、同梱の検査、遅延描画の故障注入までを対象にする
  （同梱の検査・故障注入まで安定して到達させるため、答えを明かさずに修正後の確認方法も尋ねる）
- eval 30 は、API record と assertion の網羅の差（Issue #330）の回帰である。record 全体に対して代表 2 項目だけを assertion にし、残りは `parity-diff` に任せる案を押し戻せるかを見る。
  捕捉した全 JSON path を、assertion／両工程で同じ正規化をする揮発項目／`gaps.md` の未検証へ分類し、未分類のまま authoring を完了しない取り決めを対象にする。
  修正手順と修正後の確認を開かれた形で尋ねて、詳細へ到達できるようにする。
  一方で、分類先のファイル名・全 path の列挙を求める語は書かず、スキル固有の前倒しの手順を baseline に渡さない
- eval 32 は、撮影前の静止待ち（Issue #361）の回帰である。出現を待つだけで撮り、2 回撮りのノイズ 0 を安定の根拠にして、差分の揺れを実装差として戻す案を押し戻せるかを見る。
  矩形が 2 回続けて同じ値になるまで待つ形・固定待機でない読み比べ・操作アダプタ側に置くこと・落ち着かない状態の扱い・採り直しを対象にする。プロンプトには待ち方の答えを書かない。
  iteration-29 では assertion 1（2 回一致は安定の証明にならず戻さない）・2（矩形が 2 回続けて同じ値になるまで待つ）・6（採り直し）を `without_skill` も満たした。
  症状（コードを変えずに差分が 2 値で入れ替わる）から一般的な flaky 対策として導けるので、これらは**後退の検知**のためのもので、Delta には寄与しない。
  差を出すのは、3（自動リトライでの読み比べ）・4（操作アダプタに置く）・5（落ち着かない状態の扱い）である
- eval 33 は、撮影状態のポップアップの棚卸し（Issue #360）の回帰である。
  網羅表の present を根拠に 2 段目のポップアップを撮影状態から外し、別機能で撮るポップアップを何も書かずに外す案を押し戻せるかを見る。
  再帰的に数えること・撮る／撮らないの記録・`gaps.md` の種別・ポップアップを開く呼び出し（関数名 × 開く対象）との突き合わせを対象にする。
  プロンプトは、複数のポップアップを 1 つの引数付きの関数で開く事実だけを置く（関数名だけの突き合わせを弾けるように）。
  iteration-31 では、`without_skill` も呼び出し単位の考え方には到達した（assertion 5 は、棚卸しの `opened_by` を記録先にしていないことで差を出している）。プロンプトには棚卸しのキー名・ファイル名を書かない。
  Issue #364 で、1 つのポップアップを複数の操作で開ける場合（クリックとキーボード）と、同じ呼び出しを別の親のポップアップから呼ぶ場合をプロンプトへ足した。
  あわせて、assertion 6（行を分けず `opened_by` の配列に並べる）・7（`parent` × 呼び出しの単位で識別する）を追加した。
  プロンプトが置くのは「2 行に分けるつもり」「同じ呼び出しを 2 つの親から呼んでいる」という事実だけで、行の単位・配列・照合の単位は書かない。
  iteration-40 の内訳は、**差が出たのが 3・4・5・6**（6 は `without_skill` が「2 行にするのは正しい」と逆の結論を出した）、**後退の検知が 1・2・7・8** である。
  7（`parent` × 呼び出しの単位）は「容器が違えば 2 行・2 枚」と自力で到達するので、Delta には寄与しない
- eval 34 は、操作の反応の網羅（Issue #351）の回帰である。
  押した直後のスナップショットと時間を置いた再観測を根拠に「トーストは無い」とし、反応が無い操作を書かずに完了とする案を押し戻せるかを見る。
  最上位の文書と全フレームでの上限つきの出現待ち・消える時間の複数標本と assertion 化・「反応なし」の実測の記録・移行元のソースのフィードバック呼び出しとの突き合わせを対象にする。
  出現待ちと再観測の不備は症状から一般的に導けるので、差を出すのは 3（消える時間を assertion に）・4（反応なしの実測の記録）・5（設定の呼び出し一覧での突き合わせ）である。
  プロンプトには網羅表のキー名・ファイル名・ツール名を書かない
- eval 35 は、寸法の決まり方（Issue #367）の回帰である。
  撮影条件を 1 ビューポートにし、他の窓は `gaps.md` に一行書いて済ませ、その 1 点の px で新側を組ませる案を押し戻せるかを見る。
  3 つの比較方法が宣言した 1 点でしか比べないこと・未測定を `gaps.md` で免除しないこと・画素比較を増やさず式を測ること・窓の選び方・同梱ツールでの当てはめと新側の照合を対象にする。
  式の当てはめと照合の判定（窓の数・一直線上の配置・測り忘れ・予測値との偏差・exit 2 の記録）は、ユニットテスト `scripts/skills/parity-suite/dimension-fit.test.js` が確かめる
- eval 36 は、撮影状態の導出（Issue #389）の回帰である。
  網羅表が全て `present` なことを根拠に、思い付きで決めた 2 状態で足りるとし、不活性のメニュー項目を何も書かずに飛ばす案を押し戻せるかを見る。
  対象は、網羅表の `present` から機械的に導くこと、6 種の語彙（操作の途中の 5 種と、終えた後に残る見た目。Issue #471）、`capture_conditions.states` との差の報告、
  撮れない理由の残し先、後から足すと現行側も採り直しになることである。
  「思い付きをやめて網羅表から導く」までは `without_skill` も到達する（プロンプトが網羅表を手がかりとして含むため）。
  そのため差を出すのは、2（6 種の語彙）・3（同梱ツールでの差の報告）・4（行の理由と `gaps.md` の種別）・5（現新 2 side の採り直し）・6（導出は下限）である。
  行の粒度（要求元の操作ごとに分かれ、同じ種別を束ねない）と、未決・未照合を失敗として扱う判定は、次の 2 つのテストが確かめる。
  `scripts/skills/parity-suite/coverage-expand.test.js` と `scripts/skills/parity-diff/coverage-check.test.js` である。
  プロンプトにはツール名・キー名・種別の語彙を書かない
- eval 37 は、部品とインスタンスの集合の出所（Issue #392 / #393）の回帰である。受領ソースが読めるのに画面を歩いて部品とページを洗い出し、
  列数が一致したことと未検証領域の一行を根拠に引き渡す案を押し戻せるかを見る。
  対象は、集合そのものへの出所・完全性の宣言、受領ソースからの静的な列挙を先に置くこと、実 UI の歩行が本体の周りの部品を落とす仕組み、軸の一致が集合の根拠にならないこと、
  一次情報源を使わなかった理由の申告、散文では収束が止まらないこと、いま渡したときの採り直しの範囲である。プロンプトにはキー名・ファイル名・ツール名を書かない。
  iteration-33 では、`without_skill` も assertion 1・4・6・8 に到達した。
  1 は母集団が自己申告なので未測定 0 は完全性の証拠にならないこと、4 は観測値と定義値は別であること、6 は注記は測定の代わりにならないこと、8 は矛盾する結論の併記が無いことである。
  症状（洗い出しが画面由来）から導けるので、これらは**後退の検知**のためのもので、Delta には寄与しない。差を出すのは次の 4 つである。
  2（受領ソースから先に静的に列挙し、画面は期待値の確定に使う）・3（周辺の部品が本体の軸に現れないので、集合の側で落ちる仕組み）・
  5（一次情報源を使わなかった理由の申告）・7（現行側のベースラインとノイズ基準値まで採り直しになる）。
  宣言の欠落・語彙外・完全性の未宣言・理由の欠落を未測定として数える判定は、`scripts/skills/parity-diff/coverage-check.test.js` と `scripts/skills/parity-suite/coverage-expand.test.js` が確かめる
- 網羅プロファイルの機械的な照合（候補の展開・欠落・同値クラス・新しい仮想部品の追加・根拠付きの不在）は、会話の eval では区別できない。
  そのため、リポジトリ側のユニットテスト `scripts/skills/parity-suite/coverage-expand.test.js` と `scripts/skills/parity-diff/coverage-check.test.js` が確かめる。
  反応の網羅表の照合（空欄・証拠の欠け・呼び出しの記録の抜け・表の指紋）は、`scripts/skills/parity-suite/reaction-check.test.js` が確かめる
- eval 38 は、採取対象が「画面に描かれているもの」かの回帰（Issue #386）である。
  固定プロパティ集合が全一致で緑なのに画素だけ差が出る状況から、書体の版・ヒンティングの切り分けへ進む案を押し戻せるかを見る。
  対象は、採取した要素の矩形の確認、画面の外へ置かれたコピー、論理名の付け直し、同梱ツールが文書の外の要素で採取を失敗させること（欠落へ変換しない）、`child_inline_styles`、マッピング修正後の採り直しである。
  プロンプトには固定プロパティ集合の件数を書かない（初版で書いたところ、件数が現行と合わないことを手がかりに、「採取が古い」という別の筋へ寄った。iteration-36）。
  矩形の判定そのもの（文書の外で落ちる・折り返し下やスクロール外は通る・面積 0 は判定から外す）と、子の inline style の記録は、`scripts/skills/parity-suite/trait-capture.test.js` が確かめる
- eval 39 は、採取物の健全性（Issue #382）の回帰である。実体だけ採り直して展開結果が古いまま、読み手のいない採取物がある状態から、
  差分ツールのすべての比較方法が緑であることを根拠に完了とする案を押し戻せるかを見る。
  対象は、`artifact_health` の読み手の宣言・字面の照合・`unread_reason` の宣言の口・`derived_from` による鮮度・`freshness_unverified_reason`・`artifact-health-check.mjs` の通過である。
  **prompt で読み手の検査がどこまで見れば足りるかを問う一文は、あえて取り決めと反対の答えを示唆する形**にしてある。
  iteration-39 で、`without_skill` は「参照の有無まででは意味がありません」として、摂動で赤くなるテスト名まで見よと答えた。
  `with_skill` は「字面で足ります」「assertion に使っているかまでは見ません」と答え、依存の実在は強度チェックが持つと段を分けた（7/7 対 1/7）。
  初版（iteration-38）は、skill 固有の宣言と汎用の grep の発想を 1 本の assertion に同居させていた。
  `without_skill` のほうが先に「ファイル名を spec 全体に grep」へ到達していたので、2 本へ分けた。
  検査そのもの（未宣言・sha256 の不一致・字面の不一致・0 件の扱い・名前の境界で一致を取ること）は、`scripts/skills/parity-suite/artifact-health-check.test.js` が確かめる。
