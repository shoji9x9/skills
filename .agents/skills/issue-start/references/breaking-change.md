# 破壊的変更に当たるかの判断

リリースのバージョンを commit message から決めるプロジェクト（semantic-release など）では、破壊的変更を commit message に書かないと major が上がらない。
利用者は、バージョンから「更新しても従来の使い方が変わらないか」を読み取れなくなる。
そこで `--commit` と `--pr` では、最初の commit の前に、変更が破壊的変更に当たるかを判断する。`--pr` では、PR の本文にも結果と理由を書く。
何を破壊的変更とするかはプロジェクトごとに違うので、このスキルの中に定義を持たない。

## 定義を探す

`SKILL.md` の「ブランチ運用・commit 規約の参照」で決めた規約の文書を読む。
その文書か、その文書がリンクや節名で案内する文書に、破壊的変更に当たるものの定義があれば、それに従う。
規約の文書が定義の置き場所を案内しているのに読めない（リンク先が無い・節が無い）ときは、定義が無いとして扱わず、利用者に確認する。
規約の文書もそこから案内される文書も、何を破壊的変更とするかを書いていないときは、定義が無いとして扱う。確認せずに進み、PR の本文の節に「定義が無い」と書く。
commit message の書き方の仕様（conventional commits など）は、破壊的変更の書き方を決めるだけなので、定義に数えない。

## 判断する時点と書き方

当たるかは、最初の commit の前に判断する。commit message に書く形は、規約の文書に従う。
conventional commits なら、1 行目の種別の後に `!` を付ける（`feat!:`・`feat(<scope>)!:`）か、本文の後のフッターに `BREAKING CHANGE: <利用者がすること>` を書く。
commit した後に当たると分かったら、`--amend` せず、次の commit のフッターに書く。
squash で取り込むリポジトリでは、取り込むときの commit message（PR のタイトルなど）にも同じ形で書く。
PR を作った後の修正（レビューへの対応など）で当たるようになったときも、その commit のフッターに書き、PR の本文の節を書き直す。

定義の表で決められない変更と、境界で迷う変更は、仮に決めて進めない。
その変更に沿った commit・push・PR の作成より前に、判断の材料（変更の内容・当たると判断できる箇所・当たらないと判断できる箇所）を添えて利用者に確認する。
確認は [`user-confirmation.md`](user-confirmation.md) の手順で行う。

## PR の本文の節

PR の本文に `## 破壊的変更` の節を置き、次のどれかを書く。

| 場合 | 書くこと |
| --- | --- |
| 当たる | 「当たる」と、定義のどの項目に当たるか、利用者が何をすれば従来の使い方を続けられるか、`!` か `BREAKING CHANGE:` を書いた commit |
| 当たらない | 「当たらない」と、定義に照らした理由（例: 「設定のキーを足したが、デフォルトが従来と同じ動作になる」） |
| 定義が無い | 「規約の文書に破壊的変更の定義が無いので、判断していない」と、読んだ文書のパス |

定義が無いときも節を置く。節が無いと、判断していないのか、書き忘れたのかをレビューする人が区別できないからである。
