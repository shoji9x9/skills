# 強度の検証（故障注入＝ネガティブコントロール）

**この工程が抜けると下流が全部無意味になる。** assertion が弱められた／そもそも無いテストも pass するため、テストがあること自体は品質の証拠にならない。

## 位置づけと実行タイミング

- **authoring 時のゲート**。以後はスケジュールではなく、**スイートの assertion が変わるたび**（穴埋め・データセット更新でベースライン再取得した等）に再実行する
- **強度は機能ごとに `strength.md` に記録し、`replace-strategy status` が参照する**

## ブラックボックス前提

古典的な mutation testing は SUT のソースを変異させる前提だが、本スキルには字義どおり乗らない。パリティスイートは現行アプリの外側から当てるブラックボックスであり、**現行を変更しない**（変更しないことが設計原則。加えて現行はソース変異と mutant ごとの再デプロイが非現実的な生成物でありうる）。

そこで**変異対象を差し替え、テストが観測する境界に既知の故障を注入する（ネガティブコントロール）**。

## ポジティブコントロール（無注入で全経路が緑）

**故障を注入する前に、無注入で現行検出一式の全経路が緑になることを確認する。** これが対照であり、無いと「赤くなった」を注入由来と言えない（注入スクリプトの副作用・環境差・ベースラインの陳腐化でも赤くなるため、常に赤い状態を「捕捉できている」と読み違える）。

- **同じ実行系で取る**——同じ Playwright config・同じ `actionTimeout`・同じ差分器としきい値・同じベースライン。注入用の設定だけを足した状態で 1 回流す
- 確認する経路は**注入後に判定に使う経路すべて**（手書き assertion／特性照合／画素／aria 比較）。1 経路でも赤ければ、その原因を潰してから注入に進む（赤いまま注入すると、その経路の結果は読めない）
- 結果を `strength.md` に記録する。無注入が緑であることは**故障ごとの判定の前提**であり、注入結果の表だけでは復元できない

## 判定単位は「現行検出一式」

**強度は「手書き assertion 単体」ではなく「現行検出一式＝手書き assertion ＋ ベースライン ＋ 差分器」で判定する。** 故障を注入して、この一式のどれもが赤くならなければ、その故障種別に対して一式は弱い（例: ボタン色を変えて手書き assertion も差分器も赤にならなければ、一式はスタイルに対して弱い）。

## 故障カタログ

**恣意的に作らず、既知の回帰分類から導出する**——意図的差異レジストリ、`references.db_semantics` の差、コンポーネントライブラリ差、既知の移行ハザード。故障クラスと注入手段:

| 故障クラス | 例 | 注入手段 | 拾う経路 |
|---|---|---|---|
| 値・件数・並び（データ由来） | 応答の値・順序の改変 | **上流摂動**（`page.route` で応答を摂動し描画経路へ伝播。「上流」の定義は下記） | 手書き assertion（＋差分器） |
| 構造（aria） | role・構造の欠落 | DOM 摂動（`page.evaluate`） | 手書き assertion ＋ aria 比較（摂動後に aria を再取得し**ベースライン相手に**構造比較） |
| 静的ラベル・placeholder・role | 文言・placeholder の改変 | **DOM 摂動**（`page.evaluate`。上流で届かない静的マークアップ用の第二経路） | 手書き assertion |
| 要素スタイル（色・余白・フォント・罫線） | 色・余白等の改変 | **スタイル注入**（`page.evaluate` / `addStyleTag` / CSS 応答摂動）して撮り直す | 差分器を**ベースライン相手に**回す（新側不要） |
| ドキュメントレベル要素 | `title` / favicon / `meta` / `html[lang]` の改変 | DOM 摂動（`page.evaluate` で `document.title` や `link[rel~="icon"]` の `href` を書き換え） | 手書き assertion（**画素・特性照合・aria のどれにも写らない**ため、この経路しか無い） |

- **検出＝手書き assertion が赤 ∪ 差分器（特性照合／画素／aria 比較）が赤。** 名前付き要素のスタイルは特性照合が、名前無しは画素が拾う。
  aria 比較＝取得済み aria スナップショット（参考資料）のベースラインとの構造比較で、`parity-diff` の第 3 経路（テーブル/フォームの内容パリティ）に相当する
- **両方を素通りした故障が一式の弱点**——強化するか、`gaps.md` に記録する（確認済みにしない）

### 「上流」は API とは限らない

**上流＝その画面がデータを受け取る境界**であって、API 応答のことではない。境界は現行アプリの作りで決まるため、**対象画面で実際にデータがどこから来るかを見てから注入手段を選ぶ**。

| 現行の作り | データの上流 | 上流摂動の具体 |
|---|---|---|
| 画面が API を呼ぶ | API 応答 | `page.route` で API 応答を摂動する |
| API を持たない（サーバー描画・静的サイト。データはリポジトリ内の静的ファイル） | **document 応答そのもの** | `page.route` で document 応答を捕まえ、`route.fetch()` で得た元応答のボディを改変して `route.fulfill()` する |
| 外部リソース（画像・フォント・CSS）に依存する | その配信 | `route.abort()` で遮断する（フォールバックの見た目・欠落を一式が拾えるか） |

出典: <https://playwright.dev/docs/api/class-route>（`route.fetch()` は「元応答を取得し、変更してから fulfill するため」の API。`route.abort()` は要求の中止）。

- **API を持たないから上流摂動を組めない、と読まない。** 静的サイトでも上流は在り、データ由来の故障（値・件数・並び）はここから注入する
- **摂動が実際に描画へ伝播したことを確認してから判定する**（ポジティブコントロールの画面と見比べる）。ルート指定が当たっておらず**現行そのまま**を描画している状態は、「全経路が緑＝素通り」と見分けが付かない

## 要素が消える故障は待たせない（タイムアウトと解決不能の扱い）

**注入で要素が消えると、特性採取（`locator.evaluate` 等の操作）はロケータの解決を待ち続ける。** 既定では待ちは打ち切られず（`actionTimeout` の既定は `0` ＝ 無制限。出典: <https://playwright.dev/docs/api/class-testoptions>）、テスト全体のタイムアウトまで止まる。1 故障あたりその時間を待つと、カタログ全体を回すのが現実的でなくなる。

- **待ちを決めるつまみは 2 つあり、別物**。操作（特性採取・クリック等）は `actionTimeout`、手書き assertion（`expect(locator).toBeVisible()` 等の自動リトライ assertion）は**独立した expect タイムアウト**（既定 5000ms。`actionTimeout` とは無関係。出典: <https://playwright.dev/docs/test-timeouts>）。
  片方だけ縮めても、もう片方を伸ばしているプロジェクトでは強度ゲートが遅いままになる
- **強度ゲートの実行では `actionTimeout` を短く設定する**（`use.actionTimeout`。注入用のプロジェクト／設定側で指定し、通常実行の値は変えない）。長さは「現行が正常なら確実に解決する」下限で決め、採用値を `strength.md` に記録する。
  プロジェクトが `expect.timeout` を既定より伸ばしている場合は、注入用の設定で同様に短く上書きする
- **ロケータが解決しないことは、失敗ではなく差分（要素の欠落）として扱う。** 呼び出し側（現側専用スペック）で捕捉し、その論理名を採取結果から**落として**先へ進む。例外を上げて run を止めない——止めると残りの経路の判定が取れず、故障が「捕捉できた」のか「実行できなかった」のか分からなくなる
  - 同梱の `trait-capture.mjs` は失敗をどの論理名かを付けたエラーで上げる（通常採取では原因特定を優先するため）。強度ゲートではその例外を呼び出し側で捕捉して欠落に変換する
  - **その際 `captureTraits` は論理名 1 件ずつ（`entries` を 1 要素にして）呼び、失敗した名前だけ落として結果を連結する。**
    まとめて 1 回呼んで try/catch で包むと、最初の失敗で関数が抜けて**既採取分ごと失う**（採取結果が空になり、差分器はベースラインの全論理名を `missing` として出す）。
    これは注入と無関係に「全経路が赤＝捕捉」に見えるため、下の「run が落ちたを検出扱いにしない」と同じ誤判定になる
  - 欠落は差分器が拾う: `trait-compare.mjs` は**ベースラインに在って採取に無い論理名**を `kind: "missing"` として出す（＝特性照合が赤）。したがって欠落を差分として表に記録できる
- **「解決不能で run が落ちた」を検出扱いにしない。** 検出は手書き assertion か差分器が赤になったことであり、実行系の停止はどちらでもない

## 差分器の健全性の確認

強度ゲートでは差分器の健全性も確認する。対象は `parity-diff` が再利用する **3 経路すべて**（特性照合・画素・aria 比較）:

- 注入した**既知の差を差分器が赤にできる**こと（スタイル注入 → 特性照合・画素、構造の DOM 摂動 → aria 比較）
- **注入量がノイズ基準値に埋もれない**こと（ノイズ基準値は [`baseline.md`](baseline.md)）

**ここで検証した差分器を `parity-diff` が現新比較にそのまま再利用する**（ツール・しきい値・ノイズ基準値は `metadata.json` の `differ` / `noise_baseline` 経由で引き渡す）。

## カタログの外は射程外

故障注入が与えるのは強度の**下限**（「少なくともこれらは捕捉した」）であって完全性の証明ではない。緑は「反例が見つからなかった」に過ぎない。**捕捉した故障種別と未検証の種別を `strength.md` に記録し、「強い」と宣言しない。**

- **新側 TypeScript・自作コード（マッピング層・データセット生成ツール）の本物の mutation testing は本スキルのスコープ外**（通常の開発衛生であり、パリティの強度検証とは別物）
