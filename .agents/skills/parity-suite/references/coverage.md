# 手書きの aria スナップショットと、操作・状態のカバレッジ

ページを表示しただけで終わりにしない。表示は仕様のごく一部なので、操作・状態・副作用出力まで特性化する。

## 寛容な aria スナップショット（手書き）

- スナップショットは取得して diff せず、仕様として書く。
  新旧のスナップショットを機械的に突き合わせると、差分の多くは新しい実装が正しくなったことに由来する（`div` → `role=alert`、リンクで偽装したタブ → 正しい `tablist`）。
  ノイズと改善が混在するので、判定の材料にならない。
- `toMatchAriaSnapshot` のデフォルトが部分一致であることを使い、仕様が保証する項目だけを並べる。

### 部分一致で許容されること・されないこと

部分一致でも、何でも許容されるわけではない。許容されるのは、テンプレートに書いていない兄弟が実際に在ることだけである。
テンプレートに書いた子が実際に無ければ、一致しない。階層と順序は厳密に照合される。
デフォルトの `/children: contain` は「指定した子がその順序で存在すれば一致」を意味する。
`equal` と `deep-equal` で厳密にもできるが、このスキルでは使わない（出典: <https://playwright.dev/docs/aria-snapshots>）。

| 差異 | デフォルトの部分一致での扱い |
|---|---|
| テンプレートに書いていない兄弟が実際には在る | 許容される |
| 中間の階層を省いて、孫を直接書く | 一致しない（照合は直下の子の関係で行うので、深さは飛ばせない） |
| 兄弟の順序が違う | 一致しない（順序は厳密） |

そのため、ページ全体を 1 枚のスナップショットで書かない。深さを飛ばせないので、1 枚で書くと、現行の平坦な DOM の階層がそのまま取り決めに固定される。
すると、新側がセクションをランドマークにするなど、構造を良くしただけで失敗する。仕様は変わっていないのに失敗するので、パリティの判定として誤りである。

- セクションごとにアンカーを置き、複数枚に分ける。
  ページ本体ではなく、論理名で取得したセクションのロケータ（ランドマークや見出しで取得できる単位）に `toMatchAriaSnapshot` を当てる。
  そのセクションの中で、仕様が保証する構造だけを書く。
- アンカーより上（セクションどうしの並びや、ページの外枠）は取り決めに含めない。
  セクションが在ることそのものは、別の assertion で確かめる（「同じページに乗る他機能の在席」と同じ形）。
- セクションの中でも、階層が実装の都合で決まる箇所（装飾のための入れ子など）は書かない。書くと、深さが取り決めに入る。
- 現行が非セマンティックな箇所と、実装の仕組みが違う箇所は、意図して書かない。
- ビューポートごとに書けば、レスポンシブの構造のパリティも確かめられる。
  ブレークポイントでの `display:none` などの表示の切り替えは、aria スナップショットに現れる。余白や色の変化は現れないので、`parity-diff` が受け持つ。
- ベースラインの採取のときに取得する aria スナップショット（[`baseline.md`](baseline.md)）は参考資料で、assertion ではない。
  判定に使うと、「取得して diff する」失敗に戻る。

## 操作・状態のカバレッジ

次の観点を対象にする。

| 観点 | 内容 |
|---|---|
| 初期表示と初期値 | フォームとフィルターの初期の選択値、リセットした後の値、保存済みの条件を当てたときに代わりに使われる値 |
| マウスの操作 | クリック、hover、ドラッグ。hover・focus・active・disabled・selected・error の状態にするのは、このスキルの責務である（見た目の比較は `parity-diff` が行う） |
| キーボードの操作 | Tab で到達できるか、focus の表示、Enter と Space での発火、ショートカット。タブの順序の厳密な一致は、判定の基準にしない（到達できることと、論理的な順序だけを見る） |
| スクリーンサイズ | 対象のブレークポイントごとに確かめる。対象は現行アプリの実測（CSS のメディアクエリと、実際の UI の表示が切り替わる点）から決め、採用したビューポートを `metadata.json` の撮影条件に記録する（実行ごとにその場で選ばない）。表示の切り替えは aria スナップショットに現れる。余白と色は `parity-diff` に任せる |
| 検索・フィルター・ソート・ページネーション | 条件を変えたときの挙動。ページネーションは、2 ページ目があれば、実際に移るところまで確かめる |
| バリデーション | エラーメッセージの文言と、発火する時機（onChange・onBlur・onSubmit のどれか）、初めて入力する前は出さないなどの UX のパターン。操作が呼ぶ部品の内側で送る前に止める判定（件数・長さ・大きさの上限など）は、下の「送る前の判定（`pre_send`）」で操作ごとに挙げる |
| 状態表示 | 0 件、取得の失敗、読み込み中、トースト、ダイアログ。画面ごとに、候補ごとの「ある」「ない」を現行で測って記録する（下の「画面ごとの状態表示（`state_displays`）」）。読み込み中の表示が無い画面も、応答を保留して何も出ないことを確かめた「ない」として記録する。操作が返すトーストやダイアログの開閉などは、下の「操作の反応」の網羅表で確かめる |
| 権限による違い | ロールごとに、表示や操作が変わる箇所（[`auth.md`](auth.md)） |
| 文書全体に関わる要素 | `<head>` 側の要素と、文書の属性。ページごとに 1 回確かめる。対象は `title`、favicon（`link[rel~="icon"]` が指す先の URL）、現行が持つ主な `meta`（`description`・`viewport`・OGP など）、`html[lang]` である。どれも決まった値として取得できるので、手書きの assertion に向く |
| ファイルの入力（アップロード） | 選択・複数選択・選択の解除、バリデーション（形式・大きさの上限）、成功と失敗の表示、保存の結果（バイト列・派生物・保存先のパスの規則）。この操作は書き込みなので、[`data-discipline.md`](data-discipline.md) の規律に従う。操作の手段、fixture の作り方、何を確かめるかの原本は、`replace-strategy` の `references/file-io.md` にある（ドラッグ & ドロップは対象外） |

- アニメーションのパリティは対象外である。差分の比較では `animations: 'disabled'` で止めるので、この方法では扱えない。対象外であることを明記する。
  ただし、共通の部品を先に作る進め方では、`parity-component` が部品の動きを部品ごとに数え、時系列で比べる（`parity-component` の `references/motion.md`）。
  この一般論を、部品の動きを比べない理由にしない。
  対象・対象外・条件付きの一覧の原本は `replace-strategy` の `references/scope.md` で、このファイルは各項目で何をするかを持つ。
- ページ本文の要素だけを対象にしない。`<head>` 側の要素は、視覚のベースラインにも aria スナップショットにも現れない。
  そのため、対象から外すと、スイートでも差分ツールでも検出できない。新側のテンプレートのデフォルトの favicon や `title` のまま置き換わっても、どのテストも失敗しない。

### 機能の在否は「コンテナと文言がある」で確かめない

移行元の部品は、使わない機能のコンテナを、高さ 1px などに畳んだまま DOM に残すことがある。文言も残る。
「コンテナがあり、文言を含む」だけを見る観点は移行元で成功するので、無い機能が「ある」と読まれる。
すると新側で失敗し、要らない依存の追加や、無い機能の実装を求めることになる。
`toBeVisible()` でも足りない。Playwright は、矩形が空でなく `visibility: hidden` でもなければ、見えると判定する。
そのため、高さ 1px のコンテナは見えると判定される（出典: <https://playwright.dev/docs/actionability#visible>）。

- 機能が「ある」ことは、次のどれかで確かめてから観点にする。
  - 使える大きさで見えている。矩形の幅と高さが、その機能の中身（文言や操作する要素）を収める大きさである。
  - 操作が機能する。操作すると、その機能の反応（並び替わる・開く・値が変わる）が出る。
  - 移行元がその機能を有効にしている設定値（ソースや設定）を読み、その箇所を根拠に書く。
- 確かめた結果、移行元でその機能が無効なら、観点は「その機能は出ない」にする。コンテナの畳み方を、新側に引き継がせないためである。
- 強度チェックでは、「コンテナを畳む」故障で、在否だけを見る観点が通ってしまわないことを確かめる（[`strength-gate.md`](strength-gate.md)「故障カタログ」）。

## 操作の反応（押した直後で止めない）

数える単位は「操作 → 反応」にし、「操作 → 直後の状態」にしない。
操作が返す反応は、次の 3 つの性質が重なると、直後のスナップショットにも、操作した要素の近くにも現れない。
そのため、網羅表が埋まったまま取りこぼされ、未測定の欄すら立たない。

| 性質 | 取りこぼし方 |
|---|---|
| 遅れて出る | 往復の後に出る（例: 押してから約 0.5 秒）。直後に見ると無い |
| 操作したコンテナの外に出る | ダイアログの中で操作すると、トーストが親の文書（iframe の外）の最上部に出る。操作した対象の近くを探しても見つからない |
| 自動で消える | 出てから一定の時間で消える。測る時刻を外すと「無い」が返り、同じ操作で違う結論になる |

これを防ぐのが、反応の網羅表 `.replace/parity/<slug>/reactions.json` である。
テンプレートの原本は [`../assets/reactions-template.json`](../assets/reactions-template.json)、照合は [`../scripts/reaction-check.mjs`](../scripts/reaction-check.mjs) が行う。
feature モードのときだけ作る。

- 操作は、操作アダプタ（`suite.interactions`）とスイートの呼び出しから挙げる（`trigger` に `<関数名>(<論理名>)` で書く）。
  1 つの操作に、`reactions`・`layout`・`aftermath` を必ず持たせる。
- 反応の欄を空にしない。反応が無いなら、`kind: none` を実測の結果として書く。
  `observation` には、見続けた時間（表の `observation_window_ms` 以上）と、見た文書・見方を残す。
  見た文書には、表の `documents`（対象のページの最上位の文書 `top` と、全フレームの棚卸し）をすべて含める（欠けると失敗する）。
  欄が無ければ、「見ていない」と「無い」が同じに見える。測れなければ、`kind: unmeasured` と理由を書く（`gaps.md` にも残す）。
  「反応なし」もスイートの assertion にする（`covered_by`）。新側が遅れて出て消える反応を足しても、静止画にも特性照合にも現れないからである。
  固定の待機は使わない。全文書の変化を記録する監視を仕掛けてから操作し、`page.waitForFunction` が観測時間の中で成立しない（タイムアウトする）ことで、反応が無いことを確かめる。
- 文書を棚卸しするときは、各文書のオリジンが対象の URL（`targets[].url`）のオリジンと同じかを、`document_origins` に記録する（`same-origin` / `cross-origin`）。
  値そのもの（ホストやポート）は書かず、関係だけを残す。`url_command` の target は、URL を成果物に残さないからである。
  移行元が自分の URL を絶対 URL で組み立てる（埋め込みのフレームの読み込み先や遷移先）ことがある。
  この場合、`targets[].url` にホストやポートの別名を書いた環境では、そのフレームだけが別のオリジンになる。
  別のオリジンのフレームの中の処理は、親の文書に届かない（同一オリジンポリシー）。
  そのため、移行元に実在する反応が測った環境では現れず、`kind: none` として記録される。
  差分ツールは「無い」どうしを一致とみなすので、この取り違えを検出できない。
  - 測り方は次のとおりである。`page.frames()` の各フレームで `frame.evaluate(() => self.origin)` を読み、`new URL(<targets[].url>).origin` と比べる。
    フレームの URL ではなく、実効オリジンで比べる。`about:blank` や `srcdoc` のフレームは、親のオリジンを引き継ぐからである（出典: <https://developer.mozilla.org/docs/Web/API/Window/origin>）。
  - `cross-origin` の文書があれば、反応を記録する前に、移行元がその読み込み先を組み立てる絶対 URL（設定やソース）を確かめる。
    移行元の本来の配置でも別のオリジンになるなら、確かめた根拠を `cross_origin_evidence` に文書ごとに書く（`{ "<文書>": "<根拠>" }`。別のオリジンの文書が無ければ `{}`）。
    表全体で 1 つにまとめない。まとめると、意図して別のオリジンにした文書の根拠が、環境の都合で別のオリジンになった文書まで通してしまう。
    環境の都合（ホストやポートの別名）で別のオリジンになっているなら、反応を記録せずに止まる。
    `targets[].url` を、移行元が組み立てるオリジンに合わせるよう、ユーザーに促す（設定の原本は `replace-strategy` の `references/project-config.md`）。合わせてから測り直す。
  - `kind: none` には、操作した文書（`observation.source_document`）も書く。見た文書と合わせて、どのオリジンの間で「無い」を確かめたかが残る。
- 観測では、出るまで待ち、消えるまで測る。1 回のスナップショットで判定しない。
  - 出るまでは、上限を決めて待ち（`appearance.wait_limit_ms`）、操作から出るまでの時間を `delay_ms_samples` に残す。
    操作したコンテナの中だけでなく、最上位の文書と全フレームを探す。出た先は `destination`（文書と論理名）に書く。
  - 自動で消えるなら、出てから消えるまでを 2 回以上測って `duration_ms_samples` に残し、標本の幅以上の `tolerance_ms` を決める。
    消える時間を測らないと、新側が出しっぱなしでも、静止画にも特性照合にも差が出ない。どの比較にも現れない振る舞いになる。
    消えないなら、`mode: persistent` と、それを確かめた記録を書く。
    標本は、下の assertion と同じ測り方で採る。出現の assertion が成立した時刻から、消える assertion が成立した時刻までを測る。
    測り方が違うと、ポーリングの遅れの分だけ、assertion が許容の幅を外れる。
  - 画面に出ない反応（クリップボードへの書き込みなど）は、`visible: false` と、確かめ方（`observation`）を書く。
- 観測した反応は、スイートの assertion にする（`covered_by`）。`parity-replace` が新側でスイートを成功させる時点で、反応のパリティも確かめられる。
  消える時間は、固定の待機（[`locator-mapping.md`](locator-mapping.md) が禁じる）ではなく、自動で再試行する assertion と経過時間で確かめる。

  ```ts
  // 出典: https://playwright.dev/docs/api/class-locatorassertions（toBeVisible / toBeHidden の timeout）
  await trigger();
  await expect(toast).toBeVisible({ timeout: waitLimitMs });
  const shownAt = Date.now();
  await expect(toast).toBeHidden({ timeout: durationMs + toleranceMs });
  expect(Date.now() - shownAt).toBeGreaterThanOrEqual(durationMs - toleranceMs);
  ```

- 画面に出る反応は、撮るか撮らないかを `capture` に決める。
  撮るなら `capture_conditions.states` の状態名を書き、撮らないなら理由を書いて、`gaps.md` の「撮影状態の対象外」に残す。
  自動で消える反応を撮るときの注意は、[`baseline.md`](baseline.md)「撮る対象が動かなくなるまで待つ」にある。
- 表は、操作ごとに `scripts/table-upsert.mjs` で書く。本文ごと書き直さない（[`checkpoints.md`](checkpoints.md)「大きな JSON 成果物は 1 行ずつ書く」）。

### 操作で変わる頁の組み方（`layout`）

寸法の式（`dimension_model`）と視覚のベースラインは、初期表示の状態しか見ない。
操作で現れる要素の位置や、操作のたびにコンテナの高さを書き直す振る舞いは、寸法の照合にも、3 つの比較方法（画素・特性・aria）にも入らない。
例は、検索条件の行を足すたびに、グリッドの高さを窓の高さから計算し直して、頁を窓に収める振る舞いである。
新側が組み方を変えない実装でも、すべての比較が成功し、利用者が画面を触って初めて見つかる。

- 操作ごとに `layout` を必ず書く（欠けると未測定）。
  操作の前と後で、頁の `document.documentElement.scrollHeight` と `clientHeight`、主な論理名（操作で動く・現れる要素と、窓の寸法で決まるコンテナ）の矩形を測る。
  - 変わらないなら、`changes: false` と、変わらないことを確かめた記録（`evidence`）、それを確かめる assertion（`covered_by`）を書く。
  - 変わるなら、`changes: true` と、次の測定と assertion を書く。測るのは、操作の前（`before`）と、同じ操作を 2 回以上くり返した後（`samples`。`repeat` は 1 からの連番）である。
    1 回の差分では、「窓から書き直す絶対値」と「前の値からの相対」を区別できない。相対の値として扱うと、2 往復目からずれる。
    その時点で表示されない要素の矩形は、`null` にする。
  - 測れなければ、`changes: null` と理由を書く（`gaps.md` にも残す）。未測定として数えられる。
- 頁が窓に収まるかは、高さで見る。Playwright はスクロールバーを隠す。
  そのため、新側の頁が窓を超えて縦のスクロールバーが出ても、その分の横幅のずれは、測った矩形に出ない（[`baseline.md`](baseline.md)「スクロールバーが場所を取る窓のはみ出し」と同じ原因）。
  `scroll_height` が `client_height` を超えるかを、assertion に入れる。
- assertion は、`samples` の最後の回と同じ回数だけ操作してから、頁の高さと矩形を確かめる（途中の回だけを見ない）。
- 測るのは、撮影したビューポートだけでよい。窓を変えたときの追従は初期表示の寸法の式だけが持つので、操作の後の組み方の追従は `gaps.md` に残す。

### 押した後に残るもの（`aftermath`）

撮影状態の導出は、操作の途中（コンテナを開く・指を乗せる・焦点・押している最中・不活性）を導く。反応では、出て消えるものを測る。
どちらも、操作を終えた後に残る見た目と、どこへ戻るかを挙げさせない。
次のものは、撮っていなければ 3 つの比較方法のどれにも差が出ない。行を選んだ後の列ごとの塗り、絞り込み中の見出しの色、複数列の並べ替えの印、ロゴを押した後の遷移、Clear が戻す範囲である。
スイートは両側で成功し、`parity-diff` も収束したまま、利用者が並べて操作して初めて見つかる。

- 操作ごとに `aftermath` を必ず書く（欠けると未測定）。`look`（残る見た目）と `returns_to`（戻り先）の両方を、現行で 1 回ずつ測って書く。
- `look` には、押した後に残る塗り・色・印・焦点を、要素（論理名）ごとに `items` に 1 行ずつ挙げる。
  `observed` には、現行で測った値（計算後のスタイルの値や、印の文言）を書く。付かないことも値として書く。
  現行が特定の列だけに選択の塗りを付けないなら、その列の行に「付かない」と書く。付く列だけを見ると、新側が全列を塗っても差が出ない。
  - 各行は、撮る状態か assertion に割り当てる（両方でもよい）。撮る状態は `captured` に `capture_conditions.states` の状態名で、assertion は `covered_by`（`toHaveCSS` や印の文言など）に書く。
    どちらにもしないなら、`reason` を書いて、`gaps.md` の「撮影状態の対象外」に残す。割り当ても理由も無い行は、未測定になる。
    同じ `captured` の状態名を複数の行（別の操作を含む）が指すなら、全行の `shared_capture_reason` に根拠を書く。
    根拠には、その 1 枚がすべての操作の後を撮っていることを、実際の UI で確かめた内容を書く。
    撮影状態の導出の「状態名も撮影単位の中で一意にする」と同じ理由である。根拠の無い使い回しを許すと、片方の操作しか作っていない 1 枚でも、全行が満たされてしまう。
    観測した反応の `capture.state` も同じ集合で数え、共有するなら `capture.shared_capture_reason` を書く。
    照合は、ページ × 状態名で行う。押した後に撮ったページ（遷移する操作なら遷移先）を `capture_page`（`capture_conditions.pages` の名前）に書く。
    そうすれば、別のページの同じ状態名は、別の 1 枚として扱う（操作が載るページではない）。
    撮る状態を持つ操作は、`capture_conditions.pages` が 2 つ以上なら、`capture_page` が要る（1 つならそのページとみなす）。
    名乗ったページは、押した後の URL（`returns_to.url_after`）と照合する。
    URL を、[`baseline.md`](baseline.md)「ページの path の解決規則」で宣言したページのどれか 1 つに解決する。
    名乗ったページと違う、どのページにも解決できない、または曖昧なら、失敗する。
    ページは名前ではなく、解決したページで数える（path が同じ別名は同じ 1 枚）。
    `target.ui_url` が `runtime` で、相対の path があるときは照合しない（`reaction-check.mjs` の出力の `capture_page_urls` に理由が出る）。
  - 残らないなら、`changes: false` と、確かめた記録（`evidence`）、確かめた論理名（`targets`）、残らないことを確かめる assertion（`covered_by`）を書く。
    強度チェックは、`targets` の論理名に残る塗りを注入する。新側が塗りや焦点の輪を残しても、撮っていない状態には現れないので、assertion が要る。
    測れなければ、`changes: null` と理由を書く。
  - 部品の操作から生じる残る見た目（選択の塗り・絞り込みの印・並べ替えの印）は、網羅プロファイルの `after-operation` が撮影状態の行を導く
    （[`baseline.md`](baseline.md)「撮影状態の決め方（1）網羅表から導く」）。`look` は、部品に関係なく、操作ごとに数える側である。
    導いた行と同じページで同じ状態名を `captured` に書くなら、両方の行に根拠を書く。
    書く欄は `visual_state_coverage.rows[].shared_capture_reason` と `items[].shared_capture_reason` で、その 1 枚が両方の操作の後を撮っていることを、実際の UI で確かめた内容を書く。
    `reaction-check.mjs` は、`metadata.json` の `component_coverage` が指す部品網羅表を読む。
    部品から導いた行（ページはインスタンスの `page`）も、反応・残る見た目・状態表示と同じ集合（解決したページ × 状態名）で数える。
    根拠の無い行が 1 つでもあれば、失敗する。
    部品網羅表を宣言したのに読めないときと、`visual_state_coverage.rows` が無いときも、失敗する。
    出力の `coverage_captures` は、数えた行数 `counted` と、インスタンスの `page` を取得できずに数えなかった行数 `skipped` を持つ。
    数えなかった行は、`coverage-expand.mjs` が失敗にする。`null` は、部品網羅表を宣言していないことを表す。
- `returns_to` には、押す前と後の URL（`url_before` と `url_after`）と、押す前にデフォルトから動かした状態（`probed`）のうち、押した後にデフォルトへ戻ったもの（`reset`）を書く。
  URL は、オリジンを除いた `/` で始まるパスで書き、ホストやポートは書かない。
  - 画面が持つ状態（検索条件・並べ替え・列フィルター・列の変更・行の選択・ページ送りなど）を、表の `screen_states` に 1 回だけ棚卸しする（出どころは `source` に書く）。
    押す前に、そのすべてをデフォルトから動かしてから押す。
    動かしていない状態が戻るかは、測れない。検索条件だけを入れて Clear を押すと、並べ替えや列フィルターも戻す現行と、検索条件だけを戻す新側が、同じ記録になる。
    操作ごとの自己申告にしないのは、1 つだけ動かして 1 つだけ確かめた記録を通さないためである。
    動かせない状態は、`not_probed` に状態ごとの理由を書く。棚卸しにあって、`probed` にも `not_probed` にも無い状態は、失敗になる。
    `probed` に無い状態を `reset` に書くと、失敗する。状態を持たない画面なら、`screen_states.states: []` にする。
  - 遷移しない操作は、`url_after` を `url_before` と同じ値にする（遷移しないことも、実測の結果として書く）。
  - URL と、戻る状態・戻らない状態（`probed` と `reset` の差）を、スイートの assertion にする（`covered_by`）。
    測れなければ、`measured: false` と理由を書く（未測定として数えられる）。

### 送る前の判定（`pre_send`）

観点を「画面の処理」で止めず、「操作が最後に呼ぶ関数」まで追う。
件数の上限（選んだ行・添付・一括処理の対象）、長さや大きさの上限（文字数・ファイルの大きさ・URL の長さ）、必須と形式の検証は、画面の処理の外に置かれることがある。
置かれる場所は、共通の部品のクライアント側のスクリプト、部品が持つ送信の関数、サーバー側の共通処理である。
これらは、画面の処理にも、画面が部品に渡す引数にも現れない。
しかも、境界の外側でしか表に出ない。ふだんの操作（数件を選んで押す）では通るので、スイートも `parity-diff` も両側で成功したまま、新側に判定が無いことが分からない。
実例では、書き出しボタンの共通部品が呼ぶ送信の関数に、「選んだ行が 500 件を超えたら知らせて、書き出さない」判定があった。新側は何件でも書き出した。

- 操作ごとに `pre_send` を必ず書く（欠けると未測定）。
  操作のハンドラ（`handlers`）から、部品の内側を、送信・実行の直前まで読む。到達した点を `traced_to`（ファイルとシンボル）に、たどり方を `trace` に書く。
  - 判定が無いなら、`found: false` と、到達した点まで読んで無いことを確かめた記録（`evidence`）を書く。
    追えなければ、`found: null` と理由を書く（`gaps.md` にも残す。未測定として数えられる）。
  - 判定があれば `found: true` とし、`items` に判定を 1 つずつ書く。
    書くのは、種類（`kind`）、場所（`location`）、止める条件（`condition`）、止めたときに起きること（`on_block`）である。
- 判定ごとに境界の両側を現行で測り、それぞれを assertion にする（`sides`）。
  通る側（`inside`。上限ちょうど・形式の内側・必須を満たす）と、止まる側（`outside`。1 つ超え・形式の外側・必須が欠ける）を、1 つ以上ずつ書く。
  - 与えた値（`input`）、境界の状態の作り方（`setup`）、現行で測った結果（`observed`）、assertion（`covered_by`）を書く。
    ゴールデンデータの件数が境界に届かないときは、届かないことと、代わりの作り方（画面の中で状態を作る、データを足す）を `setup` に書く。
    足すデータが要るなら、「データ不足」として `gaps.md` に記録し、`golden-dataset` に戻す。
  - 測れない側は、`observed` と `covered_by` を書かず、`reason` を書く（未測定として数えられる。`gaps.md` にも残す）。
- 判定の順序を `order` に残す。この判定の id を、確認・記録・送信などの工程と合わせて、実行の順に並べる（例: `confirm` → `max-rows` → `write-log` → `send`）。
  順序が違うと、止めたときに残る記録（下の「表への書き込み」）や、出る確認の回数が変わる。止まる側の assertion で、確認が出たかと、記録が残ったかも確かめる。
- 到達した点と判定の場所は、`feedback_calls.source.paths` の走査の範囲に入れる。入っていなければ、照合で失敗する。
  `feedback_calls.declared: false` のときは、`--root` から直接読んで照合し、読めない、またはシンボルが無ければ失敗する。
  移行元のソースを読めないなら、`found: null` と理由を書く。
  部品の内側まで範囲を広げると、止めたときの通知（フィードバックの呼び出し）も `call_sites` に現れ、反応と突き合わせられる。
  止まる側の操作の反応は、`on_block` と `sides[].observed` に書き、通知が出るなら `outside` の assertion で確かめる。
- 1 つの部品を複数の操作が呼ぶなら、判定は操作ごとに書く。部品の設定で上限が変わることがあるからで、インスタンスごとに測る網羅表と同じ理由である。

### 表への書き込み（`side_effect_writes`）

利用者に見える反応を出さない副作用は、反応の欄では「反応が無い」として扱われる。
監査や利用のログのような表への書き込みは、差分ツールの 3 つの比較方法（画素・特性・aria）でも見ない。
そのため、書き込みがまるごと無い新側でも、スイートと差分の検出が成功する。
実例では、新側が、詳細画面を開いたとき・例外のとき・書き出しのときのアクセスログを 1 つも書かなかった。
一覧画面では、準備の例外のときの行（移行元のソースの `catch` の中の呼び出し）が抜けていた。

- 表の直下に `side_effect_writes` を必ず書く（キーごと省かない）。`.replace/features.md` の副作用出力の列にある表を、`tables` に転記する。
  書き込みを持たない機能は、`declared: false` と根拠（`reason`）だけを書く。
  `tables`・`patterns`・`sites` を残すと、「無い」と「在る」が同時に成り立つので、失敗にする。
- 書き込みの呼び出しを、移行元のソースからすべて挙げる（例外処理の中も含む）。
  表ごとに、書き込みの字面に当たるパターン（`patterns`）を作る。パターンは、`regex` と、実際の呼び出しをコピーした `example` の組である。
  `source.paths`（操作のハンドラと、操作が呼ぶ共通処理・サーバー側の処理を含む範囲）を走査し、見つかった呼び出しをすべて `sites` に 1 行ずつ記録する。
  走査する版は、`feedback_calls` と同じく、測った現行の版に合わせる。
- 1 か所ずつ、次のものを書く。書く値（`values`）、時機（`occasion`。送信・確認・例外との前後）、回数（`count`）、通る処理（`path`。`normal` か `exception`）、きっかけの操作（`operation`）である。
  画面を開いたときのように、操作に結び付かない書き込みなら、`operation` は `null` にする。
  この機能の書き込みでない呼び出しは、`excluded_reason` だけを書く。
- 確かめ方（`verification`）は、次のどちらかにする。
  - `assertion`: API テストか E2E で、書いた行の値・回数・時機を確かめる（`covered_by`）。
    移行元の DB を読めるなら、既存の行で値を裏づけ、`db_evidence` に残す。
    テストが書いた行の後始末は、[`data-discipline.md`](data-discipline.md) に従う。
  - `source-only`: 例外のときのように移行元で起こせない書き込みは、ソースを読んだだけと記録し、理由（`source_only_reason`）を書く。
    新側の書き込みの箇所は、`parity-replace` が `porting.md` に残す。
- 表への書き込みは、副作用出力（ファイルや帳票。下の「副作用出力の特性化」）とは別の欄で数える。
  ファイルは生成物を捕捉して比べ、表への書き込みは呼び出しの全件と行の値で確かめる。

### 送っている間の押し直し（`resubmit`）

要求を送っている間（応答が返る前）にもう一度押したときの振る舞いは、どの比較にも現れない。
撮影状態の `active` は押している最中の見た目で、反応の欄は 1 回押した後を測る。
往復している間に操作をどう受け付けるかは、移行元と移行先で違いやすい。たとえば、画面を覆って受け付けない・フラグで弾く・何もせずにもう一度送る・確認をもう一度出す、がある。
それでも、測らなければ、スイートも `parity-diff` も両側で成功する。
実例では、押し直したとき、移行元のある画面は何もせず、別の画面は確認を 2 回出して 2 回送った。移行先には、どちらとも違う画面があった。

- 操作ごとに `resubmit` を必ず書く（欠けると未測定）。
  - 要求を送らない操作（クリップボードに書くだけなど）は、`sends: false` と、押している間の通信を見て送らないことを確かめた記録（`reason`）を書く。
    表への書き込み（`side_effect_writes.sites`）を持つ操作は、`sends: false` にできない（書き込む操作は送っている）。
  - 測れなければ、`sends: null` と理由を書く（`gaps.md` にも残す。未測定として数えられる）。
- 送る操作は `sends: true` とし、応答を保留して押し直す。
  `page.route` で対象の要求を捕まえ、応答を返さずに待たせている間に、同じ操作をもう一度送る。
  保留を解くまで往復が終わらないので、「送っている間」を毎回同じ形で作れる（出典: <https://playwright.dev/docs/api/class-route>）。
  - `hold` には、`{ "method": "route-delay", "request": "<保留した要求の URL のパターン。オリジンは書かない>" }` を書く。
  - `presses` には、保留している間に押した回数（最初の 1 回を含む。2 以上）を書く。
  - `observed` には、現行で測った次の 3 つを書く。送った回数（`requests_sent`。捕まえた要求の数）、確認の回数（`confirms_shown`）、覆い（`overlay`）である。
    覆いの例は、画面を覆って受け付けない・押した要素だけを不活性にする・何もしない、である。
  - 書き込みを持つ操作は、送った回数を、表への書き込みの回数と突き合わせる（`writes`: `{ "count": <押し直しで書かれた行の数>, "evidence": "<数え方>" }`）。
    1 回の送信で 2 行書く処理や、2 回送っても 1 行にまとめる処理があるので、送った回数だけでは書き込みの差を読めない。
    移行元の表に書けないとき（[`data-discipline.md`](data-discipline.md)）は、横取りした要求を届けずに数える。
    そのうえで、1 回の送信の書き込み数（`side_effect_writes.sites` の `count`）から導いた数と、導き方を `evidence` に書く。
  - 送った回数・確認の回数・覆いを、スイートの assertion にする（`covered_by`）。
- 押し直した後に残る見た目と戻り先は `aftermath` が、押した後の反応は `reactions` が持つ。`resubmit` は、往復の間の受け付けだけを数える。

### 画面ごとの状態表示（`state_displays`）

「状態表示」の観点を散文のままにしておくと、画面がその状態を持つかを、一度も測らないまま完了できる。
0 件、取得の失敗、読み込み中は、操作の反応の欄にも、撮影状態の導出にも現れない（ふだんの操作では、その状態にならない）。
移行元が 0 件のときに覆いに文言とページ表示 `1 / 0` を出し、移行先が何も出さずに `1 / 1` を出しても、撮っていなければ差は出ない。

- 表の直下に `state_displays.pages` を必ず書く（キーごと省かない）。
  `metadata.json` の `capture_conditions.pages` のすべての画面を 1 回ずつ（`page` に名前）挙げ、候補の 5 つ（`empty`・`fetch-error`・`loading`・`toast`・`dialog`）をすべて振り分ける。
  画面や候補が欠けると未測定として数えられ、宣言に無い画面名や候補名は失敗になる。
- 候補ごとに `status` を書く。
  - `present`（ある）: 状態の作り方（`setup`）と、現行で見たもの（`observed`。文言・覆い・ページ表示）を書く。
    そのうえで、撮る状態（`captured`）か assertion（`covered_by`）に割り当てる。
    `toast` と `dialog` も、操作の反応を参照せず、反応と同じ assertion 名を `covered_by` に書く。
    1 本を 2 行が名乗るので、両方の行に `shared_assertion_reason` が要る。`reactions` の欄は書けない。
    参照を許すと、画面・見えるか・種別が一致することを、検査が保証し続ける必要がある。
    検出できない範囲を 1 つ塞ぐたびに別の抜けが見つかったので、参照する入力の形式ごと外した。
    撮る状態は、反応・残る見た目・部品網羅表の撮る状態と同じ集合（解決したページ × 状態名）で数え、共有するなら全行に `shared_capture_reason` を書く。
  - `absent`（ない）: 作ろうとした手段（`setup`）と、代わりに見えたもの（`observed`）を書き、何も出ないことを assertion にする（`covered_by`）。
    新側が警告のダイアログを足しても、撮っていない状態には現れないからである。
    assertion を省けるのは、画面がその状態に結び付く要求を送らない（`no-request`）ときと、その状態を持つコンテナが無い（`not-applicable`）ときだけである。
  - `unmeasured`: 理由（`reason`）を書き、`gaps.md` にも残す。未測定として数えられる。
- 作り方（`setup.method`）は、次の語のどれかにする。
  `data`（ゴールデンデータ・検索条件）、`ui`（画面の操作）、`route-abort`・`route-fulfill`・`route-delay`（要求の横取り）、`no-request`、`not-applicable` である。
  要求を横取りしたときは、`setup.request` に横取りした要求の URL のパターンを書く。
  `setup.detail` には、具体的な内容（検索条件、返した応答の中身、保留した時間）を書く。
- 取得の失敗と読み込み中を「起こせない」と書く前に、要求の横取りで起こせるかを試す。
  `page.route` で要求を `abort` するか、エラーの状態コードで `fulfill` すれば、失敗を作れる。応答を保留すれば、読み込み中を作れる。
  どちらも移行元で作れる（出典: <https://playwright.dev/docs/api/class-route>）。
  そのため、`fetch-error` の `absent` は `route-abort`・`route-fulfill`・`no-request` でしか名乗れない。`loading` の `absent` は、`route-delay`・`no-request` でしか名乗れない。
  試した記録の無い「ない」は、失敗になる。
- 画面が要求を送る先の一覧は、画面を開いて操作するまでの通信（`page.on('request')`）から取得する。
  `no-request` は、その一覧が空であることを `observed` に書く。
- 操作を持たない、画面で動く機能も、この振り分けを持つ。表示だけの画面も、0 件・取得の失敗・読み込み中を持つことがある。
  そこで、反応の網羅表を `operations: []` と `operations_none_reason`（押せる要素が無いことをどう確かめたか）で作り、同じ検査を当てる（書き方は「照合と宣言」）。

### 移行元のフィードバック呼び出しと突き合わせる

反応があることを知らなければ、欄は作れない。
利用者に見える副作用を出す呼び出し（トースト、画面を直接触るスクリプト、ダイアログの開閉など）は、プラットフォームごとに決まった名前を持つ。
そこで、移行元のソースの字面から機械的に挙げて、網羅表と突き合わせる。

- 呼び出しの一覧は、設定の `current.feedback_calls`（パターンの id・正規表現・種類）にある。
  原本は `replace-strategy` の `references/project-config.md`「フィードバック呼び出し」である。
  これを網羅表の `feedback_calls.patterns` に転記し、対象の slug の操作のハンドラを含む範囲に `source.paths` を絞って、走査する。
  走査する版は、測った現行の版に合わせる。`source.version` が `metadata.json` の `target.commit` と違えば失敗し、どちらかが `none` なら `version_unverified_reason` が要る。
  操作ごとに、ハンドラ（`handlers[].file` と `symbol`）を記録する。ファイルが走査の範囲に無い、またはシンボルがファイルに無ければ、失敗する。
  これは、走査の範囲の書き忘れを、操作の単位で見えるようにするためである。
  操作そのものの書き忘れまでは検出しない。操作を挙げるのは、上の「操作アダプタとスイートの呼び出しから挙げる」の役目である。
  転記が設定と一致しているかは、照合のスクリプトでは確かめない（チェックの無い規約である）。
  設定を変えたら、網羅表に転記し直して、`--write` から通し直す。
- 走査で見つかった呼び出しは、すべて `call_sites` に 1 行ずつ記録する。
  1 件は、ファイル・行・列・パターンの組である。同じ行に複数の呼び出しがあれば、列で分けて、すべて記録する。
  各呼び出しは、観測した反応（`<操作 id>/<反応 id>`）に対応付けるか、この機能の反応でない理由（`excluded_reason`）を書く。
  呼び出しがあるのに、`none` の反応に対応付けない。ソースが反応を出すと示しているのに、観測で見落としているからである。
- 走査の結果が 0 件でも、「呼び出しが無い」と読まない。
  パターンごとの `example`（実際の呼び出しの字面）に `regex` が一致することを、照合で確かめる。
  それでも 0 件なら、根拠を `zero_calls_reason` に書く（空なら失敗する）。
- 設定にキーが無い（確かめていない）ときは、移行元のソースから候補を挙げてユーザーに確認し、決まった値を設定に 1 回記録する。
  移行元のソースを読めない（`current.repo: none` など）なら、`feedback_calls.declared: false` と理由を書き、`gaps.md` に残す。突き合わせを省いた事実を、伏せないためである。
  設定が空のリスト（呼び出しが無いと確認済み）のときも、`declared: false` と、その旨を理由に書く。

### `covered_by` をテストへ解決し、assertion が期待値まで届くかを監査する

`covered_by` は、「期待値」と「それを確かめる assertion の名前」の組である。しかし、欄をチェックするだけでは、両者が合っているかを誰も確かめない。
期待値より浅い assertion を名乗っても、網羅表・スイート・`parity-diff` の収束が、すべて通る。
浅い assertion の例は、「押した行の詳細が別タブで開く」に「ボタンがある」だけを見るテストや、「書き出した中身が一致する」に拡張子だけを見るテストである。
強度チェックは、故障カタログにある種類しか検出しない。

- 名前は `スペックのパス › describe の題 › テストの題` で書く。Playwright の一覧の表示から、project と行番号を除いた形である。
  パスは、`playwright test --list --reporter=json` の `file`（rootDir からの相対）である。
  題が空の describe は、題に入れない。手で組み立てず、一覧か `--audit-sheet` の出力からコピーする。
- 名前は、スイートに実在するテストへ機械的に解決させる。`playwright test --list --reporter=json` の出力を `--tests` に渡すと、次の名前を失敗にする。
  - 一覧のどのテストにも当たらない名前
  - 2 本以上に当たる、曖昧な名前
  - `current` と `new` の片方でしか実行されないテスト（現側専用のスペックなど）

  一覧に読み込みのエラーがあるか、テストが 0 件なら、exit 2 になる。読めなかったスペックのテストは、警告なしに一覧から消えるからである。
  `test.skip` や `test.fixme` で静的に飛ばすテストは、飛ばす側では実行されないものとして数える（一覧の `expectedStatus: skipped`）。
  一覧で `expectedStatus` が `passed` でない側（失敗を期待する `failed` など）も、実行されないものとして数える。
  本文の中で条件付きで飛ばす `test.skip(条件)` と、失敗を期待する `test.fail(...)` は、一覧に現れない（Playwright 1.63.0 の `--list` では `passed` のまま）。
  そのため、`covered_by` のテストでは使わない。使うと、片側で assertion が実行されないか、失敗しても成功のまま解決される。
- 1 本のテストを 2 行以上の `covered_by` が名乗るなら、すべての行に `shared_assertion_reason` を書く。
  書くのは、その 1 本が各行の期待値をすべて確かめている根拠である。
  1 本で数行分を確かめたと数えられても、各行の期待値まで届いている保証は無い。根拠を書けないなら、行ごとにテストを分ける。
  表のどの欄の `covered_by` も、同じ集合で数える。
- assertion が期待値まで届いているかは、実装役とは別の subagent に、1 行ずつ監査させる。渡す入力は、次の 2 つだけにする。
  実装の経緯を渡すと、書いた側の意図で読んでしまい、浅さを見落とす。
  - `node <skill>/scripts/reaction-check.mjs --metadata <metadata.json> --tests <一覧> --audit-sheet` が出す `entries`。
    各項目は、行の位置 `path`、それを含む祖先（操作・送る前の判定の項目・画面など）の位置と値の欄 `context`、期待値 `expected`、テストの場所 `tests` を持つ。
  - そのテストのソース

  問いは「差分があるか」ではなく、「期待値のうち、この assertion が確かめていない部分はどこか」にする。
  期待値の語ごとに、assertion と対応付けさせる。
  「別タブで開く」なら、開いた先がどの行の詳細かを確かめているかを見る。「中身が一致する」なら、中身そのものを確かめているかを見る。
- 結果は、表の直下の `assertion_audit` に書く。書くのは次のものである。
  - `auditor`（監査した subagent）
  - `table_fingerprint` と `specs_fingerprint`（どちらも `--audit-sheet` の出力の値をコピーする）
  - `entries[]`（`path` ごとに 1 件。`verdict: reaches` なら、確かめている部分を `checked` に書く。`verdict: short` なら、届いていない部分を `missing` に書く）

  次の表は失敗になる。
  - `short` が残る表
  - 監査していない行がある表
  - 監査の後に、期待値か `covered_by` を変えた表（表の指紋が違う）
  - 監査の後に、`covered_by` のスペックファイルを書き換えた表（スペックの指紋が違う）

  そのときは、assertion を深くするか、測れないなら行を未測定にして、監査し直す。
  スペックの指紋は、`--write` でも `--recorded` でも、一覧の `config.rootDir` から読み直す。
  そのため、監査の後にスペックの assertion を弱める（`toHaveText` を `toBeVisible` に置き換えるなど）と、表を触らなくても失敗する。
  指紋が対象にするのは、`covered_by` が名指ししたスペックファイルだけである。マッピング層と期待値解決層は、新側の実装に合わせて正当に変わるので、含めない。
  期待値を確かめる assertion はスペックファイルに書き、その層に移さない（移した分は、監査の後に弱めても検出されない）。
  深くした assertion が移行元で失敗したら、それは移行元の振る舞いを測り損ねていた差である。期待値の側を実測で直す（assertion を浅く戻さない）。

### 照合と宣言

- `metadata.json` に `reaction_coverage` と撮影状態（`capture_conditions.states`）を書いたら、スイートのテストの一覧を取得する。
  取得には、`npx playwright test --list --reporter=json --project=current --project=new > "$TESTS"` を使う。
  - 置き場所は、作業ツリーの外の一時ファイル（`TESTS="$(mktemp)"`）にする。
    一覧は、絶対パスの `config.rootDir` を含む、手元の環境の出力なので、`.replace/` に置いて commit しない。照合のたびに取得し直し、終わったら消す。
  - `current` と `new` の両方を明示する。片方に絞ると、両側で実行されることを確かめられない。
    省くと、`new-capture` の採取用のスペックまで読み込まれ、採取用の環境変数（`PARITY_SLUG` など）が無いと失敗する。
    `--project` は複数の値を取るので、`=` を付けて書く。
  - 一覧の取得では、テストもブラウザも実行されない。

  上の監査を済ませてから、次のコマンドを exit 0 になるまで通す。
  `node <skill>/scripts/reaction-check.mjs --metadata .replace/parity/<slug>/metadata.json --root <移行元のソースのルート> --tests "$TESTS" --write`
  コピーせず、スキルの中から実行する。`--root` のデフォルトは cwd で、`--tests` を省くと exit 2 になる。
  次のものは失敗になる。
  - 空欄、証拠の欠け、消える時間の標本が 1 つだけのもの
  - `layout` の欠けと、標本が 1 回だけのもの
  - `aftermath` の欠け（割り当ての無い残る見た目、動かしていない状態の `reset`、オリジン付きの URL）
  - `pre_send` の欠け（到達した点の無い記録、境界の片側だけの判定、順序の無い判定、走査の範囲の外の到達点）
  - `side_effect_writes` の欠け（ソースにある書き込みの記録の抜け、書く箇所の無い表、値や時機の空欄）
  - `resubmit` の欠け（保留せずに押し直した記録、書き込む操作の書き込みの回数の欠け）
  - `state_displays` の欠け（振り分けていない画面と候補、横取りで試していない取得の失敗・読み込み中の「ない」、割り当ての無い「ある」）
  - 呼び出しの記録の抜けと、走査の対象が 0 件のもの
  - `/` を含む id、observed の遅れの最大値以下の `observation_window_ms`、理由の無い空の `operations`
  - `slug` と `measured_target` が、`metadata.json` の `slug` と `target.name` と違う表
  - 解決しない `covered_by`、根拠の無い共有、`assertion_audit` の欠けと不備

  `metadata.json` に、これらと撮影状態・`target.commit`（取得できなければ `none`）が無ければ、exit 2 になる。
  終了コードは、0 が通過、1 が未測定や不整合、2 が使い方の誤りか形式の誤りである。
- `metadata.json` の `reaction_coverage` に、`declared: true` と `path` を書く。キーごと省かない。
  キーが無いと古い成果物とみなされ、`parity-diff` が判定を飛ばす。
- 操作を持たない、画面で動く機能も、`declared: true` で表を作る。`declared: false` と理由で済ませてよいのは、画面を持たない `api-resource` と `batch` だけである。
  表には `operations: []` と `operations_none_reason` を書き、`state_displays` で、すべての画面とすべての候補を振り分ける。
  none の反応が無いので、`observation_window_ms` は `null` にする。
  書き込みもフィードバックの呼び出しも無ければ、`side_effect_writes` と `feedback_calls` は、`declared: false` と理由にする。
  次のものは exit 1 になる。理由の無い空の `operations`、操作があるのに理由が残った表、操作の痕跡がある空の `operations` である。
  操作の痕跡とは、空でない `popup_inventory` か、`component_coverage.declared: true` を指す。
  `default` 以外の撮影状態は、`state_displays` の `present` の `captured` に使われていないものだけを、痕跡として数える。状態表示（0 件など）も、撮る状態になるからである。
  画面で動く機能の `declared: false` は、`run.procedure_revision` が 4 以上なら exit 2 になる。
  改訂 4 より前の成果物（キーが無いものを含む）の `declared: false` は、古い手順のものとして判定しない（`judged: false`。`parity-diff` は未検証のまま残す）。
  当て直すかどうかは、`replace-strategy` の `references/procedure-changes.md` の台帳で決める。
  古い成果物でも、`default` 以外の撮影状態、空でない `popup_inventory`、`component_coverage.declared: true` のどれかがあれば、操作の痕跡と矛盾するので exit 2 になる。
- `parity-diff` は、同じスクリプトを `--recorded` で呼ぶ。このときは移行元のソースを読まず、`conformance.ok`・`conformance.covered_by_resolved`・表の指紋と、監査の記録を求める。
  テストの一覧（`--tests`）は要る。スペックの指紋を読み直して、`--write` の後に assertion を弱めていないかを数えるためである。
  未測定が残る間は、収束させない。照合の後に表を手で直したら、`--write` から通し直す。

## 状態網羅の導出源

確かめるべき状態の網羅は、部品の規範的な資料から導いてよい。
たとえば、「これは Tabs のパターンなので、hover・focus・disabled・selected の状態があるはずだ」というチェックリストを作る材料にする。導出源は 2 種類ある。

| 導出源 | 具体例 | 使うところ |
|---|---|---|
| コンポーネントカタログ | 自作や OSS の UI ライブラリの見本（カタログサイトなど） | 状態とバリアントを挙げる |
| 部品ベンダーの機能一覧 | 市販の部品の公式サンプル、ベンダーや CoE が配る非互換の検証用の試験仕様書、版を上げる前後の比較用の資料 | 1 つの部品が持つ、数十の操作を挙げる |

- 版を上げる前後の比較用の資料は、採取する状態の一覧として、そのまま使える。
  「更新の前後で同じケースを実行して、結果を比べる」方針がパリティの検証と同じで、ケースが比較用の識別子付きで並んでいるからである。
- ただし、どちらも比較の正解にしない。資料は、ライブラリや部品の規範的な姿である。
  テーマ、カスタムの CSS、上書き、版の違い、そのインスタンスの設定によって、実際の描画とずれる。正解は、動いている現行アプリである。
- 資料が 1 つの状態として挙げるものでも、現行が種類ごとに描き分けるなら、別の状態として採る。
  典型的な例は選択である。データグリッドのように、単一選択と、範囲選択・複数選択（複数のセル・複数の行）で塗りが違う部品がある。
  このとき `selected` を 1 つのセルの選択だけで作ると、範囲選択の見た目が、採取にも照合にも一度も現れない。
  描き分けがあるかは、現行の UI で実際に作って確かめる（同じ状態の中で、別の論理名として採ってもよい）。
- 資料が無い場合は、現行アプリの実際の UI から状態を洗い出す。その場合も、洗い出した項目を一覧として残す（下の網羅表の `source.kind: app-ui`）。
  一覧が残らないと、何を測っていないかが、後から誰にも分からない。

### 部品網羅表（同じ部品でもインスタンスごとに測る）

<!-- textlint-disable ai-words-ja/no-ai-words -->

旧称: 部品被覆表・反応の被覆表・被覆プロファイル。既存の成果物（`gaps.md`・`diff.md`・`strength.md` など）の見出しや列名には、旧称や「強度ゲート」「差分器」「経路」が残っていることがある。それぞれ部品網羅表・反応の網羅表・網羅プロファイル・強度チェック・差分ツール・比較方法と読み替える。

<!-- textlint-enable ai-words-ja/no-ai-words -->

1 つの部品が数十の操作を持ち、画面ごとに設定が違うことがある。
このとき、あるインスタンスで測った結果を「その部品の挙動」として他のインスタンスに流用すると、実装側がその画面で使っていない操作が、採取する状態からまるごと抜ける。
抜けた状態は撮られず、assertion も無い。強度チェックは、採った状態の中でしか故障を注入できない（届く範囲の原本は [`strength-gate.md`](strength-gate.md)「カタログの外は射程外」）。
その結果、部品が持つ操作が欠けたまま、`parity-diff` が収束することがある。

これを防ぐのが、インスタンス単位の網羅表である。
`.replace/parity/<slug>/component-coverage.json` に、機能表の項目 × 部品インスタンス（ページ）の表を持つ
（テンプレートの原本: [`../assets/component-coverage-template.json`](../assets/component-coverage-template.json)）。

#### 網羅表は移行元側の測定である（新側の欠落は示さない）

3 つの値が数えるのは、「移行元でその操作が在るか」だけである。「新側で同じ操作をして、移行元と差が無いか」は数えていない。
この 2 つは別の測定で、欠落を見つけるのは後者だけである。前者をいくら積み重ねても、移行元の記録なので、新側の欠落は 1 件も示されない。

- `evidence` と `covered_by` にも、どちら側で測ったかを書く欄は無い。
  `covered_by` が指す採取の状態（`metadata.json.capture_conditions.states`）は、測定の対象（current target）に結び付いた 1 つである。
  `measured_target` も、`components[]` の直下に 1 つだけある。1 つの網羅表は、1 つの測定の対象のものである。
- そのため、`unmeasured` が 0 でも、「新側で操作を完了できる」ことは意味しない。
  新側の突き合わせは、別の成果物 `new/<target>/component-comparison.json` が持つ
  （様式の原本: [`../assets/component-comparison-template.json`](../assets/component-comparison-template.json)）。
  この成果物は、`value: present` のセル 1 つにつき 1 行を求める。
  書くのは `parity-replace`（新側を操作する工程）で、読むのは `parity-diff` の収束の判定である（突き合わせていないものが残る間は、収束させない）。
  検査には、同梱の [`../scripts/component-comparison-check.mjs`](../scripts/component-comparison-check.mjs) を使う。

  ```bash
  node <skill>/scripts/component-comparison-check.mjs \
    --coverage .replace/parity/<slug>/component-coverage.json \
    --comparison .replace/parity/<slug>/new/<target>/component-comparison.json \
    --metadata .replace/parity/<slug>/metadata.json \
    --replace-metadata .replace/parity/<slug>/new/<target>/replace-metadata.json --target <target>
  ```

- `--replace-metadata` は必須である。
  省けるようにすると、記録の後に新側を変えても、鮮度の照合（`comparison-implementation-stale`）が一度も評価されず、古い証拠で収束してしまう。
  突き合わせ表の `new_implementation.commit` は、`replace-metadata.json` の `new.commit` と一致する必要がある。
  例外は、部品の改修による持ち越しだけである。そのときは `--new-repo` を渡し、同じディレクトリの `evidence-carry.json` が対象にする違いを、
  [`../scripts/evidence-carry.mjs`](../scripts/evidence-carry.mjs) が認めたときに通す。
  記録と `new.commit` が一致したままの一括の再検証の直後は、検証先の版を `--carry-to` で渡したときだけ判定する。
  手順の原本は、`parity-diff` の `references/component-change.md` である。
  両方の `dirty` が `false` であることまで求める。commit していない変更を抱えた作業ツリーの記録は、commit で版を特定できないからである。
- `new.commit` が `none`（新側が git で管理されていない）なら、反復の回数で判定する。
  文字列の比較では両側が `none` で常に一致するので、実装を変えても、古い記録が鮮度の検査を通り続けてしまう。
  そのため、`new_implementation.iteration` と、`replace-metadata.json` の `loop.iterations` を突き合わせる。
  どちらかが読めなければ、合格として扱わず、`comparison-implementation-unversionable` で失敗にする。
  片側だけが `none` のとき（git での管理の有無が、記録の後に変わった）は、反復の回数が一致しても `comparison-implementation-stale` で失敗にする。
  `none` と実在する SHA は、同じ版を指さないからである。
- `component`・`item`・`instance` の id に `|` を使わない。突き合わせの鍵（`<component>|<item>|<instance>`）の区切りなので、含めると、あるセルの記録が別のセルの証拠として通る。
  網羅表の指紋も、区切りが曖昧になった同じ鍵を数えるので、一致してしまう。
- セルの値は変えない。
  新側で突き合わせていないことを理由に `present` を `unmeasured` に変えると、移行元で測った操作が未測定として数えられ、移行元の側で何を測ったかが読めなくなる（見た目の抜けと同じ扱い）。

##### 突き合わせの証拠は起点・当たり判定・完了に分ける

ケースの一覧からは見つからない欠落がある。実測された例には、次のものがある。

- 下位を持つ項目を押すと、メニューが閉じて下位が出ない。
- 下位を示す三角が押せる要素の外にあり、`cursor` も変わらない。
- 並び替えの印が、省略された文字に重なる。

どれも「機能は在る」が「操作を最後まで完了できない」形で、ケースの文面（「エクスポート」「列のソート」）には出てこない。
そこで、ケースに依らない 3 つの軸で観測する。3 点がすべてそろうまで、突き合わせ済みにしない。

| 軸 | 何を見るか |
|---|---|
| 起点（`entry`） | 新側でその操作を始められるか（操作を送れる要素に到達し、反応が起きる） |
| 当たり判定（`hit_area`） | 押せる範囲と `cursor` が、移行元と同じか（印が `::after` で行全体が 1 項目なのか、別の要素なのか） |
| 完了（`completion`） | 操作が最後まで通るか（下位が開く、並び替えが反映される、コンテナが閉じない） |

- 重なりと省略も、完了の側で見る。絶対配置の印は、余白を宣言していても、幅が足りなければ文字に重なる（省略が切るのは、文字の領域の端である）。
- 市販の部品のクラスの意味は、確かめてから読み替える（名前が近くても、条件が違う）。
- 突き合わせで差が出たら、`parity-replace` の実装に戻す。
  突き合わせないことを選ぶなら、利用者の承認（`disposition: accepted` と `approved_by`・`approved_at`）が要る。

#### 網羅表は見た目を見ていない

この表が数えるのは、操作と状態の有無だけである。色・寸法・余白・書体は、1 つも見ていない。
機能がそろっていて見た目が全部違う部品でも、すべてのセルが `present` で埋まる。
「部品の網羅表」という名前から、見た目も含むと読まれやすいので、ここで範囲を区切る。

- 見た目は、別の比較で確かめる。同じページの中では、画素の比較と特性照合（`parity-diff`）が受け持つ。
  画面より先に作った共通の部品では、`parity-component`（現行の要素から採った基準と、カタログ上の見本の照合）が受け持つ。
- そのため、`unmeasured` が 0 でも、「見た目が現行と合っている」ことは意味しない。
  `parity-diff` の収束の判定が網羅表を見るのは、測っていない操作が差分ゼロとして通るのを防ぐためである。見た目の合否は、あくまで画素の比較と特性照合が出す。
- 見た目の抜けを理由に、セルの値を変えない。
  見た目を確かめる比較がどこにも無い箇所（画素にも現れず、特性照合の対象でもない）は、`gaps.md` の未検証領域に、別の項目として残す。
  セルの値は、あくまで操作や状態を測ったかで決める。
  見た目の比較が無いことを理由に `present` を `unmeasured` に変えると、測った操作が未測定として数えられ、`parity-diff` が見た目とは別の理由で収束できなくなる。
  網羅表は見た目を測っていないので、変えても見た目の確認は 1 つも増えない。
- ただし、どの状態を撮るかは、この表から導く。
  表に並んだ操作は、コンテナを開く・指を乗せる・焦点を当てる・押している最中・不活性のどれを立てるかを決める材料になる。
  `value: present` のセルから、撮影状態の必要な集合が機械的に出る。
  手順と語の原本は、`parity-suite` の [`baseline.md`](baseline.md)「撮影状態の決め方（1）網羅表から導く」にある。
  導くのは「撮るべき状態の集合」までで、撮った結果が現行と合っているかは、引き続き画素の比較と特性照合が出す。

- インスタンスは「部品 × ページ」で数える。同じ部品を 2 つの画面で使っていれば、インスタンスは 2 つで、セルもそれぞれ測る。
  片方で測った結果を、共有の部品の値として固定しない。
- 値は 3 つ（`present`・`absent`・`unmeasured`）である。`absent` も、測った結果として記録する。
  「無いことを確かめた」と「測っていない」を、同じ空欄にしない。
  - `present`: 現行のインスタンスにその操作が在り、採取する状態（`metadata.json.capture_conditions.states`）か assertion で確かめた。確かめた先は `covered_by` に書く。
  - `absent`: 現行のインスタンスにその操作が無いことを、次のどちらかの方法で確かめた。
    - 操作できる要素が在る場合は、次の 1〜4 に従う。
      1. 操作用に取得した、見える要素に操作を送る。
      2. 操作のイベントが届いたことか、操作に応じた DOM や状態の変化で、発火を別に確かめる。
      3. 送り方・発火の確認・観測の結果の 3 点を、機械で読める `absence_evidence`（`action`・`fired`・`observation`）に記録する。
         `evidence` は空でない要約かどうかしか確かめられず、構造化した値を入れても検査されない。
      4. 1 つでも満たせなければ、「無い」と判定せず、`unmeasured` にする。

      この方法で `absent` に進む順序は、「発火を確かめた」→「期待する UI の応答が無い」である。発火そのものを確かめられない結果から、`absent` と結論しない。
    - どの状態にしても操作できる要素が無い場合は、次のように確かめる。
      非表示を確かめるには、`getByRole(..., { includeHidden: true })` か、同じくらい一意な構造のロケータを使う。そのロケータが、対象の部品インスタンスの操作の要素を一意に指すことを確かめる。
      確かめた結果は、後で述べる `locator_match_count` に、実測の値で残す。散文で確かめただけでは検査されない。
      hidden を含めて取得したことを、`absence_evidence.locator_includes_hidden: true` に実測として残す。
      通常の `getByRole` は hidden の要素を除くので、`display: none` の要素でも一致数が 0 になる。
      これを示さないと、非表示の状態を DOM に無いと読み替えて、`absent` で収束できてしまう。
      通常の操作と表示の判定に、role とアクセシブルネームを使う原則は変えない。
      次に、その候補を表示しうる適用可能な状態と遷移（トリガー、ビューポート、スクロール、データ、権限など）を挙げ、それぞれの状態にする。
      挙げる材料は、網羅プロファイルの候補と導出源、現行の UI である。
      すべての状態で、要素か祖先が非表示であるか、矩形の幅と高さの一方が 0 であることを実測する。
      次のものは、`absence_evidence` に機械で読める形で記録する。ロケータ・状態の導出源・試した状態と遷移・各状態の矩形と `offsetParent`・非表示の原因になった要素か祖先とその computed style である。
      `evidence` には記録しない。`evidence` は空かどうかしか検査されない散文の要約で、構造化した値を入れても読まれない。
      `offsetParent: null` だけを非表示の証拠にせず、矩形と非表示の原因も突き合わせる。
      セルの `absence_evidence` は、`kind: non-renderable`、`states_exhaustive: true` とする。
      インスタンスの `applicable_states` には、セルとは独立した状態の manifest を置く。manifest は、完全な source と `complete: true`、一意な `items[].id` と遷移を持つ。
      `applicable_states.source.kind` は、`profile`・`vendor-spec`・`current-source`・`app-ui` のどれかである。それ以外は出所が不明として、`unmeasured` にする。
      `state_source` から導いた重複の無い状態の id を `expected_states` に並べ、`applicable_states.items[].id` と `states[].name` の一意な集合と同じにする。遷移も manifest と一致させる。
      `locator` が対象の操作の要素に一意に当たることは、散文では保証されない。そこで、状態ごとに実測した一致数を、`states[].locator_match_count` として記録する。
      2 件以上なら、一意に取得できていないので `unmeasured` にする。0 件は、その状態で DOM に無いことの実測として扱う。
      このとき、矩形・`offset_parent`・`hidden_by` はすべて `null` にする（値が入っていれば、矛盾として `unmeasured`）。
      測り方は次のとおりである。`toHaveCount(n)` は期待値 `n` を先に渡して照合するので、件数を調べることはできない。
      `count()` は、`expect.poll` で包んでも、[`locator-mapping.md`](locator-mapping.md) と `scripts/auto-wait-check.mjs` が禁止している（実測）。そこで、0 か 1 かを判定する。
      このセルを `current-only/` で測る場合も、`count()` は使わない。検査は採取用のスペックの `immediate-read` を免除するが、免除は報告を止めるだけで、待たないことは変わらない。
      描画が終わる前の件数を `locator_match_count` に書くと、誤った `locator` と区別できなくなる。
      1. その状態に遷移し、状態が確定したことを、その状態に固有の assertion（開閉のフラグの `toHaveAttribute`、一覧の `toHaveCount` など）で先に確かめる。
      2. 確かめた後に `await expect(locator).toHaveCount(1)` を試し、成立すれば `locator_match_count: 1` にする。
      3. 成立しなければ `await expect(locator).toHaveCount(0)` を試し、成立すれば `locator_match_count: 0` にする。
      4. どちらも成立しなければ、対象を一意に取得できていないので、値を推測せず、そのセルを `unmeasured` にする（2 以上を自己申告で書かない）。

      すべての状態で 0 件だと、`locator` が対象を取得できていることを一度も示せず、誤った `locator` と区別できないので、`unmeasured` にする。
      同じ証拠を、`locator`・`state_source`・`states[]`（状態名・遷移・矩形・`offset_parent`・`hidden_by`）に、機械で読める形で記録する。
      `hidden_by` には、`target_locator`、`relation: self | ancestor`、`relationship_verified: true` で、対象との関係を記録する。
      `computed_style` が `display: none` か `visibility: hidden | collapse` を含む場合だけ、非表示の原因とする。
      `hidden_by` があるのに矩形が `null` でなければ、矛盾として `unmeasured` にする。
      これらを満たした場合だけ、操作を送らずに `absent` とする。
      確かめていない適用可能な状態がある、状態に到達できない、対象の要素の取得の仕方が不確か、または描画されない理由を実測できない場合は、`unmeasured` とする。
      ある時点の非表示や 0 の寸法だけで `absent` にすると、存在する操作が網羅から抜けるからである。
      抜けるのは、メニューを開く前、レスポンシブの切り替えの前、仮想スクロールの前、状態や権限を変える前に存在する操作である。

    操作できる要素で発火を確かめる方法では、`absence_evidence.kind: fired-without-response` を記録する。
    送り方・発火の確認・観測の結果の 3 点は、散文の `evidence` ではなく、機械で読める形で残す。
    - `action` には、`locator`、`method`（`locator-api` か `coordinate`）、`detail` を書く。
    - `fired` には、`signal`（`event-listener`・`dom-change`・`state-change` のどれか）、`detail`、`verified: true` を書く。
    - `observation` を書く。

    この方法は見える要素への操作が前提なので、`method` に関わらず、`bounding_box`（幅と高さがどちらも正）、`visible: true`、`actionability_bypassed: false` を実測の値で記録する。
    `force` や `dispatchEvent` で actionability を迂回した操作は、見える要素への操作の証拠にならない。
    `method: coordinate` では、さらに `hit_test_target` と `hit_test_is_target_or_descendant: true` も記録する。
    どれかが欠けるか、`true` にならない場合は、`absent` にせず `unmeasured` とする。
    コンテキストメニューで `locator.click({ button: 'right' })` が発火しない場合は、[`locator-mapping.md`](locator-mapping.md)「操作の実装差を吸収する層」に従って、判定用と操作用のロケータを分ける。
    操作用の要素の `boundingBox()` が `null` でなく、幅と高さがどちらも正で、中心の座標の hit-test がその要素か子孫を指す状態になるまで、`expect.poll` で自動で再試行する。
    条件が成立した直後にだけ、中心の座標に `page.mouse.click(x, y, { button: 'right' })` を送り、測り直す。
    前提を満たさない座標に操作を送ると、重なった別の要素の発火を取り違えるので、座標での操作に進まない。
  - `unmeasured`: 測っていない。`unmeasured_reason` に理由を書き、`gaps.md` にも残す。
- 行が無い組み合わせは、`unmeasured` として数える（判定できないものは、未測定として扱う）。
  `present` か `absent` なのに `evidence` が空のセルと、`present` なのに `covered_by` が空のセルも同じである。測った証拠が無いものを、測ったものとして扱わない。
- 期待するセルの数と未測定の数を、`metadata.json` の `component_coverage` に書く。
  期待するセルの数は、プロファイルを宣言していない部品なら「項目数 × インスタンス数」、宣言した部品ならインスタンスごとの候補の数の合計である。
  `declared: true` のときだけ `parity-diff` の収束の判定に入り、未測定が残る間は収束しない（判定の原本は `parity-diff` の `references/convergence.md`）。
- 部品を使っていない場合や、資料にも実際の UI にも到達できず一覧を作れない場合は、`declared: false` と理由を書き、同じ理由を `gaps.md` に残す。
  理由は必須で、空だと `parity-diff` の側で失敗する。キーごと省かない。
  キーが無いと、「古い版の `parity-suite` が作った成果物」とみなされ、`parity-diff` は後方互換のために判定を飛ばす。測らなかった事実が、そこに紛れ込む。
- 網羅表は現行の側の測定の結果なので、slug の直下に 1 つだけ置く（環境ごとに分けない）。
  `api-resource` と `batch` のモードは画面の部品を持たないので、作らない。

#### 3 つの集合に出所と完全性を要求する

網羅表は、3 つの集合の上に成り立つ。部品の集合（`components[]`）、インスタンスの集合（`components[].instances[]`）、軸の要素（`instances[].enumeration` と `applicable_states`）である。
挙げなかった要素は、期待するセルにも現れない。
そのため、出所と完全性を宣言させない集合では、測り忘れがあっても `unmeasured` が 0 のまま収束する。「載せなかった」と「本当に無い」が、同じに見えるからである。
どの集合も、同じ形で宣言する。形は、`source` の `kind`・`ref`・`version`・`condition`、`complete`、`false` のときの `incomplete_reason` である。

| 集合 | 宣言する場所 |
|---|---|
| 部品 | `component_inventory`（表の直下。この機能の画面に載っている部品の全体） |
| インスタンス | `components[].instance_inventory`（その部品を、どの画面に何個置いたか） |
| 項目 | `components[].source`（`kind` は `vendor-feature-list`・`vendor-test-spec`・`official-sample`・`current-source`・`app-ui` のどれか） |
| 軸の要素 | `instances[].enumeration.source` |
| 適用可能な状態 | `instances[].applicable_states.source`（`kind` の語は、前に述べた描画されない `absent` の規定に従う。強い順の語と `stronger_source_unavailable_reason` は当てはめない） |

- 集合の出所の `kind` は、強い順に `current-source` → `config` → `app-ui` である。
  これは、`component_inventory`・`instance_inventory`・`enumeration.source` の 3 つに当てはまる。項目の集合の `components[].source` と、適用可能な状態は、上の表の語を使う。
  先頭の、受け取った現行のソースが一次情報である。読めるなら、そこから部品の配置を静的に挙げてから、画面を開く。
  サーバー側のテンプレート（`.aspx`・`.ascx`・`.jsp` など）や部品の定義には、「どの画面にどの部品を何個置いたか」がそのまま並んでいる。
  画面は期待値を決めるのに使い、集合を挙げるのには使わない。
- 実際の UI を見て回る方法（`app-ui`）で拾えるのは、その画面がそのときに描いたものだけである。
  本体の周りに置かれた部品（ページャ、設定の保存と復元、右クリックで開くメニュー）は、本体の軸には現れない。集合の側で抜けると、誰も数えない。
- 一次情報以外で挙げたときは、`stronger_source_unavailable_reason` に理由を書く（受け取っていない・難読化されている・動的に生成されて追えない、など）。
  「読めなかった」と「実際の UI から作った」は別の事実だが、機械では区別できないので、申告させる。
  この欄は、`complete: false`（読めないときに、失敗として扱うための宣言）の反対側を残すためのものである。反対側とは、「読めるのに読まなかった」ことである。
  一次情報で挙げたのに理由が書かれている場合は、意味の無い免除として失敗にする。
- 意味の無い免除は、どの欄でも失敗にする（集合の出所と、インスタンスの `enumeration` の両方）。
  `complete: true` なのに `incomplete_reason` が残っている記録も、同じ扱いである。
  機械は収束させるのに、成果物を読む人には「まだ読み切れていない集合」に見え、`gaps.md` の行も同じ文言のまま残り続けるからである。
  `complete: true` にしたら、`incomplete_reason` は `null` にする。
- `components[].source.kind` に `current-source` があるのは、受け取ったソースから作った項目の集合を、`app-ui` として扱わないためである。
  `app-ui` として扱うと、静的にすべて読んだのか、画面に出ていたものを数えたのかが、後から区別できない。
- 検査するのは、記録する側の `coverage-expand.mjs` と、判定する側の `coverage-check.mjs` の両方である。
  `SET_SOURCE_KINDS` と `ITEM_SOURCE_KINDS` は、2 つのスクリプトで同じに保つ取り決めの領域に置く。
  欠けている、語の一覧に無い、完全性を宣言していない、理由が無い、のどれも未測定として数える。
  数える粒度は、宣言の置き場所に合わせる。`component_inventory` は表全体で 1 件、`instance_inventory` と `components[].source` は、その部品で合わせて 1 件である。
- この宣言を、ツールが自動で埋めることはしない（出所は捏造できない）。既存の網羅表には人かエージェントが追記し、追記するまでは未測定として残る。
  `--write` が警告なしに埋めると、どこから挙げたかを誰も測っていない表が収束してしまう。

### 項目集合そのものを導出する（網羅プロファイル）

網羅表は、登録された項目しか数えない。
データグリッドで代表の列だけを操作して、「フィルターあり」「ソートあり」の 2 項目を登録したとする。
すると、他の列・非表示の列・横スクロールの先の列・コンテキストメニューは、期待するセルにすら現れず、未測定 0 で収束する。
項目の粒度を、実行するエージェントの判断に任せている限り、この欠落は機械的には残らない。

これを防ぐのが、UI の部品ごとの網羅プロファイルである。
部品の構成要素（列やメニューの項目など）を出所付きで挙げ、プロファイルが宣言する軸との直積から、候補の集合を機械的に展開して、網羅表と照合する。

- 部品に固有の軸を、このファイルに書かない。軸、候補の挙げ方、必須の組み合わせ、同値クラスの制約は、各プロファイルが宣言する。
  共通の処理は、プロファイルを解釈するだけにする。Chart・Tree・DatePicker などを、共通の処理と中心の文書を変えずに足せるようにするためである。
- 取り決めの原本は [`coverage-profiles.md`](coverage-profiles.md) である。
  照合のツールは [`../scripts/coverage-expand.mjs`](../scripts/coverage-expand.mjs)、同梱のプロファイルは [`../assets/coverage-profiles/`](../assets/coverage-profiles/) にある。
- 合うプロファイルが無い複雑な部品を、暗黙のうちに汎用として扱わない。
  `profile: null` と `profile_absent_reason` を書き、同じ理由を `gaps.md` の未検証領域に残す（`profile` のキーを省くと、失敗する）。
- 上の 3 つの値、`evidence`、`covered_by`、判定できないものを未測定として扱う規則は、候補から来た期待するセルにも、そのまま当てはまる。

## 同じページに乗る他機能の在席

機能ごとに分けて、1 つずつ成功させる設計にしている。その裏返しとして、同じページに乗る別の機能のセクションがまるごと欠けていても、どのスイートも失敗しない。
各スイートは、自分の担当の範囲しか見ないからである。対象の機能のスイートに在席のチェックを置いて、これを防ぐ。

- 根拠は、`.replace/features.md` の「ページ一覧」（ページ × 乗る機能の slug）である。
  対象の機能のページに乗る他の機能ごとに 1 つ、そのセクションが在ることだけを確かめる assertion を置く。
- `.replace/features.md` の「ページ要素の帰属」の表で、対象のページの要素を他の slug が持っていれば、その要素にも在席のチェックを置く。
  共通のヘッダ、外部システムへ移るためのリンク、スコープ外と決めた操作の要素は、機能のセクションを持たないので、セクション単位の在席のチェックからは外れる。
  `扱い` が `スコープ外（配置のみ）` の要素も、在ることは確かめる。
  対象の slug 自身が持つ要素は、在席ではなく、自分のスイートの assertion で確かめる。在席の側に置くと、自分の担当の分がスキップの対象になるからである。
- 在ることだけを見る（ランドマークや見出しの role とアクセシブルネーム）。中身のパリティは、その機能のスイートの担当なので、踏み込まない。
- 新側でまだ実装していない機能の在席のチェックは、`new` のプロジェクトでスキップする（現側ではすべての機能が在るので、スキップしない）。
  スキップの注記には、対象の機能の slug を書く。実装が済んだ時点で、`parity-replace` が自分の slug を手がかりにスキップを外し、在席が成功することを確かめる。
  要素単位の在席のチェックの注記には、配置の持ち主の slug を書く。要素の内容を提供する機能ではなく、その要素を置く機能の slug である。
  `parity-replace` は自分の slug で検索して外すので、別の slug を書くと、いつまでも外されない。
  - スキップは、テスト単位（`new` のプロジェクトのときだけ飛ばす、条件付きのスキップ）で置く。
    現側専用のスペックのファイル単位の除外（`testIgnore`。[`locator-mapping.md`](locator-mapping.md)）とは、別のものである。
    ここでは、条件分岐が正しい方法である。成果物を書き出さず、外し忘れは在席が成功しないことで分かる。
  - 注記は、`parity-replace` が機械的に検索できる形にする（例: 注記に `presence:<slug>` を含め、その文字列で検索して外す）。自然な文だけだと、外す対象を見つけられない。
    `<slug>` に入れるものは、上の 2 つの規則で決まる。
    機能単位の在席のチェックなら、対象の機能の slug である。要素単位の在席のチェックなら、配置の持ち主の slug（要素の内容を提供する機能ではない）である。
- ページ一覧に無いページと、在席を確かめられない機能は、`gaps.md` に残す（確認済みにしない）。
- ページ一覧を持たない `.replace/features.md`（更新する前のインベントリ）では、機能一覧の「ページ」列から逆にたどれる範囲で、在席のチェックを置く。
  そのうえで、ページ一覧を `replace-strategy` の側で足すよう、ユーザーに促す（このスキルは features.md を書かない）。
  ただ 1 つの例外も、自分で書くのではなく、任せる。要求単位の根拠の書き戻しは、`replace-strategy evidence` が行う（[`api-batch.md`](api-batch.md)「要求単位を確定したら features.md へ書き戻す」）。
- 「ページ要素の帰属」の表を持たない `.replace/features.md`（この節を持たない版のインベントリ）では、要素の持ち主を推測で埋めない。
  持ち主が分からない要素を `gaps.md` に残し、表を `replace-strategy` の側で足すよう、ユーザーに促す。
  - 表はあるが持ち主が空欄の行（`replace-strategy` が確認待ちにした行）も、同じように扱う。
    空欄を自分で埋めず、その要素の在席を確認済みにせず、`gaps.md` に残す。

## 副作用出力の特性化

機能のページやバッチが作るファイルの出力と、帳票（PDF）を、現行アプリを操作して読み取りだけで捕捉し、ベースラインにする。

- 比べる観点は、文字コード、BOM、改行コード、列の順序、数値と日付の書式、PDF から抜き出したテキストと構造である。
- **揮発項目は意図的差異として除外する。** 揮発項目とは、生成日時のように毎回変わる項目である。
  xlsx は ZIP の中に生成日時などが入るので、バイト列の一致は取らず、シート × セルの値と構造で比べる（この節の対象）。
- バイト列の取得の方法（ダウンロードのイベント、`page.request`、batch ではファイルシステムから直接読む）、形式ごとの扱い、xlsx と PDF の解析ツールの選び方と記録の原本は、
  `replace-strategy` の `references/file-io.md` である（ここに転記しない）。到達できない出力は「対象」と判定せず、`gaps.md` に残す。
- 採用した解析ツールとその版は、`metadata.json` の `differ.file_extract` に記録する。`parity-diff` が、同じツールで新側から抜き出すためである。
- 表への書き込み（監査や利用のログなど）は、ここではなく、反応の網羅表の `side_effect_writes` で確かめる（上の「表への書き込み（`side_effect_writes`）」）。
- メールと外部との連携は、スコープ外である（捕捉するには、現行アプリの変更が要る）。`gaps.md` に記録する。
  対象と対象外の一覧の原本は、`replace-strategy` の `references/scope.md` である。

## 未測定を機械可読にする（収束判定の入力にする）

`gaps.md` は人が読む散文で、収束の判定には使われない。
そのため、「この状態は測っていない」と正しく書いてあっても、`parity-diff` は採った差分の分類が終わっているかだけを見て `converged: true` にできる。
実測では、6 つの機能すべてが収束した状態で、利用者が手作業で 8 件の差を見つけた。
うち 1 件は機能の欠落で、見つかった差の多くは、`gaps.md` に「測っていない」と正しく書かれていた領域にあった。

強度チェックも助けにならない。故障の注入は採った状態の中で行うので、採っていない状態には故障を入れられない。
通ってしまった故障が 0 件という結果は、確かめた範囲の広さの証拠にならない。

そこで、未測定を `metadata.json` の `unmeasured` に、機械で読める形で宣言する（様式の原本は [`../assets/metadata-template.json`](../assets/metadata-template.json)）。
書くのは、このスキルである。`gaps.md` に未検証として残した項目のうち、測るまで機能を閉じさせないものを、ここに転記する。
`item` と `reason` は、`gaps.md` の該当する行と同じ文言にし、成果物の片側だけに残さない。

- `disposition: blocking` が 1 件でも残る間は、`parity-diff` を収束させない（数え直しは [`../scripts/artifact-health-check.mjs`](../scripts/artifact-health-check.mjs) が行う）。
  止まるのは `parity-diff` だけである。このスキルの完了の判定は `--stage suite` で通すので、blocking を書いても、自分のチェックは止まらない。
  書き手が記録を消したくなる理由を作らないためである。
- API の要求単位を確定できなかった項目は、`endpoint` にその API を書く。`.replace/features.md` の API の列に書いた値を、1 文字も変えずに入れる。
  `replace-strategy` の `scripts/evidence-gap-check.mjs` は、この値の完全な一致だけを宣言として数える。
  `item` の散文に API が含まれるだけでは、宣言にならない（部分一致を許すと、別の API が宣言済みと誤って判定される）。
  書かないと、その API は、`parity-replace` の完了の判定で「書き戻しの抜け」として失敗する（API に結び付かない未測定では `null`）。
- `accepted` は、「測らないことをユーザーが承認した」記録で、`approved_by` と `approved_at` が要る。
  語の一覧に無いもの、欠けているもの、承認の記録が空のものは、`blocking` として数える（判定できないものは、止める側として扱う）。
- 後方互換のため、デフォルトでは振る舞いを変えない。`unmeasured` のキーを持たない成果物は、判定に入れない。
  「宣言が無ければ未収束」にすると、既存のすべての機能が一斉に未収束に変わる。そこで、宣言を持つ成果物から順に、厳しくなる形にする。
- `gaps.md` は残す。散文の説明（測れなかった事情や戻し先）はそのままで、ここに転記するのは、判定に入れる項目だけである。
- `entries` は追記専用である。`item` を消すと、`replace-strategy` の `scripts/append-only-check.mjs` が失敗にする（一覧の `parity-unmeasured`）。
  同じ項目かどうかは `item` で判定するので、`blocking` から `accepted` への承認の追記は、正当な変化として通る。
  この保護が無いと、`gaps.md` を触らずに `entries` から 1 件消すだけで、`checkUnmeasured` が空の一覧を見て収束してしまう。
  散文と機械で読める記録の組のうち、判定に入るのは後者だけなので、片側を消す書き換えは、両方の検査を通ってしまう。
