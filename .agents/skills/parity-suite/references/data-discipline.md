# 書き込み系データの扱い（全モード共通）

このファイルが原本である。feature・api-resource・batch のどのモードでも、状態を変える検証（書き込み系のスペック・ファイルのアップロード・バッチの実行）は、この規律に従う。

- 読み取り側の特性化を先に行う。状態を変えないので何度でも実行でき、DB を復元する環境が整う前でも進められる。
- 書き込み側は、復元できる環境でだけ行う（スナップショット → 実行 → リストア）。
- 復元できない場合は、一意な接頭辞を付けて自分で作ったデータと、その後始末で代える。
- 後始末できないもの（削除の機能が無いなど）は、事前にユーザーへ、残してよいかを確認する。
  そのうえで「hermetic でない」と明示して印を付け、`gaps.md` に一覧にする（隠さない）。
- 選択した target の `forbidden_actions` を、常に守る。対象は UI と API の操作で、空のリストはすべて実施してよい、定義が無ければ読み取りだけ、を意味する。
  意味の原本は、`replace-strategy` の `references/project-config.md` である。
  現行アプリのコードと構成には手を入れない。データの書き込みは、上の復元と後始末の規律と、承認の範囲でだけ行う。
  書き込みが許可されない target では、書き込み系のスペックを実行せず、`gaps.md` に「未検証」として記録する。

## ファイル・ストレージへの書き込み

- ファイルのアップロードも、この規律の対象である。アプリのストレージやファイルシステムに残る書き込みで、UI から消せないことが多いので、後始末できない側になりやすい。
  `gaps.md` の「hermetic でないテスト一覧」に頻繁に載る前提で、計画する。
  操作・fixture の作り方・何を確かめるかの原本は、`replace-strategy` の `references/file-io.md` である。
- 書き込んでよい範囲は、設定が決める。
  - ストレージに直接書く・消す（後始末など）のは、選択した target の `storage.write_scope` の下だけである（`storage.seedable: true` が前提）。アプリを通したアップロードは、`forbidden_actions` が決める。
  - DB は `db.seedable`、静的なデータは `dataset_static_paths` が決める。

  範囲の外に書こうとしたら、実行せずに止まる（取り決めの原本は、`replace-strategy` の `references/project-config.md`）。
- ストレージの実体へのゴールデンデータの投入は、スコープ外である（原本は `replace-strategy` の `references/project-config.md`「ファイルストレージ」）。
  アップロードの操作の特性化はスコープ内で、投入だけがスコープ外である。
