# Pr Finalize Loop

作成済みの GitHub PR を、CI が成功し、未解決のレビューの指摘が無くなるまで、自律して収束させる。
CI の失敗の修正、レビューの指摘への返信と解決、commit と push、設定したレビューツールへの再レビューの依頼という決まった往復を、人が何度も繰り返す代わりにループで回す。
PR そのものを作ることは、このスキルの対象外である（別に行う）。

この往復では、直して push すると CI とレビューがもう一度実行され、また直すことになる。収束するまで続けるので、止める時点を誤ると終わらない。
そのため、このスキルは次の 3 点を固定する。

1. ループの間は、利用者に確認せずに自律して進める。自分の PR でなければ、着手する前に 1 回だけ確認する。
2. 例外として、人の判断が要るレビューの指摘だけは確認し、判断を反映した後でループに戻る。
3. 反復の回数の上限と、行き詰まりの検知で、必ず止まる。

1 回分のレビューへの対応（確認・返信・解決）のやり方は、姉妹スキル [[pr-review-handle]] と同じである。このスキルは、それを自律したループとしてまとめる。

## 使い方

```text
pr-finalize-loop <PR URL> [--max-iterations <N>] [--wait-ci-before-review] [--review-tool <tool>] [--defer-decisions]
```

- `<PR URL>`（必須）: `https://github.com/<owner>/<repo>/pull/<番号>`。番号だけを渡されたら、現在の repo の PR とみなす。
- `--max-iterations <N>`（任意。デフォルトは 5）: 最初の effort で反復する回数。effort を下げるたびに、その半分の回数を追加で反復する（「反復の段階と effort」）。ループが終わらないのを防ぐ。
  1 回の反復は、状態の取得、CI とレビューへの対応、commit と push、再実行を待つ、までの 1 周である。
- `--wait-ci-before-review`（任意。デフォルトはオフ）: push した後の再レビューの依頼を、CI の再実行が終わるのを待ってから出す。
  デフォルト（オフ）では、push の直後に CI の完了を待たずに依頼し、CI とレビューを並行して進める。収束が速くなる。
  レビューが進行中なら（設定したツールの自動レビューでも、別のエージェントのレビューでも）依頼を保留する。
  失敗している HEAD にレビューを始めさせたくないときだけ指定する。
- `--review-tool <tool>`（任意）: この実行だけ、`copilot`・`claude-code`・`codex`・`local`・`none` のどれかを使う。設定ファイルを変えずに、クレジットの状況などに一時的に対応できる。
- `--defer-decisions`（任意。デフォルトはオフ）: 人の判断が要る指摘を利用者に確認せず、判断待ちとして残す。利用者が不在の自律実行の呼び出し元（`issue-batch` の run など）が付ける。
  付けたときの扱いは「自律性ポリシー」で定義する。単独で使うときは付けず、従来どおり確認する。
- ループの間は、利用者に確認せずに自律して進める。
  ループの中での例外は、後述の「自律性ポリシー」にある、人の判断が要るレビューの指摘だけである。着手する前の PR の持ち主の確認は、ループの外で行う。

例: `pr-finalize-loop https://github.com/<owner>/<repo>/pull/6` / `pr-finalize-loop 6 --max-iterations 3` / `pr-finalize-loop 6 --review-tool codex`

自然文でも発動する（「PR を最後まで解決して」「CI とレビュー指摘がなくなるまで回して」「PR の CI とレビューを収束させて」）。

## 前提

- ツール: `gh`（GitHub CLI。`gh api graphql`・`gh api` の REST・`gh pr checks`・`gh run view`・`gh run cancel`・`gh run rerun` を含む）、`git`
- 前提スキル: なし。レビューへの対応のやり方は [[pr-review-handle]] と同じだが、このスキルは自律して動くバージョンを中に持ち、単独で動く
- MCP: なし
- シェル: bash（POSIX 互換シェル）。コマンド例は bash で書いているので、Windows では WSL や Git Bash などの bash 環境で実行する
- ランタイム: pnpm や python は要らない。ただし、CI を直すときに、対象のリポジトリのランタイムが要ることはある
- Node.js は、設定ファイル（`.config/skills/shoji9x9/common.jsonc` など）を読むときだけ要る（同梱の `scripts/skill-config/skill-config.mjs` で読む）。
  設定ファイルがどの層にも無ければ、Node.js なしでデフォルトの値を使う。設定ファイルがあって Node.js が無ければ、設定を読めないとして止まる（`review_tool` のデフォルトは `copilot`）

## ブランチ運用・commit 規約の参照

ブランチ運用と commit の規約はリポジトリごとに違う。
決め方（設定ファイル、よく使われる文書の探索、利用者への確認の順）と、設定 `common` の `conventions_doc` の扱いは、[`references/conventions.md`](references/conventions.md) にある。
どの規約に決まっても、次の操作の決まりは常に守る。`--amend` と force push をしない。関係するファイルだけを stage する。長い commit の本文は `git commit -F <file>` で渡す。

## レビューツールの選択

push の後などに再レビューを依頼する AI レビュアーは、CLI のオプションと、設定ファイルの 3 つの層（このリポジトリの自分だけ・自分のすべてのリポジトリ・リポジトリの全員）から選ぶ。
選ぶ順序と、ツールごとの依頼の方法と成立の確かめ方は、[`references/review-tool.md`](references/review-tool.md) にある。
依頼先は同梱のスクリプト `scripts/resolve-review-tool.sh` で決め、値と、それがどの層（cli・local・user・repo・default）から来たかを報告してから使う。
決める順序を推測すると層を取り違え、設定してある値を「未設定」と判定して、別のツールに依頼してしまう。手順は [`references/review-tool.md`](references/review-tool.md) にある。

値は `copilot`・`claude-code`・`codex`・`local`・`none` のどれかである。
`local` のときは、依頼する代わりにエージェント自身が手元で HEAD をレビューし、レビューした HEAD の SHA と指摘の件数を、同梱のスクリプト `scripts/local-review-record.sh` で PR に記録する。
「HEAD がレビュー済み」は、その記録の SHA が HEAD と一致するかで判定する。手順は [`references/review-tool.md`](references/review-tool.md) の「local」にある。
`none` のときは再レビューを一切依頼せず、収束と完了の判定から「HEAD がレビュー済み」の条件を外す。CI がすべて成功し、未解決のスレッドが無く、スレッドの外の指摘にも対応していれば完了とする。
この先の本文で「レビューの依頼」と書くときは、設定した `review_tool` への依頼を指す。

## 自律性ポリシー

- ループの間は、確認せずに自律して実行する。CI の失敗の修正、レビューの指摘への返信と解決、commit と push、レビューツールへの再依頼を、利用者に 1 つずつ確認せずに進める。
- ループの中での例外は、人の判断が要るレビューの指摘だけである（着手する前の PR の持ち主の確認は、下の必須の前提を確かめた後で別に行う）。
  [`references/review-response.md`](references/review-response.md)「人に回すかの基準」で人に回すと決まった指摘は、勝手に直さず、誤って解決もせず、その 1 件だけ利用者に判断を求める。
  基準の要点は、調べて決まることは回さない、元に戻す手段が無い影響は必ず回す、元に戻せるものは影響の大きさと後で覆せるかで決める、の 3 つである。参照先を読めなければ、指摘への対応を始めずに止まる。
  判断を求めている間は、その指摘と関係する指摘（判断の答えで、直すかどうか・直し方・直す対象の行が変わりうる指摘）も直さず、返信も解決もしない。関係しない指摘は、答えを待たずに進める。
  関係の決め方は [`references/review-response.md`](references/review-response.md)「関係する指摘を、判断が出るまで直さない」で定める。参照先を読めなければ、答えが出るまで、ほかのすべての指摘を関係する指摘として扱う。
  判断を反映したら（直すか、直さない根拠を返信して解決したら）ループに戻り、収束するまで続ける。この確認でループを打ち切らない。
- `--defer-decisions` を付けたときの判断待ちの扱いは、ここで定義する（他の箇所はここを指す）。
  - 判断待ちにするのは、上の基準で人に回すと決まった指摘である。判断待ちの軸を、ここで別に定めない。
  - 基準で人に回さないと決まり、推奨の案で直すか見送った指摘は、選んだ案と根拠をスレッドの返信（スレッドの外の指摘はトップレベルのコメント）に書いて、通常の指摘と同じように解決する。
    呼び出し元（issue-batch の run など）は、これを「自分で判断して進めたもの」に記録する。
  - 判断待ちにした指摘と関係する指摘（上の関係の決め方による）は、それ自体の影響の大きさに関わらず、判断待ちに含める。
    印の返信（スレッドの外の指摘はトップレベルのコメント）には、どの判断待ちの指摘と関係するかを、その指摘の URL で書く。関係するかを決められずに含めたときは、その理由も書く。
    判断待ちの記録では、関係する指摘の選択肢を別に立てず、関係する判断待ちの指摘の URL を書く。呼び出し元が同じ判断を 2 回利用者に求めないためである。
    関係する判断待ちの指摘が 2 件以上あれば、印と記録にすべての URL を書く。
    関係する指摘が、それ自体も判断待ちに当たる形でも、関係する指摘として含める（`references/review-response.md`「関係する指摘を、判断が出るまで直さない」）。印と記録には、答えの後にもう一度判断が要りうることも書く。
    判断待ちから外れた後に評価し直し、まだ判断待ちに当たれば、新しい印を付けて判断待ちの指摘として記録する。同じ指摘に印が複数あるときは、最後の印で扱いを決める。
  - 判断待ちにした指摘は、利用者に確認しない。直さず、解決せずに残し、指摘の URL・選択肢とそれぞれの根拠と影響・推奨を判断待ちとして記録する。
    関係する指摘として含めた指摘は、選択肢と推奨を記録せず、上のとおり関係する判断待ちの指摘の URL を記録する。
  - 印を残す。スレッドの指摘には「判断待ちにした」ことを返信し（解決はしない）、スレッドの外の指摘はトップレベルのコメントでその旨と元の指摘の URL を記録する。
    どちらも本文の先頭に目印 `<!-- pr-finalize-loop:deferred -->` を入れる。
    `references/state-query.md` の索引は作成者のコメントを除くので、トップレベルの印は次のコマンドで別に読む。

    ```bash
    gh api --paginate repos/<owner>/<repo>/issues/<番号>/comments \
      --jq '.[] | select(.body | startswith("<!-- pr-finalize-loop:deferred -->")) | {id, login: .user.login, created_at, body}'
    ```

    印として読むのは、利用者（`gh api user` の login）が投稿したものだけである。ほかの人が目印を書いたコメントは、印として扱わない。

    次の反復やコンテキストの圧縮の後は、この印で判断待ちと見分ける。HEAD が進んで元のレビューを読まなくなっても、一覧から外さない。
  - 印より後に、その指摘に人が判断を返していれば、判断待ちから外し、その判断に従って通常の指摘として扱う。
    関係する指摘として判断待ちに含めた指摘は、それ自体に人の返信が無くても、印に書いたすべての判断待ちの指摘に人が判断を返した時点で判断待ちから外し、その判断に従って扱う。
    判断が要る形の関係する指摘は、外した後に、上の「関係する指摘が、それ自体も判断待ちに当たる形でも」の項のとおり評価し直す。
    人の判断とみなすのは、bot（`user.type` が `Bot`）でなく、目印を持たない投稿のうち、投稿した人が利用者（`gh api user` の login）か、リポジトリへの書き込み権限を持つ人のものである。
    書き込み権限は `gh api repos/<owner>/<repo>/collaborators/<login>/permission --jq .permission` が `admin` か `write` かで確かめ、取得できなければ判断とみなさない。
    PR にコメントできる人なら誰でも返信できるので、それ以外の人の返信を判断とみなすと、その人が人に回した判断の答えを選べる。それ以外の人の返信は、判断待ちのまま残す。
    利用者とエージェントが同じ login でも、エージェントは判断待ちの指摘に印しか投稿しないので区別できる。
  - CI の失敗と他の指摘は、続けてループで扱う。手順 2 の判定と再レビューの依頼の判定では、判断待ちの指摘を未解決に数えず、印の返信とコメントを「直近のレビューへの対応」に数えない。
    そのため、判断待ちだけが残り、HEAD がレビューされていなければ、手順 2 のとおり再レビューを依頼して待つ。
  - 判断待ちが 1 件でも残っていれば、手順 2 の条件がそろっても「完了」にせず、「判断待ちで終了」として止まる。`--max-iterations` は待たない。判断待ちの一覧を報告して呼び出し元に返す。
- 着手する前に、次の必須の前提を確かめる。満たさなければ着手せずに止まり、報告する。自律して commit と push をするので、対象を取り違えると危ない。そのため必ず先に確かめる。
  - PR が OPEN である。`MERGED` か `CLOSED` なら、仕上げる対象が無いと報告して終える。head ブランチが消えていることがあるので、これを最初に判定する。
  - 現在の repo と、PR の owner・repo が一致する。
  - 現在のローカルブランチが、PR の head ブランチと一致する。
- 必須の前提を確かめた後、ループに入る前に 1 回、PR の持ち主を確かめる。
  自分が PR の作成者でも担当者でもなければ、自律したループは他の人の PR に commit・push・resolve をすることになる。
  判定の方法は [`references/pr-ownership.md`](references/pr-ownership.md) で定義している。判定が `not-owner` なら、作成者と担当者を示して、続けるか中止するかを利用者に確認する。続けると決まったら、ループの間は聞き直さない。
  PR の作成者と担当者を取得できなければ、着手せずに止まる。
  自分の login を取得できない（ユーザーでないトークンで認証している）なら、判定を飛ばして続けるか中止するかを利用者に確認する。この扱いも、同じ `references/pr-ownership.md` で定義している。
  `--defer-decisions` のときは、この確認も送らない。`not-owner` か判定できないなら、着手せずに止まり、その理由を呼び出し元に返す（止まった理由は「持ち主の確認で中止」）。

## 基本フロー

着手する前の必須の前提と、PR の持ち主の確認を通ったら、`iteration = 1` から「反復の段階と effort」の最後の段階の回数を使い切るまで、次を繰り返す。
最初の段階の回数は `--max-iterations`（デフォルトは 5）である。

1. 状態を取得する。この段階ではレビューを依頼しない。待つ間隔と上限は、後述の「ポーリングと待機」に従う。
   - 要約を先に取得する。[`references/state-query.md`](references/state-query.md) を読み、review・thread・トップレベルのコメント・timeline・check-run は、先に索引（compact index）を取得する。
     全文を個別に取得するのは、現在の HEAD、前回の取得より後に遅れて届いた前の HEAD のレビュー、未処理の ID、未解決の指摘、レビューが届いたかの判定に要る check-run の出力だけにする。
     加工していない API の応答の全体を、反復のたびに会話に返さない。
   - PR の状態を確かめ直す。`gh pr view <番号> --repo <owner>/<repo> --json state` を再取得し、`OPEN` でなくなっていたら（他の人のマージやクローズなどで対象が無くなったら）、仕上げる対象が無くなったとして止まる。
     着手する前だけでなく、各反復の最初にも確かめ、無くなった対象の CI とレビューを待ち続けない。
   - CI: `gh pr checks <番号> --repo <owner>/<repo> --watch --fail-fast` で完了を待つ（どれかが失敗した時点で抜ける）。
     待っている間は、runner が割り当てられないジョブと、承認などを待つジョブを `references/ci-checks.md`「CI の完了を待つ」の手順で別に確かめる。`--watch` は、そのジョブが始まらないままでも返らないからである。
     push の直後は、チェックがまだ登録されておらず、すぐに `no checks` が返ることがある。そのときは `references/ci-checks.md`「`no checks` を確かめ直す」に従い、ベースブランチとの競合を確かめてから、間隔を空けて数回まで確かめ直す。
   - 未解決のレビュースレッド: [`references/state-query.md`](references/state-query.md) の reviewThreads の索引を `--paginate` で全件取得し、`isResolved == false` で絞る。すべてのレビュアーを対象にし、作成者では絞らない。
   - 現在の HEAD がレビュー済みかを判定する（`references/review-status.md`「HEAD のレビュー済み判定」）。
     根拠に使うのは、レビュー、現在の HEAD のレビュー用の check-run、現在の HEAD の完全な commit の OID を書いたレビューの bot のコメントである。
   - レビューが進行中かを確かめる。現在の HEAD に進行中のレビュー（PR の作成時や push のときの自動レビューを含む）や、進行中のレビューのエージェントが無いかを見る。
     方法は `references/review-request.md`「レビュー進行中の検出」にあり、`review_tool` によって変わる。`none` は再依頼しないので、この保留そのものが要らない。`local` は自分のレビューの完了を待たないが、別のエージェントの進行中のレビューは確かめる。
     進行中なら依頼せず、上限を決めて結果を待ち、届いた分を反映してから判定する。
   - レビューの内容と突き合わせる。HEAD への作成者以外のレビューがコメントを作っているのに、reviewThreads から取得できなければ、反映が遅れているとみなし、間隔を空けて再取得する（`references/review-status.md`「レビュー内容との整合検証」）。
   - スレッドの外の指摘を取得する。指摘はスレッドだけでなく、レビューの本文と PR のトップレベルのコメントにも書かれる（`references/review-status.md`「スレッド外に置かれた指摘」）。
     スレッドが 0 件で `comments.totalCount` が 0 でも、対応していない指摘が残っていることがある。そのため、HEAD への作成者以外のレビューの `body` とトップレベルのコメントを、必ず切り詰めずに読む。
2. 収束したかを判定する。依頼するより先に判定する。
   次のすべてを満たせば完了とし、要約を報告して終える。すでに CI とレビューがそろっている PR は、この時点でレビューも依頼せずに、何も変えずに終わる。
   `--defer-decisions` のときの判断待ちの数え方と、判断待ちが残るときの止まり方は、「自律性ポリシー」で定義する（判断待ちが残れば「完了」ではなく「判断待ちで終了」）。
   - CI がすべて成功している。
   - 未解決のスレッドが無い。
   - レビューの本文とトップレベルのコメントに、対応していない指摘が無い。
   - 現在の HEAD がレビュー済みである。
   - レビューの内容との突き合わせが通っている。

   `review_tool: none` のときは「HEAD がレビュー済み」を条件にしない。CI がすべて成功し、未解決のスレッドが無く、スレッドの外（レビューの本文とトップレベルのコメント）の指摘にも対応していれば完了とする（この先の依頼の手順も飛ばす）。
   - 直近のレビューへの対応（返信、解決、スレッドの外への対応の記録）の `createdAt` より後のレビューが HEAD に付いていなければ、コードを push したかに関わらず、「HEAD がレビュー済み」を満たさないものとして扱う（`review_tool: none` を除く）。
     今の HEAD へのレビューはその対応より前に行われたもので、レビュアーは対応の内容を見ていない。
     手順 2 は手順 4 より前に判定するので、判定の材料は「この反復でこれから行う対応」ではなく、「直近の対応より後のレビューがあるか」にする。
     前者にすると、前の反復の対応を拾えず、対応した反復の次で収束したと判定してしまう。
     満たさなければ手順 6 で再レビューを依頼し、新しいレビューの結果が届くか、上限まで待ち終えるまで、収束したと判定しない。
     この時刻の条件は、`review_tool: local` には当てない。`local` では、記録の SHA が HEAD と一致すれば満たす。返信と解決をしたエージェント自身がレビューするからである（[`references/review-tool.md`](references/review-tool.md) の「local」）。
   - CI がすべて成功して未解決のスレッドも無いのに、HEAD がレビューされていないときだけ（`review_tool: none` を除く）、レビューを依頼する。
     `references/review-request.md`「レビュー進行中の検出」を通ってから、設定したレビューツールに依頼し、上限を決めて待つ（同じファイルの「再レビュー依頼」）。
     レビューが付けば、次の反復で拾う。
     上限までに付かなければ、「レビュー未着で待機終了」として止まる。これは「完了」とは別の止まった理由にする。
     上限は目安なので、そう報告する前に、判定に使うすべての方法でもう一度取得する。
3. CI の失敗を直す。失敗したチェックのログを取得し（`references/ci-checks.md`「CI 失敗ログの取得」）、原因をコードの事実と照らして分析して直す。
   失敗が PR の変更と関係が無く、最新のベースブランチで直っていると確かめた事実で示せたら、PR で直さずにベースブランチを取り込み、判定の根拠を PR に記録する。
   判定の根拠・取り込み方・記録の仕方は `references/ci-checks.md`「PR と関係が無く、ベースブランチで直っている失敗」で定める。どちらかを確かめられないときと、参照先を読めないときは、取り込まずにログから原因を特定して直す。
   直せないとき、または同じ失敗が前の反復から良くならないときは、「行き詰まり」として扱う（後述の「停止条件」）。
4. レビューの指摘を 1 件ずつ解消する。スレッド、レビューの本文、トップレベルのコメントの 3 つをすべて対象にする。
   `review_tool: local` で `check` が `status=open` を返したら、その記録（出力の `record`）の本文に書いた、直すと決めた指摘も対象にする。この記録は、スレッドの外の指摘を集める処理が読まないので、ここで読む。
   1 件目を直し始める前に、すべての指摘を評価し、人の判断が要る指摘（手順 4 の 5）と、それに関係する指摘を決める。関係する指摘の扱いは「自律性ポリシー」で定める。
   1. 該当する `path` の `line` の付近を読み、指摘がコードの事実と合うかを評価する。
   2. 妥当で直す必要があれば、対象のファイルを直す。
      機能を足す・作り込む指摘（「この機能をきちんと実装すべき」など）は、直す前に、その機能の呼び出し元をリポジトリ全体で探す。
      呼び出し元が無ければ、削る案を作り込む案と並べて判断する。手順は [`references/review-response.md`](references/review-response.md)「機能を足す・作り込む指摘」で定める。
      指摘が特定の行の誤りではなく書き方の形（規則の違反・単位の書き方など）を指すなら、直す前に、その形を PR の差分で足した行全体で探す。
      差分の取り方・見つかった行の扱い・返信に書くことは、[`references/pattern-search.md`](references/pattern-search.md) で定義する。ここへ転記しない。
      参照先を読めなければ、指摘された行だけを直して済ませず、探せなかったことを返信に書く。
      この反復でまだ commit していない修正の行も探す対象に入る（commit は手順 5 でまとめて行う）。
      整形だけで変わった行に前からある問題は、下に挙げる直さない根拠の 2 つ目（指摘が PR の範囲の外にある）に当たる。
      直さないなら、その根拠を用意する。直さない根拠にしてよいのは、次の 4 つだけである。
      - 指摘が事実と違う（別の仕組みですでに対処している場合と、Issue やリポジトリの文書に書かれた設計の意図と食い違う場合を含む）。
        既存の取り決め（受け入れ条件・テストの期待値・コピーの決まり）を根拠にするときは、[`references/review-response.md`](references/review-response.md)「既存の取り決めを、直さない根拠にするとき」で、その前提が今も成り立つかを確かめる。
      - 指摘が PR の範囲の外にある。範囲の中は次の 3 つで、同じ PR で直す。PR が閉じる Issue の受け入れ条件のうちまだ満たしていない項目・この PR が意味を変えた行にある問題・この PR の変更が影響する箇所に生んだ問題である。
        受け入れ条件の節が無い Issue では、本文に書かれた要件を受け入れ条件として扱う。
        意味を変えた行は、PR の差分で足した行と、内容を変えた行である。意味を変えない語の置き換えや整形（折り返し・空白）だけで変わった行は含めない。
        変更が影響する箇所は、変えた行そのもの（整形だけで変えた行を含む）・変えた関数の呼び出し元・変えた手順を参照する文書・変えた設定を読むテストである。整形で YAML の字下げや Markdown の表が不正になった場合も、変更が生んだ問題に当たる。例は、変えた関数の新しい戻り値で、前からある呼び出し元が失敗することである。
        受け入れ条件の外にあり、この PR の前からある問題（レビューで見つかった既存の不具合など）は、意味を変えた行に無ければ範囲の外として扱い、別の Issue に回してよい。変更が影響する箇所にあっても同じである
      - 直すかに人の判断が要る（手順 4 の 5）。文書に書かれていない設計の意図を理由に見送りたいときも、ここに当たる
      - 「自律性ポリシー」が参照する基準で人に回さないと決まり、推奨の案に従って見送ったもの

      残っている反復の回数が少ないこと（`--max-iterations` の上限に近いこと）は、直さない根拠にしない。
      リポジトリの文書が定める書き方や手順（規約）に反するという指摘も、妥当なら直す。
      直した結果として上限に達しても、「最大反復到達」として止まって報告すればよいので、反復を節約するために見送る必要は無い。
   3. スレッドに返信してから解決する。この順序を必ず守り、返信していないスレッドは解決しない。
      返信は直した内容か直さない根拠から書き始め、同意・お礼・謝罪だけの文（「ご指摘のとおりです」「ありがとうございます」など）を書かない。
      書き方は [`references/review-response.md`](references/review-response.md)「返信の書き方」で定める。手順 4 の 4 のトップレベルのコメントも同じである。
      返信とトップレベルのコメントの本文は、投稿する前に `writing-style` スキルの手順で読み直す（スキルが無ければ省く）。
   4. レビューの本文とトップレベルのコメントの指摘には、返信するスレッドが無い（`resolve` もできない）。
      PR のトップレベルのコメントで、対象の箇所・判断・根拠・実測した結果を書いて返す。直した場合も、見送った場合も残す。
      `--defer-decisions` で判断待ちにした指摘は、この返し方ではなく、「自律性ポリシー」の印を残す。
   5. 人の判断が要るときは、直しも解決もせずに残す。この反復で関係しない指摘を 1〜4 で処理し、その修正を手順 5 で commit して push してから、利用者に判断を求める。
      返信で「直した」と書いた修正が、答えを待つ間も PR に入っているようにするためである。
      判断を求めると答えが来るまで先へ進めないので、先に求めると、関係しない指摘まで答えを待つことになる。
      答えを受けたら、その指摘と関係する指摘を、ふだんと同じ順序で処理する。手順 4 の 1〜4 で直すか根拠を書いて返信と解決をし、直したなら手順 5 で commit して push してから、手順 6 に進む。
      返信が push より前になるので、push に合わせて始まるレビューは返信も見る。手順 6 の基準の時刻は、この push が終わった時刻にする（直さずに返信だけをしたなら、手順 6 の push しなかった反復として扱う。前の push で始まった自動レビューは答えの後の返信を見ていないので、進行中ならその完了を待ってから依頼する）。
      `--defer-decisions` のときは確認しない。「自律性ポリシー」が参照する基準で人に回すと決まった指摘を、判断待ちとして記録して残す。
5. commit と push をする。手順 3 と 4 を両方終えてから、まとめて行う。
   レビューへの対応と CI の修正で触ったファイルだけを stage し、論理的な単位で conventional commit にして push する。関係の無い変更を入れない。コードを直していなければ、commit も push もしない。
   手順 3 でベースブランチを取り込んだ merge commit は、コードを直したものとして同じく push する。
6. 対応した後で、レビューが確実に実行される状態にする（`review_tool: none` のときは、この手順を丸ごと飛ばす）。
   きっかけは push だけではない。コードを直さず、手順 4 の返信・解決・スレッドの外への対応の記録だけで終わった反復も、その対応をレビュアーが見ていないので、同じように扱う。対応したから収束した、とはしない。
   - push した反復: 新しい HEAD はレビューされていないので依頼する。
     まず、push に合わせて自動レビューが始まっていないかを、`references/review-request.md`「レビュー進行中の検出」で確かめる。
     `copilot` ではタイムラインの Copilot 宛ての `review_requested` イベントで、`claude-code` と `codex` では進行中の bot のレビューかコメントで確かめる。
     始まっていれば、このスキルからは依頼せず、そのレビューの結果を次の反復で拾う。
     自動レビューが無いときだけ、レビューツールに再依頼する。依頼は、モードに関わらず、`references/review-request.md`「レビュー進行中の検出」を通ってから行う。
     デフォルトでは CI の完了を待たずに依頼し、CI の再実行が終わるのは次の反復の最初の手順 1 で待つ（CI とレビューが並行して進む）。
     `--wait-ci-before-review` を指定したときだけ、push による CI の再実行が終わるのを待ち、新しい HEAD がまだレビューされていなければ依頼する。
   - push しなかった反復（返信・解決・スレッドの外への対応の記録だけ）: この反復でそのどれも行っていなければ、何もしない（依頼せず、手順 7 に進む）。
     行っていれば、リモートの HEAD は変わらず、CI も新しく実行されないので、`--wait-ci-before-review` は関係しない。判断待ちの印だけを残した反復は、行ったものに数えない（「自律性ポリシー」）。
     `references/review-request.md`「レビュー進行中の検出」を通ってから、今の HEAD を対象に依頼する。
     基準の時刻には push が終わった時刻が無いので、HEAD の commit の `committedDate` ではなく、この反復で最後に投稿した返信やコメントの `createdAt` を下限に使う。それより前のレビューは対応を見ていない。

   `review_tool: local` では、push した反復でだけ、新しい HEAD を手元でレビューして記録する（[`references/review-tool.md`](references/review-tool.md) の「local」）。
   記録は、そのレビューの指摘を直して手順 5 で push するより前に、レビューの前に保存した SHA で投稿する。push の後に回すと、レビューした HEAD の記録を残せず、次の反復が PR の全体をレビューし直す。
   push しなかった反復では、HEAD の記録があれば（`check` が exit 0）、SHA が変わらず前の記録が有効なので、何もしない。
   記録が無ければ（ループを始めた最初の反復で、人のレビューのスレッドに返信しただけのときなど）、今の HEAD を手元でレビューして記録する。
   `check` が `status=open` を返したら（今の HEAD の記録に未対応の指摘が残っている）、レビューし直さない。扱いは `references/review-status.md`「HEAD のレビュー済み判定」の `local` の項にある。

   リポジトリに別のレビューの bot（CI から起動される auto-review など）があるというだけで、それをレビューツールへの依頼の代わりとみなして依頼を省かない。
   進行中のときに保留して判定し直すのは、検出の手順に従う。保留は省略ではない。HEAD がレビュー済みなら依頼しないのは、収束の判定のとおりである。
   HEAD がレビューされていないまま依頼そのものを省いてよいのは、利用者が明示して指示したときだけである。
7. 行き詰まりを検知する。この反復で、コードの修正もレビューへの対応も新しく何もできず、かつ CI の失敗が前の反復と同じで良くなっていなければ、止まる（後述の「停止条件」）。
8. `iteration` を 1 増やす。今の段階の回数を使い切ったら、「反復の段階と effort」に従って、effort を下げて次の段階に進むか、止まる。

## 反復の段階と effort

レビューツールが effort を指定できるなら、レビューが収束しないときに effort を下げて反復を足す。
指摘の数が多い effort のまま反復を続けると、直すたびに新しい指摘が出て、収束しないまま上限に達するからである。

- 最初の段階は、`--max-iterations` の回数を反復する。effort を指定できるツールで、呼び出し元が effort を決めていなければ、最初の段階の effort は high にする。
- 段階の回数を使い切ったら、CI の再実行が終わるのを待ってから（手順 1 の CI の確認と同じ）判定する。
  CI の失敗も判断待ちも残っていなければ（残っているのがレビューの指摘か、HEAD のレビュー待ちだけなら）、effort を 1 段下げて次の段階に進む。次の段階の回数は、前の段階の半分（切り下げ）にする。
- 半分の回数が 0 回になるか、それより下の effort が無くなったら、「最大反復到達」で止まる。
- 段階の回数を使い切ったときに、CI の失敗か判断待ちが残っていれば、effort を下げずに「最大反復到達」で止まる。effort を下げても、CI と判断待ちは片付かないからである。

effort を指定できるのは、`review_tool: local` で Claude Code の `/code-review <effort>` を使う場合だけである。effort は高い順に max・xhigh・high・medium・low である。
それ以外の依頼の方法は、effort を指定できないツールとして扱う。Copilot の `requested_reviewers`、`@claude review`・`@codex review` の mention、`codex review`、Copilot CLI がこれに当たる。
`references/review-tool.md` の依頼の手順に、これらに effort を渡す方法が無いからである。
手順に無い語を依頼に足して effort を渡そうとしない（`@codex review` に `review` 以外の語を足すと別の動作になることは、同じファイルに書いてある）。
一番下の effort（`low`）で始めた場合と、effort を指定できないツールの場合は、最初の段階が終わったら止まる。

| `--max-iterations` | 反復（`/code-review` を high で始めた場合） | 合計 |
| --- | --- | --- |
| 5 | high 5 回 → medium 2 回 → low 1 回 | 8 回 |
| 3 | high 3 回 → medium 1 回 | 4 回 |
| 1 | high 1 回 | 1 回 |

回数は段階ごとに半分になるので、合計は `--max-iterations` の 2 倍より少ない。
止まったときの報告には、段階ごとの effort と反復の回数（例: high 5 回 → medium 2 回 → low 1 回）を書く。
段階を下げたときは、下げた時点ごとに、その時点の HEAD の完全な SHA も書く（high から medium と、medium から low の 2 つなど）。段階を下げなかったときは SHA を書かず、段階を下げなかったと書く。
`review_tool: local` の記録を投稿するときは、`--reviewer` に使った effort を含める（例: `--reviewer '/code-review medium'`）。報告と後の確認の材料にするためで、段階を導き直す材料には使わない。
コンテキストの圧縮で進み具合のメモを失い、今の段階と残りの回数が分からなくなったら、「長時間実行・コンテキストの引き継ぎ」の手順で今の状況を導き直す。
残りの作業があれば、effort を下げずに最初の effort で 1 回だけ反復して止まる。
最後の段階を使い切った直後にメモを失うと、この 1 回で上限を 1 回超える。反復せずに止まると、残った指摘を直す機会が無くなるので、1 回に限って超えることを許す。
止まった理由は、「停止条件」の「完了」「レビュー未着で待機終了」「判断待ちで終了」のいずれかの条件を満たせばそれにし、どれも満たさなければ「最大反復到達」にする。
報告には、段階が分からなくなったことと、分かっている範囲の段階ごとの回数と、段階を下げた時点の HEAD の完全な SHA を書く。SHA が分からなければ、分からないと書く。

## 停止条件

どの場合も、終えるときに次を要約して報告する。CI の状態、残った未解決のスレッド、スレッドの外（レビューの本文とトップレベルのコメント）に残った指摘と総合の判定、反復の回数、止まった理由。
`--defer-decisions` のときは、止まった理由に関わらず、判断待ちの一覧（指摘の URL・選択肢・推奨。関係する指摘として含めた指摘は、指摘の URL と関係する判断待ちの指摘の URL）も載せる。
影響が小さく覆せるとして推奨の案で進めた指摘の一覧（指摘の URL・選んだ案・根拠）も載せる。呼び出し元は、この一覧から「自分で判断して進めたもの」を記録する。
未解決のスレッドを残して終わるときも、中身に対応せずに resolve して、偽って解決したことにはしない。

| 止まった理由 | 条件 |
| --- | --- |
| 完了 | CI がすべて成功し、未解決のスレッドが無く、レビューの本文とトップレベルのコメントに対応していない指摘が無く、HEAD がレビュー済みである。`review_tool: none` では HEAD がレビュー済みかを問わず、CI がすべて成功し、未解決のスレッドが無く、スレッドの外の指摘にも対応していれば完了とする |
| レビュー未着で待機終了 | 上のうち HEAD がレビュー済みであることだけを満たさず、レビューが現れるのを待つ時間が上限に達した |
| 最大反復到達 | 「反復の段階と effort」の最後の段階の回数を使い切った（effort を下げられないツールでは `--max-iterations` に達した）。または、進み具合のメモを失って段階が分からなくなり、1 回だけ反復した（「完了」「レビュー未着で待機終了」「判断待ちで終了」の条件を満たせば、そちらにする）。段階ごとの effort と反復の回数を書く。残っている CI の失敗、未解決のスレッド、スレッドの外（レビューの本文とトップレベルのコメント）の指摘を書く。止まった時点の HEAD が `references/review-status.md`「HEAD のレビュー済み判定」でレビュー済みでなければ、そのことを書く（`none` を除く）。その HEAD の CI が終わっていなければ、終わっていないと書く |
| 行き詰まり | 同じ CI の失敗が良くならず、新しく打てる手が無い。失敗の内容と、どうすれば直せそうかを報告する。runner が割り当てられないジョブか、承認などを待つジョブが上限を超えて始まらないときも、ここで止まる。ベースブランチとの競合で CI が起動しないとき（競合があるかを判定できないときを含む）も同じである（`references/ci-checks.md`「`no checks` を確かめ直す」）。手順 3 でベースブランチを取り込もうとして、merge が競合したときと、規約が merge を許さないときも同じである |
| 仕上げ対象なし | 着手する前か、ループの中の状態の取得で見つける。PR が OPEN でない（`MERGED` か `CLOSED`）。ループの途中で他の人のマージやクローズで対象が無くなったときも同じように止まる |
| 前提不一致 | 着手する前に止まる。repo が一致しない、または現在のブランチが PR の head と一致しない |
| 判断待ちで終了 | `--defer-decisions` のときだけ。CI がすべて成功し、残りの未解決のスレッドとスレッドの外の指摘が、すべて判断待ちにした人の判断が要る指摘か、それと関係するとして判断待ちに含めた指摘であり、HEAD がレビュー済みである（`review_tool: none` を除く）。判断待ちの一覧を、上の報告と同じ形で書く。「完了」とは別の止まった理由にする |
| 持ち主の確認で中止 | 着手する前に止まる。自分が PR の作成者でも担当者でもない（または自分の login を取得できない）ことを示し、利用者が中止を選んだ。`--defer-decisions` では利用者に確認せずに止まるので、利用者の判断が済んでいないことを報告に書く |
| 基準を読めずに停止 | 指摘への対応を始める前に止まる。人に回すかの基準のうちプロジェクトの基準（`references/review-response.md`「プロジェクトの基準」）を読めない、または PR の差分が基準の設定か文書を変えている。読めなかった理由か、変えているファイルを書く |

「レビュー未着で待機終了」は、「完了」とは別の止まった理由として報告する。依頼が成立していれば、遅れて届いたレビューに未解決の指摘が残りうる。
報告には、依頼した時刻、最後に取得した時刻、待つ時間の上限とその根拠（観測した届くまでの時間）を添える。

人の判断が要るレビューの指摘で確認するのは、止まる条件ではない。判断を反映した後でループに戻る（`--defer-decisions` のときは確認せず、判断待ちとして残す）。

## ポーリングと待機

待つときは必ず上限を決める。終わらない待ちと、ポーリングのしすぎの両方を避ける。具体的な間隔と回数は、リポジトリの CI にかかる時間に合わせて変えてよい。

待ち方の詳細は、待つ対象ごとに次のファイルで定める。参照先を読めなければ、その待ちを終わったものとして扱わず、「行き詰まり」として止まる。

| 待つ対象 | 参照先 |
| --- | --- |
| CI の完了（runner が割り当てられないジョブと、承認などを待つジョブの上限を含む） | [`references/ci-checks.md`](references/ci-checks.md)「CI の完了を待つ」 |
| push の直後に CI のチェックが登録されるまで | [`references/ci-checks.md`](references/ci-checks.md)「`no checks` を確かめ直す」 |
| 依頼したレビューが現れるまで | [`references/review-request.md`](references/review-request.md)「レビューが現れるのを待つ」 |

## 長時間実行・コンテキストの引き継ぎ

収束には時間がかかり、途中でコンテキストの自動圧縮（auto-compaction）が起きることがある。それに耐えるため、状態は GitHub にある実際の状態から取得し直す。

- 各反復は、GitHub の実際の状態から再開できるようにする。手順 1 で CI の状態と未解決のスレッドを取得し直す。保存済みの返信と解決から、実際の状態を組み立て直せる。
- 反復の回数の予算（`--max-iterations`）と行き詰まりの検知だけは、記憶に頼りやすい。「何回目の反復か」「今の段階の effort と、その段階で残っている回数」「段階を下げた時点の HEAD の完全な SHA」「直近の CI の失敗の要点」「上限を置いて待つジョブの `id`・状態と、その状態で初めて見つけた時刻」を短い進み具合のメモに残し、再開するときの起点にする。
  `waiting` の run では、environment ごとの初めて見つけた時刻も残す。
  メモを失ったら、GitHub の実際の状態から今の状況を導き直す。残りの作業が無ければ、反復を足さずに今の状況を報告して止まる。
  そのときは HEAD がレビュー済みかを取得し直して確かめ、レビューされていなければ「完了」ではなく「レビュー未着で待機終了」として報告する。予算がはっきりしないことを、レビューがそろった根拠にしない。

### 着手前チェック（repo / head ブランチの一致）

```bash
gh pr view <番号> --repo <owner>/<repo> --json headRefName,baseRefName,url,state
git branch --show-current
```

- `state` が `OPEN` でなければ（`MERGED` か `CLOSED`）、仕上げる対象が無いと報告して終える。head ブランチが削除されていることもあるので、ブランチの一致より先に判定する。
- 現在の repo（`gh repo view --json nameWithOwner -q .nameWithOwner`）と、PR の owner・repo が一致しなければ止まる。
- `headRefName` と現在のブランチが違えば、直す対象を取り違えるので止まる。

### 未解決スレッドの取得・返信・解決

未解決スレッドの一覧は、手順 1 のとおり [`references/state-query.md`](references/state-query.md) の索引で取得する。
索引はスレッドの `id` と先頭のコメントの `databaseId` を返すので、返信と解決にはそれを使う。返信（REST）と解決（GraphQL）の手順は [`references/review-threads.md`](references/review-threads.md) にある。参照先を読めなければ、返信も解決もせずに止まる。
`isResolved == false` のスレッドだけを 1 件ずつ処理し、返信してから解決する。
返信の本文は先にファイルに書き、`gh api` に `-F body=@<path>` で渡す（`gh api` に `--body-file` は無い）。

## commit の扱い

- commit message は、「ブランチ運用・commit 規約の参照」で決めた規約に従う。
  commit-msg の検証（commitlint や lefthook など）があれば、それにも従う。本文の行の長さに上限があれば守り、長い本文は `git commit -F <file>` で渡す。
  commit message の 1 行目は、commit する前に `writing-style` スキルの手順で読み直す（スキルが無ければ省く）。
- リリースのバージョンを上げる破壊的変更の定義が、規約の文書か、それがリンクや節名で案内する文書にあるとする。そのときは、修正で当たるかの判断が変わるかを commit の前に確かめる。変わるとは、当たるようになることと当たらなくなることである。
  変わるなら、直し方を自分で決めず、修正を commit する前に利用者に確認する（`--defer-decisions` では判断待ちとして残す）。案内先を読めないときと、定義で決められないときも同じである。
  答えで決まった直し方で、新しい commit（conventional commits なら `BREAKING CHANGE:` のフッター）と PR のタイトル・本文を直す。既にある commit は書き直さない。
- 規約の文書にも案内先の文書にも破壊的変更の定義が無いときは、修正が当たるかを判断しない。
  修正の後の変更が一般の意味で破壊的に見えるかで、PR の本文の見立てと理由を書くか、書き直すか、消す。
  一般の意味で破壊的とは、更新した利用者が手を入れないと従来の使い方を続けられないことである。
  破壊的に見えるなら、規約の文書に定義を置くことも勧める。プロジェクトが決めていない基準を持ち込まないので、commit message にも PR のタイトルと本文にも、`!` や `BREAKING CHANGE:` を書かない。
- 関係の無い変更を同じ commit に入れない。CI の修正とレビューへの対応で触ったファイルだけを stage する。既存の worktree に関係の無い差分があれば、入れない。
- pre-commit フック（lefthook など）や kaizen の commit 前のチェックがあれば実行される。チェックで止まったら、指示に従って `kaizen --current` を実行してから commit し直す。
- commit の `--amend` と force push はしない。

## 妥当性の判断ガイド

CI の失敗もレビューの指摘も、機械的にすべて直すことも、すべて退けることもせず、事実に基づいて 1 件ずつ判断する。

- レビューの指摘がコードの今の状態と合っていて、バグ・リスク・読みにくさなどの実害があるかを見る。別の仕組みですでに対処しているなら、直さずに根拠を返信する。
- 外部のツール・API・ライブラリの仕様についての指摘（特に「常に失敗する」という指摘）は、直す前に、公式のドキュメント・実際の出力・テストで確かめる。
  自信ありげな誤った指摘をそのまま「修正」すると、その修正が新しい不具合になる。
- CI の失敗は、失敗のログの事実から原因を特定して直す。結果が不安定なテストが疑われるときも、まず再実行や原因の確認で切り分け、テストやコードの本当のバグと取り違えない。
  PR と関係が無くベースブランチで直っている失敗だけは、PR で直さずに取り込む（手順 3）。
- 人に回すかは、「自律性ポリシー」が参照する基準で決める。人に回すと決まった指摘は、「人の判断が要る指摘」として扱う。その 1 件だけ利用者に確認してから、ループに戻る。
  確認している間は、その指摘と関係する指摘も直さず、返信も解決もしない（「自律性ポリシー」）。

## 追加確認が必要な条件

ループの間は自律して進めるが、次のときだけ確認する。最初の 2 つは止まり、3 つ目は着手する前に確認し、最後の 1 つは確認した後でループに戻る。

- 現在の repo と、PR の owner・repo が一致しない（着手する前に止まる）。
- 現在のローカルブランチが、PR の head ブランチと違う（着手する前に止まる）。
- 自分が PR の作成者でも担当者でもない（着手する前に 1 回確認し、続けるならループに入り、中止なら止まる。[`references/pr-ownership.md`](references/pr-ownership.md)）。
- レビューの指摘が、[`references/review-response.md`](references/review-response.md)「人に回すかの基準」で人に回すと決まった（その 1 件を確認し、反映した後でループに戻る。`--defer-decisions` のときは確認せず、判断待ちとして残す）。

## 利用者への確認

このスキルが利用者に確認する段・承認を得る段・選んでもらう段は、すべて [`references/user-confirmation.md`](references/user-confirmation.md) の手順で行う。
確認のツールを使えないエージェントでは、判断の材料と選択肢を本文に出して返事を待ち、返事を受け取る前に、その返事で決まる操作へ進まない。
`--defer-decisions` を付けた実行では、この節より「自律性ポリシー」の判断待ちの扱いが優先する。確認を送らずに判断待ちとして記録し、返事で決まる操作には進まない。
