# 検査ツールからの除外

worktree をリポジトリ内に置くと、その中身が**共有ツリー側の検査の対象になる**。
中身は別 branch の作業状態であり、[運搬した `.env`](carry-in.md) があれば**実物の資格情報**が入っている。
除外が無いと、自分の変更と無関係な理由で共有ツリー側の検査が落ちる。

## 1 か所では足りない

`.gitignore` に足せば済む、とは限らない。**`.gitignore` を読まない検査がある。**
除外を入れる先は「`.gitignore` に書いたか」ではなく「**どの検査がその dir を走査するか**」で列挙する。

このリポジトリで実際に必要だった除外は 4 種類だった。

| 検査 | 除外の書き方の例 | `.gitignore` を読むか |
| --- | --- | --- |
| `.gitignore` 本体 | `.claude/worktrees/` | — |
| Markdown linter（独自 glob） | `globs:` に `"!.claude/worktrees/**"` | 読まない |
| シークレット走査 | 設定ファイルの `[allowlist] paths` 等 | 読まない |
| 脆弱性スキャナ | スキャナ側の ignore 設定 | 読まない |

**必ず自分のリポジトリで列挙し直す。** 上の表は「4 つ入れれば済む」という意味ではない。

### 列挙のしかた

pre-commit フック（lefthook 等）と CI ワークフローの設定を開き、
**リポジトリ全体を走査する（対象ファイルを引数で受け取らない）ジョブ**を全部挙げる。
それらが除外先の候補になる。ファイル引数を受け取るジョブは staged 差分しか見ないため、
worktree 内のファイルは元々 staged にならず問題にならない。

## 検証は陽性コントロールで行う

除外は「何も出なくなった」ことで確かめられない。
**本当に無い**のと**検査が動いていない**のは同じ出力になる。

**既知マーカーを除外の対象外に置いて、検出できることを確かめる。**
除外の対象内に置いた確認は何も実証しない。

```bash
# 1. 陽性コントロール: 除外されない場所へ標的パターンを置き、検査が検出することを確認
# 2. 陰性コントロール: 同じパターンを worktree ディレクトリへ置き、検出されないことを確認
# 1 が検出できなければ 2 の結果には意味が無い
```

打ち切り（`timeout`）・非ゼロ終了は合格に倒さず FAIL として扱う。

## 除外パターンはルート起点

除外パターンは**リポジトリルート起点に固定され、入れ子には届かない**ことが多い。

**この点が置き場所の判断に直結する。**
worktree の中にさらに設定ファイルがある構造では、外側の除外が内側の走査に効かないことがある。
除外の手間と取りこぼしを避けたいなら、worktree をリポジトリ外に置く。
ただし代償が 2 つある。[自動運搬が走らなくなる](carry-in.md)ことと、
**`.claude/worktrees/` の外のパスへセッションを移すたびにユーザー承認が要る**こと
（[isolation.md](isolation.md)。無人実行ではここで詰まる）。

| 判断材料 | リポジトリ内（`.claude/worktrees/`） | リポジトリ外 |
| --- | --- | --- |
| 検査からの除外 | 全走査ジョブに必要 | 不要 |
| 自動運搬 | 走る（新規作成時） | 走らない |
| セッション移動時の承認 | 不要 | **毎回必要** |
| worktree 間の移動（複数 worktree を渡り歩く） | できる | **できない**（起動ディレクトリからの 1 回だけ。[isolation.md](isolation.md)「入れ子と再入場」） |
