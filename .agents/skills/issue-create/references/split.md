# 大きな依頼を分ける

1 つの PR に収まらない依頼を、複数の Issue に分けて起票する手順。
分けた Issue の本文には、先に済んでいる必要がある Issue を書く。複数の Issue を依存を考えた順に処理するツール（姉妹スキル `issue-batch` など）が、その記述を処理の順に使う。

## 分けるかを判断する

下書きを作る前に、依頼が 1 つの PR に収まるかを判断する。次のどれかに当たれば、収まらないとみなして分ける案を作る。

- 依頼に、それぞれ単独で使える機能が 2 つ以上あり、機能ごとに確かめ方が違う
- 1 つの変更を済ませないと、別の変更を始められない（前提の変更と、それを使う変更）

直す箇所が複数あっても、同じ確かめ方で 1 回のレビューに収まるなら（複数の箇所の同じ誤字など）、分けない。
迷ったら分けずに 1 件の下書きを作り、分けるかを確認の問いに含める。分けると答えたら、分けた下書きを作ってもう一度確かめる。
分けすぎると、それぞれの Issue が単独で確かめられなくなる。

## 縦の単位で分ける

1 つの Issue は、それだけで動作を確かめられる単位にする。層ごと（データベース・API・画面）には分けない。
層ごとに分けると、どの Issue も単独では動作を確かめられず、最後の Issue を済ませるまで受け入れ条件を判定できない。

- 各 Issue に、それだけで確かめられる受け入れ条件を書く。「後の Issue で確かめる」とは書かない
- 複数の Issue が使う共通の変更（設定・スキーマの追加など）がどうしても先に要るなら、それを最初の Issue にし、その Issue の受け入れ条件も単独で確かめられる形にする
- 分けた Issue の数が多くなる（目安は 5 件を超える）なら、依頼そのものを利用者と絞り込む

## 依存を書く

分けた Issue のうち、別の Issue の変更を前提にするものは、本文の最後に「依存」の節を置き、先に済んでいる必要がある Issue を番号で書く。テンプレートにこの節が無くても足す。

```markdown
## 依存

- #<番号>（<その Issue の何を前提にするか>）
```

- 書くのは前提にする側（後に処理する側）の本文だけである。前提にされる側には書かない
- 依存の無い Issue には、この節を置かない
- 番号は起票した後でないと決まらない。下書きでは `#<下書き N の番号>` のように、どの下書きの番号が入るかを書く。
  承認の後、前提にされる Issue から先に起票し、`gh issue create` が出力した URL から番号を取得して、後の Issue の本文の `#<下書き N の番号>` だけを置き換えてから起票する。
  置き換える以外に、承認を得た本文を変えない
- 依存が循環する分け方（A が B を、B が A を前提にする）にしない。循環すると、処理の順を決められない

## 確認と起票

- 分ける案は、全件の下書き（タイトル・本文・依存）をまとめて 1 回の確認で見せる。1 件ずつ確かめない。
  確かめ方は [`user-confirmation.md`](user-confirmation.md) に従う。選択肢には、案のとおり分けて起票する・1 件にまとめる・分け方を直す・起票しない、を含める
- 1 件にまとめると答えたら、まとめた下書きを作ってもう一度確かめる。見せていない本文で起票しない
- 承認を得たら、起票を始める前に、対象のリポジトリで最も新しい Issue の番号を控える（`gh issue list --repo <owner>/<repo> --state all --limit 1 --json number`）。
  Issue が 1 件も無ければ、0 を控える。番号を取得できなければ（コマンドの失敗など）、起票を始めずに止めて報告する。Issue の番号は増える一方なので、これより大きい番号の Issue は、起票を始めた後に作られたものである
- 前提にされる Issue から順に起票する。途中で起票に失敗したら、残りを起票せずに止める
- 失敗した呼び出しでも Issue が作られていることがあるので、作られたかを確かめる。
  手順 1 で決めたリポジトリで、自分が作った Issue の一覧を取得する。
  コマンドは `gh issue list --repo <owner>/<repo> --author @me --state all --limit 100 --json number,title,url` である。
  一覧は新しい順に返る。そのうち、控えた番号より大きく、タイトルが下書きと同じものを数える。
  タイトルはシェルの引用の中に書かず、ファイルに書いて読み込んで比べる。引用符や `\` を含むタイトルでも、比較が崩れないようにするためである
  - 1 件ならそれを作られた Issue とする
  - 0 件なら、1 分ほど置いてもう一度数え、それでも 0 件なら作られていないとする。一覧は、作られた直後の Issue をすぐには返さないことがある
  - 2 件以上・一覧の取得の失敗・打ち切りのときは、どれが作られたかを決められない。
    打ち切りとは、取得した件数が `--limit` に達し、かつ控えた番号以下の Issue が一覧に 1 件も無いことである（起票を始めた後の Issue を取りこぼしている）
    作られたものとしても作られていないものとしても扱わず、その Issue と残りの下書きを利用者に報告して止める
- 作った Issue の URL と残りの下書きを報告する。やり直すときは、作られた Issue を起票し直さず、その番号を後の Issue の依存の節に入れる
- 起票を終えたら、次の「GitHub の依存関係を設定する」を行う。途中で止めたときも、報告の前に、起票できた Issue の間の組を設定する
- 最後に、作った Issue の URL を処理する順に並べて返す

## GitHub の依存関係を設定する

本文の依存の節は、GitHub の画面や検索からは辿れない。
そこで、起票した後に、依存の節に書いた組ごとに GitHub の Issue の依存関係（blocked by）も設定する。
本文の依存の節は消さない。依存を本文から読むツール（姉妹スキル `issue-batch` など）があるからである。
起票を途中で止めたときは、起票できた Issue の間の組だけを設定する。やり直しで残りを起票したら、まだ設定していない組を設定する。

API は REST の Issue dependencies である（<https://docs.github.com/en/rest/issues/issue-dependencies>）。
`issue_id` には Issue の番号ではなく、Issue の `id`（整数）を渡す。

1. 前提にする側の Issue に、前提にされる Issue がすでに設定されていないかを確かめる。一覧はページに分かれるので `--paginate` で全件を読む。
   すでに含まれていれば、その組は設定済みとして 2 と 3 を飛ばす。やり直しで同じ組を 2 回設定しようとすると、API はエラーを返すからである。

   ```bash
   gh api --paginate "repos/<owner>/<repo>/issues/<前提にする番号>/dependencies/blocked_by" --jq '.[].number'
   ```

2. 前提にされる Issue の `id` を取得し、空でない整数であることを確かめてから、前提にする側の Issue に設定する。`-F` は値を整数として送る。

   ```bash
   blocker_id=$(gh api "repos/<owner>/<repo>/issues/<前提にされる番号>" --jq .id)
   if [[ $blocker_id =~ ^[0-9]+$ ]]; then
     gh api -X POST "repos/<owner>/<repo>/issues/<前提にする番号>/dependencies/blocked_by" -F "issue_id=$blocker_id"
   else
     echo "前提にされる Issue の id を取得できない: '$blocker_id'" >&2
   fi
   ```

3. 設定できたかを、1 と同じコマンドで一覧を取得して確かめる。前提にされる番号が含まれていれば、設定できている。

設定できなかった組（1 の一覧を取得できない・2 が失敗した・3 で番号が見つからない）があっても、起票した Issue は消さず、本文の依存の節もそのまま残す。
残りの組の設定は続け、最後に、設定できなかった組（前提にする番号と前提にされる番号）と、失敗したときの応答（HTTP の状態と `message`）を利用者に伝える。
依存関係の機能が使えないリポジトリや、書き込みの権限が無い場合に起きる。依存は本文の節で伝わるので、起票はやり直さない。
