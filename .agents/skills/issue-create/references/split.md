# 大きな依頼を分ける

1 つの PR に収まらない依頼を、複数の Issue に分けて起票する手順。
分けた Issue の本文には、先に済んでいる必要がある Issue を書く。複数の Issue を依存を考えた順に処理するツール（姉妹スキル `issue-batch` など）が、その記述を処理の順に使う。

## 分けるかを判断する

下書きを作る前に、依頼が 1 つの PR に収まるかを判断する。次のどれかに当たれば、収まらないとみなして分ける案を作る。

- 依頼に、それぞれ単独で使える機能や直す箇所が 2 つ以上ある
- 1 つの変更を済ませないと、別の変更を始められない（前提の変更と、それを使う変更）
- 変更を 1 回のレビューで確かめきれない（変える箇所が多く、確かめ方も箇所ごとに違う）

迷ったら分けずに 1 件で起票し、分けるかを確認の問いに含める。分けすぎると、それぞれの Issue が単独で確かめられなくなる。

## 縦の単位で分ける

1 つの Issue は、それだけで動作を確かめられる単位にする。層ごと（データベース・API・画面）には分けない。
層ごとに分けると、どの Issue も単独では動作を確かめられず、最後の Issue を済ませるまで受け入れ条件を判定できない。

- 各 Issue に、それだけで確かめられる受け入れ条件を書く。「後の Issue で確かめる」とは書かない
- 複数の Issue が使う共通の変更（設定・スキーマの追加など）がどうしても先に要るなら、それを最初の Issue にし、その Issue の受け入れ条件も単独で確かめられる形にする
- 分けた Issue の数が多くなる（目安は 5 件を超える）なら、依頼そのものを利用者と絞り込む

## 依存を書く

分けた Issue のうち、別の Issue の変更を前提にするものは、本文の最後に「依存」の節を置き、先に済んでいる必要がある Issue を番号で書く。テンプレートにこの節が無くても足す。

```markdown
## 依存

- #<番号>（<その Issue の何を前提にするか>）
```

- 書くのは前提にする側（後に処理する側）の本文だけである。前提にされる側には書かない
- 依存の無い Issue には、この節を置かない
- 番号は起票した後でないと決まらない。そのため、前提にされる Issue から先に起票し、得た番号を後の Issue の本文に入れてから起票する
- 依存が循環する分け方（A が B を、B が A を前提にする）にしない。循環すると、処理の順を決められない

## 確認と起票

- 分ける案は、全件の下書き（タイトル・本文・依存）をまとめて 1 回の確認で見せる。1 件ずつ確かめない。
  確かめ方は [`user-confirmation.md`](user-confirmation.md) に従う。選択肢には、案のとおり分けて起票する・1 件にまとめて起票する・分け方を直す、を含める
- 承認を得たら、前提にされる Issue から順に起票する。途中で起票に失敗したら、残りを起票せずに止め、作った Issue の URL と残りの下書きを報告する
- 最後に、作った Issue の URL を処理する順に並べて返す
