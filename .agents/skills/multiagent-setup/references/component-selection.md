# コンポーネント選択基準

追加したい知識・規約・自動の処理を、skill・rule・hook・ドキュメントのどれにするかを決める基準である。
スキルを明示的に呼んだときだけでなく、ドキュメントの整理を頼まれたときや、エージェントが自分からドキュメントを作ったり分けたりするときにも当てる。

## 最初の振り分け

追加したいものの性質で振り分ける。

| 追加したいもの | コンポーネント |
|-------------|-------------|
| 人／エージェントが実行する一連の手順・ワークフロー | スキル（`references/skills.md`） |
| 特定のファイル群を触るときに守らせたい規約 | ルール（`references/rules.md`。paths で自動適用） |
| 特定イベントで自動実行したい決定論的な処理（チェック・整形） | Hook（`references/hooks.md`） |
| 上記に当たらない知識・方針・仕様 | ドキュメント（`references/docs.md`） |

## ルール vs ドキュメントの分岐

規約や方針を残したいとき、ルールとドキュメントの境目は「いつ関係するか」で決める。

- 特定のファイル群を触るときだけ関係する規約は、ルールにする。paths で対象を絞り、その範囲を触るときだけ自動で読み込まれるようにする。
- 作業の対象に関わらず、常に把握しておく必要がある方針と規約は、ドキュメント（後で述べる基底ドキュメント）に置く。

ルールにすると決めたら、paths は最小の範囲で切る（`references/rules.md` の「rules 化とスコープの基準」）。

## ドキュメントの中での置き場所

ドキュメントにすると決めたら、置き場所を選ぶ。

- すべてのエージェントが常に把握しておく必要があるものは、基底ドキュメント（下で説明する）に置く。内容はここだけに書き、他からは複製せずに参照する。
- 特定のスキルを実行するときだけ要る詳しい手順は、そのスキルの `SKILL.md` か `references/` に置く。
- 長い参照情報や設計資料は、`docs/` などの専用のドキュメントに置き、基底ドキュメントからは参照だけを張る。

### 基底ドキュメントとは

プロジェクトが基本として常に読み込む、指示のドキュメントである。構成によって、どのファイルかが変わる。

- マルチエージェントの構成: `AGENTS.md`（`CLAUDE.md` と `.github/copilot-instructions.md` には差分だけを書く）
- Claude Code だけを使う: `CLAUDE.md`
- GitHub Copilot だけを使う: `.github/copilot-instructions.md`

`AGENTS.md` を持たない構成では、実際に使っている常に読み込まれるドキュメント（`CLAUDE.md` か `.github/copilot-instructions.md`）が、基底ドキュメントの役割を持つ。
「AGENTS.md へ」と書いた箇所は、その基底ドキュメントと読み替える。

## この基準自体の置き場所

この選択基準は、ドキュメントや規約を追加・整理するたびに関係するので、特定のファイルを触るときだけ関係するものではない。
そのため、この基準そのものは paths 付きのルールにしない。
ドキュメントの群を paths できれいに捉えられず、`**/*.md` にすると広すぎる、という問題に戻ってしまうからである。
代わりに、基底ドキュメントに短い判断基準（この表と分岐の要点）を置き、詳しくはこのファイルを参照させる。
こうすると、スキルを明示的に呼ばない場面でも、常にこの基準が当たる。
