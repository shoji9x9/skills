# データ設計（フェーズ A）

一から作る以上、**何を含めるかが品質のすべて**になる。データ設計は現行と新側の値比較を成立させる基盤であり、`.replace/dataset/design.md` に記録する（正本テンプレート: [`../assets/design-template.md`](../assets/design-template.md)）。

## 起点は DDL と機能インベントリ

- **DDL の制約**: テーブル、必須項目、型、一意制約、外部キーを起点にする。各テーブルの必須・一意・FK を満たす最小構成をまず作る
- **機能インベントリ**（`.replace/features.md`）: どのテーブルが対象か、どのリソースドメインに属するかを引く。対象テーブルは features.md の記録に従う（推測で足さない）。
  **テーブルは 3 つの表に分散して記録されているので、3 つとも読む**——機能一覧の「テーブル」列・**横断 API の「参照テーブル」列**・バッチの「参照テーブル」列。
  機能一覧だけを見ると、**横断 API からしか参照されないテーブル**（マスタ・設定・URL 解決など）が対象から落ち、fan-out 先の全機能で「画面の一部の値がゴールデンデータで制御できない」状態になる
- **横断 API 行の「参照テーブル」が空欄、または「参照テーブル」列そのものが無い**（列を持たない版のテンプレートで作られた features.md）なら、
  **対象なしと解釈せず `replace-strategy` 側の記録漏れを疑う**（空欄・列欠落と「参照テーブル無し」を同じに扱わない）。判断できなければ利用者に確認し、埋めてから設計に進む
- **「読むテーブル無し」の sentinel は `-` に統一する**（書き方の正本は `replace-strategy`）。`-` と書かれている行だけをゼロ件として扱い、
  それ以外の表記は空欄と同じく記録漏れとして確認する（表記を増やすと下流でブレて判定が曖昧になる）
- **`dataset_mode: static` では DDL の代わりに現行の静的データ形式**（ファイル配置・フィールド構成・型・ファイル間の参照）を起点にする。以降の設計規律（エッジケース・現実的な値・未カバー領域の記録）はモードに依らず同じで、「テーブル」を「静的データの単位」と読み替える

## 消費側から必要な値と量を導く

テーブル名だけでは、検索可能な値・順序を識別する値・ページ境界を越える件数を決められない。各機能／横断 API／バッチについて、対象テーブルを読むコードと現行 target の観測から、**絞り込み列と条件、並び替え列・方向・同値時の順序、ページサイズと切替候補**を調べ、`design.md` の「消費側パラメータ」に根拠付きで記録する。

- 候補列を DDL の型や列名だけから推測しない。現行コードを読み、UI に現れる条件・操作は現行 target で確定する
- 絞り込み条件ごとに一致／不一致／境界のデータを置き、ソートは主キー順に偶然一致しない値を置く
- ページサイズは想定値で固定せず、実測値と切替候補ごとに必要件数を算出する
- 調べられないパラメータは既定値を捏造せず未カバーとして残す。後の `parity-suite` で不足が判明したら version を上げて追加する

## エッジケースのチェックリスト

表示・挙動の比較で差が出る箇所を**意図的に**含める。各項目について「含めた／含めなかった（理由）」を design.md に残す。

- null（許容カラムに実際に null が入る行）
- 境界値（数値・日付の下限／上限、0・空文字と null の区別）
- 最大長（カラム定義の最大長ちょうどの値。表示の折り返し・省略に影響する）
- 権限・ロールのパターン（各ロールが少なくとも 1 件）
- 状態遷移の各状態（取りうる全ステータスをそれぞれ 1 件以上）
- **空リストになるケース**（フィルタ結果が 0 件になる条件を作れるデータ配置）
- **ページネーションの全操作を識別できる量**。対象一覧ごとに現行の 1 ページ表示件数 `P` と操作（次／前、ページ番号、先頭／最終、表示件数切替）を確認し、操作ごとに必要なページ数 `K` を決める。
  `K` ページを成立させる最小件数は `(K - 1) × P + 1`。単に 2 ページにせず、最終ページへの直接遷移や中間ページの確認があるなら 3 ページ以上を作る。表示件数を切り替える場合は、検証対象の各 `P` で必要件数を算出し、その最大値を採用する
- ソート順が判別できる並び（同点で崩れない、順序が視認できる値の散らばり）

ページネーションは `design.md` の表に、対象一覧、確認した操作、各表示件数、必要ページ数、採用件数、算出根拠を残す。
仕様の確認は、選択した現行 target から取得し、対象版・採取時点・条件を追跡できる実行ログ／観測記録 → ソースコード → API → UI の順に、十分な証拠が得られるところまで進める。
この順序は調査コストが実行ログ／観測記録 < ソースコード < API 操作 < UI 操作の順に高くなるためで、必要な証拠が得られた時点で止め、API／UI 操作は不足する場合だけ行う。
設計書・仕様書・受領ログを含む受領資料は調査候補の抽出にだけ使い、現行挙動の確定根拠にはしない。UI に現れる操作の有無は UI で確定する。確認できない操作は想像でデータを増やさず未カバーとして残す。

## 現実的な値の規律

**表示の検証に影響する項目に注意する。** 文字幅・桁数・改行の有無はレイアウト比較に影響する。

- 現実的な長さと文字種にする（`テスト1` のような値ばかりにしない）
- 全角・半角混在、改行を含む値、桁数の大きい数値など、実運用で現れる形を代表させる
- ただし非現実的な値ばかりにもしない（禁止事項 6）。**現実的な分布の中にエッジを混ぜる**

## 未カバー領域の記録

**「代表性がある」ことは証明できない。** 何を含め、何を含めなかったかを記録し、**未カバーの領域を明示する**（確認済みにしない）。

- design.md の「未カバーの領域と理由」節に、含めなかったパターンとその理由を残す
- `parity-suite` の探索で不足が判明したら追加する前提で作る（→ フェーズ A 再実行。[`versioning.md`](versioning.md)）

## 基準時刻の決め方

時刻に依存するデータは**基準時刻（`base_time`）を固定**し、そこからの相対で生成する。

- 「今週」「先週」の判定など、**週境界・日境界のロジックを持つ機能では特に重要**。境界の内・外に落ちる相対時刻を意図的に配置する
- `base_time` は `metadata.json` に記録し、投入ツールはハードコードせずここから相対時刻を計算する
- **基準時刻の変更はバージョンアップとして扱う**（論理データが変わるため。[`versioning.md`](versioning.md)）
