# 投入ツールの生成（両フェーズ共通の機構）

ツールは両フェーズで共通の機構を持ち、フェーズ A では現行を、フェーズ B では新側を投入先にする。
投入先の実体は、設定の `dataset_mode`（デフォルトは `db`）で決まる。`db` では各 target の DB を、`static` ではリポジトリの中の静的データ（`dataset_static_paths` の下）を書き換える。
以下の機構（削除・投入・検証の順、冪等、決定論）は両モードで共通で、違うのは書き込み先だけである。

## ツールの位置づけ

- 投入ツールは、対象のプロジェクトに生成する成果物であり、スキルに同梱して配布するものではない。
  そのため、配布スキルの拡張子の規約（`skills/**` は `.mjs`）の対象外で、プロジェクトの TypeScript（または SQL）として置く。
- スキルに同梱するのは、投入ツールを生成する手順とテンプレートであり、ツールそのものではない。
- 置き場所は、設定の `dataset_tool_dir`（指定が無ければ `seed/`）である。
- プロジェクトのコードなので、そのリポジトリのコーディング規約（設定の `references.coding_conventions`）に従って書く。規約が未整備でも停止しない。
  ただし、推測で自分の書き方を持ち込まず、基底ドキュメント・リントの設定・既存のコードから読み取る（解決の順は `replace-strategy` の `references/project-config.md`「コーディング規約」で定義する）。
  生成した後は、設定の `verification_commands.full` を通す（下記の「生成後の検証」）。

## 言語の選択

- TypeScript をデフォルトにする（このスキル群が前提にするスタックで、新側が TypeScript のため）。
- 難しい場合は SQL でもよい。SQL の場合は、まとめて commit できる形にする（作成したデータで PII を含まないので、commit に支障がない）。
- 選んだ言語は、`metadata.json` の `tool.language`（`typescript | sql`）に記録する。
- `dataset_mode: static` でも、TypeScript をデフォルトにする。生成物が JSON・Markdown・フィクスチャでも、それを生成するツールを書く。
  手で書いた静的データを直接 commit して、ツールを省かない。冪等性・決定論・作り直せることが失われ、フェーズ A の再実行（`version` を 1 上げる）を繰り返せなくなる。

## 構造（削除 → 投入 → 検証）

冪等性を保つため、毎回この順で実行する 1 つのエントリから実行する。

1. 削除: 外部キーの依存の逆順で、対象のデータを削除する（子のテーブルから先に消す）。先に削除するので、何度実行しても同じ状態から始まる。
   `static` では、`dataset_static_paths` の下の生成物を消す。消すのはこの下だけで、それ以外は読むだけにする。
2. 投入: 外部キーの依存の順で投入する（親のテーブルから先に入れる）。`static` では、`dataset_static_paths` の下に生成する。
3. 検証: 投入の直後に、FK の整合・必須項目・件数（`static` では参照の整合・必須フィールド・型・件数）を自分で検査する。詳しい検証の観点は、各フェーズの流れにある。

## 冪等性の確認

- 2 回続けて実行し、同じ状態になることを確かめる（件数と値が一致する）。
- 追記型（既存のデータを消さずに足す）にしない。再実行で件数が増えるものは、冪等ではない。

## 決定論

- ID・連番・UUID を固定の値にする（自動採番やランダムな生成をそのまま使わない）。
- 時刻に依存するデータは、`metadata.json` の `base_time` からの相対時刻で生成する（実行した時刻を参照しない）。
- これが無いと、投入のたびに現行と新側で値が変わって比較できず、投入し直すたびにパリティスイートが失敗する。

## 生成後の検証（`verification_commands`）

投入ツールは対象のプロジェクトのコードなので、生成・更新したら、設定の `verification_commands.full`（全体を対象にする列。静的解析・型の検査・テスト）を通す。
`diff`（変更したファイルだけを受け取る列）は使わない。投入ツールの生成は、他のファイルの正しさを変えることがあるので、差分に限った実行では見つけられない。
実行する範囲は、`replace-strategy` の `references/project-config.md` の、`verification_commands` の実行範囲を書いた節で定義する。

- 設定に `verification_commands.full` が無くても、停止しない。そのことを `verification.md` に記録して先に進む。
  `parity-replace` の完了の判定と違い、ここでの検証は生成物の品質を保つためのもので、投入の合否を決めるものではない。
  値がリスト（古い形式で、実行する範囲を宣言していない）のときも停止せず、範囲を宣言していないことを `verification.md` に記録して進む。
- 検証のコマンドが投入ツールのパスを対象に含んでいない場合（対象が新側のアプリのソースだけに絞られている、など）は、含まれていないことを記録する。範囲を自分で広げない。
- 冪等性・決定論の確認（2 回続けた実行・固定の値）は、この検証の代わりにならない。両方を行う。検証のコマンドは書き方を見るだけで、同じ状態に収束するかは見ない。

## 書き込み先のチェック（設定によるチェック）

ツールが破壊的に書き換えてよい先は、設定が決める。このチェックはツールそのものに実装し、範囲の外を指されたら書かずに終了する。実行時のエージェントの判断だけに任せない。

| `dataset_mode` | 書き込んでよい先 | チェック |
|---|---|---|
| `db`（デフォルト） | 投入先の target の DB | その target が `db.seedable: true` を持つこと。`db.env_vars` があっても `seedable` が無ければ読み取り専用として扱い、削除も投入もしない |
| `static` | `dataset_static_paths` の下 | 生成・削除の対象のパスが、すべて `dataset_static_paths` の下に収まること。1 つでも外に出たら停止する |
| （ストレージの実体） | 書き込まない（スコープの外） | `targets[].storage.seedable: true` でも、ツールはストレージに書かない。ストレージに依存するデータは未投入として記録し、`gaps` に回す |

- 許可が無ければ、設定を直すよう促して停止する。ツールにもスキルにも、「設定に `seedable: true` を足して続ける」という処理の流れを作らない。
- これは、自己申告の「本番でないことの確認」（SKILL.md の「厳守の制約」1）と併用する、2 つ目の安全策である。どちらかの代わりではない。両方を通って初めて投入する。
- 投入先の target の `forbidden_actions` の対象は、アプリへの UI・API の操作であり、投入ツールには適用されない（適用の範囲は `replace-strategy` の `references/project-config.md` で定義する）。
  投入してよいかを決めるのは、`forbidden_actions` ではなく上の表のチェックである。

## 同時実行の排他（ロック）

冪等性は、同時の実行を防がない。「同じ実行を繰り返せば同じ状態になる」ことと、「2 つの実行が同時に入っても失敗しない」ことは、別の性質である。
このツールは、上の「構造（削除 → 投入 → 検証）」のとおり、投入の途中で対象のテーブル（`static` では生成先）が空になる。
機能ごとに別のブランチ・別の worktree で並行して進めるのは普通の進め方である。フェーズ B は slug ごとに同じ target の同じマスタ表を入れ直すので、工程の設計から自然に衝突が起きる。

- ロックの単位は投入先である。`dataset_mode: db` では、投入先ごとに 1 つにする。
  同じ DB を指す target が複数あれば衝突するので、target 名ではなく、解決した接続先を鍵にする。
  `static` では、`dataset_static_paths` を持つリポジトリごとに 1 つにする。
- 方法は 2 つある。投入先の DB がセッション単位の排他（アドバイザリロック）を持つなら、それを使う。接続が切れれば必ず外れるので、異常終了しても残らない。
  持たない場合はロックファイルを使い、次のことを満たす。
  - 作るときは、既にあれば失敗する方法で作る（`O_EXCL` に当たるもの）。「無ければ作る」の 2 段階にすると、競合する。
  - 中身に、ホスト名・PID・開始時刻・投入先を書く。誰が持っているかを人が読めるようにする。
  - 正常終了と異常終了の両方で消す（`finally` とシグナル）。強制終了で残ることは避けられない。
    しかし、残ったロックを、経過時間で古いと判断して自動で消さない。実行中のプロセスを巻き込むからである（止まって見える実行と、入力待ちで出力の無い実行は、経過時間では区別できない）。人が中身を読んで消す。
- ロックを取れなければ、待たずに終了する。持っているプロセスの情報と、「同じ投入先に別の投入が実行されている」ことを stderr に出し、0 以外で終える。
  待つと、CI でもエージェントでもタイムアウトまで出力が無いまま止まり、投入したのかしていないのかが出力から読めなくなる。
- 書き込み先のチェックと同じく、ツールそのものに実装する（実行時のエージェントの判断に任せない）。順序は、ロックを取ってから削除を始める。
- 機能することを、検出されることの確認で実測してから使う。ロックを持ったまま 2 つ目の実行を起動し、2 つ目が 1 行も書かずに 0 以外で終わることを確かめる。
  同時に実行して失敗しなかったことは、排他が機能した証拠にならない（衝突しなかっただけのことがある）。実測した日時を、`metadata.json` の `tool.lock.verified_at` に残す。
- ロックが止めるのは、投入どうしの衝突だけである。同じ投入先を読むテスト（`parity-suite` や `parity-diff` の実行）との衝突は止まらない。
  読む側と投入を順に実行するか、並行して進めるなら投入先そのものを分ける（target を分ける）。運用で守る部分は、守れなかったことを検出できない
  （取り決めの原本は、このスキルの `SKILL.md`「厳守の制約」15）。

## 接続とシークレット

- 接続の情報は、設定の投入先の target（フェーズ A は `side: current`、フェーズ B は選んだ `side: new` の target）の `db.env_vars` にある環境変数の名前を通して読む。値を、設定・コード・ログ・成果物に書かない。
- シークレットが要るコマンドには、`secrets.wrapper` を前に付ける。
- `dataset_mode: static` では DB に接続しないので、この節は投入ツールには当てはまらない。アプリの認証など、他の用途で要る環境変数は、同じ規律で扱う。

## アップロード用ファイルの生成

アップロードを持つ機能では、`parity-suite` が渡す入力ファイルも論理データの一部である。ツールはこれを生成する。手で書いた静的なファイルを commit して、生成を省かない。

- 置き場所は、投入ツールと同じ `dataset_tool_dir` の下にする。現行と新側の両方で同じ入力を使うので、DB や静的データと同じ冪等・決定論の規律で扱う。
- 実際のアプリは、中身が妥当かを検査する（xlsx として開ける、画像としてデコードできる、サイズの上限）。数バイトのダミーでは処理が通らないので、本物として通るバイト列を生成する。
- 生成したファイルを、ストレージの実体に配置しない（スコープの外）。ファイルは、スイートが `setInputFiles` に渡す入力として使い、投入はしない。
- 操作・検証の対象・生成できない形式の扱いは、`replace-strategy` の `references/file-io.md`「ファイル入力（アップロード）」で定義する。

## フェーズ B のターゲット追加

フェーズ B では、同じ論理データを新側の受け皿の形に変換して投入する先を足す（論理データそのものは変えない）。変換の設計は [`phase-b.md`](phase-b.md) に従う。
ツールの削除・投入・検証の構造は共通で、書き込み先と変換の層だけが新側向けになる。
`dataset_mode: db` では、選んだ新側の target の `db.env_vars` で接続先を切り替えられるようにし、複数の新側の target に同じツールを再実行できる形にする。
`static` では、新側のリポジトリの `dataset_static_paths` の下に生成する。生成物は target をまたいで同じになるので、target ごとに変わるのは投入した後の検証だけである。
