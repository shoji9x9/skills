# 投入ツールの生成（両フェーズ共通の機構）

ツールは両フェーズで共通の機構を持ち、フェーズ A では現行、フェーズ B では新側をターゲットにする。**投入先の実体は設定の `dataset_mode`**（既定 `db`）で決まり、`db` は各 target の DB、`static` はリポジトリ内の静的データ（`dataset_static_paths` 配下）を書き換える。以下の機構（削除 → 投入 → 検証・冪等・決定論）は両モード共通で、違うのは書き込み先だけである。

## ツールの位置づけ

- 投入ツールは**対象プロジェクト側に生成される成果物**であり、スキル本体に同梱する配布物ではない。したがって配布スキルの拡張子規約（`skills/**` は `.mjs`）の対象外で、**プロジェクト側の TypeScript（または SQL）として置く**
- スキルに同梱するのは「投入ツールを生成する手順・テンプレート」であって、ツール本体ではない
- 配置先は設定の `dataset_tool_dir`（未指定時は `seed/`）
- **プロジェクト側のコードなので、そのリポジトリのコーディング規約（設定の `references.coding_conventions`）に従って書く。** 未整備でも停止しないが、
  **推測で自分の流儀を持ち込まず**、基底ドキュメント・リント設定・既存コードから読み取る（解決順の正本は `replace-strategy` の `references/project-config.md`「コーディング規約」）。
  生成後は設定の `verification_commands.full` を通す（下記「生成後の検証」）

## 言語の選択

- **TypeScript が既定**（本スキル群の前提スタック。新側が TypeScript のため）
- 難しい場合は **SQL** でもよい。SQL の場合は**まとめてコミットできる形**にする（authored データであり PII を含まないため、コミットに支障がない）
- 選んだ言語は `metadata.json` の `tool.language`（`typescript | sql`）に記録する
- `dataset_mode: static` でも TypeScript が既定（生成物が JSON / Markdown / フィクスチャでも、それを**生成するツール**を書く）。
  **手書きの静的データを直接コミットしてツールを省略しない**——冪等性・決定論・再生成可能性が失われ、フェーズ A 再実行（`version` +1）のループが回らなくなる

## 構造（削除 → 投入 → 検証）

冪等性を担保するため、毎回この順で走る 1 つのエントリから実行する。

1. **削除**: **外部キーの依存の逆順**で対象データを削除する（子テーブルから先に消す）。事前削除により、何度実行しても同じ状態から始まる。
   `static` では `dataset_static_paths` 配下の生成物を消す（**この配下だけ**。それ以外は読むだけで消さない）
2. **投入**: **外部キーの依存順**で投入する（親テーブルから先に入れる）。`static` では `dataset_static_paths` 配下へ生成する
3. **検証**: 投入直後に FK 整合・必須項目・件数（`static` では参照整合・必須フィールド・型・件数）を自己検査する（詳細な検証観点は各フェーズのフロー）

## 冪等性の確認

- **2 回連続で実行し、同一状態になることを確認する**（件数・値が一致する）
- 追記型（既存を消さずに足す）にしない。再実行で件数が増えるものは冪等でない

## 決定論

- **ID・連番・UUID を固定値にする**（自動採番・ランダム生成をそのまま使わない）
- 時刻に依存するデータは `metadata.json` の `base_time` からの**相対時刻**で生成する（実行時刻を参照しない）
- これが無いと投入のたびに現行と新側で違う値になり比較が成立せず、再投入のたびにパリティスイートが壊れる

## 生成後の検証（`verification_commands`）

投入ツールは対象プロジェクト側のコードなので、**生成・更新したら設定の `verification_commands.full`（全体走査の列。静的解析・型検査・テスト）を通す**。
**`diff`（変更ファイルだけを受け取る列）は使わない**——投入ツールの生成は他ファイルの正しさを変えうるため、差分限定では捕まらない（走る範囲の正本は `replace-strategy` の `references/project-config.md`「走る範囲」）。

- **設定に `verification_commands.full` が無ければ停止しない。** その旨を `verification.md` に記録して先へ進む（`parity-replace` の完了判定と違い、ここでの検証は生成物の品質担保であって投入の合否判定ではない）。
  **値がリスト（旧形式＝走る範囲が未宣言）のときも停止せず**、範囲未宣言であることを `verification.md` に記録して進む
- **検証コマンドが投入ツールのパスを対象に含んでいない場合**（対象範囲が新側アプリのソースだけに絞られている等）は、**含まれていないことを記録する**。範囲を勝手に広げない
- **冪等性・決定論の確認（2 回連続実行・固定値）はこの検証の代替ではない。** 両方行う——検証コマンドは書き方を見るだけで、同じ状態に収束するかは見ない

## 書き込み先のゲート（設定由来）

ツールが破壊的に書き換えてよい先は設定が決める。**ツール自身にこのゲートを実装し**、範囲外を指されたら書かずに終了する（実行時のエージェント判断だけに委ねない）。

| `dataset_mode` | 書き込んでよい先 | ゲート |
|---|---|---|
| `db`（既定） | 投入先 target の DB | その target が `db.seedable: true` を持つこと。`db.env_vars` があっても `seedable` が無ければ**読み取り専用**として扱い、削除・投入をしない |
| `static` | `dataset_static_paths` 配下 | 生成・削除の対象パスがすべて `dataset_static_paths` 配下に収まること。1 つでも外に出たら停止する |
| （ストレージ実体） | **書き込まない**（v1 スコープ外） | `targets[].storage.seedable: true` でもツールはストレージへ書かない。ストレージ依存のデータは未投入として記録し `gaps` へ回す |

- 許可が無ければ**設定の修正を促して停止する**（ツールにもスキルにも「設定に `seedable: true` を足して続行する」経路を作らない）
- これは**自己申告の「本番でないことの確認ゲート」（SKILL.md「厳守の制約」1）と併用する 2 枚目の安全弁**であり、片方の代替ではない。両方通ってはじめて投入する
- 投入先 target の `forbidden_actions` は**アプリへの UI / API 操作**が対象であり、投入ツールには**適用されない**（適用範囲の正本は `replace-strategy` の `references/project-config.md`）。
  投入可否を決めるのは `forbidden_actions` ではなく上表のゲートである

## 接続とシークレット

- 接続情報は設定の**投入先 target**（フェーズ A は `side: current`、フェーズ B は `side: new` の選択 target）の `db.env_vars` の環境変数**名**経由で読む。**値を設定・コード・ログ・成果物に書かない**
- シークレットが要るコマンドは `secrets.wrapper` を前置する
- `dataset_mode: static` では DB 接続を持たないため、この節は投入ツールには当てはまらない（アプリの認証等、他の用途で要る環境変数は同じ規律で扱う）

## アップロード用ファイルの生成

アップロードを持つ機能では、`parity-suite` が流す**入力ファイルも論理データの一部**である。ツールはこれを**生成する**（手書きの静的ファイルをコミットして生成を省略しない）。

- 置き場所は投入ツールと同じ `dataset_tool_dir` 配下。**現・新の両側で同じ入力を使う**ため、DB / 静的データと同じ冪等・決定論の規律に乗せる
- **実アプリは中身の妥当性を検査する**（xlsx として開ける・画像としてデコードできる・サイズ上限）。数バイトのダミーでは経路を通らないため、**本物として通るバイト列**を生成する
- **生成したファイルをストレージ実体へ配置しない**（v1 スコープ外）。ファイルはスイートが `setInputFiles` に渡す入力として使い、投入はしない
- 操作・検証対象・生成できない形式の扱いの正本は `replace-strategy` の `references/file-io.md`「ファイル入力（アップロード）」

## フェーズ B のターゲット追加

フェーズ B では、同じ論理データを**新側の受け皿へ写像**して投入するターゲットを追加する（論理データ自体は変えない）。写像の設計は [`phase-b.md`](phase-b.md) に従う。ツールの削除・投入・検証の構造は共通のまま、書き込み先と写像層だけが新側向けになる。
`dataset_mode: db` では接続先を選択した新側 target の `db.env_vars` で切り替えられるようにし、複数の新側 target に対して同じツールを再実行できる形にする。
`static` では新側リポジトリの `dataset_static_paths` 配下へ生成する（生成物は target をまたいで同一になるため、target ごとに変わるのは投入後の検証だけ）。
