# 新側の実装（現行のコードを一次情報源として読み、確信度を申告する）

現行のコードの読み方、照合の単位の振り分け、確信度を常に申告すること、未解決の箇所を書くこと、振る舞いを保つことと品質を改善することを分けることを定める。

## 現行のコードは、常にロジックの一次情報源である

現行のコードは、フロントエンドでもバックエンドでも読む。バリデーションの規則・fetch・状態の遷移・エラー処理・ログの送信は、コードを確かめないと再現できない。

フロントエンドとバックエンドで違うのは、現行のコードを読むかどうかではなく、レビューの照合の単位である。

| | ロジックの情報源 | レビューの照合の単位 |
|---|---|---|
| バックエンド（現行のコードがある） | 現行のコード | 旧と新を並べた diff が成り立つ |
| フロントエンド（1 対 1 の対応を作れない） | 現行のコード（ロジック）と、視覚ベースライン（見た目・構造） | diff は成り立たない。パリティスイートが green か、`parity-diff` の差分がゼロかで照合する |

- `replace-strategy` の測定（現行のコードを入手できるか）に従って振り分ける。現行のコードを入手できない側は、パリティスイートとベースラインだけが頼りになる
- 意図的差異レジストリの `keep`（テーブル名・項目名・API のエンドポイント・同じ機能なら同じ関数名・スコープの広い変数名）があるので、diff をレビューできる。
  ディレクトリの構成・ファイル名・スコープの狭い変数名は変えてよいが、変えるほど照合のコストが上がる

## 推測せず、確信度を常に申告する

- 推測で実装しない。判断できない箇所は、未解決であることをコード上に書き（`TODO` コメントなど）、レビューへ回す。間違ったコードより、未解決と書いてあるほうがよい
- 確信度（高・中・低）を、実装単位（ファイル、またはページの中のエリア）ごとに 1 行、常に `porting.md` へ申告する
  - 迷ったときだけにしない。迷ったときだけの申告にすると、迷っていることに気付かなかった箇所が素通りする。
    常に書けば「低」が普通の申告になり、言い出すコストが下がり、レビューの側で優先順位を付けるのにも使える
  - 「低」は、おそらく間違っているので、レビューで現行を読み直す必要があることを表す
- 長い言い訳のコメントが付いている箇所は、コードが間違っている兆しとして扱う
- 実装の途中で部品が足りないと分かったら、そのまま自前で書き始めない。実行フローの「部品の洗い出しと依存の決定」と同じ基準で判断し、`.replace/dependencies.md` へ追記してから実装を続ける
  （基準の原本は `replace-strategy` の `references/dependency-selection.md`）。`porting.md` の該当する実装単位にも、どの部品をどう決めたかを 1 行残す

## DB の方言差は、書く前に点検する

現行の DB と新しい DB は、同じ意味で書いたクエリでも同じ結果を返さない。差は、読んでから書けば出ない。
書いてから敵対的レビュー（手順 7）で見つけると、手戻りが最も大きい。
しかも、絞り込みが全件の取得に変わるような差は、ゴールデンデータセットの件数が少ないとパリティスイートが green のまま残るので、レビューが最後の確認になる。

- 点検表は、設定の `references.db_semantics` から読む。点検の項目（NULL の並び順、暗黙の型変換と失敗したときの値、照合順序、連結するときの NULL、書式のロケールへの依存）と、
  点検表が網羅ではないことの原本は、`replace-strategy` の `references/project-config.md`「DB 意味論」である。ここへ転記しない
- 点検表を通したことを、実測の代わりにしない。列挙されていない差は、点検表からは出てこない。
  実際の検証は、`golden-dataset`（フェーズ B の一致の検証）と `parity-suite`（並び順の特性化）が担う
- 整備されていない（キーが無い・値が空・パスを解決できない）ときも止まらない。ただし、方言差を推測で埋めない。
  原本の点検項目を、現行の DB と新しい DB のそれぞれの一次ドキュメントで確かめる（記憶や「たぶん同じ」で埋めない）。
  原本を読めない場合（姉妹スキル `replace-strategy` が導入されていないなど。`references.db_semantics` が整備されていないこととは別の理由）は、点検を省略しない。
  `gh skill install shoji9x9/skills replace-strategy` での導入を促して止まる（`SKILL.md`「前提」の、インストールされていないときの扱いと同じ）
- 点検の単位は、このフェーズで書くクエリとデータアクセスである。機能全体の DB の仕様を先に調べ切るのではなく、書く直前に該当する項目だけを当てる（フェーズの順を変えない）
- 結果は、`porting.md` の「DB 方言差の点検結果」へ記録する。該当が無くても「該当なし」と書く。空欄にすると、差が無いのか、誰も見ていないのかを区別できない
- 差を実装で吸収しないと決めたら、それは意図的差異である。自分だけで「許容」と判断せず、`intentional_diffs.pending` へ非破壊で追記し、ユーザーの確認へ回す
  （下の「振る舞いを保つことと品質を改善することを分ける」と同じ扱い）
- 確かめきれなかった項目は、`TODO` で未解決と書き、確信度を「低」で申告する（上の「推測せず、確信度を常に申告する」）

## 書き方は、新側リポジトリの規約に従う

移植するのは現行の振る舞いで、現行の書き方ではない。現行のコードを一次情報源として読むことと、現行のコーディングのスタイルを持ち込むことは別である。

- 規約は、設定の `references.coding_conventions` から読む。
  解決の順（規約のドキュメント、新側リポジトリの基底ドキュメントとリントの設定、既存のコード）と、新側が別のリポジトリのときの扱いの原本は、
  `replace-strategy` の `references/project-config.md`「コーディング規約」である。整備されていなくても止まらないが、推測で自分の流儀を持ち込まない
- 規約が現行の書き方とぶつかったら、規約を採る（命名・エラー処理・型の扱い・ファイルの分け方）。
  ただし、意図的差異レジストリの `keep`（テーブル名・項目名・API のエンドポイント・関数名）が優先する。`keep` は、旧と新の diff のレビューを成り立たせるための規律なので、規約より上に置く
- 規約に合わせた結果として振る舞いが変わるなら、それは意図的差異である。自分の判断で進めず、`intentional_diffs.pending` へ非破壊で追記し、ユーザーの確認へ回す
  （下の「振る舞いを保つことと品質を改善することを分ける」を当てはめた例）
- 規約に従ったことは、`verification_commands` の代わりにならない（機械的な検査は別に通す。手順 7）。
  反対に、規約のうち `verification_commands.full` で失敗にならない項目には、機械的な検査が無い。
  `setup` の仕分けの結果（`.replace/strategy.md` の「未検証領域の扱い」。原本は `replace-strategy` の `references/project-config.md`「コーディング規約」）で検査されないとされた項目は、
  敵対的レビュー（手順 7）で人が見る対象にする。`review.md` の「観点（機械検査が無いもの）」へ転記し、レビュー役へ渡す。
  `.replace/strategy.md` が無い、またはその節が無い（この仕分けを入れる前に `setup` を終えたプロジェクト）ときは、止まらずにその旨を同じ節に書いて進む。
  推測で検査されない項目を作らず、規約のドキュメントを読んで観点を立てる

## 振る舞いを保つことと品質を改善することを分ける

- 同じフェーズで両方を狙わない。忠実な移植は、良い性質も悪い性質も同じように運ぶ前提で進め、レガシーの奇妙な挙動も再現する
- リントによる修正は認める（アクセシビリティの改善、不要な副作用の削除など）。リントを off にしない。
  ロケータマッピングの層が現側の非セマンティックな部分を隔離しているので、新側を改善してもスイートは失敗しない
- 改善で role や構造が変わった場合は、意図的差異レジストリ（`intentional_diffs`）へ追記する。`parity-diff` は、それをノイズのフィルタとして使う。
  特性照合の差分（計算後のスタイル・相対的な幾何）に当てるなら、要素を `item` と `match` で書く。
  理由を添えた散文だけでは、差分に当たらない（原本は `replace-strategy` の `references/project-config.md`「照合キー（`match`）」）
- タブ順の厳密な一致を目標にしない（ARIA APG に準拠した実装で新側のほうが正しくても、タブで止まる数が減ることがある）
