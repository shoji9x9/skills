# 見た目の系統差を源流で縮める（トークン寄せ・component_diffs 宣言・gap 記録）

新側 UI ライブラリを reference で選び、旧 design token を寄せ、テーマで消せない構造差を宣言または gap 記録する手順を定める。これは比較の正規化であって仕様変更ではない。

## 源流で縮める理由

コンポーネントライブラリが変わる以上、見た目はライブラリ由来で正当に違う。これを差分器側だけで説明しようとすると宣言が膨らむため、**実装側でも源流の差を縮める**。**論理名・振る舞い・構造は不変で、見た目の系統差だけを扱う。**

## 新側 UI ライブラリは reference で選ぶ（固定しない）

- 新側ライブラリと旧→新トークンマッピングは設定 `references.ui_library` が指すファイルから読む。**特定のライブラリ名・DB 名を本スキルやコードに固定で書かない**
- reference は `replace-strategy` の測定と `ui_library` 設定を基に生成・レビュー済みのプロジェクト知識

## 旧 design token を新側テーマへ寄せる

- **選ばれたライブラリがテーマ可能なら、旧アプリの design token（色・余白・角丸・タイポグラフィのスケール）を新側テーマに寄せる。** 旧→新マッピングは `ui_library` reference から与えられる
- **テーマ機能が無い／限定的なライブラリなら**、源流縮小の効きは限定的で、次項のクラス系統差宣言の比重が上がる

## フォントは版とヒンティングまで揃える

フォントは移行で供給経路が変わりやすい（フレームワークのフォント最適化機構の違い、配布パッケージの違い）。**同じフォント名を指定しても、版が違う／ヒンティング命令を持たないビルドだと本文の幅が変わる**（小サイズでの送り幅の丸めが変わるため）。

- 部品として選ぶとき（実行フロー 3）は、**フォント名だけでなく版と配信ビルド**（ヒンティング命令を含むか）まで見て決め、`.replace/dependencies.md` に記録する
- **フォントスタックに総称ファミリー（`system-ui` / `sans-serif`）を残さない。** CJK のフォールバック先は OS で変わるため、採取環境では一致して利用者環境でだけ崩れる（差分器はゼロを返す）
- 切り分け手順（版差かヒンティング差か）の正本は `parity-diff` の `references/font-diff.md`

## 移行元の宣言を「写さない」と決めるなら、その宣言が変える次元を全部測る

移植では移行元の CSS の宣言を「写す / 写さない」で仕分ける。**「写さない」と決めるときは、その宣言が変える次元を全部測ってから決める。**

**`display` / `position` / `box-sizing` のような「箱の作り方」を変える宣言は、複数の次元を同時に変える**（箱の寸法・中身の配置・匿名ボックスの生成）。
**1 つの次元が一致していることは、他の次元が一致している根拠にならない。** この形の差は**3 経路のどれにも出ないことがある**——
特性照合が測れない要素（論理名が現側で画面外の複製へ解決する等）で、差が 0.0156px なら画素にもほとんど出ない。**人が数値を見るまで出ない。**

**宣言ごとに次元を並べてから測る。**

| 宣言 | 変える次元 | 測る値 |
|---|---|---|
| `display: table` 等の箱の作り方 | 箱の寸法・中身の配置・匿名ボックスの生成 | `getBoundingClientRect()` の寸法 ＋ 中身の位置 |
| `vertical-align` | 中身の配置だけ | 中身の位置 |
| `padding` | 箱の寸法と中身の位置の両方 | 両方 |

- **測り方は「両側で同じ要素の矩形を並べて出す」**（`getBoundingClientRect()` と `getComputedStyle().height` を両方）。追加の道具は要らない
- **箱の寸法だけでは「中身の配置」を測ったことにならない。** 容器の寸法が一致したまま中身だけ動く形があるので、
  **中身の矩形を容器とは別に取る**——`Range.selectNodeContents(<容器>)` の矩形を使うと、包む要素が片側に無くても両側を同じ測り方で取れる。
  記録するのは容器の上端・下端それぞれからの距離（上端だけだと、行の高さが中身ちょうどのとき `vertical-align` の効きを区別できない）
- **匿名ボックスの生成は寸法にも位置にも出ないことがある。** 子の構造（包む要素の有無・`display` の解決結果）を別の証拠として並べる
- **1 点で測らない。** 「中身より行が高くなる状態」（別セルの折り返し・高さ指定・背の高いインライン要素）でも測る——
  その状態を作らないと、`vertical-align` のように**効く条件でしか差が出ない宣言**は写しても写さなくても同じ値になる
- **写さない理由を先に決めてから確かめない。** 「その結論と矛盾しない観測」ではなく、**「その結論が誤りなら違う値になる観測」**を選ぶ
  （実測: 当てる相手の `div` が新側に無いので写さないと決め、根拠に**文字の位置**〈セルの上端から 5px〉を測って一致を確認した。
  測っていなかった**箱の高さ**が 31.0156px〈`display: table` は中身で決まる〉/ 31px で、利用者が画面で見つけた。写す判断を最初にしていれば 4 行足すだけだった）
- **結果は `porting.md` の「移行元の宣言を写さないと決めた箇所」へ記録する**（様式は [`../assets/porting-template.md`](../assets/porting-template.md)）。該当なしも「該当なし」と書く——空欄にすると「写さなくてよい」と「誰も測っていない」が区別できない

## テーマで消せない構造差の扱い

テーマで消せない構造差（フォーカスリング形状・内部 DOM・余白の配り方）は残る。二段構えで扱う。

1. **クラス/トークン単位で表せる系統差** → 共有契約の `component_diffs` レジストリ（`intentional_diffs` とは**別のキー**。要素の形の正本: `replace-strategy` の `references/project-config.md`）へ**ユーザー確認の上で宣言**する。`parity-diff` が比較の正規化に使う。
   **`component` は照合キー**なので、対象要素の論理名（複数インスタンスに効かせるなら `filter-popup-*` のような glob）を書く——ここを空にしたり実在しない名前を書いたりすると宣言が 1 件も掛からない（`parity-diff` が stderr に警告を出す。照合方法の正本は同スキルの `references/normalize.md`）。
   確認が取れるまでは `component_diffs` にも `intentional_diffs.pending`（分類ラベルの列で要素の形が違う）にも書かず、対話で確認してから宣言する
2. **クラス/トークン単位でも表せない構造差**（フォーカスリング形状・内部 DOM・余白の配り方等） → `.replace/parity/<slug>/gaps.md` の「宣言できない構造差」節へ追記する（正本の様式は `parity-suite` の `assets/gaps-template.md`）。`parity-diff` の正規化対象外＝未検証として残す

- **`component_diffs` は特性照合経路（computed style の値比較）にしか効かない。** 現・新で computed style が一致し画素だけ違う差（フォントのサブセットビルド差等）は、系統的な原因でもここへ宣言して吸収させられない——
  置き場所は `parity-diff` のインスタンス例外（`property: pixel`）で、**共有契約の設定ファイルではなく slug 成果物** `.replace/parity/<slug>/component-diff-exceptions.json` に住み、宣言者もトリアージで承認を取る `parity-diff`。
  **本スキルはここへ書かない**（テーマで消せないなら上記 2 の `gaps.md` か、`parity-diff` の往復で承認を取る）。スキーマ・置き場所・レジストリごとに効く経路の正本は同スキルの `references/normalize.md`

いずれも比較の正規化であって仕様変更ではない。**論理名・振る舞い・構造は不変**に保つ。
