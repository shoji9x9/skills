# ページ分割とフェーズ構成

機能をページ単位のフェーズに分けて 1 つずつ作り切る手順と、api-resource / batch モードの縮退を定める。

## ページ単位のフェーズ分割（feature モード）

機能 Issue は 1 度に作らず、**ページ単位でフェーズを切る**。

- **1 ページを作り切って比較してから次のページへ進む。** ページをまたいで並行に進めない（調査・実装・比較が浅くなり、差異を見落とす）
- ページの単位は `.replace/features.md` が機能に紐づけたページ一覧を起点にする。推測で足さない
- **`.replace/features.md` の「ページ要素の帰属」表で自分の slug が所有する要素は、そのページのフェーズで配置する。**
  `扱い` が `スコープ外（配置のみ）` の要素も置く——その先の挙動は作らないが**場所を占める**ので、置かないと現行との差分になる。
  所有者が空欄の要素があれば実装側で決めず `replace-strategy` へ差し戻す
- フェーズは「実装 → 新側マッピング充填 → 見た目の系統差の縮小 → 敵対的レビュー → スイート green ＋ 検証コマンド（`verification_commands.full`）」までを 1 ページ分回し切る単位とする

## フェーズ内の順序（読み取り → 書き込み）

フェーズ内では**読み取り経路を先に、書き込み経路を後に**扱う。

- 読み取り経路は DB 復元が不要なため先に回すと安く比較できる
- これはフェーズ内の順序であって、機能の並び順の話ではない（機能の並び順は `replace-strategy` の依存順が決める）
- **ファイル出力の実装は読み取り側、ファイルアップロードの実装は書き込み側**に置く。アップロードはアプリのストレージ／ファイルシステムに残るため、
  規律（復元 → 一意プレフィックス＋後始末 → 後始末できないなら明示）は `parity-suite` の `references/data-discipline.md` に従う

## ファイル入出力を持つページ

- **バイト列の取得経路を現側と揃える**（ダウンロードイベント／`page.request`／batch はファイルシステム直読み）。実現手段の正本は `replace-strategy` の `references/file-io.md`
- **アップロード経路（`targets[].storage.upload_route`）を現側から変えるなら、それは仕様外の変更ではなく意図的差異である。** 保存 path の命名規則も変わるため、
  勝手に決めず `intentional_diffs.pending` へ非破壊追記してユーザーに確認する（`upload_route` が未宣言のまま実装しない）。
  **`presigned` はブラウザがストレージへ直接 PUT するためアプリサーバを通らず、API パリティの対象面が変わる**（アプリ側に残るのは署名発行 API だけ。
  経路別の影響の正本は `replace-strategy` の `references/project-config.md`「ファイルストレージ」）
- **ストレージ実体へのゴールデンデータ投入は v1 スコープ外**なので、事前配置されたファイルに依存する画面（既存添付の一覧・サムネイル等）は
  スイート green の対象にできない。アップロード操作で自分が作った状態を使うか、`gaps.md` に未検証として残す（確認済みにしない）
- xlsx / PDF を生成するなら、現側の**シート × セル値・構造**（xlsx）・**抽出テキストと構造**（PDF）に一致させる。**バイト一致は目標にしない**（揮発項目が入るため到達不能）

## api-resource モード（横断 API リソース）

画面を持たない。**ページ分割・視覚差分・新側ロケータマッピングは行わない。**

- 担うのはバックエンド実装（現行コードとの diff レビュー）と、API パリティスイートを新に対して green にすることだけ
- 成果物パスの `slug` は当該リソースのもの
- 完了判定は API スイート green ＋ 検証コマンド（`verification_commands.full`。視覚 3 点セットは無い）。green 化の前に `golden-dataset --phase b --feature <slug> --target <選択中の new target>` で新側 DB へ投入する

## batch モード（バッチ Issue）

画面系の工程を動かさない。

- バッチ本体の新側実装（現行コードとの diff レビュー）と、その出力（DB 状態・生成ファイル・対象範囲内の副作用出力）が現行と一致することを担う
- 出力一致の検証手段は `parity-suite` がバッチモードで採取した現行ベースライン（`.replace/parity/<slug>/` 配下）に対して行う
- 完了判定は出力一致 ＋ 検証コマンド（`verification_commands.full`）。新側でバッチを走らせる前に `golden-dataset --phase b --feature <slug> --target <選択中の new target>` で新側 DB へ投入する
