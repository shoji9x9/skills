# 敵対的レビュー（ローカルの未コミット差分・実装役とレビュー役の分離）

commit の前にローカルの差分を敵対的にレビューする手順と、`review.md` への記録を定める。

## 原則

- ローカルの未コミット差分に対して行う。PR を作ってからではなく、`issue-start` の commit へ渡す前に行う
- 実装役とレビュー役を分ける。レビュー役には判断の基準（差分・現行コード・規約・DB 意味論の点検表・`keep` / `may_change`・現行の弱点の仕分け）を渡し、実装役の主観（実装意図・確信度・設計判断の経緯）は知らせない（下の手順 3）
- レビュー役の仕事は、動かない理由を見つけることで、理解を示すことではない
- 「型検査が通った」「テストが通った」を理由に、レビューを省略しない
- レビューの間は、レビューの対象を固定する。起動した後に対象が変わると、指摘がどの版に向いたものかを判定できず、1 ラウンドのレビューが照合の作業になってしまう

## 手順

1. 検証コマンドを先に通す。レビュー役へ差分の本文を渡す前に検証コマンドを通し、明らかな誤りを安く見つける。通ったことを、レビューを省略する理由にしない。
   どの列を実行するかは、変更の集合を先に見て決める。`git status --porcelain` と `git diff --name-status`（`--staged` も）で、変更したファイルの名前と `D` / `R` を取得する（差分の本文は手順 2 で取得する）。
   実行するのは `verification_commands.diff`（無ければ `full`）である。ただし、変更の集合が次のどれかを含むなら `full` を実行する。差分に限った実行では、変更の集合の外で起きる不具合を検出できないからである。
   - ファイルの削除・改名
   - 定義元の削除・改名
   - 共有された型・スキーマへの必須プロパティの追加（変更の集合の外の利用側が満たさなくなる追加）

   `diff` を実行するときの `{changed_files}` の展開の規則（対象の集合・0 件のときの扱い）は、`replace-strategy` の `references/project-config.md` の、`full` と `diff` の範囲を定める節に従う。完了の判定（`SKILL.md` 手順 8）では、列に関わらず別に `full` を実行する。
   検証コマンドが作業ツリーを書き換えたら、その差分を再取得してからレビューへ渡す。設定に auto-fix 付きの起動形が紛れていると、レビュー役が見る差分と実装役が書いた差分がずれる。
   起動形はチェックの形であるべきなので、書き換えが起きたこと自体を `review.md` に記録し、設定を直すよう促す
2. レビューの対象を取得して固定する。`git diff`（ステージしていない）と `git diff --staged`（ステージ済み）で、ローカルの未コミット差分の本文を取得する。
   未追跡のファイル（`git status --porcelain` の `??`）は `git diff` に出ないので、同じ時点の内容を別に読んでレビューの対象に含める。範囲を `review.md` の「レビュー対象」に記録する。
   取得してからレビューの結果が返るまでは、実装役はレビューの対象のファイルを編集せず、対象を書き換える操作や検証コマンドも実行しない。待つ間に進めてよいのは、レビューの対象と重ならない作業だけである。
   対象を変える必要が出たら、進行中のレビューの結果を採用しない。変更と検証を終えた後に、差分と未追跡のファイルの内容を再取得し、その版を新しいラウンドとしてレビューへ渡す
3. レビュー役へ渡すものを分ける。実装役とは別のサブエージェント（例: Claude Code の Agent ツール）をレビュー役として起動する。判断の基準は渡し、実装役の主観は渡さない。
   レビュー役には、手順 2 で固定した差分の本文と未追跡のファイルの内容を、レビューの対象として明示する。起動した後の作業ツリーを、レビューの対象に含めさせない。

   | | 渡すもの |
   |---|---|
   | 渡す | 未コミット差分のテキスト／現行コード（一次情報源）／現側の反応の網羅表 `reactions.json`（`pre_send` と `side_effect_writes` の照合に使う）／新側リポジトリのコーディング規約（設定の `references.coding_conventions`。未整備なら新側リポジトリの基底ドキュメントとリント設定のパス）／機械検査が無い規約の項目の一覧（`review.md` の「観点（機械検査が無いもの）」。出所は `.replace/strategy.md`「未検証領域の扱い」）／DB 意味論の点検表（設定の `references.db_semantics`。未整備なら `replace-strategy` の `references/project-config.md`「DB 意味論」の点検項目）／意図的差異レジストリの `keep`・`may_change`／現行の弱点の仕分け `.replace/weaknesses.md`（`replace-strategy` の `setup` が作る。無ければ無いことを渡す）|
   | 渡さない | 実装意図・設計判断の経緯・確信度の申告（`porting.md` を丸ごと渡さない）。バイアスを持ち込ませないため |

   規約や点検表を渡すことは、意図を渡すことではない。どちらもレビュー役が独立に照合できる外部の基準で、実装役の主観ではない。
   `porting.md` の「DB 方言差の点検結果」は渡さない。実装役が何を確かめたかは主観の側で、レビュー役は点検表と差分だけで独立に照合する。
   新側が別のリポジトリなら、規約の場所をパスで渡す。レビュー役が読み込んでいる基底ドキュメントは現側のものなので、そのままでは新側の規約が反映されない。
   サブエージェントを起動できない実行環境（起動する手段が無い、実行のたびに承認が要って回せない）では、同じものを人間のレビュアーへ渡す。
   この場合も工程は省略せず、レビュー役が人間だったことと、結果・対応を `review.md` に記録する。レビューを受けられないまま commit へ進まない。能力が足りないことは、工程を免除する理由にならない
4. レビュー役の観点。現行コード（一次情報源）に照らして、動かない理由を探す。探すのは、ロジックの取りこぼし、状態遷移・エラー処理・バリデーションの差、`porting.md` の `TODO`（未解決）に対応するコードが本当に未解決のままか、`keep` の項目（テーブル名・API・関数名）を勝手に変えていないかである。
   次の観点も見る。
   - 依存の追加と自前の実装。差分に新しい依存（`package.json` など）が入っていれば、`.replace/dependencies.md` に判断の材料が記録されているかを見る。
     材料は、ライセンス・メンテナンスの状況・採用の規模・配布元の素性・バンドルサイズ・型定義・実行基盤との両立・代替の候補と採らなかった理由である。
     既存のパッケージで済む処理を自前で書いていないか（書いているなら理由が記録されているか）も見る。基準は `replace-strategy` の `references/dependency-selection.md` で定義する
   - 静的資産。差分に、移行元の画像・書体ファイルの取り込みか、グリフや画像を図形で描いた実装が入っていれば、`.replace/assets.md` の同じ種類の行の方針と一致しているかを見る。
     台帳に無い、または方針が空欄なのに実装していないかも見る。「同等物を作る」なら、宣言が `intentional_diffs.may_change` にあるかを見る
   - リポジトリの規約からの逸脱。命名・エラー処理・型の扱い・テストの書き方・ファイルの配置が、渡された規約から外れていないかを見る。
     規約に合わせた結果として振る舞いが変わっているのに、`intentional_diffs.pending` へ回っていないかも見る。規約と振る舞いの保存が衝突したときは、振る舞いの保存を優先する。
     `keep` は規約より上位なので、規約を理由にテーブル名・API・関数名を変えていたら指摘する
   - DB の方言差。渡された点検表の項目ごとに、差分に当てて確かめる。
     `ORDER BY` に NULL の位置が明示されているか。暗黙の型変換が失敗したときに、絞り込みが全件の取得にならないか。比較や `LIKE` の正規化が両辺に当たっているか。
     連結した文字列が NULL のせいで意図しないパターンにならないか。数値・日付の書式がロケールの設定に依存していないか。
     スイートが green であることを、点検の代わりにしない。絞り込みの誤りは、データの件数が少ないと表に出ない
   - 画面から見えない振る舞い。操作が呼ぶ現行の共通部品の内側（送信・実行の直前まで）にある送る前の判定（上限・必須・形式）と、表への書き込み（監査・利用ログ。例外処理の中を含む）が、新側にもあるかを見る。
     材料は、現側の `reactions.json` の `pre_send` と `side_effect_writes` である。どちらも現行を測った記録で、実装役の主観ではない。
     `side_effect_writes` の `source-only` の行は、新側で同じ表へ同じ値・時機・回数で書く箇所を、差分から名指しできるかまで見る。スイートに現れないので、ここが唯一の確認の機会になる
   - 現行の弱点。仕分けは `replace-strategy` の `references/security.md`「現行の弱点の仕分け」で定義する。
     「現行と一致しているか」だけを見ると、現行と同じ弱点は指摘に上がらない。そのため、台帳を使って次の 3 つを別に確かめる。
     - (a) 対象 slug の処理に当たる `状態: 有効` で `仕分け: 直す` の行が、差分で塞がれているか（正規の使い方の振る舞いは変えずに）
     - (b) 意図的差異として入れた変更（`may_change` に宣言済みの差、この差分で新たに宣言を求める差）が、`状態: 有効` で `仕分け: 引き継ぐ`（旧い値 `写す` を含む）の弱点の露出を広げていないか。
       たとえば ID を URL に載せると、ID を指定すれば他人のレコードを取れる弱点は、URL の ID を書き換えるだけで突ける。改ざんの手間が下がる。
       広げるなら、台帳の「露出を広げた差異」列に差異と影響が書かれているかまで見る（書かれていなければ指摘する）
     - (c) 現行コードに、台帳に無い弱点が見えるか。あれば指摘し、実装役が仕分けを空欄にした行を台帳へ既存を消さずに追記して、人の仕分けへ回す。レビュー役は仕分けを決めない

     新側だけに入った弱点（現行には無いもの）は、現行との不一致なので、上の観点と同じくロジックの取りこぼしとして指摘する
   - IaC の変更。差分に IaC の変更（CDK・Terraform など）が入っていれば、それが実装に付随する差分の範囲に収まっているか（パイプラインの新規構築にはみ出していないか）を見る
5. 指摘、修正、再レビュー。指摘があれば実装役が直し、もう一度レビュー役へ差分を渡す。指摘が尽きるまでラウンドを繰り返す
6. 記録。各ラウンドの指摘と対応、最終の判定を `review.md` に残す

## `review.md` の位置づけ

- 敵対的レビューは、PR のレビュー機能（PR のコメント・レビュースレッド）では行わず、ローカルの未コミット差分に対して行う。その記録が `.replace/parity/<slug>/review.md` である
- 記録のファイル自体は、ほかのテキストの成果物と同じく Git で管理してよい。レビューを PR で行わないことと矛盾しない
- テンプレートの原本は `assets/review-template.md` である
