# LLM のトリアージ（crop 対を 1 件ずつ、3 値で分類する）

正規化（[`normalize.md`](normalize.md)）の後に残った候補だけを、モデルに渡す。モデルが行うのは分類だけである。差分があるかどうかは、決定論的なツールが判定し終えている。

## 入力の作り方

- 候補は 1 件ずつ渡す。まとめて渡すと、モデルが差を探し始め、検出をさせることになる
- 渡すものは次のとおりである。
  - 名前の無い要素（画素の比較だけで拾った候補）には、差分の領域の crop 対（現側の crop と新側の crop）だけを渡す。全画面は渡さない。
    `strict_only_regions[]`（しきい値の内側にだけ差がある領域）も同じ形の候補として、1 件ずつ渡す（crop 対は `pixel-crops.mjs` が出す）。
    芯＋`--pad` の範囲の縁は、`pixel-crops.mjs` がしきい値つきの領域に取り込んでいる。それより外まで続く縁は `strict_only_regions[]` に残り、`overlaps_regions` に隣り合う領域の `id` を持つ。
    この組は同じ場所の 1 つの差として一緒に見せ、1 回の判断で分類する（別々の原因として 2 回承認させない）
  - 名前の付いた要素が関わる候補には、crop 対に加えて、特性の差分のテキスト（プロパティの値・状態・相対位置）を添える
- crop は分類を助けるための見せ方であって、検出させるための工夫ではない。検出は決定論的なツールが済ませている、という前提は変えない。
  crop を使う目的は、モデルに差を探させないことと、全画面を縮小して渡すことで解像度が落ちるのを避けることである

## 質問の形

- 聞くのは「この差分は重要か」だけである
- 分類は 3 値で、要対応・許容・環境ノイズのどれかにする。対象は、`normalize.md` の機械分類で決まらずに残った候補（説明の付いていないもの）である。
  `許容候補（要確認）` は 4 つ目の分類ではない。「許容」がまだ承認されていないことを示す仮の書き方である（下の節「『許容』の確定は 2 段階」）
- ユーザーから「スクリーンショットを見比べて違いを見つけて」と頼まれても、目で見て差を探すことはしない。
  検出は画素の比較（記録した差分ツールと `pixel-crops.mjs` の crop 対）に任せ、モデルは crop 対の分類だけを受け持つ。この分担を説明して、そちらに案内する

## テキストの幅・字形の差は先に切り分ける

テキストの幅と字形の差は、フォントのバージョンと、ヒンティング命令の有無の 2 つの軸で決まる。同じフォント名でも本文の幅は変わるので、「同じフォント名だから」という理由で分類しない。
切り分けの手順と、分類への当てはめ方は [`font-diff.md`](font-diff.md) にある。
手順は 3 段階である。読み込まれた実際のファイルを特定する。次に `head` とテーブルの一覧を確かめる。最後に `text-rendering: geometricPrecision` でヒンティングの差を切り離す。

## 仮説の検証は観測条件を列挙してから組む

説明の付いていない差分の原因を追うには、仮説を立てて実験する工程が要る。
実験を組む前に、差分が観測された条件を検出結果から列挙する。条件は、ページ・状態・ビューポート・要素・フォントサイズ・ウェイトなど、差分ツールの出力が持っている属性である。

- 手近な代表値 1 点で測って、全体に当てはめない。画素の差が特定のウェイトの要素にだけ出ているなら、その要素とそのウェイトで測る。別の条件で測った「差ゼロ」は、仮説を否定する根拠にならない
- 比べる相手は常に現行である。新側の実験の変種どうしを突き合わせて「一致した」を結論にしない。正解である現行の実測値と突き合わせていない比較には、比べるべき正解が入っていない
- 結論を `diff.md` に書くときは、どの条件で測ったかも書く。条件を書けない結論は結論として扱わず、その候補は説明の付いていないまま残す

## 差分検出の外で撮って比べるときは撮影条件を先に並べる

このスキルの差分の検出は、side・locale・viewport を検出の前に照合する。ところが、調べるために使い捨てのスクリプトで撮った 2 枚には、この照合が無い。
別の画面から撮った 2 枚でも、そのまま画素の差が出る。実測では、ヘッダーの `?` の切り出しで 116 画素の差が出た。計算値は、幅・高さ・枠の太さ・枠の色・`box-sizing` がすべて一致していた。

- 撮る前に、「どの画面のどの状態か」を両側でそろえて宣言する。宣言するのは、ページ・状態・ビューポート・DPR・locale・side である。片側だけ別の画面から撮らない
- 撮った 2 枚の要素の矩形（`x`・`y`・幅・高さ）を、先に並べて出す。部品を包む要素の位置が違えば、部品が同じでも画素の差は必ず出る。
  小数部が違うと、1 画素ずれて切り出される。実測では、現側の x が 1200.19、新側の x が 1204.81 で、116 画素の差が出た。
  同じ画面どうしで撮り直すと 0 になり、DPR が 1・1.25・1.5・2 のどれでも 0 だった
- 条件と矩形を並べられない 2 枚は、根拠にしない（`diff.md` に書かない）。上の「仮説の検証は観測条件を列挙してから組む」の「条件を書けない結論は結論として扱わない」と同じ扱いである
- このスキルの検出の結果と食い違ったら、まず自分の測り方を疑う。利用者の指摘は仮説の材料であって、測り方が正しいことを保証しない。
  実測では、`border-radius` の `50%` と `3.35544e+07px` を疑い始めていたが、原因は撮影条件のほうだった

## 「許容」の確定は 2 段階（レポートへの記入と承認）

分類をレポートに書くと、その時点で後の判断の入力になる。承認の前の分類をそのまま「許容」と書くと、承認されていない分類が既に決まったことになってしまう。
そのため、レポートへの記入は止めず、分類の確定だけを承認に掛ける。

1. 承認の前: `diff.md` の分類の欄には `許容候補（要確認）` と書く（根拠と観測条件は書いてよい）。この段階では、説明の付いていない差分として数える（[`convergence.md`](convergence.md) の収束の条件）。レジストリには書かない
2. 承認の後: 分類を「許容」に確定し、承認の日時と一緒に記録先へ追記する（既にある記録は消さない）

- 自律実行（`--autonomous`）でも、承認は省かない。原因ごとに `diff-metadata.json` の `pending_decisions[]` に保留として記録する。
  分類は `許容候補（要確認）` のまま残し、他の候補のトリアージに進む。
  承認は、その実行の終わりにまとめて聞く（手順の原本は `replace-strategy` の `references/autonomy.md`）
- 「許容」の確定には、ユーザーの承認が要る。承認の求め方（確認のツールを使えないときを含む）は [`user-confirmation.md`](user-confirmation.md) に従う。
  このスキルの「承認 UI」は、承認を求める確認を指す（このファイル・`detect.md`・`assets/diff-template.md` で同じ意味である）。確認のツールを使えないときは、本文で聞く確認（`user-confirmation.md` の「本文で聞く」）を指す。
  承認 UI には、crop や特性の差分などの判断の材料を一緒に載せる（直前のテキストが見えていることを前提にしない）。
  承認を求める単位と、UI に載せるものは、下の「承認の単位は原因」にある
- 承認されたら、記録先に追記する（既にある記録は消さない）。
  - クラスやトークンの単位で表せる系統の差は、設定ファイルの `component_diffs` に書く。宣言するのは本来 `parity-replace` で、ここで確定した系統の差は `parity-replace` 側の宣言として整理する。
    `component` は照合のキーなので、対象の要素の論理名を書く（複数のインスタンスに当てるなら glob にする）。
    空にすると、宣言は 1 件にも当たらない（[`normalize.md`](normalize.md)「component_diffs T の照合方法」）
  - T を引けないインスタンス単位の差と、画素の比較でしか出ない差は、`.replace/parity/<slug>/component-diff-exceptions.json` に書く。画素の差は `property: pixel` にし、設定ファイルには書かない
  - 環境で変わる値のような意図的差異は、設定ファイルの `intentional_diffs` に書く。
    特性照合の差分なら、要素を `item`（散文）と `match`（`element`・`property`）を持つオブジェクトで書く。
    理由を添えた散文だけの宣言は次の実行で差分に当たらず、同じ差が `unexplained` としてまた出てくる（[`normalize.md`](normalize.md)「意図的差異の照合キー（`match`）」）
- インスタンス例外は、2 つのファイルで 1 組である。どちらも無ければ、同梱のテンプレート（[`../assets/`](../assets/)）から作り、その後は追記する（既にある記録は消さない）。
  スキーマと置き場所の原本は [`normalize.md`](normalize.md) にある。
  1. `component-diff-exceptions.json`: 原因を `component_diff_exception_causes[]` に 1 回だけ定義し（既にあれば足さない）、インスタンスは `cause` で参照する。
     同じ原因のインスタンスに、同じ文言を複製しない（インスタンスに `reason` のフィールドは無い）。
     件数はまとめない。ワイルドカードで N 箇所を 1 つのエントリにしない
  2. `component-diff-exceptions.md`: 原因ごとに、`cause` の id と同じ名前の節を作り、原因を調べた経緯・観測条件・承認の記録を書く（`causes[].evidence` がこの節を指す）。
     `reason` は 1〜2 行の識別のラベルにとどめ、経緯はこちらに書く（YAML や JSON のコメントにためない）
- 承認を求める前に、同じ種類の前例を探して、承認 UI に載せる。レジストリと他の機能の `diff.md` に、同じ種類の差を「現行に合わせる」とした判断があれば、今回の判断と食い違う。
  要対応（現行に合わせる）と分類するときも、同じように前例を探す。前の機能で同じ種類の差を意図的差異にしていれば、そちらを見直す対象になる。
  `diff.md` の根拠には、前例か `なし（検索語: …／自身: …）` を書く。同じ検索で今回の差そのものの記録が当たることを確かめて、検索が機能していることの確認にする。
  探し方と食い違ったときの扱いの原本は、`replace-strategy` の `references/project-config.md`「同じ種類の前例を突き合わせる」である
- 根拠の宛先を `gaps.md` にしない。`gaps.md` は未検証の領域の台帳なので、承認済み（説明済み）の根拠と混ぜない
- 承認されていなければ、説明の付いていない差分のまま残す（`diff.md` の未説明の差分。収束していないものとして扱う）

### 承認の単位は原因（候補ごとに N 回求めない）

分類は候補ごとに行い、承認は原因ごとに取る。`component_diff_exception_causes[]` の 1 つの原因につき、承認は 1 回である。同じ原因の N 個のインスタンスは、その承認で確定する。
原因の数に比べてインスタンスの数が 1 桁以上多いのはふつうのことである。候補ごとに承認を求めると、人が判断できる粒度から離れ、承認されないまま `converged: false` が続く。

- 承認の前に、原因を確定する。束ねてよいのは、上の「仮説の検証は観測条件を列挙してから組む」で、同じ原因だと確かめた候補だけである。
  crop の見た目が似ているだけで束ねない。確かめていない候補は、別の承認の単位として残す（まとめて承認することを、原因の分からない差分を通す手段にしない）
- 1 回の承認 UI に載せるものは、次のとおりである。
  - 原因の識別のラベル（`reason`）
  - その原因が当てはまるインスタンスの件数 N と内訳（ページ・状態・ビューポート・要素の別）
  - 原因を代表するインスタンスの crop 対と特性の差分
  - 上流で消せない理由（ほかの案を検討した結果）
- 「件数をまとめない」は台帳の規則であって、承認の粒度ではない。承認を原因の単位にしても、台帳のインスタンスは N 件のまま並べ、承認 UI にも N を出す。
  件数が見えることは、検証の弱さを知らせる手がかりなので、失わせない
- 承認されたら、その承認が当てはまるインスタンスをすべて「許容」に確定し、その承認の日時を `approved_at` に書く（同じ承認で確定した分には同じ日時が入る）。
  承認の記録（日時・見せた判断の材料・その承認が当てはまる件数 N）は、`component-diff-exceptions.md` の原因ごとの節に、承認 1 回につき 1 行書く
- 承認の後に同じ原因のインスタンスが増えたら、観測条件で同じ原因だと確かめる。そのうえで、増えた分の件数と内訳を見せて、増えた分の承認を 1 回取る。
  インスタンスごとではないので、承認は 1 回である。増えた分の `approved_at` はその日時にし、承認の記録は同じ節に行を足す。
  同じ原因だと確かめられなければ、新しい原因として立て、承認をもう一度取る
- 承認済みの原因への `cause` の参照を足すだけで済ませない。承認の記録の累計 N と `cause` の参照の数がずれ、ユーザーが一度も見ていないインスタンスが「許容」として扱われてしまう。
  収束の判定はこの一致を確かめる（[`convergence.md`](convergence.md)）

## 操作中のエラーの分類

`runtime-errors.mjs compare` が挙げた `new_signatures[]` も、1 件ずつ 3 値で分類する。crop 対は無いので、署名（種類・ページ・リクエストの path・状態コード・正規化した本文）と、最初に出た本文（`sample`）・出た回数（`seen_runs` / `runs`）を見せる。
聞くのは、ほかの候補と同じく「この差分は重要か」だけである。

- 要対応: 新側の実装の不具合で起きたエラーである。`parity-replace` へ差し戻す。
- 許容: 現行と違うが、仕様として問題が無いエラーである（現行の不具合を直した結果、別のエラーに変わった、など）。
  ほかの候補と同じく、承認を経て確定する。承認の前は `許容候補（要確認）` で、`compare` も説明の付いていない差分として数える。
- 環境ノイズ: 新側の環境の都合で起きたエラーである（新側の環境だけにある外部の配信元への通信の失敗、など）。
  根拠として、どの条件で出てどの条件で出ないかを書く。出た回数が `runs` より少ないことだけでは根拠にしない。
  環境ノイズも、利用者の承認を経て確定する。許容を環境ノイズに書き換えると、承認を経ずに収束できてしまうからである。

分類は、`diff-metadata.json` の `runtime_errors.new_signatures[]` の該当する要素に書く。書く欄は次のとおりである。

| 欄 | 書く値 |
| --- | --- |
| `classification` | `要対応` / `許容` / `環境ノイズ` のどれか |
| `reason` | 分類の根拠。`許容` では必須 |
| `approved_at` | `許容` を利用者が承認した日時。承認の前は書かない |
| `evidence` | `環境ノイズ` の根拠（出る条件と出ない条件）。`環境ノイズ` では必須 |

書いたら `compare --write` を通し直す。`許容` で `approved_at` か `reason` が無いもの、`環境ノイズ` で `evidence` が無いもの、どの分類も無いものは `unexplained` として残り、収束しない。
雛形のプレースホルダ（`<...>`）のままの欄は、書いていないものとして数える。
分類と根拠は `diff.md` の差分の一覧にも書く。承認の単位は、ほかの候補と同じく原因である（同じ原因の署名をまとめて 1 回承認し、件数と内訳を承認 UI に載せる）。

### 承認の記録（`approvals`）

分類の欄は、`compare --write` と実行のたびの書き直しで変わるので、承認を後から書き換えても欄だけでは検出できない。
そこで、許容と環境ノイズを利用者が承認したら、同じ `diff-metadata.json` の `approvals[]` に、署名（テスト × 署名）ごとに 1 件ずつ要素を追記する。
同じ原因の署名をまとめて 1 回承認したときも、要素は署名ごとに足す。`approvals[]` は追記専用の記録で、既にある要素を消したり書き換えたりしない。

| 承認 | 追記する要素 |
|---|---|
| 許容 | `kind: runtime_errors`・署名の `test` と `id`・`classification: 許容`・`approved_by`・`approved_at`・`reason` |
| 環境ノイズ | `kind: runtime_errors`・署名の `test` と `id`・`classification: 環境ノイズ`・`approved_by`・`approved_at`・`evidence` |

- 許容の `approved_at` と `reason`、環境ノイズの `evidence` は、`new_signatures[]` の該当する要素の欄と同じ値にする。`approved_by` には承認した人を書く。
  環境ノイズの署名は `approved_at` の欄を持たないので、環境ノイズの要素の `approved_at` には利用者が承認した日時を書く（署名の欄とは突き合わせない）。
- 収束の判定（インストール済みの `parity-suite` の `scripts/artifact-health-check.mjs --target <target> --stage diff`）は、許容と環境ノイズの署名について、次の要素が `approvals[]` に無ければ承認待ちとして失敗にする。
  同じテスト × 署名・同じ `classification`・同じ `approved_at` と `reason`（許容）か同じ `evidence`（環境ノイズ）を持ち、`approved_by` と `approved_at` を書いた要素である。
  `kind` が `runtime_errors` でない要素と、`approved_by`・`approved_at` が雛形のプレースホルダのままの要素は、承認として数えない。
  `classification` を持たない要素は、許容の承認として読む（`spec-parity` と同じ照合の関数を使い、`spec-parity` が環境ノイズを照合する前に積んだ要素を許容として読むため）。追記するときは `classification` を書く。
- 照合の鍵に新側のバージョンは入れない。承認は原因ごとに 1 回取り、新側のバージョンをまたいで持つ。
  `compare` は前の分類を新側のバージョンを見ずに同じテスト × 署名へ持ち越すので、`parity-replace` と往復しても、承認し直さずに続けられる。
- 許容と環境ノイズの間で分類を書き換えると、`classification` が食い違うので、承認として数えない。承認の欄（`approved_at`・`reason`・`evidence`）を書き換えたときも同じである。
  分類を変えるなら、利用者に承認し直してもらい、新しい要素を追記する（前の要素は消さない）。
- `diff-metadata.json` は実行のたびに雛形から作り直す。作り直す前に、前の `diff-metadata.json` の `approvals[]` を読み、そのまま書き戻してから、この実行の結果を書く。
  書き戻しを忘れると、要素が消えたものとして、追記専用の成果物の確認（`replace-strategy` の `append-only-check.mjs`）が失敗する。
  比較元より後に積んだ要素は、その確認では検出しない。そのときも、`compare` が持ち越した許容と環境ノイズに対応する要素が無いので、収束の判定が承認待ちにする。
- `approvals` をキーごと持たない `diff-metadata.json`（この記録を始める前のもの）は、承認が 0 件として読む。そこにある許容と環境ノイズは承認待ちになるので、利用者に承認し直してもらい、要素を追記する。
- 自律実行（`--autonomous`）では、承認を待つ分類を `pending_decisions[]` に保留として記録し、要素は承認を得てから追記する（上の「『許容』の確定は 2 段階」）。
- このチェックが検出しない範囲は、`replace-strategy` の `references/scope.md` の一覧にある（エージェントが `approvals[]` に要素を足すこと自体は止めない、など）。

## 環境ノイズの分類

- 「環境ノイズ」に分類するときは、ノイズ基準値と比べた結果を根拠として記録する。`metadata.json.noise_baseline` の該当する page・state・viewport の差分の量と同じくらいであることを示す
- 画素の候補では、しきい値つきの数だけで比べない。`pixel-crops.mjs` の `summary` のしきい値なしの数（`strict_pixels`・`strict_only_pixels`）は、基準値の同じ軸（`noise_baseline[].pixel_diff_strict`・`pixel_diff_strict_only`）と突き合わせる。
  strict の基準値が無い組はノイズと断定せず、要確認として残す（原本: [`detect.md`](detect.md)「画素の量は 2 本で報告する」）
- ノイズ基準値が無い組はノイズと断定せず、要確認として残す

## 出力

各候補の分類（要対応・許容・環境ノイズ・未説明）と根拠を、[`convergence.md`](convergence.md) の収束の判定と、`diff.md` の差分の一覧に渡す。
分類は候補ごとに行い、承認は原因ごとに取る（上の「承認の単位は原因」）。修正はここでは行わない。
