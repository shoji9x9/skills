# LLM トリアージ（crop 対・1 件ずつ・分類 3 値）

正規化（[`normalize.md`](normalize.md)）を生き残った候補だけをモデルに渡す。**モデルの仕事は分類だけ**——「差分があるか」は決定論的ツールが済ませている。

## 入力の作り方

- **1 件ずつ**渡す（まとめて渡すとモデルが探し始め、検出させることになる）
- 渡すもの:
  - 名前無し要素（画素経路のみで拾った候補）: **差分領域の crop 対だけ**（現側 crop・新側 crop）。全画面を渡さない
  - 名前付き要素が絡む候補: crop 対に加えて特性の差分テキスト（プロパティ値・状態・相対位置）を添える
- **crop の位置づけ**: crop は分類を助ける提示方法であって、検出させるための工夫ではない。検出は決定論的ツールが済ませている前提を崩さない。目的はモデルに探させないことと、全画面を縮小して渡すことによる解像度劣化を避けること

## 質問形式

- 聞くのは「**この差分は重要か**」だけ
- 分類は 3 値: **要対応 / 許容 / 環境ノイズ**（`normalize.md` の機械分類で未確定のまま残った候補＝未説明のものが対象）。
  `許容候補（要確認）` は 4 つ目の分類ではなく、**「許容」が承認前であることを示す暫定表記**（下記「『許容』の確定は 2 段階」）
- ユーザーから「スクリーンショットを見比べて違いを見つけて」と頼まれた場合も**目視検出を代替提供しない**。検出は画素経路（記録済み差分ツール＋ `pixel-crops.mjs` の crop 対）に任せ、モデルは crop 対の分類だけを担う、という分担を説明して誘導する

## テキストの幅・字形の差は先に切り分ける

テキストの幅・字形の差は、フォントの**版**とヒンティング命令の**有無**の 2 軸で決まる。**同じフォント名でも本文の幅は変わる**ため、「同じフォント名だから」で分類しない。
切り分け手順（読み込まれた実ファイルの特定 → `head` / テーブル一覧の確認 → `text-rendering: geometricPrecision` での分離）と分類への落とし込みは [`font-diff.md`](font-diff.md) を参照する。

## 仮説の検証は観測条件を列挙してから組む

未説明差分の原因を追うには仮説を立てて実験する工程が要る。**実験を組む前に、差分が観測された条件を検出結果から列挙する**（ページ・状態・ビューポート・要素・フォントサイズ・ウェイト等、差分器の出力が持っている属性）。

- **手近な代表値 1 点で測って全体に一般化しない。** 画素差が特定のウェイトの要素にだけ出ているなら、その要素・そのウェイトで測る（別の条件で測った「差ゼロ」は仮説の否定にならない）
- **比較の相手は常に現行。** 新側の実験変種どうしを突き合わせて「一致した」を結論にしない（正解＝現行の実測値と突き合わせていない比較は、土俵から正解が抜けている）
- **結論を `diff.md` に書くときは、どの条件で測ったかを併記する。** 条件を書けない結論は結論として扱わず、その候補は未説明のまま残す

## 「許容」の確定は 2 段階（レポートへの記入 → 承認）

**分類をレポートに書いた時点で後続の判断の入力になる**ため、承認前の分類をそのまま「許容」と書くと未承認の分類が既成事実になる。レポートへの記入自体は禁じず、**分類の確定だけを承認に掛ける**。

1. **承認前**: `diff.md` の分類欄は `許容候補（要確認）` と書く（根拠・観測条件は書いてよい）。この段階では**未説明として数える**（[`convergence.md`](convergence.md) の収束条件）。レジストリへは書かない
2. **承認後**: 分類を「許容」へ確定し、承認日時とともに記録先へ非破壊追記する

- **「許容」の確定にはユーザー承認が要る**（AskUserQuestion）。承認 UI には crop・特性差分など**判断材料を同梱する**（直前のテキストが見えている前提を置かない）。
  **承認を求める単位と UI に載せるものは下記「承認の単位は原因」**
- 承認されたら記録先へ**非破壊追記**する:
  - クラス/トークン単位で表せる系統差 → 設定ファイルの `component_diffs`（宣言者は本来 `parity-replace`。ここで確定した系統差は `parity-replace` 側の宣言として整理する）
  - T が引けないインスタンス単位・**画素経路でしか出ない差** → `.replace/parity/<slug>/component-diff-exceptions.json`（画素は `property: pixel`。**設定ファイルには書かない**）
  - 環境揮発など意図的差異 → 設定ファイルの `intentional_diffs`
- **インスタンス例外は 2 ファイルで 1 組**（どちらも無ければ同梱テンプレート〈[`../assets/`](../assets/)〉から作成し、以降は非破壊追記する。スキーマと配置の正本は [`normalize.md`](normalize.md)）:
  1. `component-diff-exceptions.json`: 原因を `component_diff_exception_causes[]` に **1 回だけ**定義し（既にあれば足さない）、インスタンスは `cause` で参照する。
     **同一原因のインスタンスに同じ文言を複製しない**（インスタンスに `reason` フィールドは無い）。**件数は畳まない**——ワイルドカードで N 箇所を 1 エントリにしない
  2. `component-diff-exceptions.md`: 原因ごとに `cause` の id と同名の節を作り、**原因調査の経緯・観測条件・承認記録**を書く（`causes[].evidence` がこの節を指す）。
     `reason` は 1〜2 行の識別ラベルに留め、経緯はこちらに置く（YAML／JSON コメントへ溜めない）
- **根拠の宛先を `gaps.md` にしない**（未検証領域の台帳であり、承認済み＝説明済みの根拠を混ぜない）
- **未承認なら未説明のまま残す**（`diff.md` の未説明差分。未収束として扱う）

### 承認の単位は原因（候補ごとに N 回求めない）

**分類は候補ごと、承認は原因ごと。** `component_diff_exception_causes[]` の 1 原因につき**承認は 1 回**で、同一原因の N インスタンスはその承認で確定する。
原因数に対してインスタンス数が 1 桁以上多いのは普通なので、候補単位で承認を求めると**判断できる粒度から離れ**、未承認のまま `converged: false` が続く。

- **承認の前に原因を確定させる。** 束ねられるのは、上記「仮説の検証は観測条件を列挙してから組む」で**同一原因だと確かめた**候補だけ。
  crop の見た目が似ているだけで束ねない。確かめていない候補は別の承認単位として残す（まとめ承認を原因未特定の差分の抜け道にしない）
- **1 回の承認 UI に載せるもの**: 原因の識別ラベル（`reason`）／**その原因が覆うインスタンス件数 N と内訳**（ページ・状態・ビューポート・要素の別）／
  **原因を代表するインスタンス**の crop 対・特性差分／源流で消せない理由（代替案の検討結果）
- **「件数を畳まない」は台帳の規則であって承認の粒度ではない。** 承認を原因単位にしても、台帳のインスタンスは N 件のまま並べ、承認 UI にも N を出す
  （件数の可視性＝検証の弱さのシグナルは失わせない）
- 承認されたら、**その承認で覆ったインスタンスすべて**を「許容」へ確定し、**その承認の日時**を `approved_at` に書く（同じ承認で確定した分には同じ日時が入る）。
  承認記録（日時・提示した判断材料・その承認で覆った件数 N）は `component-diff-exceptions.md` の原因ごとの節に、**その承認につき 1 行**書く
- **承認後に同じ原因のインスタンスが増えたら**、観測条件で同一原因だと確かめたうえで、**増えた分の件数と内訳を提示して増分の承認を 1 回取る**
  （インスタンス単位ではないので承認は 1 回。増分の `approved_at` はその日時で、承認記録は同じ節へ行を追記する）。
  確かめられなければ新しい原因として立て、承認を取り直す
- **承認済み原因への `cause` 参照を足すだけで済ませない。** 承認記録の累計 N と `cause` 参照数がずれ、
  ユーザーが一度も見ていないインスタンスが「許容」として吸収される（収束判定はこの一致を確認する。[`convergence.md`](convergence.md)）

## 環境ノイズの分類

- 「環境ノイズ」に分類する根拠は**ノイズ基準値との対比を記録する**（`metadata.json.noise_baseline` の該当 page/state/viewport の差分量と同程度であること）
- ノイズ基準値が無い組はノイズと断定せず、要確認として残す

## 出力

各候補の分類（要対応 / 許容 / 環境ノイズ / 未説明）と根拠を [`convergence.md`](convergence.md) の収束判定・`diff.md` の差分一覧へ渡す。**分類は候補ごと、承認は原因ごと**（上記「承認の単位は原因」）。**修正はここで行わない。**
