# フォントの差の切り分け（版の差とヒンティングの差）

テキストの幅と字形の差は、移行でよく起きる。フレームワークのフォント最適化の仕組みや、配布パッケージが変わるためである。
「同じフォント名だから同じ」で済ませない。同じ名前でも、本文の幅は変わる。

## 差は 2 つの軸で決まる

| 軸 | 見るもの | 変わるもの |
|---|---|---|
| フォントの版 | `head` テーブルの `fontRevision`（フォントの製造者が設定する版。補助として `name` テーブルの version string〈ID 5〉） | グリフの形と送り値そのもの |
| ヒンティング命令の有無 | `prep`（Control Value Program）・`fpgm`・`cvt` テーブルの有無 | 小さいサイズでの送り幅の整数への丸め |

同じ版でも、`prep` の有無で本文の幅が変わる。ヒンティング命令は、サイズや変換行列が変わるたびに実行され、送り幅を変えることがある。
`head.flags` のビット 4「Instructions may alter advance width」が、そのことの宣言である。
そのため 16px 前後の小さいサイズでは、グリフの送り値が 1 単位まで同じでも、描画した結果の幅は違う。送り値を比べただけで「同じフォント」と結論しない。

出典: [head](https://learn.microsoft.com/en-us/typography/opentype/spec/head)・[prep](https://learn.microsoft.com/en-us/typography/opentype/spec/prep)（OpenType spec）

## フォントの切り分けに入る前に確かめること

幅の差が 0.1px 前後だと、書体の版とヒンティングの切り分けに進みたくなる。
その前に、差がフォント以外で説明できないかを、次の 3 点で確かめる。どれも採取物を読むだけで済む。

- 名前を付けた要素の差なら、先に特性の差分の `kind: "text"`（文字の持ち主の書体・大きさ・行の高さ・文字の寸法）を見る。
  文字を描いているのが子孫の要素だと、要素自身の計算値がすべて一致していても、書体や大きさが違うことがある。
  `text[<i>]/font-family` などの差が出ていれば、フォントの版やヒンティングではなく、文字の持ち主の指定の差である。切り分けには進まず、`parity-replace` に差し戻す。
  どの要素が文字を持っているかは、採取物の `text_owners[].path` で読む
- 名前を付けた要素の差なら、採取物の `child_inline_styles` も読む。これは、`parity-suite` の trait-capture.mjs が採る、1 段下の子の inline style である。
  要素自身の計算値がすべて一致していても、子の inline style が見た目を変えていることがある。
  実測では、`<a><span style="font-weight: bold;">Back</span></a>` で 34 のプロパティがすべて一致したまま、画素の差が 62、要素の幅が 71.125px と 71px だった。
  比べるのは、文字列ではなく宣言の集合である。`style` 属性は、宣言の順序・空白・大文字と小文字で簡単に食い違う。そのため、プロパティ名と値の組に正規化してから突き合わせる。
  そのうえで、描画に出る差（`font-weight`・`color`・余白などの差、または子の有無）があるときだけ、フォントの差ではなく装飾を付けた場所の差として扱う。切り分けには進まず、`parity-replace` に差し戻す。
  正規化した後に一致するときや、差が描画に出ない項目（`cursor`・`user-select` など）だけのときは、この分岐に入らず、下の切り分けの手順に進む
- このスキルの検出（`metadata.json.differ` に記録した手段による検出）の外で撮った 2 枚を、根拠にしていないかを確かめる。撮影条件がそろっていない 2 枚は、部品が同じでも画素の差を出す。
  原本は [`triage.md`](triage.md)「差分検出の外で撮って比べるときは撮影条件を先に並べる」である

## 切り分けの手順

1. 現側と新側が実際に読み込んだフォントのファイルを特定する。ベースラインに含めたネットワークのログ（`parity-suite` の 3 点セットの補助）と、必要なら `document.fonts` の解決の結果を使う。
   CSS のフォントスタックの宣言だけで判断しない（実際に解決されたファイルが正しい）
2. 両側のフォントのファイルについて、テーブルの一覧と `head`・`name` を読む。版（`head.fontRevision`）と、ヒンティング命令の有無（`prep` などがあるか）を確定する。
   例えば、fontTools の `ttx -l <font>` を使う（"List table info: instead of dumping to a TTX file, list some minimal info about each table"）。
   woff2 を読み書きするには Brotli の拡張が要るので、対応していなければ展開してから読む。
   出典: [fontTools ttx](https://fonttools.readthedocs.io/en/latest/ttx.html)。ツールを導入してよいかはユーザーに確認する（このスキルは自分ではインストールしない）
3. ヒンティングの差だけを切り離す。現側と新側の両方に `text-rendering: geometricPrecision` を当てて撮り直すと、送り幅の丸めがなくなり、残る差が版の差になる。
   ただし、これはエンジンに依存する（Gecko は `optimizeLegibility` と同じに扱う）。当てる前と後で幅が変わることを確かめてから、切り分けの根拠に使う。変わらなければ、この方法は使えない。
   出典: [text-rendering](https://developer.mozilla.org/en-US/docs/Web/CSS/text-rendering)（MDN）

- これは切り分けのための一時的な計測であり、ベースラインと新側のベースラインの撮影条件を変えるものではない。計測した後は、記録した撮影条件に戻す（条件を変えたまま差分の検出に進まない）

## 分類への当てはめ

切り分けた結果は、[`triage.md`](triage.md) の 3 値の分類の根拠として、`diff.md` に記録する。

| 切り分けた結果 | 扱い |
|---|---|
| 版の差 | 要対応。現行と同じ版を新側に配信する（配信の方法が違えば、版も違うことがある） |
| ヒンティングの差 | 要対応。ヒンティング命令を持つビルドを配信する。配信するものを選べずに差を消せないなら、承認を得て、インスタンス例外（`property: pixel`。置き場所は `.replace/parity/<slug>/component-diff-exceptions.json`）か、`gaps.md` の未検証にする |
| 版もヒンティングも同じ | フォント以外（`font-size`・`letter-spacing`・`line-height`・フォールバックの解決）を疑う。採取した環境と利用者の環境のずれ（総称ファミリーの解決先が OS で変わる）では、差分ツールがゼロを返すので、`metadata.json.capture_conditions.viewer_environment` を確かめる |

- フォントの差を「環境ノイズ」に分類しない。ノイズ基準値は同じ環境で撮り直したときの差であり、配信されたフォントが違うことはノイズではない
- フォントの差は、画素の比較でしか出ないことがある（版・送り値・`font-family` の値がすべて一致し、ラスタライズの濃さだけが違う）。
  この差は、`component_diffs` に宣言しても吸収されない。レジストリごとに、どの方法の差に当たるかの原本は [`normalize.md`](normalize.md)「レジストリの適用対象」である
- 1 つの原因で複数の箇所に例外を書くときは、原因を 1 回定義して `cause` で参照する（`reason` をすべてのインスタンスに複製しない）。
  切り分けの経緯と観測条件は、`component-diff-exceptions.md` の原因の節に書く（原本: [`normalize.md`](normalize.md)「インスタンス例外のスキーマ」）
- 手順 3 の切り分けは実験である。差が観測された条件（要素・サイズ・ウェイト・状態）を列挙してから測る。
  別の条件で測った「差ゼロ」を、仮説を否定する根拠にしない（原本は [`triage.md`](triage.md)「仮説の検証は観測条件を列挙してから組む」）
