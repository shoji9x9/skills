# 学び適用ガイド

## フロー概要

`.kaizen/` の中の `status: pending` のファイルを、根本原因と種別でグループに分け、グループごとに 1 つの対策を作る。成果物は `multiagent-setup` スキルを使って作る。

## 手順

### 1. 学びファイルの一覧とグループ分け

```bash
ls .kaizen/*.md 2>/dev/null
```

`status: pending` のファイルが無ければ、「適用待ちの学びはありません」とユーザーに伝えて終える。

ファイルを Read して内容をつかみ、次の観点でグループに分ける。

- 同じ根本原因を持つファイルをまとめる
- `type` が同じで、対象のファイルや対策が共通するものをまとめる
- 明らかに関係の無いものは別のグループにする

グループの一覧をユーザーに示し、分け方が適切かを確認する。

> このファイルの各確認・承認では、判断材料（グループの一覧、統合した事象・根本原因・提案、成果物のドラフト）を確認の UI そのものに入れる。
> 直前の通常のテキストが、確認ダイアログと同時に見えることを前提にしない（Claude Code の AskUserQuestion では、選択肢の preview フィールドに入れる）。

### 2. グループごとに適用（繰り返し）

各グループについて、次を行う。

1. グループ内のファイルの一覧と、統合した事象・根本原因・提案をユーザーに示す
2. 適用するかを確認する（承認 / 却下 / スキップ）
3. 承認されたら、Step 3 へ進む
4. 却下されたら、グループ内のすべてのファイルを `status: rejected` に更新し、`applied-to` に `"rejected: <理由>"` を記録して次へ進む
5. スキップなら、そのまま次へ進む

### 3. 成果物の作成

`type` フィールドに応じて、`multiagent-setup` スキルで成果物を 1 つ作る。

| type | 適用先 | multiagent-setup コンポーネント |
|------|--------|-------------------------------|
| `rule` | `.agents/rules/<name>.md`（`paths`/`applyTo` で対象を絞れる場合。`**` しか書けないなら rule にする利点が小さいので、基底ドキュメントか hook を検討する） | rule |
| `skill` | `.agents/skills/<name>/` | skill |
| `hook` | `.claude/settings.json` 等 | hooks |
| `doc` | 基底ドキュメント（`AGENTS.md`、無ければ `CLAUDE.md` / `.github/copilot-instructions.md`）。長い知見や専用の知見なら `docs/` 等の専用のドキュメント（置き場所は利用先で異なる） | docs |
| `upstream` | 根本原因を持つ外部ツールや依存の上流。下の「上流への報告」に従う | — |
| `other` | ユーザーと相談して決める | — |
| （type 共通）機構 | リポジトリのツール（lint / pre-commit / スクリプト / CI ジョブ）の改修・新設。`type` が `rule` / `doc` / `other` でも、文章だけで終えると再発する対策はここで扱う（判断は下の「決定性で選ぶ」） | Hook を足すときだけ hooks。lint / スクリプト / CI は、リポジトリのツールを直接直す |

#### 記述先の選び方

`type` は出発点にすぎない。どこに書けば、エージェントが期待どおりに振る舞う確率が最も高くなるかを、次の観点で検討して適用先を決める。

##### 決定性で選ぶ

文章での指示（rule / doc）には、エージェントが従わない確率が残る。確実に有効にしたい再発防止は、リンター・pre-commit・Hook などの機構（hook / script）を優先する（基本原則の「決定論的な仕組みで再発を防ぐ」）。

- 判定の仕方: 書こうとしている対策が「次に〜するときはこうする」という手順の記述で終わるなら、それは知識であって仕組みではない。
- 同じ組み立てを人が毎回くり返している対策（毎回手でラッパーを組む、毎回目で確認する）は、その組み立てがツールのデフォルトの挙動になるまで機構に寄せる。
- 同じ学びが再発している（`.kaizen/` に同じ種類の記録が複数ある）ときは、文章を足す選択肢を疑う。過去の文章が機能しなかった証拠がすでにある。

この判断は `kaizen-status-check.sh` が `type` でチェックする。`type: hook`（機構で解決すると宣言したノート）なのに、`applied-to` がドキュメント（`.md`）だけなら警告を出す。
警告であって、止めはしない。検査にできない形の学びは文書に置くしかないので、意図してドキュメントに寄せる判断も実際にある。

ただし、警告を受けたら次のどちらかを記録してから閉じる。

- ドキュメントに寄せると決めたら、`type` を実際に行ったこと（`doc` / `rule`）に直す。後で機構にするなら、どこで行うかをノートか適用先に書く。
- 機構にする作業を別に切り出すなら、`applied-to` に `"#<Issue番号>"` を書く。追跡できる形で任せたことになるので、警告の対象から外れる（`.md` 以外の要素が 1 つでもあるかで判定する）。

判定の材料を提案の文面から取らないのは、実データで分けられないと測れたからである（語の照合は、「機構を適用したノート」に 38%、「doc だけのノート」に 33% 一致した）。

##### 責務の所在で選ぶ

- 特定のエージェントに固有の特性は、そのエージェントの設定（例: `CLAUDE.md`）に置く。
- すべてのエージェントに共通する一般原則は、プロジェクトの基底ドキュメント（`AGENTS.md` 等）に置く。
- 特定のスキルの運用で閉じる知見は、そのスキルの中に置く。

基底ドキュメントの定義、`**` を対象にする rule にせず基底ドキュメントに書く判断、skill / rule / hook / doc の振り分けの基準は、`multiagent-setup` の `references/component-selection.md` で定義する。このガイドでは定義し直さない。

##### パスで対象を絞れるかで選ぶ

特定のパスの下で作業するときだけ要るルールは、`paths` / `applyTo` を絞った rule にする。そのファイルを編集するときに、確実に読み込まれる（例: スキルを作るときだけ有効にしたいなら `paths: skills/**`）。
すべてのファイル（`**`）を対象にするしかないものは、rule にする利点が小さいので、doc か hook を検討する。

##### 配布スキルに関わる知見はスキルに同梱する

他のプロジェクトに配布・インストールして使うスキルの、使い方や規約に関わる知見を、置かれたリポジトリのドキュメントにだけ書くと、スキルを単体で配布したときにインストール先へ伝わらない。
スキル本体（`SKILL.md` / コンポーネント / `assets` 等）に同梱するのを基本にする。スキルを使うエージェントは必ずこれを読むので、スキル固有の挙動を伝える方法として最も確実である。
インストール先でも確実に有効にしたい再発防止は、ドキュメントに文章を追記させるのではなく、スキルのインストール手順で hook や lint などの機構を入れる（「決定性で選ぶ」参照）。文章の追記は守られない確率が残るので、最後の手段にする。

迷う場合や、`type` と最適な適用先が合わない場合は、ここまでの観点を踏まえた候補をユーザーに示して決める。

グループ内に複数のファイルがある場合は、すべての内容を統合して 1 つの成果物に反映する。

`type: rule` の場合は、各ファイルの「提案」セクションを統合してルールの文面を作る。

#### 既に作り終えた成果物へ当てるか

成果物が、手順に確かめる軸を足すもの（検査の項目・観点・網羅の候補を増やすもの）なら、反映はこれから作る成果物にしか当たらない。
その手順で既に作り終えた成果物（完了した機能・作成済みの記録等）にも当てるかを、適用の中で決める。決めないと、見つけた箇所だけが直り、前に作ったものは古い手順のまま残る。

- Step 4 の確認に「既存の成果物への適用」を 1 項目入れ、当てる対象の一覧か、当てない理由のどちらかを示す（空欄のまま通さない）
- 当てるなら、その見直しを適用の完了条件に入れる。別の作業にするなら Issue の起票までを完了条件にし、`applied-to` に `"#<Issue番号>"` を書く
- プロジェクトが観点の変更を記録する台帳を持つなら、そこに行を足す（例: `replace-strategy` を使うプロジェクトの `.replace/procedure-changes.md`。形式はその台帳の定義に従う）

#### 上流への報告

`type: upstream` は、kaizen の内部の成果物には直接適用しない。次の順で、根本原因を持つ相手に渡す。frog は使えるときだけ使う手段で、kaizen の必須の依存にはしない。

1. `frog` コマンドが入っていれば `frog targets` を実行し、対象が受け入れを opt-in していることを確かめてから `frog log --target <pkg>` を使う。
   対象が 0 件、App が未設定、inbound が無効、コマンドが失敗した、のどれかなら次へ進む。
   仕様は、[wevm/frog の CLI の実装](https://github.com/wevm/frog/blob/main/src/cli/commands/log.ts) と [Target の実装](https://github.com/wevm/frog/blob/main/src/Target.ts) で、実行時にも確かめ直す。
2. frog を使えなければ、`issue-create` スキルに任せる。外部のリポジトリへの起票は外部への発信なので、起票先・ドラフト・既存 Issue の確認結果を判断材料として示し、必ずユーザーの承認を得てから作る。
3. どちらもできなければ、内部の rule / doc / script に回避策を置く。その場合は、上流の Issue の URL か修正版を基準に、いつ外すかを同じ成果物に書く。

`frog targets` が 0 件なのは、次の手段へ進む正常な条件であり、止まる理由にしない。frog の導入や受け入れ設定の変更は、このフローから自動で行わない。
確かめた基準: frog 1.1.0 で、空の一時ディレクトリで `pnpm dlx frog@1.1.0 targets --format json` を実行すると、exit 0 と `{"targets":[]}` が返った。
版を上げたら同じ未設定の状態を作り、0 件と失敗を終了コードで区別できることを測り直す。

### 4. 成果物の確認と後処理（status の更新は必須）

1. 作った成果物をユーザーに確認する（成果物が確かめる軸を足すなら、上の「既に作り終えた成果物へ当てるか」の対象の一覧か、当てない理由も同じ確認に載せる）
2. 問題なければ、グループ内のすべてのファイルの `status` を `pending → applied` に更新し、`applied-to` に成果物のパスか `"#<Issue番号>"` を並べる
3. 直す必要があれば、直してから更新する
4. グループを処理した直後に、lifecycle の整合を検査する。

```bash
bash <スキル>/scripts/kaizen-status-check.sh
```

   `warning:` の行が出たら、`type: hook` と宣言したノートが、機構を作らないまま閉じられようとしている。
   機構を作るか、`type` を実際に行ったことに直してから閉じる（上の「決定性で選ぶ」）。警告は exit 0 なので、commit は止まらない。

### 5. 全グループの処理後の対応

すべてのグループを処理したら、status・`applied-to`・アーカイブの索引を最後に確認する。不整合があれば、stderr に出たファイルを直す。

```bash
bash <スキル>/scripts/kaizen-status-check.sh
```

続いて、適用したグループについて、次のどちらにするかをユーザーに確認する。

- このブランチで作業を続ける。コミットして次の作業へ進む
- Issue を作る。グループ（＝対策）ごとに 1 つの Issue を作り、別のブランチで詳細を詰める

## 適用しないまま古くなった学び（忘却）

適用されないまま閾値の日数が過ぎ、優先度も上がらなかった（＝再発していない）pending は、`status: forgotten` にして SessionStart の注入から外す。
デフォルトでは抽出の完了時（`kaizen-extract-done.sh`）に自動で行うので、apply フローで行う必要はない。本文は残るので KEDB 照合では見つかり、再発したら pending に戻す。
判定の条件・閾値の設定・呼び戻しの手順は、`references/housekeeping.md`「忘却」を参照する。

## クリーンアップ（整理）

`.kaizen/` のファイルが増えすぎたら、適用済み・却下済み・忘却済みの学びを整理する。手順は `references/housekeeping.md` を参照する。
デフォルトは `.kaizen/archive/` へのアーカイブ（ファイルを消さない移動）で、物理削除はユーザーが明示したときだけ行う（対象は対話で確認する）。

## `.kaizen/` の Git 管理

`.kaizen/` ディレクトリはコミットの対象にする（`.gitignore` に入れない）。`.kaizen/archive/`（整理で移した applied / rejected / forgotten の置き場）もコミットの対象にする。

- `status: applied` / `status: rejected` / `status: forgotten` の履歴が残り、改善の経緯を追える
- チームの中で学びを共有し、レビューできる
- `.kaizen/` の中のすべてのファイル（status を問わず、`archive/` の下も含む）を、どのエージェントも参照できる（Claude Code / Codex / Copilot の間で学びを共有する）

例外として、Hook が作る一時的な制御ファイルはコミットの対象から外す。センチネル `.kaizen/.pending-extract*`、抽出完了マーカー `.kaizen/.extract-done*`、transcript の処理位置 `.kaizen/.extract-checkpoint*` で、どれも session 単位である。
これらは `.gitignore` に入れて除外する（設定の手順は `references/setup.md` を参照）。
