# 現行からの採取（要素単位の 4 点）

インスタンス × 状態ごとに 4 点を採る。撮影条件・ノイズ基準値・保存先の規約は `parity-suite` の `references/baseline.md` を原本とし、ここへ転記しない。
このファイルが定めるのは、採取の単位がページではなく要素になることで変わる部分だけである。
**`parity-suite` の `references/baseline.md` を読めない場合は、条件を推測して採取へ進まず、止まる。** 撮影条件が違うと、採取物を比較に使えない。

| 採るもの | 手段 | なぜ要るか |
|---|---|---|
| 要素のスクリーンショット | `parity-suite` 同梱の element-shot.mjs（`locator.screenshot()` は使わない） | 名前の付かない内部要素の見た目の差を、画素の比較で検出する |
| 計算後スタイル | `parity-suite` 同梱の trait-capture.mjs | 決定論的に比較できる値。状態ごとに採る。文字の書体・大きさは、要素自身の `computed` ではなく `text_owners`（文字の持ち主ごとの行）を読む。文字を子孫の要素が持つ部品では、要素自身の font 系の値は文字の見た目を表さないためである。採取が `element is outside the document` で失敗したら、指定した要素は画面に描かれていない（市販部品が、支援技術のためのコピーを別の木に作っている）。セレクタを描かれている要素へ直して採り直す |
| 当たっている CSS 規則 | 同梱の `scripts/css-rules-capture.mjs` | 計算値からは見えない側（`:hover` の宣言・`!important` の競合・どの規則が適用されているか）を採る |
| データ依存部品の実データ | 現行の画面に表示されている行から抽出する | 見本に同じ入力を与えないと、データによる差と実装の差を分けられない |

## `parity-suite` 同梱ツールの用意

次の 3 つのツールは、`parity-suite` に同梱したものを原本とする。

- 計算後スタイルの採取（trait-capture.mjs）
- 要素のスクリーンショットの撮影（element-shot.mjs）
- `build` の照合で使う差分ツール（trait-compare.mjs）

これらは、プロジェクト側の `<parity_suite_dir>/parity/lib/tools/vendor/` へコピーして使う（置き場所の規約の原本は `parity-suite` の `references/locator-mapping.md`）。
ここにコピーを置くのは、ふつうは `parity-suite` の機能単位の採取である。
このスキルは機能より先に実行するので、コピーが無いのがふつうである。採取と照合の前に、次を行う。

1. インストール済みの `parity-suite` を特定する。このスキルと同じインストール先にある `parity-suite/scripts/` に、使うツールが在ることを確かめる。
   見つからなければ、推測で探し回らずに止まり、`gh skill install shoji9x9/skills parity-suite` を促す
   （引数の形 `gh skill install <repository> [<skill[@version]>]` の出典: <https://cli.github.com/manual/gh_skill_install>）
2. コピー先に無ければ、同梱版をそのままコピーする。修正も整形もしない（コピーは修正しない規約）
3. コピー先に既に在れば、同梱版とバイト列で一致することを確かめる。一致しなければ、**上書きせずに止まり、ユーザーに確認する**。
   機能単位のスイートが古い版で採ったベースラインを持っている可能性があり、警告なしに差し替えると、機能側の採取物と版がずれる。
   このスキルに同梱の motion-probe.mjs（動きのプローブ）も、同じ置き場所へ同じ規律でコピーする。
   コピー元は `parity-suite` ではなくこのスキルの `scripts/` なので、手順 1 は当てない（[`motion.md`](motion.md)）
4. `metadata.json` に次を記録する。値はコピーしたファイルから読み、手で入力しない
   - 使ったコピー先のパスを `capture.tools.traits` に
   - trait-capture.mjs の `VERSION` と `FIXED_PROPERTIES`（集合）を `traits_version` と `traits_property_set` に
   - element-shot.mjs の `VERSION` を `element_shot_version` に
   - motion-probe.mjs のコピー先と `VERSION` を `motion_probe` と `motion_probe_version` に（動きの無い部品では、両方を `null` にする）

## 保存先はファイル名まで固定する

インスタンス × 状態ごとに `baseline/<instance>/<state>/` を作り、次の 4 つをこの名前で置く。

- `element.png`（要素のスクリーンショット）
- `element.shot.json`（撮影の記録）
- `traits.json`（計算後スタイル）
- `css-rules.json`（当たっている CSS 規則）

データ依存部品の実データだけは、状態に依らないので `baseline/<instance>/data.json` に置く。
`build` の前提の判定は、このファイル名で実体を確かめる。名前が揺れると、採取済みの基準が「無い」と判定される。

element-shot.mjs に `path` として `element.png` を渡すと、PNG と同じ実行の値で `element.shot.json` が隣に書かれる。
中身は、実際に使った clip・出力した PNG の実寸・最上位の座標での矩形である。
`traits.json` の `rect` は要素が居るフレームでの座標なので、iframe の中の部品では `rect` から PNG の実寸を求められない。
寸法を突き合わせるときは、`element.shot.json` の `png` を読む。

## ページ全体ではなく要素を撮る

**`locator.screenshot()` で撮らずに、`parity-suite` 同梱の element-shot.mjs で撮る。**
呼び出し方は `captureElementShot(page, locator, { path })` である。
`locator.screenshot()` は、要素の矩形を外接する整数の矩形へ広げてから撮る。
処理は Playwright v1.56.1 の `helper.enclosingIntRect` にある（出典: <https://github.com/microsoft/playwright/blob/v1.56.1/packages/playwright-core/src/server/helper.ts>）。
そのため、絶対座標が小数だと、要素自身の寸法とは関係なく、PNG が軸ごとに最大 1px 大きくなる。
現行が小数の座標で、新側（カタログ）が整数の座標という組み合わせはふつうに起きる。
すると、同じ寸法の部品でも PNG の寸法が食い違い、寸法の一致を求める画素の比較がすべて実行できなくなる（`button` の 84/84 セルで実測した）。
element-shot.mjs は、矩形を最も近い整数へ丸めた寸法で `page.screenshot({ clip })` を撮るので、両側が同じ整数の寸法になる。

- カタログ側も同じツールで撮る（[`compare.md`](compare.md)）。片側だけ差し替えると、外接による 1px がそのまま寸法の差として残る
- 撮る前に、対象の要素を一意に取得できることを確かめる。複数に一致したまま撮ると、どのインスタンスを撮ったかを後から決められない
- 要素のスクリーンショットは要素の矩形で切られるので、外側の余白（`margin`）は PNG に入らない。余白は計算後スタイルと相対的な幾何で採る
- 要素の矩形の外に出る見た目も PNG に入らない。典型は外側に出る `box-shadow` で、画素の比較では検出できないので、
  計算後スタイルの固定の集合（trait-capture.mjs の `FIXED_PROPERTIES`）で採る。
  `position` / `top` / `left` も、切り出しが要素についていくぶん矩形の中には出ないので、同じ扱いにする
- `position` や親の `overflow` で要素が切れる場合は、切れた状態のまま撮り、切れていることを `gaps.md` に記録する。
  親ごと撮って範囲を広げると、比較の対象が部品でなくなる
- iframe の中の要素（ダイアログの中の iframe にある部品など）も、element-shot.mjs で撮れる。
  `page.screenshot({ clip })` の clip は最上位のフレームのビューポートの座標なので、ツールがフレームをさかのぼってオフセット（フレーム要素の位置・枠線・padding）を足す。
  locator は `page.frameLocator(...)` から取得したものをそのまま渡す。次の形は、撮らずに失敗する。
  - 足すべきオフセットを読めない（クロスオリジンのフレーム）。
  - フレームか、親の文書の中の祖先に、平行移動以外の変形（拡大縮小・回転・反転）がある。
  - 途中のフレームの見える範囲から要素がはみ出す（フレームに切られて、部品の一部だけが撮られる）。

  前の 2 つは、フレームの URL 自体をページとして開いて撮る（Storybook なら `/iframe.html?id=<story>`）。
  最後の 1 つは、撮れないことを `gaps.md` に残す
- element-shot.mjs は、撮る前に動いているアニメーションを数え、あれば撮らずに失敗する。
  数える範囲は、要素の部分木ではなく、要素が居る文書と、iframe をさかのぼった先の各文書の全体である（開いたシャドウルートの中を含む）。
  祖先・フレーム要素・前に並ぶ兄弟のアニメーションも、レイアウトを通じて要素を動かすためである。
  要素と関係の無い場所のアニメーション（別の位置のスピナーなど）でも失敗するので、ページ側でまとめて止めてから撮る。
  `animations: "disabled"` は、撮影の中で有限のアニメーションを早送りし、無限のアニメーションを初期状態へ戻してから撮り、撮り終えたら元の時刻へ戻す。
  そのため、一時停止した無限のアニメーションでは、前後の矩形が同じなのに PNG だけが別の幾何になる（撮った後に測り直しても検出できない）。
  ページ側で止めてから撮る
- element-shot.mjs は、撮影の後にもう一度矩形を測り、撮影中に動いていたら失敗する。
  clip は撮影の前の矩形から決まる一方で、`animations: "disabled"` は撮影の時点で有効になる（有限のアニメーションは完了まで早送りされる）。
  そのため、早送りで動いた要素を古い矩形で切った PNG が、エラーにならずに残りうる。
  失敗したら、ページ側でアニメーションを止めてから撮る（矩形が 2 回続けて同じ値になるまで待つ規律は「状態への遷移は呼び出し側が行う」）
- element-shot.mjs は、デフォルトでアニメーションとトランジションを止めて撮る（`animations: "disabled"`）。
  Playwright のデフォルトは `"allow"` なので、止めないとトランジションの途中のフレームが PNG になり、実行ごとに揺れる
  （撮影条件は `animations: disabled` として記録されるので、記録と実体が食い違う）
- element-shot.mjs は、丸めた clip がビューポートからはみ出すときと、面積が 0 のときは、撮らずに失敗する。
  Playwright は clip をビューポートへ警告なしに切り詰めるので、失敗させないと、部品の一部だけを撮った PNG が基準として残る。
  ビューポートを広げる（撮影条件の記録も更新する）か、撮れないことを `gaps.md` に残す

## 状態への遷移は呼び出し側が行う

trait-capture.mjs も css-rules-capture.mjs も「いまの状態」を採るだけで、状態の遷移は行わない。
`hover` / `active` / `focus` / `disabled` / `checked` などへ遷移させてから採る。

- 遷移したことを、採る前に、その状態に固有の assertion で確かめる（属性・クラス・表示される要素の変化）。
  遷移できていないまま採ると、`default` の値が `hover` として記録される
- 確かめた後、撮る要素の矩形が 2 回続けて同じ値になるまで待ってから採る。
  1 回目・ノイズ測定の 2 回目・カタログ側（[`compare.md`](compare.md)）のすべてで同じにする。
  出現した直後に採ると、1 画素の揺れで値が 2 通りに分かれる。原本と実装例は `parity-suite` の `references/baseline.md`「撮る対象が動かなくなるまで待つ」
- 遷移の手段が書き込みになりうる場合は、選んだ target の `forbidden_actions` を先に読む。
  `hover` / `focus` はポインタとキーボードの移動で作れるが、`checked` / `selected` / `error` は、クリック・送信といったアプリへの操作が要る。
  このスキルが「読み取りだけ」と言えるのは採取そのものの話で、状態を作る操作までは含まない。
  禁止されている操作で作る状態は、遷移させずに、`gaps.md` に「その target では作れない状態」として残し、`metadata.json` の `instances[].unreachable_states` にも書く
  （規律の原本は `parity-suite` の `references/data-discipline.md`）
- 遷移できない状態の扱いは、[`instances.md`](instances.md)「状態集合はインスタンス間で揃える」に従う

### 自動で消える部品（トースト・通知等）

**表示される時間が限られる部品は、「採る前に状態を確かめる」だけでは、消えた後の値を採ってしまう。**
待っている間に消えると、`display: none` の値や別の要素のスクリーンショットが「その状態」として記録され、採るたびに違う基準になる。

- 採り終えた後にも表示されていることを、もう一度 assertion で確かめる。4 点のどれかを採っている間に消えていたら、その回の採取物を捨てて採り直す。
  消えるまでの時間の内に 4 点を採り終えられないなら、推測で基準を作らず、`gaps.md` に残す
- 表示される先の文書から取得する。操作した要素と別の文書（ダイアログの iframe に対する親の文書など）に表示される部品があるので、
  インスタンスの論理名を、表示される先の文書で一意に取得できることを確かめる
- 出し入れの動きと表示時間は、プローブで測る（[`motion.md`](motion.md)。自動で閉じるまでの時間は、閉じる遷移の遅れとして採る）。
  ページ上のどこに表示されるかは、このスキルの照合の範囲外である。
  部品を載せた画面の振る舞いとして、`parity-suite` の反応の網羅表（`parity-suite` の `references/coverage.md`「操作の反応」）が測る。
  **表示時間を引数の既定値として実装するなら、根拠は現行のソースコードとプローブの実測の両方に求め、静止画の採取物から推測しない。**
  範囲外であることは `gaps.md` に残す

## 当たっている CSS 規則

`scripts/css-rules-capture.mjs` は、コピーせずにスキル配下からそのまま実行する。出力は `baseline/<instance>/<state>/css-rules.json` に置く。

- 計算値の代わりではなく、計算値の裏側を採る。どの宣言が勝つかは計算後スタイルが持っており、このツールは候補と条件（状態・擬似要素・`@media` / `@supports` / `@layer`・`!important`）を出す。
  どちらか片方だけでは、実装するときに「なぜこの値になっているのか」を再現できない
- **`inaccessible` が 0 でないなら、そのスタイルシートの規則は 1 件も見えていない。**
  典型はクロスオリジンで配信される CSS（CDN で配信される市販部品のテーマなど）で、0 件を「そのシートには関係する規則が無い」と読まない。
  `gaps.md` の「特性化できなかった箇所と理由」へ、種別「採取値の射程外」として残す。
  読み込めていない `@import`（ロードされていない・404・解析の失敗）も同じ扱いで、`error: "ImportNotLoaded"` として並ぶ。
  取得できなかっただけなので、その先に関係する規則が無いことの証拠にはならない
- **`unresolved` が 0 でないなら、そのセレクタは当たるかどうかを判定していない。** 同じく `gaps.md` に残す。
  既知の原因が 1 つある。状態付きの親に入れ子になった規則（`.btn:hover { & .icon { … } }`）は、`&` の解決で親の状態が `:is(.btn:hover)` の中へ入る。
  そのため、`state-inside-functional-pseudo` として `unresolved` になる。
  当たるか当たらないかを確かめずに決めないための設計なので、該当する規則は、現行の CSS を直接読んで実装の材料にする
- 出力は大きくなりやすい。宣言が空の規則は実装の材料にならないが、削らずにそのまま残す（削ると、もう一度実行したときに差が出た理由を追えない）
- シャドウ DOM が絡むと、採れる範囲が変わる。
  - 対象がシャドウツリーの中にあるときは、外側の document の規則を当てない（カプセル化で届かないため。飛ばした数は `counts.outer_scope_skipped`）。
    外から届く `::part()` だけは判定せず、`unresolved` に残す
  - 対象がカスタム要素のホストのときは、ホスト自身のシャドウルートの `:host` 系の規則を `unresolved` に残し、残りを `counts.host_scope_skipped` に数える（`shadow_host` が真になる）
  - 対象がシャドウの `<slot>` に割り当てられたライト DOM の要素のときは、その要素に適用される `::slotted()` 規則がスロット側のシャドウルートにある。
    そこも調べて `::slotted()` を `unresolved`（`slotted-not-evaluated`）に残し、残りを `counts.slotted_scope_skipped` に数える（`slotted` が真になる）

  どの場合も、`unresolved` に出た規則は、現行の CSS を直接読んで実装の材料にする。
  引数（`:host(.foo)` の `.foo`、`::slotted(.btn)` の `.btn` など）の解決はこのツールの範囲外で、当たるか当たらないかを確かめずに決めない
- `inline_declarations` は `style` 属性の宣言で、どのスタイルシートにも現れないので、`matched` とは別に並ぶ。
  空の配列は「インラインの指定が無い」ことの実測である。キーごと無い採取物は、ツールの版 1 で採ったものなので採り直す。
  インスタンスに固有の幅を `style` で当てている部品では、ここを採らないと計算後スタイルの結果の値しか残らない。
  すると、その値がインライン由来か規則由来か、`!important` が付いているかを、実装するときに復元できない
- **`states` が空の規則を「どの状態でも当たる」と読まない。** 採取は状態ごとに別のファイルなので、
  `states: []` は「この状態で、追加の状態擬似クラス無しに当たった」という意味しかない。
  `.btn:not(:disabled)` のように状態を否定する規則は、`:not()` ごと base に残る。
  そのため、`default` では `states: []` で載り、`disabled` の採取では一致せずに消える。状態をまたいで突き合わせて、初めて条件付きだと分かる

## データ依存部品

データグリッドのように描画がデータに左右される部品では、見本側のデータはいくらでも作れる。一方で、現行側のデータを部品の都合で書き換えることはできない。
そこで、**現行の画面に実際に表示されている一部分を採り、それを見本の入力にする。**

1. 現行のインスタンスで、1 画面に収まる範囲の行（先頭 N 件など、撮影範囲に全体が入る件数）を決める。N は `metadata.json` の `instances[].data.rows` に記録する
2. その範囲が画面に表示された状態で、スクリーンショットと計算後スタイルを採る（表示されていない行を後から足さない）
3. 同じ範囲の実データを DOM から抽出し、`baseline/<instance>/data.json` に保存する。
   列の論理名と値を対応させる（表示される文字列だけでなく、書式を当てる前の値を DOM から取れるなら、それも保存する）
4. データの出所を確認する。ファイルが在るだけでは足りない。確認の仕方は、`.replace/dataset/metadata.json` の `mode` で分かれる
   （原本は `golden-dataset` の `assets/metadata-template.json`）。
   - `mode` が `db` のとき: `current.target` が、採取の対象の target（`--target` で選んだもの）と一致することを確かめる。
     一致しなければ、そのデータセットは別の環境へ投入されており、いま採っている target には投入されていない
   - `mode` が `static` のとき: 投入先の環境を持たないので、`current.target` は `null` になる。target 名は照合しない
     （`parity-suite` も、`current.target` が `null` なら照合しない）。
     代わりに、`current.fingerprint` が記録されていることと、リポジトリの中の静的なデータがその指紋と一致することを確かめる

   どちらの場合も、確認できたら、`version` を `metadata.json` の `dataset_version` に記録する。
   **一致しない場合と確認できない場合は、抽出したデータを見本に使わない。**
   使うと、別の target の版を記録しながら、投入されていない環境の行をカタログへコピーすることになる。
   これは、出所と利用の許可が分からないデータを新側へ持ち込まない規律に反する（原本は `replace-strategy` の `references/scope.md`「スキルが行う作業の範囲」）。
   投入の対象かどうかの取り決め（`dataset_mode` と `db.seedable`）は、`replace-strategy` の `references/project-config.md` を読む
5. 抽出したデータに、個人情報とシークレットが含まれていないことを確認する。含まれるなら見本に使わず、`golden-dataset` へ戻して、比較に使えるデータを用意してもらう

- データセットの版が上がっても、数値が古いことだけでは古くなったと判定しない。
  記録した版から現在までの `changes[].affects` が、その部品の実効の参照テーブルと交わるときだけ、採取物と抽出したデータの両方が古くなる（交わらなければ、古い版のままで有効）。
  判定の規則・部品の slug の実効の参照テーブルの求め方・求められないときに止まる規律の原本は、`golden-dataset` の `references/versioning.md`
- 抽出したデータを手で整形しない。見やすくするために値を丸めたり並べ替えたりすると、見本と現行で入力が変わり、差の原因が実装なのか入力なのか分からなくなる

## ノイズ基準値

`parity-suite` と同じく、同じ条件で 2 回採る。
画素の差分と特性の照合を 2 回分に対して実行し、その差分量を `metadata.json.noise_baseline` に、インスタンス × 状態ごとに記録する。

- 2 回目の書き出し先は `.replace/components/<slug>/noise-pass2/`。基準値を記録したら削除する（どの工程も読まない。原本は `parity-suite` の `references/baseline.md`）
- 2 回の一致は、採取が決定論的であることの証明ではない。2 回とも、上の「状態への遷移は呼び出し側が行う」の矩形の待ちを通して採る
- 部品単体は画面全体より描画する要素が少ないので、ノイズも小さくなりやすい。**それでも、小さいことを前提に測定を省かない。**
  省くと、照合で出た差が回帰なのか揺れなのかを決める根拠が無くなる

## 採取環境と利用者環境の乖離

**採取環境でだけ成り立つ一致は、差分ツールでは検出できない。**
総称のフォントファミリー（`system-ui` / `sans-serif`）や、OS のデフォルトのフォームコントロールの外観は、現行と新側の両方に同じ解決を与える。
そのため、採取環境では差分が 0 になり、別の環境でだけ見た目が変わる。

- 扱い（環境に依存しない形にする・利用者の環境でも採る・`gaps.md` に残す）の原本は、`parity-suite` の `references/baseline.md`「採取環境と利用者環境の乖離」
- 部品では、この検出できない範囲が広がる。チェックボックス・ラジオ・`select` のように、現行が標準のコントロールをそのまま使っている部品は、
  見た目の大半が OS とブラウザのデフォルトで決まる。
  採取した値が現行アプリの CSS 由来なのか、環境のデフォルト由来なのかを、css-rules-capture.mjs の出力（当たっている規則があるか）で切り分ける。
  **規則が無い値は、環境由来として `metadata.json` の `instances[].ua_defaults` に記録する。**
  ここを混同すると、新側が自前の描画で作り直しているのに、採取環境でだけ一致する
