# 部品の一生の順番で壊れる経路

見本の照合・操作の突き合わせ・パリティスイートは、**毎回同じ順番で**部品を描いて操作する。
部品の一生の順番（付ける → 片付ける → 付け直す、初期化の後に引数が変わる）で割れる不具合には、どの工程も一度も入らない。

市販部品を初期化のコールバック（`initialized` 等）で命令的に結び、effect の片付けで外す部品で、実際に次の 3 件が起きた。
いずれもパリティスイートと `parity-diff` は両側で緑で、利用者が開発サーバーで確かめた画面でだけ壊れていた。

- 開発時の結び直しで、1 つのグリッドに列フィルターが 2 つ付いた（絞り込んでも見出しの印が付かない）
- 開いたまま列定義が差し替わると列が作り直され、フィルターの種別が既定に戻った（フィルターを持たない列にボタンが出る）
- 行データが差し替わると、フィルターが種別ごと捨てられた

直した処理が後で消えても、どの検査も落ちない。そこで `build` で対象を判定し、壊れる経路を見本で強制して確かめる。

## 対象の判定（build の手順 4 の実装の後）

次の 3 つが**すべて**当てはまる部品を対象にする。判定と根拠を `build-metadata.json` の `lifecycle.applies` / `lifecycle.reason` に書く（当てはまらない部品も、どれが外れたかを書く）。

1. **部品が初期化を 1 度しか通らず、後から来る変化を自分で受け直す形である**（初期化のコールバックで命令的に結ぶ・effect の片付けで外す・引数の変化を部品の側で購読して反映する）
2. **その経路を既存の検査が通らない**（見本の照合・操作の突き合わせ・E2E は毎回同じ順で描く）
3. **壊れる処理を名指しできる**（「フィルターを付ける処理」「列の作り直しの後にフィルターの種別を戻す処理」のように）

## 4 つの経路

対象の部品は、次の 4 経路それぞれについて、**壊れる処理を名指しできるものを `lifecycle.paths[]` に、名指しできないものを `lifecycle.not_applicable_paths[]` に理由付きで**書く。

| `path` | 何が起きるか | 典型の壊れ方 |
|---|---|---|
| `strict-rebind` | 開発時の結び直し（React の `StrictMode` 等で effect が 付ける → 片付ける → 付ける） | 二重に付く・片付けの後に古い参照を使う |
| `prop-identity` | 開発サーバーの差し替えで、同じ内容の引数が別のオブジェクトになる | 同じ内容で作り直して状態が既定に戻る |
| `remount` | 外して付け直す | 片付け漏れ・前回の状態の持ち越し |
| `prop-change-after-init` | 初期化の後に引数が変わる（一覧が後から届く・取り直す・列定義や行データの差し替え） | 初期化時の値のまま・差し替えで付けた処理が捨てられる |

## 順番を強制する見本

**経路ごとに、その順番を強制する見本を置く。** 例（React の場合。カタログの実体は `references.component_catalog` に従う）:

- **結び直し**: 自前の `createRoot` を `act` の外で作って `StrictMode` で描き、遅延 0 の `setTimeout` をその場で呼んで初期化のコールバックを effect の 2 回目より先に走らせる
  （Storybook の描画に載せたままでは effect の 2 回目が走らない）
- **引数が変わる経路**: 見本に「列を作り直す」「行データを差し替える」のような、その変化を起こすボタンを置く
- **見本は経路に入った回数を `data-*` 属性で出し、検査は「経路に入った」ことを先に確かめてから症状を見る。**
  入らないまま症状だけを見ると、直した処理が消えても（経路自体に入っていないので）緑になる

検査は Playwright 等で見本を開いて行い、コマンドと結果を `lifecycle.paths[]` に記録する。
**直した処理を 1 つずつ外すと、その経路の検査だけが落ちることを 1 度確かめる**（`fix_removal_verified`）——検査が経路の症状を実際に捉えている証拠はこれしかない。

- **この見本は見た目の照合の見本ではない。** `catalog.stories` の対応表に載せず、見た目の基準も採らない。
  カタログにしか無い見本として `parity.unbaselined_stories` に数えない根拠は、`lifecycle.paths[].story` に載っていることだけ（[`catalog.md`](catalog.md)「現行に無い見た目を見本に作らない」）
- 対象でない部品に、この種の見本を置かない（置くと、照合されない見本がカタログに残る）

## 完了判定

`lifecycle.applies: true` の部品は、次の 4 つを完了の条件にする。

- `lifecycle.paths[]` の全件で検査が通っている（`result: pass`）
- 各検査が**経路に入ったこと（`data-*` 属性の回数が 1 以上）を症状より先に確かめている**
- `fix_removal_verified` が真である
- 順番の見本が `catalog.stories` に無く、`parity.unbaselined_stories` にも数えていない（`lifecycle.paths[].story` に載っているものだけを除く）

名指しできない経路は `not_applicable_paths[]` に理由付きで残っていること（空の経路を黙って落とさない）。

**判定は同梱の [`../scripts/lifecycle-check.mjs`](../scripts/lifecycle-check.mjs) が行う**（コピーせずスキル配下から実行する）。
4 経路が `paths` と `not_applicable_paths` のどちらかにちょうど 1 回ずつ現れること、`paths` の各行の検査が通り・経路に入った回数が 1 以上で・
`fix_removal_verified` が真であること、対象でない部品が `paths` を持たないことを確かめる。結果の終了コードを `lifecycle.check_exit` に書く。

```bash
node <skill>/scripts/lifecycle-check.mjs \
  --build-metadata .replace/components/<slug>/new/<target>/build-metadata.json
```

exit 0 ＝ 条件を満たす（対象でない部品を含む）、1 ＝ 不足が残る、2 ＝ 使い方の誤り・型崩れ（`lifecycle` が無い・`applies` が真偽値でない等）。
部品を改修したら検査を回し直す（[`amend.md`](amend.md)「回帰は目視で確かめない」）。完了報告には、対象にした経路と `not_applicable_paths` の理由を収束と並べて示す。
