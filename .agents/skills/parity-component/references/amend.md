# 共通部品の改修（機能の実装中に課題が出たとき）

機能を実装する段になって、先に作った共通部品に手を入れる必要が出ることがある（引数が足りない、その画面でだけ崩れる、状態が足りない）。
**この規律の正本は本ファイル**で、`parity-replace` はここへ委譲する。

改修が危険なのは、**部品が既に他の場所で使われている**ためである。目の前の画面を直す変更が、別の画面の見た目を静かに変える。
そして変わったことは、**その画面のパリティスイートが作られるまで誰も赤くしない**。

**適用対象は「先に作られた部品」だけ。** `.replace/components.md` の存在は入口の条件にならない——同じファイルが「先に作らない部品」も併記するためで、
対象を**部品一覧**の行に引き当て、その slug の `.replace/components/<slug>/new/<選択中の new target>/build-metadata.json` が在ることまで確かめてから本ファイルの規律に入る。
一覧に無い・「先に作らない部品」表にある・build 成果物が無い部品は、採取物も見本も無いので下記の「全見本を採り直して差分ゼロ」を満たしようがない。その部品は機能の実装として普通に作る。

## まず切り分ける

部品を直す前に、**どちらの問題かを決める**。

| 症状 | 疑う先 | 確かめ方 |
|---|---|---|
| その画面でだけ崩れる | **利用側** | カタログの見本では正しいか。正しければ親からの継承・周囲の余白・幅の制約が原因 |
| どの見本でも同じように違う | **部品** | 現行の採取物と突き合わせる。採取物と違うなら部品の実装の誤り |
| 現行にその状態・バリアントが在るのに部品に無い | **採取の漏れ** | `.replace/components.md` のインスタンスに、その画面のインスタンスが入っているか |
| インスタンスも状態も採っていたが、その軸（プロパティ）を測っていなかった | **採取の穴** | 部品インベントリの全インスタンス × 採っていた全状態で、その軸を現行・新側について測る |

- **採取の漏れだった場合は、部品を直す前に採取へ戻る。** そのインスタンスを部品インベントリへ足してもらい、`capture` を回し直して軸を割り出す。
  漏れた状態を採らずに引数だけ足すと、**その引数の正しい値を誰も知らないまま**実装することになる
- **採取の穴だった場合は、下記「現行に合わせ直す修正」で直す。** 見つけた画面の 1 インスタンスだけ測って直すと、同じ軸が割れている他のインスタンスを取りこぼす
- 利用側の問題を部品側で吸収しない（その画面のためだけの分岐が部品に溜まり、他の利用箇所の挙動が読めなくなる）

## 他の利用箇所を壊さない直し方

この節は**利用側の要求で新しい見た目を足す改修**の規律である。部品が現行と違っていたのを直す改修は次節「現行に合わせ直す修正」に従う。

1. **既存の引数の意味と既定値を変えない。** 足すのは新しい引数で、**既定値は改修前の挙動**にする——既定値を新しい挙動にすると、渡していない既存の利用箇所が全部変わる
2. **スタイルを足すときは、既存の見本に効かない形で足す。** 新しい引数が立っているときだけ効く規則にする。既存の規則の値を書き換えない
3. **削除・改名はしない。** 引数・クラス・トークンの削除や改名は破壊的変更として扱う（下記）

## 現行に合わせ直す修正

部品の値が現行と違っていた（切り分けで**部品**か**採取の穴**だった）ときの直し方。前節の「既定値は改修前の挙動」は当てない——
据え置くと現行と違う既定が残り、渡していない全利用箇所で現行との差が出続ける。

1. **直す前に横断の測定を行う。** 部品インベントリの全インスタンス × 採っていた全状態で、その軸を現行と新側の両方について測る。
   見つけた画面の 1 インスタンスから直すと、同じ差を持つ他のインスタンスが次の画面で再び見つかる
2. **現行でその見た目を出す全経路を数える。** 現行のソースで、その値を与える経路（クラス・スタイル・スクリプト・呼び出し元）を全部読み、
   全経路が同じ値なのか、一部だけなのかを決める。全経路が同じなら既定をその値にし、一部だけなら系統か引数で分ける。
   数える前に既定を決めると、読み進めた後で既定を変え直すことになる（出し入れの動きを既定無しで足し、全経路を読んだ後に既定ありへ変え直した実例がある）
3. **修正は系統単位で、既定を現行の値にする。** 横断の測定で値が変わった全インスタンスが属する系統をまとめて直す
4. **影響範囲を変更宣言に書く。** `.replace/components/<slug>/changes/<change-id>.json`（雛形 `assets/component-change-template.json`、`kind: align-to-current`）に、
   影響するインスタンス・状態・プロパティ・新側で部品を使うページ・変えたファイル・改修前後のコミットと横断の測定の記録を書く
5. **照合の合格条件は「宣言した範囲の外は差分ゼロ・範囲の中は現行の値と一致」。** 全見本を採り直し、範囲の外は改修前の見本と差分ゼロ、
   範囲の中は横断の測定で採った現行の値と一致することを示して `parity.md` に追記する（下記「回帰は目視で確かめない」）

この修正は「破壊的変更はユーザーが決める」の「既定値の変更」「既存の見本の出力が変わる実装の変更」に**当たらない**。
既定と見本の出力が変わるのは現行との差を消す向きだけで、それを上の 5 の照合（範囲の外は差分ゼロ）で示すためである。
範囲の外に差が出た・横断の測定で現行の値が経路ごとに割れて既定を決められないなら、破壊的変更として判断を求める。

変更宣言は `parity-suite` の `scripts/component-impact.mjs` の入力になり、部品を使うページ側の再検証は `parity-diff` の `references/component-change.md` に続く。

## 見本を変更に追従させる

- **足した引数には見本を足す。** 見本の無い引数は照合されず、現行と合っているかを誰も確かめていない状態になる
- 足した見本の照合相手は**現行から採った基準**である。基準が無い（現行に対応するインスタンス・状態が無い）なら、
  それは現行に無い見た目を作ろうとしている——実装せずユーザーに上げる
- **基準の無い見本をカタログに残さない。** 足した状態の見本は、その状態の基準を現行から採ってから照合に入れる。
  母集合に入らない見本は、改修で状態を作れなくなってもどの照合も落ちない（扱いの正本は [`catalog.md`](catalog.md)「現行に無い見た目を見本に作らない」）
- **既存の見本は変えない。** 既存の見本の出力が変わったら、それは破壊的変更が起きた合図である
  （現行に合わせ直す修正で、変更宣言の範囲の中が現行の値へ変わるのは除く）

## 回帰は目視で確かめない

改修後は、**その部品の全見本を採り直して基準と照合し、操作の結果も突き合わせ直す**（`compare.md` と `behavior.md` の手順をそのまま回す）。
見た目が変わらない改修でも、イベントの扱いを変えれば操作の結果は変わる。

- **「他の画面は見た目を変えていないはず」を根拠にしない。** 変わっていないことは、採り直して差分ゼロで示す
- 差分が出た見本は、**その差が意図した改修によるものでも**そのままにしない。意図した変更なら基準側が古いので、
  **現行を採り直してよいか**を確かめる——現行が変わっていないのに基準と差が出たなら、それは回帰である
- 照合の結果は `parity.md` に改修として追記する（**非破壊追記**。前の照合記録を書き換えない）

## 破壊的変更はユーザーが決める

次のいずれかに当たるなら、**自分で決めずに判断を求める**。

- 既存の引数の削除・改名・意味の変更
- 既定値の変更（渡していない利用箇所の挙動が変わる。現行に合わせ直す修正で既定を現行の値にするのは除く——「現行に合わせ直す修正」）
- 既存の見本の出力が変わる実装の変更
- 現行に無い見た目・状態を部品へ足すこと

**利用者が破壊的変更を明示的に依頼した場合も、依頼を承認とみなさない。**
依頼した時点では影響範囲も代替案もまだ見ていないので、3 点を示してから確認する
（示したうえで改めて指示されたらそれに従う。**拒否する節ではない**）。
ここを「依頼＝決定済み」と読むと、この節はいちばん必要な場面——利用者が破壊的だと気付かずに頼んだ場面——で働かない。

判断を求めるときは、**次の 3 つを示す**（「破壊的変更をしてよいか」だけを聞かない）。

1. **影響範囲**——その部品を使っている箇所の一覧と、変更後に見た目が変わる見本の一覧
2. **代替案**——引数を足して既定値を据え置く形で解けるか、解けないならなぜか
3. **やらない場合に残るもの**——回避のために利用側へ入れる分岐と、それが溜まったときに何が読めなくなるか
