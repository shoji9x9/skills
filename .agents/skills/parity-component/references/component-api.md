# 固定と可変の切り分け・引数の設計

共通部品の引数は、どこが可変かを決めてから設計する。**可変かどうかの判断を目視に任せない。**
現行に 6 種あるバリアントを 3 種で作る、ページャを汎用のボタンではなく専用の見た目と仮定する、といった取りこぼしは、
実装が終わってから人が現行と見比べるまで見つからない。

採取物がそろっていれば、固定と可変は機械的に決まる。インスタンスの間で値が分かれた軸が可変で、分かれない軸が固定である。
割り出しは `scripts/axis-diff.mjs` が行い、人とエージェントは、どれを引数にするかだけを判断する。

## 割り出しの実行

```bash
node <skill>/scripts/axis-diff.mjs --baseline .replace/components/<slug>/ --out .replace/components/<slug>/axes.json
```

- コピーせずに、スキル配下のスクリプトをそのまま実行する（`gh skill update` の自動更新が反映されるようにする）
- マニフェストは手で組まない。`--baseline` は、`metadata.json`（インスタンス・状態・宣言済みの `unreachable_states`）と
  `baseline/<instance>/<state>/traits.json` だけを入力に、決定論的にマニフェストを組み立てる。
  手で組む余地を残すと、`axes.json` が採取物に対応している保証が無くなり、古い軸や手で直した軸がそのまま引数の設計へ渡る
  （`build` の前提の検証は、この同じコマンドを実行し直して、記録済みの `axes.json` と突き合わせる）
- 宣言の無い欠落は、読みに行って失敗する（採り忘れを警告なしに除外しない）。宣言済みの到達できない状態は、読みに行かない
- マニフェストを直接渡す形（`node <skill>/scripts/axis-diff.mjs <manifest.json>`）も残っている。
  ただし、採取物から組み立てる方法は `--baseline` を原本とする。マニフェストの形の原本は、スクリプトの冒頭のコメントである（`component` と `instances[].states[].traits`）
- **exit 0 になるまで、採取へ戻る。** 失敗する条件は「インスタンスが 2 件未満」「状態の集合がそろっていない」「一部のインスタンスでしか採れていない軸」「id の欠落・重複」である。
  どれも、測っていない軸を固定として扱わないために止まる。`problems` を残したまま、`fixed` だけを読まない

## 割り出し結果の読み方

| 出力 | 意味 | デフォルトの扱い |
|---|---|---|
| `variable` | インスタンスの間で値が分かれた軸 | 引数の候補。引数にしないなら、理由を書く |
| `fixed` | すべてのインスタンスで同じだった軸 | 実装の定数。引数にしない |
| `problems` | 突き合わせられなかった軸と状態 | 採取へ戻す。空欄のまま先へ進まない |
| `not_compared` | 軸の割り出しから外した組み合わせ（宣言済みの到達できない状態） | 引数の設計の対象にしない。その組み合わせは照合の母集合からも外れるので、見本も作らない（到達できないので、基準が無い）。理由は `gaps.md` に残す |

- `fixed` は「このアプリのこの部品では分かれなかった」という意味で、「部品として変えてはならない」という意味ではない。
  インスタンスを増やせば分かれる可能性があるので、`fixed` を根拠に、将来の引数の追加を拒まない
- `variable` を、機械的にすべて引数にしない。分かれ方には 3 種類あり、扱いが違う

| 分かれ方 | 見分け方 | 扱い |
|---|---|---|
| 意図された差 | 分かれた値が、意味のある区分になっている（主ボタンと副ボタンの色） | 引数にする。値の集合を `component-api.md` に列挙する |
| 文脈で決まる差 | 寸法が中身に追従している（`rect/width` が文言の長さで変わる） | 引数にしない。中身（`children` に当たるもの）から決まることを書く |
| 現行の不整合 | 分かれているが、区別する理由が見つからない（同じ用途で余白が 1px 違う） | 自分でそろえない。差を示してユーザーに確認し、そろえるなら `intentional_diffs.pending` へ非破壊で追記する |

- **判別できない分かれ方を「現行の不整合」として扱わない。** 用途の違いを見つけられていないだけのことがある。
  判別できないものは、`component-api.md` に「未判別」として残し、ユーザーに上げる

### 値が「部品自身の見た目」か「ページ内配置」かを決めるときは勝者を先に確定する

軸を `fixed` と `variable` に振り分けた後、その値を部品の定数にするか、ページ側の配置として部品の外へ出すかを判断する。
この場面では、`css-rules.json` の `inline_declarations` と `matched` の両方を読む。
片方だけで判断すると、次の 2 つの形を取り違える（実測で 3 件あった）。

- インラインの値が、`!important` 付きの規則に負けている形
- 後のテーマの再宣言が、前のテーマの宣言を上書きしている形

詳細と確定の手順は、[`catalog.md`](catalog.md)「勝っている宣言を確定してから転記する」にある。

- 確定は手で追わずに、`node <skill>/scripts/cascade-resolve.mjs --css-rules <path> --state <state> --all` に出させる。
  `undecidable` が残った軸は、現行の CSS を直接読んで決め、根拠（どのスタイルシートのどの宣言が勝ったか）をここに残す
- インスタンスごとに勝つ宣言が違う軸は、`variable` である（インスタンスに固有の値を `style` 属性で当てている部品が典型）。
  勝つ宣言を確定しないまま `fixed` として扱うと、負けている宣言を、すべてのインスタンスに共通の定数として実装することになる

## 状態を表す引数

`hover` / `active` / `focus` は、利用する側が渡すものではなく、CSS が引き受ける。引数にするのは、利用する側が決める状態だけである。

- 引数にする状態は、`disabled`、`checked` / `selected`、`readonly`、`error`（バリデーションの結果の表示）、`loading` である。どれも利用する側が制御する
- 引数にしない状態は、`hover` / `active` / `focus-visible` である。採取した状態ごとの値は、引数ではなく、実装のスタイル規則に入れる
- 採取した状態のうち、実装のどこにも入っていないものが無いことを確かめる。
  `component-api.md` の状態の表に「採取した状態 × 入れた先（引数かスタイル規則か）」を書き、空欄を残さない

## 擬似要素で描いているかどうかは軸である

`::before` / `::after` の有無は、`axis-diff.mjs` が `::before/<present>` という軸で出す。
現行が標準のコントロールを使っているのか、擬似要素で描いているのかは、実装の方式そのものを決める。そのため、値の差より先に見る。

- 現行が標準の `select` / `checkbox` を使っているなら、新側も標準の要素で作るのがデフォルトである。自前の描画に置き換えるのは仕様の変更に近いので、ユーザーの確認が要る
- 逆に、現行が擬似要素で描いているなら、標準の要素で作り直すと採取した値とそろわない。
  現行の方式をそのまま採る（振る舞いを保つことと品質を改善することを、同じフェーズで狙わない）

## 記録

割り出しと判断は、`component-api.md`（テンプレート: `assets/component-api-template.md`）に残す。`axes.json` を貼り直さない。
残すのは「割り出しの結果をどう判断したか」で、ツールの出力そのものは、ファイルとして並べて置く。

- 引数ごとに「対応する軸」「値の集合」「既定値」「既定値の根拠となったインスタンス」を書く
- CSS の値の根拠は、勝った宣言で書く（どのスタイルシート・どのセレクタ・`!important` の有無）。
  `css-rules.json` に競合があった軸は、負けた宣言も 1 行添える。次の改修で、前のテーマの値を採り直す往復を防ぐためである
- 引数にしなかった `variable` の軸は、理由と一緒にすべて残す（後から「なぜこの差を吸収したのか」を追えるようにする）
- ユーザーの確認へ回した差は、`intentional_diffs.pending` への追記と対応づける。
  差異の文言は、照合のキーの `item` に書く。`item` / `slug` / `added_by` / `added_at` の形の原本は、`replace-strategy` の `references/project-config.md`
