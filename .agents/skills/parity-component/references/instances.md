# 採取対象の確定（部品インスタンス）

採取の単位は、部品インスタンス（部品 × ページ）である。
対象の一覧は、`.replace/components.md`（`replace-strategy` の `setup` の手順 10 が作る部品インベントリ）から読む。
**このスキルはこのファイルを書かない。** 足りないものは、`replace-strategy` の側で埋めるようユーザーに促す。
勝手に採番したり補ったりすると、その後の採取が、誰も確認していない対象の一覧の上に載る。

## なぜページ単位の網羅表を使わないか

`parity-suite` の網羅表 `component-coverage.json` も「部品 × ページ」のインスタンスを持つ。
しかし、これは機能（画面）の採取の成果物なので、部品を画面より先に作る時点では 1 つも存在しない。
採取の対象の一覧は部品インベントリを原本とし、網羅表はページができてから別に作られる。

2 つは、数えているものも違う。網羅表が数えるのは操作と状態の有無（`present` / `absent` / `unmeasured`）で、色・寸法・余白は見ていない。
網羅表が緑でも見た目が同じことの保証にはならないので、片方をもう片方の代わりにしない。

## 読む項目

対象の行から、次の項目を読む。**どれか 1 つでも空なら、採取へ進まない。**

| 項目 | 用途 | 空のときの扱い |
|---|---|---|
| slug | 成果物のパス `.replace/components/<slug>/` の識別子 | 止まる（自分で採番しない） |
| インスタンス（ページと、その部品を指す論理名） | 採取の対象そのもの | 止まる。2 件未満でも止まる（後述） |
| URL（パターンのページだけ） | `/orders/:id` のようなページを実際に開くための具体的な URL か、解決の規則 | パターンのページを含む行では止まる。パターンのままでは開けないので、`replace-strategy` の側で埋めてもらう |
| データ依存の有無 | 実データを採るかの分岐（[`capture.md`](capture.md)） | 止まる（推測で決めない） |
| 採否（自前の実装か、採用したパッケージか） | `build` の出発点 | `build` だけ止まる。`capture` は進めてよい |
| Issue 番号 | `build` のブランチの作成 | `build` だけ止まる（`replace-strategy issues` を促す） |

- 論理名とページは、インベントリに書いてあるからといって取得できるとは限らない。採取に入る前に対象の target で実際に開き、
  その論理名で要素を一意に取得できることを確かめる。複数に一致したり 0 件だったりしたら、インベントリの誤りとして `replace-strategy` へ戻す
- 論理名は、ロケータマッピングの取り決めの名前と同じ流儀で付ける。
  role とアクセシブルネームで取得できる名前にし、id や自動生成のクラスを目印にしない（原本は `parity-suite` の `references/locator-mapping.md`）
- ページは、現行の target で実際に到達できる URL にする。到達できないページは採取の対象から外し、外したことを `gaps.md` に残す（警告なしに減らさない）
- `metadata.json` の `instances[].page` は、target の baseURL からの相対パスで書く。
  `parity-suite` の `capture_conditions.pages[].path` と同じ語彙で、パターンのページは具体化した値にする。
  部品の改修で影響する機能を探すとき、この値を機能側のパスと完全一致で照合する。語彙がずれると、どの機能とも一致しなくなる

## インスタンスが 2 件未満の部品は共通部品として先に作らない

固定と可変は、2 つ以上のインスタンスを突き合わせないと区別できない。
1 件しか無い部品を先に作ると、そのインスタンスに固有の値が、部品の固定値として埋め込まれる。
すると、2 つ目の利用箇所が出た時点で、引数を後から足すことになる。
`amend.md` の改修は既存の見本の採り直しを伴うので、先に作った利点が無くなる。

- 1 件しか無い部品は、その機能を実装するときに `parity-replace` が作るのが正しい割り当てである。部品インベントリから外すよう、ユーザーに促す
- 「いまは 1 件だが、今後増える見込み」も同じ扱いにする。見込みは採取物ではない

## インスタンスの id

id は `axis-diff.mjs` の照合のキーになる。インスタンスごとに一意で、後から見てどのページのものか分かる文字列にする（例: `orders-list` / `users-detail`）。

- 一意でない id は、`axis-diff.mjs` が重複として失敗にする。失敗したものを、採取の側で警告なしに結合しない（別のインスタンスの値が 1 件にまとまってしまう）
- id は、`metadata.json` の `instances[].id` と、成果物のパス `baseline/<id>/` に使う。
  採取の後に変えると過去の採取物と突き合わせられなくなるので、採取の前に確定させる

## 状態集合はインスタンス間で揃える

列挙する候補の状態の集合（`default` / `hover` / `disabled` など）は、すべてのインスタンスで共通にする。
片方でしか採っていない状態は、「その状態では差が無い」ではなく「測っていない」である。`axis-diff.mjs` は、そろっていない状態を問題として失敗にする。

例外は、到達できない状態だけである。候補に挙げたうえで、そのインスタンスでは作れないことを宣言する（後述）。
宣言した状態は、`axis-diff.mjs` が除外として扱い、問題にしない。宣言の無い欠落は採り忘れと区別できないので、問題になる。

- 現行のそのインスタンスで到達できない状態（そのページでは常に活性、など）がある場合は、状態を減らすのではなく、その旨を記録する。
  `metadata.json` の `instances[].unreachable_states` に状態名と到達できない理由を書き、同じ内容を `gaps.md` にも残す。
  `axis-diff.mjs` へ渡すマニフェストからもその状態を外し、すべてのインスタンスで採れた状態だけで軸を割り出す
- 到達できない状態が多くて、割り出せる軸がほとんど残らないなら、その部品は先に作る対象に向かないので、ユーザーに上げる

## ロールで見た目が変わる部品

権限で表示や操作が変わるのは、仕様である（原本は `parity-suite` の `references/auth.md`「認可はそれ自体が仕様」）。
部品も同じで、同じページの同じ論理名でも、ロールによって無効になっている・ラベルが違う・表示されない、ということがある。

- インスタンスの単位は部品 × ページで、ロールを含まない。そのため、同じページでロールごとに見た目が違う部品は、そのままでは 1 つのインスタンスにまとまる。
  どちらのロールで採ったかによって基準が変わり、しかも出力からはそれが分からない
- 採ったロールは、`metadata.json` の `instances[].auth_role` に必ず残す。
  **ロールをまたいだ差を見つけたら、確かめずにどちらかを採ることはしない。**
  `gaps.md` に「ロールで分かれる部品」として記録し、`.replace/components.md` へインスタンスを足してもらう（インベントリの原本は `replace-strategy`）
- ロールを 1 つしか採らずに済ませた場合も、採っていないロールがあることを `gaps.md` に残す。採取の範囲の記録であって、差が無いことの証拠ではない
