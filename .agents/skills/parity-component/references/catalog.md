# 部品カタログの取り決めと見本

実装した部品を現行の基準と突き合わせるには、部品を単体で、状態ごとに、決まった URL で描画できる場所が要る。
この場所を「部品カタログ」と呼ぶ。実体はこのスキルが決めない。プロジェクトが選び、設定 `references.component_catalog` が指す文書に書く。

## 取り決め（満たせば実体は問わない）

| 条件 | 要る理由 |
|---|---|
| 1 インスタンス × 1 状態を、1 つの固定の URL で開ける | 採取のスペックが URL を組み立てて順に開ける。手で操作して状態を作る場所だと、再現できない。単位を「部品 × 状態」にしないこと。インスタンスごとに引数の値が違う部品では、1 つの URL で両方を再現できず、片方の照合が、別のインスタンスのデフォルト値をコピーした見本に対して行われる |
| Playwright で到達でき、要素を論理名で探せる | 現行と同じ差分ツールと、同じ探し方を当てるため |
| 静的なデータを見本に入れられる | データ依存の部品に、現行から採った実データを与えるため |
| アニメーションとトランジションを止められる | 撮影条件を現行と揃えるため（`animations: 'disabled'` と同じ） |
| 止めずにも開ける（動きのある部品だけ） | 動きの時系列を採るため。カタログ全体で動きを止める仕掛け（全要素の `transition: none` など）があると、動きのある部品も長さ 0 で記録される（[`motion.md`](motion.md)） |
| 描画が外部のサービスに依存しない | ネットワークの状態で採取物が揺れると、ノイズ基準値が使えない |

- 実体の例は Storybook、Ladle、Histoire、アプリの中のカタログのページ、採取だけのための最小のルートである。デフォルトの実体は置かない。
- `references.component_catalog` が整備されていなければ、`build` に入らずに停止する。
  カタログの実体・見本の書き方・URL の決まり方・データの入れ方を推測で決めると、後で別のカタログへ移したときに、見本と採取のスペックの両方を書き直すことになる。
- URL の baseURL は、設定の `targets[].catalog_url` か `targets[].catalog_url_command` から解決する。
  `catalog_url` は固定の文字列である。`catalog_url_command` は、標準出力に URL を 1 行出すコマンドで、実行のたびにポートが変わる環境に使う。
  この 2 つは同時に書けない。両方あるときも、どちらも無いときも停止する（`url` / `url_command` と同じ形である。同じキーに両方の形を入れると、開くのか実行するのかが決まらない）。
  `catalog_url_command` の解決に失敗したときと、出力が空のときは停止する。解決した値は成果物に書かず、`"runtime"` と記録する。

## 勝っている宣言を確定してから転記する

実装で CSS の値を決めるときは、`css-rules.json` の `inline_declarations` と `matched` の両方を読む。
片方だけを読むと、実際の描画と逆の値を実装に転記してしまう。

- インラインがいつも勝つとは限らない。`!important` 付きの作者スタイルシートの規則は、インラインの `!important` の無い宣言を上書きする。
  実測では、`inline_declarations` の `width: 10px` が、`.SearchBoxButton { width: 25px !important }` に負けていた。
- `matched` を読んでも、最初に見つかった宣言を採ると、同じ間違いをする。
  基礎のスタイルシート → テーマの層 → 個別のテーマの順に読み込み、後のものが同じセレクタ・同じプロパティを再宣言して上書きする構成では、勝つ宣言は後のものにある。
  実測では 3 件あった。`feedback-message` の閉じるボタンの `top` が 0 → 2px → 5px、そのグリフの不透明度が不透明 → alpha≈0.5、`radio-button` の外側の輪の `box-shadow` が inset の影 → `none` である。
  どれも、前の段の値を実装に残していた。

勝つ宣言は手で追わず、同梱の cascade-resolve.mjs で確定する。コピーせず、スキルの中のものをそのまま実行する。

```bash
node <skill>/scripts/cascade-resolve.mjs \
  --css-rules .replace/components/<slug>/baseline/<instance>/<state>/css-rules.json \
  --state <state> --all
```

- `--state` は必須で、`baseline/<instance>/<state>/` の `<state>` をそのまま渡す。
  `css-rules.json` はどの状態で採ったかを持たず、`matched` にはほかの状態でだけ当たる規則も並ぶ。そのため、省くと別の状態の宣言を勝つ宣言にしてしまう。
  `default` は、「状態の擬似クラスを足さずに当たる規則だけ」を意味する。
- `--state` に渡すのは「作った状態」だけでよいが、要素の性質を表す状態と、同時に成り立つ状態は扱いが違う。
  `:hover` や `:focus` のように、ポインタやキーボードで作る一時的な状態は、渡さなければ成り立たないものとして除かれる。
  一方、`:enabled`・`:valid`・`:read-only`・`:link` のように要素の性質を表す状態は、ディレクトリ名からは成り立つかが決まらない。
  そのため「不明」として扱い、勝つ可能性があれば `undecidable` になる。その要素で成り立っていたと分かっているなら、`--state enabled` のように足す（`--state` は繰り返して書ける）。
  同時に成り立ちうる一時的な状態も、成り立たないものとして扱わない。`:active` を作ればポインタは要素の上にあるので、`:hover` も当たっている。
  `--state active` だけを渡した採取では、`:hover` の宣言が「不明」になる。成り立っていたなら、`--state active --state hover` と渡す。
- 状態の擬似クラスが主語以外に付いた規則は、成り立つものとして扱わない。
  `css-rules-capture.mjs` は状態を外して名前だけを `states` に記録するので、`.trigger:hover + .target` は `states: ["hover"]` になる。
  `.target` を hover した採取でこれを成り立つものとすると、隣の要素が hover されていたかを確かめないまま、勝つ宣言にしてしまう。
  主語の外に付いた状態は不明として `undecidable` に回すので、現行の CSS を直接読んで決める。
- `all` の宣言があると、個別のプロパティの勝つ宣言を確定しない。
  ブラウザは `margin`・`background`・`font` を個別のプロパティに展開して採取物に渡すが、`all` は展開しない（Chrome 149 で実測した）。
  そのため、`all` が勝つ可能性がある場面では `undecidable` になる。現行の CSS を直接読んで、その要素に `all` が何を与えているかを確定する。
- 採取が不完全なら止まる。`css-rules.json` の `inaccessible`（見えていないスタイルシート）か `unresolved`（当たるかを判定していないセレクタ）が 0 でなければ、
  そこに `matched` のどの候補より強い宣言が隠れていても分からない。
  デフォルトでは解決せずに停止するので、採り直すか、現行の CSS を直接読んで確定する。
  それでも先へ進むなら `--allow-incomplete` で明示して免除し、免除したことと理由を `component-api.md` に残す。
- 優先の順は、インラインの `!important` → 規則の `!important` → インライン → 規則である。同じ段の中では、詳細度 → 出てくる順（`order` の後のものが勝つ）で決まる。
- `--property` には、CSS のカスタムプロパティ（`--brand-color` など）もそのまま渡せる（`--all` で全件を出してから絞ってもよい）。
- exit 1（`undecidable`）を、警告なしに無視しない。
  次の 3 つは入力から決まらないので、勝つ宣言を作り出さず、理由を付けて残す作りになっている。
  - 詳細度を機械的に決められないセレクタ（トップレベルのカンマ、解決していない `&`）
  - 競合が別のカスケードレイヤにある（レイヤの宣言の順は `css-rules.json` に無い）
  - 条件付き（`@media`・`@supports`・`@container`）の候補が勝つ可能性がある（css-rules-capture.mjs は条件を評価せず、記録するだけである）

  これらは現行の CSS を直接読んで確定し、判断の根拠を `component-api.md` に残す。
- これは合否の判定ではない。勝つ宣言を決めるのは、何を実装に転記するのかを確定するためである。
  現行と新側の差分は、画素の比較と特性の照合が出す（[`compare.md`](compare.md)「3 つの比較方法の役割」）。

## 見本の粒度は採取の粒度に合わせる

見本は「インスタンス × 状態」ごとに置く。採取したのにその組み合わせの見本が無いと、その組み合わせは照合されない。
`build` の完了判定が「比較の母集合のすべての組み合わせに対応する見本がある」ことを求めるのは、このためである。
母集合の定義は、`parity-component` の `SKILL.md`「前提」にある。`instances[]` × `capture.states` から、宣言済みの `unreachable_states` を除いたものである。
そのインスタンスで作れない状態の見本は作らない。

- 見本の識別子は、採取物のパスと機械的に対応づける（`baseline/<instance>/<state>/` ↔ 見本の ID）。
  対応表は、target ごとの `new/<target>/build-metadata.json` の `catalog.stories` に書く。
  `build` は `side: new` の target ごとに実行されるので、slug の直下の採取の `metadata.json` に置くと、2 つ目の target が 1 つ目の対応表を上書きし、先に行った照合を後から追えなくなる。
- 対応表は、見本の側の名前を書き写して作らない。
  カタログから見本の一覧を取得し（多くのカタログは一覧を機械で読める形で持つ）、採取物の一覧と突き合わせて、片側にしか無いものを見つける。
  手で書き写すと、名前を変えた見本が対応表の中だけに残る。
- インスタンスによって引数の値が違うのが正しい姿なので、見本ごとに、`component-api.md` が決めた引数の値を明示して渡す。
  デフォルト値に頼ると、デフォルト値を変えたとたんに見本の意味が変わる。

## データ依存部品の見本

`capture` が保存した `baseline/<instance>/data.json` を、そのまま見本の入力にする。

- 件数を減らさず、並べ替えず、値を丸めない。採取したときに映っていた範囲と同じ入力でないと、差分の原因が実装なのか入力なのかを分けられない。
- カタログが非同期でデータを読む作りなら、採取の前に、データの描画が終わったことを assertion で確かめる（件数の `toHaveCount` など）。
  読み込み中の状態を撮ると、現行との差が実装の差に見える。
- 現行の 1 ページが 100 件で、採取の範囲が先頭の 10 件なら、見本にも 10 件だけを与える。
  100 件を与えて上から 10 件を撮ると、スクロールバーの有無や仮想スクロールの動きが入り込んで、採取の条件が変わる。変えるなら、条件を記録して現行の側も同じにする。

## 現行に無い見た目を見本に作らない

カタログは何でも表示できるので、現行に無いバリアントや状態の見本も作れてしまう。
作ると、その見本は照合されないまま実装に残り、利用する側から呼ばれたときに、誰も現行と比べていない見た目が画面に出る。

- 見本の集合は、採取物の集合と一致させる。採取していない見た目の見本は置かない。
- 現行に在る状態でも、基準を採っていない見本は置かない。たとえば、採取の状態に無い「ポップアップを開いた状態」の見本である。
  照合の母集合に入らない見本は、部品を変えて状態を作れなくなっても（ポップアップが開かないなど）、どの照合と完了判定も失敗しない。利用者がカタログを開くまで、誰も気付かない。
  上の対応表の突き合わせで、カタログの側にしか無い見本が見つかったら、その件数を `build-metadata.json` の `parity.unbaselined_stories` に記録する。1 以上なら完了しない。
  例外は、部品の一生の順番を強制する見本だけである。`build-metadata.json` の `lifecycle.paths[].story` に載っているものは数えない。見た目の照合の見本ではなく、順番の検査の見本だからである（[`lifecycle.md`](lifecycle.md)）。
  載っていない見本を、「順番の検査のため」として除かない。
  現行にその状態が在るなら、採取の抜けなので、状態を足して `capture` へ戻り、基準を採る。現行に無いなら、次の項目の仕様の変更として扱う。
- 現行に無いが新側で要ると判断した見た目（新しい状態の表示など）は、仕様の変更なので、実装せずにユーザーに上げる。
