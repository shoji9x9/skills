# データ意味論の根拠（工程 4）

DB の制約を満たすだけのデータは作れる。作れないのは、**ドメインとして正しい値と、代表的な状態**である。
項目名や型から推測した値をパリティ比較の正解として扱うと、誤った現行環境を基準にして新側を実装することになり、その後のすべての検証がその誤りを認めてしまう。

台帳は `.replace/bootstrap/semantics.md`（テンプレート: [`../assets/semantics-template.md`](../assets/semantics-template.md)）である。この台帳を `golden-dataset` と `parity-suite` に引き継ぐ。

## 確定の根拠として使えるもの・使えないもの

| 確定の根拠として**使える** | 確定の根拠として**使えない** |
|---|---|
| 利用許可と出所を確かめた、非本番・匿名化済みのサンプルデータ | カラム名や型だけからの推測 |
| 公式の seed・fixture・テストデータ | LLM が一般論から生成した値 |
| データ辞書・コード表・業務シナリオ・画面／帳票仕様 | 出所や利用許可が不明な DB dump |
| コードの中の enum・バリデーション・定数・選択肢・状態遷移 | 本番由来かどうかを判定できないサンプルデータ |
| 既存テスト・API 例・SQL の条件式 | コードから複数の解釈ができる値 |
| 先方またはドメインの SME が確かめた回答 | 「よくある業務アプリだからこうだろう」という見込み |

- コードから候補を導出できても、意味が 1 つに決まらなければ確定にしない（禁止事項 2）。
  たとえば `status` の enum に `0..4` があると分かっても、どれが初期状態で、どの遷移が正常系かは、コードから 1 つに決まらないことがある。
  この場合は、推測で埋めずに「確認待ち」として台帳に記録し、質問票に回す
- 現行コードが生成物なら、生成元（モデル・定義ファイル）を根拠にする。
  生成コードでは、生成ツールが機械的に補ったデフォルト値と、業務上そう決めた値が同じ形で並び、区別が付かない。
  生成元を受領していれば、生成元を根拠にする。受領していなければ、生成コードから導いた値は確定にせず「確認待ち」に置き、生成元の受領を追加資産の依頼に立てる
- enum があっても、値を網羅しているとは限らない。現行で実際には使っていない値や、移行の途中の値が含まれる。代表的かどうかの判断には、別の根拠が要る

## 出所と利用許可

中身を見る前に出所を確かめる。出所が不明な DB dump は、使えるデータとしてではなく、本番データが含まれている可能性のある資産として扱う。

- 出所と利用許可のどちらかでも不明なら、投入しない（禁止事項 4）。参照して意味論を読み取ることもしない。
  本番データからドメインの値を学んで暫定データに反映すれば、実質的に本番データを持ち込んだことになるからである
- 確かめた結果で初めて分類が決まる。確かめた結果は、台帳と `assets-inventory.md` の両方に残す

| 出所 | 利用許可 | 扱い |
|---|---|---|
| 非本番と確認済み | あり | 確定の根拠として使える（匿名化済みであること） |
| 非本番と確認済み | 不明 | 使わず、利用許可の確認を依頼する |
| 本番由来・判定できない | — | **使わない**。投入も参照もしない。非本番データの追加受領を依頼する |

## 台帳に記録する項目

各データパターンについて、次の項目を記録する。**1 つでも欠けたら、確定として扱わない。**

| 項目 | 内容 |
|---|---|
| 値または状態 | 実際の値・状態遷移・組み合わせ |
| 根拠 | 根拠になる資産・コードの所在（ファイルと位置）、回答者と回答日 |
| 確認状態 | 「確定済み」と「確認待ち」の 2 値（「たぶん確定」を作らない） |
| 対象機能 | この意味論を必要とする機能。`.replace/features.md` の採番の後は slug、採番の前は機能の呼び名でよい |
| 未確認のまま残す場合の影響 | その機能の何が検証できなくなるか（`parity-suite` を始められるかがここで決まる） |

- 「対象機能」列の slug は、`replace-strategy` の機能インベントリが書き戻す。このスキルを実行する時点では、`.replace/features.md` がまだ無いからである。
  後から `--resume` で実行する場合は、採番済みの slug をそのまま使う
- 確認待ちが残ったまま完了してよい。この工程の目的は、確認待ちを 0 件にすることではなく、どの機能がどこで止まるかを見えるようにして引き渡すことである
- 「確認したが確定できなかった」ものも、確定ではない。
  台帳の別表（3 節）に移した項目は「確認待ち」から消える。それでも、その意味論に依存する機能を始められないことは変わらない。
  そこで、対象機能を必ず埋め、`metadata.json` の `semantics.pending_features` にも残す。
  下流の開始の可否のチェックが「確認待ち」だけを見て、この項目を見落とさないようにするためである
