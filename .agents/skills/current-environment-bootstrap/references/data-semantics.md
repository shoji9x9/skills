# データ意味論の根拠（工程 4）

**DB 制約を満たすだけのデータは作れる。作れないのは「ドメイン上正しい値」と「代表的な状態」である。**
項目名や型から推測した値をパリティ比較の正解として扱うと、**誤った現行環境を基準に新側を実装する**ことになり、以降のすべての検証がその誤りを追認する。

台帳は `.replace/bootstrap/semantics.md`（テンプレート: [`../assets/semantics-template.md`](../assets/semantics-template.md)）。**この台帳が `golden-dataset` / `parity-suite` への引き継ぎ先である。**

## 確定根拠として使えるもの／使えないもの

| 確定根拠として**使える** | 確定根拠として**使えない** |
|---|---|
| 利用許可と来歴が確認された非本番・匿名化済みサンプルデータ | カラム名や型だけからの推測 |
| 公式の seed・fixture・テストデータ | LLM が一般論から生成した値 |
| データ辞書・コード表・業務シナリオ・画面／帳票仕様 | 来歴や利用許可が不明な DB dump |
| コード中の enum・バリデーション・定数・選択肢・状態遷移 | 本番由来か判定できないサンプルデータ |
| 既存テスト・API 例・SQL の条件式 | コードから複数の解釈が可能な値 |
| 先方またはドメイン SME が確認した回答 | 「よくある業務アプリだからこうだろう」 |

- **コードから候補を導出できても、意味が一意でなければ確定にしない。** 例: `status` の enum に `0..4` があると分かっても、どれが初期状態でどの遷移が正常系かはコードから一意に決まらないことがある。
  この場合は**「推測」ではなく「確認待ち」**として台帳に記録し、質問票へ回す（禁止事項 2）
- **現行コードが生成物なら、生成元（モデル・定義ファイル）を根拠にする。** 生成コード上では、**生成器が機械的に補った既定値**と、**業務上そう決められた値**が同じ形で並び、区別が付かない。
  生成元が受領されていれば生成元を根拠にし、受領されていなければ生成コードから導いた値は**確定にせず「確認待ち」に置く**（生成元の受領を追加資産依頼に立てる）
- **enum の存在は値の網羅を意味しない。** 現行で実際に使われていない値・移行途中の値が混ざる。代表性の判断には別の根拠が要る

## 来歴と利用許可

**中身を見る前に来歴を確認する。** 出所不明の DB dump は「使えるかもしれないデータ」ではなく、**本番データが混入している可能性のある資産**として扱う。

- 来歴・利用許可のどちらかでも不明なら**投入しない**（禁止事項 4）。参照して意味論を読み取ることも行わない——本番データからドメイン値を学習して暫定データに写せば、実質的に本番データを持ち込んだことになる
- 確認して初めて分類が決まる。確認結果は台帳と `assets-inventory.md` の両方に残す

| 来歴 | 利用許可 | 扱い |
|---|---|---|
| 非本番と確認済み | あり | 確定根拠として使える（匿名化済みであること） |
| 非本番と確認済み | 不明 | 使わず、利用許可の確認を依頼する |
| 本番由来・判定不能 | — | **使わない**。投入も参照もしない。追加受領（非本番データ）を依頼する |

## 台帳に記録する項目

各データパターンについて、次を記録する。**1 つでも欠けたら確定扱いにしない。**

| 項目 | 内容 |
|---|---|
| 値または状態 | 実際の値・状態遷移・組み合わせ |
| 根拠 | 根拠となる資産・コードの所在（ファイルと位置）・回答者と回答日 |
| 確認状態 | **確定済み** / **確認待ち** の 2 値（「たぶん確定」を作らない） |
| 対象機能 | この意味論を必要とする機能。`.replace/features.md` 採番後は slug（採番前は機能の呼び名でよい） |
| 未確認のまま残す場合の影響 | その機能の何が検証できなくなるか（`parity-suite` の開始可否がここで決まる） |

- **「対象機能」列の slug は `replace-strategy` の機能インベントリが書き戻す**（本スキルの実行時点では `.replace/features.md` がまだ無い）。
  `--resume` で後から実行する場合は、既に採番済みの slug をそのまま使う
- **確認待ちのまま完了してよい。** 確認待ちがゼロになるまで待つのではなく、**どの機能がどこで止まるかを見えるようにして引き渡す**のが本工程の目的である
- **「確認したが確定できなかった」も確定ではない。** 台帳の別表（3 節）へ移した項目は「確認待ち」から消えるが、**その意味論に依存する機能が開始できないことは変わらない**——
  対象機能を必ず埋め、`metadata.json` の `semantics.pending_features` にも残す（下流の開始可否ゲートが「確認待ち」だけを見て素通りするのを防ぐ）
