# DB スキーマと設定の復元（工程 3）

**復元の合否は、挙動に影響する設定まで根拠を持って決まったかで判定する。** テーブルを作れたかだけでは判定しない。
照合順序が 1 つ違うだけで並び順が変わり、その差は後の `parity-diff` で説明できない差分として出てくる。
そこまで進んでから原因を遡っても、現・新のどちらが正しいかを判定する基準がもう無い。

結果は `.replace/bootstrap/schema.md`（テンプレート: [`../assets/schema-template.md`](../assets/schema-template.md)）に記録する。項目ごとに根拠（どの資産か、どのコードの何行目か）を書く。

`dataset_mode: static`（DB を持たない構成）では、この工程を「該当なし」として記録する。
代わりに、現行の静的データの形式（ファイルの配置・フィールドの構成・型）を同じ粒度で復元する。

## 必ず決める項目

次の項目はすべて、「値」と「根拠」の両方が揃って初めて確定とする。片方でも欠ければ「不足」として扱う。

| 分類 | 項目 |
|---|---|
| エンジン | DB エンジンの種別、メジャー／マイナーバージョン |
| 構造 | テーブル、カラム、型、NULL 可否、デフォルト値 |
| 制約 | PK、FK、UNIQUE、CHECK、インデックス、シーケンス（開始値・増分） |
| プログラム | ビュー、トリガー、関数、プロシージャと、それらをまとめる単位（パッケージ・モジュールなど） |
| 文字・照合 | そのエンジンで文字コードと照合／ソート順を持てる**すべての階層**（インスタンス・DB・スキーマ／ユーザー・テーブル・カラム、および**セッション／接続**） |
| 実行時の設定 | タイムゾーン、バージョン互換パラメータ、SQL の解釈を変えるモードの設定、追加でインストールしたオプション・拡張・コンポーネント |
| 初期化 | 初期化・マイグレーションの実行順、適用済みの範囲 |

- 階層ごとに持てる設定は、階層ごとに確かめる。DB のデフォルトの照合順序と、個別のカラムに付いた照合順序は別のもので、前者だけを揃えても並び順は一致しない
- 階層の名前と数は、エンジンによって違う。上の表の階層の名前を持たないエンジンで、「該当なし」と書いて済ませない。
  並び順・比較・大文字小文字や幅の同一視を変える設定が、別の名前で、別の階層に置かれていることがある（インスタンス単位のパラメータ、ユーザー単位のデフォルト、接続時に適用される初期化の処理など）。
  上の表は、確かめる項目の一覧ではなく、効果の一覧である。そのエンジンで同じ効果を持つ設定は何かを、毎回調べ直す
- セッション／接続の設定を確かめ忘れない。接続時にデフォルトを上書きする構成（接続文字列・初期化 SQL・ログオン時に実行される処理）では、
  DB 側のデフォルトを揃えても、実際の並び順は一致しない。アプリがどう接続しているかまで遡って確かめる
- バージョンは「メジャーが同じ」で済ませない。照合順序の定義や関数の挙動は、マイナーバージョンで変わることがある。分かった粒度のまま記録する（推測で丸めない）

## DDL が無い場合

DDL が無くても、決定論的に完全なスキーマを生成できれば先に進める。

- マイグレーションから得る場合は、空の DB にすべてのマイグレーションを実際に適用して、最終のスキーマを得る。
  適用が通り、得られたスキーマで上の表の項目を埋められることを確かめる。
  「マイグレーションがあるから復元できる」と机上で判定しない。途中のマイグレーションが、手作業を前提にしていることがある
- ORM の定義から得る場合は、ORM のスキーマ生成の機能で DDL を出力し、上の表の項目が埋まるかを確かめる。
  ORM の定義とマイグレーションが表現しない領域（照合／ソート順、セッションの初期化、トリガー、プロシージャ、一部の CHECK）は、埋まらないことが多い。
  埋まらなかった項目は、1 つずつ「不足」として立てる。
  ツールが表現できない設定は、受領資産の別の場所（環境構築の手順・接続設定・ログオン処理の定義）に分かれて置かれている。
  そのため、マイグレーションだけを見て「全部入っている」と判定しない
- どちらの方法でも、復元したスキーマを実際に構築できるところまで通す（構築できて初めて「復元可」とする）

## デフォルト値で補わない

判断できない項目を、環境のデフォルト値で補わない（禁止事項 5）。
デフォルト値で補うと、値が決まったように見えるが根拠が無く、後の差分がすべて説明できなくなる。

- 一部しか復元できないときや、照合順序・タイムゾーンなどを判断できないときは、「不足」として止まり、質問票（[`questionnaire.md`](questionnaire.md)）に回す
- 「開発環境ではデフォルト値で動いたから」を根拠にしない。動くことと、現行の本番と同じ挙動になることは別である
- 例外は無い。「この設定は差分に影響しないはず」という判断そのものが推測である。影響しないことを実測で示せない限り、「不足」として扱う

## 記録すること

- 項目ごとの値・根拠・区分（確定か不足か）
- 復元の方法（受領 DDL そのまま／マイグレーションの適用／ORM による生成）と、実際に構築を通した結果
- ORM とマイグレーションで埋まらなかった領域の一覧（不足として質問票に回した項目との対応）
- 復元したスキーマを構築するツールと手順の所在（`<bootstrap_tool_dir>`）

`references.db_semantics` の整備は、このスキルの担当ではない。ここで作った `schema.md` が、`replace-strategy setup` が `db_semantics` の下書きを作るときの入力になる。
