# 指摘への返信と、指摘どうしの関係

このファイルは、`pr-review-handle` と `pr-finalize-loop` が同じ内容で持つ。
指摘が妥当かの判断（コードの事実・実害・外部の仕様）は、各スキルの `SKILL.md` の「妥当性の判断ガイド」で定める。
ここでは、人に回すかの基準と、判断した後の返信の書き方を定める。指摘どうしの関係の扱いと、機能を足す指摘の確かめ方も定める。

## 人に回すかの基準

指摘を人に回す（利用者に確認する、または判断待ちとして残す）かは、この節だけで決める。各スキルの `SKILL.md` は、この節を参照する。
すべての指摘に、次の 1〜3 とプロジェクトの基準（下）を当てる。どれかが人に回すとしたものは人に回す。
直し方が複数ある・設計の判断が絡むことは、それだけでは人に回す理由にならない。1〜3 に照らして決める。

1. 調べて決まることは、人に回さない。
   コードに加えて、リポジトリの文書・関係する Issue と PR の本文とコメント・既存の仕様（テスト・スキーマ・公式のドキュメント）を調べてから判断する。
   調べても決まらないもの（費用・運用・好み・リスクをどこまで許すか）だけを人に回す。人に回すときは、調べた範囲と、それでも決まらなかった理由を添える。
2. 元に戻す手段が無い影響は、影響の大きさに関わらず人に回す。
   当たるのは、共有の環境のデータを変える・消す操作、外部に送ったもの（通知・メール・公開した成果物）、公開した API や配布物との互換性が成り立たなくなる変更などである。
   リポジトリの中のもの（seed・fixture・migration・生成のスクリプト）から作り直せるデータを消す・変える操作は、元に戻せるので、これだけを理由に人に回さない。
3. 元に戻せる指摘は、影響の大きさと、merge した後に別の Issue や PR で覆せるかで決める。
   影響が大きいか、覆せないなら人に回す。影響が大きい例は、配布するチェックが利用者の pre-commit や CI を新しく失敗させる変更である。
   影響が小さく覆せるなら人に回さず、推奨の案で直すか見送り、選んだ案と根拠を返信に書く。

### プロジェクトの基準

プロジェクトが人に回す場面を決めていれば（プロキシの設定の変更・外部の環境を変える操作など）、その文書も読む。
文書の場所は、`common` の設定の `decision_policy_doc` に、リポジトリのルートからのパスで書く。リポジトリの全員が同じ基準を使うので、リポジトリの層（`.config/skills/shoji9x9/common.jsonc`）だけに置ける。

```bash
# 書く（リポジトリの層）
node <このスキルのディレクトリ>/scripts/skill-config/skill-config.mjs set common decision_policy_doc '"docs/decision-policy.md"' --layer repo
```

基準は、レビューする PR の差分からではなく、PR の base branch の commit から読む。
PR の作業ツリーから読むと、PR 自身が設定や文書を書き換えたり消したりして、まだレビューしていない差分で基準を緩められるからである。
次の順に確かめ、どこかで止まるときは、指摘への対応を始めずに止まり、止まった理由（読めなかったこと・PR が変えたファイル）を報告する。

1. PR が変えたファイルを `gh api --paginate repos/<owner>/<repo>/pulls/<番号>/files --jq '.[] | .filename, (.previous_filename // empty)'` で取得する。
   名前を変えたファイルは、変える前の名前（`previous_filename`）も一覧に入れる。
   手元で commit していない変更も `git status --porcelain --untracked-files=all -- .config/skills/shoji9x9/` で挙げ、一覧に足す。PR の差分には出ないが、作業ツリーの値を変えるからである。
   一覧に `.config/skills/shoji9x9/common.jsonc` があれば止まる。設定を消した・名前を変えた・キーを消した PR も、ここで止まる。
   基準の変更は PR の差分そのものなので、人がレビューして merge するまで、変えた後の基準で判断しない。
2. 設定の値を読む（`node <このスキルのディレクトリ>/scripts/skill-config/skill-config.mjs get common decision_policy_doc --raw`）。
   1 で設定ファイルが PR の差分に無いことを確かめたので、作業ツリーの値は base branch の値と同じである。
   - exit 3（設定が無い）なら、1〜3 だけで決める。設定ファイルがどの層にも無く、Node.js も無いときも同じである
   - exit 1（設定の誤り）か、設定ファイルがあるのに Node.js が無ければ、止まる
   - exit 0 なら、出力した値を引用符で囲んだ変数に入れて、3 に進む。値はスキーマが、英数字と `.`・`_`・`-`・`/` だけからなる相対パスに限る（`/` で始まる値と `..` の区切りは設定の誤りになる）
3. 1 の一覧にその値（文書のパス）があるか、`git status --porcelain --untracked-files=all -- "$doc"` が何かを出せば止まる。
4. PR の base branch を、`references/pattern-search.md` と同じ方法で専用の ref（`refs/worktree/pr-review/base`）に取得する。
   ベースリポジトリを指す remote の決め方も同じである（fork から出した PR では `origin` でないことがある）。
5. `git ls-tree refs/worktree/pr-review/base -- "$doc"` で種類を確かめる。通常のファイル（モード `100644` か `100755`）でなければ（シンボリックリンク `120000`・ディレクトリ・無い）、止まる。
6. `git show "refs/worktree/pr-review/base:$doc"` で本文を読む。git のオブジェクトから読むので、作業ツリーの変更とリポジトリの外のファイルは読まない。
   読み終えたら、`git update-ref -d refs/worktree/pr-review/base` で ref を消す。

### PR がまだ無いとき

PR を作る前に基準を当てるとき（`issue-start` が仮の決定を判断するときなど）は、上の 1〜6 の代わりに次の順に確かめる。
どこかで止まるときは、人に回すかを自分で決めずに止まり、止まった理由を報告する。

1. 作業ブランチのベースブランチを決める。呼び出し元のスキルが規約から決めたものを使う（`issue-start` では「ブランチ運用・commit 規約の参照」で決めたもの）。
   決められなければ止まる。
2. ベースブランチを専用の ref に取得する。`<remote>` は、ベースリポジトリを指す remote である（多くは `origin`）。取得に失敗したら止まる。
   設定が無いリポジトリでも取得する。作業ブランチが設定を消した場合と、ベースブランチの側で設定が足された場合を、3 で見分けるためである。

   ```bash
   git fetch --no-tags <remote> "+refs/heads/<ベースブランチ>:refs/worktree/pr-review/base"
   ```

3. 作業ツリーの設定が、ベースブランチの先端と同じかを確かめる。

   ```bash
   git diff --name-only refs/worktree/pr-review/base -- .config/skills/shoji9x9/common.jsonc
   git status --porcelain --untracked-files=all -- .config/skills/shoji9x9/
   ```

   1 つ目は、作業ブランチの commit と、commit していない変更の両方を、ベースブランチの先端と比べる。
   作業ブランチが設定を変えた・名前を変えた・消した場合と、ブランチを作った後にベースブランチの側で変わった場合に、ファイル名を出す。
   2 つ目は、1 つ目が比べない untracked のファイルを挙げる。
   どちらかが何かを出すか、0 以外で終わったら止まる。エラーは標準エラーにだけ出て、何も出さない結果と区別できないので、終了コードも確かめる。
4. 上の 2 と同じ方法で設定の値を読む。3 で、作業ツリーの設定がベースブランチの先端と同じことを確かめてある。
   exit 3 なら 1〜3 だけで決め、6 に進む。exit 1 と、設定ファイルがあるのに Node.js が無いときは止まる。
   exit 0 なら、出力した値を引用符で囲んだ変数 `doc` に入れる。
   文書についても 3 と同じ 2 つ（`git diff --name-only refs/worktree/pr-review/base -- "$doc"` と `git status --porcelain --untracked-files=all -- "$doc"`）を実行し、同じ条件で止まる。
5. 上の 5 と 6 を、2 で取得した ref に当てる（種類を確かめ、本文を読む）。
6. 止まったときも、読み終えたときも、`git update-ref -d refs/worktree/pr-review/base` で ref を消す（ref が無ければ何もしない）。

プロジェクトが足した基準を読まずに、人に回さないと決めてしまわないため、読めないときは 1〜3 だけで進めない。設定の誤りを直すか、基準の変更を別の PR で merge すれば、次の実行で読める。

## 返信の書き方

スレッドへの返信と、スレッドの外の指摘に返すトップレベルのコメントは、直した内容か直さない根拠から書き始める。

- 同意・お礼・謝罪だけの文（「ご指摘のとおりです」「ありがとうございます」「失礼しました」など）を書かない。冒頭にも末尾にも置かない。
  これらの文は対応の中身を伝えない。指摘が誤っていたときにも、同意したように読める。
- 直したなら、何をどう直したか（ファイル・変えた内容・確かめた方法）を書く。
- 直さないなら、根拠（事実と違う点・すでに対処している仕組み・範囲の外であること）を書く。
- 指摘が妥当だと確かめたことを伝えたいときは、同意の言葉ではなく、確かめた事実を書く。
  例えば「`parse()` は空の入力で `null` を返すので、呼び出し元に分岐を足した」のように書く。

## 関係する指摘を、判断が出るまで直さない

利用者に確認する指摘があるときは、その指摘と関係する指摘も、答えが出るまで直さず、返信も解決もしない。
答えによって直し方が変わると、先に直した分をやり直すことになるからである。

関係する指摘は、確認する指摘の答えによって、直すかどうか・直し方・直す対象の行が変わりうる指摘である。
答えとは、直すかどうか・どの直し方を選ぶか・設計をどうするかの決定である。
離れた行やほかのファイルの指摘でも、答えで変わりうれば関係する。

- 確認する指摘と同じ関数・同じ節・同じ設定キーを変える指摘は、関係すると推定する。答えで変わらないと言い切れるときだけ、関係しない指摘として扱う。
- 答えで変わりうるかを決められない指摘は、関係する指摘として扱う。そう判断した理由は、利用者に確認するときのメッセージに書く（判断待ちとして残すスキルでは、関係する指摘の印に書く）。
- 指摘を含まない総評（変更の概要など）は、関係する指摘にも関係しない指摘にも数えない。
- 関係する指摘が、それ自体も「人に回すかの基準」で人に回すものに当たるときも、関係する指摘として扱い、選択肢は立てない。答えが出た後に、その指摘を評価し直し、まだ判断が要れば改めて確認する（判断待ちとして残すスキルでは、改めて判断待ちにする）。利用者に確認するときは、答えの後にもう一度判断が要りうる指摘があることも、確認のメッセージに書く（判断待ちとして残すスキルでは、関係する指摘の印に書く）。片方の答えを知らずにもう片方を決めないためである。
- 2 件の確認する指摘が互いに関係するときは、先に評価した 1 件を確認する指摘とし、残りを関係する指摘として扱う。

関係しない指摘は、確認の答えを待たずに進める。
そのため、1 件ずつ直し始める前に、集めたすべての指摘を評価し、確認する指摘と、それに関係する指摘を先に決める。
答えを待つ間の扱い（利用者に確認して待つか、判断待ちとして残すか）は、各スキルの `SKILL.md` で定める。

## 機能を足す・作り込む指摘

「この機能をきちんと実装すべき」「この場合にも対応すべき」のように、機能を足したり作り込んだりする指摘は、直す前に、その機能が使われているかを確かめる。
使われていない機能を作り込むと、使われないコードと、その保守の手間が増えるからである。

1. その機能の呼び出し元を、名前（関数名・オプション名・設定キーなど）でリポジトリ全体から探す（`git grep -n '<名前>'` など）。
2. 呼び出し元があれば、他の指摘と同じように妥当かを判断する。
3. 呼び出し元が無いか、テストからしか呼ばれていなければ、その機能を削る案を、作り込む案と並べて判断する。
   返信には、探した名前と範囲、呼び出し元が無かったこと、選んだ案と根拠を書く。
4. どちらの案を選ぶかに人の判断が要るかは、他の指摘と同じ基準で決める（各スキルの `SKILL.md`）。
