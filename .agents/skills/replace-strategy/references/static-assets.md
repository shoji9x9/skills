# 移行元の静的資産の棚卸しと方針決定（`.replace/assets.md`）

移行元が配信している静的な資産（画像・アイコン・favicon・ロゴ・図・本文の書体・アイコン用の書体）を、新側へコピーするかどうかを、実装が始まる前に種類ごとにまとめて決める。
その工程と記録をこのファイルで定義する。
`replace-strategy setup` の手順 11 が台帳を作り、`parity-replace` / `parity-component` が実装のときに読む。
`parity-replace` は、完了の判定で新側の配信物と突き合わせる（下の「完了判定での突き合わせ」）。

依存（`.replace/dependencies.md`）とは別のものである。
依存は「自前で書くか、どのパッケージを使うか」で、判断材料は更新の頻度・採用の規模・ライセンス・サイズである（[`dependency-selection.md`](dependency-selection.md)）。
資産は移行元の配信物そのもので、判断材料は、再配布してよいか・出どころ・同等のもので置き換えたときに残る差である。混ぜると、次の失敗が起きる。

- 資産の判断が工程に無いまま、各機能の実装者が実装の順に 1 人ずつ決める。同じ種類の資産に逆の判断が付き、後から覆る。
- 依存の選定の表が「本文フォント」の行しか持たないので、アイコン用の書体が「依存」にも「画像」にも分類されない。
- 覆ったときに「何を根拠に取り込んだか」が残らず、次に同じ資産に出会った人が、同じ判断からやり直す。

比較の範囲（[`scope.md`](scope.md)「比較・検証の範囲」）とは別の軸である。
`url()` で参照する資産の中身が比較の対象外でも、コピーしなければ画面に出ない。この工程は「コピーするか」だけを決め、比較するかは変えない。

## 棚卸し（起点は 2 つ）

どちらか一方だけでは抜ける。両方を突き合わせて、1 つの一覧にする。

1. 配信物と受領資産の中のファイル: 現行のソース・ビルドの成果物・受領資産（`current.received_assets`）の中の画像と書体のファイル。
   読めない（ソースを入手できないなど）なら「未確認」と書き、2 だけで作った一覧を網羅とみなさない。
2. 現行の画面が実際に描いているもの: 同梱の [`../scripts/asset-probe.mjs`](../scripts/asset-probe.mjs) の `assetProbe` 関数リテラルを、chrome-devtools MCP の `evaluate_script` の `function` 引数に渡す
   （IIFE にする必要は無い。呼び方は `role-probe.mjs` と同じ）。
   対象のページは手順 9 のページの一覧から選び、選んだページを台帳に明記する（すべてのページでなくてよいが、ダイアログと、ヘッダー・フッターの共通の部分を含める）。

プローブの返り値は、次のように読む。

| キー | 読むもの |
|---|---|
| `images` | `img` / `input[type=image]` / SVG の `image`・`use` の参照先と、`rendered`（描かれている件数） |
| `glyphs` | 疑似要素（`::before` / `::after`）の `content` の文字・コードポイント・`font-family`。`privateUse: true` は、アイコン用の書体のグリフの目印である |
| `urlRefs` | `url()` の参照（疑似要素を含む）。走査したプロパティは `urlPropsScanned` が返す |
| `localFragmentRefs` | 同じ文書の中の断片の参照（`fill: url(#grad)` など）。外部の資産ではないので、台帳の行にしない。文書の中の SVG の定義がどこにあるかとして、コピーする対象の画面を特定する手がかりに使う |
| `urlPropsScanned` | `url()` を読んだプロパティの一覧（許可リスト）。ここに無いプロパティは見ていない。現行の CSS に `url()` を取る別のプロパティがあれば、その資産は棚卸しに出ないので、台帳に「未走査（プロパティ名）」と書く |
| `fontFaces` / `loadedFonts` | `@font-face` の `src` と、実際に読み込まれた書体 |
| `icons` | favicon などの `link[rel]`（`icon` / `apple-touch-icon` / `mask-icon`） |
| `manifests` | `link[rel=manifest]` の参照だけ（`iconsInspected: false`）。プローブは manifest の `icons` を読まない。manifest を開いて `icons` の各画像を棚卸しに加え、開けなければ「未確認」と書く（インストール用のアイコンは、描画では取得されず、`resources` にも出ないことがある） |
| `resources` | 実際に取得された画像と書体のファイルの URL（`matchedBy` は `extension` / `initiator` / `corroborated`）。拡張子だけで選り分けない。`link` / `css` のように資産以外にも付く initiator は、DOM・`@font-face`・計算後のスタイル・アイコンで裏付けが取れたものだけを入れる（裏付けが取れないものは `unclassifiedResources`） |
| `unclassifiedResources` | 拡張子にも `initiatorType` にも当たらなかった取得（`/assets/content?id=123` のような拡張子の無い配信）。捨てずに中身を確かめる。クロスオリジンのシートが読めない書体は、ここにしか出ないことがある |
| `resourcesCompleteness` / `resourceEntryCount` | Resource Timing の網羅性は常に `unknown` である（バッファの容量は API から読めず、`setResourceTimingBufferSize` で変わるので、あふれたかを後から証明できない）。件数は目安として使い、`resources` を「これですべて」の根拠にしない。`fontFaces` / `urlRefs` / `unclassifiedResources` と突き合わせ、埋まらなければ「未確認」と書く |
| `shadowRoots` | 走査した open な shadow root の数（内側の要素とスタイルシートも、上の各キーに含む）。closed な shadow root は読めないので、Web Components を使うページでは画面と突き合わせる |
| `unreadableSheets` | `cssRules` を読めなかったスタイルシート。1 件以上あれば、`fontFaces` は網羅ではない。`resources` の書体のファイルと突き合わせ、埋まらなければ「未確認」と書く |

- `rendered: 0` の `img` を、「画面に出ないからコピーしない」と決めない。
  同じ宿主や近くの要素が、疑似要素のグリフや `background-image` で同じ場所を描いていることがある（`img` を隠して、アイコン用の書体で描く実装）。
  `glyphs` / `urlRefs` の `samples[].path` と突き合わせ、実際に描いているものを行にする。
- 書体は、`font-family` と `fontFaces` の `src` で、本文用とアイコン用に分ける。
  同じ「移行元が配信している書体のファイル」でも、本文用とアイコン用ではコピーするかの判断が分かれうるので、別の行にする。
- 状態（ホバー・展開・エラーの表示）でしか出ない資産は、その状態に入れてから、もう一度プローブを当てる。入れなかった状態は、台帳に「未走査」と書く。

## 決めること（種類ごとに 3 択）

行の単位は資産の種類である（例: 本文の書体、アイコン用の書体、ロゴ、画面の中の図、favicon、状態のアイコン）。個々のファイルは、行の中に挙げる。
**同じ種類に別々の判断を付けない。** 分けたいなら、分ける理由を書いて種類を分ける。

方針の値は、同梱のスクリプトが文字列として読む語彙なので、次の表の書き方のまま使う。

| 方針 | 意味 | 追加で要ること |
|---|---|---|
| `実体をコピーする` | 移行元の配信物（再エンコードを含む）を新側に同梱する | 再配布してよいことの根拠（ライセンス・利用の条件を定めた文書・先方の許諾）。確かめられなければ選ばない |
| `同等物を作る` | 輪郭を図形にする・自前で描く・同等のパッケージに置き換える | 残る差を書き、この時点で意図的な差異として宣言する（下記）。パッケージに置き換えるなら、そのパッケージを採るかは [`dependency-selection.md`](dependency-selection.md) の基準で決め、`.replace/dependencies.md` に記録する |
| `コピーしない` | 新側に置かない | 画面から消えることが仕様の上で許されるかの根拠。許されないなら選ばない |

<!-- textlint-disable ai-words-ja/no-ai-words -->

旧称: `実体をコピーする` は `実体を写す`、`コピーしない` は `写さない` と書いていた。既存の台帳の旧称は、同梱の `asset-delivery-check.mjs` が同じ意味として読むので、書き直さなくてよい。

<!-- textlint-enable ai-words-ja/no-ai-words -->

- 再配布してよいか・出どころ・残る差を、推測で埋めない。確かめられない項目は「未確認」と書く。
  方針を選ぶのに要る項目（上の表の「追加で要ること」）が未確認なら、その方針で確定させず、候補を添えてユーザーに確認する。
  例: 再配布してよいかが未確認なら、`実体をコピーする` は選べないが、残る差を確かめられた `同等物を作る` は選べる。
- 決めるのは人である。スキルは、棚卸しの結果・候補・残る差を示し、ユーザーの決定を記録する。

### `同等物を作る` は選んだ時点で宣言する

ラスタライズの差は、実装では消せない。書体のラスタライズ（サブピクセルの平滑化が乗る）と、輪郭を図形にした描画は、形と位置が合っていても縁が一致しないので、差分ツールに毎回出る。
宣言が無いまま実装すると、その差は差分ツールの出力に説明の付かない差として現れる。
人は、「実装の誤りか、資産をコピーしなかった結果か」を、差分を見てから調べ直すことになる。
着手の前に宣言しておけば、`parity-diff` のトリアージが最初からその根拠で分類でき、同じ判断を機能ごとに繰り返さない。

ただし、宣言だけでは画素の比較の差は消えない。`intentional_diffs` は分類の根拠としてはすべての比較方法に当たる。
しかし、画素の比較の候補は、インスタンスの単位の例外（`.replace/parity/<slug>/component-diff-exceptions.json` の `property: pixel`）でしか吸収できない。
それを書くのは、差分が出た後の `parity-diff` である（`parity-diff` の `references/normalize.md`「レジストリの適用対象」と「画素の比較の例外の適用」で定義する）。
宣言は往復を無くすものではない。承認の根拠を実装の前に用意し、分類を決定論的にするものとして扱う。

- ユーザーが `同等物を作る` を選んだら、残る差を 1 文の宣言にし、ユーザーの承認を得てから、`intentional_diffs.may_change` に非破壊で追記する。
  承認された方針を 1 回記録するだけである（書き手の区分は [`project-config.md`](project-config.md)「キーの書き手とライフサイクル」で定義する）。
  台帳の「宣言」の列に、同じ文言を転記する（照合のキー）。
- 承認が得られないうちは、`may_change` に書かない。`pending` にも書かない。`pending` は実装の途中で見つけた差の置き場で、機能ごとの棚卸しに毎回出るからである。方針を決めないまま残す。

## 記録（`.replace/assets.md`）

テンプレートは [`../assets/assets-template.md`](../assets/assets-template.md) である。更新は非破壊にする（既存の決定を書き換えない。覆すときは、下の「決定を覆すとき」に従って新しい行を足す）。

- 無ければ、最初に書くスキルがテンプレートから作る。この工程の導入より前に `setup` を終えたプロジェクトには無い。`setup` の再実行を待たない。
- 方針が決まっていない行は、方針の列を空欄にし、理由（未確認の項目・判断待ち）を書く。暫定の方針で埋めない。
  決まったら、その行の空欄（方針・再配布の可否・同等物で残る差・決定日）を、その場で埋める。
  対象は空のセルである。決めた「該当なし」の `-` は値として守られる。追記専用の検査は、これらの列を「空から空でない値への変更だけ」を許す形で守る。
  既に入っている値を変えるなら、下の「決定を覆すとき」に従う。
- 各行は「状態」の列を持つ（`有効` ／ `取り消し済み（YYYY-MM-DD → <新しい行>）`）。同じ種類で `有効` の行は、常に 1 つだけにする。

### 決定を覆すとき

非破壊の追記だけでは、古い決定と古い宣言が残り続ける。
台帳は追記で履歴を残す。一方、`intentional_diffs.may_change` の宣言は、`parity-diff` の正規化で差分を除くフィルタとして当たり続ける。
そのため、`同等物を作る` から `実体をコピーする` へ変えた後も、本来は直すべき差が許容され続ける。覆すときは、次のことを同じ作業で行う。

1. 古い行の状態を `取り消し済み（YYYY-MM-DD → <新しい行>）` にする（行そのものは消さない。理由の列に覆した理由を書く）
2. 新しい行を `有効` として追記する
3. 古い行に宣言があれば、その文言を `intentional_diffs.may_change` から取り消す。
   `keep` / `may_change` は人が書くキーなので、スキルは削除しない。該当する文言・行番号・取り消す理由を示して人に削除を頼み、削除されたことを確かめてから、新しい方針での実装に進む
   （残したまま進むと、同じ差が警告なしに許容される）。取り消した後は、古い行の宣言の列を `取り消し済み` にする
4. 新しい方針が `同等物を作る` なら、上の「`同等物を作る` は選んだ時点で宣言する」に従って、新しい宣言を承認を得てから追記する

消費する側（`parity-replace` / `parity-component`）は、状態が `有効` の行だけに従う。
`取り消し済み` の行は履歴で、その方針では実装しない。`有効` の行が 0 件（決めないまま覆した）なら、決まるまで、その資産に依存する実装の単位を進めない。

## 実装時に台帳に無い資産に出会ったら（`parity-replace` / `parity-component`）

機能や部品の中で決めない。台帳に戻す。

1. 台帳（`.replace/assets.md`。無ければテンプレートから作る）で、同じ種類で状態が `有効` の行を探す。あれば、その方針に従う（別の判断を付けない）。`取り消し済み` の行は履歴なので従わない
2. 無ければ、プローブの返り値（どのページで・どう描いているか）を添えて、台帳に方針が空欄の行を追記する。候補（3 択と、それぞれの再配布の可否・残る差）を示して、ユーザーに確認する
3. 決まるまで、その資産に依存する実装の単位は進めない。`porting.md` には、台帳の行を指す 1 行だけを残す（`porting.md` に判断を書いて先に進まない）
4. 決まったら台帳に記録し、`同等物を作る` なら、上のとおり宣言してから実装する

## 完了判定での突き合わせ（`parity-replace`）

決めた方針どおりに新側が配っているかは、スイート・画素・特性照合・aria のどれにも表れないことがある。
favicon はタブにしか出ず、`title` や印刷用の資産もページの外に出る。新側の `index.html` に指定が無いまま機能を完了とし、利用者がタブを見比べて気づいた実例がある。
`parity-replace` は、feature モードの完了の判定（手順 8）で、台帳の「状態 `有効` × 方針 `実体をコピーする`」の行を、1 行ずつ新側の配信物と突き合わせる。

1. 台帳のその行 1 つにつき 1 件を、`.replace/parity/<slug>/new/<target>/asset-delivery.json` に書く（環境ごと。様式は `parity-replace` の `assets/asset-delivery-template.json`）。
   各行は、次の 2 つのどちらかにする。「この機能の画面では使わない」と自分で宣言して外す形は無い。
   台帳の「描き方と使われるページ」は自由記述である。そこから外してよい行を読み取る規則を作ると、表記の揺れ（全ページ・共通ヘッダー・`/*`・サブパスの配下など）のたびに、外せる側へ抜ける。
   外すのは、常に利用者が決める。
   - 突き合わせる: 移行元と新側の URL の組（`files[].current` / `files[].new`）を書く。
     URL は、`/` で始まるパス（`--current-base` / `--new-base` のオリジンで解決する）か、http(s) の絶対 URL で書く。
     サブパスの配下で配る環境（base が `/app/` など）や、別のオリジンの配信物は、絶対 URL で書く。
     クエリ（`?v=2` など）も、新側が参照している形のまま書く（参照は完全一致で数える）。
     新側と移行元が別のオリジンの構成では、次の行は失敗にする（転送された先のオリジンでも同じ判定をする）。
     `new` が移行元の側のオリジン（`--current-base` か、移行元が CDN から配る資産ならその CDN）を指す行（新側が移行元へ直接リンクしている）と、
     `current` が新側のオリジンを指す行（移行元を取得していない）である。`current` と `new` が同じ URL に解決される行も失敗にする。
   - 突き合わせない: `disposition: accepted` と、理由と、利用者の承認（`approved_by` / `approved_at`）を書く。
     この機能の画面が使わない資産も、機械的に突き合わせられない資産（manifest の `icons` からだけ参照されるインストール用のアイコン、認証の内側にしか無い資産など）も、こちらにする。

   該当する行が 0 件でも、記録（`{"entries": []}`）は置く（無ければ入力の不備である）。
2. 新側の対象の画面で [`../scripts/asset-probe.mjs`](../scripts/asset-probe.mjs) を当て（呼び方は「棚卸し」と同じ）、返り値を 1 画面 1 ファイルの JSON に保存する（`new/<target>/asset-probe/` の下）
3. インストール済みの `replace-strategy` から、次を実行する（コピーせず、スキルの中から実行する）

   ```bash
   node <replace-strategy>/scripts/asset-delivery-check.mjs --assets .replace/assets.md \
     --record .replace/parity/<slug>/new/<target>/asset-delivery.json \
     --current-base <現行 target の UI URL> --new-base <選択中の new target の UI URL> \
     --probe .replace/parity/<slug>/new/<target>/asset-probe/<page>.json \
     --write .replace/parity/<slug>/new/<target>/replace-metadata.json
   ```

`files` の組ごとに確かめるのは、次の 2 つである。

- 新側の配信物が参照していること: `new` を `--new-base` で解決した URL が、プローブの `images[].src` / `urlRefs[].url` / `fontFaces[].src[]` / `icons[].href` / `resources[].url` のどれかに、完全一致で現れる。
  `unclassifiedResources`（資産以外の取得が含まれる）・`manifests`（manifest そのものの URL）・`localFragmentRefs`（文書の中の参照）は、参照に数えない。
  ファイルを置いただけで、`index.html` から指していない形は、ここで失敗になる。
- 取得したバイトが、移行元の配信物と一致すること: `current` と `new` をそれぞれ取得する。どちらも、転送を追った最後の応答が 2xx・空でない・HTML でない、のすべてを満たし、sha256 が一致する。
  SPA のフォールバックが 200 で `index.html` を返す形も、ここで失敗になる。
  両側とも同じフォールバックを返すと一致してしまう。そのため、`current` には、実際に資産を返すことを棚卸しのプローブで確かめた URL を使う。
  - 転送（ハッシュ付きのパスへの 301、署名付きの URL への 302 など）は、正規の配り方として通す。
    参照は転送の前の URL（記録の `new`。プローブが記録するのもこちら）で見て、バイトと HTML かどうかは最後の応答で見る。
  - 両側が同じ転送先に着いた組は、同じ配信物を比べているだけなので、失敗にする。転送先は署名付きの URL のクエリを含みうるので、記録にはオリジンとパスだけを出す。
  - 取得には認証情報を付けない。ログインが要る配信物は、両側とも同じログイン画面が返って一致しうるので、最後の応答が HTML なら不一致として失敗にする。
    認証の内側にしか無い資産は機械的に突き合わせられないので、`disposition: accepted` と利用者の承認で扱う。

終了コードは次のとおりである。

- exit 0: すべての行が突き合った（該当が 0 行の場合を含む）
- exit 1: 完了していない（参照が無い・バイトの不一致・取得の失敗・空の配信物・HTML の応答・同じ転送先・移行元のオリジンへの直接のリンク・同じ URL・記録に無い行・台帳に無い記録）
- exit 2: 判定していないので、完了として扱わない。次の場合である。
  - 台帳の方針の表が無い、または複数ある
  - 表の本体が空行で切れた後に行がある（行頭に `|` がある行か、方針の表と同じセルの数の行。どの表の行か決められない）
  - 状態や方針が語彙の外にある
  - 同じ種類に `有効` が 2 行ある
  - 記録の形が正しくない（`used` を書いた行を含む）
  - 承認済み以外の行があるのに、プローブが無い

結果は `--write` で、`replace-metadata.json` の `asset_delivery_check` に書かれる（exit 2 でも `ok: false` と `error` を書き、前回の合格を残さない）。
