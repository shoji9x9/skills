# 横断の応答ヘッダーと現行の弱点の仕分け

`setup` の手順 5（測定の 7）と手順 8（意図的差異レジストリ）の詳細。**現行の防御を黙って失うこと**と、**現行の弱点を黙って写すこと**を、機能ごとの工程に入る前に見える形にする。

両者は同じ理由で機能ごとの工程から漏れる——**スイートも `parity-diff` も「現行と一致しているか」しか見ない**。
アプリのコードの外（サーバー・リバースプロキシの設定）で付く防御は機能インベントリの起点から見えず、新側が付けなくても両側で緑のままになる。
現行と同じ弱点は一致しているので、敵対的レビューにも差分にも現れない。どちらも気づくのは全機能を実装した後の横断レビューか本番で、手戻りは全機能に及ぶ。

## 横断の応答ヘッダー（測定の 7）

**応答ヘッダーを 1 度だけ採り、アプリのコードの外で付くものを一覧にする。** 一覧は `.replace/survey.md` の「7. 横断の応答ヘッダー」に置き、`parity-suite` が各機能の特性化で読む（読み方の正本は `parity-suite` の `references/api-batch.md`「応答ヘッダー」）。

- **採る応答**: 代表的な画面（ログイン画面を含む）・`Set-Cookie` を返す応答（ログインの成功）・未ログインでリダイレクトを返す画面・API（成功とエラー）・静的ファイル（CSS / JS / 画像）・存在しないパス（404）。
  種類ごとに 1 つ以上。画面だけを採ると、静的ファイルとエラー応答にだけ付く・付かないヘッダーを取りこぼす
- **採り方**: 現側 target へ要求し（ログインの成功だけは正規のログイン操作と同じ要求。それ以外は GET）、**リダイレクトを追わずに**最初の応答のヘッダーを採る（例: `curl -sS -o /dev/null -D - --max-redirs 0 "$URL"`。認証が要る応答は `targets[].auth.roles` の環境変数から得たセッションで採り、値を出力しない）。
  ブラウザが付けたヘッダーや中継点のヘッダーを混ぜない。
  **`Set-Cookie` の値（セッション ID 等）は出力・記録しない**——`-D -` の出力をそのまま残さず、cookie 名と属性だけを残す
- **分類**: 採ったヘッダーを次の 3 つへ分ける
  - **防御**: `X-Content-Type-Options`・`X-Frame-Options`・`Content-Security-Policy`（`frame-ancestors` を含む）・`Strict-Transport-Security`・`Referrer-Policy`・`Permissions-Policy`・
    `Set-Cookie` の属性（`HttpOnly`・`Secure`・`SameSite`）・キャッシュ制御（認証後の応答の `Cache-Control`）。**有無と値を assertion にする**。
    ただし要求ごとに変わる部分・秘密の部分は値に含めない（`Set-Cookie` は cookie 名と属性だけ、CSP の `nonce-` の値は伏せた形で比べる）——そのまま固定すると現側でも毎回赤くなり、秘密の値が一覧とスイートに残る
  - **露出の抑止**: 外したことに意味があるもの（`Server`・`X-Powered-By`・`X-AspNet-Version` 等が**付かない**こと）。**無いことを assertion にする**
  - **揮発・比較不要**: `Date`・`Content-Length`・`ETag` 等。一覧に載せず、比較しない
- **付け手を記録する**: ヘッダーごとに、アプリのコードで付くのか、サーバー・リバースプロキシの設定で付くのかを現行ソース・設定ファイルから読む（読めなければ `不明`）。
  付け手がコードの外にあるものは機能を実装しても付かないので、新側の**サーバー設定の作業**を 1 つの機能 Issue が引き受ける（下の所有者 slug の機能。`issues` モードがその Issue の受け入れ条件へ置く。[`features-issues.md`](features-issues.md)「機能 Issue」）
- **どの機能にも属さない応答（静的ファイル・404）の所有者 slug は手順 9 で決める**——測定（手順 5）の時点では slug が無いので空欄で残し、
  手順 9 で slug を採番した後、ページ要素の帰属と同じく候補（最初に着手する機能が既定の候補）を添えてユーザーへ確認し、`.replace/survey.md` の 7 節へ書き戻す。確定するまで空欄で残す（暫定値で埋めない）。
  所有者が無いと、その応答のヘッダーはどのスイートからも assertion されず、サーバー設定の作業も誰も引き受けない
- **横断の 1 本のスイートにせず、各機能のスイートに分配する**——ヘッダーの付き方は応答の種類ごとに違いうる（静的ファイルとエラー応答にだけ付かない等）ので、機能が駆動する応答それぞれで確かめるほうが取りこぼしが無く、
  横断 API の表（fan-out・要求単位の根拠）に載せると消費側の配線検査が意味を持たない。機能に属さない応答だけを所有者 slug で 1 つの機能へ寄せる
- **`current.origin: received-assets` の場合、採った値は再構築した環境のもの**である。受領資産にサーバーの設定（`web.config`・リバースプロキシの設定等）が含まれ、再構築がそれを当てたと確かめられたヘッダーだけを現行の値として扱い、
  そうでないものは付け手を `不明` にし、`gaps` に未検証として残して先方への確認をユーザーに促す。再構築の既定値を現行の仕様として固定しない
- 現行が付けていない防御ヘッダーは、この一覧ではなく下記「現行の弱点の仕分け」の対象になる（付けないことを写すか、付けて直すかを決める）

## 現行の弱点の仕分け（手順 8）

**現行の振る舞いに含まれるセキュリティ上の弱点を列挙し、1 件ずつ「直す（`may_change`）」か「写す（`keep`）」へ仕分けて `.replace/weaknesses.md` に記録する**（テンプレート: [`../assets/weaknesses-template.md`](../assets/weaknesses-template.md)）。
仕分けは人が決める（`--autonomous` では `.replace/strategy-pending.json` の保留に落とし、台帳の仕分けは空欄で残す）。スキルは列挙・基準の当てはめ・宣言の文言の下書きまでを行う。

### 列挙

- **起点は OWASP Top 10 の 1 版に固定する**（観点が案件ごとにばらつかないように）。プロジェクトに指定があればそれに従い、無ければ着手時点の最新版を使い、**使った版を台帳に記録する**。
  分類ごとに、現行ソース・設定・測定の 7（横断の応答ヘッダー）から該当する経路を探し、**該当なしも分類ごとに行として残す**（見ていない分類と区別するため）
- 経路の単位は「どの画面・API・設定で、何をすると成立するか」。書き込みの API が `Content-Type` を検査しない、保存した設定値を検証せずに描画へ使う、ID を指定すれば他人のレコードを取れる、の粒度で書く
- **`setup` の時点で全機能の弱点を見つけきる必要はない**——機能ごとの工程（`parity-suite` の特性化・`parity-replace` の敵対的レビュー）で見つけた弱点は、仕分けを空欄にした行（弱点・分類・経路・根拠は埋める）を台帳へ非破壊追記し、
  「直す」「写す」の**両案を併記した 1 件**を `intentional_diffs.pending` へ回してユーザー確認へ出す（`slug` は対象の機能 slug、`added_by` は追記したスキル。要素の形と重複の扱いは [`project-config.md`](project-config.md)「`pending` 要素の形」）。
  人が決めたら、その文言を `keep` / `may_change` へ移し、**空欄の行は書き換えずに `取り消し済み` にして、決めた仕分け・宣言を持つ行を追記する**（台帳の決定の列はその場で書き換えない。追記専用の検査が「空欄を埋めた」と「決定を覆した」を区別できないため、どちらも追記に揃えて検査で守る）。`setup` 自身が保留にする場合は手順 8 の規則どおり `slug: cross-cutting`

### 仕分けの基準

次の **3 つをすべて満たすものは「直す」**（`may_change` に置いて新側で塞ぐ）。1 つでも満たさなければ「写す」（`keep` に置き、既知のリスクとして記録する）。

1. **特別な権限の無い人が、アプリへ届くか利用者を誘導するだけで成立する**
2. **影響が、他の利用者のブラウザでのスクリプトの実行か、許可の無い書き込みである**
3. **直しても、正規の使い方では振る舞いが変わらない**（例: 表示設定のプロパティを許可したものに絞る、書き込みの API で JSON の `Content-Type` か同一オリジンを必須にする、`frame-ancestors` を付ける、防御ヘッダーを付ける）

- **直すと仕様そのものが変わるもの**（認可の欠落を塞ぐと見える範囲が変わる、など）は基準 3 を満たさないので「写す」に置き、**どの設計の作業で扱うか**（別 Issue・リリース後の改修等）を台帳に書く。扱い先が決まらないまま空欄で閉じない
- 基準を満たすかを推測で埋めない。確かめられない基準は `未確認` と書き、仕分けを空欄のまま人へ上げる

### 宣言と台帳

- **「直す」は `may_change` に、「写す」は `keep` に、人が承認した文言を記録する**（`setup` の対話で決めた値の記録。書き手区分の正本は [`project-config.md`](project-config.md)「キーの書き手とライフサイクル」）。
  文言は弱点と新側の振る舞いの両方が読める形にする（例: 「書き込みの API は `Content-Type: application/json` 以外を 415 で拒否する（現行は `text/plain` を受け付ける CSRF の経路）」）。台帳の「宣言」列に同じ文言を書く（照合キー）
- **写した弱点の露出を広げる意図的差異に注意する。** 別の理由で `may_change` に置いた変更（例: ID を URL に載せる）が、写した弱点の成立を容易にすることがある。
  広げる差異を見つけたら、台帳の該当行の「露出を広げた差異」列に差異の `item` と影響を書く（宣言済みの `item` の文言は書き換えない——追記専用の検査が要素を `item` で突き合わせるため）。
  影響を受けて仕分けを見直すなら、古い行を `取り消し済み` にして新しい行を追記する
- 「直す」行のスイートでの扱い（現行の弱い振る舞いを side 共通の期待値に固定しない）は `parity-suite` の `references/locator-mapping.md`「期待値解決層」、敵対的レビューでの確認は `parity-replace` の `references/adversarial-review.md` が持つ（ここへ転記しない）
