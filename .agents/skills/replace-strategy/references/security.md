# 横断の応答ヘッダーと現行の弱点の仕分け

`setup` の手順 5（測定の 7）と手順 8（意図的差異レジストリ）の詳細である。
現行の防御を警告なしに失うことと、現行の弱点を警告なしに引き継ぐことを、機能ごとの工程に入る前に見える形にする。

両者は同じ理由で、機能ごとの工程から抜ける。スイートも `parity-diff` も、「現行と一致しているか」しか見ないからである。
アプリのコードの外（サーバーやリバースプロキシの設定）で付く防御は、機能インベントリの起点から見えず、新側が付けなくても両側で緑のままになる。
現行と同じ弱点は一致しているので、敵対的レビューにも差分にも現れない。
どちらも、気づくのは全機能を実装した後の横断のレビューか本番で、手戻りはすべての機能に及ぶ。

## 横断の応答ヘッダー（測定の 7）

応答ヘッダーを 1 度だけ採り、アプリのコードの外で付くものを一覧にする。
一覧は `.replace/response-headers.json` に置き（形式は [`../assets/response-headers-template.json`](../assets/response-headers-template.json) で定義する）、
`parity-suite` が各機能の特性化で読む（読み方は `parity-suite` の `references/api-batch.md`「応答ヘッダー」で定義する）。

一覧を Markdown の表で書かない。検査が人の書いた表を解析すると、区切り・強調・注記・空欄の書き方ごとに、読み違いが出続けた。
そのため、検査が読む JSON を原本にした（`survey.md` の 7 節は、このファイルを指すだけである）。
7 節が表のままの既存のプロジェクトでは、表は読まれないので、一覧が無いものとして扱われる。
測定の 7 をやり直して JSON に書き、表を消す（表から転記するときも、下の分類と付け手の語彙に 1 行ずつ当て直す）。

- 採る応答: 代表的な画面（ログインの画面を含む）・`Set-Cookie` を返す応答（ログインの成功）・未ログインでリダイレクトを返す画面・API（成功とエラー）・静的なファイル（CSS / JS / 画像）・存在しないパス（404）。
  種類ごとに 1 つ以上を採る。画面だけを採ると、静的なファイルとエラーの応答にだけ付く、または付かないヘッダーを取りこぼす。
- 採り方: 現側の target へ要求し（ログインの成功だけは正規のログインの操作と同じ要求、それ以外は GET）、リダイレクトを追わずに、最初の応答のヘッダーを採る。
  例は `curl -sS -o /dev/null -D - --max-redirs 0 "$URL"` である。認証が要る応答は、`targets[].auth.roles` の環境変数から得たセッションで採り、値を出力しない。
  ブラウザが付けたヘッダーや、中継点のヘッダーを含めない。
  `Set-Cookie` の値（セッション ID など）は出力も記録もしない。`-D -` の出力をそのまま残さず、cookie の名前と属性だけを残す。
- 分類: 採ったヘッダーと、下の「露出の抑止」の候補を、次の 3 つに分ける（一覧の `class` は、防御が `defense`、露出の抑止が `exposure`）。
  - 防御: `X-Content-Type-Options`・`X-Frame-Options`・`Content-Security-Policy`（`frame-ancestors` を含む）・`Strict-Transport-Security`・`Referrer-Policy`・`Permissions-Policy`・
    `Set-Cookie` の属性（`HttpOnly`・`Secure`・`SameSite`）・キャッシュの制御（認証の後の応答の `Cache-Control`）。有無と値を assertion にする。
    ただし、要求ごとに変わる部分と秘密の部分は、値に含めない（`Set-Cookie` は cookie の名前と属性だけ、CSP の `nonce-` の値は伏せた形で比べる）。
    比べる前の正規化は、`parity-suite` の `scripts/header-normalize.mjs` で定義する。そのまま固定すると、現側でも毎回赤くなり、秘密の値が一覧とスイートに残る。
  - 露出の抑止: 外したことに意味があるもの。応答にあったヘッダーからは生まれないので、候補（`Server`・`X-Powered-By`・`X-AspNet-Version`・`X-AspNetMvc-Version`）を 1 つずつ、採った応答と突き合わせる。
    現行のどの応答にも付かない候補は、値を `null`（付かない）にしてこの分類の行にし、無いことを assertion にする（新側が付けても緑のまま通るのを防ぐ）。
    付いている候補は、下の「現行の弱点の仕分け」の対象にする。
  - 揮発する、比べなくてよいもの: `Date`・`Content-Length`・`ETag` など。一覧に載せず、比べない。
- 付け手を記録する: ヘッダーごとに、アプリのコードで付くのか、サーバーやリバースプロキシの設定で付くのかを、現行のソースと設定ファイルから読む。
  一覧の `setter` は `app-code` / `server-config` で、読めなければ `unknown` にする。付け手のファイルは `setter_source` に書く。
  付け手がコードの外にあるものは、機能を実装しても付かないので、新側のサーバーの設定の作業を、1 つの機能の Issue が引き受ける。
  これは一覧の `server_config_slug` で、手順 9 で決める。デフォルトの候補は、下の所有者の slug と同じ機能である。
  `owner_slug` が `null` の行からは決まらない。`issues` モードが、その Issue の受け入れ条件に置く（[`features-issues.md`](features-issues.md)「機能 Issue」）。
- どの機能にも属さない応答（静的なファイル・404）の所有者の slug は、手順 9 で決める。
  測定（手順 5）の時点では slug が無いので、一覧の `owner_slug` を `null` で残す。
  手順 9 で slug を採番した後、ページの要素の帰属と同じく、候補（最初に着手する機能がデフォルトの候補）を添えてユーザーに確認し、`.replace/response-headers.json` の `owner_slug` に書き戻す。
  書けるのは、`responses` に `static` か `not-found` を含む行だけである。確定するまで `null` で残す（暫定の値で埋めない）。
  所有者が無いと、その応答のヘッダーはどのスイートからも assertion されず、サーバーの設定の作業も誰も引き受けない。
- 横断の 1 本のスイートにせず、各機能のスイートに分ける。
  ヘッダーの付き方は応答の種類ごとに違いうる（静的なファイルとエラーの応答にだけ付かない、など）ので、機能が駆動する応答それぞれで確かめるほうが、取りこぼしが無い。
  横断 API の表（fan-out・要求単位の根拠）に載せると、消費する側の組み込みの検査が意味を持たない。機能に属さない応答だけを、所有者の slug で 1 つの機能に寄せる。
- `current.origin: received-assets` の場合、採った値は作り直した環境のものである。
  受領資産にサーバーの設定（`web.config`・リバースプロキシの設定など）が含まれ、作り直しでそれを当てたと確かめられたヘッダーだけを、現行の値として扱う。
  そうでないものは付け手を `unknown` にし、`gaps` に未検証として残して、先方への確認をユーザーに促す。作り直しのデフォルト値を、現行の仕様として固定しない。
- 現行が付けていない防御のヘッダーは、この一覧ではなく、下の「現行の弱点の仕分け」の対象になる（付けないことを引き継ぐか、付けて直すかを決める）。

## 現行の弱点の仕分け（手順 8）

現行の振る舞いに含まれるセキュリティの弱点を挙げ、1 件ずつ `直す`（`may_change`）か `引き継ぐ`（`keep`。現行の振る舞いを引き継ぐ）に仕分けて、`.replace/weaknesses.md` に記録する
（テンプレートは [`../assets/weaknesses-template.md`](../assets/weaknesses-template.md)）。
仕分けの値（`直す` ／ `引き継ぐ` ／ `該当なし`）と、台帳の列名 `攻撃の流れ` は、テンプレートが定める固定の語彙なので、言い換えない。
<!-- textlint-disable ai-words-ja/no-ai-words -->

旧称: 仕分けの値 `引き継ぐ` は `写す`、列名 `攻撃の流れ` は `経路` と書いていた。既存の台帳の旧称は、同じ意味として読む。

<!-- textlint-enable ai-words-ja/no-ai-words -->

仕分けは人が決める（`--autonomous` では `.replace/strategy-pending.json` の保留にし、台帳の仕分けは空欄で残す）。スキルは、挙げる・基準を当てる・宣言の文言を下書きする、までを行う。

### 列挙

- 起点は、OWASP Top 10 の 1 つの版に固定する（観点が案件ごとにばらつかないように）。
  プロジェクトに指定があればそれに従い、無ければ着手の時点の最新版を使い、使った版を台帳に記録する。
  分類ごとに、現行のソース・設定・測定の 7（横断の応答ヘッダー）から、弱点が成立する箇所を探し、該当が無い分類も行として残す（見ていない分類と区別するため）。
- 成立する箇所（台帳の `攻撃の流れ` の列）の単位は、「どの画面・API・設定で、何をすると成立するか」である。
  書き込みの API が `Content-Type` を検査しない、保存した設定値を検証せずに描画に使う、ID を指定すれば他の人のレコードを取れる、という粒度で書く。
- `setup` の時点で、全機能の弱点を見つけきる必要はない。機能ごとの工程（`parity-suite` の特性化・`parity-replace` の敵対的レビュー）で見つけた弱点は、次のように扱う。
  - 仕分けを空欄にした行（弱点・分類・`攻撃の流れ`・根拠は埋める）を、台帳に非破壊で追記する。
  - 3 つの基準を当てた結果の案（すべて満なら `直す`、1 つでも否なら `引き継ぐ`）の宣言の文言を 1 件作り、`intentional_diffs.pending` に回してユーザーの確認に出す。
    `pending` の文言はそのまま `keep` / `may_change` へ移す決まりで、両方の案を並べた文言は、移した先で決定の文言にならない
    （`slug` は対象の機能の slug、`added_by` は追記したスキル。要素の形と重複の扱いは [`project-config.md`](project-config.md)「`pending` 要素の形」で定義する）。
  - `未確認` の基準が残る弱点は、案を出さず、`pending` にも回さない。「満」でないことを理由に `引き継ぐ` の案を出すと、承認だけで直せた弱点が引き継がれてしまう。
    仕分けが空欄の行として人に上げ、`status` が未決として挙げる。
  - 人が案どおりに決めたら、その文言を `keep` / `may_change` へ移す。
    案と違う決定なら、文言を書き換えて移し、棚卸しの記録の `promoted_as` に書く（`parity-diff` の `references/convergence.md`「`intentional_diffs.pending` の棚卸し」で定義する）。
  - 台帳は、空欄の行の決定の列（空のセル）を、その場で埋める。
    追記専用の検査は、決定の列を「空から空でない値への変更だけ」を許す形で守る。空欄を埋めるのは通り、入っている値の書き換えは失敗になる。
    基準の `未確認` を確かめた結果で書き換えるなら、決めた仕分けを見直すときと同じく、古い行を `取り消し済み` にして新しい行を追記する。
  - 未決の行の宣言や扱う設計の作業を `-` と書いていた古いテンプレートで作った行も、同じである。`-` は決めた値として守られるので、その場で埋めると失敗になる。取り消し済みにして追記する。
  - 根拠は、その場で埋めるときも書き換えない。追記の時点で弱点の根拠を埋めてあるので、決定の理由を書き足すと、入っている値の書き換えとして失敗になる。理由を根拠に残すなら、取り消し済みにして追記する。
  - `setup` 自身が保留にする場合は、手順 8 の規則どおり `slug: cross-cutting` にする。

### 仕分けの基準

次の 3 つをすべて満たすものは `直す`（`may_change` に置いて、新側でふさぐ）。1 つでも満たさなければ `引き継ぐ`（`keep` に置き、既知のリスクとして記録する）。

1. 特別な権限の無い人が、アプリに届くか、利用者を誘導するだけで成立する
2. 影響が、他の利用者のブラウザでのスクリプトの実行か、許可の無い書き込みである
3. 直しても、正規の使い方では振る舞いが変わらない（例: 表示の設定のプロパティを許可したものに絞る・書き込みの API で JSON の `Content-Type` か同一オリジンを必須にする・`frame-ancestors` を付ける・防御のヘッダーを付ける）

- 直すと仕様そのものが変わるもの（認可の欠落をふさぐと見える範囲が変わる、など）は、基準 3 を満たさないので `引き継ぐ` に置く。
  どの設計の作業で扱うか（別の Issue、リリースの後の改修など）を台帳に書く。扱う先が決まらないまま、空欄で閉じない。
- 基準を満たすかを推測で埋めない。確かめられない基準は `未確認` と書き、仕分けを空欄のまま人に上げる。

### 宣言と台帳

- `直す` は `may_change` に、`引き継ぐ` は `keep` に、人が承認した文言を記録する
  （`setup` の対話で決めた値の記録である。書き手の区分は [`project-config.md`](project-config.md)「キーの書き手とライフサイクル」で定義する）。
  文言は、弱点と新側の振る舞いの両方が読める形にする
  （例: 「書き込みの API は `Content-Type: application/json` 以外を 415 で拒否する（現行は `text/plain` を受け付け、CSRF が成立する）」）。
  台帳の「宣言」の列に同じ文言を書く（照合のキー）。
- 引き継いだ弱点の露出を広げる意図的な差異に気をつける。別の理由で `may_change` に置いた変更（例: ID を URL に載せる）が、引き継いだ弱点を成立させやすくすることがある。
  広げる差異を見つけたら、台帳の該当する行の「露出を広げた差異」の列に、差異の `item` と影響を書く
  （宣言済みの `item` の文言は書き換えない。追記専用の検査が、要素を `item` で突き合わせるため）。
  影響を受けて仕分けを見直すなら、古い行を `取り消し済み` にして、新しい行を追記する。
- `直す` の行のスイートでの扱い（現行の弱い振る舞いを、side に共通の期待値として固定しない）は、`parity-suite` の `references/locator-mapping.md`「期待値解決層」が持つ。
  敵対的レビューでの確認は、`parity-replace` の `references/adversarial-review.md` が持つ（ここへ転記しない）。
