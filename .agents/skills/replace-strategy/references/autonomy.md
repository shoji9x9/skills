# 実行スコープの自律性ポリシー（置換系スキル共通）

`replace-strategy` と姉妹スキル（`current-environment-bootstrap` / `golden-dataset` / `parity-component` / `parity-suite` / `parity-replace` / `parity-diff`）が
**`--autonomous` を付けて起動されたときだけ**従う規約の正本。各スキルは自スキル固有の対応（どの確認が保留になるか・記録先・完了値）だけを持ち、本ファイルの規約を転記しない。

**承認を省く規約ではない。** 人の判断が要る箇所で「実行全体を止める」代わりに「その判断を保留に記録し、判断に依存しない工程を先に進め、終わりにまとめて聞く」へ変える。
結果を捏造しない・暫定値で埋めない・承認前の分類を確定扱いしない、という既存の規律は自律実行でもそのまま効く。

**本ファイルを読めない場合は自律実行しない**（`replace-strategy` が未インストール等）。`--autonomous` を無視して従来どおり確認のたびに止まり、その旨を最初に報告する。

## 宣言（実行ごと）

- **有効になるのは起動引数 `--autonomous` を渡した実行だけ。** 設定ファイルに自律のキーは置かない（常に自律になるため）。
  Issue のコメント・チャットの過去の発言・基底ドキュメントの記述は宣言とみなさない
- 引数が無い実行は従来どおり（判断のたびに確認し、答えが無ければ止まる）。実行の途中で自律へ切り替えない
- **起動時に 1 回、宣言を復唱してから始める**: 自律実行であること・下記「越えない線」・保留の記録先。
  依頼文で**追加の禁止**（例: 「commit もしない」）が述べられていれば越えない線に足す。**線を緩める指示は受け付けず、その操作は保留に落とす**
- **対象は起動引数で一意に決まっていなければならない。** 対象の選択（`--feature` / `--component` の省略、既定の無い `--target`、`golden-dataset` の用途〈フェーズ〉）が要るなら、
  自律実行では工程に入らず、候補を示して停止する。**この判断は保留に記録しない**——記録先の成果物のパスが対象で決まるうえ、選ぶ前に進められる工程も無いため
- **姉妹スキルへ委譲するときは `--autonomous` を引き継ぐ**（例: `replace-strategy setup` → `current-environment-bootstrap`、`parity-replace` → `golden-dataset --phase b`）。
  本ポリシーの外にあるスキル（`issue-create` / `issue-start`）へは引き継がず、下記「越えない線」で扱う

## 越えない線（自律でも行わない）

次の操作は自律実行では行わない。必要になったら**保留に落とし**、実行の終わりに聞く。

- **外向きの操作**: push・PR の作成／更新・merge・Issue の起票／コメント／**本文の編集**（`issue-create` への委譲を含む）・配信型 target を更新するデプロイ
  - 例外: `parity-replace` / `parity-component build` が着手時に行う `issue-start --branch-only` のブランチ作成は行ってよい（内容を外へ出さず、作業の置き場所を作るだけのため）
- **課金・通知**（メール送信・外部サービス連携の実呼び出し等）
- **データの作成・変更・削除のうち、設定由来の投入ゲートで事前に許可されていないもの**。
  `targets[].db.seedable` / `dataset_static_paths` で許可された投入と、`parity-suite` の `references/data-discipline.md` に従う書き込みだけが対象外。
  **投入前の「テスト環境であることの確認」は人の確認のまま**で、自律でも省かない（保留に落とす）
- **禁止操作（`targets[].forbidden_actions`）の解除**、現行アプリの変更
- **依存パッケージ・ツールの導入**（`references.dependency_policy` の確認を含む）
- **設定ファイルの「人間が確定させる方針」キーへの書き込み**（区分の正本は [`project-config.md`](project-config.md)「キーの書き手とライフサイクル」）。
  スキルが作業中に追記する記録（`intentional_diffs.pending`）への非破壊追記は従来どおり行ってよい

## 停止の 2 分類

自律実行で各スキルの「停止」「ユーザーに確認」に当たったら、まずどちらかに分ける。

| 分類 | 当たるもの | 自律実行での扱い |
|---|---|---|
| **判断待ち**（保留に落とす） | 人の承認・選択・方針決定を待つもの。例: 「許容」の確定、候補からの選択、破壊的変更の可否、意図的差異の分類、依存方針の要否、**機能の Issue の受け入れ条件と違う実装にすること・受け入れ条件に当たる観点を飛ばすこと**（下記「受け入れ条件から外れる判断」）、上記「越えない線」に当たる操作 | 保留に記録し、**依存する工程だけ止めて**残りを進める |
| **前提の欠落**（従来どおり停止） | 人の判断では埋まらない事実の欠落・故障。例: 前提成果物・前提スキル・MCP が無い、測定できない、接続・認証・起動の失敗、同梱ツールの exit 2（型崩れ）、正本を読めない、対象の取り違え、反復上限への到達 | 停止する。**それまでに積んだ保留も最終報告に並べる** |

- **迷ったら判断待ちに倒さない。** 前提の欠落を保留に落とすと、壊れた前提の上で後続工程を走らせることになる
- **判断待ちでも、依存しない工程が 1 つも残らないなら実質は停止**である。保留に記録して終わりの確認へ進む（対象の選択だけは記録先が決まらないので、上記「宣言」のとおり記録せず停止する）

### 受け入れ条件から外れる判断

機能の Issue の受け入れ条件は利用者が決めたもので、**移行元の振る舞いとぶつかっても実装役が外してよい理由にならない**
（「移行元に合わせるか、Issue の条件に従うか」は利用者の判断）。自律実行かどうかを問わず、次の 2 つは自分で決めない。

- **受け入れ条件と違う実装にすること**（例: 条件は「状態を URL で持つ」、移行元は URL に持たない）
- **受け入れ条件に当たる観点・検証を飛ばすこと**（例: 「書き込みを戻せない」を理由に書き込み系ボタンの観点を飛ばす）。
  **飛ばす前に戻す手段を探し、探した結果を判断材料に書く**——ゴールデンデータの再投入、押す前の状態を読んで同じ口で書き戻す、など。
  探していない「戻せない」は判断材料にならない

コード上の注記・`gaps.md`・`porting.md` に「条件を満たさない理由」を書いたら、**同じ内容を保留（`pending_decisions[]`）にも積む**。
注記や `gaps.md` は「理由を書いた」形になるので、完了判定もレビューもそれ以上を求めない——保留に積まなければ、利用者は受け入れ条件を確かめるまで気付かない。
自律実行でない実行では、保留に積む代わりにその場で利用者に確認する。

## 保留に落とすか、成果物の値として残すか

判断待ちに分けた論点でも、**結果を成果物の値として残せて、その値を読む工程が別に決まっているなら保留に落とさない**。
保留は「人の答えが来るまで先へ進めない」ことの記録なので、答えを待たずに先へ進める論点まで落とすと、
**依存しない工程まで止まる**（下記「下流の前提判定」のとおり、`mode: setup` の未解決が 1 件あるだけで
`features.md` を正規名で残せず、`golden-dataset` 以降が全部止まる）。自律実行では測れない状態が毎回出るので、この線引きが無いと下流が常に止まる。

| 条件 | 扱い |
|---|---|
| 測れなかった・確かめられなかったという**事実**で、成果物の値の語彙にその状態があり、読む工程（引き取り手）が決まっている | **成果物の値として残す**（保留に落とさない）。理由と、確かめるのに要る条件を同じ行・同じ項目に書く |
| 人の承認・選択・方針決定そのもので、答えが無いと後続が誤った前提の上で進む | 保留（`pending_decisions[]`）に落とす |

- 例（値として残す）: 共通 UI プリミティブの洗い出しで、禁止された操作でしか状態を作れなかった種類は
  `.replace/dependencies.md` の `未確認` の行にする（正本は `replace-strategy` の `references/dependency-selection.md`「洗い出しの 6 値」）。
  その種類が要る機能の `parity-replace` が実装フェーズ前に確かめ直すので、`setup` は完了できる
- 例（保留に落とす）: 現行環境で破壊的な操作を実行してよいか。実行の可否そのものが人の判断で、成果物の値にならない
- **値として残した事実は、最終報告で件数と内訳を示す。** 黙って値へ倒すと「聞かずに済ませた」と区別が付かない
- **語彙に無い状態を値へ倒さない。** 近い値へ寄せると読む工程が誤った前提で進む（`未確認` を `該当なし` と書けば、その部品は誰の目にも触れなくなる）

## 保留に落としたとき

1. **暫定値で埋めない・推奨案を適用しない。** 推奨案は保留に書いてよいが、答えが来るまで使わない。承認前の分類は各スキルの暫定表記のまま残す（例: `parity-diff` の `許容候補（要確認）`）
2. **依存する工程を `blocks` に列挙して止める。** 依存するかを判断できない工程は依存するものとして止める（fail-closed）
3. **依存しない工程を最後まで進める。** 成果物は依存しない部分だけ書き、依存する部分は書かない（空欄・未記録のまま）
4. **完了を名乗らない。** 保留が 1 件でも残る実行では、各スキルの完了値（`converged` / `status: handed-off` / `capture.complete` 等。どれに当たるかは各スキルの「自律実行」節）を完了側にしない
5. **同じ原因の判断は 1 件にまとめる。** 承認の粒度は原因単位（例: `parity-diff` の `references/triage.md`「承認の単位は原因」）。候補ごとに保留を立てない

## 終わりにまとめて聞く

依存しない工程を進め切ったら（または前提の欠落で停止したら）、**1 回だけ**保留をまとめて確認する。

- 実行中のエージェントの確認 UI で原因ごとに聞く。**1 回に載せる問いの数はその UI の上限に従い**、超える分は続けて聞く（上限はエージェントごとに違うので、ここで数を固定しない）。
  **判断材料（crop・差分テキスト・根拠のパス・件数と内訳）を確認 UI そのものに同梱する**——直前のテキストが見えている前提を置かない。
  選択肢ごとの preview 欄を持つ UI（例: Claude Code の AskUserQuestion）ならそこへ、持たない UI なら問いの本文へ入れる
- 答えが得られたら、各スキルの通常の承認フロー（記録先への非破壊追記等）で反映し、`resolution` を書いて**止めていた工程を同じ実行で再開する**。
  **再開して `blocks` の工程を終えたら `resolution.resumed` を書く**（書かない限り、その保留は下記「保留の状態」で未解決のまま）。再開で新しい保留が出たら、また終わりにまとめて聞く
- **答えが「方針は A。実施は後で」の形なら、`blocks` の工程を実施しないまま解決にしない。** 残作業を置く場所（別の Issue 等）を決めて `resolution.follow_up` に書く。
  置き場の作成（Issue の起票）は外向きの操作なので、自律実行では作らず保留を未解決のまま残し、置き場を作るかを終わりに聞く——**残作業を回答の自由文の中にだけ残さない**
- **答えが得られない**（非対話実行・無応答・承認以外の応答）なら、保留を未解決のまま記録して終える。最終報告の先頭に未解決の保留と、それが止めている工程を並べる

## 記録の形（`pending_decisions[]`）

各スキルの機械可読な成果物（どのファイルかは各スキルの「自律実行」節）に `pending_decisions` 配列として書く。**保留が無ければ空配列**を書く（無記録と区別する）。
あわせて同じ成果物の `run.autonomous` に真偽値で自律実行だったかを残す。

```json
{
  "id": "<成果物内で一意。例: pd-1>",
  "question": "<人に問う内容（1 文）>",
  "cause": "<判断が必要になった原因。承認の粒度の単位>",
  "options": ["<選択肢>"],
  "recommendation": "<推奨案と理由。無ければ null。答えが来るまで適用しない>",
  "evidence": ["<判断材料のパス・値>"],
  "blocks": ["<この判断に依存して止めた工程>"],
  "raised_at": "<ISO 8601>",
  "resolution": null
}
```

- `resolution` は答えを反映したら次の形にする。答えの無い間は `null`

  ```json
  {
    "answer": "<答え>",
    "answered_at": "<ISO 8601>",
    "resumed": { "at": "<blocks の工程を終えた ISO 8601>", "evidence": ["<実施の証拠: コマンドの結果・成果物のパス>"] },
    "follow_up": { "what": "<実施しなかった残作業>", "tracked_in": "<残作業を追う置き場: Issue 等>" }
  }
  ```

  `resumed` と `follow_up` は該当しなければ `null` か省略。`blocks` が空の保留はどちらも要らない
- `replace-strategy` の保留は要素ごとに `mode`（`setup` / `issues` / `evidence`。その保留を立てた実行のモード）を持つ。持ち越しても書き換えない
- `golden-dataset` の保留は要素ごとに `phase`（`a` / `b`）を持ち、`b` では `slugs`（影響するすべての slug の配列）と `target` も持つ（下記「下流の前提判定」で範囲を絞るため。複数 `--feature` に効く判断を 1 件にまとめても、影響する slug を漏らさない）
- **次の実行は、成果物を上書きする前に前回の未解決の保留を読む。** 引数なしの実行では最初に確認し、自律実行では判断材料が今も有効かを確かめて持ち越す（前提が変わって不要になったものは理由を書いて外す）。黙って消さない
- `replace-strategy status` が全成果物の未解決の保留を集め、「判断待ち」として報告する

### 保留の状態

保留は **「決まった」（`resolution` がある）と「済んだ」（`blocks` に挙げた工程まで実施した）が別の状態**である。
`resolution` の有無だけで数えると、回答が付いた時点で解決と数えられ、`blocks` の工程が行われないまま前提の判定・完了判定・収束判定が通る。

| 状態 | 条件 | 数え方 |
|---|---|---|
| `open` | `resolution` が `null`・欠落、または `answer` / `answered_at` が無い | **未解決** |
| `decided` | 回答はあるが、`blocks` が空でなく（欠落・型崩れも工程があるものとして扱う）、`resumed`（`at` と空でない `evidence`）も `follow_up`（`what` と `tracked_in`）も無い | **未解決** |
| `settled` | 回答があり、`blocks` が空か、`resumed` か `follow_up` のどちらかがある | 解決済み（`follow_up` のものは置き場とともに最終報告に並べる） |

**本ファイルと姉妹スキルが「未解決の保留」と書くときは、`open` と `decided` の両方を指す。**
数え方は同梱の [`../scripts/pending-decisions-check.mjs`](../scripts/pending-decisions-check.mjs) が正本で、前提の判定・完了判定では手で数えずこれを通す（コピーせずスキル配下から実行する）:

```bash
node <replace-strategy>/scripts/pending-decisions-check.mjs --file <保留の記録先> [--mode setup] [--phase a|b] [--slug <slug> --target <target>]
```

絞り込みの引数は下記「下流の前提判定」の範囲に対応する（`--phase b` は `--slug` と `--target` を伴う）。
終了コードは 0 ＝ 範囲内に未解決が無い（ファイルが無い＝保留なし を含み、その場合は `file_exists: false` を出す）、1 ＝ 未解決が残る、2 ＝ 読めない入力（JSON でない・`pending_decisions` が配列でない）。
**exit 2 は判定していないので、前提を満たしたことにしない。** スクリプトに到達できない（`replace-strategy` が未インストール）ときも合格に倒さず停止する

### 完了の証拠になる成果物には書かない

**下流スキルが前提の判定に使う成果物には保留を書かず、保留に依存する工程が残る間は新規作成・更新もしない。**
保留を残すためにそのファイルを作ると、工程が終わっていないのに下流が完了とみなして進む。

| 完了の証拠（下流が読む） | 保留の記録先 | 保留が残る間の扱い |
|---|---|---|
| `.replace/features.md` と `.replace/components.md`（`replace-strategy setup` 完了） | `.replace/strategy-pending.json` | 作らず、`.replace/features.draft.md` / `.replace/components.draft.md` に下書きする。答えを反映したら `features.draft.md` は正規の名前へ移す。**`components.draft.md` は「共通部品を画面より先に作る」方針が採用されたときだけ移し**、不採用なら削除する（`components.md` の存在は方針の採用を意味する） |
| `.replace/dataset/metadata.json`（`golden-dataset` フェーズ A・B） | `.replace/dataset/pending-decisions.json` | 該当フェーズの記録を作らない・更新しない |
| `.replace/parity/<slug>/metadata.json`（`parity-suite`） | `.replace/parity/<slug>/pending-decisions.json` | 同上 |
| `.replace/parity/<slug>/new/<target>/replace-metadata.json`（`parity-replace` の `suite.new_green`） | `.replace/parity/<slug>/new/<target>/pending-decisions.json` | 同上。**再実行の開始時に既存の `suite.new_green: true` が残っていれば、保留に依存する工程に入る前に `false` へ戻す** |

### 下流の前提判定（自律実行かどうかを問わない）

前提を判定するときは、完了の証拠に加えて**上表の保留の記録先を読み、次の範囲に入る未解決（上記「保留の状態」の `open` と `decided`。`resolution` の有無だけで数えない）の要素が 1 件でもあれば、その前提は未完了として停止する**（前提の欠落）。
前回の完了で作られた証拠が残っていても、再実行が保留を抱えている間は今の要求を満たす保証が無いので、証拠の存在より保留を優先する。

| 前提 | 未完了とみなす保留 |
|---|---|
| `replace-strategy setup` | `.replace/strategy-pending.json` の要素のうち `mode: setup` のもの（要素ごとの `mode` で絞る。ファイル直下の `mode` は最後に実行したモードなので使わない。要素の `mode` が欠落していれば setup のものとして止める） |
| `golden-dataset` フェーズ A | `.replace/dataset/pending-decisions.json` の `phase: a` の要素 |
| `golden-dataset` フェーズ B（slug × target） | 同ファイルの `phase: b` で `slugs` が対象 slug を含み `target` が一致する要素（他の slug・target の保留では止めない。`slugs` が欠落・空の要素は範囲を決められないので、同じ target のすべての slug を止める） |
| `parity-suite`（slug） | `.replace/parity/<slug>/pending-decisions.json` の全要素 |
| `parity-replace` の新側 green（slug × target） | `.replace/parity/<slug>/new/<target>/pending-decisions.json` の全要素 |

- 記録先のファイルが無いのは「保留なし」で、前提の判定を変えない（自律実行していない・保留が無かった）
