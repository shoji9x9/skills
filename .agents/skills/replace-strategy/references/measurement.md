# 測定手順

`setup` モードのステップ 5 である。**すべて実測し、推測した値には「未測定」と書く。** 測れない場合の扱いは、末尾の「停止条件」に従う。

結果は `.replace/survey.md`（テンプレート: [`../assets/survey-template.md`](../assets/survey-template.md)）に記録する。
後から測り直して比べられるように、各測定値に測定方法・対象・日時を添える。

測定対象の環境は、`side: current` の target から選ぶ。依頼で環境を指定されたら、`--target <name>` と同じに扱う。

- `current.origin: received-assets` の場合、対象は `current-environment-bootstrap` が再構築して引き渡した target である。
  引き渡しが完了した（`.replace/bootstrap/metadata.json` が `status: handed-off`）ことを確かめてから、測定に入る。
  完了していなければ測定せず、`setup` の手順 4 へ戻す。
- 指定が無いときのデフォルト・候補の示し方・存在しない名前や側の違う名前の扱いは、[`project-config.md`](project-config.md)「実行対象環境」の「選択規則」に従う（ここへ転記しない）。
- 選んだ target の名前は、`.replace/survey.md` の項目「対象環境」に記録する。
  現側の target を変えるとベースラインが古くなったと扱われるので、どの環境で測ったかを後から辿れるようにするためである。
- `received-assets` の場合は、同じファイルの「現行環境の由来」欄に、再構築した環境であることと引き渡しの状態も残す。
  同じ URL でも、再構築の版が変われば測定値が変わることがあるからである。

## 1. セマンティクス測定（role プローブ）

現行アプリの代表ページで role プローブを実行し、role とアクセシブルネームで引ける要素の割合を出す。
この値で、ロケータマッピング層（`parity-suite`）の規模と、HTML の id・name を変えてよいか（意図的差異レジストリの `pending` の確定）が決まる。

手順は次のとおりである。

1. chrome-devtools MCP で、現行アプリの対象ページを開く。認証が要るなら、ユーザーにログインを頼む
2. 同梱の [`../scripts/role-probe.mjs`](../scripts/role-probe.mjs) を読み、`roleProbe` 関数のリテラル（`() => { ... }` の部分）を、chrome-devtools MCP の `evaluate_script` の `function` 引数に渡す。
   `evaluate_script` は渡された関数を自分で呼び出し、返り値（測定結果のオブジェクト）を JSON で返す。IIFE にする必要は無い
3. 返り値（総数・named と unnamed・role ごとの内訳・(role, name) の重複数・unnamed のサンプル）を、ページごとに記録する
4. 対象のページは、機能インベントリの代表ページから選ぶ。一覧・フォーム・ダイアログを含めて、最低でも 3 ページにする。
   全ページでなくてよいが、対象にしたページを書く

注意することは次のとおりである。

- プローブが求めるアクセシブルネームは、仕様の近似である（アクセシビリティツリーの実装そのものではない）。
  値は「引ける割合の目安」で、`parity-suite` を作るときに個別のページで確かめ直す前提で扱う
- (role, name) が重複する要素は、そのままではロケータとして一意に引けない。重複数も、マッピング層の規模の見積もりに含める
- 測定値が低い（引ける要素が少ない）ことは、止まる理由ではない。ロケータマッピング層が厚くなるという、戦略への入力である。
  止まるのは、測定そのものができないとき（MCP が使えない、現行アプリに届かないなど）である

## 2. DB 復元可否

スナップショットとリストアができるかを確かめる。
手段を問わない能力の測定であり、特定のサービスを前提にしない。手段の例は、DB ネイティブのスナップショット・dump と restore・コンテナのリセット・マネージド DB のスナップショットである。
この結果で、書き込み側のパリティスイートの強度が決まる。

- 「スナップショットを取る → 無害な変更を入れる → リストアする → 変更が消えたことを確かめる」まで通して、初めて「復元可」とする。手段があるはずだ、というだけなら「未測定」にする
- 対象はテスト環境の DB である。本番の DB には触れない
- 接続には、環境変数（測定対象の `side: current` の target の `db.env_vars`）と起動ラッパーを使う。値は出力しない
- 復元にかかる時間も記録する。書き込みテストの実行コストの見積もりに使う

## 3. 現行コードの入手性

バックエンドとフロントエンドのコードが揃っているかを確かめる。
この結果で、バックエンドは直接移植し、フロントエンドは別の戦略を取るという、非対称の設計を取れるかが決まる。

- `current.repo` のコードを実際に読めるか、ビルドの生成物ではなくソースかを、フロントエンドとバックエンドのそれぞれについて確かめる
- 一部しか無い場合（例: バックエンドだけ）は、その旨を記録する。無い側はパリティスイートとベースラインだけが頼りになることを、戦略に反映する

## 4. 副作用の棚卸し

メールの送信・外部との連携・冪等でない操作を洗い出す。
コードを読めるなら、コードから洗い出す（送信・HTTP クライアント・ジョブ登録の呼び出し箇所を grep する）。
読めないなら、画面と設定の情報から推定し、推定であることを書く。

- 各副作用に、パリティ検証の対象か対象外かを付ける。判定の基準は、現行アプリを変えずに現と新の結果を比べられるかである。
  対象・対象外・条件付きの一覧の原本は [`scope.md`](scope.md) である（ここへ転記しない。判定に迷ったら、同じファイルの表を見る）。
  - ファイル出力（CSV・Excel など）と帳票・PDF は対象である。生成物を読み取り専用で捕捉して比べられる。
    バイト列の取得方法は [`file-io.md`](file-io.md) で決め、到達できるかは下の 5 で実測する
  - メール送信と外部連携はスコープ外である。捕捉するには現行アプリを変える必要がある。
    `gaps` に「手動検証が必要」として記録する（確認済みにしない）
- 表への書き込み（監査ログ・利用ログなど）も棚卸しに含める。
  利用者に見える反応を出さないので、画面からは見つからない。コードを読めるなら、書き込みの呼び出しを grep する。
  例外処理の中と、操作が呼ぶ共通処理・サーバー側の処理の中まで数える。
  これは比較の対象で、押さえ方は `parity-suite` の `references/coverage.md`「表への書き込み（`side_effect_writes`）」で定義する
- 副作用は独立した Issue にしない。それを生み出す持ち主（機能ページかバッチ）の一機能として、インベントリに記録する

## 5. ファイル入出力の到達性（ファイル出力・アップロードがある場合）

生成物のバイト列に届くかが、比べるための前提になる。
届かない出力は「対象」と判定できない（判定は [`scope.md`](scope.md)、取得方法は [`file-io.md`](file-io.md) で決める）。

- 画面駆動の出力: ブラウザ経由で捕捉できるか（ダウンロードが発生するか、ビューアにインラインで表示されるか）を、実際に 1 件通して確かめる
- バッチの出力: バッチはブラウザを経由せず、サーバーのファイルシステムに書く。そのため、現行テスト環境のファイルシステムに届くかを実測する。
  出力ディレクトリを読めたか、読めた手段（コンテナへの入り方・リモートからの転送方法）とパスを記録する。読めるはずだ、というだけなら「未測定」にする
- ストレージ: `uses_storage: true` なら、選んだ target の `storage.env_vars` があることを確かめ（値は出さない）、出力先（`<bucket>/<prefix>` かパス）の一覧を読めるかを実測する。
  `upload_route`（`direct` か `presigned`）によって特性化の対象が変わるので、宣言と実際が一致するかも確かめる。
  原本は [`project-config.md`](project-config.md)「ファイルストレージ」である
- xlsx や PDF がある場合は、解析ツールの候補で現行の実際の出力から 2 回抽出し、同じ結果になるか（出力が決定論的か）を実測して記録する。
  選定の原本は [`file-io.md`](file-io.md) である
- 届かないことは、止まる条件ではない。その出力を「スコープ外（未検証）」として `gaps` に回す、戦略への入力である

## 6. 既存テストの有無・密度・実装非依存性

現行のテストを、新旧の両方に当てられるか（実装の言語やフレームワークに依存していないか）を確かめる。

- HTTP や DOM を通す E2E テストは、新旧に共通の判定基準として使い回せる見込みがある。ユニットテストは実装と結び付いているので、対象にしない
- 件数・対象の範囲・実行できるか（実際に 1 回実行する）を記録する

## 7. 横断の応答ヘッダー

サーバーやリバースプロキシの設定がすべての応答に付けるヘッダー（防御のヘッダーと、外したことに意味のあるヘッダー）を 1 回だけ採り、一覧にする。
機能ごとの工程はどれも応答ヘッダーを見ない。そのため、ここで採らないと、新側がヘッダーを付けなくても全工程が緑のまま、安全性だけが下がる。
採る応答・採り方・分類・付けた側の記録・受領資産から再構築した環境での扱いの原本は、[`security.md`](security.md)「横断の応答ヘッダー」である（ここへ転記しない）。

- 結果は `.replace/response-headers.json` に記録する。形式の原本は [`../assets/response-headers-template.json`](../assets/response-headers-template.json) で、`parity-suite` が各機能の特性化で読む。
  `.replace/survey.md` の 7 節には一覧を書かず、このファイルを指すだけにする
- 採れないこと（現側の target へ HTTP で届かないなど）は、止まる条件ではない。一覧を `status: unmeasured` と理由（`unmeasured_reason`）だけにし、`gaps` に未検証として回す

## 停止条件

次のどれかに当たったら、戦略の提示に進まずに止まり、足りないものと解消の手順をユーザーに示す。

- chrome-devtools MCP が使えない（セマンティクス測定ができない）
- 現行アプリの対象環境に届かない（URL が分からない・疎通しない・ログインできない）
- DB 接続の環境変数が用意されていない（存在の確認で失敗する。値は表示しない）

DB の復元が「不可」なことや、コードが「無し」なことは、止まる条件ではなく戦略への入力である。
復元できないなら、書き込み側は自分で作ったデータと後始末に切り替える。コードが無いなら、その側はスイートとベースラインを頼りに進める。
