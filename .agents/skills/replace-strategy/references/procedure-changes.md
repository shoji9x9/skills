# 手順・観点の変更を既に閉じた機能へ当て直す（`.replace/procedure-changes.md`）

機能は 1 つずつ Issue にして閉じる。後の機能で確かめる軸の漏れ（0 件の表示・送っている間の押し直し・入力の重複など）が見つかると、
その機能の被覆表とスイート、手順（スキルか、プロジェクトの観点の決まり）には足されるが、**それより前に閉じた機能へ遡って当てる工程が無いと、
前の機能は古い手順のまま収束扱いで残る**。どの陳腐化の検出（データセット版・採取ツールの版）も「手順が変わった」ことには当たらず、
スイートは緑・`parity-diff` は収束のまま、差は人が監査で見つけるまで残る。

そこで、**軸を足した変更ごとに、それより前に特性化を終えた機能を機械的に列挙し、機能ごとに「当て直した／当てない」の判断を記録させる**。

## 変更の出所は 2 つ

| 出所 | 記録する場所 | 対象になる機能 |
|---|---|---|
| スキル側の手順の改訂 | `parity-suite` の `assets/procedure-revisions.json`（スキルに同梱。プロジェクトは書かない） | `.replace/parity/<slug>/metadata.json` の `run.procedure_revision` がその改訂より小さく、`mode` が改訂の `affects` に入る機能。**キーが無い成果物は改訂番号の導入前**なので、すべての改訂の対象になる |
| プロジェクト側の観点の追加 | `.replace/procedure-changes.md` の「観点の追加」表 | 同じ `metadata.json` の `run.finished_at` に書かれた日付（**オフセットを UTC へ換算しない**。換算すると UTC より遅れた地域の終了日時が翌日になり、同じ日の追加から漏れる）が追加日**以前（同じ日を含む）**で、`mode` が「対象の種類」に入る機能。**`finished_at` も `procedure_revision` と同じく特性化を全体でやり直したときだけ書き換える**（部分的な再取得・当て直しで新しい日付にすると、閉じた機能が追加の対象から黙って外れる） |

- `metadata.json` の無い slug は特性化前なので対象にしない（着手時に新しい手順で作られる）
- **改訂一覧を持つのは `parity-suite` だけ**。他のスキル（`parity-replace` / `parity-diff` 等）の手順の更新で確かめる軸が増えたら、プロジェクト側の台帳に行を足す
- **Issue の open / closed は見ない。** 成果物があれば、閉じていなくても旧手順で特性化されている

## 台帳（`.replace/procedure-changes.md`）

テンプレート: [`../assets/procedure-changes-template.md`](../assets/procedure-changes-template.md)。**無ければ最初に書く工程がテンプレートから作る**。
**更新は非破壊**（追記専用。検査は [`../assets/append-only-manifest.json`](../assets/append-only-manifest.json) の `procedure-changes`）。
**表の列名を変えない**——検査は列名で表を探し、見つからなければ exit 2 で落とす（列名を変えた台帳を「変更なし」と読まないため）。
**表の途中に空行を挟まない**——Markdown の表は空行で終わり、以降の行は表の外になる（検査は表の外の表の行を数えて exit 2 で落とす）。
**HTML コメントは行頭の `<!--` で始め、行末の `-->` で閉じる**（1 行で閉じるか、開始行と終了行に分ける）。散文の後ろの `<!--`・行の途中の `-->`・1 行に 2 つのコメント・閉じないコメントは、
中の表を生きた表として読むか以降の表を読み飛ばすので、検査は exit 2 で落とす（セル・インラインコードにも `<!--` / `-->` を書かない。矢印は `→` を使う）。セル内の縦棒は `\|` で書く（GFM と同じ）。

### 行を足す契機

**確かめる軸を足す変更は、次のどれであっても同じ作業の中で「観点の追加」に 1 行足す。**

- **機能 Issue の中で、他の機能にも要りうる軸を見つけて手順に足したとき**（被覆表の候補・プロジェクトの観点の決まり等。
  見つけた機能の被覆表とスイートに足すだけで終えると、直しは見つけた機能にしか入らない）
- **プロジェクトの観点の決まり（ドキュメント・設定）へ項目を足したとき**
- **kaizen の apply で、成果物を作る手順に確かめる軸を足したとき**（手順の反映だけでは既存の成果物に当たらない）

「足すかは次の画面で使ってから決める」として手順に足さずに置いた軸も、**置いた時点で行を足す**（次の画面が無いと、その軸は最後の機能の記録にしか残らない）。
**コードの TODO に残さない**——TODO はどの検査にも数えられない。

### 列

| 列 | 値 |
|---|---|
| `ID` | `PC-001` のような一意の名前。**`#` を含めない**（`parity-suite#<改訂>` はスキル側の改訂の ID に予約） |
| `追加日` | `YYYY-MM-DD`。この日以前に特性化を終えた機能が対象 |
| `足した軸` | 何を確かめるようにしたか（1 文） |
| `由来` | どこで見つけて、どこに足したか（`project-rule: <パス>` ／ `kaizen: <学びファイル>` ／ `issue: #<番号>`） |
| `対象の種類` | `*` か、`feature` / `api-resource` / `batch` の列挙（`metadata.json` の `mode`） |
| `見直しの置き場` | `この変更の完了条件` か `#<Issue 番号>`。**前者なら、対象の機能の当て直しをその変更の完了条件に入れる**。後者なら、**別 Issue の起票までをその変更の完了条件にする**（起票した番号を書く。空欄・「後で」は検査が落とす） |

### 判断の語彙（「既に閉じた機能への当て直し」表）

対象になった `変更 ID` × `slug` ごとに 1 行足す。**同じ組み合わせの行が複数あれば後の行が現在の判断**（追記専用なので書き換えず、判断が変わったら行を足す）。

| 判断 | 意味 | `根拠・理由` に書くもの |
|---|---|---|
| `当て直し済み` | その機能で軸を測り、被覆表・スイートに足し、差を直して流し直した | PR・commit・更新した成果物 |
| `当てない` | その機能には当てないと決めた | 当てない理由（その機能に軸の対象が無い等）。**「時間が無い」は理由にしない**——後で払う費用が見えなくなるだけで、`見直し中` と置き場で残す |
| `見直し中` | 当て直しを置き場で追っている | 置き場（`#<Issue 番号>` で始める。検査が形を確かめる）。**未解決として数え続ける** |

- **当て直すときは、移行元で測るところからやり直す**——「移行元で測る → 被覆表とスイートに足す → 差を直す → 両側のスイートと `parity-diff` を流し直す」。
  スイートに assertion を足すだけでは、移行元の振る舞いを確かめていない
- **当て直しで `run.procedure_revision` を上げず、`run.finished_at` も書き換えない。** 上げてよいのは特性化を全体でやり直したときだけで、1 つの軸を当て直しただけで上げると、
  同じ改訂に含まれる他の軸まで当てたことになる。当て直しは台帳の行で記録する
- **後に作る機能で前の機能のテストの形を写すときは、写し元の機能の未解決の行を先に確かめる**（浅さも写る）

## 検査

```bash
node <replace-strategy>/scripts/procedure-staleness-check.mjs \
  --revisions <parity-suite>/assets/procedure-revisions.json \
  [--ledger .replace/procedure-changes.md] [--parity-dir .replace/parity] [--change <変更 ID>]
```

- `--change` は 1 つの変更の当て直しを完了条件に持つ工程（機能 Issue の受け入れ条件・kaizen の適用）で使う。名指した変更の組み合わせだけで判定し、
  他の変更の未判断では止めない（成果物を読めない機能は、その変更の対象かも決められないので残る）。実在しない変更 ID は exit 2
- **`--parity-dir` が無い・ディレクトリでないときは exit 2**（cwd の誤り・綴り違いを「旧手順の機能なし」と読まない）。特性化前のプロジェクト（空の `.replace/parity/`）は exit 4 で、当て直す対象が無いことを表す

- `--revisions` は**インストール済みの `parity-suite`** の同梱物を渡す（プロジェクトへコピーしない。コピーすると新しい改訂が届かない）
- 既定の置き場に台帳が無いのは「プロジェクト側で軸を足していない」として読み、スキル側の改訂だけで判定する（出力の `ledger_exists: false` で区別できる）。
  **`--ledger` で明示したパスが無いときは exit 2**（綴り違いで台帳の未判断を消さない）
- 終了コード: **0** ＝ 対象の組み合わせがすべて判断済み、**1** ＝ 未判断・見直し中が残る（`unresolved`）、
  **2** ＝ 入力の誤り（使い方の誤り、改訂一覧・台帳・成果物の置き場を読めない、台帳の表・列の欠落や表の外の行、扱えない位置の HTML コメント、語彙外の値、重複 ID、実在しない変更 ID、空の根拠、壊れた改訂一覧・`parity-suite` 以外の改訂一覧）、
  **3** ＝ 未判断は無いが、成果物を読めず対象かどうかを決められない機能がある（`undeterminable`。合格に倒さない）、
  **4** ＝ 対象外（特性化済みの成果物が 1 つも無い。「旧手順の機能なし」と「何も見ていない」を同じ exit 0 にしない）
- `stray` は**対象でない組み合わせへの記録**（slug の綴り違い・作り直して対象から外れた機能）。落とさないが、綴り違いなら対象の組み合わせが未判断のまま残っている
- 未判断を「旧手順で閉じた機能」として報告するのは `replace-strategy status`（[`status.md`](status.md)「導出する内容」14）
