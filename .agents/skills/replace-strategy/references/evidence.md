# evidence モード（要求単位の根拠の書き戻し）

`.replace/features.md` の「要求単位の根拠」列を `推定` → `実測` へ更新する**唯一の経路**。
列そのものの意味論・根拠の形の正本は [`features-issues.md`](features-issues.md)「API の形は要求単位を読んでから決める」にあり、ここへ転記しない。
本ファイルが定めるのは、**確定した後に誰がどう書き戻すか**だけである。

## 呼び出し

```text
replace-strategy evidence --feature <slug> (--endpoint <口> --evidence <根拠>)... [--autonomous]
```

- `--feature` は 1 実行につき 1 つ。`--endpoint` と `--evidence` は**対**で、口の数だけ繰り返す
- 呼び出し元は 3 つ: **人**（着手時に確定した）、**`parity-suite`**（特性化の record/replay で確定した）、**`parity-replace`**（実装で現行ソースを読んで確定した）
- 口を省略して「この行は全部確定した」とは書けない。行単位の昇格を許すと、1 つでも `実測` があれば行全体が実測に見えるという、この列を作った理由そのものが失われる

## 「停止する」の粒度

手順ごとに止める範囲が違う。**前提検証（手順 1）だけが実行全体を止め、手順 2・4 は当たった口だけを書かずに残す。**

- **手順 1 で止めるのは実行全体**——features.md が無い・根拠列が無い・`--endpoint` と `--evidence` の対応が取れない、はどの口も書けない状態なので、1 口も書かずに返す
- **手順 2（候補 0 件・複数件）と手順 4（口の食い違い）で止まるのはその口だけ。** 他の口の書き戻しは進め、
  止めた口とその理由を手順 6 の報告に必ず載せる。1 口の曖昧さで実行全体を捨てると、同じ実行で確定した他の口まで台帳へ戻らない
- **手順 3 で昇格させないのも口単位**（`推定` のまま残すだけで、他の口は書き戻す）

## 手順

1. **前提検証**（欠けたら 1 口も書かずに実行全体を止める。部分的に書いて途中で止めない）
   - `.replace/features.md` が無い → `setup` 未完了。`setup` の実行を促す
   - **「要求単位の根拠」列が無い**（列を持たない版のテンプレートで作られた） → 書き戻さず停止し、`setup` / `issues` の非破壊更新で**列を追加してその行の口を全て埋める**よう促す。
     1 口だけ埋めた列を足すと「列を足しただけ」と区別が付かず、残りの口が空欄のまま `status` の報告に乗る
   - `--endpoint` と `--evidence` の数が合わない・どちらかが空 → 停止する（対応づけを推測で補わない）
2. **対象の同定**（`--feature` の slug を機能一覧・横断 API 表から引く）
   - **バッチ表・「その他の Issue」表の行は対象外**。API の口を持たないので、当たったら書かずに報告して返す（機械検査では exit 4）
   - 口の照合は**完全一致**で行う。`GET /api/orders` と `GET /api/orders/:id` のように一方が他方の部分文字列になる口があるため、前方一致・部分一致で当てない
   - **候補の件数で分岐する。0 件と複数件はどちらも、その口を書かずに残す**（他の口の書き戻しは続ける。上記「「停止する」の粒度」）
     - **0 件**（その口が API 列に無い）: 口の書き間違いか、API 列に無い口を確定したか。後者は口の追加であって根拠の更新ではないので、`issues` の再突き合わせへ回す
     - **複数件**（同じ口が 2 行以上に現れる）: 単一機能からしか使われない API は機能一覧へ、2 つ以上から使われる API は横断 API 表へ、という分類が崩れている。曖昧なまま先勝ちで書かず、どちらの行が正かをユーザーに確認する
3. **昇格条件の検査**（満たさなければ `推定` のまま残す。「読んだ」を「確定した」に読み替えない）
   - **読み取りの口**: 入口の問い合わせ**と応答への写像**の両方を辿った、または実動作で母集合と 1 行が表すものを観測した
   - **書き込みの口**: 要求の組み立て**とハンドラの受け取り・トランザクション境界**の両方を辿った、または実動作で 1 要求が扱う対象と失敗時の巻き戻し範囲を観測した
   - `--evidence` の本文が [`features-issues.md`](features-issues.md)「根拠の形」のどれにも当てはまらない、または上記の片側しか述べていない → 昇格させず、足りない側を名指しして返す
4. **口の形が変わるならその口は書き戻さない**（他の口の書き戻しは続ける）
   - 確定した要求単位が、API 列に書いた口（パス・メソッド・経路の `:id` の有無）と**食い違う**場合、根拠だけを `実測` へ直すと「間違った形が実測として確定した」状態になる。
     口の変更は Issue 本文の受け入れ条件・パリティスイート・新側実装へ波及するため、**書き戻さず**、食い違いの内容（現在の口・確定した単位・波及先）を報告して `issues` の再突き合わせと `parity-suite` の見直しへ回す
5. **非破壊更新**
   - 該当セルの**その口のエントリだけ**を差し替える。同じセルの他の口のエントリ・他の列・他の行・他の節に触らない（更新の正本は [`features-issues.md`](features-issues.md)「features.md の更新は非破壊」）
   - ヘッダの `最終更新` を ISO 8601 で更新する
   - 縮んでいないことは `scripts/append-only-check.mjs`（一覧の `features`）で確かめられる
6. **報告**
   - 昇格した口（前後の根拠）、昇格させなかった口とその理由、**その行に残る `推定` の口**を列挙する。
     残りを黙って落とすと、呼び出し元（`parity-replace` の完了判定）が「この行はもう全部確定した」と読む

## 漏れを数える（機械検査）

書き戻しと未測定の宣言のどちらも行われなかった口は、散文の規約だけでは「確定できなかった」と見分けが付かない。
同梱の [`../scripts/evidence-gap-check.mjs`](../scripts/evidence-gap-check.mjs) がその差を数える（**コピーせずスキル配下から実行する**）:

```bash
node <skill>/scripts/evidence-gap-check.mjs --features .replace/features.md --slug <slug> \
  --unmeasured .replace/parity/<slug>/metadata.json
```

- 数えるのは**未確認の口のうち `unmeasured.entries[].endpoint` に宣言されていないもの**。
  未確認の口の定義は [`status.md`](status.md) の導出項目 11 と同じ（根拠が `推定`／API 列にあるのに対応づかない／語彙外）
- **対応づけの単位は口の文字列の完全一致**。根拠エントリは矢印より前を `,` / `、` で割って突き合わせるので、
  散文でまとめた口（「両方 → …」）は対応づかないものとして数える。`unmeasured` 側も `endpoint` の完全一致だけを宣言に数える（`item` の散文に口が含まれることは宣言にしない）
- **語彙は区切りまで見る**——`実測: …` / `推定: …` だけを語彙として数え、`実測できず: …` のような前方一致は語彙外（未確認）に倒す
- **`unmeasured` キーを持たない成果物は「宣言ゼロ」として数える**（判定不能にしない）——宣言の置き場所が無い以上、未確認の口は 1 つも宣言されていないのが事実で、
  判定不能へ倒すと消費側が完了を止めず推定の口が残ったまま通過する。その旨は `note:` に出す
- **`endpoint` が文字列でない要素は宣言に数えないが、件数を `note:` に出す**（`parity-suite` の検査はこのキーを見ないので、黙って捨てると「宣言したのに未宣言と言われる」が読めない）
- **未確認の口が 1 つも無ければ宣言を読まない**（全て `実測` の行は、`unmeasured` キーの無い旧成果物でも exit 0）——
  宣言は未確認の口の行き先を確かめるためのもので、未確認が 0 件なら判定に寄与しない。判定不能を日常化させると消費側が exit 3 を無視する運用に倒れる
- **`unmeasured.declared: false` は「宣言を持たない」**として `entries` を読まない（`parity-suite` の `artifact-health-check.mjs` がその節を判定しないので、読むと誰も効かせていない宣言で合格に倒れる）
- exit 0 = 漏れなし／**1 = 未宣言の未確認の口がある**／2 = 入力の不備（slug が無い・重複・口の重複・入力を読めない・`unmeasured.declared` が真偽値でない）／
  **3 = 判定不能**（その行の表に「要求単位の根拠」列が無い。`unmeasured` キーが無い旧成果物は**宣言ゼロ**として数えるのでここに入らない）／
  **4 = 対象外**（その slug の行がバッチ・「その他の Issue」の表にある。検査対象が無い。
  **対象外は表の見出しで陽性に同定したときだけ名乗る**——口の列も根拠列も無いだけで対象外にすると、列の導入前の機能一覧まで
  「バッチ表にある」という事実と違う記録で通過する。同定できない表は判定不能（3）へ倒す。
  **口の列・根拠列「らしい」見出し**（空白違い・全角・規約外の名前）がある表は、対象外にも判定不能にもせず exit 2 に倒す——
  どちらへ倒しても完了判定を止めないので、推定の口が残る現役インベントリが素通りする）。
  **1 以外はどれも「検査して 0 件」（exit 0）と読み替えない**——2・3・4 は口を数えていないので、合格の証拠にならない。
  消費側（`parity-replace` の完了判定）が 3 だけ完了を止めないのは、列を持たない旧インベントリで全機能が一斉に止まるのを避けるための後方互換であり、
  「判定不能は合格」という意味ではない。**判定不能だった事実は消費側が記録に残す**（`parity-replace` の `porting.md`）。
  4 を 0 と混同しないのも同じ理由で、口を持つ行が表を間違えて置かれたときに合格へ化ける
- `--unmeasured` を省くと宣言を考慮しないので、未確認の口が 1 つでもあれば exit 1 になる（`status` が一覧を出すときの使い方）

## 自律実行（`--autonomous`）

- **書き戻し自体は越えない線ではない**（リポジトリ内の成果物の更新であり、外向きの副作用を持たない）。手順 1〜5 を満たすなら自律で書いてよい
- **手順 2 の複数件・手順 4 の食い違い**は人の判断が要るので保留に記録して終える（記録先は `.replace/strategy-pending.json`。形の正本は [`autonomy.md`](autonomy.md)）
- 手順 3 で昇格させなかった口は保留にしない——**まだ確定していないという事実がそのまま `推定` に残る**のが正しい状態で、保留に積むと「人が答えれば進む」と誤って読まれる
