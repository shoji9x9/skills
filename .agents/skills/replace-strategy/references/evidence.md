# evidence モード（要求単位の根拠の書き戻し）

`.replace/features.md` の「要求単位の根拠」の列を `推定` から `実測` へ更新するのは、このモードだけである。
列の意味と根拠の形は、[`features-issues.md`](features-issues.md)「API の形は要求単位を読んでから決める」で定義する。ここへ転記しない。
このファイルが定めるのは、確定した後に誰がどう書き戻すかだけである。

## 呼び出し

```text
replace-strategy evidence --feature <slug> (--endpoint <口> --evidence <根拠>)... [--autonomous]
```

- `--feature` は 1 回の実行につき 1 つである。`--endpoint` と `--evidence` は対で、口の数だけ繰り返す。
- 呼び出し元は 3 つある。人（着手のときに確定した）、`parity-suite`（特性化の record/replay で確定した）、`parity-replace`（実装で現行のソースを読んで確定した）である。
- 口を省いて「この行はすべて確定した」とは書けない。行の単位で昇格させると、1 つでも `実測` があれば行全体が実測に見える。それを防ぐのが、この列を作った理由である。

## 「停止する」の粒度

手順ごとに止める範囲が違う。**前提の検証（手順 1）だけが実行全体を止め、手順 2・4 は当たった口だけを書かずに残す。**

- 手順 1 で止めるのは実行全体である。features.md が無いとき・根拠の列が無いとき・`--endpoint` と `--evidence` の対応が取れないときは、どの口も書けないので、1 つの口も書かずに返す。
- 手順 2（候補が 0 件・複数件）と手順 4（口の食い違い）で止めるのは、その口だけである。他の口の書き戻しは進め、止めた口とその理由を手順 6 の報告に必ず載せる。
  1 つの口があいまいなだけで実行全体を捨てると、同じ実行で確定した他の口まで台帳に戻らない。
- 手順 3 で昇格させないのも、口の単位である（`推定` のまま残すだけで、他の口は書き戻す）。

## 手順

1. 前提を検証する。欠けていたら、1 つの口も書かずに実行全体を止める。一部だけ書いて途中で止めない。
   - `.replace/features.md` が無い: `setup` が終わっていない。`setup` の実行を促す。
   - 「要求単位の根拠」の列が無い（列を持たない版のテンプレートで作られた）: 書き戻さずに止め、`setup` か `issues` の非破壊の更新で、列を足してその行の口をすべて埋めるよう促す。
     1 つの口だけ埋めた列を足すと、「列を足しただけ」と区別できず、残りの口が空欄のまま `status` の報告に載る。
   - `--endpoint` と `--evidence` の数が合わない、またはどちらかが空: 止める。対応づけを推測で補わない。
2. 対象を特定する（`--feature` の slug を、機能の一覧と横断 API の表から探す）。
   - バッチの表と「その他の Issue」の表の行は対象外である。API の口を持たないので、当たったら書かずに報告して返す（機械の検査では exit 4）。
   - 口の照合は完全一致で行う。`GET /api/orders` と `GET /api/orders/:id` のように、一方が他方の部分文字列になる口があるので、前方一致や部分一致で当てない。
   - 候補の件数で分ける。0 件と複数件は、どちらもその口を書かずに残す（他の口の書き戻しは続ける。止める範囲は、上の節で定めた粒度に従う）。
     - 0 件（その口が API の列に無い）: 口の書き間違いか、API の列に無い口を確定したかのどちらかである。後者は口の追加で、根拠の更新ではないので、`issues` の突き合わせのやり直しに回す。
     - 複数件（同じ口が 2 行以上に現れる）: 1 つの機能からしか使わない API は機能の一覧へ、2 つ以上から使う API は横断 API の表へ、という分類が成り立っていない。
       あいまいなまま先の行に書かず、どちらの行が正しいかをユーザーに確認する。
3. 昇格の条件を検査する。満たさなければ `推定` のまま残す。「読んだ」を「確定した」と読み替えない。
   - 読み取りの口: 起点の問い合わせと、応答への対応づけの両方をたどった。または、実際の動作で、母集合と 1 行が表すものを観測した。
   - 書き込みの口: 要求の組み立てと、ハンドラの受け取りやトランザクションの境界の両方をたどった。または、実際の動作で、1 つの要求が扱う対象と、失敗したときに巻き戻す範囲を観測した。
   - `--evidence` の本文が [`features-issues.md`](features-issues.md)「根拠の形」のどれにも当てはまらない、または上のどちらか片方しか述べていない: 昇格させず、足りない側を名指しして返す。
4. 口の形が変わるなら、その口は書き戻さない（他の口の書き戻しは続ける）。
   - 確定した要求の単位が、API の列に書いた口（パス・メソッド・パスの `:id` の有無）と食い違う場合がある。
     そのとき根拠だけを `実測` に直すと、「間違った形が実測として確定した」状態になる。
     口の変更は、Issue の本文の受け入れ条件・パリティスイート・新側の実装に影響する。
     そのため書き戻さず、食い違いの内容（今の口・確定した単位・影響する先）を報告して、`issues` の突き合わせのやり直しと `parity-suite` の見直しに回す。
5. 非破壊で更新する。
   - 該当するセルの、その口のエントリだけを差し替える。同じセルの他の口のエントリ・他の列・他の行・他の節には触らない
     （更新の仕方は [`features-issues.md`](features-issues.md)「features.md の更新は非破壊」で定義する）。
   - ヘッダの `最終更新` を ISO 8601 で更新する。
   - 縮んでいないことは、`scripts/append-only-check.mjs`（一覧の `features`）で確かめられる。
6. 報告する。
   - 昇格した口（前と後の根拠）、昇格させなかった口とその理由、その行に残る `推定` の口を挙げる。
     残りを報告から警告なしに外すと、呼び出し元（`parity-replace` の完了判定）が「この行はもうすべて確定した」と読む。

## 抜けを数える（機械検査）

書き戻しも未測定の宣言もされなかった口は、文章の規約だけでは「確定できなかった」と見分けが付かない。
同梱の [`../scripts/evidence-gap-check.mjs`](../scripts/evidence-gap-check.mjs) がその差を数える（コピーせず、スキルの中から実行する）。

```bash
node <skill>/scripts/evidence-gap-check.mjs --features .replace/features.md --slug <slug> \
  --unmeasured .replace/parity/<slug>/metadata.json
```

- 数えるのは、未確認の口のうち、`unmeasured.entries[].endpoint` に宣言されていないものである。
  未確認の口の定義は、[`status.md`](status.md) の導出項目 11 と同じである（根拠が `推定`・API の列にあるのに対応づかない・語彙の外、のいずれかに当たる口）。
- 対応づけの単位は、口の文字列の完全一致である。根拠のエントリは、矢印より前を `,` / `、` で分けて突き合わせる。
  そのため、文章でまとめた口（「両方 → …」）は対応づかないものとして数える。
  `unmeasured` の側も、`endpoint` の完全一致だけを宣言に数える（`item` の文章に口が含まれていても、宣言にしない）。
- 語彙は区切りまで見る。`実測: …` と `推定: …` だけを語彙として数え、`実測できず: …` のような前方一致は語彙の外（未確認）として扱う。
- `unmeasured` のキーを持たない成果物は、「宣言が 0 件」として数える（判定できないとはしない）。
  宣言の置き場所が無いので、未確認の口が 1 つも宣言されていないのが事実である。
  判定できないとすると、消費する側が完了を止めず、推定の口が残ったまま通る。その旨は `note:` に出す。
- `endpoint` が文字列でない要素は、宣言に数えないが、件数を `note:` に出す。
  `parity-suite` の検査はこのキーを見ないので、警告なしに捨てると、「宣言したのに未宣言と言われる」理由を読めない。
- 未確認の口が 1 つも無ければ、宣言を読まない（すべて `実測` の行は、`unmeasured` のキーの無い古い成果物でも exit 0）。
  宣言は、未確認の口の行き先を確かめるためのもので、未確認が 0 件なら判定に関係しない。
  判定できない結果を日常的に出すと、消費する側が exit 3 を無視する運用になる。
- `unmeasured.declared: false` は「宣言を持たない」として、`entries` を読まない。
  `parity-suite` の `artifact-health-check.mjs` はその節を判定しないので、読むと、誰も確かめていない宣言で合格と判定してしまう。
- 終了コードは次のとおりである。
  - 0: 抜けが無い
  - 1: 宣言していない未確認の口がある
  - 2: 入力の不備（slug が無い・重複している・口が重複している・入力を読めない・`unmeasured.declared` が真偽値でない）
  - 3: 判定できない（その行の表に「要求単位の根拠」の列が無い）。`unmeasured` のキーが無い古い成果物は、宣言が 0 件として数えるので、ここには入らない
  - 4: 対象外（その slug の行が、バッチの表か「その他の Issue」の表にある。検査する対象が無い）
- 対象外を名乗るのは、表の見出しで確かに特定したときだけである。
  口の列も根拠の列も無いだけで対象外にすると、列を導入する前の機能の一覧まで、「バッチの表にある」という事実と違う記録で通る。特定できない表は、判定できない（3）とする。
- 口の列や根拠の列「らしい」見出し（空白の違い・全角・規約の外の名前）がある表は、対象外にも判定できないにもせず、exit 2 にする。
  どちらにしても完了の判定を止めないので、推定の口が残る現役のインベントリが、そのまま通ってしまう。
- 1 以外のどの値も、「検査して 0 件」（exit 0）と読み替えない。2・3・4 は口を数えていないので、合格の証拠にならない。
  - 消費する側（`parity-replace` の完了判定）が 3 のときだけ完了を止めないのは、列を持たない古いインベントリで、全機能が一斉に止まるのを避けるための後方互換である。
    「判定できないなら合格」という意味ではない。判定できなかった事実は、消費する側が記録に残す（`parity-replace` の `porting.md`）。
  - 4 を 0 と混同しないのも同じ理由である。口を持つ行が間違った表に置かれたときに、合格と判定されてしまう。
- `--unmeasured` を省くと宣言を考えないので、未確認の口が 1 つでもあれば exit 1 になる（`status` が一覧を出すときの使い方）。

## 自律実行（`--autonomous`）

- 書き戻しそのものは、越えてはいけない線ではない。リポジトリの中の成果物の更新で、外向きの副作用を持たないからである。手順 1〜5 を満たすなら、自律で書いてよい。
- 手順 2 の複数件と、手順 4 の食い違いは、人の判断が要るので、保留に記録して終える
  （記録先は `.replace/strategy-pending.json`。形は [`autonomy.md`](autonomy.md) で定義する）。
- 手順 3 で昇格させなかった口は、保留にしない。まだ確定していないという事実が、そのまま `推定` として残るのが正しい状態である。
  保留に積むと、「人が答えれば進む」と誤って読まれる。
