# 機能インベントリと Issue 起票

`setup` モードのステップ 9（インベントリ作成）と、`issues` モード（起票）の詳細。
インベントリの原本は `.replace/features.md` で、テンプレートは [`../assets/features-template.md`](../assets/features-template.md) にある。

## 機能インベントリ（`.replace/features.md`）

現行アプリを機能単位に分け、次のものを記録する。

- 機能一覧。各機能が持つページ・API・テーブル・副作用出力を、所有者として記録する。対象かスコープ外かも書く
- 要求単位の根拠。API の形を何から決めたか（`実測` か `推定`）を書く。
  採番は特性化より先に行うので、まだ測っていない画面の口もこの列に入る（下記「API の形は要求単位を読んでから決める」）
- 依存順。「依存の浅い順」とは、横断 API の Issue を機能 Issue より先に置くことを指す。
  ゴールデンデータセット Issue は、4 種の中ではすべての Issue の前提として先頭に置く。
  ただし「その他の Issue」表の行が「ゴールデンデータセットより前」と明記していれば、その行を先にする
- 横断 API。API ごとに利用側の機能の一覧（fan-out）を持つ。2 つ以上の機能から使われる API に「横断」の印を付け、リソース単位でまとめる。
  参照テーブルも記録する（下記「テーブルの記録先」）
- バッチ。バッチ・スケジュール実行の単位で、画面を持たない。入力と出力（DB 状態・生成ファイル）を記録する
- slug。下記の規則で採番して記録する
- Issue 番号。起票済みの Issue 番号で、`issues` モードが書き戻す。
  番号だけを持ち、`open` / `closed` は列にしない（下記「Issue の状態は転記しない」）
- その他の Issue。4 種のどれにも当てはまらない Issue で、専用の表を持つ（下記「その他 Issue」）。
  ヘッダに独自の項目を足したり、記録を諦めたりしない
- ページ一覧。ページ（パス）ごとに、そのページに乗る機能の slug を並べる。機能一覧の「ページ」列を逆向きに引いた表である（下記「ページ一覧」）
- ページ要素の帰属。どの機能行のセクションにも収まらない可視要素ごとに、配置の所有者の slug を書く（下記「ページ要素の帰属」）

### ページ一覧（機能をまたぐ在席の根拠）

機能単位に分けて 1 機能ずつ green にしていく設計なので、同じページに乗る別の機能のセクションが丸ごと欠けていても、どのスイートも赤くならない。
移行済みの機能のスイートは、自分の担当範囲しか見ないからである。この欠けを捕まえるには、ページ単位の在席の一覧が要る。

- 1 ページに複数の機能が乗るなら、その slug をすべて並べる。機能一覧の「ページ」列だけでは、あるページに何が乗るかを逆向きに引けない
- `parity-suite` はこの表を根拠に、対象の機能のスイートに、同じページに乗る他の機能の在席チェックを置く。
  新側で未実装の機能はスキップとして扱い、実装が済んだ時点で `parity-replace` がスキップを外す
- `parity-suite` は同じ表から、別の機能の未実装の領域を `capture_conditions.cofeature_masks` の候補として記録する。
  `parity-diff` はそれを同じ target の green の記録と突き合わせ、未実装の間だけ現側・新側の両方に同じようにマスクする
- 機能を追加・分割したら、この表も更新する。更新しないと、在席チェックの対象から外れる

### ページ要素の帰属（配置の所有者）

**ページ一覧を書いたら、そのページの可視要素がすべてどれかの slug に帰属しているかを確かめる。**
機能一覧が所有者を記録するのはテーブル・API・副作用出力だけで、画面に見えている要素の帰属は誰も確かめていない。
どの機能も配置を担当しない要素は、スイートを書いて実装を終えた後に、`parity-diff` の視覚ベースラインの比較で「説明できない差分」として初めて現れる。

- ページごとに可視要素を並べ、それぞれの配置の所有者（slug）を決める。
  並べる要素は現行アプリの実際の画面から取り、機能一覧の「ページ」列から逆算して済ませない。
  同じ要素が複数のページに出るなら、ページごとに 1 行ずつ書く（共通のヘッダ・フッタがよくある例）。
  1 行にまとめると、その要素を置くページが 1 つしか決まらず、残りのページで抜ける
- 機能行のセクションに収まる要素は、所有者が明らかなので個別に書かない。
  表に残すのは、どの機能行のセクションにも収まらない要素である。
  共通のヘッダ・フッタ・ページ内の導線・外部システムへの導線・スコープ外と決めた操作要素がこれに当たる
- スコープ外の要素にも所有者を決める。「作らない」と決めた要素にも場所を占めるものがある（押しても何も起きないボタン、外部の機能への登録の導線など）。
  誰も配置しないと、現行との差分になる。スコープ外は「配置しない」という意味ではない。
  要素として置くのか、その先の挙動まで作るのかを分けて、「扱い」列に書く（`対象` / `スコープ外（配置のみ）`）
- 記録は `ページ` / `要素` / `配置の所有者（slug）` / `扱い` / `備考` の 5 列にする。
  所有者には、その要素を実装のフェーズで置く機能の slug を書く。要素の内容が誰のものかではなく、誰が配置するかで決める
- 所有者は、ページ一覧でそのページに乗る機能の slug から選ぶ。`parity-replace` はページ単位のフェーズで配置する。
  そのページに乗らない機能を所有者にすると、置く場所（フェーズ）が無く、誰も配置しないまま残る。
  候補の中から置く機能を決められないなら、空欄のままユーザーに確認する
- 帰属の無い要素が 1 つでも残るなら、着手する前にユーザーに確認する。確認には、候補の slug（そのページに乗る機能）と、決められない理由を添える
- 確認を待つ間も行を消さず、所有者を空欄のまま残す。仮の値で埋めない。
  行ごと消すと「そんな要素は無い」と同じになる。仮の値を入れると「確定した所有者」と区別できない。
  どちらの場合も、下流（`parity-suite` の `gaps.md`・`parity-replace` の差し戻し・`status` の未検証領域）が未確定を検出できなくなる。
  空欄は下流が読む値であって、進行を止めるための欠落ではない
- 下流は所有者の slug で探す。`parity-suite` は、対象の slug が所有する要素を自分のスイートの対象に含め、他の slug が所有する要素は在席チェックの側に置く。
  `parity-replace` は、自分の slug が所有する要素を実装のフェーズで配置する
- 該当が無ければ、節を消さずに「なし」と書く。「まだ確かめていない」と「確かめた結果、帰属の無い要素が無い」を書き分けるためである
- 既存の `.replace/features.md` にこの節が無い場合（この節を持たない版のテンプレートで作られた場合）は、元の記述を消さない更新で節を足して埋める
- 機能を追加・分割したときや、ページを増やしたときは、この表も更新する

### 機能の分解基準

- 利用者の目的（誰が何を達成するか）・データの境界（所有するテーブル群）・依存関係・副作用の所有者で分ける。
  画面の中の表示セクション（一覧・追加フォーム・絞り込み・完了済みなど）の単位では分けない。
  表示セクションで分けると、目的もデータの境界も依存関係も共通の要素まで別の Issue に分かれ、実装と検証の単位が必要以上に細かくなる
- 複数のページを持つ機能は、1 行・1 Issue にまとめる（例: 注文一覧と注文詳細は `order` の 1 行）。
  ページ単位の作業の分割は、Issue の中のフェーズで行う（後述の「機能 Issue」）。大きなアプリでも、ページの数に比例して Issue を増やさない
- 1 つの機能からしか使われない API は、横断 API にせず、その機能の「新規実装 API」に含める。横断 API の表に載せるのは、2 つ以上の機能が使うリソースだけである

### API の形は要求単位を読んでから決める

機能一覧の「新規実装 API」列と、横断 API の表の「API」列は、採番の時点（`setup` / `issues`）で埋まる。
画面の特性化（`parity-suite`）はそれより後なので、まだ 1 度も測っていない画面の口もここに書かれる。
下流（機能 Issue の本文・`parity-replace`）はこの列を「決まっている形」として読む。
そのため推定を印なしで書くと、実装のほぼ最後（画面をつなぎ込む直前）まで誤りが見つからない。
その時点で口を作り直すと、リポジトリ層・ルート・型・統合試験・決定の記録を同時に直すことになる。

- 口を決める前に、その口の要求単位を現行のソースコードから読む。読む場所は口の向きで変わる。
  - 読み取りの口では、起点の問い合わせ（「母集合＝起点の `SELECT` の対象」と「1 行が表すもの」）と、応答への変換を読む
  - 書き込みの口では、要求の組み立て（画面が何を 1 要求に詰めるか）と、ハンドラの受け取りとトランザクションの境界（1 要求が何件を 1 つのトランザクションで変え（一部だけが変わることは無い）、失敗したときにどこまで戻すか）を読む
  - どちらの口でも、操作が共通部品を通るなら、部品の内側を送信・実行の直前まで読む（共通部品のクライアント側のスクリプト・部品が持つ送信の関数・サーバー側の共通処理）。
    件数・長さの上限や、必須・形式の判定と、表への書き込み（監査・利用ログ。例外処理の中を含む）はそこに置かれる。これらは画面の処理にも、部品へ渡す引数にも現れない。
    見つけた書き込み先の表は、「副作用出力」列に書く。
    判定と書き込みの特性化は、`parity-suite` の `references/coverage.md`「送る前の判定（`pre_send`）」「表への書き込み（`side_effect_writes`）」で定義する

  どちらも現行のソースコードで確定できるので、UI の操作や特性化を待たない。
  証拠の段階は、`replace-strategy` の `SKILL.md`「厳守の制約」にある、最もコストの低い方法から始める規則に従う
- 同じ表・同じ主キーを触ることは、要求の単位が同じだという根拠にならない。主キーが同じでも、一方は親 1 件を、もう一方は（親, 子）の組を 1 行にすることがある。
  後者で、移行元が選んだ行を 1 要求で送り、失敗したときにすべて戻しているなら、`:id` をパスに持つ口を子ごとに呼ぶ形では再現できない。途中で失敗すると、一部だけ変わった状態が残るからである
- 根拠は口ごとに書き、空欄にしない。1 つの行が複数の口を持ち、口ごとに根拠が違うことはよくある（一覧の `GET` は起点の問い合わせを読めたが、更新・削除の要求単位は未確定、など）。
  セルに根拠を 1 つだけ書くと、1 つでも実測があれば行全体が実測に見え、未確定の口が `status` の未検証領域から外れる。この列を作った理由そのものが失われる
- セルには、`<口> → <根拠>` を口の数だけ並べる。区切りは次のとおりで、機械のチェック（`scripts/evidence-gap-check.mjs`）がこの 3 つで分解する。
  - エントリの区切りは全角のスラッシュ `／`
  - 口と根拠の区切りは全角の矢印 `→`
  - 1 つのエントリに複数の口を並べるときの区切りは `,` か `、`

  半角の `/` や改行で区切ると、セル全体が 1 つのエントリとして読まれ、2 つ目以降の口が「対応づかない」として未確認に数えられる。
  根拠が同じ口は 1 つのエントリにまとめてよいが、まとめるときも `,` で口を並べて名前で示す。
  「両方」のような文章でまとめると、機械のチェックが口に対応づけられず、その行の口をすべて未確認として数える
- API 列に書いた口は、1 つ残らず根拠に対応づける。対応づけの無い口は根拠が無いのと同じで、`status` は未確認として挙げる（[`status.md`](status.md) の導出項目 11 が API 列との差分を取る）
- 問い合わせの行の粒度を、そのまま API の外部の単位として `実測` にしない。問い合わせと応答の間には変換の層（マッパー・シリアライザ）がある。
  そこで `(親, 子)` の複数の行が `{親, 子: []}` の 1 件にまとめられることがある。
  起点の問い合わせを読んで確定できるのは、母集合と問い合わせの行の単位までである。
  API の要求・応答の単位は、変換の層までたどるか、実際の動作を観測して確定する。
  変換の層が読めないなら、母集合と問い合わせの行の単位は根拠の材料として書き、その口は `推定: 応答への変換が未確認・要求単位は未確定` のまま残す。
  問い合わせを読んだことを理由に `実測` にしない
- **根拠の形**は次のとおりにする。`実測` は読み取りの口に限らない。
  `replace-strategy` の `SKILL.md`「厳守の制約」の証拠の段階のとおり、ソースで確定できるならソースで確定し、読めないときだけ実際の動作の観測に進む。
  ソースで足りるのに、実際の動作の観測を求めない。
  - `実測: <読んだ起点の問い合わせ>＋<応答への変換>（母集合=… / 1 行=…）`。読み取りの口をソースで確定した場合。問い合わせだけでは足りない（上記）
  - `実測: <読んだ要求の組み立て>＋<ハンドラの受け取りとトランザクション境界>（1 要求が扱う対象=… / 失敗時の巻き戻し範囲=…）`。書き込みの口をソースで確定した場合
  - `実測: <観測した操作と条件>（母集合=… / 1 行=… または 1 要求が扱う対象=…。根拠: API の実動作 / UI の実動作）`。
    上の 2 つのソースが読めず、実際の動作で確定した場合。
    観測していない部分を推測で補わない。観測した操作・条件・対象の版を書き、確定できなかった軸は `推定` のまま残す
  - `推定: <根拠にした slug> と同形と仮定・要求単位は未確定`。まだ確定していない場合。
    同じ形とみなした slug が無いなら `推定: 同形の参照なし・要求単位は未確定` と書く。
    既存の features.md で根拠をたどれないなら `推定: 出どころ不明・要求単位は未確定` と書く。書ける形が無いことを理由に空欄にしない
- 推定のまま起票してよい。起票の条件にすると、確定できない場で「実測」と書かれるだけになる。
  `推定` のエントリを持つ行は、機能 Issue の本文と `status` モードの未検証領域に、その口の名前とともに出る。そのため、着手するときに確定すべき口として残る
- この列は書いた時点の事実なので、上記「Issue の状態は転記しない」が禁じる転記には当たらない。
  書き換えるのは、その口の要求単位を実際に確定したときだけ（`推定` → `実測`）で、書き換えるのは確定した本人である
- 「起点の問い合わせを読んだ」は、`実測` に上げる条件にならない。
  読み取りの口は応答への変換まで、書き込みの口は要求の組み立てとハンドラの受け取り・トランザクションの境界までたどるか、実際の動作を観測して初めて確定する（上記の根拠の形）。
  途中まで読んだ段階で `実測` に上げると、その口は `status` の未検証領域から外れたまま、外部の単位が分からずに残る
- features.md への書き戻しは、`replace-strategy evidence` だけで行う（手順の原本は [`evidence.md`](evidence.md)）。
  `parity-suite` / `parity-replace` は features.md を自分では書かず、確定した時点でこのモードに任せる。
  `実測` に上げる条件を 3 つのスキルに分けて持たせると、実装を急ぐ側で条件が緩むからである
- 確定できなかった口は `推定` のまま残す。測るまで機能を完了させないものは、`parity-suite` が `.replace/parity/<slug>/metadata.json` の `unmeasured` に宣言する
  （原本は `parity-suite` の `references/coverage.md`「未測定を機械可読にする」）。
  書き戻しも宣言も行われなければ、`status` はその口をいつまでも未確認として報告し続ける。
  そのため、「確定した口は書き戻し、確定できなかった口は未測定として宣言する」ことを、機能 Issue の受け入れ条件に含める
- その取りこぼしは、`parity-replace` の完了判定が拾う（原本は `parity-replace` の `SKILL.md`「実行フロー」手順 8）。
  自分の slug に `推定` の口が残り、`unmeasured` の宣言も無い状態では、完了にしない
- 既存の `.replace/features.md` にこの列が無い場合（この列を持たない版のテンプレートで作られた場合）は、元の記述を消さない更新で列を足し、口ごとに埋める。
  空欄で残さない。空欄だと「列を足しただけ」と区別できない

### テーブルの記録先

インベントリに出てくるテーブルを記録する場所は、次の 3 つの列だけである。

- 機能一覧の「テーブル」列
- 横断 API の「参照テーブル」列
- バッチの「参照テーブル」列

下流の `golden-dataset` は、対象のテーブルをこの 3 列から読む（原本は `golden-dataset` の `references/data-design.md`「起点は DDL と機能インベントリ」）。
**どの列にも書かれていないテーブルは、ゴールデンデータセットの対象から外れる。**

- 横断 API からしか参照されないテーブルの置き場所は、横断 API の表の「参照テーブル」列だけである。機能一覧の「テーブル」列は機能が所有するテーブルなので、そこには現れない
- 横断 API の参照テーブルが抜けると、その API が返す値をゴールデンデータで制御できない。
  そのため、fan-out 先のすべての機能（マスタの表示・プルダウン・遷移先の解決など）が、現新の比較の対象から外れる。
  fan-out が広いほど被害が大きいので、横断 API の行を書いたら、参照テーブルを空欄のまま残さない
- 参照テーブルが本当に無い横断 API は、空欄にせず `-` と書く。
  空欄は下流で「記録の抜けの疑い」として扱われ、確認待ちになる。「まだ調べていない（空欄）」と「調べた結果、テーブルを読まない（`-`）」を書き分ける
- 既存の `.replace/features.md` に「参照テーブル」列が無い場合（この列を持たない版のテンプレートで作られた場合）は、元の記述を消さない更新で列を足して埋める。
  列が無いことを理由に記録を諦めない。下記「features.md の更新は非破壊」が禁じるのは削除で、列の追加は妨げない
- 同じテーブルが、機能一覧と横断 API の両方に出てきてよい（所有者は機能の側、参照は横断 API の側）。重複を避けるために片方から消さない

### slug の採番（成果物パスの識別子）

- 各機能・各横断 API リソース・各バッチに、ASCII の kebab-case（`[a-z0-9-]`）で一意な `slug` を付ける
- 日本語の機能名は書き写さず、作業の内容を表す短い英語にまとめる（例: 注文一覧と注文詳細は `order`）
- 下流のスキルの成果物のパス `.replace/parity/<slug>/` は、この slug を使う。
  下流のスキルは slug を自分で作らず、features.md から読む。別々に採番すると、成果物が合流しないからである
- 一意性は、インベントリ全体（機能・横断 API リソース・バッチ・その他 Issue の間）で保つ
- `cross-cutting` は予約語なので、slug に使わない。
  意図的差異のレジストリの `pending` で、「機能に帰属しない追記」を表すからである。使うと、横断の追記と機能の追記を区別できなくなる。
  原本は [`project-config.md`](project-config.md)「`pending` 要素の形」にある
- その他 Issue の slug は `.replace/parity/<slug>/` を持たず、下流のスキル（`golden-dataset` / `parity-suite` / `parity-replace` / `parity-diff`）の対象にならない。
  下流のスキルが features.md から読むのは、機能・横断 API リソース・バッチの slug だけである。
  その他 Issue の slug を対象に指定されたら、「下流の対象外」として止まる。名前の空間は共有するが、対象の範囲は共有しない

### Issue の状態は転記しない

**インベントリが持つのは Issue 番号だけで、`open` / `closed` の状態は列にしない。** 状態の原本はトラッカーにある。

- 状態をここに転記すると、閉じたときに更新するきっかけが無い。
  列を書くのは着手時（起票時）で、完了時の作業は成果物の側（`.replace/parity/<slug>/` の metadata など）に集まり、インベントリに戻る手順が無い。
  転記した値は警告なしに古くなる。古い `open` は「まだ終わっていない機能がある」と読めてしまい、そのずれを検出するチェックも無い
- 状態が要るときは、`status` モードが features.md の番号でトラッカーに問い合わせる（[`status.md`](status.md)「Issue 状態の取得」）。
  インベントリの役目は分解と依存順であって、進み具合の台帳ではない
- 既存の `.replace/features.md` に「状態」列がある場合（この列を持つ版のテンプレートで作られた場合）は、その値を現在の状態の根拠にせず、番号でトラッカーに問い合わせる。
  列そのものは下記「features.md の更新は非破壊」の対象なので、削除を提案し、承認を得てから外す。警告なしに消さない

### 横断 API のグルーピング

- 横断 API は、リソース単位で Issue にまとめる。同じリソースを扱う横断 API は 1 つの Issue にする（例: ユーザー一覧の取得とユーザー詳細の取得は「ユーザー」の Issue）。
  すべての横断 API を 1 つの Issue にまとめず、API ごとに 1 Issue も作らない。粒度の基準はリソースである
- 横断 API はバックエンドだけで、パリティスイートの作り方も画面駆動ではなく API の record/replay になる。
  そのため、機能 Issue とはワークフローが違う（`parity-suite` / `parity-replace` の API モード）

## Issue の種類（6 つ）

| 種類 | 単位 | 記録先 | 依存順 |
|---|---|---|---|
| ゴールデンデータセット Issue（`golden-dataset`） | 全機能をまたいで 1 本（規模が大きければリソースのドメインで分割） | `.replace/features.md` のヘッダの「ゴールデンデータセット Issue」 | すべての Issue の前提。共通部品・横断 API・機能・バッチのすべてより先に置く。その他 Issue の行が「ゴールデンデータセットより前」と明記していれば、その行を先にする |
| 共通部品 Issue（`parity-component`） | 部品単位 | `.replace/components.md` の「部品一覧」表 | ゴールデンデータセットの後で、横断 API・機能 Issue より先 |
| 横断 API Issue | リソース単位 | `.replace/features.md` の「横断 API」表 | 機能 Issue より先 |
| 機能 Issue | 機能単位。バックエンドとフロントエンドの両方を含む | `.replace/features.md` の「機能一覧」表 | 横断 API の後で、依存の浅い順 |
| バッチ Issue | バッチ・スケジュール実行の単位 | `.replace/features.md` の「バッチ」表 | 入力データと参照テーブルが揃った後 |
| その他 Issue | 上の 5 種に還元できない作業の単位 | `.replace/features.md` の「その他の Issue（4 種以外）」表 | 行の「依存順」列に書く（先頭から任意の位置まで） |

- 共通部品 Issue が出るのは、共通部品を画面より先に作る方針を採ったとき（`.replace/components.md` があるとき）だけである。方針を採らないプロジェクトでは、5 種のまま変わらない
- 「その他の Issue（4 種以外）」表の名前は変えない。既存のインベントリの見出しなので、名前を変えると、元の記述を消さない更新ではなくなる。
  共通部品 Issue は `components.md` の側に置くので、この表の対象にはならない

### 本文に含める内容（共通）

- 対象の slug と、その種類のインベントリへの参照。原本はインベントリなので、本文にすべてを書き写さない。
  共通部品 Issue は `.replace/components.md`、それ以外は `.replace/features.md` を指す。上の表の「記録先」列と同じものである
- 使う姉妹スキルと、その順序
- 受け入れ条件（スイートの green・強度の記録・gaps の記録など、種類に応じて）
- 引き受けたインベントリの行の slug を、引き受けを述べる形で受け入れ条件に書く（「`<slug>` のスイートが新側で green」など）。
  起票の後の突き合わせ（下記「[起票の後に行と受け入れ条件を突き合わせる](#起票の後に行と受け入れ条件を突き合わせる)」）は、
  受け入れ条件がその行を引き受けていると読める項だけを、引き受けとして数える。
  本文の他の場所（対象・参照・背景）にだけ書かれた slug も、除外や参照だけの言及（「`<slug>` は対象外」）も、その行を引き受けたことにならない
- slug に加えて、その Issue が引き受ける行の部分（ページ・API の口・比較対象の副作用出力）も名前で示す。
  名前で示さないと、受け入れ条件が行のどこまでを含むかを確かめられない。
  その結果、一部のページや口だけが完了の条件になっている状態が、slug の一致で緑になる（下記「突き合わせの取り方」の、部分の集合の差分）
- 機能・横断 API・バッチ Issue の受け入れ条件には、`parity-diff` の収束を 1 項置く。
  文面は次のとおりにする。
  「`<slug>` について、`parity-replace` と同じ target で `parity-diff` を実行する。
  `.replace/parity/<slug>/new/<target>/diff-metadata.json` の `converged: true` まで進める。スイートが green なことだけで一致と報告しない」
  `parity-replace` の完了（新側の green と検証コマンド）は、値・ラベル・役割しか見ない。機能 Issue の余白・幅・罫線・背景といった見た目は、`parity-diff` だけが見る。
  横断 API・バッチ Issue でも、例外の承認・判断待ちの解消・採取物の健全性を含む収束の条件は、`parity-diff` だけが判定する。
  この項が無いと、チェックを埋めきった Issue が、`parity-diff` を通らないまま閉じられる

### 機能 Issue

- ページ・API・テーブル・副作用出力の一覧
- `.replace/response-headers.json` の `server_config_slug` は、新側のサーバー設定でヘッダーを付ける作業を引き受ける機能の slug である。
  これがこの機能なら、受け入れ条件に「新側のサーバー設定で、一覧のヘッダー（`setter` が `server-config` のもの）を付ける」を 1 項置く
- `owner_slug` がこの機能の行があれば、「機能に属さない応答（静的ファイル・404）のヘッダーをスイートで確かめる」も置く。
  この 2 つは別の記録で、引き受ける機能は `owner_slug` が `null` の行からは決まらない。
  サーバーの設定は機能を実装しても付かないので、どの Issue にも無いと誰も付けない。原本は [`security.md`](security.md)「横断の応答ヘッダー」にある
- この機能が配置する要素（「ページ要素の帰属」表で、所有者がこの slug の行）と、そのページで配置の所有者が決まっていない要素（同じ表の空欄の行。無ければ「なし」）。
  決まっていない行は、着手する前に確定させる項目である。本文から外すと、誰も配置しないまま実装が進む
- 「この機能が新しく実装する API」と「依存する横断 API（どの Issue で実装されるか）」を分けて書き、実装し直さない
- 新しく実装する API のうち、要求単位が未確認の口（根拠が `推定`、または根拠のエントリが無い）は、そのまま「決まっている形」として書かない。
  その口の要求単位を何で確定するかを、着手時の作業として本文に残す。
  作業は、根拠のどの部分が欠けているかで決める（証拠の段階は `replace-strategy` の `SKILL.md`「厳守の制約」）。ソースで足りるなら、実際の動作の観測を求めない。
  - 読み取りの口で、起点の問い合わせをまだ読んでいなければ、その問い合わせを読む。問い合わせは読んだが応答への変換を確かめていなければ、変換の層（マッパー・シリアライザ）をたどる
  - 書き込みの口では、次の 2 つのうち、まだ読んでいないものを読む。要求の組み立て（画面が何を 1 要求に詰めるか）と、ハンドラの受け取りとトランザクションの境界（1 要求が何件を 1 つのトランザクションで変え（一部だけが変わることは無い）、失敗したときにどこまで戻すか）である
  - 上のソースが読めない（受け取った資産に無い、など）なら、API か UI の実際の動作を観測する

  済んでいる作業は書かない。読み終えた問い合わせを「読む」と書くと、受け入れ条件が何もしない項になる。
  受け取った資産に無いモジュールを「読む」と書くと、実装者は実行できない作業を渡される。どちらの場合も、口はいつまでも `推定` のまま残る
- 確定した口は書き戻し、確定できなかった口は未測定として宣言することを、受け入れ条件に 1 項置く。
  `replace-strategy evidence --feature <slug> --endpoint <口> --evidence <根拠>` で `.replace/features.md` を更新する。
  確定できなかった口は、`parity-suite` が `.replace/parity/<slug>/metadata.json` の `unmeasured` に宣言する（手順の原本は [`evidence.md`](evidence.md)）。
  着手時の作業を書いただけでは、結果が台帳に戻らない。書き戻しが無いと、`status` はその口をいつまでも未確認として報告し、未検証領域の一覧が実際より多く出る
- 依存する横断 API のリソース slug ごとに、受け入れ条件に「この機能から `<リソース slug>` を呼ぶ」を 1 項ずつ置く。
  横断 API Issue の側に「全機能から使われる」と書いても、消費側の完了の条件にはならない
  （下記「[横断リソースの呼び出しは消費側の受け入れ条件に届いて初めて引き受けられる](#横断リソースの呼び出しは消費側の受け入れ条件に届いて初めて引き受けられる)」）
- 応答が画面にも出力にも出ない呼び出し（画面を開いたときの記録など）にも、同じ項を置く。要求が出ていること自体を、スイートの assertion にする。
  見た目と応答だけを見る受け入れ条件では、呼ばれていないことが誰の赤にもならない
- 確かめる軸を足したときの当て直しを、受け入れ条件に 1 項置く。文面は次のとおりにする。
  「この Issue で確かめる軸（網羅表の候補・プロジェクトの観点の決まり）を足したら、`.replace/procedure-changes.md` の「観点の追加」に行を足す。
  すでに特性化を終えた機能への当て直しを、置き場（この Issue の完了の条件か、起票した別の Issue）に回す。
  `procedure-staleness-check.mjs --change <足した変更の ID>` が exit 0（特性化を終えた機能が 1 つも無ければ exit 4）になる」
- 置き場を別の Issue にしたなら、対象の機能ごとに `見直し中 | #<その Issue>` を書けば exit 0 になる。当て直しの完了は、その Issue で追う。
  `--change` を付けないと、他の変更の未判断のせいで、この Issue を閉じられなくなる。
  軸を見つけた機能の網羅表とスイートに足すだけでは、直しはその機能にしか入らず、前に収束した機能は古い手順のまま収束した扱いで残る
  （台帳・判断の語彙・チェックの原本は [`procedure-changes.md`](procedure-changes.md)）
- Issue の中は、ページ単位でフェーズを分ける（1 ページを作り切って比べてから、次のページに進む）
- ワークフローは `parity-suite` → `parity-replace` → `golden-dataset`（フェーズ B）→ `parity-diff`（`parity-replace` と往復）の順である

### 共通部品 Issue

- 対象の部品の slug と、`.replace/components.md` への参照。原本はインベントリなので、本文にすべてを書き写さない
- 採取の対象のインスタンス（ページ ＋ 論理名）の件数と、データ依存の有無
- ワークフローは、`parity-component capture`（現行から基準を採り、固定の軸・可変の軸を割り出す）→ `parity-component build`（引数を設計して実装し、カタログの上で照合する）の順である
- 受け入れ条件は次のとおり。
  - 未説明の差分がゼロ
  - `verification_commands.full` が通る
  - 比較の母集合のすべての組み合わせに対応する見本があり、全件を照合した
  - 母集合に対応しない見本（基準の無い見本）が 0 件
  - 操作の結果の突き合わせ（`parity-component` に同梱の `behavior-compare.mjs`）と、動きの突き合わせ（同じく `motion-compare.mjs`）が通る
  - 部品の一生の順番で不具合が出る実行パスの記録のチェック（同じく `lifecycle-check.mjs`）が通る（判定の原本は `parity-component` の `references/lifecycle.md`）
  - `gaps.md` に残した未検証の一覧
- 母集合は、`parity-component` の `SKILL.md`「前提」が定義する。インスタンス × 状態から、そのインスタンスで到達できないと宣言された状態を除いたものである。
  すべてのインスタンス × すべての状態を求めると、到達できない状態を持つ正当な部品を受け入れられなくなる
- 機能 Issue より先に並べる（部品ができてから画面を作る方針のため）。逆にすると、機能の実装中に部品を作ることになり、この Issue の意味が無くなる

### 横断 API Issue

- 対象のリソースと API の一覧、利用側の機能（fan-out）、参照テーブル
- 要求単位が未確認の口（根拠が `推定`、または根拠のエントリが無い）は、そのまま「決まっている形」として書かない。
  その口の要求単位を何で確定するかを、着手時の作業として本文に残す。作業は、欠けている根拠から決める。
  読み取りの口は問い合わせと応答への変換、書き込みの口は要求の組み立てとハンドラの受け取り・トランザクションの境界のうち、まだ読んでいないものを読む。
  ソースが読めないときだけ、実際の動作を観測する。済んでいる作業は書かない（上記「機能 Issue」と「API の形は要求単位を読んでから決める」）
- 確定した後の書き戻しと未測定の宣言も、機能 Issue と同じく受け入れ条件に置く（上記「機能 Issue」・[`evidence.md`](evidence.md)）
- fan-out に挙げた機能の slug ごとに、消費側の受け入れ条件に足す項（「この機能から `<リソース slug>` を呼ぶ」）を本文に書く。
  書いて渡すだけでは、消費側に届かない。
  消費側が未起票なら、その機能 Issue の本文に入れる。すでに起票済みなら、その本文に足すところまでが、この Issue の起票の作業である（手順は下記「[塞ぎ方](#塞ぎ方)」）
- 画面が無くても旧 API の実際の応答が正解になるので、消費側の機能を待たずに仕様は確定する。パリティスイートは 1 度だけ書いて共有し、機能ごとに重複して書かない
- 新側の検証（`parity-replace` の green 化・`parity-diff`）の前に、対象のリソースのテーブルに `golden-dataset`（フェーズ B）で投入されている必要がある。新側の DB にデータが入っていないと、値の比較が成り立たない

### バッチ Issue

- 対象のバッチ、入力（ゴールデンデータセットと入力ファイル）、比較する出力（DB 状態・生成ファイル）
- ワークフローは、姉妹スキルのバッチモードで次の順に進む。
  `parity-suite` が現行の出力をベースラインとして採る → `parity-replace` が新側を実装する → `golden-dataset`（フェーズ B）で新側に投入する → `parity-diff` が決定論的に比べる

### その他 Issue

4 種は、「機能・リソース・バッチ・データセット」という成果物の所有者で分けている。
所有者を 1 つに決められない作業は、4 種のどれにも入らない。複数の機能のテーブルにまたがる設計や、どの機能にも帰属しない前提の整備がこれに当たる。
**これを記録する場所が無いと、ヘッダへの独自の追記か、Issue の本文だけの記録になり、次の書き直しで消える。**
そのための枠が、`.replace/features.md` の「その他の Issue（4 種以外）」表である。
4 種と同じく、`issues` モードの起票の候補・書き戻しの先・`status` モードの報告の対象になる。

- 4 種に還元できるものは、ここに置かない。機能・リソース・バッチに帰属する作業は、必ずその表に置く。
  この表を受け皿にして分解を省くと、依存順も fan-out も成果物のパスも失われる
- 各行に「4 種に当てはまらない理由」と「影響範囲」（波及するテーブル・機能の slug など）を書く。理由を書けないなら、4 種のどれかに当てはまる
- 依存順は行に明記する（`先頭` / `ゴールデンデータセットより前` / 数値）。4 種の依存順は種類で決まるが、その他 Issue は行ごとに違う
- slug を採る（インベントリ全体で一意）。ただし `.replace/parity/<slug>/` の成果物は持たず、下流のスキルの対象にもならない。
  上記「slug の採番」を参照する。`status` モードでの扱いは、[`status.md`](status.md)「導出する内容」の 5（その他の Issue の状態）にある
- 本文には、共通の項目（対象・受け入れ条件）に加えて、この Issue が前提になる下流の Issue（または「下流なし」）を書く
- 例として、新側のスキーマを先に作る Issue がある。デフォルトでは、新側のスキーマは `parity-replace` が機能ごとに作る。
  しかし外部キー・一意キーの設計はテーブルをまたぐので、機能ごとに小分けにすると、両端が揃うまで FK を張れず、型の移し方の判断も Issue ごとにばらばらになる。
  1 本に前倒しするかは利用側の判断であり、スキルはデフォルトを変えない。前倒しした場合の置き場所が、この表である

## 起票の後に行と受け入れ条件を突き合わせる

**起票で保証されるのは「行に Issue 番号が付いた」ことまでで、その行が誰かの完了の条件になったことではない。**
起票の単位はインベントリの行で（種類ごとの単位は上記「Issue の種類」）、ページ単位の分割は Issue の中のフェーズで行う（上記「機能 Issue」）。
機能・横断 API・バッチ・共通部品の行は Issue を 1 対 1 で持ち、番号を他の行と共有しない。
下流（`parity-replace` / `parity-suite` / `parity-diff`、部品は `parity-component`）は、slug ごとに、その行の Issue 番号で着手する。
そのため、番号を共有した 2 行は同じブランチ・PR の流れにまとめられ、別々に進められなくなる。

それでも、実際の起票は行の粒度からずれる。複数の行が 1 つの番号を共有したり、受け入れ条件が行の一部しか名前で示さなかったり、1 行が複数の Issue に散ったりする。
そのため、どの Issue の受け入れ条件にも現れない行や部分が残ることがある。
この段は、そのずれを検出して報告する。ずれを正しい形として認めない。
そうした行が実装されるかどうかは成り行き次第になり、症状は「緑」になる。抜けた機能のスイートはそもそも書かれないので、赤くなるものが無い。

**引き受けの原本は Issue の本文の受け入れ条件であって、インベントリの Issue 列ではない。**
Issue 列が埋まっていることを、引き受けの根拠にしない。まとめ先の番号を書いた行がよくある例で、番号はあるのに受け入れ条件には現れない。

### 突き合わせの取り方

2 つの集合の差分で取る。表を目で追って数えない。

- 母集合は、インベントリのすべての行の slug である。
  `.replace/features.md` の機能一覧・横断 API・バッチ・その他の Issue と、`.replace/components.md` があればその部品一覧を含む。
  ゴールデンデータセット Issue はヘッダの項目なので、番号の有無で見る
- 引き受け集合は、インベントリに記録された Issue 番号の本文の受け入れ条件で、その行を引き受けると述べている slug である。
  本文は番号ごとに取得する。`#` を外した数字を渡す。
  失敗した番号を出力から消さず「判定不能」として残す形は、[`status.md`](status.md)「Issue 状態の取得」と同じである

  ```bash
  gh api "repos/$OWNER/$REPO/issues/$n" --jq '.body'
  ```

  照合は slug の完全一致で取り、部分一致にしない。
  一方が他方の部分文字列になる slug（`order` と `order-export`、`report` と `report-export` など）があると、長いほうの記述が短いほうを引き受けたと誤って判定される。
  その結果、抜けた行が警告なしに消える。
  消費側の呼び出しの項（「この機能から `<リソース slug>` を呼ぶ」）に出てくるリソース slug は、引き受け集合に入れない。
  これはその Issue が引き受ける行ではなく、下記「[横断リソースの呼び出しは消費側の受け入れ条件に届いて初めて引き受けられる](#横断リソースの呼び出しは消費側の受け入れ条件に届いて初めて引き受けられる)」で別の軸として見る項目である

  slug が出てきたことを、引き受けとして数えない。引き受けを述べている項だけを数える。
  受け入れ条件には、その行を除外・参照・言及するだけの文も入る（「`notification-banner` は対象外」「`user` の Issue で実装される」など）。
  出てきただけで数えると、誰も実装を約束していない行が集合の差分から消え、この段が防ごうとしている「症状が緑」の状態そのものを作る。
  数えるのは引き受けの形の項だけである。
  `<slug>` のスイートが新側で green・`<slug>` の未説明の差分がゼロ・`<slug>` を実装する、のように、その Issue の完了の条件がその行の完了を含むと読める項を数える。
  引き受けか除外かを決められない項は、引き受けとして数えず `未対応` として扱い、その文を添えて確認に回す（判定できないときは失敗として扱う）。
  あいまいな文を引き受けとして数えると、抜けた行が確認されないまま消える
- 落ちた行は、母集合から引き受け集合を引いた残りのうち、Issue 列が埋まっている行である（番号はあるのに、受け入れ条件には現れない）。
  記録された番号の本文を取得できなかった行は、落ちた行に数えず、`判定不能` として別に挙げる。引き受けが無いのではなく、確かめられていないからである。
  取得できなかった行を落ちた行に含めると、確かめていない判断で、外向きの本文の追記（下記「[塞ぎ方](#塞ぎ方)」）を提案することになる。
  「落ちた行は無い」と言えるのは、すべての番号の本文を取得できたときだけである。
  判定不能の番号が 1 つでもあれば、落ちた行 0 件を結論にせず、判定不能の番号を挙げて未確定として扱う
- 落ちた部分とは、行は引き受けられているのに、その行が所有するものの一部が、どの受け入れ条件にも名前で示されていない状態である。
  slug の一致だけでは出てこない。受け入れ条件が `/orders` しか名前で示していなくても、`order` は引き受け集合に入り、行の差分から消える。
  そこで、もう 1 段、部分の集合の差分を取る。
  - 部分の母集合は、インベントリがすでに並べている。その行が所有するものを、1 つの軸に絞らずすべて入れる。
    入れるのは、その Issue が作るものと比べるものの単位に限る。
    - 機能行は、「ページ」列のページ、「新規実装 API」列の口、「副作用出力」列のうち比較の対象のもの（スコープ外と記録した出力は除く）
    - 横断 API の行は、「API」列の口
    - バッチの行は、「比較する出力」
    - 部品行（`.replace/components.md`）は、「インスタンス」列のインスタンス（ページ ＋ 論理名）
  - 入力・前提として使うもの（横断 API の行の「参照テーブル」、バッチの行の「入力」）は、部分に入れない。
    これらは `golden-dataset` が投入する側のもので、受け入れ条件の様式（上記「本文に含める内容（共通）」と種類ごとの節）も、本文の対象の記述に置くことしか求めていない。
    部分に入れると、取り決めどおりに書かれた Issue がいつまでも「部分が未対応」になり、不要な本文の編集を促す（投入の抜けは `golden-dataset` の側のチェックが見る）
  - 「その他の Issue（4 種以外）」表の行は、部分を持たない。成果物のディレクトリも、下流のスキルの着手の対象も無く、インベントリが並べる構成要素も無い。
    そのため部分の集合の差分の対象にせず、行の引き受けだけを見る。
    下記の「部分を並べられない行」の規定は、部分を持つ行なのに並べられないときのもので、この種類の行には当たらない
  - ページだけを母集合にすると、ページが含まれている裏で、API や副作用出力がどの受け入れ条件にも入っていない状態が緑になる。
    行の slug でも部分でも差分が出ないので、どこにも赤が出ない
  - 部分の引き受け集合は、その行を引き受ける Issue の受け入れ条件が名前で示した部分（`/orders` / `GET /api/orders` など）と、部分の全体を含むと述べている項が含む部分である。
    個々の名前の列挙だけを求めない。
    共通部品 Issue の受け入れ条件は、「比較の母集合のすべての組み合わせに対応する見本があり、全件を照合した」という形で、インスタンスを並べずに全体を含む
    （上記「[共通部品 Issue](#共通部品-issue)」。母集合から到達できない状態を除く定義も、同じ項にある）。
    この形を名前の不足として扱うと、取り決めどおりに書かれた Issue が毎回「部分が未対応」になり、不要な本文の編集を促す。
    全体を含む項がある行は、その軸の部分を引き受け済みとして数える。軸ごとに見る（ページは全体の宣言、API は個別の名前、という混在もありうる）
  - 差が空でなければ、その部分は落ちた行と同じ抜けとして塞ぐ。列には `#10（未対応: /orders/:id）` のように残す
  - 部分を並べられない行や、受け入れ条件が部分を名前で示していない行は、すべてを含んでいる根拠が無い。
    含んでいるとは判定せず、「要確認」として報告する（判定できないときは失敗として扱う）
- Issue 列が未起票の行は、落ちた行と分けて、未起票のまま別に挙げる。まだ起票していないので、引き受けが無いのは当然である。
  ただし、起票を一通り終えたつもりのインベントリに残る未起票の行は、粒度の判断で他の行に吸収されたつもりになっている候補である。
  「起票の対象から外したのか、まだ起票していないのか」を確認する。落ちた行として扱って勝手に起票しない（起票には承認が要る）
- Issue 番号を共有する行とは、同じ番号が 2 つ以上の行の Issue 列に入っている状態である。
  対象は `.replace/features.md` の機能・横断 API・バッチと、`.replace/components.md` の部品一覧である。
  ファイルをまたいだ共有も数える（部品と機能が同じ番号を持つ形。`parity-component` も、部品行の Issue 番号で `issue-start <番号> --branch-only` を実行する）。
  受け入れ条件が両方の行を引き受けていても、引き受けの差分には出ない。しかし下流は slug ごとにその番号で着手するので、2 行が同じブランチ・PR にまとめられる。
  これは要確認として報告する。塞ぐ方法は受け入れ条件への追記ではなく、行ごとの Issue を起こして、Issue 列を 1 対 1 に戻すことである（起票には承認が要るので、勝手に実行しない）。
  ゴールデンデータセット Issue（ヘッダの項目）と「その他の Issue」表は、下流のスキルの着手の対象ではないので、このチェックの対象にしない
- 重複して引き受けられた行とは、2 つ以上の Issue が、引き受ける行として受け入れ条件に挙げた slug である。
  起票の単位は行で、ページ単位の分割は Issue の中のフェーズで行う（上記「機能 Issue」。下流の `parity-replace` は、行の Issue 番号 1 つでブランチを作る取り決めである）。
  したがって、重複は偶然の重複所有として扱い、どちらが引き受けるかを確定させて、1 度だけ現れる状態にする。
  - ただし、片方の引き受けを外す前に、部分の引き受けを確かめる。2 つの Issue が行の別々の部分を持っているなら、片方を外すと、残った側が含んでいない部分が、どの Issue の完了の条件からも外れる。
    このときは警告なしに減らさず、行の部分をどう 1 つの Issue にまとめるか（またはインベントリの行自体を分けるか）を、「要確認」として報告する
  - 消費側の呼び出しの項に出てくる横断 API のリソース slug は、重複に数えない。
    リソース slug が自分の Issue と消費側の Issue の両方に出てくるのは、呼び出しが消費側に届いている正常な状態である。
    これを重複として 1 つに減らすと、呼び出しの項が外れる

### 横断リソースの呼び出しは消費側の受け入れ条件に届いて初めて引き受けられる

**横断 API Issue が「全機能から使われる」と書いても、消費側の受け入れ条件には入らない。**
消費側の Issue は自分の slug の緑しか見ない。そのため、渡された呼び出しが無いことは、別の slug のスイートが赤いという形でしか現れない。
その赤は、どの Issue の完了の条件にもなっていない。応答が画面にも出力にも出ない呼び出し（画面を開いたときの記録など）では、その赤すら現れない。

- 各横断 API の行について、fan-out に挙げた機能の slug ごとに、その機能の Issue の受け入れ条件に「この機能から `<リソース slug>` を呼ぶ」項があるかを見る。
  無ければ、呼び出しが届いていない状態（列の値は `呼び出し未達`）として、落ちた行と同じように塞ぐ
- 消費側の行が複数の Issue に散っているとき（上記「重複して引き受けられた行」の要確認の状態）は、1 つの Issue に呼び出しの項があることを、行全体が満たされたとは読まない。
  呼び出しの項の無い側が引き受けた部分からの呼び出しは、どの Issue の完了の条件にもなっていない。その呼び出しが画面にも出力にも出なければ、どのスイートも赤くならない。
  行を 1 つの Issue にまとめ直すまでは、「要確認」として報告する（判定できないときは失敗として扱う）
- 消費側の機能が未起票の行は、呼び出しが届いていない状態に数えず、未起票として別に挙げる。Issue が無いので、項が無いのは当然である。落ちた行と同じく、勝手に起票しない
- 消費側の Issue の本文を取得できなかった場合も、呼び出しが届いていない状態に数えず、`判定不能` として残す。どちらも確かめられていないだけで、届いていない証拠ではない
- fan-out が空欄の横断 API の行は、「消費側が無い」ではなく未調査として扱う。0 件を、呼び出しが届いている根拠にしない

### 塞ぎ方

- 落ちた行や、届いていない呼び出しは、既存の Issue の受け入れ条件に足すか、その行のための Issue を起こして塞ぐ。行を消して辻褄を合わせない
- 既存の Issue の本文を書き換えるのは外向きの副作用なので、差分を示して承認を得てから行う。
  本文は、取得した全文に追記してファイルに書き、ファイルで渡す（`gh issue edit <番号> --body-file <path>`）。
  `--body-file` を持つのは `gh issue` / `gh pr` の側で、`gh api` には無い。`gh api` では `-F body=@<path>` か `--input <path>` を使う。
  出典は <https://cli.github.com/manual/gh_issue_edit> と <https://cli.github.com/manual/gh_api> である
- 承認が得られない場合は、編集も起票もしない。利用者が不在（非対話の実行）・応答が無い・応答が承認以外、のいずれもこれに当たる。
  落ちた行と届いていない呼び出しを一覧にし、反映していないことを明示する（起票と同じ規律。下記「[issues モードのフロー](#issues-モードのフロー)」手順 4）

### 結果の記録

突き合わせの結果は、各表の「受け入れ条件」列に書き戻す（`.replace/components.md` は、部品一覧の表の同じ名前の列）。値は次の 5 種類で、書き分ける。

| 値 | 意味 |
|---|---|
| `#<番号>` | その Issue の受け入れ条件が、この行を引き受けている。含まれない部分があれば `（未対応: /orders/:id）` を、届いていない呼び出しがあれば `（呼び出し未達: user）` を併記する |
| `未対応` | 起票済み（Issue 列に番号がある）なのに、どの Issue の受け入れ条件にも現れない（落ちた行） |
| `未起票` | Issue 列が未起票なので、引き受けが無い（突き合わせは済んでいる。落ちた行と分ける） |
| `判定不能` | 本文を取得できない Issue があり、この行の引き受けを確定できない |
| 空欄 | まだ突き合わせていない（この列を持たない版で作られた features.md を含む） |

- この列はチェックの出力であって、引き受けの原本ではない。突き合わせのたびに Issue の本文から取得し直し、対象の行を上書きする。前回の値を根拠に、チェックを省かない
- 列の値を、引き受けの根拠にしない。本文が後で書き換わると、転記した値は警告なしに古くなる。
  判定は毎回、本文との差分で取る（`status` モードもこの列を読まない。[`status.md`](status.md)）
- `未対応` を空欄で表さない。空欄は「まだチェックしていない」という意味である。
  両者を同じ表記にすると、チェックしていないことが、落ちた行が無いことと誤って判定される
- 届いていない呼び出しは、行の引き受けとは別の軸なので、上の値に `（呼び出し未達: <リソース slug>）` を併記する。
  行が引き受けられていれば `#<番号>` と書けてしまい、横断 API の呼び出しがどの Issue の完了の条件にもなっていないことが、列から消えるからである

## features.md の更新は非破壊

**`.replace/features.md` を書き直すときに、すでにある記述を消さない。**
テンプレート（[`../assets/features-template.md`](../assets/features-template.md)）は最初に作るときの雛形であって、更新のときに許される項目の上限ではない。

- `issues` / `setup` の更新は、変える行・列だけを書き換える。全文を作り直して、テンプレートに揃え直さない
- テンプレートに無いヘッダの項目・節・列・行を見つけても、削除しない。意味を判断できないものは、そのまま残す（利用者が意図して足した記録である可能性のほうが高い）
- テンプレートに無い項目を「その他の Issue（4 種以外）」表で表せるなら、削除ではなく、その表への移動を提案し、承認を得てから移す。警告なしに移したり消したりしない
- 旧版のテンプレートから来た「状態」列（上記「Issue の状態は転記しない」）も同じ扱いで、削除を提案し、承認を得てから外す。承認が得られない間は列を残したまま、値を現在の状態の根拠にしない
- 「受け入れ条件」列が無い旧版のテンプレートから来た features.md（と `.replace/components.md` の部品一覧）には、突き合わせの時点で列を足して埋める。
  読む側は、列が無いことを「落ちた行が無い」とは読まない。列が無いのは突き合わせていないだけで、引き受けの証拠ではない。
  `status` モードは列を読まず、毎回 Issue の本文から導出する
- 「要求単位の根拠」列が無い旧版のテンプレートから来た features.md には、元の記述を消さない更新で列を足して埋める（上記「API の形は要求単位を読んでから決める」）。
  列の追加は、この節が禁じる削除に当たらない
- 更新のたびに、ヘッダの `最終更新` を更新する

## issues モードのフロー

1. `.replace/features.md` を読み、未起票（Issue 番号が空）の機能・横断 API リソース・バッチ・その他 Issue を並べる。
   `--feature <slug>...` があればそれで絞り、無ければ対話で選んでもらう。
   未起票の候補をすべて選ぶことをデフォルトにしない（警告なしにすべてを起票の対象にしない）。
   features.md が無い場合は、`setup` が終わっていないとして起票せずに止まり、`setup` の実行を促す
   - 「ページ要素の帰属」表に所有者が空欄の行があれば、候補の slug（そのページに乗る機能）を添えて示し、所有者を確定するよう求める
   - 確定が得られなくても起票は止めず、空欄のまま次に進む。起票の条件にすると、確定できない場（非対話の実行・判断の材料が現行の画面にしか無い場合）で、空欄を仮の値で埋める圧力になる。
     そうなると未確定が消えて、下流が検出できなくなる
   - 確定しなかった行は、その要素が乗るページを持つ機能 Issue の本文に、「配置の所有者が未確定の要素」として書く（下記「機能 Issue」）。
     配置が決まらないまま実装が始まる流れは、そこと `parity-suite` の `gaps.md` で防ぐ
2. ゴールデンデータセット Issue が未起票なら、選択にかかわらず、最初の起票の対象として提案する（すべての前提なので）。
   ただし「その他の Issue」表に、依存順が「ゴールデンデータセットより前」の未起票の行があれば、その行を先に提案する。後に続く本文から、先の Issue 番号を参照できなくなるからである
3. 起票の対象の一覧（種類・slug・タイトルの案・依存関係）と、各 Issue の本文の下書きを示す。
   - 機能 Issue は、ページ一覧で同じページに乗る関係をつながりごとにまとめ、同じページの束の機能を続けて並べて提案する。横断 API などの実際の依存を優先し、束のために順序を逆にしない
   - 提案の順に左から実装すると仮定する。後の slug が green になるたびに、その slug とページを共有する着手済みの slug について、`parity-diff` が 1 回必要になるとして数える。
     同じ 2 つの slug が複数のページを共有しても 1 回と数える
   - 各 slug の再実行の回数と、束の合計を示す。各 slug について、同じページに乗る機能のマスクが最後に外れる再実行を「全面比較」と明記する
   - ページ一覧が導出されていない、または食い違っているなら、回数を作らず「算出不能」として setup に戻す

   そのうえで、対象を選んでもらい、明示の承認を得る
4. **明示の承認が得られない場合は、起票せずに止まる。** 利用者が不在（非対話の実行）・応答が無い・応答が承認以外、のいずれもこれに当たる。
   `gh issue create` を実行せず、`issue-create` にも任せない。起票は外部への副作用なので、承認なしに実行しない。
   非対話の実行では、候補・依存関係・本文の下書きを示す（または保存する）ところで止め、承認を待っていることを明示する
5. 承認の後、1 件ずつ `issue-create` スキルに任せる（本文の下書きは、上記の構成でこのスキルが用意する）。依存順に起票し、後に続く本文から先の Issue 番号を参照できるようにする
6. 起票された Issue 番号を、`.replace/features.md` の該当する表・ヘッダの項目（機能一覧／横断 API／バッチ／その他の Issue／ヘッダのゴールデンデータセット Issue）に書き戻す。
   共通部品 Issue だけは、`.replace/components.md` の「部品一覧」表の Issue 列に書き戻す（上の表の「記録先」列）。
   起票していない行の Issue 列は、「未起票」のまま変えない。書き戻しは上記「features.md の更新は非破壊」に従い、他の記述を巻き込んで作り直さない
7. 起票した Issue の受け入れ条件と、インベントリの行を突き合わせる（上記「[起票の後に行と受け入れ条件を突き合わせる](#起票の後に行と受け入れ条件を突き合わせる)」）。
   - 今回起票した分だけでなく、インベントリのすべての行を母集合にする。今回の起票で粒度が変わり、すでに番号が付いていた行が引き受けから外れることがある
   - 落ちた行や届いていない呼び出しがあれば、承認を得て受け入れ条件に足すか、Issue を起こして塞ぎ、結果を「受け入れ条件」列に書き戻す
   - 重複して引き受けられた行は、部分の引き受けを確かめてから 1 つに確定させる。別々の部分を持っているなら、減らさずに要確認とする
   - 本文を取得できない番号があれば、落ちた行 0 件を結論にせず、判定不能として報告する
8. 重複の確認（既存の Issue の確認）では、ページネーションに注意する。issue-create の側の重複の確認がデフォルトの件数で打ち切る場合に備えて、このモードでも起票の前に全件を確かめる。

   ```bash
   gh api "repos/$OWNER/$REPO/issues?state=all&per_page=100" --paginate \
     --jq '.[] | select(.pull_request | not) | [.number, .title] | @tsv'
   ```

9. 完了したら、起票した Issue の実施に必要な姉妹スキルがインストールされているかを確かめる。
   対象は `golden-dataset` / `parity-suite` / `parity-replace` / `parity-diff` で、共通部品 Issue を起票したら `parity-component` も含む。
   インストールされていなければ、`gh skill install` の手順を案内する
