# 対応範囲（比較・検証の範囲／スキルが行う作業の範囲）

着手の前に、「自分のアプリのどこまでをこのスキル群で検証できるか」「どこからがプロジェクトの側の担当か」を判断するための一覧である。
`setup` の測定（副作用の棚卸し）・戦略の提示・`issues` の起票の範囲で読み、判断に迷ったときもこのファイルを読む。

**一覧はこのファイルで定義する。** 各スキルの `SKILL.md` と `references` は、実行するときの行動（どう記録するか・どこへ差し戻すか）を持つ。
行動は各スキルに、一覧はこのファイルに置くという分担で、どちらの向きにも転記しない。
一覧を各スキルにコピーすると改訂が伝わらず、行動をこのファイルにコピーすると、実行するときに読む場所が 2 つになる。

軸の異なる 2 つの一覧を持つ。2 つを 1 つの表に混ぜない。混ぜると、「対象外」の意味が「比較しない」と「スキルが手を出さない」の間で揺れる。

| 一覧 | 問い |
|---|---|
| [比較・検証の範囲](#比較検証の範囲) | その領域について、現側と新側の結果を比べて合否を出すか |
| [スキルが行う作業の範囲](#スキルが行う作業の範囲) | その作業をスキルが行うか、事前の条件としてプロジェクトの側が済ませておくか |

新しい領域を分類するときは、先にどちらの一覧の話かを決める。同じ題材が両方に行を持つこともある（例: IaC は「比較しない」かつ「付随する差分だけ触る」）。

## 比較・検証の範囲

### 判定の軸（比較・検証）

**現行のアプリを変えずに、現側と新側の結果を決定論的に比べられるか。**

比べるために現行のアプリのコードや構成を変える必要があるもの（ログの挿入・SMTP の迂回・プロキシの挿入）と、比べること自体が現実的でないものは、対象外とする。
対象外は「無いこと」にせず、`gaps.md` に「手動検証が必要」「スコープ外」として記録する。確認済みにしないことが、このスキル群の原則である。

| スクロールバーが場所を取る窓でのページの高さ（`height: 100%` と `100vh`） | 対象 | ヘッドレスの撮影はスクロールバーを隠すので、3 つの比較方法では検出されない。`parity-suite` がスクロールバーを表示し、ページの最小幅より狭い窓で縦と横のはみ出しを測る（`capture_conditions.overflow`）。同じスペックを現側と新側の両方に当てる | `parity-suite` の `references/baseline.md` |
| 採取する環境に依存する一致（フォントなど） | 条件付き | 環境に依存しないフォントスタックにする、利用者の環境でも採取する、`gaps.md` に残す、のどれかにする | `parity-suite` の `references/baseline.md` |
| 書き込みの検証 | 条件付き | 対象の target が書き込みを許可していること（`forbidden_actions` / `seedable`）。許可されていなければ実行せず、未検証として記録する | [`project-config.md`](project-config.md)「実行対象環境」 |
| 後始末できない書き込み（削除の機能が無いなど） | 条件付き | 事前に、残してよいかをユーザーに確認し、「hermetic でない」と明示して一覧にする | `parity-suite` の `references/data-discipline.md` |

## スキルが行う作業の範囲

### 判定の軸（作業範囲）

**その作業をスキルが行うか、事前の条件としてプロジェクトの側（人）が済ませておくか。**

対象外に置く根拠は 2 つある。
1 つは、スキルがセットアップも検証もできないものである（線引きの詳細は [`project-config.md`](project-config.md)「成果物の保存先」「シークレットの扱い」）。
もう 1 つは、測定からは決まらないものである。組織の制約・運用・既存の資産で決まり、スキルが決めると、「測定できなければ停止する」という規律が成り立たなくなる。

この一覧の「対象外」には 3 つの型があり、整っていないときの扱いが違う。混同しない。

- 事前条件型（新側のアーキテクチャの選定、配信型の target を使う場合の IaC / CI-CD）: 「やらなくてよい」ではなく、着手の前に済んでいる必要がある。
  整っていないまま進むと後戻りのコストが最も大きいので、該当するスキルは推測で埋めずに止まる。ただし、前提になる条件は行ごとに違う。
  IaC / CI-CD は、配信型の target を登録する場合にだけ前提になり、`side: new` のローカルの target だけなら、作っていなくても止まらない。
- 禁止型（本番環境への参照・投入、現行のアプリの変更・駆動、出所が分からないデータの投入、足りないものの推測での補完）: 誰かが先に済ませておくものではなく、スキルが恒久的に行わないと決まっているものである。
  指示されても実行せず、止めてユーザーに上げる。
- 利用者の選択に任せる型（成果物の外部での保管、環境変数・シークレットの用意）: 選ぶかどうかは利用者が決める。選んだ場合の用意は利用者の側で、スキルは検証しない。

### 一覧（作業範囲）

| 作業 | 区分 | 条件・補足 | 実行するときの行動（原本） |
|---|---|---|---|
| 受領資産から現行のテスト環境を作り直す | 対象 | 現行の環境が「既にある」か「これから作る」かで分かれる（`current.origin`）。作り直しが要るなら `current-environment-bootstrap` が担い、`replace-strategy` は測定の前に任せる。受領資産の出所と利用の許可を確かめられることが条件である | [`project-config.md`](project-config.md)「現行環境の由来」、`current-environment-bootstrap` の `SKILL.md` |
| 受領資産の足りないものを推測で埋めること（DB の設定のデフォルト値での補完・ドメインの値の推測） | 対象外 | 禁止型。判断できない項目は、デフォルト値や推測で補わず、足りないものとして止め、先方や SME への質問票に回す。推測で作った環境を正解の基準にすると、以降のすべての比較がその誤りを正しいとしてしまう | `current-environment-bootstrap` の `references/schema-restoration.md` / `references/data-semantics.md` |
| 出所や利用の許可が分からないデータの投入 | 対象外 | 禁止型。出所が分からない DB の dump や、本番に由来するかを判定できないサンプルのデータは、投入も参照もしない（意味の読み取りもしない。読み取って転記すれば、実質的に持ち込んだことになる） | `current-environment-bootstrap` の `references/data-semantics.md`「出所と利用許可」 |
| 暫定の起動用のデータをゴールデンデータとして扱うこと | 対象外 | 禁止型。暫定の起動用のデータは、起動・ログイン・画面の探索のための最小限のもので、比較の正解ではない。ゴールデンデータセットは、確かめた意味から `golden-dataset` が別に作る | `current-environment-bootstrap` の `references/provisional-data.md` |
| 新側のアーキテクチャ（骨格）の選定 | 対象外 | 事前に定義されていることが前提である。スキルは確認・記録・参照だけをする。実行基盤と、使うマネージドサービスを含む | [`project-config.md`](project-config.md)「新側アーキテクチャ」 |
| IaC / CI-CD のパイプラインを新しく作ること | 対象外 | 事前の条件である。スキル群に必須の要件ではなく、配信型の target（`develop` / `preview` など）を `targets` に登録する場合にだけ、「動いていること」が前提になる（ローカルの target だけなら要らない） | [`../SKILL.md`](../SKILL.md)「前提」 |
| 既存の IaC への付随する差分（テーブルの追加・ルートの追加など） | 対象 | 新側の実装に付随する差分だけを対象にする。パリティスイートでは検証できないので、敵対的レビューと `verification_commands.full`（`cdk synth` / `terraform validate` など、認証情報やリモートの state を要さない機械的な検証）を通す | `parity-replace` の `SKILL.md`「厳守の制約」 |
| 移行元の静的な資産（画像・アイコン・favicon・ロゴ・図・書体）を新側へコピーするかの方針 | 対象 | `setup` が実装の前に種類ごとに決める（決めるのは人）。比較の範囲とは別の軸である。`url()` で参照する資産の中身が比較の対象外でも、コピーしなければ画面に出ない。再配布してよいかを確かめられない資産は、「実体をコピーする」を選ばない | [`static-assets.md`](static-assets.md) |

## 対象外・条件付きの扱い

- 対象外は、記録して初めて扱ったことになる。`gaps.md`（`parity-suite` が形式を定義する）に理由を付けて残し、`.replace/survey.md` の副作用の棚卸しにも判定を残す。
  これは比較・検証の範囲の対象外が対象である。作業の範囲の対象外は「事前の条件が済んでいるか」の確認で、整っていなければ該当するスキルが止まる。
- 条件付きは、「条件を満たせるか」を実測してから区分を確定する。「満たせるはずだ」では、測っていないのと同じである。
- どちらの一覧にも無い領域を見つけたら、自分で対象か対象外かを決めない。
  まずどちらの軸の話かを決め、その軸で判断できるなら、ユーザーに確認する。確認した結果を、このファイルの該当する一覧に追記する。

## この一覧に到達できないとき

このファイルを読めない環境（インストールされていない・ファイルが移動した）では、対象か対象外かを推測で断定しない。
「確認済み」にはせず、その領域を `gaps` に未検証として残し、一覧の場所をユーザーに確認する。判定できないときは、安全な側（未検証）として扱う。
