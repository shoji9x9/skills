# 構成図の作図ルール

AWS 構成図を、交差が少なく、軸が揃い、ラベルが読める状態に保つための規約である。
一般原則は公開資料に基づき、AWS に固有の事情を補う。図はコード（spec）から生成し、テキストの差分で管理する（GUI は使わない）。
このルールがスキルの中心であり、spec を書くときと図を直すときは常にこの観点で確かめる。

## 一般原則（公開出典）

- エッジの交差を最小にすることを最優先にし、次に屈曲（bend）を減らすこと、直交させること、ノードを重ねないことを重視する。
  読みやすさに最も寄与するのは交差の最小化である。
  出典は [Metrics for Graph Drawing Aesthetics](https://www.researchgate.net/publication/222546202_Metrics_for_Graph_Drawing_Aesthetics)。
- 直交の線（orthogonal routing）では、エッジを水平と垂直の線分だけで描き、ノードとラベルを避けて通す。
  複数の線が同じ通り道を使うときは、一定の量ずらして重なりを防ぐ。
  出典は [yWorks – Drawing Orthogonal Diagrams](https://www.yworks.com/pages/drawing-orthogonal-diagrams)。
- 矢印は流れの向きを表す。性質の違う線（認証・非同期）は破線で区別する。
  出典は [C4 model – Notation](https://c4model.com/diagrams/notation)。
- AWS 公式アイコンには、ラベルを必ず付ける。線は直線を優先し、余白を取り、アイコンのバージョンを混在させない。
  出典は [AWS Architecture Icons](https://aws.amazon.com/architecture/icons/) と [AWS diagram guidelines](https://dev.to/aws-builders/aws-architecture-diagrams-guidelines-595d)。

## 本スキル固有のルール

spec を書くときに守る具体的な規約である。
描画エンジン（`diagram-engine.mjs`）は、重複したエッジ・直交していない線・アイコンのパスの制限をエラーで止め、交差の飛び越しとエッジのラベルの位置を自動で決める。
図の形から計算できるそのほかの規約は、生成の後に検査（`diagram-checks.mjs`）で確かめる（下の「生成と品質確認」）。

- グループの枠（`groups`）を互いに重ねない。各ノードは、所属するグループの枠の内側に、アイコンの半分（32px）以上の余白を取って収める。
- ノードを軸の方向に揃える。同じ層のノードは x か y を共有させて格子に乗せる（例: 永続層は x を 1 つに揃えて縦一列に並べる）。
- 依存先のグループは、アプリ層からの線が関係の無いグループを貫かない位置に置く。
  例えば、外部 API を永続層の上の段に積み、アプリ層から外部 API への線が永続層をまたがないようにする。
- エッジは直交させる。
  - `waypoints` は前後の点と x か y のどちらかを共有させ、斜めの線を作らない。
  - 直線で結べるものは `waypoints` を付けず、自動の L 字に任せる。屈曲は、他のノードやラベルを避けるとき、交差を避けるときだけ足す。
  - 斜めの区間は `diagram-engine.mjs` が検出してエラーで止める（目視では見落としやすいので、エンジンで確かめる）。
  - 両端の区間も直交のチェックの対象になる。ノードの側の接続点は、相手の側の `waypoint` に合わせて辺の上を動く。
    ただし、辺の範囲（中心から ±20px）を超える指定は丸められて斜めになる。
    最初と最後の `waypoint` は、接続先のノードの中心と x か y を ±20px 以内で揃える。
- エッジのラベル（`label`）は、屈曲点を避けて自動で配置される。
  - 中央が屈曲点に当たるときは、隣の直線区間の中点へ寄る（角をラベルの背景で隠さないため）。
  - 位置を指定したいときは、`labelAt: [x, y]` で中心の座標を直接指定する。
  - ラベルを動かすために `waypoints` を足さない。線の形が変わり、座標を調整するたびにラベルの位置を確かめ直すことになる。
- ノードの間の矢印は最大 1 本にする。同じ `from`→`to` を重複させない（`diagram-engine.mjs` の重複チェックが、違反したときにエラーを投げる）。
- 1 つの辺に複数の線が入ってよいが、入る位置をずらして区別する。
  - 複数の依存元が同じ先に接続するときは、入る辺を変えるか、同じ辺でも入る y や x をずらす。
  - アンカーは最後の `waypoint` の座標に沿って辺の上の位置を決めるので、`waypoint` で入る位置を制御する。
  - 1 点に集めると、どの線がどこから来たかが分からなくなる。
- 多くの線が集まる領域は、共有の幹線の x にいったん寄せてから分岐させ、平行な線は最低 20px 離す。
  幹線で関係の無いアイコン（中心から ±32px）を貫かない。
- 交差は飛び越し（line jump）で示す。
  まず配置と入る位置で交差を減らす。残った交差は、水平線の側に小さな半円のアーチ（∩、上に膨らむ）を描き、交わっているが接続していないことを示す。
  アーチは `diagram-engine.mjs` が自動で付ける（水平線が、他のエッジの垂直線を飛び越す）。
- 線をグループの枠線と重ねない（枠線に沿わせない）。枠をまたぐのは直交の通過だけにし、枠線と同じ x や y に平行な線を置かない。
- キャンバスの端に余白を取る。最も外側のグループの枠がキャンバスの端に接しないよう、`W`・`H` に余白（おおむね 50px 以上）を持たせる。
- ラベル（`lp`）は、線の出ていない辺（top・bottom・left・right）に寄せる。ラベルを置いた辺に線を引いたら、`lp` を別の空いた辺へ移す。
- アイコンは、AWS 公式（`aws-icons/`）と AWS 以外（`browser`・`internet` など）を使い分ける。
  取得の方法と出典は [icons.md](icons.md) にある。バージョンを混在させない。

## 生成と品質確認

spec を編集し、図を生成し直し、検査を通してから PNG にラスタライズして目で見て確かめ、座標と `waypoints` を細かく直す。これを繰り返す。
画像を読むツールは SVG を直接描画できないので、必ず PNG への変換を挟む。

1. `render-diagram.mjs` で SVG を生成する。生成した後、下の表で「検査」とした観点を検査する。
   違反があれば、環境・観点の記号・場所（エッジの区間の座標、ノードの id、グループのラベル）を出して 1 で終える。
   SVG は違反があっても書き出すので、違反の場所を PNG で見られる。
2. 違反が 0 件になるまで、座標か `waypoints` を直して生成し直す。違反が残ったまま、目で見て合格にしない。
3. PNG にして、検査で測れない見た目を目で見て確かめる。
4. 報告では、検査に通ったこと（違反 0 件）と、目で見て確かめたことを分けて書く。

```bash
cd docs/diagrams   # 図ディレクトリ（$SKILL は本スキルの導入先）

# 1. SVG を生成し、検査する（既定=全環境。環境選択は environments.md を参照）
node "$SKILL/scripts/render-diagram.mjs"

# 2. 違反が 0 件になったら、PNG にラスタライズ（出力パスが表示される）
node "$SKILL/scripts/preview-diagram.mjs" prod
node "$SKILL/scripts/preview-diagram.mjs" local
```

確認の観点と、それぞれの確かめ方は次のとおりである。
検査の判定はエンジンと同じ座標（アイコンは中心から ±32px の矩形）で計算し、違反を出すだけで配置は直さない。

| 観点 | 確かめ方 | 検査が違反とする形 |
| --- | --- | --- |
| (a) グループの枠とノードが重なっていない | 検査 | ノードのアイコンが枠線にかかる。または、枠の内側にあって枠線との余白が 32px 未満 |
| (b) 線が関係の無いアイコンを貫いていない | 検査 | 線の区間が、そのエッジの端点でないノードのアイコンの内側を通る（斜めの線はエンジンがエラーで止める） |
| (c) 平行な線が重なっていない（最低 20px 離れている） | 検査 | 別のエッジの平行な区間が、20px 未満の間隔で並ぶ。幹線（端点を共有するエッジが同じ座標で重なる区間）は除く |
| (d) 線がラベルを貫いていない | 検査 | 線の区間が、ノードのラベルか、他のエッジのラベルの矩形を通る。幹線に沿って通り、ラベルの中心が幹線の上にある形は除く。ラベルの幅はエンジンの概算で、実際の幅はフォントで変わる |
| (e) 矢印の向きが流れ（`from`→`to`）と一致している | 確かめない | エンジンは矢印を必ず `to` の側の端に描くので、spec の書き方で崩れない |
| (f) ノードの間の矢印が最大 1 本で、同じ辺に入る複数の線が位置で区別できる | 検査 | 同じ `from`→`to` の重複は、エンジンがエラーで止める。ノードに入る線の端が、同じノードの他の線の端と 13px（矢印の頭の幅）未満 |
| (g) 線が、関係の無いグループを貫いていない | 検査 | 線の区間が、どちらの端点のノードも含まないグループの内側を通る（アプリ層からの線に限らない） |
| (h) 線がグループの枠線と重なって（沿って）いない | 検査 | 線の区間が、枠線と平行に 20px 未満の間隔で並ぶ |
| (i) 最も外側の枠とキャンバスの端の間に余白がある | 検査 | グループの枠とキャンバスの端の間が 50px 未満 |
| (j) 交差点に飛び越し（line jump）が付き、接続と区別できる | 検査 | 別のエッジの線が、飛び越しの付かない形で接する（T 字、屈曲点が他の線に乗る、自動の L 字が線を分けた点で交わる）。幹線の端（線が幹線に寄る点と、幹線から分かれる点）は除く |

目で見て確かめるのは、検査で測れない見た目である。
例えば、配置の釣り合い、ラベルの文言と折り返し、淡色（`dim`）と通常の色の区別、アイコンの取り違えを見る。

## 座標の決め方（実務のコツ）

- 層ごとに基準の線を決める。アプリ層は y を数本（例: 380 と 540）に、永続層は x を 1 本に揃えると、格子に乗って交差が減る。
- 幹線を先に引く。多対多で集まる領域（例: アプリ層から永続層）では、まず縦の幹線の x を 2 本（依存元ごと）決め、そこから各ノードへ分岐させる。幹線どうしは 20px 以上離す。
- 入る y をずらす。同じノードの同じ辺に複数の線が入るときは、最後の `waypoint` の y を少しずつ変えて、辺の上で入る点を散らす。
- 外へ向かう線は、層の外周から出す。外部 API へ向かう線は、関係の無いグループの上か下の余白（グループの間の隙間）を通してから、目的地へ寄せる。
