# 記録と集計の取り決め

`.agent-usage/` の記録の構成、行の種類、費用の決め方、稼働状況（稼働中の時間と、分類した停止の時間）を定義する。

## ファイルの構成

```text
.agent-usage/
  config.json                                   リポジトリの設定（setup.md「リポジトリの設定」）
  records/
    <person-id>/branches/<UTC の時刻>-<ブランチ>.csv   ローカルのログ・人の活動からの行（ブランチごとに 1 ファイル）
    _github/<person-id>/<UTC の時刻>-<ブランチ>.csv    GitHub から取った行（CI・レビュー・取得した期間。ブランチごとに 1 ファイル）
  report/<yyyyMMdd>/                                  report の結果（index.html・usage.csv・intervals.csv・reviews.csv）
```

- 時刻は、そのブランチで初めて collect した時刻である。`<ブランチ>` は、ブランチの名前の `/` などを `-` にした形（detached なら `detached`）
- 英数字・`.`・`_`・`-`・`/` 以外の文字（日本語など）を含むブランチの名前は、その形の後ろに名前のハッシュの先頭 8 文字を足す。別のブランチと同じファイル名にならないようにするためである
- collect は、今のブランチのファイルだけを変える（既存の行の後ろに足す）。そのブランチのファイルを書くのはそのブランチだけなので、並行するブランチで記録しても、merge で競合しない
- ブランチのファイルがデフォルトブランチ（`origin` の追跡ブランチ）に既に入っていれば（squash merge の後に同じブランチで作業を続けた場合）、そのファイルには足さず、新しいファイルを作る。
  足すと、デフォルトブランチを取り込むときに add/add で競合するからである。`origin` を fetch する前に足した分と、リモートの名前が `origin` でない場合、`origin/HEAD` が無くデフォルトブランチが `main`・`master` 以外の場合は、この判定に当たらない
- 同じ名前のブランチを複数の clone（別のマシン）で記録すると、同じファイルの後ろに両方が足すので、pull で競合しうる。detached HEAD の手動の collect も、すべて `detached` の 1 つのファイルに足す。
  `/` と `-` だけが違う名前（`fix/x` と `fix-x`）や、大文字と小文字だけが違う名前も、同じファイル名になる（並行して使うと競合しうる）
- 同じ worktree で collect を同時に 2 つ実行すると、片方の行が書かれないことがある。書かれなかった行は、次の collect で書く
- 古い形のファイル（collect 1 回につき 1 ファイルの `<person-id>/<時刻>-<Issue 番号>.csv`・`_github/<時刻>-<person-id>.csv`）は、そのまま残して読む。移したりまとめたりしない
- PR の差分で記録のファイルを折りたたむには、`.gitattributes` に `.agent-usage/records/** linguist-generated=true` を置く（[`setup.md`](setup.md)）
- すべてのエージェントとセッションの行を、1 つのファイルにまとめる。どのエージェントの行かは `agent` 列で分かる
- ログの解析の結果（セッションの要約）のキャッシュは、git の共通のディレクトリの `agent-usage/cache.json` に置く。消しても結果は変わらない
- Hook と collect は、その時点の worktree のパスを git の共通のディレクトリの `agent-usage/worktrees.json` に足していく。
  Claude Code のログは作業したパスごとのディレクトリに分かれ、どのリポジトリのものかを示す情報を持たないので、削除した worktree のログはこのパスから探す。
  Hook も collect も一度も実行しないまま削除した worktree のログは、探せない

## 行

列の順は `scripts/lib/rows.mjs` の `COLUMNS` で定義する。
識別の列（`key`・`kind`・`observed_at`・`person`）、出所の列（`agent`・`session`・`subagent`・`model`）、時刻の列（`start`・`end`・`tz`）を持つ。
ほかに、作業の列（`branch`・`issue`）、トークン数の 5 列と `messages`、費用の列（`cost_usd`・`cost_source`）、`wait_ms`・`detail`・`retracted` を持つ。
`retracted` の無い前の版の記録も、空欄として読む。
時刻はすべて、末尾が `Z` の ISO 8601（UTC）で書く。`tz` は、その行を日付に切るときに使うタイムゾーンである。
`usage` は、その人のタイムゾーン（`tz`）の正時で区切り、区切りの開始時刻で日付に切る。
オフセットが 30 分・45 分のタイムゾーン（`Asia/Kolkata` など）でも、日付の境目をまたがない。
整数時間のオフセットのタイムゾーンでは、UTC の正時と同じ区切りになる。
`branch` は、Claude Code ではログの行ごとのブランチを使う。
1 時間の途中でブランチを切り替えたら、`usage` の行をブランチごとに分け、切り替えた後の応答を切り替えた後のブランチに数える。
モデルごとに、その 1 時間で最初に応答したブランチの行は、ブランチで分けない場合と同じ `key` にする。
ほかのブランチの行は、`key` の末尾に `:<ブランチ>` を足す。
Codex のログはセッションの開始時のブランチ（`session_meta`）しか記録しないので、セッションの途中でブランチを切り替えると、後の利用も開始時のブランチに数える。

| `kind` | 内容 |
| --- | --- |
| `usage` | セッション・モデル・1 時間・ブランチごとのトークン数と費用 |
| `run` | 1 回の指示の稼働の区間。`wait_ms` はその中の外部待ち |
| `human-wait` | 人を待った区間（人への質問・人が判断した権限の確認） |
| `prompt` | 人の指示の時刻 |
| `activity` | 人の活動の時刻（このマシンの reflog に残った人の commit・GitHub での自分のレビューとコメント） |
| `ci` | GitHub Actions（設定で有効にしたら外部の CI も）の実行の区間 |
| `review-wait` | レビューの依頼（`@codex review` のコメントを含む）から、同じツールのレビューが届くまでの区間 |
| `review` | PR のレビュー 1 件、または自分の Actions で実行したレビューの使用量 |
| `billing` | 課金 API から取った日別の実額 |
| `coverage` | GitHub の情報を取得した期間と、その成否（`ok` か `failed:<段>`） |

### 重複の扱い

`key` が行の同一性である。同じ `key` の行が複数あれば、report は `observed_at` の最も新しい行を使う。
後の collect ほど多くのログを見ているからである（ログは増えるだけで、一度見た分は減らない）。
collect は、既に記録した内容と同じ行を書き直さない。

collect が重複を除くために読むのは、ファイル名の時刻か最後の行の `observed_at` が 60 日（GitHub を初めて取る範囲と同じ）より新しいファイルと、今のブランチのファイルだけである。
ブランチのファイルの名前の時刻は初めて書いた時刻なので、後から足した行は最後の行で見る（collect は行を後ろに足すので、最後の行が最も新しい）。
最後の行はファイルの末尾だけを読んで確かめる。ファイルの更新時刻は、clone や worktree の作成ですべて今の時刻になるので使わない。
読む行数を記録の総量に依らず一定にするためである。
範囲より古い開始時刻の行は、読んだ記録に同じ `key` が無ければ書かない。範囲の外のファイルにあって読んでいないので、書くと重複するからである。
ただし、この clone でこの人が範囲の中に collect していないとき（久しぶりの collect や初めての collect）は、記録の全体を読み、記録していない行をすべて書く。
最後に collect した時刻は、git の共通のディレクトリの `agent-usage/last-collect.json` に人ごとに残す。
記録の行の有無では決めない。別のマシン（clone）の行が範囲の中にあっても、このマシンのログにある古い行は、まだ書いていないことがあるからである。
このファイルが無いとき（この版に更新した後の最初の collect・新しい clone・ファイルを消したとき）も、記録の全体を読むので、記録済みの行を重ねて書かない。

範囲の上限による制限は次のとおりである。

- merge しなかったブランチにだけ書いた、範囲より古い開始時刻の行は、後のブランチでは書かない（この clone は範囲の中で collect しているため）
- 範囲より古い開始時刻の行は、料金表の更新などで内容が変わっても書き直さない（範囲の外のファイルにある前の値と比べられないため）
読まなかったファイルと同じ `key` の行を書いても、report は `key` で 1 行にまとめるので、集計の結果は変わらない。

並行するブランチは、お互いの記録を見られないので、同じ行を両方で記録しうる。merge した後も、report は `key` で 1 行にまとめる。

Claude Code は、セッションを別のセッションに引き継ぐとき（バックグラウンドへの移行など）に、元の履歴の行を新しいセッションのファイルにコピーする。
`key` はセッションを含むので、collect は行を作る前に、セッションをまたいで同じ応答（message id）を 1 つのセッションにだけ数える。

- 数えるのは、最初の時刻が早いセッション、同じなら最後の時刻が早いセッション（引き継いだ元）である。
- 数えなかった側では、コピーした範囲（外した応答の後の、最初の人の指示の手前まで）の指示・完了・待ちも外す。
- 決めた結果は、git の共通のディレクトリの `agent-usage/claims.json` に残す。元のセッションのログが後で消えても、コピーした側で数え直さない。
  残すのは、collect が両方のログを同時に見た応答だけである。元のログが消えた後に初めてコピーを見た応答は、二重に記録しうる。
  逆に、コピーした側を先に記録した後で元のセッションのログが見つかると、コピーした側の記録済みの指示・稼働・待ちの行は打ち消しの行で打ち消すが、使用量の行は残る（次の「打ち消し」）。
  キャッシュと違い、このファイルを消すと、元のログが消えた応答を二重に記録しうる。

### 打ち消し

記録は追記だけで書くので、記録済みの行は、同じ `key` で `retracted` が `1` の行（打ち消しの行）を後から足して打ち消す。
report は、`observed_at` の最も新しい行が打ち消しの行なら、その `key` を数えない。
打ち消しの行の `observed_at` は、元の行より後にする（元の行を書いたマシンの時計が進んでいても、打ち消しの行を最も新しくする）。
後で同じ `key` の行をまた作れば、その行が新しくなるので数える。

collect が打ち消すのは、ログが今もあるセッションの行のうち、次のものである。

- `run`・`human-wait`・`prompt`（メインのログだけから作る）: 今の collect で作らなくなった行。重複を除いた後のコピーした側の行が当たる
- cost-state から作った使用量の行（時刻を `key` に持たない）: 今の collect で作らなくなった行。そのモデルが応答に現れて、応答から数えるようになった行が当たる
- `usage`: 今の collect で作らなくなった行（タイムゾーンを変えた後の、前の区切りの行など）。
  使用量はメインのセッションにまとめたサブエージェントのログも材料にするので、セッションとモデルごとに、次をすべて満たすときだけ打ち消す。
  作り直した行がすべて書かれるか記録済みであること（範囲の下限より古くて書かれない行が無い）と、作り直した合計が記録済みの合計より少なくないこと（ログが欠けていない）。
  満たさないときは前の区切りの行を残し、それと時間が重なる新しい行を書かない（両方を数えて二重にしないため）

次の行は打ち消さない。

- ログが消えたセッションの行（作れないだけなので）。メインのログが消えてサブエージェントのログだけが残ったセッションも、同じに扱う
- サブエージェントとして記録した行（サブエージェントのログだけが先に消えることがある）
- 開始時刻が書く範囲の下限より古い指示・稼働・待ち・cost-state の行（範囲の外の行は書き直さないので、打ち消すと消えるため）。使用量の行は、上のまとまりの条件で判定する
- 読む範囲の外のファイルにある行と、まだ取り込んでいない別のブランチのファイルにある行（取り込んだ後に二重に数えうる）

記録の `person` は、`aliases` で今の ID に読み替えてから判定する。
`retracted` の値は、空か `1` だけを受け付け、ほかの値の記録は読むときに失敗にする。
見出しの列が今と違うファイル（前の版が書いたファイル）に足すときは、今の列で全体を書き直す（デフォルトブランチを複数の clone で記録すると、競合しうる）。

打ち消しの行は、`retracted` の列を知らない前の版のスキルでは、普通の行として数えられる。
記録を共有する人は、全員がこの版以降のスキルで report を実行する。
夏時間の変化が 30 分のタイムゾーン（`Australia/Lord_Howe`）では、変わる前後の区切りが重なることがある。

## 費用

| エージェント | 決め方 | `cost_source` |
| --- | --- | --- |
| Claude Code | ログの `cost-state`（Claude Code 自身が計算したセッションの累計）。その時刻までの応答の費用の合計を、モデルごとに `cost-state` の値に合わせる。各応答への配分は、単価表で計算した費用の比（単価が無ければトークン数の重み付きの比）で行う | `log` |
| Claude Code（`cost-state` より後の応答・`cost-state` の無いセッション） | トークン数 × 単価表 | `repo` か `bundled` |
| Codex | トークン数 × 単価表 | `repo` か `bundled` |
| 単価表に無いモデル | 費用を空欄にし、トークン数だけを記録する。単価を足して report を実行し直すと、集計に入る | `unknown` |

- 単価表は、リポジトリの設定の `pricing`、同梱の `assets/pricing.json` の順に探す。モデル名の末尾の `[1m]` と `-YYYYMMDD` は除いて引く
- `cost-state` は、transcript に残らない呼び出し（自動モードの分類・要約など）の分も含むので、transcript だけで計算した値より大きい。
  応答の記録の無いモデルの分は、`cost-state` の時刻の `usage` の行にまとめる
- Codex の `input_tokens` はキャッシュに当たった分を含むので、`input_tokens` 列にはそれを引いた値を書き、キャッシュの分は `cache_read_tokens` 列に書く

## 稼働の区間（run）

- 始まり: 人の指示、または人を待った区間の終わり
- 終わり: 次の区切り（人の指示・人を待った区間の始まり）の前の、最後の応答の完了
- 自動の再開（バックグラウンドの処理の通知・予約した再開・他のセッションからの連絡）では区切らない。完了から再開までを、その run の外部待ち（`wait_ms`）として数える
- 応答の途中の人の指示（処理中に追加で送った指示）は区切らない
- 人を待った区間は、ログの `permissionDecision.source` が `user_` で始まる権限の確認と、人に質問するツール（Claude Code の `AskUserQuestion`・Codex の `request_user_input`）である
- ログの終わりで応答が完了していない run は、ログの最後の時刻までとし、`detail` に `open` を付ける。次の collect で書き直される
- サブエージェントのログは使用量だけを数え、run を作らない

## 稼働状況

report は、人ごとにすべてのセッション・エージェントの run を合わせる。合わせた区間を稼働中、その隙間を停止とし、2 つを合わせて稼働状況と呼ぶ。
report の HTML は、run を「指示」と表示する（指示の数、1 回の指示で動き続けた時間）。

- 稼働中は、run の中の外部待ち（`wait_ms`）を含む。同じ人の run が重なった時間は 1 回だけ数える
- 人ごとの表、Issue ごとの表、上部の稼働状況、日別と時刻ごとのチャートは、この定義の稼働中を出す。どれも合計が一致する
- Issue ごとの表は、人ごとの稼働中を Issue に配る。同じ人が同時に複数の Issue の run を動かした時間は、その Issue の数で等分する
- 期間の終わりは、人ごとに、その人のタイムゾーンでの `--until` の日の終わりにする。行を期間で絞るのも行のタイムゾーンなので、費用・指示の数・稼働中・停止が同じ期間を数える
- intervals.csv の `active_minutes` は、run の長さから外部待ちを除いた値で、稼働中とは別の値である

### 停止の分類

停止の各部分を、次の表の上から順に当てはめ、最初に当たった分類にする。

| 分類 | 表示 | 条件 |
| --- | --- | --- |
| `reviewing` | 確認中 | 人の活動（`prompt`・`activity`・`human-wait` の終わり）の前後 `activityWindowMinutes` 分 |
| `ci-wait` | CI 待ち | 停止の直前に動いていたブランチの CI が実行中 |
| `review-wait` | レビュー待ち | 停止の直前に動いていたブランチの PR のレビューを待っている |
| `unknown` | 判定不能 | GitHub の情報を取得していない期間（`coverage` が `ok` でない） |
| `idle` | 未活用 | どれにも当たらない |

- 停止は、期間の最初の run の始まりから、期間の終わり（その人のタイムゾーンでの `--until` の日の終わりか、report を実行した時刻の早い方）までの隙間である。
  その人が最後に記録した時刻（`observed_at`）より後は数えない。稼働中も、期間の終わりより後は数えない
- 画面を読むだけの確認のように、記録に現れない人の活動は数えられない。その時間は、近くに活動が無ければ「未活用」になる
- collect が GitHub を取得するのは、初めての取得では最大 60 日前から、以降は最後に成功した取得（`coverage` が `ok` の行）の終わりの 1 日前からである。失敗した期間は、次の collect が取得し直す
