# 文書に載せる粒度と、文書の階層

エージェントが読む文書（`AGENTS.md`・`CLAUDE.md`・`SKILL.md`・`skills/*/references/`・`.agents/rules/`・`docs/`）には、エージェントが正しく行動するために欠かせない情報だけを載せる。
網羅するために書くのではない。

- 網羅するための説明、読み手のいない節、他の文書と重複する内容は置かない。
- 詳細は `docs/` や `references/` に置き、リンクで参照する。
- 重複すると二重に管理することになり、一方が古くなる。原本を 1 か所に置き、他からは参照する。
- 「原本は〜」と書いた内容を、その直後に全文で書き直さない。原本を示すのは参照のためで、転記してよい理由にはならない。
  転記したくなったら、原本の側に「ここへ転記しない」と書き、参照する側には要約と原本の節名だけを置く。
  安全のための確認や選び方の規則のように複数のスキルが従う規約は、特にこう書く。食い違うと、スキルごとに確認の内容が変わってしまう。
- 追記する前に、「エージェントがこれを知らないと、誤った行動を取るか」を考える。取らないなら載せない。コンテキストを圧迫しないためである。

## 文書の階層（Tier）

文書を 4 つの階層に分け、置き場所と参照の向きを決める。どのファイルがどの階層かは次の表で決める。

<!-- doc-tiers:begin（scripts/gates/doc-tiers.json から scripts/gates/check-doc-tiers.js --fix で生成する。手で直さない） -->

| Tier | 文書 | 置くもの |
| --- | --- | --- |
| 1 | `AGENTS.md`、`CLAUDE.md`（`AGENTS.md` を読み込むだけ）、`.github/copilot-instructions.md`（`AGENTS.md` を参照するだけ） | リポジトリの目的と、作業内容に依らず常に守る原則・規約の要約 |
| 2 | `.agents/rules/**`、`docs/**`、`skills/**`、private skill（`.agents/skills/<name>/` のうち `.private-skill` を持つもの）、`.textlint/word-list.md`（`.textlint/words.json` から生成する）、`README.md` | 特定の作業で守る規約・手順と、スキル |
| 3 | `evals/*/README.md`、コードコメント（設定ファイルのコメントを含む） | テストの設計と、実装の説明 |
| 4 | `.kaizen/**`、`tests/` の結果、Issue・PR | 経過と判断の記録（追記していく） |

階層の外に置く文書: `evals/*/fixtures/**`（eval の入力）、`.github/ISSUE_TEMPLATE/**`（Issue のテンプレート）。

<!-- doc-tiers:end -->

コードと設定の値そのものは階層の外に置く。文書がスクリプトや設定ファイルの名前・パスを挙げるのは、案内として書いてよい。
インストール済みのスキルのコピー（`.agents/skills/<name>/`）とエージェント用のリンク（`.claude/`）は `skills/` と同じ中身なので、階層に数えない。

- 上位と下位の記述が食い違ったら、上位に従い、下位を直す。
- 上位の文書は下位の文書を参照しない。ただし「詳細は X」「参照ルールガイド」のように、どこに何があるかを示す案内だけは書いてよい。
  規則の中身を下位に任せる書き方（「原本は docs/... にある」）や、下位の内容を前提にした書き方はしない。
- `AGENTS.md` が `@path` で取り込む文書（Claude Code がセッション開始時に読み込む）も、階層は元のままにする。
  取り込みは案内と同じに扱い、`AGENTS.md` だけを読むエージェント（Codex など）にも要点が届くよう、要点は `AGENTS.md` に書く。
- 同じ内容を複数の文書に書かない。1 か所に書き、他からは参照する。
- 作成日、「現状は」「当面」のように時間がたつと正しくなくなる記述を Tier 1〜3 に書かない。経過は Tier 4 に追記する。
- 配布するスキル（`skills/`）は配布先で単独で動く。階層とは別の制約として、このリポジトリの他の文書を参照せず、必要なものは同梱する。

参照の向き・リンクと節名の実在は `scripts/gates/check-doc-refs.js`、時間がたつと正しくなくなる記述は `scripts/gates/check-time-sensitive-prose.js` がチェックする。

## 重複を原本への参照にまとめるとき

重複した文字列を消すだけでは終わらない。転記は重複であると同時に、原本を読めないときの代わりや、規則どうしをつなぐ役目も持っていることがある。
転記を消したら、消した文字列だけを見て終えず、次の 3 点を確かめる。

1. 規則が別の形で書き直されて残っていないかを探す。箇条書きだけでなく、表のセル・脚注・短縮した形も対象にする。
   文書の形で転記かどうかを判断せず、規則の内容が書き直されているかで判断する。
   同じファイルの中で「ここへ転記しない」と書いたら、まずそのファイル自身を確かめる。
2. 原本を読めないときの分岐を、参照する側に置く。安全のための確認（ガードレール・停止条件）の転記を消すなら、参照先を読めない場合は従わずに止まる指示を残す。
   この指示は原本自身には書けないので、参照する側が持つ。
3. 一般の規則と、個別の条件とのつながりを書く。原本から個別の事情（スキル名・例外の条件）の列挙を消すなら、「個別の条件を持つ側の規定に従う」ことを原本に残す。
   そうしないと、どの規則にも属さない条件が残る。

## 他のスキルの原本を指すときは、指示語を使わずスキル名を書く

「同スキルの」「本スキルの」「同ファイルの」と書くと、読み手はそのファイルが属するスキルのことだと解釈する。
姉妹スキル（`replace-strategy`・`parity-*` など）は `references/` の構成が対称で、ファイル名も似ている。読み違えると、存在しないパスを探すことになる。

- 原本への参照は、1 行で完結させる。直前の文でスキル名を挙げていても、繰り返して書く。
  例: 「原本は同スキルの `references/baseline.md`」ではなく、「原本は `parity-suite` の `references/baseline.md`」と書く。
- 指示語を使ってよいのは、同じファイルの中の別の節を指すときだけである。

## 複数の文書に同じ取り決めを足すとき

語句をそろえるだけでは足りない。書く前に、足す先ごとに親の見出しと前後の構造を確かめる。

- 番号付きのリストなら、番号と、その番号を参照しているすべての箇所を同じ変更で直す。
  箇条書きで割り込ませると番号が飛び、他から番号で参照している箇所が別の項目を指す。
- 順序のある手順なら、その順序の理由と停止条件まで書く。なぜその位置なのかが書いていない項目は、次に編集する人に並べ替えられる。
- 足す先ごとに、番号の参照・表の列・手順の前後関係という、その場所の取り決めがある。
  語句がそろっていても、それを変えてしまうと手順が成り立たなくなる。

このルールは、そもそも載せるか、どの粒度で載せるかを扱う。どこに置くかは、別の基準で決める。
