# チェックを作る前に、効果と費用を書く

新しいチェック（pre-commit・CI・Hook）は、作り始める前に効果と費用を Issue か PR の本文に書き、見合うときだけ作る。
仮想の懸念からチェックを作り、レビューが判定の抜けを指摘するたびに例外と分岐を足すと、効果に比べて費用の大きいチェックが残る。

## 作る前に書く効果と費用

効果として、次の 2 つを書く。

- 実際に起きた誤りの記録（Issue・PR・kaizen の学び）と、同じ種類の誤りが繰り返されているか。記録が無く、起きうると考えただけなら、そう書く。
  記録が 1 回だけなら、チェックを作らずに規約の追記で閉じることを基本にする。
- チェックが無いときに、その誤りが起きやすいか。頻度と、ほかに気付く手段（レビュー・CI や実行時のエラー）があるかを書く。

費用として、次の 3 つを書く。

- 例外の一覧（免除・対象外のファイル）が要るか
- 判定する対象の書き方（表記・構文・入力の形）の数だけ、分岐が要るか
- 実行時間。pre-commit と Hook は毎回実行されるので、特に書く

## 判断

効果が小さいか、費用が効果に見合わないときは、チェックを作らずに規約の追記（`AGENTS.md`・rule・`docs/`）で終える。
追記で終えたことと、その理由を Issue か PR に残す。

チェックを作ると決めたら、`state-space-and-mutation-proof.md` の手順で入力の状態を列挙してから書く。

## レビューが判定の抜けを続けて指摘したとき

チェックを作る PR で、レビューが 3 回続けて判定の抜け（扱っていない書き方・入力の状態）を指摘したら、3 回目の指摘を直す前に利用者に確かめる。
確かめるのは、チェックをやめて規約の追記に切り替えるかである。
利用者に確かめられない実行（自律実行のループ、`pr-finalize-loop` の `--defer-decisions` など）では、3 回目の指摘を、影響が大きく後で覆しにくい指摘として扱い、直さずに判断待ちとして残す。
抜けの指摘が続くのは、判定する対象の書き方が、費用を見積もったときより多いからである。

`state-space-and-mutation-proof.md` の「入力を構造化するか、自由記述を解析するか」にある、同じ種類の誤りを 3 回以上指摘されたら入力の形式を疑う基準が当たっていれば、入力の形式を変える（構造化する）案も同じ確認に並べる。
配布スキル `kaizen` の `references/apply.md` にある「2 巡」の基準（呼び出し側で入力の形を読む検査は、別の形の指摘が 2 巡続いたら置き場所を移す）が当たる検査では、その基準をこの 3 回より先に当てる。

## ミューテーションテストの定義

ミューテーションテストの定義を作るかは、判定ごとに `docs/testing.md`「定義を作る対象」の 3 つの条件で決める。ここへ転記しない。
チェックを作ると決めたことは、そのチェックのすべての判定に定義を作る理由にならない。

## kaizen の提案

kaizen が機構（Hook・lint・CI のチェックなど）を提案するときも、提案に効果と費用を書き、同じ基準で作るかを決める。
kaizen の側の基準は、配布スキル `kaizen` の `references/apply.md`「機構を作る前に効果と費用を書く」で定義する。
