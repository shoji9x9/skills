# 回帰 eval の assertion と fixture は、測れるかを書いた時点で確かめる

assertion を「スキルが正しく動けば true になるか」だけで考えて書くと、真偽を実際には測れない形が残る。
そうした eval は Delta に寄与しない。
採点の後の批評で気づくと、測り直す費用を払うことになる。
assertion を書いた時点で次の 7 点を確かめてから確定する。

## 書いた時点で確かめる 7 点

### 区別できるか

baseline（スキルを使わない run）が満たせない、スキル固有の具体的な内容を検査する。
behind を検出する、changelog を見る、といった一般的な振る舞いは baseline も自力で満たすので、差が出ない。
スキル固有の設定パス、正確な述語、固有のコマンド、固有の安全確認を検査し、できれば with と without の両方の出力を `grep` で突き合わせる。

### 到達できるか

その fixture と prompt の求め方で、スキルがその工程まで進めるかを確かめる。
fixture で揃えられるのは、リポジトリ内の前提の成果物だけである。現行アプリの稼働、実際の DB、外部サービスは揃えられない。
外部依存より後の工程を検査しない。正常系の eval を足すときに、この誤りが起きやすい。

リポジトリの外以外にも、到達できない場所がある。
`with_skill` は対象のスキルの成果物だけを被験体へコピーするので、姉妹スキルの `references` の中身は run から読めない。
doc-altitude に従って原本を姉妹スキルの側に置いた取り決めでは、自スキルの `SKILL.md` に残るのは原本のパスと、そこへ任せる判断だけである。
assertion もその粒度で書く。原本を示して判断を任せているかを検査し、原本の中身を述べているかは検査しない。

### 材料が採点入力に入るか

判定に要る成果物が、採点の入力に入るかを確かめる。
`project-files/` に入るのは、許可した拡張子のファイルと、名前で指定した dotfile だけである。対象外のファイルは `project-files-skipped.txt` にも載らない。
`result.json` に入るのは、最後のアシスタントのメッセージだけである。
assertion ごとに、材料がどの採取物に載るかを答える。答えられなければ、採取の範囲か assertion を変える。

### スキルの主な価値を検査しているか

その eval の assertion 群が、そのスキルが存在する理由を 1 本でも検査しているかを見る。
1 本ずつは区別・到達・材料の条件を満たしていても、全部がそろって主な価値の外を測っていることがある。

実例を挙げる。受け取った資産から現行環境を作り直すスキルで、5 本の assertion がすべて DB の設定を復元する推論を検査していた。
下流へ渡す台帳、質問票、引き渡しのメタデータは 1 本も検査していなかった。baseline はこれらを一切作らないのに、Delta に差が出なかった。

ただし、成果物が存在するかどうかは検査しない。
作る側のスキルにとってはほぼ必ず真で、baseline にとってはほぼ必ず偽なので、Delta は大きく出る。しかし測っているのはテンプレートに従ったかであって、判断ではない。
検査するのは、下流が実際に読むフィールドの中身と、そこで下す判断である。
たとえば「もっともらしい成果物を作れたが、実測していない工程があるので完了とは書かない」という判断を検査する。

### 入力が答えを持っていないか

fixture だけでなく、被験体に同梱されるすべてのファイルが、その eval が検査している結論を述べていないかを見る。
判定、分類、あるべき置き場所、「意図的にそう作った」という説明を fixture に書くと、baseline がそれを読んで assertion を満たし、Delta が消える。
fixture に置いてよいのは、下流のプロジェクトに実在しうる記述（調査メモや運用上の但し書き）だけである。
「〜を理由に停止していない」のような否定形の assertion は、「意図的」と書いた 1 行で通ってしまうので、特に注意する。

### 原本と合っているか

assertion が求める挙動がスキルの取り決めに実在するかを、`SKILL.md` と `references/` を開いて確かめる。
fixture に置いた値から逆算して要求を作らない。fixture に番号や項目があっても、スキルがそれを読む取り決めがある証拠にはならない。
実例を挙げる。fixture のヘッダに置いた Issue 番号を取得するよう求めたが、読む側のスキルが導出する項目はヘッダを対象にしていなかった。
その結果、取り決めどおりに動いた run が落ちる誤った判定を、回帰テストに埋め込んだ。

fixture の様式、キー名、型は、その成果物を生成する側のスキルの原本に合わせる。同じ種類の実物の fixture があれば、それを雛形にする。
原本に無いキーを作らず、型も変えない。
実在しない入力への挙動を測る eval は、本番で起きない故障だけを検出し、本番で起きる故障を見逃す。

prompt には、原本から導ける件数やバージョンの値（`FIXED_PROPERTIES` の件数、ツールの `VERSION` など）を書かない。
原本を更新したとたんに eval が別の内容になり、run は件数の食い違いを手がかりに別の方向へ進む。
書くなら「集合が全項目で一致する」のように、値を持たない表現にする。

入力データの意味（返す行の単位、集計値、件数、順序）を述べる assertion は、その値を実際の入力に当てて導く。
書くつもりだった意図のまま書かない。
入力も assertion も同じ人が作るので、食い違いを止める人がいない。正しく読んだ回答が fail し、誤って読んだ回答が pass する採点が、回帰テストに固定される。
SQL の `JOIN` や `GROUP BY`、ページング、フィルタで起きやすい。
入力を後から書き換えたときも、その入力を根拠にしている assertion を同じ変更で導き直す。

### 姉妹スキルの原本で答えられないか

`requires_skills` で設置したスキルは `without_skill` にも入る。
そのため、その原本（`SKILL.md` と `references/`）を読めば答えられる内容を assertion にすると、両方の config が pass する。
検査するのは、対象のスキルの側にだけ書いた判断にする。

## 到達できるかを確かめる方法

assertion を 1 本ずつ取り上げ、その要求をプロンプトのどの文が引き出すかを問う。引き出す文を引用して並べた対応表を書き出す。
頭の中で問うだけで済ませると、抜けても誰にも見えず、run を捨ててから気づくことになる。
引用を書けない assertion は、プロンプトに問いを足して到達できるようにするか、assertion を削る。
表を書き終えてから run を実行する。
assertion を弱めるのではなく、プロンプトで問う形にする。
プロンプトが問うていない話題に自分から触れることを期待すると、検査しているのは取り決めの知識ではなく冗長さになり、run ごとに結果が揺れる。
プロンプトを 1 語でも変えたら、追加・変更した assertion だけでなく、すべての assertion の対応表を作り直す。過去の run が pass したことは、到達できる証拠にならない。

対応表は eval の `reachability`（`{ assertion, prompt_quote }` の配列）として残す。
`scripts/gates/check-eval-reachability.js` が pre-commit と CI で、`prompt_quote` が prompt の部分文字列であることと、`assertion` がその eval の assertions に実在することを確かめる。
機械のチェックが見るのは部分文字列が実在するかまでなので、次の 4 点はレビューで確かめる。どれも、実行してからやり直した実例がある。

- 1 つの assertion で 1 つのことを主張する。複数の主張を束ねた assertion は、1 つの主張の引用だけでチェックを通り、引き出す文の無い主張だけが落ち続ける。
- 「選ぶ」「どちらか」を求めるなら、それぞれの選択肢を成り立たせる材料が prompt にあるかを見る。材料が片方にしか無いと正解が 1 つに決まり、選ぶための言葉が出てこない。
- 下流の工程や他のスキルの分担を問う assertion は、その工程に触れる文が prompt にあるときだけ置く。次の工程が何を読むかは、prompt がその工程を話題にしない限り引き出されない。
- 取り決めを満たす正しい答えが複数あるときは、全部が通るかを確かめる。1 つの手順だけを書いた assertion は、原本が許すもう一方の手順で答えた run を落とす。

使い捨てのプロジェクトが repo でないなど、外部の前提のせいで実行を求めると早く止まってしまう場合は、手順や判断を検査する eval を dry-run の形で問う。

## 問う形にすると差が出なくなることがある

到達と区別は両立しないことがあるので、プロンプトを強めたら両方を測り直す。
assertion に固有の判断の軸をプロンプトで直接問うと、その判断の軸、分類の語、列挙の対象をプロンプトが渡すことになる。baseline はそれを埋めて pass する。
プロンプトを強めたら、`with_skill` が到達することに加えて、`without_skill` を 1 run 実行して差が残ることを実測してから確定する。
範囲の決め方は `docs/skill-development.md` の「実走の既定スコープ」で定義する。

- 上位の概念を引用していても、到達できることはある。`with_skill` が実測で到達していれば、それが到達できる証拠であり、強める理由にならない。
  強める前に、その assertion がいまの prompt で到達できていないことを run で確かめる。レビューで読んだだけで到達できないと判断しない。
- 実例を挙げる。「ベンダー資料 3 種を個別に分類」という prompt を、「受領済み／導出可能／不足／該当なしで 1 件ずつ判定して」と直接問う形に変えた。
  すると同じ executor の `without_skill` が 2/4 から 4/4 になり、差が消えた。
  上位の概念を引用したままの元の prompt では、`with_skill` が 3/3 で pass し、`without_skill` が fail していた。到達と区別が両立していた。
- 強めた prompt で差が消え、元の prompt にも戻せないなら、その assertion が後退の検出のためのものであることを `evals/<name>/README.md` に書く。その assertion は Delta に寄与しない。

## 手がかりを消しても差が出ない項目

手がかりを消しても差が出ないなら、その項目はこの eval では測れないと判断する。
差が出ない原因を、fixture に答えが書いてあることだけに決めつけない。
結論が出来事の事実そのものから導ける場合がある。たとえば「同じ成果物を 5 回手で作り直した」という事実から「コードにすべき」という結論が導ける。
その事実は学びが成り立つのに欠かせず、削れない。入力をどう書き直しても差は戻らない。
fixture をさらに削るのではなく、検査の項目をスキル固有の手順、語、成果物（設定パス、固有のコマンド、記録先の様式）に替える。
測れない項目を残すなら、Delta ではなく後退の検出が目的であることを benchmark に書く。

区別できる assertion と、読み取りの隔離（`without_skill` がこのリポジトリのスキルの資産を読めないこと）は別の仕組みで、両方が要る。
assertion をスキル固有にしても、隔離されずに資産を読める状態では baseline がそれを満たす。
隔離と、資産を読んだかの判定は、ハーネスがデフォルトで行う（`docs/skill-development.md` の「eval 実行の隔離（必須）」）。

## fixture に置く成果物は、誰が書くかで分ける

同梱の決定論的なツールが書く成果物は、手で書かず、そのツールを実行した出力をそのまま置く。
`axis-diff.mjs` の `axes.json`、`coverage-expand.mjs` が書き戻す `conformance`、特性の照合の出力がこれに当たる。
もっともらしく手で書いた JSON は構文が正しいので、どのチェックにも掛からない。
そのまま、ツールの仕様に反する組み合わせ（値が分かれない軸を `variable` に置くなど）を fixture に固定してしまう。

スキル（LLM）が書く成果物（`metadata.json` の宣言値、`porting.md` など）は、手で書いてよい。

生成した出力を要約や省略で置き換えない。要約が要るなら別のファイルに書き、成果物には実際の出力を置く。

fixture を作った時点でそのツールに 1 回通し、終了コードと主な件数が一致することを確かめる。
同じ fixture の他のファイル（宣言値を持つ `metadata.json` など）とも、件数と状態の集合を突き合わせる。

## 採点（grading）の規律

判定は、位置ではなく対象のテキストで対応づける。
assertion を 1 本でも追加・削除・並べ替えしたら、判定のリストを配列の index ではなく assertion のテキスト（または安定した id）で対応づけ直す。
生成する前に対応表を突き合わせ、一致しなければ中断する。
`summary.passed` が変わらないことを、正しい根拠にしない。挿入によるずれは件数を変えないので、合計では見つからない。
実例を挙げる。index 2 に assertion を挿入したら以降の判定が 1 つずつずれ、正しく説明できていた項目を FAIL、一度も触れていない項目を PASS として記録した。
pass の件数は変わらず、`summary` では異常が見えなかった。

必要な語句が出力にあるだけで pass にしない。
出力の中に原本と食い違う結論や反対の命題があれば、関係する assertion を fail にする。
assertion ごとに局所的に照合するだけで採点すると、後半で取り決めを否定していても全項目が緑になり、スコアが品質を実際より高く見せる。
判定できないときに失敗として扱うこと、停止すること、否定することを検査する eval には、「回答の中で食い違う判断をしていない」ことを観測できる assertion を 1 本置く。

## 判定の条件を変えたら、すべての入力形式を更新する

検出の処理のしきい値、照合のキー、判定の条件を変えたら、その処理に入るすべての入力形式を意味で列挙する。
fixture、検出されることの確認、誤検知しないことの確認、境界のケース、eval の assertion を同じ変更で更新し、形式ごとに実行して、期待する終了コードまで確かめる。
変えた実装の行から参照先をたどるだけでは、同じ意味を別の形式で表した fixture（構造化したログ、別のエージェントの記録形式など）と、古いしきい値を前提にした評価の文が抜ける。
