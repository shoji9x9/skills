# 回帰 eval のアサーション・fixture は「測れるか」を書いた時点で検証する

アサーションを「**スキルが正しく動けば true になるか**」だけで書くと、真偽を**実際に測れない**形が残り、
その eval は Delta に寄与しない空振りになる。書いた時点で次の 4 点を確認してから確定する
（採点後の批評では、測り直しのコストを払ってからしか気づけない）。

- **弁別**: baseline（スキル無し）が満たせない skill 固有の具体を検査項目にする。一般的な振る舞い
  （behind を検出する・changelog を見る等）は baseline も自力で満たすため弁別しない。スキル固有の設定パス・
  正確な述語・固有コマンド・固有ガードを検査し、可能なら with / without 両 output を `grep` で突き合わせる。
- **到達**: その fixture でスキルがそこまで到達できるかを確認する。fixture で揃えられるのはリポジトリ内の
  前提成果物だけで、現行アプリの稼働・実 DB・外部サービスは揃えられない。**外部依存より先の工程を検査項目にしない**
  （正常系 eval を足すときに踏みやすい）。
- **材料**: 判定に要る成果物が採点入力に入るかを確認する。`run-skill-eval.sh` の `project-files/` は拡張子で
  絞り込むため、スキルが対象プロジェクトへ生成する言語（`.ts` / `.sql` 等）が対象に入っているかを見る。
  `project-files-skipped.txt` が 0 行でないときは「無い ＝ 作らなかった」と読まない。
- **入力が答えを持っていないか**: fixture（設定・成果物・そのコメント）が、その eval の検査している結論を
  述べていないかを見る。判定・分類・あるべき置き場所・「意図的にそう作った」旨を fixture に書くと、
  **ベースラインがそれを読んで assertion を満たし Delta が消える**。fixture に置いてよいのは下流プロジェクトに
  実在しうる記述（調査メモ・運用上の但し書き）だけ。否定形の assertion（「〜を理由に停止していない」等）は
  「意図的」の 1 行で通ってしまうため特に危うい。

**到達性の検証手段**: assertion を 1 本ずつ「この要求は**プロンプトのどの文が引き出すか**」と自問し、答えられるか確かめる。
答えられないものはプロンプト側に問いを足して到達可能にするか、assertion を落とす。**assertion を弱めるのではなく問う形にする**
（プロンプトが問うていない話題の自発的言及に賭けると、検査しているのは契約知識ではなく冗長さになり、run 間で揺れて flaky になる）。

**cue を消しても弁別しないなら、その項目はこの eval では測れないと結論する。** 弁別ゼロの原因を「fixture に答えが
書いてある」だけに決め打ちしないこと——結論が**事象の事実そのもの**から演繹できる場合（例「同じ成果物を 5 回手で
再現した」→「コード化すべき」）、その事実は学びの成立に不可欠で削れないため、入力をどう書き直しても弁別は戻らない。
fixture をさらに削るのではなく、検査項目を skill 固有の手順・語彙・成果物（設定パス・固有コマンド・記録先の様式）へ
替える。測れない項目を残すなら、Delta ではなく**後退検知**が目的であることを benchmark に明記する。

弁別は read 隔離（`without_skill` が本リポジトリのスキル資産を読めないこと）とは**別機構**で、両方が要る。
アサーションを skill 固有にしても、read 汚染下では baseline がそれを満たす。隔離と汚染判定はハーネスの既定挙動
（`docs/skill-development.md`「eval 実行の隔離（必須）」）。
