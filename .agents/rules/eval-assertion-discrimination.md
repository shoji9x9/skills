# 回帰 eval のアサーション・fixture は「測れるか」を書いた時点で検証する

アサーションを「**スキルが正しく動けば true になるか**」だけで書くと、真偽を**実際に測れない**形が残り、
その eval は Delta に寄与しない空振りになる。書いた時点で次の 6 点を確認してから確定する
（採点後の批評では、測り直しのコストを払ってからしか気づけない）。

- **弁別**: baseline（スキル無し）が満たせない skill 固有の具体を検査項目にする。一般的な振る舞い
  （behind を検出する・changelog を見る等）は baseline も自力で満たすため弁別しない。スキル固有の設定パス・
  正確な述語・固有コマンド・固有ガードを検査し、可能なら with / without 両 output を `grep` で突き合わせる。
- **到達**: その fixture と prompt の要求形でスキルがそこまで到達できるかを確認する。fixture で揃えられるのはリポジトリ内の
  前提成果物だけで、現行アプリの稼働・実 DB・外部サービスは揃えられない。**外部依存より先の工程を検査項目にしない**
  （正常系 eval を足すときに踏みやすい）。
  **到達不能はリポジトリの外だけにあるのではない**——`with_skill` は**対象スキルの成果物だけ**を被験体へコピーするため、
  姉妹スキルの `references` の中身は run から読めない。doc-altitude に従って正本を姉妹スキル側へ置いた契約は、
  自スキルの `SKILL.md` に残るのが「正本のパスと、そこへ委ねる判断」だけなので、**assertion もその粒度で書く**
  （「正本を示して委ねているか」を検査し、「正本の中身を述べているか」を検査しない）。
- **材料**: 判定に要る成果物が採点入力に入るかを確認する。`project-files/` は拡張子ホワイトリストと名前指定の
  dotfile だけで、対象外は `project-files-skipped.txt` にも載らない。`result.json` は最終アシスタントメッセージだけである。
  assertion ごとに材料がどの採取物へ載るかを答え、答えられなければ採取範囲か assertion を変える。
- **主価値**: その eval の assertion 群が、**そのスキルが存在する理由**を 1 本でも検査しているかを見る。
  1 本ずつは弁別・到達・材料を満たしていても、**全部が揃って主価値の外**を測っていることがある
  （実例: 受領資産から現行環境を建てるスキルで、5 本すべてが DB 設定の復元推論を検査し、
  下流へ渡す台帳・質問票・引き渡しメタデータを 1 本も検査していなかった。baseline はそれらを一切作らないのに Delta に出ない）。
  ただし**「成果物が存在するか」を検査項目にしない**——生産側スキルにとってほぼ自明に真、baseline にとって自明に偽で、
  Delta は大きく出るが測っているのはテンプレ遵守であって判断ではない。
  検査するのは**下流が実際に読むフィールドの中身**と、**そこで下される判断**にする
  （例: 「もっともらしい成果物を作れたのに、実測していない工程があるので完了を名乗らない」）。
- **入力が答えを持っていないか**: fixture だけでなく被験体に同梱される全ファイルが、その eval の検査している結論を
  述べていないかを見る。判定・分類・あるべき置き場所・「意図的にそう作った」旨を fixture に書くと、
  **ベースラインがそれを読んで assertion を満たし Delta が消える**。fixture に置いてよいのは下流プロジェクトに
  実在しうる記述（調査メモ・運用上の但し書き）だけ。否定形の assertion（「〜を理由に停止していない」等）は
  「意図的」の 1 行で通ってしまうため特に危うい。
- **正本整合**: assertion が要求する挙動が**スキルの契約に実在する**かを、契約文（`SKILL.md` /
  `references/`）を開いて確かめる。**fixture に置いた値から逆算して要求を作らない**——
  fixture に番号・項目があることは、スキルがそれを引く契約の証拠ではない
  （実例: fixture のヘッダに置いた Issue 番号の取得を要求したが、消費側の導出項目は
  ヘッダを対象にしておらず、契約に忠実な run が落ちる偽陰性を回帰テストに埋め込んだ）。
  fixture の様式・キー名・型は、その成果物を**生成する側のスキル**の正本に合わせる
  （同種の実物 fixture があるならそれを雛形にする）。正本に無いキーを発明せず、型も変えない。
  実在しない入力に対する挙動を測る eval は、本番で起きない故障だけを検出し、本番で起きる故障を見逃す。
  **prompt に正本から導ける件数・バージョン値を書かない**（`FIXED_PROPERTIES` の件数・ツールの `VERSION` 等）。
  正本を更新した瞬間に eval が別物になり、run は件数の不一致を手がかりに別の筋へ寄る。書くなら「集合が全項目一致」のように値を持たない表現にする。
  **入力データの意味論（返却行の単位・集計値・件数・順序）を述べる assertion は、その値を入力に当てて導出する。**
  書くつもりだった意図のまま書かない——入力も assertion も同じ書き手が作るため齟齬は誰にも止められず、
  **正しく読んだ回答が fail し誤読が pass する逆転採点**として回帰テストに固定される（SQL の `JOIN` / `GROUP BY`、ページング、フィルタで踏みやすい）。
  入力を後から書き換えたときも、その入力を根拠にしている assertion を同じ変更で導出し直す。
- **姉妹スキルの正本は弁別材料にならない**: `requires_skills` で設置したスキルは `without_skill` にも入るため、
  その正本（`SKILL.md` / `references/`）を読めば答えられる内容を assertion にすると両 config が pass する。
  検査するのは**対象スキル側にだけ書かれた判断**にする。

**到達性の検証手段**: assertion を 1 本ずつ「この要求は**プロンプトのどの文が引き出すか**」と問い、**引き出す文を引用して並べた対応表を書き出す**
（内心の自問で済ませない——抜けても誰にも見えず、run を捨ててから気づくことになる）。引用を書けない assertion はプロンプト側に問いを足して到達可能にするか、assertion を落とす。
**表を書き終えてから run を回す**。**assertion を弱めるのではなく問う形にする**
（プロンプトが問うていない話題の自発的言及に賭けると、検査しているのは契約知識ではなく冗長さになり、run 間で揺れて flaky になる）。
プロンプトを 1 語でも変えたら、追加・変更した assertion だけでなく**全 assertion**の対応表を作り直す。過去 run の pass は到達性の証拠ではない。
対応表は内心ではなく eval の `reachability`（`{ assertion, prompt_quote }` の配列）として残し、`scripts/check-eval-reachability.js` が
pre-commit と CI で「`prompt_quote` が prompt の部分文字列であること」「`assertion` がその eval の assertions に実在すること」を検査する。
**機械検査が見るのは部分文字列の実在までなので、次の 4 点はレビュー側で担保する**（いずれも実走してから取り直した実例がある）。

- **1 assertion 1 主張**。複数主張を束ねた assertion は 1 主張ぶんの引用で検査を通り、引き出す文の無い主張だけが落ち続ける。
- **「選ぶ」「どちらか」を要求するなら、選択肢それぞれを立たせる材料が prompt にあるか**を見る。材料が片方しか無いと正解が一意に決まり、選択の語彙は出てこない。
- **下流工程・他スキルの分担を問う assertion は、その工程に触れる文が prompt にあるときだけ置く**。「次の工程が何を読むか」は prompt がその工程を話題にしない限り引き出されない。
- **その契約を満たす正しい答えが複数あるとき、全部通るか**を確かめる。1 つの手順だけを書いた assertion は、正本が許すもう一方の手順で答えた run を落とす。
使い捨てプロジェクトが repo でないなど外部前提により実行要求が早期停止を招く場合、手順・判断を検査する eval は dry-run 形で問う。

**ただし「問う形にする」と弁別が壊れうる。到達と弁別はトレードオフなので、強めたら両方を測り直す。**
assertion 固有の判断軸を prompt で直接問うと、**その判断軸・分類語彙・列挙対象を prompt が渡す**ことになり、
ベースラインがそれを埋めて pass する。プロンプトを強めたら、`with_skill` の到達だけでなく
**`without_skill` を 1 run 取り、弁別が残ることを実測してから確定する**（`docs/skill-development.md`「実走の既定スコープ」）。

- **上位概念の引用が必ず到達不能なわけではない。** 引用が上位概念でも `with_skill` が実測で到達しているなら、
  それが到達性の証拠であり、強める理由にならない。強める前に、その assertion が
  **現行 prompt で到達できていないこと**を run で確かめる（レビューの読みだけで到達不能と判定しない）。
- 実例: 「ベンダー資料 3 種を個別に分類」を「受領済み／導出可能／不足／該当なしで 1 件ずつ判定して」と直接問う形へ
  変えたところ、同一 executor の `without_skill` が 2/4 → **4/4** になり弁別が消えた。上位概念の引用のままの旧 prompt は
  `with_skill` 3/3 pass・`without_skill` fail で、到達と弁別を両立していた。
- 強めた prompt で弁別が消え、かつ元の prompt に戻せないなら、その assertion は**後退検知**であることを
  `evals/<name>/README.md` に明記する（Delta には寄与しない）。

**cue を消しても弁別しないなら、その項目はこの eval では測れないと結論する。** 弁別ゼロの原因を「fixture に答えが
書いてある」だけに決め打ちしないこと——結論が**事象の事実そのもの**から演繹できる場合（例「同じ成果物を 5 回手で
再現した」→「コード化すべき」）、その事実は学びの成立に不可欠で削れないため、入力をどう書き直しても弁別は戻らない。
fixture をさらに削るのではなく、検査項目を skill 固有の手順・語彙・成果物（設定パス・固有コマンド・記録先の様式）へ
替える。測れない項目を残すなら、Delta ではなく**後退検知**が目的であることを benchmark に明記する。

弁別は read 隔離（`without_skill` が本リポジトリのスキル資産を読めないこと）とは**別機構**で、両方が要る。
アサーションを skill 固有にしても、read 汚染下では baseline がそれを満たす。隔離と汚染判定はハーネスの既定挙動
（`docs/skill-development.md`「eval 実行の隔離（必須）」）。

## fixture に置く成果物は出自で分ける

- **同梱の決定論ツールが書く成果物**（`axis-diff.mjs` の `axes.json`、`coverage-expand.mjs` が書き戻す `conformance`、特性照合の出力）は
  **手書きせず、そのツールを実行して得た出力をそのまま置く**。もっともらしい手書きの JSON は妥当な構文を持ち、どの検査にも掛からないまま
  ツールの契約に反する組み合わせ（値が割れない軸を `variable` に置く等）を fixture へ固定する。
- **スキル（LLM）が書く成果物**（`metadata.json` の宣言値・`porting.md` 等）は手書きでよい。
- 生成した出力を要約・省略して置き換えない。要約が要るなら別ファイルに書き、成果物そのものは実出力を置く。
- fixture を作った時点でそのツールに 1 回通し、exit code と主要な件数が一致することを確かめる。
  同じ fixture 内の他ファイル（宣言値を持つ `metadata.json` 等）とも件数・状態集合を突き合わせる。

## 採点（grading）の規律

- **判定は位置ではなく対象のテキストで対応づける。** assertion を 1 本でも**追加・削除・並べ替え**したら、
  判定リストは配列 index ではなく assertion のテキスト（または安定した id）をキーに対応づけ直し、
  生成前に対応表を突き合わせて不一致なら中断する。
  **`summary.passed` が変わらないことを正しさの根拠にしない**——挿入によるズレは件数を保存するため
  合計値では検出できない（実例: index 2 への挿入で以降の判定が 1 つずつずれ、正しく説明できていた項目を
  FAIL、一度も触れていない項目を PASS として記録した。pass 件数は変わらず `summary` では異常が見えなかった）。
- **必要語句の存在だけで pass にしない。** 出力内に正本と矛盾する結論・反対命題があれば、
  関連 assertion を fail にする。assertion ごとの局所照合だけで採点すると、後段で契約を否定していても
  全項目が緑になり、スコアが品質を過大表示する。
  fail-closed・停止・否定を検査する eval には、「回答内で矛盾する判断をしていない」ことを
  観測可能な assertion として 1 本置く。

## 判定条件を変えたら入力形式を横断して更新する

検出器の**閾値・照合キー・判定条件**を変えたら、その検出経路へ入る**全入力形式**の fixture、
陽性・陰性・境界ケース、eval assertion を意味論で列挙して同じ変更で更新し、各形式を実行して
期待する終了コードまで確認する。
変更した実装行から参照先を追うだけでは、同じ意味論を**別形式**で表した fixture
（構造化ログ・別エージェントの記録形式など）と、旧しきい値を前提にした評価文が漏れる。
