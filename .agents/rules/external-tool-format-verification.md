# 外部ツール設定・API フォーマットの一次情報検証

配布スキル（`skills/<name>/`）が Codex / GitHub Copilot / `gh` / GitHub API など**外部ツールの
設定ファイル・Hook・API レスポンス形状**を例示・前提にする箇所は、自エージェントの記憶で断定せず、
**公式一次ドキュメントで構造とフィールド意味論を検証**してから記述する。

- 構造（入れ子・キー名・必須/任意）だけでなく、**フィールドの意味論**（matcher が正規表現か・空文字が
  match-all か・特定イベントで無視されるか、enum の許容値、null の意味）まで確認する。
- **設定を書いた後、実際に有効になるまでのライフサイクル**も確認する。feature flag、trust / approval、
  再起動・再読み込みが必要ならセットアップの完了条件へ含め、定義変更で信頼や承認が失効する場合は
  変更後の再レビューまで手順と回帰評価に含める。「パースできる」と「実行される」を同一視しない。
- CLI / API の出力 enum を部分列挙しない。ツールが提供する**正規化フィールド**（例: `gh pr checks` の
  `bucket`）があればそれを優先し、全許容値を `--help` / 公式ドキュメントで確認する。
- **分岐を書いたらその分岐が成立する状態で実測する。** 「0 件」「該当なし」「失敗時」の振る舞いは
  `--help` / 公式ドキュメントに書かれないことが多く、正常系の実測から推測すると外れる
  （例: `gh pr checks --required` は必須チェック 0 件のとき空配列ではなく stderr メッセージ＋非 0 終了）。
  自リポジトリでその状態を作れないときは、状態を持つ公開リポジトリを探して実測する。
- 外部ツールのフラグを分岐の根拠にするなら、名前から推定せず、判定したい軸そのものに実際に効くかを実測する。回帰テストの green は誤った意味論を固定しうるため代替にならない。
- 手順として書いたコマンド列は通しで 1 回実走し、各コマンドの出力・終了コード・空になる条件を確かめる。破壊的操作の直後に実行環境が壊れないことと、安全側の既定が通常運用で成立することも確認する。
- 検証に使った一次ドキュメントの URL を該当箇所に併記する（例示の根拠を残し、次回の再検証を容易にする）。
- 自エージェント（Claude Code）と他エージェント（Codex / Copilot）で**構造が同じだと仮定しない**。
  各エージェントの公式ドキュメントを個別に確認する。
