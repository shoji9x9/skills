# 外部ツール設定・API フォーマットの一次情報検証

配布スキル（`skills/<name>/`）で、Codex・GitHub Copilot・`gh`・GitHub API など外部ツールの設定ファイル・Hook・API の応答の形を例に挙げたり前提にしたりするときは、エージェントの記憶で書かない。
公式のドキュメントで、構造と各フィールドの意味を確かめてから書く。

- 構造（入れ子・キー名・必須か任意か）だけでなく、フィールドの意味も確かめる。
  たとえば matcher が正規表現か、空文字がすべてに一致するか、特定のイベントでは読まれないかを確かめる。
  enum に許される値と、null が何を表すかも確かめる。
- 設定を書いてから実際に有効になるまでの流れも確かめる。
  feature flag、trust や承認、再起動や再読み込みが要るなら、セットアップの完了条件に含める。
  定義を変えると信頼や承認が無効になる場合は、変更後に再び承認を得るところまで、手順と回帰評価に含める。
  設定を読めることと、実行されることは別に確かめる。
- CLI や API が出力する enum の値を、一部だけ挙げて判定しない。ツールが正規化したフィールド（例: `gh pr checks` の `bucket`）があればそれを使い、許される値をすべて `--help` か公式のドキュメントで確かめる。
- 分岐を書いたら、その分岐に入る状態を作って実測する。
  「0 件」「該当なし」「失敗したとき」の振る舞いは `--help` や公式のドキュメントに書かれていないことが多く、正常な場合の実測から推測すると外れる。
  たとえば `gh pr checks --required` は、必須チェックが 0 件のとき空の配列を返さず、stderr にメッセージを出して 0 以外で終了する。
  このリポジトリでその状態を作れないときは、その状態にある公開リポジトリを探して実測する。
- 外部ツールのフラグを分岐の根拠にするなら、名前から推測せず、判定したい軸にそのフラグが実際に作用するかを実測する。
  回帰テストが通っても、誤った意味のまま固定されているだけのことがあるので、実測の代わりにはならない。
- 手順として書いたコマンドの並びは、最初から最後まで 1 回実行し、各コマンドの出力・終了コード・出力が空になる条件を確かめる。
  破壊的な操作の直後に実行環境が使えなくならないことと、安全のためのデフォルトの設定が通常の運用で成り立つことも確かめる。
- 確かめるのに使った公式のドキュメントの URL を、その箇所に書く。例の根拠が残り、次に確かめ直すときに使える。
- Claude Code と他のエージェント（Codex・Copilot）で構造が同じだと仮定しない。エージェントごとに公式のドキュメントを確かめる。
