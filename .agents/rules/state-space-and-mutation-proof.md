# 照合・分岐の状態空間を列挙し、テストが効くことを変異で実証する

「分岐を新設したら状態を作って実測する」は `AGENTS.md` の一般規律だが、**何を状態空間に入れるか**と
**そのテストが実際に効いているか**は繰り返し落ちている（同じ根本原因の再発が 4 回・5 回記録されている）。
検出器・照合器・集計・ゲートを書く／直すときは、ここを機械的に通す。

## 1. 検査を書く前に決めること

実装を始める前に次の 4 つを 1 行ずつ宣言する。後から直すと、穴が形式の数だけ出る。

- **入力を構造化するか、自由記述を解析するか。** 人が書く Markdown の表・連結文字列を解析する検査は、
  **区切り・境界・重複・空欄**の 4 軸それぞれに穴が開く（1 つの PR で 16 件出た記録がある）。
  同じ情報を構造化（列を配列で持つ・鍵をタプルで持つ）すれば、その 4 軸の穴は最初から存在しない。
  **人が読む表と検査が読む構造を分ける**選択肢（表は写し、JSON を正本にする）を、二重管理のコストと
  解析の穴を塞ぎ続けるコストで比べて決める。自由記述を選ぶなら 4 軸を表にしてから実装する。
  レビューが同じクラスを 3 巡以上指摘したら、個別の修正ではなく**入力形式を疑う**。
- **一致の単位。** 識別子 / トークン / 完全一致 / 前方一致のどれかを宣言する。部分文字列を使うなら
  **一方が他方の一部になる入力**を境界テストに必ず入れる。**連結で作る鍵は、材料側で区切り文字を禁じるか
  構造化する**（鍵が利用者に見える id になるなら、符号化ではなく材料側で弾く。符号化すると id が読めなくなる）。
- **証拠に採るフィールド。** 「取れる文字列を全部集めて照合する」形は、書いた内容と読んだ内容・名前と名前の
  前方一致・記録の不在と記録された不在を、同じ証拠として扱う。**採用するフィールドと採用しないフィールドを
  意味論で表にし、採用しない側にも標的インスタンスを 1 件ずつ置く**（採用側だけのテストは、
  軸そのものを取り違えても緑のまま通る）。検出したい事象を代理指標へ置き換えるなら、
  **その近似が生む誤りの向き（偽陽性・偽陰性）を 1 行ずつ書き出してから**実装する。
- **期待集合の出所。** 集合を突き合わせる検査は、期待集合を**観測の記録ではなく宣言（仕様・設定・条件）から**
  構成する。出所を 1 行で書いたとき「観測した一覧」になるなら、その検査は欠落を検出できない
  （採らなかった組は期待値からも消え、穴 0 件で exit 0 になる）。宣言から期待集合を作れない入力
  （軸が空・区切り文字入り・重複）は合格に倒さず落とす。期待集合に対する不足は、他の欠陥と同じ出口
  （理由付きの免除宣言）へ流し、専用の抜け道を足さない。

## 2. 状態空間に入れるもの

- **軸は「判定に使う全ての入力」で引き、各軸に必ず「読めない」（欠落・空・型崩れ・未知の値）を含める。**
  判定式に現れる識別子を機械的に列挙して軸にする——片方の入力の欠落だけを列挙して、もう片方の欠落を落とさない。
  判定に効く入力を「形の不備として報告する項目」の扱いで軸から外すと、その値が読めない入力が素通りする。
- **判定に使う「値」だけでなく「キーの材料」を入れる。** id・照合キー・論理名の
  **欠落・空文字・重複・型崩れ**を列挙する。キーを文字列化して索引にする実装
  （`String(x)` / テンプレートリテラル / `Map` の key）は、欠落が `"undefined"` という
  **有効なキー**へ化けて全要素が 1 キーに潰れる。1 件のデータが全件を満たして
  fail-closed なゲートが素通りするので、**欠落を先に弾いてから索引に入れる**。
  「キーが潰れて 1 件が全件を満たさない」ことを陰性コントロールで実測する。
- **識別子は値の一致だけでなく「出どころの名前空間」も軸にする。** 同じキーへ複数の書き手が値を入れる
  レジストリでは、書き手ごとに定義域が違いうる（機能 slug と部品 slug 等）。名前空間が違う値は
  「一致しないので対象外」として**黙って合格側へ落ちる**ので、不一致を検出して対象へ倒す分岐を消費側に置く。
- **一意性・スコープを要求する規則は、その「範囲」自体を軸にする**（兄弟 / 親 / 全体）。
  部分スコープの一意性は、参照が名前で行われる限り深さが増えた瞬間に壊れる。
- **分岐が「入力の値」ではなく「入力の位置」で決まる器は、位置の軸を先に列挙する。**
  字句なら「直前に来られるトークンの種類を全部」、チェーン照合なら「先頭・途中・末尾」。
  軸を表にして `test.each` の第 1 引数へ残すと、埋まっていないセルが読める。
- **件数を報告する集計は、定義式（例: 項目数 × インスタンス数）をコード上の 1 箇所で表現する。**
  例外要素を個別に加算すると、定義から乖離しても型検査も既存テストも通る。
- **入力を解析する器（パーサ・走査器・セレクタ照合・設定リーダ）の状態空間は、自分が想定した故障モードではなく
  「その入力の文法が許す形」から列挙する。** 報告された不具合や思いついた壊れ方だけを並べると、
  同じ文法の別の形が丸ごと抜ける。引用符・エスケープ・括弧の中に現れる区切り文字、入れ子、
  スコープを持つ構文、名前が空・非文字列・重複の退化形を、文法の仕様から順に当たる。
  **取りこぼしても例外が出ない器では特に効く**——当たらなかった規則・捨てた入力は出力に現れないので、
  テストが緑でも「見えていない」ことに気づけない。捨てる分岐には必ず件数か理由を出力へ残す。
- **コマンド文字列に字句規則（引用・エスケープ）を当てるなら、その規則が効かない領域を先に列挙する。**
  `#` コメント、heredoc 本文、`case` パターン、`[[ ]]` 内ではシェルの引用規則がそのままは働かない。
  領域の範囲を確定できないなら **fail-closed に倒す**（判定不能を成功扱いにしない）。
- **開始と完了が別イベントになる非同期処理は、時刻で相関させない。**
  レビュー・CI・デプロイの完了通知は、旧対象で開始したものが新対象の開始後に完了しうる。
  完了証跡は commit OID・run の `head_sha`・安定した対象 ID など**開始時の対象と直接相関するキー**で結ぶ。
  時刻は候補を絞る補助に留め、直接相関できない通知を単独証跡にしない。
- **hot path に入るフック・ゲートは、正しさに加えて入力サイズ軸で実測する。**
  文字単位のループ（`${s:0:1}` / `s=${s:1}` の反復）は O(n²) になる。数 KB〜数十 KB の payload で
  レイテンシを測り、特殊文字までまとめて進むチャンク走査にする。

## 3. fail-closed なゲートの両側（落とす入力と通す入力）

- **「落とす入力」と同じ数だけ「通さねばならない入力」を列挙する。** 正規操作の定義はゲートの実装側ではなく
  **守る対象の正本**（テンプレートの説明・`references/` の規約）にあり、実装中に読むのは違反側だけで済んでしまう。
  **正本を開いて「この成果物に対して正規に行われる更新」を書き出し、その 1 つ 1 つを陰性コントロール
  （exit 0 を期待するテスト）にしてから green を根拠にする。** 在りがちなのは、版番号の +1・状態列やフラグの
  その場の更新・空集合への最初の追記・免除や `null` を正規値とする記録・後方互換のための欠落。
  陽性コントロールだけのゲートが「常に落とす実装」と区別が付かないのと同様に、
  **陰性コントロールの無いゲートは「通常運用を止める実装」と区別が付かない**。
- **突き合わせの粒度は、守る対象ごとに正本から決める。** 1 つの粒度（行・要素・ファイル全体）を
  全対象へ当てると、その粒度で正規に変わる対象が誤検出になる。粒度を機械可読な一覧に持たせ、語彙外は fail-closed にする。
- **受理条件は「思いついた故障モード」ではなく値の状態空間の表から決める。** 少なくとも
  「欠落 / `null` / 型違い / 空 / 0・境界 / 1 件 / 複数件」の行を埋める。
  **同梱テンプレートのプレースホルダ値を検査の入力に入れて、落ちることを確かめる**——
  テンプレートは利用者がそのまま提出しうる入力クラスで、値は `0` やプレースホルダ文字列なので、
  「実測値のつもり」で書いた受理条件を素通りしやすい。
- **緩和経路（後方互換・免除・スキップ）を置くなら、通す入力クラスを閉じた集合として列挙し、それ以外を落とす。**
  `if (壊れている) skip` ではなく `if (既知の免除条件) skip; else 判定` と書く。
  緩和条件を広く書くほど安全に見えるが、実際は逆で、緩和経路は未列挙の入力クラスを全部飲み込む。
  緩和経路ごとに「これを通してよい理由」を 1 行で書けるか確認し、書けない入力が通るなら列挙漏れ。
  免除には理由（`reason`）を必須にする。
- **判定を他所へ委譲して自分は落とさない緩和は、「委譲先」も列挙して判定式に含める。**
  正当化の文（「その要素は〜が落とす」）から主語を取り出し、それが検査されているかを見る。
  検査されていなければ、その主語は条件ではなく**前提**で、入力クラスをいくら列挙しても不在は現れない。
  委譲先が**名前で指されている**なら実在を確かめる入力（インベントリ・レジストリ）を判定へ渡し、
  渡されていない実行では緩和を適用しない。委譲先が**将来の実行**なら、実行されない場合の回収経路を
  出力に残す（件数 0 と未実行を同じ見え方にしない）。
- **検出器の過剰検知を直す変更は、それ自体が緩和経路の新設である。** 「いま落ちている入力を通す」だけでなく、
  **その変更で新たに通る入力クラスを閉じた集合として列挙**し、代表を **BLOCK 期待**の回帰ケースとして同じ変更に足す。
- **分類を狭める変更（厳格化）も同じクラスとして扱う。** 狭める前にその分岐が受けていた入力クラスを列挙し、
  **狭めた先の受け皿**（別の分類経路か、fail-closed な判定不能）を同じ変更で用意する。
  受け皿が無いとそのクラスは**違反 0 件・判定不能 0 件の黙った素通り**になり、件数を読む手順でも検出できない。
- **免除・スキップの条件は、判定に使う意味論の単位で書く**（「次の 2 文字」ではなく「次の意味を持つトークン」）。
  字面で切ると、空白・コメント・改行を挟んだ同義の入力が免除側へ落ちる。絞り込みを入れたら、
  **絞った条件が通す入力**を意味論の単位で列挙して 1 件ずつ実測する（止めすぎだけでなく通しすぎも測る）。

## 4. fixture に持たせるもの

- **対象分岐までの全前段ゲートを表にして、各入力を用意する。** 新状態の入力だけを fixture 化すると、
  eval / テストが対象分岐より手前で停止し、**前提不足による停止が成功扱い**になる。
- **fixture には「結論」ではなく一次情報を持たせる。** 期待値を fixture や prompt へ直接書くと
  baseline へ答えが漏れ、根拠を置かなければ推測でも正常系を通れてしまう。
  成果物の値だけでなく、**指定した一次情報を読んで根拠として記録したこと**を独立の assertion で検査する。
  一次情報が無い縮退状態も別ケースにして、推測で正常系へ進まないことを実走する。
- **正本（テンプレート・スキーマ文書）がある入力を取る検査器の fixture は、正本の形から作る。**
  判定に必要な列だけを残した fixture は、実装が別の列を読み始めた瞬間に「実在しない形への振る舞い」を
  固定するテストに変わる。切り詰めた形を測りたいなら、正本の形のケースと**別に**置く。
- **外部ツールの出力を模した fake（stub・fixture・record/replay）は、実測 trace を採ったその実行の中で
  同じ trace から作り直す。** 確認に使っただけで終えない。fake は「いま読んでいるフィールド」ではなく
  **実物が出すレコードの単位**で作り、呼び出しと結果・開始と完了のように**対で出るレコードは対で持たせる**
  （片方だけの fake は、コードが相手側を読み始めるまで緑のまま通る）。
  fake を文字列として埋め込む場合（テンプレートリテラル内のシェルスクリプト等）は、
  **埋め込み先のエスケープ規則を通った後の実バイト列**で 1 度検証する。

## 5. テストが効いていることの示し方

- **境界・分岐のテストは、その判定行を無効化する変異で赤くなることを実証してから green を根拠にする。**
  対象は `skills/*/evals/**` だけでなく `scripts/*.test.js` のユニットテストも含む。
  fixture が分岐へ到達していないテストは、判定行を変異させても green のままになる
  （実例: 「後続見出しで止まる」テストの fixture が空行で始まり、見出し境界の分岐に到達していなかった）。
- **変異実証は列挙の実証ではない。** 全変異が RED になっても、それは書いたテストが判定行に到達している
  証拠でしかない。書かなかった入力クラスはどの変異でも赤くならないので、軸の列挙（§1 / §2）を変異実証の前段に置く。
- **変異実証は両方向に壊れる。** 変異がスイートを壊すと「偽の赤」に、変異が当たらないと「偽の生存」に、
  記録が古いと「偽の実証済み」になる。次の 4 点を毎回確かめる。
  - **合格を終了コードで測らない。** 変異を入れた実行の出力から**走ったテスト件数と落ちたテストの名前**を取り、
    狙った assertion が落ちていることまで確かめる。`Failed Suites` / `no tests` / 収集エラー / import 失敗は
    「テストが効いた」ではなく**「実証できていない」**なので、変異を書き直して取り直す。
  - **変異が当たったことを先に証拠化する。** 変異を当てる処理は `if match: replace` ではなく **`assert` で落とす**。
    複数ファイルへ当てるなら、当てたファイル名と件数を印字し 0 件を FAIL に倒す。走らせる前に `diff` を見て、
    差分が空ならその回は実証ではない。
  - **変異は対象の判定だけを無効化する最小の書き換えにする**（式を `false` に、比較を恒真に）。
    文の構造を壊す書き換えはスイートの起動を壊し、実証と起動失敗が同じ非 0 に潰れる。
    変異させる行（needle）には制御文字を含む行を選ばない——ツールが引数ごと拒否するので、
    その場合は直前の分岐行を変異して同じ経路を無効化する。
  - **赤くなったテスト名を列挙して、その判定行のために書いたケースと突き合わせる。** 一致しないケースは
    **前段の規則で落ちている**ので、前段を通過してその判定行に到達する入力を作り直す。
    直列に並ぶ判定は、後段のテストに「前段を通過する」条件を明示的に持たせる。
- **assertion を書き換えたら、それに対する過去の変異実証は無効。** その回に追加した変異だけでなく、
  **その assertion を守っていた既存の変異**も取り直す。
- **変異の記録は散文のコメントに置かず、再実行できるデータで持つ。** 散文は「当時そうだった」ことしか示さず、
  テストを直した瞬間に検証されない主張になる（実例: 行単位の検査で分岐に混ざった変異を見逃す・
  当たらない変異を「実証」と読みかける・テストを書き換えた後に取り直さず記録だけ残る、の 3 通り。Issue #420）。
  宣言は `scripts/<テスト名>.mutations.json`（`id` / `why` / `file` / `find` / `replace` / `occurrences` /
  `expect_failing`）に置き、`node scripts/check-mutation-proof.js` で取り直す。判定の正本はそのスクリプトで、
  **置換が当たったこと**と**宣言したテストがそれだけ落ちたこと**の両方を見る
  （当たらない変異・宣言外まで落ちる変異は FAIL、実在しないテスト名・基準 run が赤いときは exit 2）。
  手元実測で約 7 分 40 秒（76 変異。70 変異時の CI 実測は 279 秒）かかるため CI の `Lint` ジョブ専任にし、pre-commit には入れない（実行中に対象ファイルを
  書き換えて戻すので、staged な変更と混ざると取り違える）。同時実行はロックで弾くが、**無関係なテスト実行と重ねない**
  ——変異中の中間状態を読んで無関係に赤くなる（実測）。
  **実行器自身を変異させる宣言があるときは、宣言の形を検査するテストを別ファイルへ置く**（同じファイルに置くと、変異中の実行器を読んだ形の検査が毎回落ちて実証と区別できない。実測）。
- **合成 fixture の green は「実装が仕様どおりか」までしか測らない。実データへの判断を出す検出器は、
  実データにラベルを付けて再現率と誤検知率を測ってから出荷する。** ラベルは既存の構造から機械的に取る
  （取れないなら標本数を決めて人が読む）。**「検出器が出した側」だけを読まない。「出していない側」も同数読む**
  ——出した側だけを読むと、測れるのは判定条件が成立しているかだけで、再現率は永久に見えない。
  件数と割合を出し、「N% なら雑音にならない」のような印象で判断しない。分離しなければ**仕様を疑う**
  （Issue やレビューが方式を指定していても、測定結果を添えて方式変更を提案する）。
- **無条件に行っていた処理をガード付きへ置き換えたら、ガードが偽になる入力を退行ケースとして同じ変更に足す。**
- **既存実装から条件をコピーして「揃える」ときは、参照元と新実装の出力の性質を突き合わせる。**
  検出（真偽を返す）と変換（文字列を返す）では、同じ述語でも境界の要求が変わる。
  一致しなければ境界条件を入力の状態空間から列挙し直す。**「揃えた」を正しさの根拠にしない。**
- テストケースは、流用元に書かれた分岐からではなく**入力の状態空間**から逆引きする。

## 6. レビュー指摘は故障クラスとして掃き出す

レビュー指摘を適用するときは、直す前にその指摘を**故障クラスへ一般化**し、同じファイル・同じ関数内を
そのクラスで grep して掃き出してから直す。1 箇所だけ直して「対応済み」としない。
探した範囲と見つかった件数を返信に書く（同一ファイル内の同型分岐を取りこぼして、
レビュー 1 往復ぶんの手戻りになった記録が複数ある）。

- **grep の範囲は指摘されたファイルに限らず、同じ PR で自分が新設したコード全体に掛ける**
  （指摘は 1 インスタンスしか報告しないが、同じ PR の他のファイルに同型が残っていることが多い）。
- **指摘された 1 例を近似で塞がず、条件そのものへ戻す。** 否定先読みのような字面の回避は、
  同じ意味の別表記（`.` / `@` 等）で再び抜ける（§3 の「免除は意味論の単位で書く」と同じ形）。
- **修正が新たに生む状態と、新しく導入した語彙を読む消費側を、同じ変更の中で列挙してから返信する。**
  実行可能なコードなら状態を作って実測する。文書契約では「実測」の代わりに**全分割を表に書き出し、
  各行がどの記述で拾われるかを 1 行ずつ対応づける**（拾えない行が残るなら未完）。
